<objective>
**As a** BombVault user, **I want** the file-set API to accept, validate, refuse, and serve my tree selection with the same discipline the container panel already enforces, **so that** a bad or empty selection can never silently change what a backup covers — and an old snapshot of a reshaped set still restores.

This plan lands the HTTP boundary and the trust edges around plan 01's compile: the additive `selectedPaths` pointer field on PATCH /api/files/sets/{id} (D-04) with per-entry containment, the 64-entry cap, atomic rejection, the D-06 empty-selection refusal (a NEW sentinel with the files-specific DELETE-orienting message, reusing the container's `empty-selection` code for uniform UI routing — research Open Question 2 recommendation), the Pitfall-2 layer-1 path-change clear, the additive `FileSetView`/api.ts wire fields (D-04), and the D-08 restore guard wired through the one `mapRestorePaths` implementation.

Purpose: nothing may lean on the compile until the write path enforces the invariants the compile assumes (canonical flat set, anchored entries, never-empty).
Output: PATCH boundary + view field + TS mirror + restore guard, all pinned by tests.
</objective>
