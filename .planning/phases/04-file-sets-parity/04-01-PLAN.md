<objective>
**As a** BombVault user, **I want to** a file set's tree selection to reach restic as multiple positional roots through the same flat persistence the container tree uses, **so that** narrowing a set to its live branches changes exactly what the next snapshot contains — with sets I never touch backing up byte-identically to today.

This plan is the phase tracer: the thinnest end-to-end path at the engine level (store column v101 → owned setter → compile step → orchestrator → restic argv), proven by tests before any HTTP or UI leans on it (the Phase 1 keystone pattern). It lands RESEARCH Pitfall 1's correction explicitly: D-01's "orchestrator unchanged" is true of the `FilesRestic` interface but false of the deps file — multi-root positionals require the additive `SourcePaths []string` field (nil ⇒ legacy `[SourceDir]`), otherwise success criterion 2 is unreachable.

Purpose: the compile step is the phase's keystone invariant — NULL column ⇒ byte-identical legacy argv, non-NULL ⇒ re-anchored maximal includes + derived excludes — and everything in plans 02–04 consumes it.
Output: migration v101, owned store setter, orchestrator additive field, one compile helper in selection.go, BackupFileSet wiring, all pinned by tests.
</objective>
