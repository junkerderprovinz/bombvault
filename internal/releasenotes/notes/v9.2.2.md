Two BombVault instances on the same network now pair directly, even inside Docker's default bridge network, where UDP multicast never reaches. Each instance learns its own address from the browser the moment someone signs in, and without a relay it searches its own subnet with a signed call only a group member can answer, so two boxes on the same LAN finish pairing in seconds. If that search finds nobody, Can't find it? takes one address by hand.

## 🐛 Fixed

- **Pairing across a Docker bridge network now works without a relay.** Two instances used to find each other only by multicast, which a bridge network blocks ([#270](https://github.com/junkerderprovinz/bombvault/issues/270)). Each instance now learns its own address from the browser, shown in the relay card as "This instance on your network" and editable for a reverse proxy, and with no relay set it sweeps its own subnet for the other instance with a signed, authenticated call, including a second instance on another port of the same machine. The instance it finds learns the searcher's address from the same call, so both list each other right away. A relay still exchanges the same addresses once it connects, so a relayed member upgrades to a direct route too, and the phrase card's member list says Direct or Via relay for each one.
- **Still alone without a relay points at the relay first, and now says the instance is searching on its own.** The hint used to open with "Created a phrase on both instances?", which sent people off to leave and rejoin a group that was fine. It leads with the missing relay, and since pairing can now finish without one, the text says this instance is searching the network itself, with a Project relay button next to it as the alternative.
- **Signing in over plain HTTP no longer bounces back to the login screen.** After signing in over HTTPS, the browser keeps a secure login cookie for that host, and a page served over plain HTTP on the same host may not replace it. Switching an instance to plain HTTP therefore made a correct password look wrong. Plain HTTP now uses its own cookie name.
