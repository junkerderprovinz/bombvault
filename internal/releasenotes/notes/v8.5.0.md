The look of the interface stops living in your browser, a received repository that fails its check now says what to do about it, and the documentation has pictures.

## ✨ Added

- **Theme, accent, labels and language are stored on the server, not in the browser** ([#191](https://github.com/junkerderprovinz/bombvault/issues/191)). Reported by someone who clears Firefox's site data to fix an unrelated problem with the VM console, and had to rebuild his view every single time. Eleven settings travel: theme, accent, the accent presets, the rainbow palette, motion, shape, the three label modes, language and the advanced view. List filters and sort orders deliberately do not, because those describe what you were doing on one page and syncing them would move someone else's filter under your cursor on another machine. Your browser still holds a copy and still renders from it instantly, which is what stops the app flashing the default theme on every load; the server is simply where the answer comes back from when the browser no longer has one. Upgrading keeps what you already had: an empty setting on the server means "no opinion", so the first load after this release seeds it from your browser rather than resetting you.
- **A failed integrity check on a received repository now says what to do next.** It used to print restic's message and stop. The page now says that BombVault only ever reads a received repository and will not repair it, that the password is derived from the **sending** instance's `APP_KEY` and lives in that instance's recovery kit rather than this box's, and that `restic repair index` comes before `restic repair snapshots`. Raised in the support forum by someone who hit "repository contains errors", opened a shell on the receiving box, and could not get past restic's password prompt because nothing said whose key it wanted.

## 🎨 Design

- **A stack member's Backup folders list says where its project folder went**, naming the stack, so an empty list reads as "backed up with the stack" rather than "nothing here".
- **Five screenshots in the documentation, which had none.** They sit under the heading they illustrate rather than at the top of a page, so skimming a page tells you whether the section is the one you want. The README's four are retaken as well: they predated the control engine, so every button in them was a wordless icon.

## ⚡ Improved

- **A Docker Compose stack's project folder is backed up once, not once per service** ([#189](https://github.com/junkerderprovinz/bombvault/issues/189)). Reported as container backups getting slower and hotter since v8.0.0, with VMs unaffected. v8.0.0 is when that folder became a backup source, and it was added to every member of the stack. restic deduplicates the stored bytes, so a five-service stack cost one copy on disk and the size column showed nothing at all; what it does not deduplicate is the work, so every service still walked, chunked and hashed the whole folder on every run. Measured on a two-service stack before changing anything: the folder appeared in both members' snapshot paths, and the second member reported zero new bytes after spending the same time computing them. It is now its own snapshot, taken once per backup round, and a stack restore puts it back first, before any member starts. Backups taken before this release still carry it inside each member and restore exactly as they did.
- **The encryption card says where the password actually is.** It said "password derived from APP_KEY" and stopped there, which reads as an explanation and lands as a riddle if you are trying to run restic by hand. It names the recovery kit now, at the one place that raises the question.
- **The documentation shows how to derive that password yourself**, so the kit is a convenience rather than the only way in: HMAC-SHA256 over `bombvault:restic-repo`, keyed with the raw bytes of the hex `APP_KEY`. The one-liner in the docs was checked against the implementation rather than written from reading it.
- **A stray listing of an exclusion-scan repository is gone.** Six concurrent scans released together could produce two `restic ls` runs instead of one, because a caller that missed the cache could become the leader for an answer that had been cached in the meantime. Rare, and exactly the burst the shared scan exists to prevent inside a memory-capped container.

## 🐛 Fixed

- **`latest` could be moved backwards by re-tagging an older version.** The image build pushed `latest` from any tag build, not only from the default branch, so re-cutting an older release pointed `latest` at that older code for everyone pulling it. Found by comparing digests after such a re-cut, not by anything failing.
