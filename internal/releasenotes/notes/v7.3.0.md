BombVault 7.3.0 adds control over the order your containers are backed up in, a health-gated restart of the dependencies BombVault stops during a backup, and an automatic refresh of Unraid's Docker update banner after BombVault updates a container.

## Added

- **Manual backup order.** You can now set the exact order your containers are backed up in. Open the backup-order panel on the Containers page and move them into the sequence you want. Scheduled and multi-select runs follow it; any container you leave unordered keeps the previous behaviour and is backed up most-overdue-first. A single container backup is unchanged.
- **Health-gated restart of stopped dependencies.** When a container uses "Stop other containers during backup", BombVault now brings the stopped containers back in the right order instead of all at once: it starts them in their Compose `depends_on` order and, by default, waits for each one to report healthy (or running, if it has no healthcheck) before starting the containers that depend on it. So a dependency like Pi-hole, a database or a VPN gateway is actually up before the services that need it, instead of those services returning to a "connection refused" and staying down. The wait is bounded by a per-container timeout (120 seconds by default) so a slow or never-healthy container can never hang the run. Both the wait and the timeout live on the Schedules tab in Settings; turn the wait off if you prefer the previous all-at-once restart. The restart also wraps the post-backup image update, so on a day an update lands the dependents are held down through the recreate and only brought back, health-gated, once it is done.

## Fixed

- **Unraid's "update available" banner clears itself after an update.** When BombVault updates a container it goes straight through the Docker API, so Unraid's Docker tab kept showing "update available" from its own cached status until you clicked "Check for Updates", and on some Unraid versions not even then, because Unraid re-read a stale cached digest. BombVault now asks Unraid to re-check that one container's update status right after the update, through Unraid's own recheck so Unraid rewrites its status itself. The banner clears on its own, and the stale-cache case is handled too. It is best-effort and never affects the backup, and there is a toggle for it in Settings.

## Upgrading

Just pull the new image. The manual backup order is empty until you set one, so ordering is unchanged out of the box. The health-gated restart and the update-banner refresh are both on by default: if a container uses "Stop other containers during backup", its dependencies now come back one by one as each becomes healthy (turn the wait off in Settings for the old all-at-once behaviour), and after a container update BombVault asks Unraid to refresh that container's update status. Both are best-effort and never fail a backup.
