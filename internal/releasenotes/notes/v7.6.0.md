BombVault 7.6.0 completes cross-instance container recovery and fixes selective file-set restores.

## Improved

- **Restoring a container from another BombVault now places its appdata correctly, even across different pools.** 7.5.0 stopped a cross-instance container restore from writing appdata to a pool this server does not have (it refused rather than write to the wrong place). 7.6.0 goes the rest of the way: it remaps the appdata onto a destination on this server (by default your restore folder, otherwise /mnt/user/appdata), so the container's data lands where it belongs and the recreated container points at it. You can pick the destination in the restore dialog, and BombVault warns you about any other mounts (for example a media share) that point at a pool this server lacks, so you can fix those in the container's template. A normal same-pool restore is unchanged.

## Fixed

- **Restoring a picked subfolder from a file set now drops it straight into the target folder.** When you restore selected folders or files from another BombVault (Recovery, "Pick a subfolder"), a deeply nested pick used to recreate the whole path under the target (for example <target>/stacks/DXP480T/xo) instead of just <target>/xo. The selection now lands directly as <target>/<name> at any depth, so you can pull one stack out of a whole-appdata set and drop it exactly where you want it.

- **Backing up a live, actively-written folder is no longer reported as failed.** restic warns (and exits with a warning code) when a source file changes or cannot be read mid-scan, which is normal for a running app's data (for example a database or a NATS stream volume), but it still creates the snapshot. BombVault now records that as a successful backup and logs the skipped file instead of a hard failure. The pinned progress bar also drops its redundant caption, since the card's button already names the running phase.

## Maintenance

- Updated dependencies: Go modules, frontend packages, Docker base images and pinned GitHub Actions.
