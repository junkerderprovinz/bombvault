Every restore now checks first and shows what it will change, and a container can be started from its backup in an isolated copy to prove it comes up. A new item gets a restore check right after its first backup. Scheduled backups can wait until an app is idle, off-site copies slow down while a media server streams, and qcow2 VMs can be backed up by reading only the blocks that changed. BombVault also gets a documented HTTP API, a Home Assistant device over MQTT and a name on the local network. Settings, schedules and repositories carry over as they are, and every new switch except the network announcement starts off.

## ✨ Added

### Retention and storage

- **Keep yearly.** The local policy under **Settings, Paths & Storage**, the off-site policy under **Settings, Off-site** and every additional off-site target have a yearly rule next to last, daily, weekly and monthly. It keeps one restore point for each of the last N calendar years that has a backup, and the oldest one as well while there are fewer such years. The retention preview and **Prune** follow it too.
- **Compression per repository.** Choose Off, Automatic or Maximum under each backup path, on each off-site destination and on each named repository. Automatic is restic's default and what every repository used so far. Backups, off-site copies and prune write with the setting, and the recovery kit names it, so plain restic can keep writing the same way. It applies to new data, and a repository in restic's old format version 1 ignores it.
- **Free space for SFTP repositories and network shares.** The dashboard's storage forecast shows free space and the weeks until full for SFTP repositories, read over the same SSH login restic uses, and for SMB and WebDAV destinations whose server reports it. S3, B2 and REST repositories cannot report their free space, so they say "Free space unknown" instead of showing nothing. The anomaly check for a disk that will be full soon covers SFTP repositories as well.

### Safer restores

- **Checks before every restore.** Before anything runs, the restore dialog checks that the repository answers, that the stored key opens it, that the restore point is there and that the target has room for what the restore writes. Start stays locked while a check fails, and the (i) in the button names it. A figure that could not be measured shows grey and does not block. The checks write nothing.
- **A plan of what the restore changes.** Before you confirm, the dialog counts new, replaced and unchanged files, with the list on request, and the files at the target that are not in the backup. Those stay where they are. restic works this out as a dry run from size and modification time without reading the files. A very large tree stops after 30 seconds and says the numbers are a lower bound.
- **Settings compared with now.** For a container the plan compares image and tag, ports, variables and volumes with the running one, and for a VM its memory, vCPUs, disks and network. Variables are compared by name only, their values are never shown.
- **Shared folders.** An in-place restore names every other container, running or not, whose bind mount reaches into a folder it writes to, for example "this path is also used by nextcloud-db". It warns and does not block.
- **Stacks are checked member by member.** **Restore stack** checks and plans every member and names the one that blocks.

### Proving a restore works

- **A restore check after the first backup.** Once an item's first backup is done, BombVault restores a sample of it (up to 100 files and 256 MiB) into a temporary folder under the restore folder, has restic read every file back against its hashes and compares the sizes with the backup. A file too large for the sample, such as a VM disk, gets its first 64 MiB read back. The result shows on the item and a failure sends a notification. **Check restore** runs the same check on the newest backup whenever you want.
- **Start test.** **Start test** on a container card restores its newest backup into a copy whose name starts with `bombvault-test-` and starts it on an internal Docker network of its own, with no published ports, no way to the LAN, 1 CPU and 2 GiB of memory. It passes when the container's healthcheck reports healthy, without one when its first exposed port answers, and with neither when it keeps running.
- **The original container is never stopped or changed.** The copy carries none of the original's labels and runs without the capabilities, security options and sysctls the original adds; when that makes it fail, the result says what it ran without. The copy, its network and its data are removed afterwards, also when BombVault restarts in the middle of a test. Containers on the host network, privileged ones, ones with devices and ones that need another container show as not testable.
- **Scheduled start tests are off by default.** Switch on **Start test** in **Automatic restore checks** under **Settings, Integrity** to test one container per scheduled check, the one tested longest ago first. The result shows on the card and on the dashboard.
- **Progress for verify, restore checks and prune.** The activity log and the Integrity card show how far restic has got, such as "12 of 47 packs", with the time left in that step once it can be estimated. restic counts packs, snapshots and index files here, not bytes, so that is what the bar shows.

### Seeing what a backup holds

- **Size by folder.** In the Backups section of a container, VM or folder set, **Size by folder** shows which folders and files take the space in the newest backup and how much of each the latest backup brought in new or changed, one level at a time. It is read from the repository's index without reading the files, and kept current after each backup once you have opened it.
- **Why a backup was slow.** When a backup takes much longer than usual and one thing was clearly at its limit, the run says so in one line, for example "The target disk disk1 was 98% busy" or "BombVault used 100% of the CPU limit of its container". Otherwise it says nothing.
- **Changed since backup.** A container that was recreated with another image, other ports, variables or volumes since its last backup gets a mark beside its name, and its (i) lists what changed, variables by name only. It is only a note and goes away with the next backup.

### Sources and imports

- **Recommended excludes per app.** For Plex, Jellyfin, Emby, Sonarr, Radarr, Lidarr, Readarr, Prowlarr, Immich, Nextcloud, PhotoPrism and Tautulli, from linuxserver, hotio, binhex or the official publisher, the exclusion assistant offers the folders the app fills again by itself: caches, logs, preview images and posters. Each entry says what it holds. Downloaded artwork starts switched off, since images you uploaded yourself sit there too, and nothing is excluded until you press **Exclude selected**.
- **ZFS properties come back.** Every ZFS backup keeps each dataset's locally set properties, such as compression, record size, quota and case sensitivity. **Into a new dataset** creates the dataset with them and restores into it. A restore into an existing dataset lists them and sets them only with **Also set these properties**; quotas and reservations are set after the files, so they cannot refuse them. The properties live in BombVault's own database, so after a rebuild they come back with the self-backup.
- **One plugin from a flash backup.** **Plugins** on a flash backup lists the plugins in it with their version and size, and puts a single one back into the running flash: its `.plg` file, its folder under `config/plugins` and the package files the backup holds. Nothing else on the flash changes. Unraid installs the plugin on the next boot, or right away under **Plugins, Install Plugin**.
- **Import from the Appdata.Backup plugin.** On the **Recovery** page, point BombVault at the plugin's backup folder. Each container archive becomes a restore point of its container, dated when the plugin made it. The archives are only read, ones imported before are skipped, and the container needs one backup in BombVault first, so the restore has its definition.

### Backups that make way

- **Streaming first.** While Plex, Jellyfin, Emby or another media server you pick streams, off-site copies upload at a lower limit (512 KiB/s unless you change it) and return to the normal one a few minutes after the stream ends. REST, S3, B2, Azure, Google Cloud, Swift and rclone over HTTP slow down in the middle of a copy; SFTP and local or mounted folders take the lower limit from their next copy step. A media server on the host network cannot be measured. Under **Settings, Off-site** in the advanced view, off by default.
- **Wait until the app is idle.** A container (advanced view) can let its scheduled backup wait while its app is busy, for at most the hours you set, and start as soon as the app is idle. A media server is idle when it isn't streaming, any other container when its CPU and traffic stay below the limits in **Idle before backup** under **Settings, Schedules** for a few minutes. The wait shows in the activity log and on the container with its reason and deadline. It holds no lock, so the other containers go ahead.
- **Stacks wait together, and a wait survives a restart.** The members of a compose stack due in the same run wait as one and back up together with their project folder. A wait carries on with its deadline after BombVault restarts. Manual backups never wait.

### Changed blocks for VMs

- **Changed blocks only.** A running VM with qcow2 disks can be backed up through libvirt checkpoints, so each backup reads only the blocks written since the previous one. The VM keeps running, as with Live. Off by default, switched on per VM on its card.
- **Every restore point is complete on its own.** Unchanged parts are taken over from the previous restore point without being read, so any of them restores the whole disk. A restore rebuilds the disk and converts it back to qcow2, which flattens a backing chain.
- **It falls back instead of failing.** A missing or broken checkpoint or a disk that changed size means one full read. A VM that is off, a raw or zvol disk, no host SSH link or a libvirt without the backup API means the usual backup. The card says which the last run used and why. Unraid creates raw vdisks by default, and those keep the usual backup.
- **Nothing stays behind in libvirt.** Between runs the VM has no checkpoint on record, so Unraid's **Remove VM** and a restore work as before. Checkpoints of other tools are left alone, and a VM that has some cannot be restored until you delete them; the restore stops before it touches the VM. The data waiting for restic takes up to 4 GiB under `/config`.

### HTTP API

- **A documented API under `/api/v1`** for scripts and dashboards: health, status, activity, items, runs, anomalies and storage, and starting or cancelling a backup. BombVault serves its description at `/api/v1/openapi.json` (OpenAPI 3.1), which needs no token. Restores, deletions and settings stay in the web interface.
- **Tokens of its own.** Create them under **Settings, System, API tokens**, read-only or allowed to start backups. A token is shown once and stored as a fingerprint, and every request needs one, even without a login password. An MCP key does not open the API, and a token does not open MCP. Each token's tile shows its last use and has a log, **Replace token** and revoke.
- **The same limits as MCP.** 12 starts per hour per token, and the 15 minutes between starts of the same item, the 4 starts per item a day and the retention guard count starts through MCP, the API and Home Assistant together. A run started this way reads "via API" with the token's name.

### Home Assistant and the local network

- **Home Assistant over MQTT discovery.** Enter your broker under **Settings, System, Home Assistant** and BombVault shows up as a device with sensors for its status, the running job, open anomalies, the next scheduled backup, and each domain's last backup, last result and repository free space. Home Assistant needs no custom component.
- **Backup buttons are off by default.** With **Buttons start backups** on, each domain gets a button that backs up the whole domain, under the API's limits. BombVault takes one press per domain at a time and at most six a minute, and ignores a press the broker kept as a retained message. Anyone who can publish to the broker can press them, so give the broker a password.
- **bombvault.local.** BombVault announces its web interface over mDNS, so a browser reaches it as `https://bombvault.local:3443`. On by default, switched under **Settings, System, Find on the network**. If the name is taken, it becomes `bombvault-2.local`.

## ⚡ Improved

- **The MCP server knows the new features.** `get_size_breakdown` answers what takes the space in a backup, `get_status` lists the backups waiting for an idle app, `list_items` carries each item's restore check and start test and what changed in a container since its backup, `list_runs` names what held a slow backup back, and `get_storage_stats` reports the free space of SFTP repositories.
- **The settings export carries the new settings**: the yearly rules, compression, Streaming first, Idle before backup, Home Assistant and the network switch. The broker password travels only in an export with credentials. A file from an older version leaves the yearly rules and compression of the instance you import it into as they are.

## 🐛 Fixed

- **A container on its own schedule gets its compose project folder backed up.** Only a run of the whole domain backed that folder up, so a stack member with a schedule of its own never had it saved.
- **A restored container keeps its healthcheck.** The stored container definition left out a healthcheck set in compose or with `--health-cmd`, so a restore recreated the container without it. Definitions saved from the next backup on keep it; older ones fall back to the image's own healthcheck.
- **Two installs sharing a local repository no longer remove each other's lock.** Every install runs under the host name `bombvault`, so the lock cleanup from v9.1.0 could mistake the live lock of a second install for one left by an interrupted run and delete it. A lock now also has to go 10 minutes without a refresh, and restic refreshes a held lock every 5 minutes. After a restart, the lock of an interrupted run is cleared within 10 minutes instead of at once.
- **A VM whose name starts with a dash** is no longer read as a virsh option.
- **A container card on a phone said "1 paths".** It uses the singular for one path now.
- **The repository picker of a VM showed two (i) buttons.** There is one, and it also names why the picker is locked when it is.
- **The authorize command on the Host SSH card was cut off** on the right at desktop widths. It wraps inside its box.

## Upgrading

- **Nothing has to be changed.** The database is upgraded on the first start, settings export files from older versions still import, and no setting or environment variable was removed or renamed. restic stays at 0.17.3 and the repositories are left as they are.
- **New switches start off:** Streaming first, waiting for an idle app, scheduled start tests, changed blocks for VMs, Home Assistant and its buttons. Yearly retention keeps nothing until you set a number, and compression stays at Automatic.
- **The network announcement starts on.** In Docker's default bridge network, which the Unraid template uses, it stays inside Docker and nobody on the LAN sees it; it reaches the LAN on br0, macvlan or the host network. Switch it off under **Settings, System, Find on the network**.
- **The restore check after the first backup** runs for items first backed up after the update. For the items you already have, press **Check restore** on the item.
- **A lock left by an interrupted run** can hold checks and prunes back for up to 10 minutes after a restart.
