ZFS datasets are a backup type of their own, read from one snapshot, so every file of a dataset and its child datasets comes from the same moment.

## ✨ Added

- **A ZFS page.** Pick a dataset from the server's list and it is backed up together with every dataset below it. New child datasets join on their own and the next backup names them. You can leave single children out.
- **Nothing is skipped silently.** A dataset that cannot be read (not mounted, key not loaded, never mounted) is skipped and named on the run, on the item and on the dashboard's coverage card.
- **Volumes are not part of it.** A volume a VM uses is backed up with that VM. A volume without a VM is counted on the page and not backed up; a later version will take care of those too.
- **Stored like a folder.** Each dataset is read from the ZFS snapshot and stored with restic, so unchanged data is not stored twice, every backup can be browsed and single files come back on their own. BombVault never uses `zfs send` for datasets.
- **Consistent apps without long downtime.** Name containers to stop just for the snapshot, or run a command before it (a database dump, for example). The stopped containers are back within seconds, and the backup reads the snapshot while they run.
- **Restores that never roll back.** Restore one dataset into its place, into a folder, or only the files you pick, or every dataset of a backup into a folder. Before writing into a dataset BombVault takes a ZFS safety snapshot (on by default), which stays until you delete it on the page. A dataset is never rolled back or replaced.
- **No leftover snapshots.** A snapshot BombVault could not remove after a backup is removed before the next one and when BombVault starts, and the page shows any that are still there.
- **Containers come back after a crash.** Containers left stopped by an interrupted snapshot are started again when BombVault starts.
- **Everywhere the other types are.** Schedules and per-item schedules, per-item repositories, retention, off-site copies (immutable too), drills, Backup Everything, coverage, metrics, Healthchecks per type, notifications, the support bundle and the recovery kit all include ZFS datasets.

## ⚡ Improved

- **The template's SSH fields are now called Host SSH: Address, Port and User**, because VM and ZFS dataset backups both use them. Your values stay.
- **The address placeholder no longer blocks the connection.** With the address still at the template's `192.168.x.x`, BombVault tries the server itself through host.docker.internal.

## 🐛 Fixed

- **TrueNAS: SSH commands went to the wrong machine.** When `LIBVIRT_URI` is set and the SSH host, user or port is not, BombVault takes each missing one from the URI for its own SSH commands as well, so the NVRAM transfer and ZFS commands reach the machine `virsh` talks to.

## 📝 Notes

- ZFS datasets need the SSH link to this server that VM backups use, and the Host Data path mapped as `/mnt` with Access Mode Read/Write - Slave (the template default).
- On TrueNAS, set the app's Host Data to a host path above the datasets, for example `/mnt/tank`.
