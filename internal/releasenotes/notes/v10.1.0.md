BombVault 10.1.0 stops a container on ZFS only for the moment its snapshot is taken, instead of for the whole backup. It also backs up VMs whose disks are zvols, lets the ZFS replica run on its own, and fixes what a full test run on TrueNAS SCALE turned up.

## ✨ Added

- **Snapshot instead of stop.** A container whose data lies on ZFS is stopped only while BombVault snapshots that data, usually a few seconds, and the backup is then read from the snapshot under the same paths and tags as before, so restores and restore checks treat both alike. It needs the SSH connection to the host that ZFS datasets use. A container with none of its data on ZFS is stopped for the whole backup as before, and when only part of it is on ZFS or the snapshot cannot be used, the run says why. The switch is under **Settings, Schedule, Snapshot instead of stop**, on by default and settable per container, and its runs show **Snapshot** and how long the container was down.
- **Containers come back after a crash.** Should BombVault stop in the middle of a container backup, it starts the containers it held down again the next time it starts.
- **VMs whose disks are zvols are backed up and restored.** BombVault snapshots each zvol, reads it as a raw image and stores that in restic, so a disk that did not change adds almost nothing to the next backup. A restore first takes a safety snapshot of the zvol (`bombvault-before-restore-…`) and then writes the image back onto it, so a `zfs rollback` to that snapshot undoes it. Exporting such a VM as files is refused with an explanation.
- **Replicate now** on the page of a ZFS entry, and **Replicate all now** on the ZFS tab of the Backups list, next to the backup actions.
- **A ZFS entry can have only a replica.** With a replica target and no storage location for its section, its backup run takes the snapshot and sends the replica, and it no longer fails for lack of a restic repository.
- **Mount read only on the server.** A switch on a ZFS server connected over SSH mounts the replicas there read only after each run, so the data can be read and copied on the target. Encrypted replicas stay locked until their key is loaded, and switching the option off unmounts nothing. ([#320](https://github.com/junkerderprovinz/bombvault/issues/320))

## 🎨 Design

- **Every one-line control stands beside its name.** In the cards and windows across BombVault, dropdowns, segmented choices and number and text fields sit at the end of their row instead of filling the width under their name. On a phone they move under the name when the row is too narrow for both.
- **Number fields are short again.** Days, weeks, retention counts and the other number fields are back to the width of a few digits.
- **The bar at the bottom of a phone shows only symbols** below 720 pixels, in equal slots, with the page name as a tooltip and for screen readers. Long names such as Wiederherstellung no longer run into each other.
- **Replicates to is a dropdown** on a ZFS entry and names the kind of target, over SSH or paired instance, so long server names fit.
- **Replicate now shows once**, among the actions of a ZFS entry's page.

## ⚡ Improved

- **The replica runs on its own.** After every backup means after the entry's backup run, whether it worked, failed or found nothing to do.
- **The list and the entry page show the replica**: Replicating, Replicated with the time, or Replica failed, instead of Waiting for the first backup.
- **Data outside Host Data is named.** When a container keeps data where BombVault does not back it up, such as a TrueNAS ixVolume, the run lists the folders it left out instead of reporting a plain success.
- **The restore check catches a missing network.** If the network a container needs is gone, for example because its TrueNAS app was deleted, the check says so before you start and tells you to reinstall the app first. The restore itself refuses before it changes anything.
- **The restore check lists the zvols a VM restore writes** and whether the pool has room for them, and it says when the restore creates a container or VM that is gone.
- **The DR drill names what it restored**, the item and the snapshot, on the drill and in the activity log.
- **Switched-off off-site targets are left alone.** When every off-site target of a section is switched off, a manual copy, a DR drill, a restore test and a tamper check are refused, and the scheduled off-site jobs of that section are skipped.
- **The exclude preview looks at the files.** A line that matches nothing, or a path that does not exist in the backup, is marked as such.
- **Paired servers fall back to the relay in time.** When a member's direct address stops answering, the call goes through the relay instead of timing out, and the calls after it go there straight away until the address answers again.
- **The mDNS setting no longer shows an address nobody reaches.** In a Docker bridge network it says that the announcement stays inside Docker instead of showing bombvault.local.
- **The first off-site copy links to its keep rules.** On a storage location's page, a section whose first off-site copy follows its own keep rules links straight to the Off-site retention settings. ([#351](https://github.com/junkerderprovinz/bombvault/issues/351))

## 🐛 Fixed

- **A section switched on after the update to 10.0 had no storage folder.** ZFS datasets switched on after the upgrade got an empty repository path, so every ZFS backup and its off-site copy failed with "" points outside the "Host Data" mount. BombVault now gives such a section its default folder when settings are saved and at every start, which also repairs installs already in this state. ([#320](https://github.com/junkerderprovinz/bombvault/issues/320))
- **Only some VM folders were recognised when adding a ZFS dataset.** Unraid's VM manager refers to disks through the user share (/mnt/user/domains), and BombVault compared that with the pool path. VM folders are now recognised either way and left out by default. ([#320](https://github.com/junkerderprovinz/bombvault/issues/320))
- **BombVault tried to create an off-site repository on a host that did not answer.** When the connection failed, for example with a timeout or a refused connection, it took the location for empty and ran restic init. It now stops with "could not reach the repository, so nothing was created there". ([#334](https://github.com/junkerderprovinz/bombvault/issues/334))
- **A database import onto a dataset mount failed** with "device or resource busy" when the data folder was itself a mount point, as on TrueNAS. BombVault now moves the old contents into a folder next to the mount, and the import result offers to remove that copy.
- **Saved database dumps got Unraid's owner on other hosts.** Outside Unraid they keep the owner of the process.
- **On TrueNAS the host was not found without LIBVIRT_HOST.** When host.docker.internal does not resolve, BombVault uses the container's default gateway.
- **TrueNAS was offered Unraid-only features and advice.** The flash backup and the Unraid notifier show up only on Unraid, the host config preset only where Host Data reaches /etc, and their messages no longer send TrueNAS users to a /boot mount.
- **The DR drill could pick a container without an off-site copy** when no target was set. It now takes the newest container that has one.
- **An interrupted zvol backup left its snapshot and clone behind.** The next start removes them and logs what it removed.
- **Restoring a VM with a disk on a ZFS volume next to the original** is refused straight away with the reason, instead of asking you to pick another backup.
- **The rollback hint after a zvol restore** says when the rollback needs `zfs rollback -r`.
- **ZFS:** an excluded child dataset can be added as its own item, and a replica snapshot that ZFS holds is kept quietly instead of filling the log.
- **A dataset in the settings of a ZFS entry showed Unknown state ()** before its first backup. It now says Not backed up yet or Replicated.
- **Error texts** keep URLs and ZFS dataset names readable and no longer lose the closing bracket after a hidden path. Some notifications showed a [path] placeholder and dashes in their error text.
- **The healthcheck left TLS errors in the log.** It now probes only the listener the server opens.
- **A failed backup of a newly added VM** now shows up in the history.
- **Leaving the group left the other servers on the Instances page.** They are removed now, and the servers still in the group drop the one that left. A server that was offline at the time drops it once it reaches that server again and hears, signed with its key, that it is in no group.
- **Saving a server's own direct address made it vanish from the group for a moment**, so calls over the relay that were under way failed. The relay connection now stays up.
- **Two instances that start at the same moment on one network** both claimed bombvault.local. One of them now takes bombvault-2.local.
- **The hint for adding BombVault's key on an Unraid ZFS server pointed to Settings, Users**, which only exists when Display Settings put Users there. It now names both places. ([#320](https://github.com/junkerderprovinz/bombvault/issues/320))

## Upgrading

- **Nothing has to be changed, except on TrueNAS.** Snapshot instead of stop is on for existing installs too, and a container that cannot use it is stopped for its whole backup as before. A section that is switched on without a storage folder gets its default folder at the first start.
- **A ZFS entry that should only replicate** also backs up to every storage location its section has switched on. To send only the replica, switch off the lines of ZFS datasets under Settings, Storage locations.
- **TrueNAS:** a custom app needs `SETPCAP` and `SYS_CHROOT` in `cap_add`, as in the [TrueNAS SCALE](https://junkerderprovinz.github.io/bombvault/getting-started/#truenas) YAML. VM backups fail without `SETPCAP`, and without `SYS_CHROOT` every container is stopped for its whole backup, with a run that names the missing capability.
