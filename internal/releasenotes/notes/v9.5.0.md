The exclusion assistant suggests the folders well-known apps fill again by themselves, ZFS backups keep each dataset's properties and can restore into a new dataset, a single plugin comes back from a flash backup, and archives of the Appdata.Backup plugin can be imported as restore points. Scheduled backups can wait until an app is idle, and off-site copies slow down while a media server streams. Settings, schedules and repositories carry over as they are, and the new switches start off.

## ✨ Added

### Sources and imports

- **Recommended excludes per app.** For Plex, Jellyfin, Emby, Sonarr, Radarr, Lidarr, Readarr, Prowlarr, Immich, Nextcloud, PhotoPrism and Tautulli, from linuxserver, hotio, binhex or the official publisher, the exclusion assistant offers the folders the app fills again by itself: caches, logs, preview images and posters. Each entry says what it holds. Downloaded artwork starts switched off, since images you uploaded yourself sit there too, and nothing is excluded until you press **Exclude selected**.
- **ZFS properties come back.** Every ZFS backup keeps each dataset's locally set properties, such as compression, record size, quota and case sensitivity. **Into a new dataset** creates the dataset with them and restores into it. A restore into an existing dataset lists them and sets them only with **Also set these properties**; quotas and reservations are set after the files, so they cannot refuse them. The properties live in BombVault's own database, so after a rebuild they come back with the self-backup.
- **The checks before a restore cover a new dataset too.** They create nothing: the plan counts the files as they will land in the new, empty dataset, and the space check looks at where it will be mounted.
- **One plugin from a flash backup.** **Plugins** on a flash backup lists the plugins in it with their version and size, and puts a single one back into the running flash: its `.plg` file, its folder under `config/plugins` and the package files the backup holds. Nothing else on the flash changes. Unraid installs the plugin on the next boot, or right away under **Plugins, Install Plugin**.
- **Import from the Appdata.Backup plugin.** On the **Recovery** page, point BombVault at the plugin's backup folder. Each container archive becomes a restore point of its container, dated when the plugin made it, and shows as an import in the activity log and the run lists. The archives are only read, ones imported before are skipped, and the container needs one backup in BombVault first, so the restore has its definition. Links inside an archive are never followed, so nothing in it can write outside BombVault's work folder.

### Backups that make way

- **Streaming first.** While Plex, Jellyfin, Emby or another media server you pick streams, off-site copies upload at a lower limit (512 KiB/s unless you change it) and return to the normal one a few minutes after the stream ends. REST, S3, B2, Azure, Google Cloud, Swift and rclone over HTTP slow down in the middle of a copy; SFTP and local or mounted folders take the lower limit from their next copy step. A media server on the host network cannot be measured. Under **Settings, Off-site** in the advanced view, off by default.
- **Wait until the app is idle.** A container (advanced view, and in its detail on a phone) can let its scheduled backup wait while its app is busy, for at most the hours you set, and start as soon as the app is idle. A media server is idle when it isn't streaming, any other container when its CPU and traffic stay below the limits in **Idle before backup** under **Settings, Schedules** for a few minutes. The wait shows in the activity log and on the container with its reason and deadline. It holds no lock, so the other containers go ahead.
- **Stacks wait together, and a wait survives a restart.** The members of a compose stack due in the same run wait as one and back up together with their project folder. A wait carries on with its deadline after BombVault restarts. Switching the containers off drops every waiting backup, switching their schedule off drops the ones its runs held back, and lowering the hours shortens a wait that has already begun. Manual backups never wait.

## ⚡ Improved

- **The MCP server knows the waiting backups.** `get_status` lists the scheduled backups waiting for an idle app, with the stack, the container that is busy, the reason and the time they start at the latest.
- **The settings export carries Streaming first and Idle before backup.** The hours a container waits are set on the container and stay out of the file, like its other settings.

## 🐛 Fixed

- **A container on its own schedule gets its compose project folder backed up.** Only a run of the whole domain backed that folder up, so a stack member with a schedule of its own never had it saved.

## Upgrading

- **Nothing has to be changed.** The database is upgraded on the first start, settings export files from older versions still import, and no setting or environment variable was removed or renamed. restic stays at 0.17.3 and the repositories are left as they are.
- **New switches start off:** Streaming first and waiting for an idle app. No recommended exclude is applied until you pick it.
- **ZFS properties are kept from the first ZFS backup after the update.** Older restore points have none, so a new dataset made from one of them starts with the pool's defaults.
- **Restoring into a new dataset as a user other than root** needs `create` on the dataset above it, and permission for each property BombVault sets.
