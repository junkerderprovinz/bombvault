This is the largest release in BombVault's history, and it has two halves. The first is capability: one scheduled pass over the whole server, disaster-recovery drills that finally cover VMs, a Fleet view that shows several BombVault instances at once, off-site storage that fleet peers can hand to each other, and support for plain Docker hosts beyond Unraid. The second is a complete overhaul of the interface: colour, shape and motion are yours to set, the Save buttons are gone because every field saves itself, and every page was rebuilt on one shared set of controls.

## ✨ Added

- **Disaster-recovery drills now cover VMs (#142).** The off-site DR drill used to refuse the VM domain outright, so the one domain whose restore takes longest was also the one you could never rehearse. VMs now go through exactly the same drill the other domains do: BombVault restores the chosen VM's newest off-site snapshot into a throwaway sandbox under your restore folder, counts the restored files and bytes back against restic's own accounting of that snapshot, and removes the sandbox afterwards whether it passed or failed. Because a VM image can be hundreds of gigabytes, the drill checks free space first and stops with a clear message naming your restore folder if there is not enough room, rather than running the host out of disk half way through. Settings, Integrity gains a **Drill target (VM)** picker next to the container one; leave it empty and the most recently backed-up VM is drilled. The scheduled off-site drill includes VMs from now on, so a green scorecard means the VMs were proved restorable too, not just assumed.

- **Fleet: several BombVault instances on one page (#143).** A new **Fleet** tab, off by default and enabled under Settings, lists the other BombVault boxes you run. You add a peer by its address and by the fleet token generated on that peer's own Settings page, and this instance then polls it once a day and whenever you press **Poll now**, caching what it gets back: each domain's protection state (protected, degraded, at risk) and when it was last backed up. It is strictly read-only in both directions. The only thing this instance ever does to another one is ask for its status; nothing on the page can start, stop or delete anything on a peer, and the token grants access to that scorecard and nothing else, revocable on the spot from the box that issued it. Adding or editing a peer probes it immediately, so a wrong address or a stale token is reported to you there and then instead of sitting in the list looking configured.

- **Fleet peers can hand each other off-site storage (#144).** Setting up mutual off-site storage between two people's boxes meant mailing a repository address and a password back and forth. Now the offering instance sends its own off-site connection details to a peer over the Fleet connection the two already trust: you choose which domain the storage is meant for and the address the rest-server will be reachable at, and send. The receiving admin sees a pending offer on their Fleet page and can accept or decline it; nothing is ever applied automatically. Accepting creates a normal named credential set and a normal off-site target for the chosen domain, both of which you can edit or remove afterwards like any other. BombVault still does not host storage itself, so the offering side deploys the rest-server, and the page hands over the ready-made run command and compose file for it. Only connection details travel over this channel; no backup data ever does.

- **BombVault runs on a plain Docker host, not only on Unraid (#149).** The handful of behaviours that are genuinely Unraid's now sit behind a platform layer. Set **PLATFORM** to `unraid`, `generic` or `truenas`, or leave it unset and BombVault detects Unraid by its marker on the flash mount and treats anything else as generic. On a generic host the Unraid-only steps (the webGUI notification mirror, the dashboard widget plugin) are skipped outright instead of attempted and failing, and the cross-instance restore destinations stop assuming Unraid's share layout. Finding a container's data no longer depends on Unraid's appdata convention either: **DATA_ROOT_SEGMENTS** lets you name the folder segments that mark backup data on your host, Docker named volumes are always included, a Compose project's own working directory is picked up from the standard label it already carries, and a `bombvault.data` label on a container pulls in all of its bind mounts for a layout none of those catch. A ready-made compose file ships for generic Docker hosts, and the files domain offers a **Host system config** preset there. One thing to plan for: named volumes and that preset can only reach paths that lie inside your Host Data mount, so on a generic host point Host Data at a common ancestor that also covers Docker's own data root, which is exactly why the Unraid template mounts everything under the array rather than a single share.

- **Backup Everything: one scheduled pass over the whole server.** Until now the five domains each ran on their own schedule, so there was no single moment you could point at and say "the server is backed up". Settings, Schedules gains a **Backup Everything** card with its own cadence, and when it fires it backs up every domain once, in order: containers, VMs, flash, folders, then BombVault's own self-backup. Each domain step behaves exactly like that domain's normal scheduled run, including retention pruning and the batched off-site copy afterwards, and one domain failing never stops the rest. The whole pass is bracketed by two optional commands you can fill in, a pre-command and a post-command. Unlike the per-container hooks, these run directly on BombVault's own server, through a shell, because a whole-server pass has no single container to run inside. The pre-command is best-effort and never blocks or fails the pass; the post-command fires exactly once after every domain has been attempted, whether or not any of them failed, which is what makes it usable as a dead man's switch: point it at a Healthchecks or Uptime Kuma ping URL and a missing ping means the pass itself never finished. Both commands are killed after five minutes so a hung one cannot wedge the pass. In the Activity Log the pass appears as its own **Backup Everything** line with its own filter entry, with every domain backup it produced recorded underneath it, and if anything failed the pass line carries a per-domain breakdown such as `containers: 11/12 ok (plex: …); vms: 2/2 ok; flash: ok`. Only one pass can be in flight at a time, so pressing the card's "Run now" button during the nightly pass tells you one is already running instead of starting a second. The cadence is **off** by default and does not replace or gate the five domain schedules, so if you turn it on and leave the per-domain schedules on as well, every item gets backed up twice; the card warns you about exactly that as soon as both are active.

- **Repository encryption is detected now, not asked.** Whether a repository has a password is not a preference, it is a fact fixed when the repository was created, and restic can only open it the way it was made. Yet the Recovery page used to put that question to you as a switch you had to set correctly from memory, on the one occasion you are least able to answer it: rebuilding a server from nothing. Get it wrong and restic simply refuses to open your backups, and in the worst case an unencrypted guess creates a fresh, empty repository next to the real one. BombVault now opens the repositories and reads the answer off them. On the Recovery page's third step, **Attach your backups**, the encryption line now sits at the top of the card and reports what was found: "Detected: your backups are encrypted. BombVault will use the password derived from your APP_KEY", or "Detected: your backups have no password". In that common case there is no control to set at all, and the detected mode is written into your settings for you. The probe is strictly read-only and can never create a repository. A switch still appears in the cases where no fact exists to detect: a genuinely fresh setup where nothing has been created yet, and the two undecided outcomes, where it acts as an override next to a plain explanation and a per-repository breakdown. A repository that could not be reached, because the path is wrong, the share is not mounted or the remote host is down, is reported as "couldn't be read", never as unencrypted. If some repositories come back encrypted and others come back password-less, you are told they disagree and which one is the odd one out, because no single setting can open both. Settings' own encryption hint was rewritten to match, in every language: it now says plainly that the setting only decides how a *new* repository is created.

- **"Every N days" works on the restore-check, tamper-test and weekly-digest schedules.** Issue (#166): those three offered the everyN cadence in the schedule editor but refused it on save, so a two-weekly restore-check drill could not be configured at all. The reason is that an everyN cadence is not a real cron entry. It is a daily trigger plus a question, "has it actually been N days since this last ran?", and the five backup domains answer that from their run history while these three had no such record anywhere. Recording one from the drill and tamper-test tables was not an option either, because those also hold the runs you start by hand, so clicking Verify on one domain would have suppressed the next scheduled pass across all of them. The three schedules now keep their own record of when their scheduled pass last ran, and the interval is genuinely enforced against it. What counts as a run differs on purpose: a drill or tamper-test pass counts as soon as its tasks were attempted, pass or fail, because the expensive part is paid on the attempt and a broken repository would otherwise re-run the whole pass every night; the digest counts only when it was actually sent, so a failed send is retried tomorrow instead of being lost for the rest of the interval. A drill pass with no domain enabled records nothing at all, so enabling a domain the next day is not blocked by a pass that did no work. The everyN option is back in the editor on all three. The five off-site replication schedules still do not offer it, for the same reason as before: they have no last-run fact, so their interval could not be enforced.

- **Webhook, Matrix and Apprise get real on/off switches.** A channel used to count as active purely because its URL field had something in it, so the only way to silence one without losing its configuration was to delete the URL and type it back in later. Each of the three now has its own toggle in Settings, Notifications, matching the one Email/SMTP already had, and its fields fold away while it is off. Nothing changes for an existing setup on upgrade: a configuration written before the switches existed is read with the rule the old build actually applied, so a webhook that had a URL, a Matrix channel with a homeserver, token and room, and an Apprise channel with a URL all come back on exactly as they were. Once you save, the switches are stored explicitly and a channel you deliberately turned off stays off, URL and all.

- **42 languages.** Sixteen new translations join the interface: Bulgarian, Catalan, Croatian, Basque, Estonian, Galician, Hindi, Icelandic, Indonesian, Latvian, Lithuanian, Malay, Persian, Serbian, Slovak and Slovenian, bringing BombVault from 26 to 42. Each is a complete translation of the entire interface, not a partial one, and the new strings in this release landed in all 42 at the same time as the English ones.

- **Every off-site destination gets its own connection test.** With two or more destinations configured for a domain, the primary Test button only ever checked the first one, so a green result could sit above a second destination that had been broken for weeks. Each additional destination now carries its own Test button, and the primary button calls itself "Test primary" as soon as a domain has more than one target.

- **A restore can pick which off-site copy it comes from.** With several off-site destinations there was no way to say which one to read back. A picker now appears whenever a domain has two or more enabled targets. The familiar local/off-site toggle is unchanged for the single-target case, which is still most setups.

- **Named cloud credential sets, one per off-site target (#141).** Every off-site target used to share one global set of S3 and restic-REST credentials, so two targets on different backends, a rented bucket and a local S3-compatible server for example, could not run side by side. Settings, Off-site has a **Cloud credential sets** card where you create named sets, and each additional target picks the set it uses or falls back to the shared default. A target pointing at a set that has since been deleted falls back to the shared credentials rather than failing outright.

- **A domain's primary repository can be remote (#152).** Each of the five backup paths, containers, VMs, flash, BombVault's own configuration and folders, has a Local/Remote switch, so the primary repository itself can sit on S3, a restic REST server, SFTP, B2 or rclone-backed storage instead of only working as an undocumented raw URL. Bandwidth limiting, the append-only flag with its tamper test, and the growth-budget alarm, all previously off-site only, apply to a remote primary as well.

## 🎨 Design

- **Three appearance engines are yours to set, under Settings, General.** Colour, shape and motion are now real settings with their own cards, not fixed decisions baked into the build. **Colour** merges the accent picker and the new rainbow mode into one Colors card: the accent presets grew from five to eight, every one of them is editable and resettable, and the picker opens as a proper popover inside the page instead of your operating system's colour window. Turn rainbow on and every list gets its colours by position, so each container, VM, file set, sidebar entry and Settings tab keeps its own hue and stays recognisable at a glance; the eight-swatch palette behind it is editable too. Two sub-options refine it: *reactive* keeps rows quiet until you hover them or until that item's own backup or restore is running, and *rotate* shifts the palette along. **Shape** switches every card, button, badge, toggle knob and picker between round, soft and square in one move, and the choice is applied before the first paint so a reload never flashes back to round. **Animations** sets motion to off, subtle or full, covering page transitions, toasts, the failure shake and the rest; if your operating system is set to reduce motion, that still wins no matter what you pick here. All three are stored in the browser you set them in, so a second machine or browser keeps its own look.

- **One horizontal selector replaced twelve hand-built ones.** The Settings tab strip, the sort and filter chips on Containers and VMs, the restore destination chips on Files, the heatmap domain toggle, the Local/Remote and Local/Off-site pairs, the schedule mode and weekday pills and the drill-type toggle were each their own small invention with its own spacing, sizing and keyboard behaviour. They are now the same control at two scales: a wide "well" track for the page-level pickers (Theme, Shape, Animations, the Settings tabs) and a compact track for the pickers that repeat inside cards. Arrow keys, Home and End move through the options everywhere, segments size themselves to their labels instead of stretching across the card, and a segment that is not selected no longer looks like a filled badge.

- **The Save buttons are gone on purpose, and your changes save themselves.** Every settings tab, the Domains card, the off-site wizard's repository, credential and bandwidth fields and the per-container editors now write your change as you make it. A toggle saves the moment you flip it; a text field saves shortly after you stop typing. Each save confirms with a toast, and if the server refuses it the control shakes and reverts, so a change that did not stick is never mistaken for one that did. If you find the confirmations chatty, Quiet toasts under Settings hides the routine ones while still always showing errors and warnings. This is also why a container's advanced view no longer has four separate save buttons for mount folders, stop-containers, excludes and hooks: none of those needed a commit step, and they now save exactly like everything else (#174). Three places deliberately kept a manual Save because a half-typed value there would be actively harmful: the rclone config paste, the cloud credential-set editor and the login password form.

- **Schedule times are set with a real hour and minute picker.** The browser's native time field is gone from every schedule. In its place is a picker that opens two scrollable columns, hours from 0 to 23 and minutes in five-minute steps, so a nightly run is two clicks instead of typing into a field that behaved differently in every browser. It is fully keyboard-operable with the arrow keys, Home and End, and it follows your shape and colour settings like every other control.

- **Headings, buttons and cards follow one visual grammar.** Section headings became small filled badges notched into the top edge of their card, so you can see where a card starts before you read a word of it. Every square icon button is now one size across the whole app, 32 pixels, instead of three sizes that were each internally consistent but sat side by side inside a single expanded container card. Icon glyphs were redrawn as filled shapes so they still read at small sizes, and the download and backup-now icons no longer look like each other. Destructive buttons dropped their bespoke red and match their neighbours, because red is a status readout here, not a button colour. Nine of the ten pages now sit on one shared shell, one width and one spacing rhythm, replacing five different card widths and two different gaps that had drifted apart page by page. Settings is the deliberate exception and keeps no width cap: capping it would squeeze its seven-tab strip onto two rows, which is a bug an earlier round already fixed once. The VM tab is now literally the container tab's card, so the two stop diverging in small ways.

- **Explanations moved into info bubbles, and tooltips are real tooltips.** Permanent blocks of hint text that sat under fields and headings are now a small info icon you click when you want them, which is what freed the space that made the heading badges and flush-right action buttons possible. Text buttons that only ever did one obvious thing, like Browse, Add registry, Download recovery kit and the per-item restore buttons, became right-aligned icon buttons. So that nothing lost its label, every icon-only control carries a proper tooltip that is styled like the rest of the app and stays inside the window, replacing the browser's own grey title balloon that appeared after a delay and could not be read on a touch screen.

- **Settings is organised the way you would look for things.** The theme toggle and the language picker left the sidebar footer and are now Cards of their own in Settings, General, moved rather than duplicated, so the sidebar shows neither; the footer keeps only the Simple/Advanced toggle. In Paths & Storage, image cleanup, the Unraid update-status setting and container registries were merged into one card, and the flash ZIP export, the plain-export encryption and repository encryption into another, before registries were given a card of its own again; the tab now reads as backup paths, local retention, image cleanup, registries, restic cache and exports & encryption. Off-site split into one card per domain rather than one long tab, Healthchecks was lifted out of the notification-channels card into its own, Email and SMTP moved above it, and the group headings that used to sit above the schedule and off-site cards were deleted outright. The flash ZIP export moved to the Flash page where the rest of the flash backup lives, and the automatic restore-check settings moved from Schedules to Integrity next to the drills they belong with, where each domain's Integrity actions now share one row instead of two. The self-backup card was rebuilt with a plain toggle and the normal schedule builder, the single Appearance card became four, empty toggles with no label are gone entirely, and the version footer, now naming the design-language version alongside the app version, shows on every Settings tab rather than only the first.

- **The Recovery page opens tidier, and two of its buttons got shorter names.** The off-site block and the optional-credentials block are both collapsible sections now, built from the same expander, and both always start closed. That deliberately reverses the previous behaviour, where a block opened by itself if credentials were already stored, so if you are used to arriving and finding your off-site details already unfolded, they are one click away rather than missing. Both triggers also grew from 24 to 32 pixels, matching the rest of the page. On step 1, "Re-check" is now just **Check**, and on step 2 "Restore BombVault settings" is now just **Restore**, in all 42 languages.

- **The Unraid dashboard widget has one name again.** Seven strings called the same thing a "tile" while the plugin itself and the rest of the card called it a widget, so one feature answered to two names inside a single card. Everything says widget now, in every language.

- **Right-to-left layouts and a visible focus ring everywhere.** Running BombVault in Arabic, Hebrew or Persian now mirrors the whole interface properly, and disclosure arrows point the right way. Paths, URLs, snapshot IDs, cron expressions, repository strings and IP addresses are held left-to-right inside that mirrored text so they stay readable and typeable. Separately, every button and link in the app now shows this app's own focus ring when you tab to it, in your accent colour or in that row's rainbow colour, instead of roughly two hundred controls falling back to whatever outline the browser felt like drawing. The whole interface is operable from the keyboard, including the new selectors, the time picker and the colour picker.

- **The conventions are enforced now, so the look cannot drift back.** Seven rules that had each been settled, broken by a later change and settled again are checked automatically on every build: an icon-only button must carry a real tooltip, there is exactly one icon-badge size, a page must use the shared shell, status colour is never used as button chrome, a control must take its corners from the shape engine and its colour from the colour engine, a message a user can see must come from the translation tables, and no user-facing sentence carries an em dash in a language that does not use one. A genuine exception needs a written reason next to the code, and there are two in the app today: the destructive confirm button in the confirmation dialog, and the Dashboard heat-map cell, which is 11 pixels across and would become a disc if it took the shape engine's control radius.

- **Smaller refinements.** Off-site replication shows a live percentage that reads as progress through the whole run rather than jumping per snapshot (#159), and off-site lines in the activity log share one colour again instead of scattering across several (#164). The per-item schedule override no longer offers an "every N days" cadence, and says why it is missing rather than leaving a silent gap, because a per-item override is the one place left with no last-run record to measure an interval against (#166). A container row's five stacked disclosure triggers became one chip row, dialogs centre so their heading badge clears the top of the window, and long list rows show their last-backup time flush right on one line. Every schedule card used to print its cadence twice about 40 pixels apart, once as a badge and once as prose inside the editor; the prose is gone, and the three cards that had no badge (restore checks, weekly digest, restoration test plan) got one, as did the per-item override, which used to show its cadence as plain italic text. On Folders, Fleet and Receiver, the add button in the top-right corner is hidden while the empty-state card is on screen, since that card already offers the same action; it returns the moment the first entry exists, so on a fresh install aim at the card, not the corner.

## ⚡ Improved

- **Status messages became toasts that wait until you have read them.** Confirmations and failures used to appear as small inline text beside the control that produced them, which meant a list refresh, a closing dialog or a navigation could wipe a failure before you noticed it existed. Across the Fleet, Receiver, Files, Flash and Config pages, the Integrity tab, the off-site target and snapshot rows and the folder browser, those messages are toasts now, and a control whose action failed shakes so the failure is attached to the thing that failed rather than floating somewhere on the page.

- **The off-site replication indicator reads as progress, not as a spinner.** While a replication is copying, the indicator is a sliding progress segment in the same style as every other progress bar in the app instead of a spinning dot. It stays deliberately indeterminate rather than inventing a number, because restic's copy step reports nothing machine-readable to count; the live percentage beside it comes from the run's own snapshot accounting.

- **Sentences are punctuated the way your own language punctuates them.** The interface leaned on the em dash as a general-purpose separator, which is an English habit and reads as an intrusion nearly everywhere else. Every user-facing sentence is now broken the way its own language actually breaks one: a comma, a full stop and a fresh sentence, a colon, a danda in Hindi, or simply a space in Thai, which has no full stop. It was not a substitution, so the languages that needed a real grammatical change to lose the clause got one. Bulgarian, Russian, Serbian and Ukrainian keep the dash, where it is ordinary punctuation rather than a habit. The same pass covered the messages the server produces itself, and a build check keeps new ones from creeping back in.

- **The compose file for generic Docker hosts is never pinned to one build (#172).** Automatic dependency updates had begun pinning BombVault's own image to a fixed digest in the compose file people copy in order to run it, which would have frozen every copy of that file on a single build forever and left it drifting from the Unraid template. That is now excluded by rule. The Go base image and the CI actions were refreshed in the same period (#169) (#170) (#171).

## 🐛 Fixed

- **Anyone on your network could lock you out of your own login.** The login throttle was a single global counter that never asked who was knocking. Five wrong passwords in a minute, from anywhere on the network, therefore locked out the real operator's *correct* password for as long as whoever was guessing kept going. The throttle is keyed per client address now, so one source's failures only slow that source down. Two related weaknesses went with it: the table of recent failures could grow without bound under a flood of one-off addresses, such as a botnet or one attacker walking through an address range, and a source that was *already* locked out could be pushed out of that table by such a flood and let straight back in unthrottled. That was reproduced end to end, with the attacker's next request coming back accepted instead of refused. Locked-out sources are now never the ones evicted, and the table is swept and capped. One thing to know if you run BombVault behind a reverse proxy: every request then arrives carrying the proxy's address, so everyone behind it shares one bucket. BombVault deliberately does not trust a forwarded-for header here, because an unauthenticated caller could otherwise pick its own bucket at will, which would defeat the point.

- **BombVault could refuse to start on an existing installation.** Two lines of development each added database changes under the same version numbers, and the ones published on the rolling image had already reached real installations. Starting this build on such a database stopped with a "duplicate column" error before the app came up, which on a backup appliance means it is down with nothing in the interface to fix it from. On the other side of the same clash, a number that had shipped carrying different work would never have run at all, leaving the schedule bookkeeping table missing for good and every "every N days" drill, tamper test and digest silently skipped. Both halves are fixed: the affected steps check whether their work is already done before running, and the piece that could be skipped forever moved to a number nobody has recorded. The upgrade is now tested against every database state that actually exists in the field, including one interrupted halfway, and each must arrive at exactly the schema a fresh install has. (#166)

- **Upgrading could switch off every webhook, Matrix and Apprise alert you had set up.** Those three channels gained their own on/off switches, and a configuration written by an earlier version has no such setting stored, which reads as off. So the first start on the new image turned off every one of them on every installation that had one: backups still failed, nobody was told. The Settings page made it worse by hiding the URL fields behind the switch, so your configuration looked deleted as well. A missing switch is not a decision you made, it is a configuration from a build where the switch did not exist, so BombVault now fills it in from the rule that build actually applied: a webhook was on if it had a URL, Matrix if homeserver, token and room were all set, Apprise if it had a URL. A switch you have explicitly set is honoured exactly as stored, so deliberately turning a channel off while keeping its URL survives. Nothing needs re-entering and no reconfiguration is required.

- **The exclusion assistant hid the very folder you opened it to find (#175).** The assistant beside a container's exclude list used to walk the live filesystem under a thirty-second budget, and on a real appdata tree sitting on an array share that walk does not finish. What it showed you when the time ran out was whatever each folder had counted so far, presented as the total: a folder holding 55 GB was offered as "5.7 GB". The wrong number was the smaller half of the problem. It also decided whether a folder was worth suggesting at all from that same half-counted figure, so a big folder the walk reached late fell under the size threshold and dropped off the list entirely, which means the item you came to find was the one most likely to be missing from the answer. Sizes now come from the container's own newest backup instead. restic already recorded the size of every file when it made that backup, so adding those up per folder is exact and needs no filesystem walk at all: on a real container of 140,000 files the panel answers in 2.8 seconds, and the figures match the backup exactly. The panel also states where its numbers came from, naming the date of the backup it read. Every remaining way the list can come up short is on screen rather than left looking like an empty folder: a scan that stopped names the folder it stopped inside, folders that could not be read or were never opened are listed by name, a size that is only a floor is labelled "at least", and a backup more than a day old warns that anything created since is missing. A container whose folders cannot be reached at all, because the array or the share is not mounted, is told exactly that and pointed at the mount, instead of the reassuring "nothing left to exclude" it used to get. Because the newest backup answers what was backed up rather than what is on the disk this minute, a **Check the folders as they are now** button asks for a live scan whenever you want that second answer, and a container with no backup yet still gets the live walk, since nothing else can serve it.

- **The schedules tab said the flash backup was never actually run. It was, all along.** Turning off "use the Containers schedule for everything" revealed a note under the flash schedule saying the flash backup executor "is not yet implemented, the schedule is stored but not executed". That was true once, early on, and stopped being true without anyone deleting the sentence that said it. Flash backups have been running on their own cadence for a long time: the scheduler starts them, the runs are in your Activity Log and the snapshots are in the flash repository. So if you read that line and concluded your boot drive was unprotected, it was not. It was being backed up on exactly the schedule you set, those backups exist, and you can restore from them. The sentence is gone, in all 42 languages.

- **Read this one if you use the "use the Containers schedule for everything" toggle: it now drives Folders as well.** That toggle used to mirror the Containers cadence onto VMs and Flash only. It now covers Folders too, both when it mirrors the cadence and when it works out on load whether the schedules are already in sync, and its label was rewritten in every language to say so. If you are running with the toggle on and have deliberately given Folders a different cadence, your Folders schedule will be overwritten with the Containers one the next time anything on that tab is edited. Turn the toggle off first if you want Folders to keep its own rhythm.

- **Typing a long secret into the Cloud card could save a fragment of it over the real credential.** The Save buttons in Paths & Storage and the off-site wizard were replaced with auto-save, and the write-only secret fields kept the behaviour that belonged to the button: clear the field after a successful save. With a button that was harmless, because you had finished typing before you clicked. With auto-save it was not. Pause for a moment part way through a 40-character access key, which is what anyone does while reading one off another screen, and the save fired, the field was wiped under the cursor, the rest of the key went into an empty box, and a moment later that fragment was written over the working credential. Nothing reported anything, because a blank field legitimately means "keep the stored one" and a fragment is not blank. The first sign was an off-site backup that no longer authenticated. The field now keeps what you typed until you leave the card, and only the "already set" indicator follows the save. If this has already happened to you, re-enter the affected key once; nothing else needs doing.

- **Settings exports and error messages could hand out your backend passwords.** Three separate leaks, all closed. A repository location can carry its credential inside the address, and the plain settings export wrote every location out verbatim while claiming in the file itself that it held no secrets, and in trusted-LAN mode, where no login password is set, that file was one unauthenticated request away. The plain export now strips the credential out of the address and keeps everything else, the apply logs which entries need the password typed back in, and a stripped address never overwrites a working one on the destination. The credentialed export, which deliberately contains the S3 keys, the REST password, your entire rclone configuration, the SMTP password and the Matrix token, had no protection at all in that same mode, while the recovery kit on the same box correctly refused; both now use the same gate. And a repository password could reach the run history, the weekly digest and the embedded widget in plain text, through error messages that quoted the address back unredacted, most reliably from a tamper test against a malformed address, which never went near the code that scrubs restic's own output. Every error is now scrubbed on its way into the run history, so the fix covers the paths nobody has found yet as well.

- **Two delete paths ignored an append-only primary repository.** When a domain's primary is a remote target you have flagged append-only, BombVault refuses to reclaim space on it, so an attacker with credentials on the box cannot destroy backup history. The bulk container delete and the file-set delete never made that check and went straight through to a pruning delete, as did the per-snapshot delete and the VM delete. All four now refuse, exactly as prune and retention already did (#152). The bulk container delete was also the only destructive operation that did not take the domain lock first, so it could run against the same repository files as a backup that was already in progress, which is a genuine hazard on the network shares this app is usually pointed at. It now waits its turn like every sibling.

- **A single failing operation could take the whole application down.** Every manually started backup, restore and replication ran without a safety net, so a crash anywhere inside one of them took the process with it: the interface, the live progress stream, and every other backup that happened to be in flight at that moment. Scheduled runs were already protected; the manual path now is too, and the run that caused it is recorded as failed rather than left showing "running" forever. Batch operations recover per item as well, so one container, file set or stack member cannot abort the rest of the batch. The whole-server pass got the same treatment, where it matters most, since a pass touches five domains in sequence and runs your own hook commands. Restoring BombVault's own configuration also ran attached to the browser request, so closing the tab or a proxy timeout could kill it midway through writing the staged configuration that the next boot applies without re-checking; it now runs to completion regardless.

- **An off-site destination that was merely unreachable could be reported as an empty location.** Encryption detection has one question it must never get wrong: whether a repository already exists where you are pointing BombVault. "Nothing here" is what licenses it to create a fresh, empty repository at that location, so answering it wrongly means a brand new empty repository sitting next to years of real backups. The old check treated almost any "cannot open the repository" answer as proof the repository was absent, unless the wording happened to match a short list of known network failures. A rest-server behind a reverse proxy that returns 502 while the container is down, a host with nothing listening on the port, or an rclone remote on a fresh recovery instance whose rclone config has not been restored yet: none of those matched the list, so a live repository full of backups was described as an empty spot. The check now works the other way round. The storage backend has to actually say the object is not there before BombVault will call it absent, and anything it cannot make sense of resolves to "cannot tell" and asks you. The cost of that is one extra line on screen and a switch you set yourself. The cost of the old behaviour was a second, empty repository.

- **Closing the browser tab could make BombVault report every repository as unreachable.** When two pages ask for encryption detection at once, they share a single probe pass instead of firing a second set of restic probes at the same repositories. That shared pass ran on the connection of whichever page asked first. Close that tab, navigate away, or let the connection drop, and every probe in the pass was cancelled, including the probes the other, perfectly healthy tabs were waiting on. A cancelled probe does not look like "repository missing" or "repository present", so every repository came back unreachable and the pass handed everyone still waiting a confident verdict of "unknown", with no error attached to explain it. The shared pass now runs independently of whoever started it, under a generous time budget of its own, and each page still gives up on its own terms while waiting. A crash on the leading page also used to leave the shared slot occupied and never released, which wedged encryption detection for as long as the container ran and parked every later request forever; that is released properly now too.

- **Every "every N days" schedule actually ran every N+1 days.** The gate compared the finish time of the last pass against an exact multiple of 24 hours with no slack, while the trigger that evaluates it comes round at a fixed time each day. The stored time is always later than the fire that produced it by however long the pass took, so on the Nth day the gate measured just short, logged a skip, and ran a day late instead. That later run stamped a later time again, so the schedule kept the extra day for good: "every 7 days" ran every 8, and "every 1 day" ran every other day. A late-evening pass that crossed midnight was worse still, because it stamped the following morning. The comparison now works in calendar days and maps the stamp back to the fire that produced it, so "every 7 days at 03:00" means the same weekday at 03:00 whatever the pass cost and whatever the clocks did in between. The catch-up after a restart uses the same rule. The dashboard's "up next" line was reading the raw daily trigger rather than the gate, so on every night the gate was going to close it told you a drill was happening tomorrow when the real one was days out; it now names the fire that will actually be allowed through.

- **A per-item schedule could stop the whole domain from being backed up.** With an "every N days" cadence on a domain and even one container, VM or file set moved onto its own more frequent schedule, the domain gate read the newest successful backup of anything in that domain, including the one item that had just run on its own override. So the single container backing up nightly kept the gate shut, and the other forty-something containers were never backed up by the schedule again. The dashboard read the same number, so its currency chip stayed green throughout. Backing up one container by hand more often than the domain's interval did the same thing, as did an item you had excluded or switched off. The gate now looks only at the items the pass would actually cover, so one item on its own cadence cannot speak for the rest. Separately, the whole-server pass's gate only counted a pass in which every single item succeeded, so one permanently failing item, a container whose volume is gone for instance, meant it never recorded a success and the entire five-domain pass plus its prune and off-site copies ran every night instead of every N days. It now counts a pass that completed, whatever the verdict, the same rule the drill and tamper passes already used. The failures themselves are still reported, in the run's own status and in your notifications.

- **A reboot in the middle of a Backup Everything pass could silently skip a whole backup interval.** The whole-server pass holds one run record open from the first domain through to the batched prune and off-site replication, which on a real box is hours. If BombVault restarted in that window, whether a reboot, an array stop or a container update, the next start closed out the abandoned run and stamped it with a finish time, exactly as it does for any run left hanging. The "every N days" gate reads that stamp to decide whether the pass is due, so a pass that never got past the containers step looked like a pass that had completed, and the gate stayed shut for the entire next interval. The catch-up that exists to recover a missed fire was fooled by the same stamp and reported nothing missed. Nothing failed, nothing was logged, and the only symptom was a week with no whole-server backup in it. BombVault now records separately whether a run reached its own conclusion, and only such a run closes the gate. A run that was cut short by a restart no longer counts, so the pass fires at its next opportunity. The upgrade preserves the current state rather than granting every installation one extra pass, and a pass that ran to the end still counts whatever its verdict was.

- **A scheduled Backup Everything pass and a manual one could run at the same time.** The guard that is supposed to allow only one whole-server pass at a time lived on the button rather than on the pass itself, so a scheduled pass neither set it nor tested it. Press "Backup Everything" at 04:05 while the nightly pass is midway through its VMs step and a second full pass started alongside the first: two run records, every domain backed up twice, and the post-hook fired twice, so your dead man's switch reported the whole server protected twice for one night's window. The guard now belongs to the pass, so every way of starting one is covered, including any added later. A scheduled pass that finds one already running logs a skip and moves on rather than reporting a failure, since the guard doing its job is not an error.

- **A domain schedule with nothing left to back up still ran a full prune and off-site copy.** With per-item schedules in use, every included container running on its own override leaves the domain's own pass with no items at all. It fired anyway: an empty backup loop, then the expensive tail behind it, a real prune and a full off-site repository open and copy, plus a green "0 of 0 items succeeded" notification for a pass that touched nothing. Because the gate reads the last success among those (zero) items, it opened at every single fire, so an "every 7 days" schedule paid that bill nightly and would have done so indefinitely. Containers, VMs and file sets now check that there is something to run before starting, and return. A genuine first run, which does have items, still proceeds normally.

- **A box that booted with the wrong clock could freeze its schedules permanently.** A host that starts with its clock years ahead, from a dead CMOS battery or in the short window before the time is corrected over the network, records its runs with that stamp. Once the clock is right again, every "how long since the last run" calculation comes out negative, and everything that reads it fails in the quiet direction: the "every N days" gate skips every fire from then on, the catch-up never flags the miss, the overdue-backup watchdog reads the domain as perfectly current and never raises an alert, and the dashboard's recovery-point chip stays green for as long as that future stamp sits there. Worse, the poisoned entry keeps winning as "the newest", so a later correctly-stamped run never displaced it and the box would have stayed stuck forever. Currency is now measured against the newest sane run, so a single successful run restores the cadence on its own. The run history still shows the odd entry exactly as it was recorded; only the arithmetic declines to measure an interval against a moment that has not happened yet.

- **Repositories received from another instance were checked at half their configured cadence.** The daily sweep that asks each received repository whether its check is due compared elapsed seconds against the full period, but the stored time is when the previous check finished and an independent check on a large repository takes minutes. So on the day a "daily 04:00" repository came due, the measurement fell a few minutes short, the check was skipped, and the next chance was the following day's sweep. Every received repository was checked every 48 hours, an "every 7 days" one every eight days, and the skipped day logged nothing at all: the only symptom was a last-checked date that quietly lagged. The comparison now works in calendar days, the same rule the backup schedules use.

- **"Every N days" could not be saved on some schedules.** Picking the "every N days" pill on the DR drill, tamper test or weekly digest card produced "this schedule does not support 'everyN'" from the server, and because the whole Schedules tab saved as one object, that one rejection failed the entire tab's save, your container edits included, with a single message that named no card. From the user's side that is indistinguishable from the schedule simply not saving. The scheduler now enforces an interval for those three, so the cadence genuinely works there and the refusal is gone. The five off-site replication schedules and the per-item overrides still cannot use it, because they have no record of a last run to measure an interval against, and the per-item picker no longer offers the mode where it will be refused: previously the pill was there, always failed, and snapped back. A cadence already stored as "every N days" on one of those still shows and stays selected rather than leaving the row with nothing active. The same restriction now applies to settings imports, so a hand-written or older export can no longer smuggle in a value that makes every subsequent save fail. (#166)

- **Importing a settings file could delete your whole-server schedule and lock you out of saving anything.** Applying a settings file rebuilt the configuration from scratch and wrote a default into every field nobody had explicitly listed. The Backup Everything schedule was one of them, so an import switched the whole-server pass off, and the pre and post hooks went with it, including the ping that proves the pass completed. The export carried all three, the preview said nothing, and the first sign was a dead man's switch that stopped arriving. An import now starts from your current configuration and only changes what the file is allowed to set, so a field nobody mapped is left alone. The preview also names the whole-server schedule as its own item, since an apply can switch that pass on for a box that has never run it. The two hook commands are deliberately not taken from the file at all and are kept from the instance being imported into: they are shell commands this host runs, and a settings file is a thing people mail each other. Separately, an import used to skip three checks that a normal save enforces, so a file carrying a path or a cadence a save would reject went in cleanly and then made every later save from every card fail with a message naming a card you had never opened, with no way out short of editing the database. The preview now refuses such a file before you confirm it. (#166)

- **A slow save from one Settings card could revert everything saved from another.** Settings are written as one whole row, and every writer paired that write with a copy of the settings read earlier, so anything saved in between was quietly overwritten while the losing save still reported success. Encryption detection was the worst case: it read the settings, spent up to a minute per repository probing (a dead off-site host really costs that), then wrote its old copy back to change a single flag. The Recovery page starts that on open, so paths you saved in the wizard while it ran, and a login password set in another tab, came back a minute later as if you had never touched them. Reading, changing and writing now happen together, so a save can only ever change the fields it actually decided on. Two more instances of the same shape went with it: saving any Settings field at all used to wipe every named S3 and REST credential set, and a blank secret was matched against a stale copy rather than what is actually stored.

- **The Settings page saves as you type, and edits no longer go missing.** The per-card Save buttons are gone, which turned several latent problems into everyday ones, all fixed here. Two changes made inside one round trip, flipping two switches or editing a cadence with the sync option on, were each built from the state before either had landed, so each carried the other's old value and whichever reply arrived last won: the screen showed both edits, the server kept one, and the loser came back reverted on the next reload. Writes are now queued so each is built on the confirmed result of the one before it. An edit typed within the last moment before you navigated away was thrown away without a toast or an error, even though the field had already shown it as accepted; a pending edit is now sent as the page closes instead of cancelled. Applying a settings import used to leave the page holding the entire pre-import configuration, so a single click on any switch afterwards wrote all of it back and silently undid the import while reporting a successful save; an import now runs through the same queue, cancels edits typed against the configuration it replaces, and reloads the page's own picture of the settings. In the registry list, a row added while a save was in flight vanished when the reply landed and characters typed into another row reverted; add a row and then go back to fix a typo elsewhere and the still-blank new row was trimmed out from under the cursor. The list on screen and the data sent to the server are now separate answers to separate questions. And because the settings request never echoes a stored registry token back, every save from every card submitted a blank one and had it filled in from a copy read before the write, so any save that overlapped a token rotation, even one from a completely unrelated card, put the old token back. That merge now happens against what is actually stored at the moment of writing.

- **A typo in the notification settings was accepted in silence and could switch a channel back on.** The notification endpoints stopped rejecting unknown fields when the configuration gained its own decoding rules, so a misspelled key was dropped without a word. The back-fill that restores the channel switches for older configurations then saw the URL sitting there and turned the channel on, inverting an explicit off. Unknown fields are refused again, while a stored configuration from an older build is still filled in as before.

- **A notification trigger saved by an older build showed nothing selected.** A notification configuration written before the "notify on" setting existed comes back as an empty value, which matches none of the three options, so the control rendered with no segment active and read as broken, especially now that an unselected segment no longer carries its own fill. It falls back to showing "never", which is what the server already assumed, without rewriting what is stored.

- **Unraid-only features could go quietly dark, and now say why.** Every Unraid-only feature, the webGUI notification mirror, the notification test and the dashboard widget plugin, is gated on platform detection, and that detection works by looking for Unraid's own marker on the flash mount. On a genuinely Unraid box whose boot device is not bind-mounted into the container, or was dropped from the template at some point, all of it went dark with no way to tell "the user turned this off" apart from "detection is wrong". There is now a warning banner directly under the Unraid toggle in Settings naming the platform that was detected and what to check, the notification test and the plugin install refuse with that same reason inline instead of failing quietly, and the platform BombVault resolved is written to the log at every boot. The instruction itself described the mount the wrong way round, in the diagnostics and in all 26 languages that carried it; that is corrected.

- **A drill target VM whose name contains a space could not be saved.** The DR-drill target was validated with the strict resource-name rule instead of the rule that applies to VM names, so a perfectly ordinary "Windows 11" or "Home Assistant" was rejected outright and the setting simply refused to save, with nothing explaining which character it objected to. VM names are validated as VM names now.

- **Restoring a zvol-backed VM onto a box whose ZFS pool has a different name.** A cross-instance restore of a TrueNAS zvol-backed VM always built its receive target from the *source* box's pool name, so restoring onto a box whose pool is called something else failed deep inside the restore, after it had already started. The restore now rebases onto the destination pool you name, or refuses immediately with a message that says what is missing rather than failing halfway. One honest caveat: there is still no field for the destination pool on the Recovery page, so today this path is reachable only through a direct API call, and the improvement is that the refusal is now clear and immediate instead of a late failure.

- **Scheduled off-site replication for Folders could silently stop running.** The replication cadence for a domain could come from two places that were allowed to disagree: the field on Settings, Schedules that you can see, and a value carried on the off-site target row itself, which no page shows but which an API call or a settings import can set. When the target row carried a cadence the Settings field did not, the domain was judged to be replicating on its own schedule, so the normal copy after each backup stood down, while no separate scheduled job was ever registered to take its place. The copy fell between the two, with no error and no log line. The Settings field is now the only source ever consulted, matching what actually registers the job, and a domain that genuinely does replicate on its own schedule logs that it skipped the after-backup copy, so a gap of this shape cannot hide again. Nothing to do on your side; it heals itself on the next scheduled run. (#150)

- **A local or mounted-share off-site copy could stay unreadable over SMB.** After copying to an off-site destination, BombVault healed file permissions on the primary repository only. restic creates a repository as root with directories and files nobody else can read, and the off-site copy never got the same treatment. Reading it back as root, which is effectively what an NFS mount does, worked fine and masked the problem; connecting as an ordinary user over SMB, where the share enforces its own permission check, showed the repository's folder names but denied access to everything inside them. Off-site copies are healed to readable permissions on every replication now, the same way the primary already was. A copy created before this fix stays as it was made: reconnect once over NFS, or over whatever connection created it, and let a replication run, or fix the permissions on the remote side yourself, and it reads correctly from then on.

- **Testing an off-site repository could fail with a permission error even though the repository was fine.** The check that verifies a repository opens tried to write a lock file first, for what is a strictly read-only read of a single object that is written once when the repository is created and never changes again. On a share whose SMB or CIFS mount enforces its own permission model independently of the real permissions on the far side, that unnecessary write could fail even though reading the repository would have succeeded, so the Test connection button reported a broken destination that was not broken. The probe never takes a lock now, the same way listing snapshots, stats and diffs already did not.

- **A relative off-site path failed with an unhelpful internal error.** Local and mounted-share off-site destinations are supported and work, but entering an absolute path failed with a raw internal message that gave no hint the field wants a path relative to the Host Data mount. The error now names that mount and shows the exact value to enter, and the setup wizard's repository fields carry the same hint before you get it wrong.

- **A newly created credential set was not selectable until you reloaded the page.** The credential picker on each off-site target and the card where you create credential sets are on screen at the same time, and each held its own copy of the list fetched once when it appeared. So a set you had just created was not offered anywhere, and only a full page reload reconciled the two. Both now read one shared list that refreshes as soon as anything changes it, so a new set is immediately selectable. The off-site target list had the same problem with a symptom of its own: the connection test button only calls itself "Test primary" once a domain has more than one target, and that count came from a stale copy, so adding a second target in the section right below left the button claiming to test the only destination. Accepting a fleet mesh offer creates both a credential set and a target, and now announces both. (#173)

- **The off-site upload percentage now reads as real progress through the run.** A line like "snapshot 15 of 126 (55%)" on a run over an hour long looked wrong, and read as a contradiction, but neither number was miscalculated: the fraction counts snapshots across the whole run, while the percentage was restic's progress within snapshot 15 alone, which restarts at zero for each one. Put side by side, the percentage read as the fraction's value, and over a long run it sawtoothed from 0 to 100 more than a hundred times while "of 126" crawled, which is exactly what a broken progress readout looks like. The two are now combined into one figure for the whole run, which agrees with the fraction beside it instead of fighting it, and the line leads with the percentage: "Off-site upload, Containers, 12% overall (snapshot 15 of 126), 1h 7m". An info bubble next to it states the caveat, which is that this counts snapshots against a best-effort estimate rather than bytes, and snapshots differ in size. The live percentage also went missing for most of a slow transfer, because the keep-alive tick that runs every five seconds republished an empty value over whatever restic had just reported; it now carries the last real figure forward. And when the number of snapshots genuinely cannot be estimated, BombVault says so and falls back to elapsed time rather than inventing a total that would have shown a run that had barely started as nearly finished. (#159)

- **Off-site log lines are one colour again on both surfaces.** The same "Off-site replication done" line was drawn in one colour in the dashboard's activity log and another in the Unraid dashboard widget, because the widget cannot read the app's theme and carries its own copy of the colours; a design pass moved the dashboard's off-site lines onto the accent colour and nothing swept the widget. The premise of that move did not hold either: the off-site status is also used for a finished, successful replication, so completed runs were being painted in the in-progress colour, and with the default accent it landed about one shade away from the colour used for informational lines, leaving two kinds of entry near-indistinguishable in the same scrolling log. Off-site lines are blue again on both surfaces, with the widget's copy now guarded against drifting from the app's again. (#164)

- **A bulk "select all" VM backup could silently skip a VM.** A VM queued immediately after one with a slow off-site replication behind it, twenty to forty seconds of it, could lose its retry window before a run was even recorded, so it dropped out of the batch with no error and no log entry. The retry now gets the same generous allowance a real running backup or restore has. (#154)

- **The Dashboard's "last result" cell could freeze on a run that had already finished.** It fetched the run list once when the page loaded and never again, so if a backup finished and a different domain started afterwards, the cell kept showing the original stale run while the Activity Log right below it, which polls, had already moved on. The cell now polls at the same cadence as the log, so the two can no longer disagree. (#158)

- **The list of other containers to stop during a backup is a picker now, not a text box.** "Other containers to stop during this backup" used to be a free-text area where you typed one container name per line, which meant a typo silently did nothing and you had to remember the exact name. It is a multi-select list built from the containers actually installed on your box, leaving out the container itself and BombVault's own. A name you saved earlier that no longer matches an installed container is kept in the list, marked "not installed" and still removable, rather than quietly dropped. The hint lost its "one name per line" sentence in all 42 languages. That list also could never leave its own card: the card clips its contents so the progress bar follows its rounded corners, and the list was cut off dead at the bottom edge. It floats above the page now, like every other menu in the app, with the same clamping and flip-above behaviour.

- **Failure messages appear in your own language.** BombVault ships in 42 languages, but 56 error strings across seven pages were never translated: "Delete failed", "Failed to load VMs", "Network error" and their siblings rendered in English whatever language you had chosen, and only ever at the moment something had already gone wrong. They had survived every previous translation pass because a fallback message does not look like interface copy to anyone reviewing one. All of them are now translated in every locale, named specifically enough that "failed to load VMs" and "failed to load containers" tell you which half of the app is unhappy, and a new build check keeps untranslated ones from creeping back in.

- **Several controls behaved as if they were broken.** The time picker's popover closed itself a few milliseconds after every open, before you could touch it, because it briefly rendered off-screen and the browser scrolled to reach it, which tripped the picker's own dismiss-on-scroll behaviour. Clicking the info icon inside a field's label jumped focus to the field and closed the tooltip in the same motion, at every such label in the app. A failed "delete all backups" on the Files page showed its error for a single frame before its own refresh wiped it, so the failure was effectively invisible; it is a toast now that stays until you have read it. Removing an off-site target never checked whether the server had accepted the delete, so a refusal, an append-only target for instance, closed the confirmation and reloaded the list with nothing saying why the target had come back. Polling a fleet peer never checked its result either and had no error handling at all, so a failure was swallowed in silence. Both report properly now.

## 🌐 Translations

- **Five strings said the wrong thing in the sixteen newest languages.** The sixteen new locales were written against one wording and then the English was deliberately reworded, without those files being swept, so they kept translating the version that had been replaced. The schedule-override box said in sixteen languages that per-item overrides do not support "every N days" twice over, once from the picker's own notice and once again underneath, and the four off-site progress lines kept the old ordering that made the percentage read as if it belonged to the current snapshot rather than the whole run. All five are propagated now.

- **The Integrity card is named the same thing in every language, and the German Fleet tab reads "Flotte".** The card was renamed from "Integrity" to "Integrity & maintenance" in English and German a while ago without a sweep of the other languages, so 24 of them named only half of what the card actually holds, since unlocking, pruning and deleting live in the other half. All 40 translation files agree now. Separately, the German sidebar still showed the untranslated English word for the Fleet tab and now says "Flotte".

- **Paths inside translated sentences no longer come out backwards in Arabic, Hebrew and Persian.** A slash is a weak character for text direction, so a path written into translated prose with nothing holding it gets swept into the surrounding right-to-left run and its leading slash migrates to the far end, turning a path into something nobody can type back. Three such strings were protected; sixteen more were not, so the Flash tab's explanation, the Storage tab's cache card, the metrics row and the VM SSH card all taught the wrong thing in those three languages. All sixteen are isolated now.

- **Dead translation keys are gone, and a build check stops new ones appearing.** Five keys this release's rework left behind, including the sidebar theme toggle that moved into Settings, were still being translated 42 times each while nothing on screen rendered them. They are deleted from every table, and a new check scans the whole interface and fails the build on an English key nothing renders, with an explicit list of the keys that were already dead before this release which may shrink but not grow.
