Restore failures name their real cause, the append-only check is where you'd look for it, and the removed-container reminder speaks clearly.

## Fixed

- **Restore errors show the real cause (#110).** A failed restore reported only "Fatal: There were 1 errors" — restic emits the actual per-file errors in a JSON form the error extraction didn't understand, so the useful part was thrown away. The run entry, the activity log and the restore panel now carry the decoded causes (path-scrubbed, up to three plus a count), e.g. "restic restore failed: Fatal: There were 1 errors: open [path]: file exists". Applies to every restore path — folder restores, file picks, VM and DR restores.
- **Metadata-only restore warnings work again.** The case that downgrades a files restore to "success with warning" when only permission metadata could not be applied (issue #62) silently stopped matching when JSON progress was introduced — it now recognises both output forms.
- **The removed-container reminder is unambiguous now (#111).** "…is still a scheduled backup target" read like BombVault kept trying to back the container up. It now says plainly: nothing is backed up anymore, the existing backups are kept and restorable, and how to stop the reminder. It also only fires on the first skip (now pinned by tests), while the nightly skip entry stays in the log.

## Changed

- **The append-only check is findable (#109).** It now sits as "Append-only check" in Integrity & Maintenance next to Verify/Prune/Verify restorability (for domains whose off-site repo is marked append-only), with its last-checked state — previously it only existed as a button inside the off-site wizard, under the less obvious name "tamper test".
- **The tamper-test schedule says when it is inactive (#109).** If no off-site repo is marked append-only, that schedule never runs — the settings now show a clear "Inactive — …" note explaining why and how to enable it, instead of silently displaying a time that never fires.
