Restoring from another instance's repository no longer requires that repository to be a mounted folder, and the dashboard stops claiming a nightly server is unscheduled.

## ✨ Added

- **Restoring from another BombVault repository accepts a remote URL, not only a mounted folder.** Point it at the source server's own `s3:`, `b2:`, `rest:` or `sftp:` repository ([#185](https://github.com/junkerderprovinz/bombvault/issues/185)). Anyone whose source server backs up primarily to S3 previously could not restore from it at all, because there was no filesystem path to point at. A remote location asks for that repository's own backend credentials, which is what makes it safe to allow rather than a relaxation: resolving a URL you typed while this instance's own off-site credentials were in scope would have disclosed them to an address of your choosing, and supplying the foreign repository's credentials removes the borrowed authority instead of the check. They are used for that one read-only session and never stored. Two limits follow from the same reasoning. An `rclone:` remote is refused, because rclone reads its remotes from this server's own configuration and ignores the credentials passed per session, so yours could not displace ours; use the repository's native URL instead. And the credentials must match the backend, an access key and secret for `s3:`/`b2:`, a username and password for `rest:`, since a field that contributes no authority should not open the session.

## 🐛 Fixed

- **The dashboard said "Not scheduled" for a server the whole-server pass backs up every night.** With Backup Everything set to a daily time and no domain carrying a cadence of its own, the summary tile reported no schedule while the Settings card two clicks away correctly showed the pass ([#186](https://github.com/junkerderprovinz/bombvault/issues/186)). The tile read each domain's own cadence and nothing else, so a server protected entirely by the pass looked unprotected. It now weighs the pass against the five domain cadences and names whichever fires soonest, saying when that answer is the pass rather than implying a domain schedules itself.
- **The same tile also named a weekly schedule while the real next backup was that night.** This is the other side of the first fault and was not in the report. When every domain has its own weekly cadence and the pass runs daily, the per-domain status deliberately reports no pass at all, because a domain with a schedule of its own is not covered by it in the sense that field describes. The pass was therefore invisible to the tile in exactly the configuration where it fires first. It now travels beside the domain list rather than inside it, so the comparison has both numbers.
- **The peer status a Fleet view polls carries the same field as the local one.** Its payload is documented as interchangeable with the local dashboard's so the same rendering can be reused, and a peer column reading only the per-domain schedules would have reproduced the fault above on someone else's server.

## ⚡ Improved

- **Both status endpoints read their settings row once instead of twice.** Serving the pass's cadence next to the domain list meant reading the same wide row a second time in the same request. The peer endpoint had been doing this all along, since its access check already holds that row.
