BombVault 7.2.0 adds multiple simultaneous off-site targets per domain, plus a set of backup and container fixes.

## Added

- **Multiple off-site targets per domain.** Each domain (containers, VMs, flash, config and file sets) can now replicate to several off-site destinations at once, instead of just one. Add extra targets on the Off-site tab, each with its own repository, S3 storage class, append-only flag, retention and growth budget. Your existing off-site copy is carried over untouched as the first target, so nothing changes until you add a second one. Every target of a domain replicates on that domain's existing off-site schedule.
- **Folder picker in a container's Backup Folders.** The custom-folder row now uses the same folder browser the File Sets editor already had, so you can click through your paths instead of typing them.

## Fixed

- **Very large backups no longer stop at 12 hours.** A single backup run was hard-capped at 12 hours so a wedged job could not hold the repository lock forever, but that cut off legitimate backups over 1 TB, especially to a slower or cloud target, at 11 hours 59 minutes with "context deadline exceeded". The cap is raised to 48 hours by default and is now configurable with the new `BACKUP_MAX_HOURS` variable (set it to a number of hours, or to 0 to remove the cap entirely). It applies to every domain.
- **A fresh off-site repository reads as empty instead of erroring.** Opening the Off-site view for a remote repository (rclone, S3, rest, sftp) that had not replicated yet showed restic's raw "repository does not exist" error. It now shows a clean "no off-site backups yet" empty state, the same as a local repository before its first backup.
- **No more phantom appdata folder.** A container whose data folder BombVault could not infer from its name (common with compose stacks that use a named Docker volume or a non-appdata pool path) was shown with a selected appdata folder that did not actually exist. BombVault now leaves it unset and tells you no data folder was detected, so you can point it at the real one, instead of silently backing up only the container definition.

## Upgrading

Nothing to do, just pull the new image. Your existing off-site setup is preserved as a single target, so backups and restores are unchanged until you add more targets. If you run a backup larger than what fits in 48 hours, set `BACKUP_MAX_HOURS` to a higher number of hours (or to 0 for no limit).
