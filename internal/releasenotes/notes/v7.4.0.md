## ✨ Added

- **Per-item backup schedules.** Some containers or VMs need backing up more often than the rest. Turn on "Per-item schedules" on the Settings Schedules tab (off by default, so nothing changes until you do) and each container or VM gains an optional schedule of its own that overrides the domain schedule. Leave an item's schedule empty and it keeps using the domain default exactly as before, and with the toggle off the interface and behaviour are unchanged. So a critical service can back up hourly while everything else stays on the daily domain schedule.

## 🐛 Fixed

- **Restoring a VM whose name contains a space, from another BombVault.** In "Restore from another BombVault repo", a VM whose name contained a space (for example "Windows Server 2022") was rejected with "invalid item name", while names without spaces restored fine. VM names in libvirt legitimately contain spaces, and this cross-instance path was using the stricter container-name validation. It now validates VM names the libvirt-aware way the normal VM restore already does, so a VM with a space in its name restores across instances (unsafe names are still rejected).

- **The "already exists" prompt during a cross-instance restore no longer misreports.** Before restoring an item from another BombVault, BombVault reads this system's container and VM list to warn you if the restore would overwrite something with the same name. If that list could not be read (for example libvirt or the Docker socket was briefly unavailable, which is common right after a reboot), the prompt still appeared but wrongly said the item "already exists" on this system. It now says BombVault could not verify your local containers and VMs, so it cannot tell whether the item exists, which is what actually happened. A real, verified same-name collision still shows the clear overwrite warning.

- **"Backup path is not mounted yet" no longer sticks on a disk that is actually mounted.** BombVault protects you from re-initialising an empty repository over a backup share that has not mounted yet, which would shadow your real backups once the share reappears. That guard could latch permanently: once a repository had been established at a path, a later run that found the repository missing always reported "backup path is not mounted yet" and refused to proceed, even when the disk was in fact mounted and writable, and a restart did not clear it. This bit first backups to an Unassigned Devices disk in particular, because such a disk mounts after the container starts and can briefly shadow an earlier repository. BombVault now checks whether the destination is genuinely mounted (via the container's own mount table) before refusing: when the disk is mounted it clears the stale marker and re-creates the repository on the live disk, and only when the destination is truly absent does it still hold back, so the protection against shadowing real backups is unchanged.
