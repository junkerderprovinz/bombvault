# Features

Everything BombVault backs up stands in one list, every entry has a page of its own, restores start from one page, and the settings are tiles. There is no advanced mode to switch on; rare things have a card or a window of their own. This page groups the full feature set.

## Backup scope

![The Backups list: every entry with its last runs as a strip, one status and its actions.](assets/screenshots/containers.png)

*The Backups list: every entry with its last runs as a strip, one status and its actions.*

| Section | What is saved |
|---|---|
| **Containers** | Appdata directory plus the container definition (image, env vars, ports, labels, volumes). The whole appdata directory by default; the **Backup folders** card on the container's **Settings** tab ticks exactly which folders the backup covers, with a live count of the paths, a list of what you left out and a **Skip cache folders (CACHEDIR.TAG)** switch. Data a container keeps outside Host Data, such as in a TrueNAS ixVolume, is not backed up, and the run names the folders it left out. |
| **VMs** | VM disk image(s), XML definition and UEFI NVRAM (graceful shutdown or live snapshot, over SSH). Live snapshots fall back to a graceful backup automatically if the snapshot cannot be created, so a VM backup never just errors out. With **Changed blocks only** switched on, a running VM with qcow2 disks is read through libvirt checkpoints, so a backup reads just the blocks written since the previous one, and every snapshot still restores the whole disk on its own. Disks on ZFS zvols are read from a ZFS snapshot over the same SSH link and stored as raw images, so blocks that did not change are not stored again, and a VM whose disks are zvols is backed up as one VM. A restore writes each zvol back in place and first keeps a ZFS snapshot of what it replaces (`bombvault-before-restore-<time>`): `zfs rollback` to it undoes the restore, and it stays until you delete it. An export as files leaves zvol disks out. The state of a passthrough vTPM is saved next to the NVRAM when the domain XML names its path. An emulated vTPM, which TrueNAS sets up for Windows 11 guests, does not publish that path, so keep such a guest's recovery key to hand. See the [VM backup guide](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md). |
| **Flash** | Unraid only. The whole USB flash (`/boot`): OS, license, array config, shares, network and plugin config. Restore is a `.zip` download and never overwrites the live flash. |
| **Self-backup** | BombVault's own `/config` (settings database, sign-ins of the storage locations, libvirt SSH keypair), snapshotted with SQLite `VACUUM INTO` so a WAL-mode database is never captured mid-write. It comes back through the Emergency wizard, which restarts BombVault, so the live database is never overwritten under an open handle. |
| **Folders** | Folder sets: any folder on the server (a share, your documents, a photo library), each with optional exclude patterns. **Add** on the Backups page lists the shares it found and takes any other folder. Folder sets have everything the other sections have: schedules, retention, off-site copies, checks and restore drills. |
| **ZFS datasets** | A dataset together with every dataset below it, read from one ZFS snapshot so all of them come from the same instant, and stored with restic like a folder: deduplicated, browsable, single files restorable. New child datasets join on their own, single children can be left out, and a child that cannot be read is skipped and named. Optionally, containers are stopped or a command runs for just the instant of the snapshot. Volumes are not included: a VM's volume is backed up with its VM, a volume without a VM is not backed up yet. A ZFS entry can also keep a block-exact replica on a second ZFS server. See [ZFS datasets](zfs-datasets.md). |

## Backups and entry pages {#backups}

- **One list.** Containers, VMs, folder sets, the flash drive, ZFS datasets and the self-backup stand in one list under **Backups**. Tiles above it pick a kind, and **Filters**, **Sort** and **Search** narrow it down. Sort goes by name, status, last backup, size or schedule, in both directions, and search finds a container by name, image or IP.
- **The last runs as a strip.** A row shows its last fourteen runs as small squares and one status. Everything else about it is in the info bubble beside its name, and the row shows the same text while the mouse is over it.
- **Select like in a file manager.** Ctrl+click, Shift+click and Ctrl+A pick rows, a long press does it on a phone, and **Select** under **More** starts a selection. A picked row shows a check in place of its icon, and every row has a right-click menu. A selection can be backed up, or paused and resumed in the schedule. Several entries are restored together on the Restore page.
- **Add** opens one window for what BombVault cannot guess: a folder or a ZFS dataset. Containers, VMs and the flash drive show up on their own. On a host without Unraid whose Host Data reaches `/etc`, the window offers **System configuration**, a starting `/etc` folder set you review before saving.
- **Don't back up** leaves an entry out on purpose. It then stops counting as not protected, and **No longer exclude** brings it back.
- **More** on the Backups page holds **Discover backups**, which rebuilds entries from what the storage locations hold (for example after a fresh install), and **Restore stack** for Compose projects.
- **A page for every entry**, with a header that names its state and holds its actions, a back button left of its icon that leads to the list, and three tabs:
    - **Backups** lists the snapshots with a bar per day, the storage locations that hold them and the database dumps.
    - **Settings** holds the schedule and storage location, the repository, the backup folders, exclude patterns, other containers to stop, commands before and after, database dumps and former names. Schedule and storage location follow the section's default until the entry gets its own.
    - **Verify** shows the checks, the size by folder, the entry's anomaly monitoring and its recent runs.
- **Mark and compare.** A snapshot can carry a tag of your own, and **Compare with another snapshot** lists the files that came, went or changed between two of them. A VM compares the disk images and says how much of them differs.
- **Export** writes a snapshot, every snapshot of an entry, or a container or VM as it is right now to the export folder on the server, as tar, zip or a restic repository of its own.

## Restore

![The Restore page: pick a section, search for an entry and choose a backup.](assets/screenshots/recovery.png)

*The Restore page: pick a section, search for an entry and choose a backup.*

- **One page.** **Restore** lists the sections as tiles. Search for what you want back and pick a backup from a list with the newest at the top; the recommended one is marked, after an anomaly it is the last one before it. **Open entry** leads to the entry's page, and a running restore shows under **Running now**.
- **One window for every kind.** It asks in steps: which **Backup** (the recommended one is preselected), which **Source** (local is fastest), **What** (all, or the files and folders you pick) and **Where to**. A scene shows the target you picked, and **What happens** says it in words before you start.
- **Several at once.** On the Restore page, Ctrl+click, Shift+click, Ctrl+A, a long press or **Select** pick entries, and a picked entry shows a check in place of its icon. **Restore** opens one window for all of them. Each takes its newest backup, or its newest from one moment you pick for all, and goes next to its original or replaces it. The restores run one after the other, and each row shows how its own went. The flash drive comes as a ZIP to download. ZFS datasets and the self-backup are restored one at a time.
- **Next to the original is the default.** A container comes back as a second container named `<name>-restored`, with ports of its own, while the original keeps running. A VM's disks and NVRAM land in a folder named `<folder>-restored` next to the original, without a second VM. A folder set comes back as `<path>-restored`. The copy is listed under Backups as excluded until you add it to the schedule.
- **Replace original backs up first.** With **Back up the current state first**, which is on by default, BombVault backs up what is there now before it replaces it, so you can go back. If that backup fails, the restore does not start. Replacing asks you to type the entry's name.
- **To a folder** writes just the files, for browsing. A ZFS dataset can also be restored **Into a new dataset**, and the flash drive comes back as **Download as ZIP**.
- **Containers are automatically reinstalled.** The container definition is replayed against the Docker API, so the container reappears in the Unraid Docker tab exactly as it was.
- **GPU, limits and links come back.** A restored container gets back its resource limits, log driver, DNS settings, legacy links and its GPU or runtime (`--gpus`, `--runtime=nvidia`). On a host without that GPU driver or runtime the restore says so and offers **Restore without GPU and runtime**, also after restoring several containers or a stack. A link to a container that is missing, or stopped while the restored one starts, is left out, and the run history says so.
- **VMs are automatically recreated.** The XML is re-imported over SSH so the VM reappears in the VM Manager with its disk and UEFI NVRAM reattached, even after the VM was deleted.
- **Flash restore is a `.zip` download.** It streams to your browser as `flash-<id>.zip`, ready to drop into the Unraid USB creator. The live `/boot` is never touched.
- **One plugin at a time.** The flash restore window lists the plugins in each flash backup with their version and size, and puts a single one back into the running flash: its `.plg` file, its folder under `config/plugins` and the package files the backup holds. Nothing else on the flash changes. Unraid installs the plugin on the next boot, or right away under **Plugins, Install Plugin**.
- **Scheduled flash zip export.** After every flash backup, optionally write the snapshot out as a plain `.zip` to a folder you pick (a single overwritten `flash-latest.zip` or a rolling history). It is the **Flash zip export** card on the flash entry's Settings tab. Point it at a Syncthing or rclone folder so your bootable-USB backup leaves the server automatically.
- **Pre-flight conflict check.** Before anything is stopped or removed, restore verifies the container's static IP and published host ports are free, and aborts with a clear message instead of leaving a half-finished restore. The restore check also names a network that is gone, such as one a deleted TrueNAS app had created, and advises reinstalling that app first.
- **Checks before the restore.** The window first checks that the repository answers, that the stored key opens it, that the restore point is there and that the target has room for what the restore writes. Start stays locked while a check fails, and the (i) in the button says which one.
- **What the restore changes.** Before you confirm, the window shows what the restore does compared with what is there now: new, replaced and unchanged files, with the list on request, and the files at the target that are not in the backup and stay where they are. For containers and VMs it also compares the settings the restore recreates with the running ones: image and tag, ports, variable names and volumes, or memory, vCPUs, disks and network. restic works this out as a dry run from size and modification time, without reading the files; a very large tree stops after 30 seconds and says so. A stack restore checks and plans every member and names the one that blocks it.
- **Shared folders.** An in-place restore names every other container, running or not, whose bind mount reaches into a folder it writes to, for example "this path is also used by nextcloud-db". It warns and does not block.
- **ZFS dataset restore.** Restore one dataset of an entry into its place (after a ZFS safety snapshot that stays until you delete it), into a folder, into a new dataset, or only the files you pick, or every dataset of a backup into a folder. A dataset is never rolled back or replaced.
- **Restore keeps the run-state.** A container or VM that was running when backed up comes back running; one that was stopped stays stopped. Switch on **Leave stopped afterwards** to recreate without starting.
- **Restore a whole stack.** Containers from the same Docker Compose project that have at least two backed-up members form a stack. **Restore stack** under **More** on the Backups page rebuilds every member from its latest backup, then optionally starts them in `depends_on` order.
- **Live progress, cancel and busy feedback.** A long restore shows a live percentage bar and can be cancelled with a type-aware confirmation. A cancelled restore is recorded as *cancelled*, not failed. The window can be closed; the progress also shows under Restore.
- **Emergency wizard.** For a server that is gone or was set up again, with the recovery kit, through the group or with the typed key. See [Off-site & recovery](offsite-recovery.md#emergency).
- **From an old backup folder.** A read-only session opens another BombVault's repository with that instance's recovery kit or its typed `APP_KEY`, so you can pull a container from server A to server B without touching your own settings. See [Off-site & recovery](offsite-recovery.md#restore-from-another-bombvault-repo).
- **ZFS properties come back.** Every ZFS backup keeps the locally set properties of each dataset, such as compression, record size, quota and case sensitivity. A restore into a new dataset creates it with them, and a restore into an existing dataset shows them and sets them only when you ask for it. See [ZFS datasets](zfs-datasets.md#new-dataset).
- **Import from the Appdata.Backup plugin.** Under **Other sources** on the Restore page, point BombVault at the plugin's backup folder. Each container archive becomes a restore point of its container, dated when the plugin made it. Archives imported before are skipped, and the archives themselves are only read. The container needs one backup in BombVault first, so the restore has its definition. Retention leaves imported restore points alone, so delete one yourself when you no longer need it.

## Storage & scheduling

- Incremental, deduplicated backups via restic, so even large VM disks do not balloon the repo.
- **Storage locations.** Local folders and off-site places stand in one list on the **Storage locations** page, which you open from its settings tile or pin to the sidebar. The folder on this server that the sections back up to is called **Local**, as on the placement buttons. Every location has a page of its own with its connection, credentials, delete protection, copy settings, retention and rules per section, and a vessel that shows how full it is and when it fills up at the growth of the last weeks. See [Storage locations](offsite-recovery.md#destinations).
- **Kinds of storage:** a local path, SMB shares and WebDAV servers (Nextcloud, ownCloud, SharePoint) through rclone with no host mount, NFS (mount the export on Unraid and use it as a local folder), native restic backends without rclone (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`), or any rclone remote via `rclone:<remote>:<bucket>/path`. All credentials are stored encrypted.
- **SSH targets need nothing installed on the far side.** `sftp:` only requires an SSH server, so a bare Raspberry Pi (no Docker, no restic) works as an off-site storage location. Host keys are pinned automatically on first contact.
- **3-2-1 as a picture.** The **Storage locations per section** card draws which section is backed up where. Every line from a section to a location is a switch for every section, **Local** included, and one click switches it at once. **Graph / Switches** gives the same as plain buttons. A section with only off-site locations backs up straight to them, into a repository BombVault picks there itself, and a section with every line off says **Not backed up**. Where entries back up somewhere other than their section, the flow says how many, such as **2 entries differ**, and leads to them. Flash, ZFS datasets and the self-backup back up to their local folder and copy off-site from that backup. Their line to **Local** can be switched off too; their backups then go straight to their off-site locations, and a ZFS entry with a replica and no location at all only sends its replica.
- **Off-site copy (local + remote).** Keep the fast local backup and add one or more off-site storage locations, copied with `restic copy` on a best-effort basis (an off-site hiccup never fails the local backup). A copy only transfers the data packs the location does not have yet. Each location's **Copy** card sets **When to copy** (**After every backup** or a plan of its own) and its bandwidth, and a section can copy on its own plan under **Settings, Schedule**.
- **Several storage locations per section.** Each section can copy to several off-site locations at once. A location's **Rules per section** give one section its own retention, compression or repository there, while sign-in, credentials, bandwidth and timing come from the location.
- **Move a section's history.** **Move** on a storage location takes a section's copy, with its whole history, to another storage location. The old place keeps everything; BombVault deletes nothing there.
- **Named repositories.** The **Repositories** card under **Settings, Storage locations** writes your backup locations down once, a local path or any restic remote with its own credential set, to be chosen as an entry's location. A row shows how many entries point at it, and a repository that an entry or a default uses cannot be moved or deleted, because BombVault never moves a backup that has already been written.
- **Several sets of credentials.** The shared cloud credentials apply everywhere by default, but any storage location can use a named set instead (**Additional credential sets** under **Settings, Storage locations**, or **Credentials** on the location's page), so a Hetzner S3 bucket and a local Garage server can run side by side, each with its own key.
- **Placement per entry.** The **Schedule and storage location** card on an entry's Settings tab has a row of buttons, **Local** and one per off-site storage location, and the lit ones get its backups. A share that already sits on a NAS does not have to go to B2 as well. An entry that follows its section moves along when the section's places change, and the place it left shows as **Earlier backups only** and can still be restored from. A location chosen on the entry stays fixed from its first backup on, the copies can change at any time, and the card says how many sites hold the entry and whether 3-2-1 is met. **Follow the default** asks first and says what that drops or uploads. See [Placement per entry](offsite-recovery.md#placement).
- **Manual backup order.** The **Order** card under **Settings, Schedule** sets the exact order containers and VMs are backed up in. Scheduled runs and the full backup follow it; anything you leave unordered keeps the most-overdue-first order, and a single backup is unchanged.
- **Retention as a timeline.** Each storage location keeps backups by **How long to keep**: **Short**, **Balanced**, **Long** or **Custom values** for the latest backups, days, weeks, months and years, pruned automatically. The timeline shows which backups a rule keeps. **Ask before keeping less** asks before a shorter rule deletes older backups whose only copy is there. A section can keep its own values at one location under **Rules per section**.
- **Compression per repository:** Off, Automatic (restic's default) or Maximum, set on each storage location and, for one section, under its rules there. Backups, off-site copies and prune write with it, and the recovery kit names it, so plain restic can keep writing the same way.
- **Schedules read as sentences**, such as *Weekly on Sunday at 04:00*, and are edited from that sentence. **Settings, Schedule** holds them all: the **Week** band with every planned run from Monday to Sunday, the **Full backup** with one command before and one after, **Plans per section**, **Off-site copies per section** and the **Scheduled entries**. **Every N days** also works for the restore drill, the tamper test and the weekly digest.
- **A section with its own plan leaves the full backup.** The **Exception** button under **Plans per section** gives a section a plan of its own, and that section then runs at its own time and not again in the full backup, so nothing is backed up twice. **Back up everything now** still takes every switched-on section. With **Own plans per entry** switched on, a single container, VM, folder set or ZFS dataset can get its own plan on its page, and it then leaves the full backup too.
- **Update containers after a successful backup.** One switch under **Settings, Schedule, Updates after the backup**, off by default, pulls a new image only after the backup before it has finished. A single container can be set differently on its own page.
- **Snapshot instead of stop.** A container whose data lies on ZFS is stopped only while BombVault takes a snapshot of that data, usually a few seconds, and starts again right away. The backup is then read from the snapshot and lands in the repository under the same paths and tags as one taken with the container stopped, so restores, restore checks, **Compare with the backup before** and the anomaly checks treat both alike. The command before the backup and the database dump still run first, the other containers to stop go down and come back with it, and the command after the backup runs as soon as the container is up again. An update after the backup still waits until the backup is done; when a newer image arrives, the other containers go down once more for the recreate. This needs the SSH connection to the host, as [ZFS datasets](zfs-datasets.md) do, and works on an Unraid user share that lies on a single ZFS pool. A container with part of its data on the array or another file system is stopped for the whole backup as before, and its run says why. A container with none of its data on ZFS is stopped as before, without a note. On TrueNAS the app also needs the `SYS_CHROOT` capability, see [TrueNAS SCALE](getting-started.md#truenas). The switch is under **Settings, Schedule, Snapshot instead of stop**, on by default, and a single container can be set differently on its own page. Its runs show **Snapshot** and how many seconds the container was down. Should BombVault stop in the middle of any container backup, it starts the containers it held down again the next time it starts.
- **Wait until the app is idle.** A container can let its scheduled backup wait while its app is busy, for at most the hours you set, and start as soon as the app is idle. A media server counts as idle when it isn't streaming, any other container when its CPU and traffic stay below the limits in the **Idle before backup** card under **Settings, Schedule** for a few minutes (on the host network only CPU counts). The waiting backup shows in the activity log and on the container with its reason and deadline. It holds no lock, so the other containers go ahead. Manual backups never wait. The members of a compose stack due in the same run wait together, and a wait carries on with its deadline after a restart. Switching the containers off drops every waiting backup, and switching their schedule off drops the ones its runs held back. Lowering the hours shortens a wait that has already begun.
- **Off-site bandwidth limits.** Cap the restic upload/download rate so copies do not saturate your WAN, in the **Off-site bandwidth** card under **Settings, Storage locations** and per location in its **Copy** card.
- **Streaming first.** While a media server such as Plex, Jellyfin or Emby streams, off-site copies upload at a lower limit and return to the normal one a few minutes after the stream ends. BombVault reads the media servers' outgoing traffic from Docker. REST, S3, B2, Azure, Google Cloud, Swift and rclone over HTTP slow down in the middle of a copy; SFTP and local or mounted folders take the lower limit at their next copy step. A media server on the host network can't be measured. It is the **Streaming** card on the Storage locations page.
- **Cold and archival storage class (S3).** For an S3 storage location you can pick the storage class, restricted to restore-readable tiers (Standard, Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier Instant Retrieval) so archival pricing never silently breaks a restore. The deep-archive tiers that first need an async thaw (Glacier Flexible, Deep Archive) are left out, because restic cannot read from them. Native S3 backends only; rclone remotes set their class in the rclone config.
- **Backup folders stay copyable off-box.** After every backup BombVault relaxes the local repo tree to dirs `0755` / files `0644` (repos are encrypted, so nothing is exposed) so a non-root sync user over SMB is not locked out. Recovery definitions live inside each repo, so a copied repo folder is fully self-contained.

## Insight, verification & monitoring

- **The overview.** It starts with a status head and four cards: **Needs you**, **Protection status**, **Storage locations** with a forecast of when each fills up, and **History** with the runs and the log. The ring in the head shows how much is protected and turns into a progress ring with its stations while a backup runs. More cards wait under **Customize**: **Anomalies**, **Not backed up**, **Calendar**, **Storage**, **Overview**, **Statistics** and **Host Integration**. Every card can be moved, resized and hidden, and the layout is saved in the browser.
- **One count everywhere.** Every card counts the entries of the switched-on sections the same way. An entry outside the schedule does not count as protected, however recent its last backup.
- **Pause from the entry.** **Pause schedule** takes an entry out of the schedule and out of the full backup, and **Resume schedule** brings it back. It sets the same switch as **On schedule** on the entry's Settings tab, so the two always agree. A paused entry wears a grey **Schedule paused** badge, and **Back up now** still works.
- **Protection status.** Every section has four checks: a current backup on this server, a copy off-site, delete protection there and a trial restore from there. An overdue backup turns red instead of hiding in a log, and a click on a section shows the details.
- **Calendar.** The last 90 days, one square per day with that day's backup outcome. A click on a day shows its lines in the log under History.
- **Run timing everywhere.** Every run reads `start, end (duration)`, and each entry carries its own **Recent runs** list on its Verify tab.
- **Repository size & dedup trend.** The **Storage** card shows how much each section takes up and how well the data deduplicates.
- **Restore-verification drills.** BombVault periodically proves your backups are restorable (`restic check --read-data-subset`, bounded), set up under **Settings, Verify, Automatic checks**. The **Check backups** card on the same tile shows the result per section and holds **Unlock** and **Prune** under **More**.
- **Restore check after the first backup.** When an entry's first backup is done, BombVault restores a sample of it (up to 100 files and 256 MiB) into a temporary folder under the restore folder, has restic read every file back against its hashes, and compares the sizes with the backup. A file too large for the sample, such as a VM disk, gets its first 64 MiB read back instead. The entry's Verify tab shows the result, a failure goes out as a notification, and **Check restore** runs the same check on the newest backup whenever you want. Later backups do not repeat it.
- **Start test.** Checking the bytes does not show that the app comes back. **Start test** on a container's Verify tab restores its newest backup into an isolated copy and starts it: a name starting with `bombvault-test-`, an internal Docker network of its own with no published ports and no way to the LAN, 1 CPU and 2 GiB of memory, and the data in a temporary folder under the restore folder. The test passes when the container's healthcheck reports healthy, or, without one, when its first exposed port answers from inside that network, or, with neither, when it keeps running. The original container is never stopped or changed, and the copy, its network and its data are removed afterwards, also after a restart of BombVault in the middle of a test. Containers on the host network, privileged ones, ones with devices and ones that need another container are shown as not testable. Switch on **Start test** under **Settings, Verify, Automatic checks** to test one container per run, the one tested longest ago first. The copy carries none of the original's labels and runs without the capabilities, security options, sysctls and cgroup parent the original adds. A container that needs them fails its test, and the result names what the copy ran without.
- **Self-healing operations.** A provably orphaned restic lock (left by a mid-operation restart) is force-cleared and retried once, automatically. Retention is identity-stable (pruned per entry, immune to path or host changes) and a retention failure sends a notification.
- **Warnings the folder scan cannot see.** The exclusion assistant answers a size question. Some of the most expensive backup mistakes are not size questions, so it also carries app-specific caveats about how an application stores its data. The one it exists for: Immich keeps every photo's albums, faces and dates in a PostgreSQL database that runs in a *separate* container, so a file-level backup of the Immich container restores the pictures without any of that, and the restore looks like it worked. The warning shows whether or not any exclusion is offered, including on a container with nothing selected to scan, because the caveat is true either way.
- **Not backed up (coverage).** An overview card naming everything on the server that no scheduled backup covers, with the reason for each: never added to BombVault at all, present but not in the schedule, its own schedule set to off, no schedule switched on anywhere, or every storage location of its section switched off. The protection status answers a different question, namely whether the backups that *are* scheduled ran on time, and it cannot see the container nobody ever set up. Containers are read from the live Docker list rather than from BombVault's own rows, because an entry with no row is exactly the one that needs naming. A section you switched off and an entry you marked **Don't back up** are left out of the count, since that was your choice.
- **Retention preview.** The **Preview** card under **Settings, Storage locations** shows what the next run is about to delete, before it happens: per repository and per entry, with the restore points named. It takes no repository lock and changes nothing, so it answers even while a backup is running. Retention switched off says so rather than showing an empty list, an append-only repository is labelled as one (retention never runs there at all), and a repository that could not be reached is named instead of silently missing.
- **Anomalies.** Every backup of a container, VM, folder set, database dump, the flash drive and the self-backup is compared with that entry's own history. The checks look at the new data a run stored, against the largest usual amounts of recent backups and against the usual rate per hour; at a backup that stored most of the data again, which includes files that were renamed and rewritten; at the source size and file count restic reports for each entry and each database dump; at restic's own backup time; at failure streaks and intermittent failures; at restore checks that stopped passing; and at the free space of local, SFTP and rclone repositories, projected from the repository's growth. An entry learns from its first 10 backups, while an almost empty source, a rewrite of most of the data and failures are checked from the start. Sensitivity (Strict, Balanced, Permissive) and the lowest severity that sends a notification are set globally in the **Anomalies** card under **Settings, Verify** and can be changed per entry on its Verify tab. Warnings close by themselves once the cause is gone; critical findings about lost data and a filling disk stay until you acknowledge them, and an acknowledged finding is not raised again until its cause has gone away once. **Mark as expected** makes a new level normal after 10 backups but never switches off the almost-empty check, and a changed selection starts the entry's history afresh by itself. While a source is almost empty, has shrunk sharply or had most of its data stored again, retention keeps that entry's old backups until you acknowledge the finding or mark it as expected, and the finding links to the last good backup. A notification goes out once per episode, and failures and restore checks that already notify are not reported twice. What it does not do: S3, B2 and REST repositories have no free-space figure, on the Unraid user share the free space is that of the whole array, and backups made before restic 0.17 carry no size history. ZFS entries are checked too, dataset by dataset: every dataset of a tree has its own history, one that was emptied or could no longer be read counts as lost data, and only that dataset's old backups are kept. How a ZFS entry is watched dataset by dataset is described under [ZFS datasets](zfs-datasets.md#anomalies), and an assistant can read the open findings through the [MCP server](mcp.md#tools). A finding about the size or file count of a source is dated to the first backup it showed in, and **Compare with the backup before** lists the folders where files went away, came in or changed, with a note when nearly all of it sits in a search index, a cache or thumbnails that the app rebuilds by itself.
- **The Anomalies page.** Tiles for **Critical**, **Warnings** and **Notes** pick a severity, with open and closed findings above the list. A critical finding sits on the same surface as the others; the severity shows in its badge and its coloured edge. A finding offers its fix first, and its details show the value as a curve over the usual range. When nothing is open, a ring per entry shows how far detection has learned what is normal.
- **Recommended excludes per app.** For well-known images (Plex, Jellyfin, Emby, Sonarr, Radarr, Lidarr, Readarr, Prowlarr, Immich, Nextcloud, PhotoPrism and Tautulli, from linuxserver, hotio, binhex or the official publisher) the exclusion assistant in the **Exclude patterns** card offers the folders the app fills again on its own: caches, logs, preview images and posters. Each entry says what it holds, any of them can be switched off, and nothing is excluded until you press **Exclude selected**.
- **Bug report.** **Bug report** on the **Help** card under **Settings, Info** downloads a redacted ZIP for a GitHub issue: the host-integration check, your configuration with every secret removed, the recent runs, what is scheduled next, and the recent log. It also carries how the last dump of each database went, the ZFS entries with the mounts the container sees, the open anomalies, and how many MCP keys exist (never their names). Passwords, tokens, the rclone config, notification credentials and any password embedded in a repository location are all stripped, and the bundle says so in its own manifest, because a support file must never be mistaken for a configuration backup. It requires a login password for the same reason the recovery kit does. The log it carries is this container's output since it last started; for a crash that restarted the container, `docker logs` remains the place to look.
- **Recovery kit.** **Download recovery kit** under **Settings, Restore** gives you the key, the derived restic password and the exact repo locations and commands, so you can restore without a running BombVault. It needs a login password. See [Off-site & recovery](offsite-recovery.md#recovery-kit).
- **Export and import your settings.** The **Export / import settings** card under **Settings, System** writes your whole configuration (section settings, storage locations, schedules, retention, notifications) to a portable JSON file, so moving to a new box or cloning a setup does not mean re-entering everything by hand. You choose whether to include the off-site and notification credentials; with them the file is as sensitive as your recovery kit. Import shows a preview and asks for confirmation, and it never touches your backup data or history.
- **Notifications.** Webhook (Discord / Slack / Gotify / ntfy), Matrix, Healthchecks.io, email (SMTP), a self-hosted [Apprise API](https://github.com/caronc/apprise-api) server, and Unraid's native notification system. Policy per backup: never / on failure / always. A scheduled run of many entries can send one *N of M items succeeded* summary. Healthchecks gets the full lifecycle (`/start`, then success or `/fail`) whenever a URL is set.
- **Weekly digest.** One message a week through the same channels: run counts, how much new backup data arrived, whether off-site is current, and the top failures. Off by default, with its own cadence under **Settings, Notifications**, so a quiet week is reported as one too.
- **Prometheus `/metrics`.** Opt-in (default off, optional bearer token) in the **Services** card under **Settings, Integrations**, for Grafana or Uptime Kuma. Exposes backup status, sizes and timestamps, with no secrets or paths in the labels.
- **HTTP API, Home Assistant and mDNS.** Scripts and dashboards get an API under `/api/v1` with named tokens, read-only or allowed to start backups. Home Assistant finds BombVault through MQTT discovery, as a device with sensors and, if you allow it, a backup button per section. And BombVault announces itself on the network as `bombvault.local`. See [API and integrations](api.md).
- **Free space and weeks until full.** Local repositories, SFTP repositories and SMB or WebDAV storage locations that report it show their free space and how many weeks are left at the current growth. S3, B2 and REST repositories say "Size unknown", since those backends do not report it.
- **Size by folder.** On the Verify tab of a container, VM or folder set, **Size by folder** shows which folders and files take the space in the newest backup and how much of each the latest backup brought in new or changed, one level at a time. BombVault reads it from the repository's index without reading the files, and keeps it current after each backup once you have opened it.
- **Why a backup was slow.** While a backup runs, BombVault watches how busy the CPU, the disks and the network are. When a backup takes much longer than usual and one thing was clearly at its limit, the run says so, for example "The target disk disk1 was 98% busy" or "BombVault used 100% of the CPU limit of its container". Otherwise it says nothing.
- **Changed since the last backup.** A container that was recreated with another image, other ports, variables or volumes since its last backup gets a mark beside its name. Its (i) lists what changed, variables by name only. It is only a note and goes away with the next backup.

## Ransomware protection

- **Delete protection (append-only).** Switch it on for an off-site storage location so ransomware or a compromised host cannot delete or rewrite your backups. The far side (a `restic/rest-server` in `--append-only` mode) enforces it; BombVault only ever verifies it and never shows green on a configuration claim alone. A folder on this server cannot refuse deletion, so local locations do not offer the switch.
- **Tamper test.** BombVault periodically proves the append-only guarantee by actually attempting a delete against the off-site repo (aimed at a non-existent object): refused means protected, accepted means not protected. An inconclusive result never flips the stored verdict. **Test delete protection now** on a location's page runs it on demand.
- **Guided setup.** **Add storage location** walks you from the provider through the sign-in, a connection test and the folder to an honest word on delete protection and the sections that back up there.
- **DR drills (off-site).** The trial restore puts a real target from the off-site repo into a sealed-off sandbox, verifies it file-for-file and byte-for-byte, then cleans up. See [Off-site & recovery](offsite-recovery.md).
- **Protection status.** The overview card checks every section for a current backup, an off-site copy, delete protection there and a trial restore from there. It only goes green on verified facts.
- **Growth-budget alarm.** For an append-only location (where old snapshots are never pruned from here), set a size budget and get alerted before it runs away.
- **Deleting needs a password.** Deleting the backups at a storage location needs a login password and a sign-in at the instance itself, so neither a paired phone nor an open interface can do it.
- **Pairing by phrase.** Instances join one group by twelve words: create the phrase on one, type it on the next. Members on the same network talk directly, the others through a relay (the project relay, your own, or none), and every call between them is end-to-end encrypted. The group carries the protection status on the Instances page, role requests, storage offers and what a receiver or fetcher needs once its role is allowed, never backup data and never the APP_KEY. See [Off-site & recovery](offsite-recovery.md#pairing).
- **Instances and roles.** Switch on **Instances** under **Settings, Instances, Multiple servers** for a page with a card for every instance of your group, this one included: its address, whether it is connected, and each section's protection with its last backup. Its roles stand on the card as tiles: **Receiver**, **Fetcher**, **ZFS server** and **Key keeper**. A role starts only after someone on the other instance presses **Allow**, and the group shows as a net of who does what for whom. **Check now** asks a member to verify one section's repository. Nothing on the page can start a backup, restore or delete anything on another box. See [Instances and roles](offsite-recovery.md#roles).
- **Storage offers.** A member can offer its own off-site storage to another member over the group. The other admin sees the offer in the member's **Details** on the Instances page and accepts or declines it; accepting creates an ordinary credential set and storage location. Only connection details travel this way, never backup data.
- **Received repositories (receiving side).** On the box that receives append-only off-site copies from another BombVault, switch on **Receiver** under **Settings, Instances** and add the received repository in the sending member's **Details**, read-only (opened with the sending instance's restic password, which arrives over the pairing group). You see its snapshot inventory grouped by source, when each source last arrived, and can run an independent `restic check` on the receiving hardware. It alerts you when a source stops sending within a window you set (a dead-man's switch) or when an integrity check fails. Strictly read-only, so it never writes to the received repository, and off by default. See [Off-site & recovery](offsite-recovery.md#receiver).
- **Fetch from another instance (fetching side).** The mirror image of an off-site copy: instead of this box pushing its snapshots out, it fetches somebody else's in. Switch on **Pull** under **Settings, Instances**, then add a source in the other member's **Details**: its repository location, which kind of backup it holds and how often to fetch. Its restic password comes over the group, never its APP_KEY. The far side configures nothing more and does not have to be running. The source repository is only ever read: it is opened to check the password, listed, and named as the source of the copy, and never initialised, unlocked, pruned or written to. Each side keeps its own credentials, and an `rclone:` source is refused because rclone would reach it with this instance's remotes. See [Off-site & recovery](offsite-recovery.md#receiver).
- **Key keeper.** Another instance of your group can keep a sealed copy of this server's recovery kit, which only your 20-character recovery code opens and which it hands out only after someone there presses **Allow**. See [Key keeper](offsite-recovery.md#key-keeper).

## Plain exports

- **Container and VM export.** **Export container** and **Export VM** under **More** on an entry's page write a browsable, tool-free copy next to the repo: the container's backup folders as they are right now plus its Unraid template, or the VM's disk images plus its definition, restorable with `virsh define` plus the disk, no BombVault or restic needed. **Export** on a snapshot writes a stored backup the same way, as tar, zip or a restic repository of its own. restic stays the engine; this is an extra convenience copy.
- **Encrypt the plain exports (age).** The exports sit outside restic, so they are plaintext by default. Switch on **Encrypt exports with age** under **Settings, System** and add one or more recipients (an age public key or an SSH public key). Each export (including the flash ZIP) is then sealed for those recipients, and you decrypt it later off the box with the matching private key. As a safety rule, with encryption on and no valid recipient set, an export fails with a clear error instead of ever writing plaintext.
- **The recovery kit is sealed too.** With the same setting on, the kit downloads as `bombvault-recovery-kit.md.age`. It is ASCII-armored rather than binary, so it stays plain readable text: you can still paste it into a password manager or print it, which is what the kit is for. The same safety rule applies, so encryption on with no usable recipient refuses the download rather than falling back to handing out the master key in the clear. One thing to get right when you turn this on: you need your age private key to open the kit, so keep that key somewhere that does not depend on the kit itself.

## AI assistants (MCP) {#mcp}

BombVault has a built-in MCP server, so an assistant such as Claude Code or Claude Desktop can read backup status, coverage, run history, restore points and current activity. With a key that allows it, the assistant can also start a backup of one entry, one section or everything, and cancel the backups it started. Restores, deletions, prune and settings stay in the web interface. Each client gets its own key under **Settings, Integrations, MCP server**; a key is shown once, stored only as a fingerprint, and can be renamed, replaced or revoked at any time. Starts are limited per hour and per entry, and a retention guard keeps assistant backups from pushing your own restore points out of a "keep last N" policy. Every run an assistant starts is marked "via MCP" with the key's name. See [MCP server](mcp.md). Database dumps and [ZFS datasets](zfs-datasets.md) are among the entries and restore points it reads, and it can list the anomalies BombVault noticed.

## Apps and companions {#apps}

- **Android app.** Every server of your group on your phone, with the activity log of all of them on one screen. It pairs with your group by QR code and opens each server already signed in, with a session that reaches only what the app shows. See [Android app](android.md).
- **Receiving server.** The box that receives off-site copies runs an append-only rest-server, set up the first time it allows a **Receiver** request, and offers it to the other instances of your group, each with a login of its own. See [Receiving server](offsite-recovery.md#receiving-server).
- **Settings, Apps.** A page that starts with the Android app, its APK for the release the server runs and a QR code for it, followed by a card for each companion. ParleyPort's card offers its Unraid template, copies the Docker command that starts it, and leads to its repository and to the relay settings under Pairing. The BombVault Widget's card offers its template and its repository, and installs or removes the plugin over the host SSH connection.
- **BombVault Widget.** A tile on the Unraid Dashboard with BombVault's activity log and the next scheduled run. Without a host SSH connection the card hands you the `.plg` address to install under **Plugins, Install Plugin**, and the plugin can be removed there like any other.
- **Embeddable activity log.** Generate a read-only token in the **Dashboard widget** card under **Settings, Integrations** and you get an address for any dashboard that shows an iframe, such as Homepage, Organizr or Heimdall: a small page with just the live activity log. The token grants that log and nothing else, and **Disable** revokes it at once. The embedded page is in English only.

## Other

- **Stop a backup that is running.** While a run is active, **Cancel backup** stands beside its progress. The run is recorded as *cancelled*, not failed. Stopping is safe, because restic writes its snapshot last, so an aborted run leaves unreferenced data and no snapshot.
- **Back up many at once.** Select entries in the Backups list and back up the selection. The batch runs server-side, so it keeps going even if you close the tab or lose the connection. BombVault never backs up (and so never stops) its own container.
- **Snapshots on the entry's page** with a restore-point list, per-snapshot delete, a tag of your own and a compare between two snapshots.
- **Repository maintenance per section** in the **Check backups** card under **Settings, Verify**: a check (`restic check`), and under **More** **Unlock** (clear a stale lock) and **Prune** (applies the retention policy on demand when one is set, otherwise a plain space-reclaim).
- **Progress for checks, restore checks and prune.** While one of them runs, the activity log and the **Check backups** card show how far restic has counted, such as *12 of 47 packs*, with the time left in that step once there is enough to estimate it. restic counts packs, snapshots and index files here, not bytes, so that is what the bar shows; before the first count it runs without a number.
- **Automatic database dumps.** Recognised PostgreSQL, MySQL and MariaDB containers (the official images, PostGIS, TimescaleDB, pgvector, pgautoupgrade, Immich's database images, linuxserver, yobasystems and jc21 MariaDB, and Oracle's mysql-server) are dumped before each backup, from the running server. Containers that only look like a database get the same option in the **Database** card on their Settings tab, switched off until you choose it. The dump streams straight into the repository as a restore point of its own, next to the files backup, and is never written to a disk. Credentials come from the container's own variables, including `*_FILE` secrets, and never leave it. The card shows whether the database's data folder is saved while stopped, copied while running, or not saved at all. A failed dump does not fail the backup: it shows up as a failed run with its reason and a hint how to fix it, and sends a notification. Dumps are never loaded back automatically. Download one (plain or compressed), save it to a folder, import it into a freshly started database with one click, or fetch it with the restic CLI. Switch it off per container, with the label `bombvault.dbdump=false`, or for all containers with **Automatic database dumps** under **Settings, General**. Anomaly detection also watches the size of every dump, and an assistant can list a container's dumps through the [MCP server](mcp.md#tools).
- **Commands before and after, per container.** Shell commands run inside the container (for example flushing a cache); a failing command before the backup aborts it. Recognised databases are dumped automatically, so they need no command.
- **Stop other containers during backup, with a health-gated restart.** Name dependent containers (for example a database) in **Stop other containers** to stop while this one is backed up. Afterwards BombVault brings them back in their Compose `depends_on` order and, by default, waits for each one to report healthy (or running, if it has no healthcheck) before starting the containers that depend on it, so a dependency like Pi-hole, a database or a VPN gateway is actually up before the services that need it, instead of those returning to a *connection refused*. The wait is bounded by a per-container timeout (120 seconds by default) so a slow or never-healthy container can never hang the run; both the wait and the timeout live under **Restart after backup** in the **Order** card under **Settings, Schedule** (turn the wait off for an all-at-once restart). The same ordered, health-gated restart also wraps the post-backup image update, so on a day an update lands the dependents are held down through the recreate and only brought back, health-gated, once it is done.
- **Exclude patterns per container.** List subdirectories to skip inside a backed-up volume, one per line. Type the paths as you see them inside the container; a live preview shows what each line resolves to and warns when a line would exclude nothing.
- **Update after a successful backup (off by default).** Switch on **Update containers after a successful backup** under **Settings, Schedule, Updates after the backup**, or set a single container differently on its page, and BombVault pulls the newest image and recreates the container, but only when there is actually a newer image, so a fresh restore point always exists first. Optional extras: a notification per updated container and **Remove the old image after an update** (a base image shared by other containers is never deleted). After the update BombVault also asks Unraid to re-check that one container's update status, so the Docker tab's stale *update available* banner clears itself instead of lingering (Unraid updates go straight through the Docker API, so its cached status, and on some versions a cached digest, would otherwise keep showing the banner). It is best-effort, never affects the backup, on by default and switched with **Refresh Unraid's update status after updating a container** in the same card.
- **Restore to an alternate folder** for cloning or inspection.
- **What's new after an update.** Once per new version a window opens by itself with a card for every release since the version you had, newest first. Each card has the release notes behind a **Release notes** button, already open on the newest card, and the changes that release brought, each with **Go there** where a page shows it. The notes are embedded in the binary, so the window works offline. Green dots mark each change on its page. **New** in the Version card under **Settings, Info** counts what you have not seen yet, such as **New · 4**, and opens the same window.
- **Info.** **Settings, Info** holds **Version** (BombVault, GlimStone, restic and rclone, with **New** and **Check for updates**), **Help** with **Manual**, in the yellow of the README's docs button, and **Bug report**, and **About BombVault**.
- **HTTPS out of the box** (self-signed, or bring your own cert behind a reverse proxy).
- **Docker healthcheck.** The container reports healthy/unhealthy from its own `/api/health`, so an auto-heal tool can restart it if the engine ever wedges.
- **42 languages** with a flag picker under **Settings, Look**.
- **Settings save themselves.** Flip a switch or leave a field and the change is written at once, with a short flash on the control and a shake if the server refuses it. A few places keep a Save button because saving them half-done would be unsafe, such as the rclone config box, the credential set editor and the login password.
- **Quiet notifications.** Under **Settings, Look** you can mute the routine confirmations, so only failures still interrupt you. This does not touch the notification channels.
- **Make it look how you want it.** **Settings, Look** sets the **Theme** (Dark, Light or System), the colours (one accent, or *Rainbow Mode* with a palette of eight), the corners (round, soft or square), the animation (off, subtle, wild or storm) and the order of the settings tiles. Theme, corners and animation show a symbol for each choice; with the **Symbol** label mode for buttons, a choice shows its symbol alone and its name in the hover bubble. BombVault keeps the look on the server, and a browser that comes for the first time takes it over. The liquid in a storage location's vessel sloshes, and the logo shakes harder and harder while you hold it, then bursts: in the sidebar, and on a phone above the overview. When your system asks for less motion, that always wins.
