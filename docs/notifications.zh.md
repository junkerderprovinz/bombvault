# 通知

BombVault 可以在备份失败、成功、逾期时通知你，并且每周一次告诉你整体情况如何。一切都在**设置、通知**下设置：**通知**卡片决定单次备份之外 BombVault 还发送什么，**渠道**卡片决定消息发到哪里。每个渠道自己决定什么时候发声，Healthchecks 检查项也是一个渠道。

## 什么会发送消息 {#what}

**通知**卡片里的开关适用于所有渠道：

- **汇总计划运行**：每次计划运行发送一条消息，例如*45 个中有 42 个成功*，而不是每个容器或虚拟机一条。你手动启动的备份仍然会各自发送消息。即使开启了汇总，冻结的客户机、失败的保留规则或超出的增长预算也会立即发出。
- **容器更新时通知**：**备份成功后更新容器**把某个容器更新到较新的镜像时，为每个这样的容器发送一条消息，方便你确认它仍然正常。
- **报告逾期的备份**：BombVault 每天 09:00 检查一次，有没有开启的备份逾期，也就是比它的计划时间超过两倍，并为每种情况发送一条消息，写明落后的条目。下一次成功的备份会清除它。
- **每周摘要**：每周一份摘要，包括运行次数、新的备份数据、哪些分区逾期、异地副本是否是最新的，以及最主要的失败。它的计划是一个按钮，和其他计划一样，**关闭**可以把它关掉。参见[计划](schedules.md#plans)。

渠道是否也通知成功，在该渠道的**通知**里设置。哪些异常会发送消息，在**设置、验证**下设置，参见[异常](anomalies.md)。被推迟的备份开始等待时发送一条消息，等待结束时再发送一条，而不是每次尝试一条。

## 渠道 {#channels}

**渠道**卡片底部的**添加渠道**提供 **Unraid 通知**、**ntfy**、**Gotify**、**Discord**、**Slack**、**Matrix**、**邮件 (SMTP)**、**Apprise**、**Webhook** 和 **Healthchecks**。想加多少就加多少，同一种类也可以加两个，例如一个 ntfy 主题只收失败，另一个什么都收。新渠道开始时是关闭的，所以在填写字段之前它就已经保存了。

每个渠道都有：

- 自己的开关，关掉它不会丢失已填的字段。
- **通知**：**从不**、**仅在失败时**或**成功和失败时**。新渠道默认是**仅在失败时**。成功了但漏掉了某些内容的备份，也会发到只收失败的渠道。
- **名称**：可选，会代替种类显示，同一种类有两个时很方便。
- **发送测试**：用表单里当前的值，不管是否已保存，通过这个渠道发送一条测试消息。渠道下面的那一行会说明服务是否接收了，没接收的话原因是什么。
- **移除渠道**：旁边的垃圾桶。

每个渠道各自发送，有自己的时间限制，所以一个始终不应答的主机不会拖住其他渠道。如果服务的失败有可能靠再试一次解决，渠道最多会尝试三次。没有渠道接收的逾期、预算或异常警报会稍后重试，每周摘要也一样。

| 渠道 | 字段 | 说明 |
|---|---|---|
| **Unraid 通知** | 无 | 发送到 Unraid 自己的通知系统，它可以转发到 Pushover、邮件或 Discord。它通过**设置、集成、主机 SSH** 的 SSH 连接运行，所以那把密钥必须已被授权。在 TrueNAS 和其他主机上它不会发送，渠道会说明原因。 |
| **ntfy** | **主题网址**、**访问令牌（可选）** | 地址以你的主题结尾。只有受保护的主题才需要令牌。 |
| **Gotify** | **服务器 URL**、**应用令牌**、**失败时的优先级**、**成功时的优先级** | 优先级从 0 到 10，失败默认为 8，成功默认为 5。 |
| **Discord** | **Webhook 网址** | 在 Discord 频道设置里创建的 webhook 的地址。 |
| **Slack** | **Webhook 网址** | 你的 Slack 应用的传入 webhook 的地址。 |
| **Matrix** | **Homeserver 网址**、**访问令牌**、**房间 ID** | 令牌背后的账号必须在这个房间里。 |
| **邮件 (SMTP)** | **SMTP 主机**、**端口**、**加密**、**用户名**、**密码**、**发件地址**、**收件地址** | **加密**可选 **STARTTLS**、**TLS (implicit)** 或 **None**。 |
| **Apprise** | **Apprise API URL**、**标签（可选）**、**Apprise 地址（可选）** | 指向你的 Apprise API 容器的 `/notify/<key>` 端点，就能用到它的 100 多种服务，标签用来选择该密钥下目标的一个子集。也可以填写 Apprise 地址，每行一个，例如 Telegram 用 `tgram://`，Pushover 用 `pover://`，这时 API URL 以 `/notify` 结尾，不带密钥。 |
| **Webhook** | **Webhook 网址**、**方法**、**请求头**、**正文** | 由你自己组织的请求，参见 [Webhook](#webhook)。 |
| **Healthchecks** | **ping 网址** | 参见 [Healthchecks](#healthchecks)。 |

令牌、SMTP 密码和 webhook 请求头的值这类密钥会加密保存，服务器不会把它们交回给页面。在已保存的密钥下面，字段会显示**已保存。留空即可保留。**当你更改渠道发送的目标时，BombVault 不会把旧的密钥发到新的地方：字段会显示**重新输入此项后，新地址才会保存。**

渠道列表之前版本的设置会在第一次启动时迁移过来，不会丢失任何东西。每个你填过的渠道都会变成一个独立的条目，并保留你原来的**通知**选择。设为 Discord、Slack、Gotify 或 ntfy 格式的 webhook 会变成对应种类的渠道，Generic JSON webhook 则通过它的**正文**继续发送 `title`、`message` 和 `ok`。Unraid 开关会变成 Unraid 渠道，Healthchecks 网址及其例外会变成 Healthchecks 渠道。

### Webhook {#webhook}

**Webhook** 渠道向任意地址发送一个 HTTP 请求。**方法**可选 GET、POST 或 PUT。**添加请求头**会在**请求头**下添加一行，请求头的值作为密钥保存，所以 `Authorization` 请求头放在这里是安全的。**正文**会按你写的原样发送，并填入以下占位符：

| 占位符 | 替换为 |
|---|---|
| `%%title%%` | 消息的标题 |
| `%%body%%` | 消息本身 |
| `%%ok%%` | `true`，失败时为 `false` |
| `%%event%%` | 发生了什么，例如 `container.failed` |
| `%%severity%%` | `info`、`success`、`warning`、`failure` 或 `critical` |
| `%%importance%%` | 对应的 Unraid 级别：`normal`、`warning` 或 `alert` |
| `%%link%%` | 与消息相关的链接，没有时为空 |
| `%%key%%` | 分区，例如 `container` 或 `VM` |
| `%%time%%` | UTC 时间，例如 `2026-11-09T03:00:00Z` |
| `%%source%%` | `BombVault` |

占位符在地址和请求头的值里也能用，每个值都会按它所在的位置转义：`Content-Type` 请求头表明是 JSON 时按 JSON 转义，在地址里按查询参数转义。新的 webhook 一开始就带着这个请求头，并发送 `{"title":"%%title%%","message":"%%body%%","ok":%%ok%%}`。BombVault 不认识的名称会原样保留，所以拼写错误会在消息里显示出来。把**正文**留空就不发送正文。

## Healthchecks {#healthchecks}

[Healthchecks.io](https://healthchecks.io) 这类服务会在 BombVault 停止签到时发出警报。添加一个 **Healthchecks** 渠道并粘贴检查项的 **ping 网址**，BombVault 就会在每次备份的整个生命周期里 ping 它：开始时、成功时，或失败时用 `/fail`。这个渠道没有**通知**选项，因为检查项需要成功的 ping 才能保持绿色。没有任何备份目的地的分区算作失败，所以它的检查项会变红，而不是收到成功信号。

使用同一个网址的分区共享一个检查项。其中一个的备份失败后，其他分区的成功备份也会 ping `/fail` 并点名它，所以检查项会一直保持红色，直到那个条目重新有一次成功的备份，或你在**需要处理**下确认这次失败。

分区可以 ping 自己的地址：Healthchecks 渠道里的**例外**会添加一个，那一行随后会写**其他所有分区都 ping 这个 URL。**在这个渠道里点击**发送测试**，会在每个检查项的日志里写入一条记录，它的状态保持不变。

## 示例：手机上的 Gotify {#example-gotify}

你在 `https://gotify.example.com` 运行 Gotify，希望失败时手机响铃，成功时静静到达。

1. 在 Gotify 里打开 **Apps**，创建一个名为 `BombVault` 的应用并复制它的令牌。
2. 在 BombVault 里打开**设置、通知**，开启**汇总计划运行**，这样 45 次备份的一晚只发送一条消息，而不是 45 条。
3. 在**渠道**里点击**添加渠道**，选择 **Gotify**。
4. 把 `https://gotify.example.com` 填入**服务器 URL**。BombVault 会自己加上 `/message`。
5. 把令牌粘贴到**应用令牌**。
6. 把**通知**设为**成功和失败时**。**失败时的优先级**保持 8，**成功时的优先级**保持 5。Gotify 的 Android 应用把 8 及以上视为高优先级，所以只有失败才会发出声音。
7. 打开渠道的开关，点击**发送测试**。渠道下面的那一行会说明 Gotify 是否接收了，令牌被拒绝时也会如实写出来。

下一次计划运行会以优先级 5 发送一条摘要，如果其中有任何失败，则以 8 发送。

## 示例：无需账号的 ntfy {#example-ntfy}

公开主题的 ntfy 不需要账号。请选一个难以猜到的主题名称，因为任何知道它的人都能读到。

1. 在**渠道**里点击**添加渠道**，选择 **ntfy**。
2. 把主题的地址填入**主题网址**，例如 `https://ntfy.sh/bombvault-tower-7f3k`，或者你自己 ntfy 服务器上的主题。公开主题的**访问令牌（可选）**留空即可。
3. 在 ntfy 应用里订阅同一个主题，打开渠道的开关，然后点击**发送测试**。

BombVault 把消息作为正文发送，标题放在 `Title` 请求头里。失败会以高优先级和标签 `warning` 发出，所以在应用里很显眼，一直处于冻结状态的虚拟机会以紧急优先级发出。
