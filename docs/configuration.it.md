# Configurazione

Questa pagina tratta le variabili d'ambiente del container, i mount forniti dal template, il modello di sicurezza, il backup delle VM via SSH e la configurazione off-site. Dove vanno i backup si imposta dentro l'app come **destinazioni**, non tramite variabili d'ambiente.

## Variabili d'ambiente {#environment-variables}

| Variabile | Obbligatoria | Descrizione |
|---|---|---|
| `APP_KEY` | **Sì** | Segreto esadecimale di 32 byte (64 caratteri esadecimali) usato per derivare la password del repository restic. Generalo con `openssl rand -hex 32`. Conservalo con cura: perderlo rende i backup cifrati irrecuperabili. |
| `LIBVIRT_HOST` | Per VM e dataset ZFS | Host Unraid raggiunto via SSH per i backup di VM e dataset ZFS (campo del template **Host SSH: Address**, predefinito `host.docker.internal`). Il template precompila il segnaposto `192.168.x.x`, che conta come non impostato. Usa l'IP LAN del tuo Unraid, obbligatorio su una rete personalizzata `br0.x`. Quando `host.docker.internal` non si risolve, come in un'app TrueNAS, e nemmeno `LIBVIRT_URI` nomina un host, BombVault usa il gateway predefinito del container e il log di avvio lo nomina. |
| `LIBVIRT_SSH_PORT` | No | Porta SSH dell'host per i backup di VM e dataset ZFS (campo del template **Host SSH: Port**, predefinita `22`). |
| `LIBVIRT_SSH_USER` | No | Utente SSH sull'host per i backup di VM e dataset ZFS (campo del template **Host SSH: User**, predefinito `root`). |
| `LIBVIRT_URI` | No | URI di connessione libvirt completo, usato **così com'è** al posto di costruirne uno dalle tre variabili `LIBVIRT_*` qui sopra (che per la stringa di connessione vengono allora ignorate). Predefinito non impostato. Serve su TrueNAS Scale, il cui libvirtd ascolta su un socket non standard che la forma costruita non sa esprimere: `qemu+ssh://<user>@<truenas-host>/system?socket=/run/truenas_libvirt/libvirt-sock`. Vedi la [guida al backup delle VM](vm-backup-ssh-setup.md#truenas-scale). Quando è un URI `qemu+ssh://`, ciascuna tra `LIBVIRT_HOST`, `LIBVIRT_SSH_USER` e `LIBVIRT_SSH_PORT` che non è impostata viene presa da lì, anche per i comandi SSH propri di BombVault (trasferimento della NVRAM, dataset ZFS). |
| `PORT` | No | Porta HTTP (predefinita `3000`. Usata solo con `HTTP_ONLY=true`). |
| `HTTPS_PORT` | No | Porta HTTPS (predefinita `3443`. Il template la pubblica 1:1, quindi la WebUI risponde su `https://<ip>:3443`). |
| `HTTP_ONLY` | No | Imposta `true` per disattivare il listener HTTPS autofirmato e servire solo HTTP semplice (da usare dietro un reverse proxy che termina il TLS). |
| `BIND_HOST` | No | Indirizzo su cui ascolta la WebUI (predefinito `0.0.0.0`, ogni interfaccia). Lascialo non impostato nel container, le cui porte pubblicate richiedono ogni interfaccia. `127.0.0.1` va bene per un'esecuzione fuori da Docker. Il healthcheck interroga lo stesso indirizzo. |
| `TRUSTED_PROXY` | No | Indirizzi o intervalli CIDR, separati da virgola, del reverse proxy davanti a BombVault (per esempio `192.168.20.11` o `10.0.0.0/8`). Solo da quei salti `X-Forwarded-For` viene creduto, e il limite degli accessi conta allora gli errori per client reale invece di mettere tutti quelli dietro il proxy nello stesso gruppo. Non impostato (il predefinito) non si fida di nessuno: un header creduto senza condizioni lascerebbe a qualsiasi chiamante la scelta del proprio gruppo. |
| `HOST_SOURCE_ROOT` | No | Il percorso dell'host montato come **Host Data** (predefinito `/mnt`). BombVault traduce le sorgenti dei bind mount che Docker riporta in percorsi sotto questo mount. Cambialo solo se hai montato una radice dell'host diversa. |
| `HOST_MOUNT_ROOT` | No | Dove Host Data è montato dentro il container (predefinito `/host/user`). Su TrueNAS Host Data è montato al suo stesso percorso dell'host, quindi questa e `HOST_SOURCE_ROOT` nominano entrambe quel percorso, per esempio `/mnt/tank` (vedi [TrueNAS SCALE](getting-started.md#truenas)). |
| `DATA_ROOT_SEGMENTS` | No | Nomi di segmenti di percorso, separati da virgola, che segnano la sorgente di un bind mount come dati di backup (predefinito `appdata`, in linea con la convenzione di Unraid `/mnt/user/appdata/<container>`). Il bind mount di un container viene scelto automaticamente per il backup quando QUALSIASI segmento elencato compare come segmento intero del percorso della sua sorgente sull'host. Per esempio `DATA_ROOT_SEGMENTS=appdata,config` raccoglie anche un bind `.../config`. Il confronto ignora maiuscole e minuscole, quindi il predefinito copre anche `/DATA/AppData/<container>` di ZimaOS. Vedi [Rilevamento delle sorgenti di backup](#backup-source-detection) per gli altri modi, sempre attivi, in cui viene trovata la cartella dei dati di un container. |
| `PLATFORM` | No | Forza su quale piattaforma BombVault si considera in esecuzione, invece di rilevarla da solo: `unraid`, `generic` o `truenas` (predefinito non impostato: rileva Unraid cercando il suo marcatore `dockerMan` sotto il mount della flash, altrimenti `generic`. Anche un valore non riconosciuto ricade su `generic`, e viene registrato nel log). Impostala esplicitamente su un host Docker generico o su TrueNAS Scale invece di affidarti al rilevamento solo per Unraid. Il file compose generico lo fa. Cambia la convenzione di ripiego per appdata, i valori predefiniti di destinazione dei ripristini tra istanze e se i passaggi solo Unraid per notifiche e plugin companion vengano tentati (vedi `internal/platform`). |
| `BOMBVAULT_SELF_CONTAINER` | No | Il nome del container di BombVault stesso, così che non salvi (e quindi non fermi) sé stesso. |
| `BACKUP_MAX_HOURS` | No | Ore massime di orologio che una singola esecuzione di backup può tenere il lock del suo dominio prima di essere annullata a forza (una protezione perché un'esecuzione bloccata non possa tenere fermo il dominio per sempre). Vuoto (il predefinito) usa `48`. Aumentalo per backup cloud molto grandi o lenti (un'esecuzione annullata al limite fallisce con `context deadline exceeded`). Imposta `0` per disattivare del tutto il limite. Anche una potatura è tenuta allo stesso limite, e un controllo o una potatura girano finché restic continua a riportare avanzamento. |
| `BACKUP_STALL_HOURS` | No | Ore in cui un backup può non fare **alcun progresso** prima di essere annullato. Vuoto (il predefinito) usa `2`. Imposta `0` per non annullare mai per stallo. È la più fine delle due protezioni e di solito quella che scatta: osserva se qualcosa sta ancora succedendo invece di quanto è durata l'esecuzione, così un backup lento ma sano di molti terabyte viene lasciato in pace mentre uno bloccato su una condivisione che non risponde viene fermato in ore invece che in giorni. Dopo 30 minuti di silenzio, prima di annullare qualsiasi cosa, viene registrato un avviso. La scansione conta come avanzamento: restic non scrive byte mentre percorre un albero grande, e quella fase viene osservata tramite i suoi totali di file e byte invece che tramite i byte scritti. Le due variabili sono indipendenti, e `BACKUP_MAX_HOURS` limita comunque le fasi dopo il backup vero e proprio (conservazione, statistiche, copia off-site), dove non ci sono contatori da osservare. |
| `DB_DUMP_MAX_HOURS` | No | Ore in cui un dump automatico del database può girare prima di essere fermato. Vuoto (il predefinito) usa `6`. I valori ammessi vanno da `1` a `48`, e il limite viene tenuto un'ora sotto `BACKUP_MAX_HOURS` (alla metà di esso quando è sotto le due ore), così un dump lungo viene interrotto dal proprio limite e segnalato come tale invece di trascinare con sé il backup. Un dump che non fa progressi viene fermato prima, dopo `BACKUP_STALL_HOURS`. Un dump fermato fallisce da solo e il backup del container prosegue. Su Unraid aggiungila al container BombVault con **Add another Path, Port, Variable**. |
| `TZ` | No | Fuso orario per lo scheduler (per esempio `Europe/Berlin`). **Se lo lasci non impostato, ogni pianificazione gira in UTC**: una impostata alle 02:30 scatta allora alle 02:30 UTC invece che sul tuo orologio. Su Unraid non lo imposti mai tu: il sistema passa il proprio fuso orario a ogni container. Il log di avvio dice quale fuso ha risolto. Un fuso con l'ora legale salta un'esecuzione in primavera e ne fa girare una due volte in autunno, mentre UTC non fa né l'uno né l'altro ma si sposta di un'ora rispetto al tuo orologio due volte l'anno. |
| `DATA_DIR` | No | Dove BombVault tiene il suo database, le chiavi e le cache (predefinito `/config`). Lascialo stare nel container. Conta quando esegui il binario fuori da Docker. |
| `FLASH_DIR`, `FLASH_TEMPLATES_DIR` | No | Dove la chiavetta flash e i suoi template Docker sono montati dentro il container (predefiniti `/host/boot` e `/host/boot/config/plugins/dockerMan/templates-user`). Seguono il mount `/boot` del template, quindi lasciali non impostati. |

## Mount {#mounts}

Monta il socket Docker, la flash (`/boot`) e la radice **Host Data** (`/mnt`) come mostrato nel template CA. Sia le *sorgenti* sia le *destinazioni* dei backup stanno sotto Host Data, che è montato **slave** così una condivisione remota che si monta dopo l'avvio del container (per esempio sotto `/mnt/remotes`) diventa visibile senza riavvio.

Su TrueNAS, Host Data è un percorso di dataset come `/mnt/tank`, mai un ixVolume. I dati che un'app tiene in un ixVolume stanno fuori da esso e non vengono salvati. Vedi [TrueNAS SCALE](getting-started.md#truenas).

Anche i backup dei dataset ZFS richiedono questa modalità: l'host monta lo snapshot di un dataset solo dopo che il container è partito. Vedi [Dataset ZFS](zfs-datasets.md).

I repository locali sono per default in `/mnt/user/bombvault/{container,vms,flash,config,files,zfs}`, creati al primo backup. Sono le **cartelle proprie** delle sezioni e formano la destinazione **Locale**. Nella sua pagina sotto **Destinazioni**, la scheda **Connessione** cambia la cartella di ogni sezione.

La cartella propria di una sezione può anche stare in una destinazione che hai già, come un NAS o un bucket S3: **Usa come cartella propria** nella pagina di quella destinazione la sposta lì e dice prima cosa succede ai backup già fatti. Vedi [La cartella propria di una sezione](offsite-recovery.md#own-folder).

Le cartelle dei repository locali restano con i permessi `0755` e `0644`, così un utente di sincronizzazione non root via SMB non ne resta escluso, e i repository sono cifrati, quindi questo non espone nulla. Le definizioni di ripristino stanno dentro ogni repository, quindi una cartella copiata è completa da sola. Il repository dell'auto-backup resta leggibile solo da root.

!!! note "Verifica dell'integrazione host"
    La scheda **Integrazione host** nella panoramica (aggiungila in **Personalizza**) sonda ogni mount e ogni CLI (socket Docker, libvirt, restic, qemu-img, rclone) e segnala ciò che manca.

## Rilevamento delle sorgenti di backup {#backup-source-detection}

Per ogni container BombVault sceglie automaticamente quali bind mount e volumi con nome salvare. Un percorso viene preso quando vale una delle condizioni seguenti (puoi sempre correggere il risultato nella scheda **Cartelle da salvare** nella scheda Impostazioni del container):

- **Corrispondenza con un segmento radice dei dati:** la sorgente del bind sull'host contiene uno dei segmenti di `DATA_ROOT_SEGMENTS` come componente intero del percorso (predefinito solo `appdata`).
- **I volumi Docker con nome** sono sempre inclusi, perché non hanno un equivalente scartabile e non c'è nulla da filtrare, **ma solo quando il vero percorso di archiviazione del volume sull'host è esso stesso raggiungibile attraverso il mount Host Data**, esattamente come qualsiasi altro percorso dell'host che BombVault salva. Il driver di volumi locali predefinito di Docker salva un volume sotto la radice dati del daemon (`/var/lib/docker/volumes/<name>/_data` a meno che tu l'abbia personalizzata. Controlla con `docker info -f '{{.DockerRootDir}}'`), che non è coperta dallo stretto mount Host Data a directory singola che il `docker-compose.yml` generico usa di default. Un volume non raggiungibile viene saltato in silenzio, non è un errore. Per salvare davvero i volumi con nome su un host generico, punta Host Data (e `HOST_SOURCE_ROOT`) a un antenato comune che copra anche la radice dati di Docker. Il commento su Host Data nel file compose spiega il compromesso (Unraid lo aggira montando tutto `/mnt`, la sua convenzione universale di primo livello, per lo stesso motivo).
- **Directory del progetto Docker Compose:** se il container porta la label standard `com.docker.compose.project.working_dir` (impostata automaticamente da `docker compose up`), viene aggiunta anche quella directory, a prescindere dal fatto che qualche bind abbia corrisposto a un segmento radice dei dati.
- **Override con la label `bombvault.data`:** imposta la label `bombvault.data=true` su un container per includere tutti i suoi bind mount, per una struttura che nessuna delle due convenzioni sopra coglie (per esempio un solo bind `/srv/plex/config` senza progetto Compose). Qualsiasi valore non vuoto diverso da `false` conta come vero. Una label assente o `bombvault.data=false` non cambia nulla.
- **Label `bombvault.dbdump`:** imposta `bombvault.dbdump=false` su un container per disattivare il suo dump automatico del database (`0`, `no` e `off` fanno lo stesso), oppure nomina il motore (`postgres`, `mysql`, `mariadb`) per fare il dump di un container che BombVault non riconosce da solo. La label prevale sull'interruttore nella scheda **Database** nella scheda Impostazioni del container, che è il modo di farlo su Unraid.

## Modello di sicurezza {#security-model}

!!! warning "Controllo dell'host equivalente a root"
    Tramite il socket Docker BombVault può fermare, rimuovere e ricreare container e leggere e scrivere appdata, e per il backup delle VM accede all'host via SSH (`qemu+ssh://`, root di default) per eseguire `virsh`. Chiunque possa raggiungere la sua interfaccia web ha di fatto accesso root all'host.

### Accesso {#login}

- **Protezione con password facoltativa** (scheda **Password** in **Impostazioni, Sicurezza**): imposta una password per richiedere l'accesso, cancellala per disattivarlo. Disattivata di default per l'uso su una LAN fidata. La password viene salvata con Argon2id su un pepper legato ad `APP_KEY`, quindi un `/config` copiato è inutile senza la chiave e lento da attaccare anche con essa. Una nuova password richiede almeno 12 caratteri. Una più corta già esistente continua a funzionare finché non viene cambiata. Le sessioni sono firmate (HMAC derivato da `APP_KEY`) e cambiare la password le invalida. Gli accessi sono limitati a cinque errori al minuto per client. Cambiare o cancellare la password richiede la **Password attuale** e, con l'autenticazione a due fattori attiva, il codice.
- **Alcune cose richiedono una password.** Scaricare il kit di ripristino e il rapporto sui bug, depositare la chiave presso un custode della chiave, consentire la consegna di un deposito, creare un nuovo codice di sblocco, eliminare i backup di una destinazione, esportare le impostazioni con le credenziali, l'autenticazione a due fattori e le passkey vengono rifiutati finché non è impostata una password di accesso, e richiedono un accesso sull'istanza stessa.
- **Autenticazione a due fattori** (**Impostazioni, Sicurezza**): un codice temporale da un'app di autenticazione oltre alla password, più otto codici di ripristino monouso consegnati una volta sola quando viene attivata. Il segreto condiviso è salvato cifrato con `APP_KEY`, e per disattivare di nuovo il fattore serve un codice valido.
- **Passkey** (WebAuthn) stanno su una scheda propria una volta impostata una password, accanto alla password e mai al suo posto, quindi rimuovere tutte le passkey non chiude fuori nessuno. Richiedono un vero nome di dominio e un certificato di cui il browser si fida. Il predefinito `https://<ip>:3443` è esattamente ciò che WebAuthn rifiuta, e la scheda lo dice invece di offrire un pulsante che fallisce. Con l'autenticazione a due fattori attiva, una passkey deve verificare il tuo PIN, la tua impronta o il tuo volto, altrimenti l'accesso chiede anche il codice.
- **Il ripristino di una configurazione** (**Ripristina le impostazioni** nella Procedura guidata di emergenza) termina ogni sessione, rimuove ogni passkey e revoca ogni token API e chiave MCP, perché le impostazioni ripristinate potrebbero riportare indietro elementi rimossi dopo il loro salvataggio. Accedi con la password e imposta di nuovo le tue passkey in **Impostazioni, Sicurezza**.
- **Una password dimenticata** si reimposta nella pagina di accesso. **Password dimenticata?** fa scrivere a BombVault un codice di 12 caratteri, in tre gruppi di quattro, nel log del suo container (su Unraid: scheda Docker, icona di BombVault, **Logs**). Quel codice e una nuova password ti fanno entrare. Il reset disattiva anche l'autenticazione a due fattori, rimuove ogni passkey, revoca ogni token API, chiave MCP e accesso OAuth, termina ogni altra sessione, fa uscire ogni telefono associato e disattiva l'associazione dei telefoni. La pagina elenca poi cosa è sparito. Un codice è valido per 10 minuti, e i tentativi sbagliati non lo consumano. I token del widget e delle metriche restano, dato che leggono soltanto.
- **Chiunque possa leggere il log del container può reimpostare la password.** Significa root sull'host, ma anche un visualizzatore di log come Dozzle, qualsiasi container a cui sia stato dato il socket Docker (anche in sola lettura basta) e un log shipper che inoltra l'output dei container. Dai queste cose solo a persone di cui ti fideresti per la password. Chi raggiunge soltanto l'interfaccia web non vede mai il codice.

### Telefoni e membri del gruppo {#phones-and-members}

- **I telefoni associati raggiungono un elenco consentito.** Un telefono che conosce le dodici parole del gruppo accede senza la password, finché **I telefoni possono associarsi con le dodici parole del gruppo** è attivo nella scheda **App Android** in **Impostazioni, Sicurezza**. La sua sessione raggiunge solo ciò che mostra l'app: la panoramica, le esecuzioni, i backup da consultare, avvio e ripristino, le anomalie da leggere e la pagina Istanze da consultare. Destinazioni e comandi gli arrivano senza indirizzi e segreti, e un ripristino che sostituisce l'originale esegue prima il backup dello stato attuale. Tutto il resto risponde che serve un accesso sull'istanza stessa: chiavi, kit di ripristino, depositi della chiave, impostazioni, eliminazione dei backup. Un reset della password disattiva l'associazione dei telefoni finché non la riattivi. Un telefono rimosso dalla pagina Istanze, o con **Interroga questa istanza** disattivato nei suoi dettagli, perde subito la sua sessione, e un telefono rimosso che riapre la sua app torna disattivato.
- **Fuori casa un telefono apre le pagine tramite il relay.** Ogni richiesta della pagina è sigillata con la chiave del gruppo, che il relay non può leggere né modificare, e firmata con una chiave propria del telefono che il server ha fissato la prima volta che ha interrogato il telefono. Il server esegue una richiesta una sola volta e solo finché è recente. Risponde solo a un telefono elencato nella pagina Istanze mentre l'associazione dei telefoni è attiva, e solo con una sessione che ha dato a quel telefono, quindi anche uscire ovunque e il reset della password chiudono queste pagine. Il server firma ogni risposta, e l'app verifica la firma con la chiave che ha fissato per quel server e avvisa quando la chiave cambia. Una pagina simile raggiunge lo stesso elenco consentito di un telefono associato, con o senza password di accesso, più lo stato di accesso che la pagina legge per primo. Accedere e uscire, il reset della password e i download restano all'indirizzo del server stesso, e una risposta è limitata a 16 MB.
- **I membri firmano ciò che chiedono.** Le richieste di ruolo e le loro risposte, la consegna di una password restic a un ricevitore o a un prelevatore, gli accessi dei ricevitori e i depositi della chiave sono firmati con una chiave di ogni membro, che un'istanza fissa la prima volta che vede quel membro. Una chiamata firmata con un'altra chiave viene rifiutata. **Dimentica la chiave** nei dettagli di un'istanza scarta la chiave fissata, nel caso in cui quella nota qui non sia del membro stesso. Al membro viene richiesta di nuovo la sua chiave alla chiamata firmata successiva. I membri con BombVault 9.x non firmano e possono essere impersonati da chiunque conosca le parole, come nella 9.9.
- **Le dodici parole sono una password.** Chiunque le abbia entra nel gruppo, vede lo stato di protezione dei membri e può chiedere ruoli, che una persona sull'altra istanza deve comunque consentire. Senza una password di accesso chiunque possa aprire l'interfaccia web può leggerle, e la scheda di associazione lo dice finché non viene impostata una password.

### Chiavi {#keys}

- **APP_KEY fa due cose.** Sigilla ciò che questa installazione memorizza (password, credenziali, token) ed è la chiave dei backup: la password restic ne deriva, e le definizioni di container e VM sono sigillate con essa.
- **Una chiave adottata resta separata.** Quando la Procedura guidata di emergenza adotta i backup di un altro server, questa installazione continua a sigillare con la propria APP_KEY e salva la chiave dell'altro server come **chiave dei backup**, sigillata come ogni altro segreto. Il kit di ripristino stampa allora entrambe. Se in seguito APP_KEY viene cambiata, la chiave dei backup non si può più aprire: BombVault smette di fare backup e lo dice sotto **Richiede attenzione**, invece di scrivere con la chiave sbagliata. Carica di nuovo il kit di ripristino in **Ripristino, Emergenza**, oppure rimetti APP_KEY com'era. Vedi [Procedura guidata di emergenza](offsite-recovery.md#emergency).
- **La crittografia** è attiva di default (**Crittografa i backup** nella scheda **Crittografia** in **Impostazioni, Sicurezza**). I backup sono cifrati da restic con la password derivata dalla chiave dei backup.
- **Depositi della chiave.** Un custode della chiave nel tuo gruppo conserva una copia sigillata del kit di ripristino di questo server che non può aprire da solo. Solo il codice di sblocco di 20 caratteri la apre, e il custode la consegna solo dopo che qualcuno lì preme **Consenti**. Vedi [Custode della chiave](offsite-recovery.md#key-keeper).

### Rete {#network}

- **Le modifiche richiedono JSON.** Una richiesta che cambia qualcosa deve inviare `Content-Type: application/json` e non deve essere contrassegnata dal browser come cross-site, così una pagina di un altro sito non può far cambiare al tuo browser le impostazioni a un indirizzo della LAN. Uno script che usa l'API invia quell'header. Tutto il resto viene rifiutato con `415`.
- Poiché la protezione è opzionale, quando non è impostata l'intera interfaccia e l'API (comprese le destinazioni, le route della prova di manomissione e le route di ripristino) sono raggiungibili da chiunque possa raggiungere la porta. Imposta una password di accesso non appena usi copie off-site, backup append-only o la crittografia.
- Esegui BombVault solo su una rete affidabile e non esposta. Per l'accesso remoto mettilo dietro un reverse proxy che aggiunge autenticazione e TLS. Le risposte portano header di sicurezza di base (CSP, `nosniff`, `X-Frame-Options`, `Referrer-Policy`).
- Dietro un reverse proxy ogni richiesta porta l'indirizzo del proxy, quindi senza `TRUSTED_PROXY` il limite degli accessi conta ogni client nello stesso gruppo e gli errori di un attaccante bloccano anche te. Nomina il proxy in `TRUSTED_PROXY` per riavere il conteggio per client.
- Un reverse proxy davanti a BombVault deve passare l'header `Authorization` o `X-API-Key` fino a `/mcp` e non deve mettere in buffer le sue risposte, altrimenti gli assistenti non riescono a connettersi. Vedi [Server MCP](mcp.md#tls).
- L'endpoint MCP `/mcp` risponde `404` finché non esiste una chiave o non è attivo l'accesso tramite OAuth, e chiede a ogni client la sua chiave o il suo token anche con la password di accesso disattivata. Nessun indirizzo è escluso, nemmeno `localhost`. Non ha strumenti di ripristino né di eliminazione, e ripristinare un backup della configurazione revoca ogni chiave. Vedi [Server MCP](mcp.md#security).
- Con `HTTP_ONLY=true` il cookie di sessione perde il flag `Secure` (deve, per funzionare su HTTP semplice), quindi attiva la password dietro un proxy che termina il TLS se la riservatezza ti importa.
- La connessione SSH del backup delle VM si fida della chiave dell'host alla prima connessione (TOFU) e da allora la fissa. Verifica la chiave dell'host fuori banda se il percorso tra container e host non è affidabile.

## Server MCP {#mcp-server}

Il server MCP non richiede alcuna variabile d'ambiente. Lo attivi creando una chiave in **Impostazioni, Integrazioni, Server MCP**, e risponde su `/mcp` alla stessa porta dell'interfaccia web (per esempio `https://192.168.1.10:3443/mcp`). Senza una chiave attiva quel percorso risponde `404`. Client, certificati e limiti sono descritti in [Server MCP](mcp.md).

## Backup delle VM via SSH {#vm-backup-over-ssh}

BombVault salva le VM KVM/libvirt **senza montare alcun percorso libvirt**. Esegue `virsh` sull'host via SSH (`qemu+ssh://`), quindi non può mai influire sul VM Manager del tuo host.

Montare il socket libvirt dell'host in un container è fragile su Unraid: il VM Manager possiede quei percorsi, e cambiare "Enable VMs" può lasciare libvirt incapace di partire. La chiave SSH concede root sull'host, lo stesso livello di fiducia del socket Docker che BombVault già usa.

Configurazione rapida:

1. **Impostazioni, Integrazioni, SSH dell'host:** copia la chiave pubblica mostrata.
2. Aggiungila in coda a `/root/.ssh/authorized_keys` di Unraid (resa persistente anche sulla flash, così sopravvive ai riavvii).
3. Clicca **Prova connessione**.

Il template aggiunge `--add-host=host.docker.internal:host-gateway` così il container può raggiungere l'host. Imposta `LIBVIRT_HOST` sull'IP LAN del tuo Unraid se quel nome non si risolve (per esempio quando il container gira su una rete personalizzata `br0.x`). Se hai cambiato la porta SSH di Unraid, imposta `LIBVIRT_SSH_PORT` di conseguenza. Gli **snapshot a caldo** richiedono anche il guest agent di qemu nella VM e il disco su `/mnt/cache` (non `/mnt/user`).

!!! important "Guida completa alla configurazione delle VM e alla rete"
    La guida completa passo per passo (attivazione di SSH, autorizzazione persistente della chiave, instradamento su rete personalizzata e VLAN, metodo per singola VM e risoluzione dei problemi lato host) è la [guida al backup delle VM](vm-backup-ssh-setup.md).

## Configurazione off-site {#off-site-setup}

Le copie off-site vanno nelle **destinazioni**. Apri **Destinazioni** dalla sua scheda delle impostazioni (o fissala alla barra laterale) e scegli **Aggiungi destinazione**. Vedi [Off-site e ripristino](offsite-recovery.md) per il flusso completo (protezione dall'eliminazione, prova di manomissione e prove DR). In breve:

- **Backend:** SMB/CIFS e WebDAV tramite rclone senza mount dell'host, NFS (monta l'export sull'host e usalo come cartella locale), backend nativi di restic senza rclone (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`), oppure qualsiasi remote rclone (`rclone:<remote>:<bucket>/path`). Backblaze B2 qui non ha un backend nativo: raggiungilo tramite il suo endpoint S3 (`s3:https://s3.<region>.backblazeb2.com/<bucket>/<path>`) con l'ID chiave e la chiave dell'applicazione come credenziali S3.
- Le **credenziali** sono salvate cifrate, come un unico elenco di credenziali salvate nella scheda **Credenziali** in **Impostazioni, Destinazioni**. Una stella segna quelle predefinite, usate dove non è scelta alcuna credenziale. La pagina di una destinazione sceglie quelle che usa nella sua scheda **Credenziali**. Vedi [Credenziali](offsite-recovery.md#sign-ins).
- **Le destinazioni SSH non richiedono nulla di installato dall'altra parte.** `sftp:` richiede solo un server SSH. Aggiungi la chiave pubblica da **Impostazioni, Integrazioni, SSH dell'host** (anche in `/config/ssh/id_ed25519.pub`) al `~/.ssh/authorized_keys` dell'utente di destinazione, oppure lascia che sia **Aggiungi chiave** in **Aggiungi destinazione** a metterla lì con la password dell'account.
- **rest-server con un certificato autofirmato:** metti il suo certificato, o quello dell'autorità che l'ha firmato, come file PEM nella cartella `certs` della cartella dati di BombVault (`/config/certs` nel container, `appdata/bombvault/certs` su Unraid). Backup, copie e prova della protezione dall'eliminazione lo accettano senza riavvio.
- **Copia off-site:** BombVault copia i nuovi snapshot con `restic copy` al meglio delle possibilità, sopra un primario (di solito locale). La scheda **Copia** di una destinazione decide se copia **Dopo ogni backup** o con un piano proprio, e **Impostazioni, Calendario, Copie off-site per sezione** dà a una sezione un piano di copia suo. **Replica ora** sta nella riga della sezione della scheda **Copie off-site** in **Impostazioni, Destinazioni**.
- **Più destinazioni per sezione:** la scheda **Destinazioni per sezione** nella pagina Destinazioni attiva o disattiva con un clic ogni collegamento da una sezione a una destinazione, **Locale** compreso. Una sezione con sole destinazioni off-site salva direttamente su di esse, e una con ogni collegamento disattivato non viene salvata. Le **Regole per sezione** di una destinazione danno a una sezione un repository, una conservazione o una compressione propri lì.
- **Destinazioni per elemento:** ogni container, VM e set di cartelle accende **Locale** e le destinazioni che ricevono i suoi backup, nella scheda **Calendario e destinazione** nella sua scheda Impostazioni. Gli elementi senza una scelta propria seguono la loro sezione. Vedi [Destinazioni per elemento](offsite-recovery.md#placement).
- **Conservazione:** ogni destinazione conserva i backup secondo la sua scheda **Per quanto tempo conservare**, e una sezione può tenervi valori propri sotto **Regole per sezione**. Questo comprende la copia nel campo off-site di una sezione. Tutti zero non pota mai gli snapshot di una destinazione.
- **Limiti di banda:** limita la velocità di upload e download di restic nella scheda **Larghezza di banda off-site** in **Impostazioni, Destinazioni**, oppure per destinazione nella sua scheda **Copia**. Inserisci KiB/s, e il campo mostra la stessa velocità in MB/s e Mbit/s.
- **Prima lo streaming:** nella scheda **Streaming** della pagina Destinazioni scegli i media server (Plex, Jellyfin ed Emby sono preselezionati per nome dell'immagine), la velocità di invio da cui conta come streaming, il limite di upload mentre fa streaming e quanto tempo dopo uno stream torna il limite normale.
- **Classe di archiviazione fredda e di archivio (S3):** per una destinazione S3 scegli nella sua pagina un livello leggibile per il ripristino (Standard, Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier Instant Retrieval). I remote rclone impostano la loro classe nella configurazione di rclone.
- **Cartella propria in una destinazione invece che locale:** la cartella propria di una sezione può stare in una delle destinazioni sopra, senza copia locale e senza passo di copia. Vedi [La cartella propria di una sezione](offsite-recovery.md#own-folder).

## Anomalie {#anomalies}

Il rilevamento delle anomalie non richiede alcuna variabile d'ambiente. Si imposta nella scheda **Anomalie** in **Impostazioni, Verifica**, descritta in [Anomalie](anomalies.md#settings).

## Impostazioni portabili (esportazione e importazione) {#portable-settings-export-and-import}

La scheda **Esporta / importa impostazioni** in **Impostazioni, Sistema** scrive l'intera configurazione di BombVault (impostazioni delle sezioni, destinazioni, pianificazioni, conservazione, notifiche) in un file JSON portabile che puoi importare su un'altra istanza, così passare a una macchina nuova o clonare una configurazione non significa reinserire tutto a mano. L'importazione mostra un'anteprima e chiede conferma, e non tocca mai i tuoi dati di backup né la cronologia. I collegamenti nel file a destinazioni o repository che non esistono più vengono lasciati fuori, e l'anteprima li nomina. Mentre gira una replica ZFS, un'importazione viene rifiutata prima che venga scritto qualsiasi cosa.

!!! warning "L'esportazione può contenere credenziali"
    Scegli tu se includere nel file le credenziali off-site, delle notifiche e del broker MQTT. Con le credenziali incluse, l'esportazione è delicata quanto il tuo kit di ripristino, quindi conservala in un posto sicuro. Senza di esse, il file contiene solo impostazioni non segrete.
