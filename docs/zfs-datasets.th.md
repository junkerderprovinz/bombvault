# ชุดข้อมูล ZFS

ชุดข้อมูล ZFS เป็นรายการในลิสต์ **การสำรองข้อมูล** เหมือนคอนเทนเนอร์และ VM หนึ่งรายการคือชุดข้อมูลหนึ่งชุดพร้อมทุกชุดข้างใต้ ในการสำรองแต่ละครั้ง BombVault ทำสแนปช็อต ZFS หนึ่งอันของทั้งต้นไม้ ทุกชุดข้อมูลในนั้นจึงถูกจับในจังหวะเดียวกัน จากนั้นมันอ่านไฟล์ของแต่ละชุดข้อมูลจากสแนปช็อตนั้นและเก็บด้วย restic แบบเดียวกับที่เก็บโฟลเดอร์ แล้วลบสแนปช็อตทันที การสำรองขจัดข้อมูลซ้ำ คุณเปิดดูทุกอันได้ และกู้คืนไฟล์เดี่ยวได้

การสำรองไม่เคยส่งสตรีมเข้า restic และไม่เคย rollback ชุดข้อมูล BombVault ทำลายเฉพาะสแนปช็อตที่มันสร้างเอง [เรพลิกา](#replica) ที่เลือกเปิดได้เป็นที่เดียวที่ใช้ `zfs send`: มันคัดลอกชุดข้อมูลไปยังเซิร์ฟเวอร์ ZFS ตัวที่สองและไม่แตะการสำรอง

## ข้อกำหนด {#requirements}

- **ลิงก์ SSH ไปยังเซิร์ฟเวอร์นี้** ชุดข้อมูล ZFS ใช้คีย์ โฮสต์ และผู้ใช้เดียวกับการสำรอง VM ถ้าการสำรอง VM ใช้ได้แล้ว อันนี้ก็ใช้ได้ ไม่เช่นนั้นทำตาม [คู่มือการสำรอง VM ผ่าน SSH](vm-backup-ssh-setup.md) ช่องเทมเพลตชื่อ **Host SSH: Address**, **Host SSH: Port** และ **Host SSH: User**
- **คำสั่ง `zfs` บนโฮสต์นั้น** Unraid 6.12 ขึ้นไปและ TrueNAS SCALE มี
- **Host Data ที่แมปเป็น `/mnt` ด้วย Access Mode Read/Write - Slave** เป็นค่าเริ่มต้นของเทมเพลต สแนปช็อตของชุดข้อมูลปรากฏในโฟลเดอร์ `.zfs/snapshot` ของชุดข้อมูลหลัง BombVault เริ่มแล้วเท่านั้น คอนเทนเนอร์จึงต้องรับ mount ที่โฮสต์ทำภายหลัง
- **ชุดข้อมูลที่เมานต์ใต้ `/mnt`** บน Unraid พูลอยู่ที่ `/mnt/<pool>` จึงเป็นเช่นนั้นอยู่แล้ว

เปิดส่วนที่ **การตั้งค่า, ทั่วไป** (ชุดข้อมูล ZFS) แล้ว **การเชื่อมต่อ ZFS กับเซิร์ฟเวอร์นี้** ใต้ **เพิ่มเติม** บนหน้าการสำรองข้อมูลจะเปิด **การเชื่อมต่อกับเซิร์ฟเวอร์นี้** มันทดสอบลิงก์ SSH ระบุผู้ใช้และโฮสต์ที่เชื่อมต่อ และบอกว่าขาดอะไรเมื่อมีอะไรขาด เมื่อลิงก์ล่ม ลิสต์การสำรองข้อมูลบอกด้วย **ดูการเชื่อมต่อ** และการ์ด **การผสานรวมโฮสต์** บนภาพรวมแสดงผลเดียวกัน

## รายการและชุดข้อมูลลูก {#items-and-children}

เลือก **เพิ่ม** บนหน้าการสำรองข้อมูล แล้ว **ชุดข้อมูล ZFS** รายการมาจากเซิร์ฟเวอร์ เลือกชุดข้อมูลบนสุดของสิ่งที่ต้องการสำรอง เช่น `cache/appdata` แล้วรายการจะครอบคลุมมันและทุกชุดข้างใต้

- **ชุดข้อมูลลูกใหม่เข้าร่วมเอง** ชุดข้อมูลที่สร้างใต้รายการทีหลังจะถูกสำรองในการรันครั้งถัดไป และการรันนั้นบอกว่าเป็นของใหม่ การสำรองครั้งแรกอ่านมันทั้งหมดหนึ่งครั้ง หลังจากนั้นอ่านเฉพาะสิ่งที่เปลี่ยน
- **เว้นลูกบางตัวได้** ปิดลูกตัวหนึ่งบนแท็บการตั้งค่าของรายการ แล้วมันจะถูกเว้นพร้อมทุกอย่างข้างใต้ ลูกที่เว้นไว้ซึ่งไม่มีบนเซิร์ฟเวอร์แล้วจะถูกทำเครื่องหมายและลบออกจากรายการได้
- **ลูกที่อ่านไม่ได้ถูกข้าม ไม่เคยข้ามเงียบ ๆ** การรันลิสต์พวกมัน รายการแสดงว่าข้ามกี่ตัว และการ์ด **ไม่ได้สำรองข้อมูล** บนภาพรวมนับแต่ละตัวว่ายังไม่ได้ป้องกัน การรันยังสำรองอย่างอื่นทั้งหมดและไม่ล้มเหลวเพราะลูกที่ข้าม เหตุผลอยู่ใน [ตารางรหัสเหตุผล](#reason-codes): ชุดข้อมูลที่ไม่ได้เมานต์ มี `canmount=off` มี mountpoint แบบ `legacy` หรือไม่มี คีย์เข้ารหัสที่ไม่ได้โหลด ปิดการเข้าถึงสแนปช็อต หรือ mountpoint ที่ BombVault มองไม่เห็น
- **ชุดข้อมูลที่ข้ามไม่พาลูกไปด้วย** ชุดข้อมูล `canmount=off` ที่เก็บแค่ชุดข้อมูลอื่นจะถูกข้าม (แสดงเป็น "structure only") และลูกที่เมานต์อยู่ถูกสำรอง ชุดข้อมูลที่เข้ารหัสซึ่งไม่ได้โหลดคีย์ถูกข้ามพร้อมลูกที่ใช้คีย์ร่วมกัน
- **ลูกที่เป็นดิสก์ VM หรือข้อมูลระบบเริ่มต้นแบบปิด** ในกล่องเพิ่ม พร้อมเหตุผลข้างสวิตช์ การเพิ่มทั้งพูลขอให้ยืนยันโดยลิสต์สิ่งที่มีอยู่ในนั้น

### Volume {#volumes}

volume (zvol) เก็บดิสก์เสมือนแทนไฟล์ และรายการ ZFS ไม่เคยสำรองมัน

- volume ที่ VM ใช้ถูกสำรองพร้อม VM นั้น
- volume ที่ไม่มี VM ใช้ (iSCSI extent ดิสก์ที่คุณถอดออก) **BombVault ไม่สำรอง** หน้าต่างเพิ่มและหน้าการสำรองข้อมูลนับ volume เหล่านี้และบอกไว้ เวอร์ชันต่อไปจะสำรองมัน

volume ภายในต้นไม้ของรายการถูกข้ามและระบุชื่อในทุกการรัน

### ที่เก็บข้อมูลของ Docker {#docker-storage}

กับไดรเวอร์จัดเก็บ ZFS ของ Docker ทุกเลเยอร์ของ image เป็นชุดข้อมูลที่มี mountpoint แบบ `legacy` กล่องเพิ่มพับเลเยอร์เหล่านี้เป็นหนึ่งบรรทัดต่อพาเรนต์ ต้นไม้ที่มีชุดข้อมูลแบบนั้นเกิน 20 ชุดเป็นรายการไม่ได้: ขณะที่มีสแนปช็อตของมัน Docker ลบเลเยอร์ image ไม่ได้ ให้เพิ่มชุดข้อมูลข้างใต้แทน เช่น `appdata`

### รายการไม่ซ้อนทับกัน {#overlap}

ชุดข้อมูลหนึ่งอยู่ในรายการเดียวได้เท่านั้น BombVault ปฏิเสธรายการใหม่ที่อยู่ในรายการที่มีอยู่ หรือที่จะมีรายการหนึ่งอยู่ข้างใน ถ้าจะรวมรายการลูกหลายอันเป็นรายการพาเรนต์เดียว ให้ลบรายการลูกก่อนและเลือกเก็บข้อมูลสำรองของมัน แล้วเพิ่มพาเรนต์ ทุกชุดข้อมูลเก็บประวัติของมันใต้ชื่อของตัวเอง การสำรองครั้งถัดไปจึงต่อจากที่รายการเก่าค้างไว้ และไม่ต้องอ่านทุกอย่างอีก

## หยุดคอนเทนเนอร์และคำสั่งรอบสแนปช็อต {#consistency}

สแนปช็อตของฐานข้อมูลที่กำลังรันเหมือนไฟดับกะทันหัน: ฐานข้อมูลมักกู้ตัวเองได้ แต่ต้องกู้ รายการหนึ่งทำได้สองอย่างเกี่ยวกับเรื่องนี้ และทั้งคู่ครอบคลุมเฉพาะจังหวะของสแนปช็อต ไม่ใช่ทั้งการสำรอง

- **หยุดคอนเทนเนอร์เหล่านี้ระหว่างสแนปช็อต** BombVault หยุดคอนเทนเนอร์ที่ลิสต์ไว้ ทำสแนปช็อต และเริ่มใหม่ทันที คอนเทนเนอร์ในระดับการพึ่งพาเดียวกันหยุดพร้อมกัน ตัวที่พึ่งพาก่อน ช่วงเวลาทั้งหมดจึงมักเป็นไม่กี่วินาที การรันแสดงว่านานเท่าไร จากนั้นการสำรองอ่านสแนปช็อตที่แช่แข็งขณะที่แอปกลับมารันแล้ว เฉพาะคอนเทนเนอร์ที่รันอยู่เท่านั้นที่ถูกหยุด
- **คำสั่งก่อนและหลังสแนปช็อต** รันภายในคอนเทนเนอร์ที่คุณเลือก เช่นเพื่อดัมป์ฐานข้อมูลลงชุดข้อมูลก่อนสแนปช็อตทันที โดยไม่หยุดอะไร ถ้าคำสั่งก่อนสแนปช็อตล้มเหลว การสำรองล้มเหลวและไม่มีการทำสแนปช็อต คำสั่งหลังสแนปช็อตที่ล้มเหลวแสดงบนการรันแต่ไม่ทำให้การสำรองล้มเหลว

เมื่อมีอะไรผิดพลาด

- ถ้าหยุดคอนเทนเนอร์ไม่ได้ BombVault เริ่มตัวที่หยุดไปแล้วใหม่ และการสำรองล้มเหลว โดยระบุชื่อคอนเทนเนอร์ มันไม่เคยถอยไปทำสแนปช็อตขณะแอปรันอยู่
- การหยุดรอให้การสำรองคอนเทนเนอร์ที่กำลังรันเสร็จ (นานถึง 30 นาทีสำหรับการรันด้วยมือ นานถึงขีดจำกัดเวลาการสำรองสำหรับการรันตามกำหนด) ทั้งสองจึงไม่หยุดและเริ่มคอนเทนเนอร์เดียวกันพร้อมกัน
- ก่อนคอนเทนเนอร์แรกหยุด BombVault จดไว้ว่าจะหยุดตัวไหน ถ้า BombVault ถูกฆ่าในช่วงนั้น มันจะเริ่มคอนเทนเนอร์เหล่านั้นอีกครั้งเมื่อเริ่มทำงานครั้งถัดไป ส่งการแจ้งเตือน และรายการแสดงหมายเหตุสีแดงสำหรับคอนเทนเนอร์ที่เริ่มไม่ได้

[ดัมป์ฐานข้อมูล](backups.md#database-dumps) อัตโนมัติรันพร้อมการสำรองของคอนเทนเนอร์เอง ไม่ใช่กับรายการ ZFS ฐานข้อมูลที่คอนเทนเนอร์ถูกสำรองผ่านชุดข้อมูลเท่านั้นจะไม่มีดัมป์ จึงให้คำสั่งที่นี่

คอนเทนเนอร์อยู่ในลิสต์นี้และถูกสำรองเป็นคอนเทนเนอร์ในเวลาเดียวกันได้ ข้อมูลของมันก็ถูกเก็บสองครั้งในสองที่เก็บ และการสำรองทั้งหมดหยุดมันสองครั้ง รายการบอกไว้

## การกู้คืน {#restore}

เปิดรายการแล้วเลือก **กู้คืน** หรือเลือกบนหน้า **การกู้คืน** หน้าต่างกู้คืนถามข้อมูลสำรอง แล้ว **ชุดข้อมูล** โดยค่าเริ่มต้นคือชุดข้อมูลบนสุดของรายการ ใต้ **อะไร** คุณกู้คืนทั้งหมดหรือเฉพาะไฟล์และโฟลเดอร์ที่เลือก **ไปที่ไหน** เสนอ

- **กู้คืนกลับเข้าชุดข้อมูล** ไฟล์จากข้อมูลสำรองถูกเขียนลงใน mountpoint ของชุดข้อมูล ไฟล์ชื่อเดียวกันถูกเขียนทับ ไฟล์อื่นอยู่ต่อ ชุดข้อมูลไม่เคยถูก rollback หรือแทนที่ BombVault ตรวจว่าชุดข้อมูลเมานต์ มองเห็นได้ และเขียนได้ หนึ่งครั้งก่อนเริ่มและอีกครั้งก่อนเขียน ที่ที่ชุดข้อมูลลูกเมานต์อยู่ข้างใน จะไม่เขียนอะไร: ลูกเก็บไฟล์ เจ้าของ และสิทธิ์ของมันไว้ และกู้คืนจากข้อมูลสำรองของตัวเอง
- **ไปยังโฟลเดอร์** เลือกโฟลเดอร์ใต้ `/mnt` BombVault ตรวจว่าโฟลเดอร์อยู่บนพูลหรือ share ที่เมานต์และมีที่ว่างพอ ใช้ได้โดยไม่ต้องมีลิงก์ SSH และสำหรับชุดข้อมูลที่ไม่มีอยู่แล้ว
- **ไปยังชุดข้อมูลใหม่** ตั้งชื่อชุดข้อมูลที่ยังไม่มี หน้าต่างเสนอ `<dataset>-restored` BombVault สร้างมันด้วยคุณสมบัติ ZFS ที่เก็บในข้อมูลสำรองและกู้คืนลงไป ดู [กู้คืนเป็นชุดข้อมูลใหม่](#new-dataset)

การเลือก **ชุดข้อมูลทั้งหมดของการสำรองนี้** เป็นชุดข้อมูลเขียนทุกชุดของต้นไม้ลงโฟลเดอร์ย่อยของตัวเองภายในโฟลเดอร์ที่คุณเลือก ชุดข้อมูลที่ถูกข้ามในการสำรองนั้นถูกระบุชื่อ ถ้าจะกู้คืนจากที่เก็บของ BombVault อีกเครื่อง ใช้ **จากโฟลเดอร์สำรองข้อมูลเก่า** บนหน้าการกู้คืน มันกู้คืนลงโฟลเดอร์เสมอ: ทุกชุดข้อมูลของการสำรองหนึ่งครั้ง แต่ละชุดลงโฟลเดอร์ย่อยของตัวเอง หรือชุดข้อมูลหนึ่งชุดของต้นไม้ ทั้งชุดหรือเฉพาะไฟล์ที่เลือก

รายการคอนเทนเนอร์ที่ต้องหยุดของรายการเสนอสำหรับการกู้คืนกลับเข้าชุดข้อมูลด้วย คอนเทนเนอร์เหล่านั้นหยุดอยู่ตลอดการกู้คืน และการสำรองคอนเทนเนอร์รอในช่วงนั้น

### สแนปช็อตเพื่อความปลอดภัย {#safety-snapshot}

ก่อนเขียนลงชุดข้อมูล BombVault ทำสแนปช็อต ZFS ของชุดข้อมูลนั้นชุดเดียว ชื่อ `bombvault-prerestore-<time>` **เก็บสแนปช็อต ZFS ของสภาพปัจจุบันก่อน** เปิดอยู่โดยค่าเริ่มต้น การปิดต้องยืนยันครั้งที่สอง ถ้าทำสแนปช็อตไม่ได้ จะไม่กู้คืนอะไร

BombVault ไม่เคยลบสแนปช็อตเพื่อความปลอดภัยเอง รายการลิสต์พวกมันพร้อมอายุและขนาด แต่ละอันมีการกระทำ **ลบ** และเตือนเมื่ออันเก่าสุดเก่ากว่า 30 วัน เพราะมันเก็บข้อมูลที่ถูกลบและเปลี่ยนไว้บนพูล

ถ้าจะย้อนหลังการกู้คืน ให้คัดลอกไฟล์เดี่ยวจาก `.zfs/snapshot/bombvault-prerestore-<time>` ภายในชุดข้อมูล `zfs rollback <dataset>@bombvault-prerestore-<time>` ใช้ได้เฉพาะขณะที่มันเป็นสแนปช็อตใหม่สุดของชุดข้อมูลนั้น `zfs rollback -r` ลบทุกสแนปช็อตที่ใหม่กว่า รวมถึงที่อัตโนมัติ

### กู้คืนเป็นชุดข้อมูลใหม่ {#new-dataset}

BombVault เก็บคุณสมบัติ ZFS ที่ตั้งในเครื่องของทุกชุดข้อมูลพร้อมการสำรองแต่ละครั้ง: compression, record size, quota, reservation, atime, xattr, acltype, case sensitivity และคุณสมบัติผู้ใช้ของคุณเอง ค่าที่สืบทอดและอ่านอย่างเดียวถูกเว้นไว้ เพราะมันกลับมาเอง ข้อมูลสำรองก่อนที่ BombVault จะเก็บคุณสมบัติไม่มีมัน

- **ไปยังชุดข้อมูลใหม่** รัน `zfs create` พร้อมทุกคุณสมบัติที่เก็บไว้ case sensitivity, normalization และ utf8only ตั้งได้ด้วยวิธีนี้เท่านั้น quota และ reservation ตั้งหลังไฟล์ จึงปฏิเสธไฟล์ไม่ได้ mountpoint ถูกเว้นไว้ สำเนาจึงไม่ชนกับต้นฉบับ และ `canmount`, `readonly` และการตั้งค่าการเข้ารหัสก็เว้นไว้ด้วย เพื่อให้การกู้คืนเขียนได้ ชุดข้อมูลใหม่ใต้ชุดที่เข้ารหัสรับการเข้ารหัสของมัน ชุดข้อมูลเหนือชุดใหม่ต้องมีอยู่ ถ้ามีอะไรล้มเหลวหลังสร้างชุดข้อมูลใหม่แล้ว มันอยู่บนเซิร์ฟเวอร์ต่อ เพราะ BombVault ไม่เคยทำลายชุดข้อมูล
- **กู้คืนกลับเข้าชุดข้อมูล** ลิสต์คุณสมบัติที่เก็บไว้ข้างการกู้คืน **ตั้งคุณสมบัติเหล่านี้ด้วย** ตั้งอันที่ชุดข้อมูลที่มีอยู่ยังรับได้ ก่อนเขียนไฟล์ใด quota และ reservation ตั้งหลังไฟล์ จึงปฏิเสธไฟล์ไม่ได้ ถ้าไม่เปิดสวิตช์นั้น ชุดข้อมูลเก็บการตั้งค่าของมันไว้

## อะไรอยู่ในการสำรอง {#contents}

อยู่ในการสำรอง: ไฟล์และโฟลเดอร์ของทุกชุดข้อมูลที่สำรอง พร้อมความเป็นเจ้าของ สิทธิ์ เวลา และ extended attributes ตามที่ restic เก็บ และคุณสมบัติ ZFS ที่ตั้งในเครื่องของแต่ละชุดข้อมูล

ไม่อยู่ในการสำรอง

- เจ้าของและสิทธิ์ของโฟลเดอร์บนสุดของแต่ละชุดข้อมูลเอง (ทุกอย่างข้างใต้รวมอยู่) การกู้คืนกลับเข้าชุดข้อมูลปล่อยโฟลเดอร์บนสุดที่มีอยู่ตามเดิม การกู้คืนไปยังโฟลเดอร์สร้างมันด้วยโหมด `0755`
- สแนปช็อต ZFS ที่มีอยู่
- ลูกที่ถูกข้ามหรือเว้นไว้
- volume

ถ้าจะกู้คืนไปยังพูลใหม่ ให้สร้างพูลและกู้คืนแต่ละชุดข้อมูลเข้าชุดข้อมูลใหม่ ยังไม่ได้ตรวจว่า ACL แบบ NFSv4 ที่ TrueNAS ใช้บนชุดข้อมูล SMB กลับมาตามที่คุณคาดหรือไม่ จึงควรตรวจการกู้คืนบนข้อมูลของคุณเองก่อนพึ่งมัน

## ชุดข้อมูลที่เข้ารหัส {#encryption}

ชุดข้อมูลที่เข้ารหัสถูกสำรองเฉพาะขณะที่โหลดคีย์ ไม่เช่นนั้นถูกข้ามพร้อมคำเตือน โหลดคีย์ด้วย `zfs load-key` และเมานต์ชุดข้อมูล BombVault อ่านข้อมูลที่ถอดรหัสแล้วและเก็บในที่เก็บของ restic ซึ่งเข้ารหัส ถ้าคุณปิดการเข้ารหัสใน BombVault ที่เก็บนั้นก็ไม่เข้ารหัส

## เรพลิกา {#replica}

เรพลิกาคือสำเนาของชุดข้อมูลของรายการบนเซิร์ฟเวอร์ ZFS ตัวที่สอง BombVault ทำให้มันเป็นปัจจุบันด้วย `zfs send` และ `zfs receive` การรันครั้งแรกส่งทุกอย่าง หลังจากนั้นเดินทางเฉพาะบล็อกที่เปลี่ยน บนเซิร์ฟเวอร์อีกตัวคุณเมานต์สำเนาได้ทันที

เรพลิกาไม่เคยแทนที่การสำรอง เวอร์ชันเก่า ไฟล์เดี่ยว และการตรวจยังมาจากการสำรอง และเรพลิกาเก็บสแนปช็อตเท่าจำนวนที่คุณตั้ง เรพลิกาที่เป็นปัจจุบันนับเป็นสำเนานอกสถานที่ แต่ไม่ใช่การสำรอง

เรพลิกาไม่รอการสำรอง **หลังสำรองทุกครั้ง** หมายถึงหลังการสำรองของรายการ ไม่ว่าการรันนั้นจะสำเร็จ ล้มเหลว หรือไม่พบอะไรให้ทำ เมื่อส่วน ZFS ไม่มีปลายทางที่จัดเก็บเปิดอยู่และรายการไม่มีที่เก็บของตัวเอง การสำรองของรายการจะส่งเฉพาะเรพลิกา และการ์ดเรพลิกาบอกไว้ในบับเบิลข้าง **เมื่อไร** ลิสต์การสำรองข้อมูล ส่วนหัวของรายการ และประวัติการรันแสดงเรพลิกา: **กำลังจำลอง** ขณะรัน และ **ทำเรพลิกาแล้ว** พร้อมเวลาเมื่อเสร็จ

**เฉพาะเรพลิกา ไม่สำรองข้อมูล** บนการ์ดเรพลิกาทำให้ทั้งส่วน ZFS ส่งเรพลิกาและไม่ทำการสำรอง โฟลเดอร์ของตัวเองและปลายทางนอกสถานที่เก็บสวิตช์ของมัน ดังนั้นการปิดจะสำรองไปที่นั่นอีกครั้ง และการ์ดของทุกรายการ ZFS แสดงสวิตช์ของส่วนตามที่เป็น รายการแบบนั้นรอเรพลิกาแรกแทนการสำรอง **สำรองข้อมูลเดี๋ยวนี้** ถูกเสนอเป็น **ทำเรพลิกาตอนนี้** และคอนเทนเนอร์ของรายการหยุดและคำสั่งรันรอบสแนปช็อตเหมือนการสำรอง เรพลิกาของมันนับสำหรับตารางเวลาแบบทุกไม่กี่วัน การเตือนที่ล่าช้า และความครอบคลุม

เปิดในการ์ด **เรพลิกา** บนแท็บการตั้งค่าของรายการ การ์ดลิสต์ทุกชุดข้อมูลและ volume พร้อมสถานะ และ **ทำเรพลิกาตอนนี้** เริ่มการรัน การรันเรพลิกามีล็อกของตัวเอง การถ่ายโอนครั้งแรกที่ยาวจึงไม่ขวางการสำรอง

| ฟิลด์ | ตั้งอะไร |
|---|---|
| **ทำเรพลิกาไปที่** | ปลายทาง: เซิร์ฟเวอร์ ZFS (ทำเครื่องหมาย **ผ่าน SSH**) หรือ **อินสแตนซ์ที่จับคู่** **เพิ่มเซิร์ฟเวอร์ ZFS** ตั้งค่าตัวใหม่ |
| **เมื่อไร** | **หลังสำรองทุกครั้ง** หมายถึงหลังการสำรองของรายการ หรือ **กำหนดการของตัวเอง** |
| **เก็บไว้ที่ปลายทาง** | จำนวนสแนปช็อตที่อยู่บนเซิร์ฟเวอร์ ZFS: **สั้น**, **สมดุล**, **ยาว** หรือ **ค่าที่กำหนดเอง** อินสแตนซ์ที่จับคู่ตัดสินใจเอง |
| **เก็บไว้บนเซิร์ฟเวอร์นี้** | สแนปช็อตเรพลิกาใหม่สุดกี่อันที่อยู่บนเซิร์ฟเวอร์นี้ด้วย 0 หรือ 1 เก็บเฉพาะอันล่าสุด |
| **เฉพาะเรพลิกา ไม่สำรองข้อมูล** | ทั้งส่วน ZFS ส่งเรพลิกาและไม่ทำการสำรอง |

![การ์ดเรพลิกาของรายการ ZFS](assets/screenshots/zfs/replica-dark.png#only-dark)
![การ์ดเรพลิกาของรายการ ZFS](assets/screenshots/zfs/replica-light.png#only-light)

**ทำเรพลิกาทั้งหมดตอนนี้** ข้างการกระทำสำรองเมื่อเลือกไทล์ ZFS บนหน้าการสำรองข้อมูล ส่งเรพลิกาของทุกรายการ ZFS ทีละรายการ เซิร์ฟเวอร์รันชุดนี้ มันจึงทำต่อเมื่อคุณออกจากหน้า และรายการที่ทำเรพลิกาไม่ได้จะถูกระบุชื่อและข้าม

### ส่งไปยังเซิร์ฟเวอร์ ZFS {#replica-push}

เครื่องใดก็ได้ที่มี ZFS และ SSH รับได้ เช่น Unraid ตัวที่สองหรือ TrueNAS BombVault ไม่ต้องรันที่นั่น

1. ใต้ **การตั้งค่า, การจับคู่** เลือก **เชื่อมต่อผ่าน SSH** ใน **เซิร์ฟเวอร์ ZFS ที่ไม่มี BombVault** หรือ **เพิ่มเซิร์ฟเวอร์ ZFS** ในการ์ด **เรพลิกา** ของรายการ
2. กรอกที่อยู่ ผู้ใช้ และพอร์ต กล่องแสดงกุญแจสาธารณะของ BombVault เพิ่มลงใน `~/.ssh/authorized_keys` ของผู้ใช้บนเซิร์ฟเวอร์ บน Unraid อยู่ใต้ **Users, root, SSH keys** ขึ้นกับ **Display Settings** Users อยู่ในเมนูส่วนหัวหรือใต้ Settings บน TrueNAS แก้ไขผู้ใช้ที่ **Credentials, Users** นี่คือคีย์เรพลิกา มันต่างจากคีย์ของลิงก์ SSH ของ VM และโฮสต์ ดังนั้นให้เพิ่มแม้อันนั้นจะได้รับอนุญาตแล้ว
3. ทดสอบการเชื่อมต่อ กล่องจะลิสต์พูลของเซิร์ฟเวอร์ เลือกหนึ่งพูลและตั้งราก ซึ่งค่าเริ่มต้นคือ `<pool>/bombvault-replica`
4. เลือกเซิร์ฟเวอร์ใหม่ในการ์ด **เรพลิกา** ของรายการ จากนั้นเซิร์ฟเวอร์มีการ์ดของตัวเองบนหน้าอินสแตนซ์ และ **เปิด** พาไปยังหน้าของมัน

ด้วย root ไม่ต้องใช้อย่างอื่น ผู้ใช้ของตัวเองต้องมีสิทธิ์เหล่านี้บนพูลของปลายทาง ซึ่งกล่องแสดงด้วย

```
zfs allow <user> receive,create,mount,rollback,destroy,userprop <pool>
```

ที่ต้นทาง ผู้ใช้แบบเดียวกันต้องมีสิทธิ์เหล่านี้บนชุดข้อมูลบนสุดของรายการ

```
zfs allow <user> send,snapshot,hold,release,bookmark,destroy <dataset>
```

ในทิศทางนี้ BombVault ที่ถือรายการยังถือคีย์ที่เขียนบนเซิร์ฟเวอร์ได้ด้วย

BombVault ปักหมุดคีย์โฮสต์ที่เซิร์ฟเวอร์แสดงตอนเชื่อมต่อครั้งแรกและปฏิเสธอันที่ต่างออกไปภายหลัง ถ้าเซิร์ฟเวอร์ถูกติดตั้งใหม่ ให้กด **ลืมกุญแจโฮสต์** บนหน้าของเซิร์ฟเวอร์ แล้วการเชื่อมต่อครั้งถัดไปจะปักหมุดคีย์ใหม่

เมื่อโฮสต์ของเซิร์ฟเวอร์นี้เข้าถึงเซิร์ฟเวอร์ ZFS ได้เอง มันส่ง `zfs send` ตรงเข้า ssh ของตัวเองไปยังเซิร์ฟเวอร์ ด้วยคีย์เรพลิกาและคีย์โฮสต์ที่ปักหมุด สตรีมจึงไม่ผ่าน BombVault ไม่เช่นนั้นสตรีมผ่าน BombVault

### ส่งไปยังอินสแตนซ์ที่จับคู่ {#replica-receive}

BombVault ที่จับคู่รับเรพลิกาเองได้ ไม่มีใครได้เข้าถึง SSH ของโฮสต์อีกฝั่ง และไม่มีคีย์ใดเข้าไฟล์ `authorized_keys`

1. ในการ์ด **เรพลิกา** ของรายการ เลือกอินสแตนซ์ที่จับคู่เป็นปลายทาง หรือเปิดบทบาท **เซิร์ฟเวอร์ ZFS** บนการ์ดของอินสแตนซ์นั้นในหน้าอินสแตนซ์ แล้วเลือกรายการ ZFS ที่นั่น การ์ดแสดง **รอการอนุมัติ** จนกว่ามันจะตอบ
2. บนอินสแตนซ์ที่รับ เปิด **อินสแตนซ์** คำขอแสดงบนการ์ดของอินสแตนซ์ที่ส่งเป็นป้าย และ **รายละเอียด** ของมันลิสต์ไว้ เลือกพูลและรากบนเซิร์ฟเวอร์นั้นและจำนวนสแนปช็อตที่คงไว้ แล้วกด **อนุญาต** หรือ **ปฏิเสธ**
3. หลัง **อนุญาต** ต้นทางส่งตามกำหนดการของตัวเอง เหมือนปลายทางอื่น

อินสแตนซ์ที่รับยอมรับเฉพาะสิ่งที่การอนุมัติครอบคลุม: ชุดข้อมูลของรายการ เข้าราก ของมันเอง มันรัน `zfs receive` เอง และต้นทางไม่มีทางลบหรือ rollback อะไรที่นั่น สำเนาจึงอยู่รอดแม้ต้นทางถูกยึดครอง อินสแตนซ์ที่รับเก็บการเก็บรักษาของตัวเอง ต้นทางแค่เสนอกฎตอนขอ

**เพิกถอนการเข้าถึง** บนอินสแตนซ์ที่รับจบการอนุมัติได้ทุกเมื่อและบอกต้นทาง ซึ่งแสดงว่าการอนุมัติถูกถอนและหยุด สิ่งที่อินสแตนซ์ที่รับถืออยู่แล้วคงอยู่ที่นั่น คำขอที่ถูกปฏิเสธยังคงปฏิเสธ ชุดข้อมูลเพิ่ม หรือคำขอหลังการเพิกถอน ต้องขออีกครั้ง

อินสแตนซ์ที่รับต้องตอบผ่าน HTTPS ต้นทางไม่ส่งอะไรไปยังที่อยู่ http ธรรมดา เพราะโทเค็นและข้อมูลจะข้ามเครือข่ายโดยไม่เข้ารหัส ทุกการถ่ายโอนยังเหลือพื้นที่หนึ่งในสิบของพูลที่รับไว้ว่างและหยุดก่อนที่จะกินเข้าไป ต้นทางตัวเดียวจึงทำให้พูลของเซิร์ฟเวอร์ที่รับเต็มไม่ได้

### ข้อมูลไปลงที่ไหน {#replica-target}

แต่ละชุดข้อมูลไปลงที่ `<root>/<server>/<pool>/<path>` โฟลเดอร์เซิร์ฟเวอร์คือชื่อของอินสแตนซ์ต้นทาง ตายตัวตั้งแต่การถ่ายโอนครั้งแรก เซิร์ฟเวอร์สองตัวที่ใช้ชื่อพูลเดียวกันจึงไม่ขวางกัน เช่น `cache/appdata` ของเซิร์ฟเวอร์ชื่อ `tower` ไปลงที่ `backup/bombvault-replica/tower/cache/appdata`

หลังตั้งค่า BombVault ใหม่ ปลายทางปฏิเสธโฟลเดอร์ที่ BombVault ตัวนี้เคยเติมไว้ การ์ดเรพลิกาจึงเสนอ **รับโฟลเดอร์มาเป็นของตน** และเรพลิกาครั้งถัดไปทำต่อจากสำเนาในนั้น รับมาเฉพาะเมื่อไม่มี BombVault ตัวอื่นยังทำเรพลิกาเข้าโฟลเดอร์นั้น

สำเนาบนปลายทางเป็นแบบอ่านอย่างเดียว โดยค่าเริ่มต้นไม่ได้เมานต์ จึงไม่เคยบังอะไรบนเซิร์ฟเวอร์นั้น เซิร์ฟเวอร์ ZFS ที่เชื่อมต่อผ่าน SSH มีสวิตช์ **เมานต์แบบอ่านอย่างเดียวบนเซิร์ฟเวอร์** บนหน้าของมัน: เมื่อเปิด BombVault เมานต์สำเนาที่นั่นแบบอ่านอย่างเดียวหลังทุกการรัน คุณจึงอ่านและคัดลอกไฟล์ของมันบนปลายทางได้ สำเนาที่เข้ารหัสยังล็อกอยู่จนกว่าจะโหลดคีย์ และการปิดไม่ unmount อะไร อินสแตนซ์ที่จับคู่ซึ่งรับเรพลิกาเก็บมันไว้โดยไม่เมานต์ คุณสมบัติ ZFS เดินทางไปด้วย ยกเว้น mountpoint และ `sharenfs` กับ `sharesmb` reservation ทั้ง `reservation` และ `refreservation` ก็ถูกทิ้งไว้ สำเนาจึงใช้เฉพาะพื้นที่ที่ข้อมูลของมันต้องการ

### อะไรเข้าไปบ้าง {#replica-contents}

ทุกอย่างที่รายการสำรองเข้าไป และ volume ข้างใต้ด้วย ซึ่งการสำรองข้าม ชุดข้อมูลลูกที่คุณปิดในรายการอยู่นอก ทุกชุดข้อมูลของการรันมาจากสแนปช็อตเดียว เหมือนในการสำรอง

### สแนปช็อตอยู่นานแค่ไหน {#replica-retention}

บนปลายทาง เรพลิกาใหม่เก็บสแนปช็อตรายวัน 7 และรายสัปดาห์ 3 เลือก **สั้น**, **สมดุล** หรือ **ยาว** แทน หรือตั้ง **ค่าที่กำหนดเอง** เฉพาะสแนปช็อตชื่อ `bombvault-replica-<14 digits>` เท่านั้นที่ถูกลบที่นั่น และไม่เคยลบอันใหม่สุดที่สองฝั่งใช้ร่วมกัน

ที่ต้นทาง BombVault เก็บสแนปช็อตเรพลิกาล่าสุด พร้อมบุ๊กมาร์กของทุกสถานะที่ส่งไปแล้ว บุ๊กมาร์กไม่เสียพื้นที่ การถ่ายโอนครั้งถัดไปเริ่มจากมัน

ถ้าจะเก็บมากกว่านั้นที่ต้นทางด้วย ตั้ง **เก็บไว้บนเซิร์ฟเวอร์นี้** บนการ์ดเรพลิกา เช่น 7 สแนปช็อตเรพลิกาใหม่สุดจำนวนนั้นจะอยู่บนเซิร์ฟเวอร์นี้หลังทุกเรพลิกา ข้างสิ่งที่ปลายทางเก็บ 0 หรือ 1 เก็บเฉพาะอันล่าสุด อันล่าสุดมี hold ฐานของการถ่ายโอนครั้งถัดไปจึงไม่ถูกทำลายโดยบังเอิญ อันเก่ากว่าไม่มี แต่ละสแนปช็อตถือบล็อกที่เปลี่ยนหลังมัน ทุกอันที่คุณเก็บจึงใช้พื้นที่บนพูล การปิดเรพลิกาหรือเปลี่ยนไปปลายทางอื่น หรือการลบรายการ ลบพวกมันออกจากเซิร์ฟเวอร์นี้ด้วย

ไฟล์ของสแนปช็อตที่เก็บไว้อ่านหรือคัดลอกได้ทันที จากโฟลเดอร์ `.zfs/snapshot` ภายในชุดข้อมูลหรือจาก clone โดยไม่แตะชุดข้อมูลหรือเรพลิกา

```
ls /mnt/cache/appdata/.zfs/snapshot/bombvault-replica-20261006014100
zfs clone cache/appdata@bombvault-replica-20261006014100 cache/appdata-20261006
```

clone ไม่ใช้พื้นที่จนกว่าจะมีอะไรในนั้นเปลี่ยน ทำลายมันด้วย `zfs destroy cache/appdata-20261006` เมื่อเสร็จ เพราะสแนปช็อตที่มี clone ลบไม่ได้

การย้อนกลับไปสแนปช็อตเรพลิกาล่าสุดต้องใช้แค่ `zfs rollback cache/appdata@<latest>` ที่นี่ และไม่ต้องทำอะไรบนปลายทาง การ rollback ทั้งชุดข้อมูลไปอันที่เก่ากว่าทำลายทุกสแนปช็อตหลังมัน ทั้งบนเซิร์ฟเวอร์นี้และบนปลายทาง อันล่าสุดถูกถือ hold ไว้ ให้ปลด hold ก่อน แล้ว rollback ชุดข้อมูลที่นี่

```
zfs release -r bombvault-replica cache/appdata@bombvault-replica-20261008014200
zfs rollback -r cache/appdata@bombvault-replica-20261006014100
```

สำเนาบนปลายทางต้องย้อนกลับด้วย แต่ไม่ใช่ไปสแนปช็อตเดียวกันเสมอไป เพราะกฎการเก็บของมันเองอาจทิ้งอันนั้นไปแล้ว รันเรพลิกาหนึ่งครั้ง มันหยุดสำหรับชุดข้อมูลนั้นเพราะปลายทางมีสแนปช็อตที่ใหม่กว่า และการ์ดเรพลิกากับประวัติการรันระบุสแนปช็อตที่ต้อง rollback ปลายทางไป: อันใหม่สุดที่สองฝั่งยังใช้ร่วมกัน rollback สำเนาไปที่มันบนเซิร์ฟเวอร์ ZFS หรือบนโฮสต์ของอินสแตนซ์ที่จับคู่ซึ่งรับเรพลิกา เช่น

```
zfs rollback -r backup/bombvault-replica/tower/cache/appdata@bombvault-replica-20261005014000
```

`zfs rollback` ทำงานกับชุดข้อมูลหนึ่งชุด จึงทำซ้ำสำหรับแต่ละชุดข้อมูลลูกที่คุณต้องการกลับมาด้วย หลังจากนั้น **ทำเรพลิกาตอนนี้** ทำต่อจากสแนปช็อตที่ใช้ร่วมกัน

### ชุดข้อมูลที่เข้ารหัสในเรพลิกา {#replica-encryption}

ชุดข้อมูลที่เข้ารหัสถูกส่งแบบ raw มันยังเข้ารหัสอยู่บนปลายทาง และปลายทางไม่เคยเห็นคีย์ เก็บคีย์ให้ปลอดภัย: คุณต้องใช้มันเปิดสำเนาหลังการกู้คืน และเรพลิกาที่ไม่มีมันอ่านไม่ได้

### ใช้เรพลิกา {#replica-use}

เปิดแท็บ **การสำรองข้อมูล** ของรายการแล้วคลิกแถว **เรพลิกา ZFS** ในบรรดาที่ที่เก็บสแนปช็อต แผ่นลิสต์สแนปช็อตบนปลายทางและแสดงคำสั่งพร้อมชื่อจริงของคุณ

ถ้าจะดูสถานะเก่า ให้ clone สแนปช็อตบนปลายทาง clone ไม่ใช้พื้นที่จนกว่าจะมีอะไรเปลี่ยน และเรพลิกาไม่ถูกแตะ

```
zfs clone backup/bombvault-replica/tower/cache/appdata@bombvault-replica-20261006014100 backup/bombvault-replica/clone-appdata
```

ถ้าต้นทางล้ม ให้เปลี่ยนสำเนาเป็นชุดข้อมูลปกติที่เขียนได้บนปลายทาง

```
zfs inherit -r readonly backup/bombvault-replica/tower/cache/appdata && zfs inherit -r canmount backup/bombvault-replica/tower/cache/appdata && zfs mount -a
```

หลังจากนั้น BombVault หยุดทำเรพลิกาไปยังชุดข้อมูลนั้น จนกว่าคุณจะเริ่มการรันแรกใหม่

ถ้าจะนำสถานะกลับไปที่ต้นทาง กด **นำกลับมาเป็นชุดข้อมูลใหม่** ในแผ่น BombVault ส่งสแนปช็อตเข้าชุดข้อมูลใหม่ข้างต้นฉบับ ชื่อ `<dataset>-bombvault-restore-` บวกเวลา มันไม่เคยเขียนทับต้นฉบับ

### ตัวอย่าง: เรพลิกาไปยังกล่อง Unraid ตัวที่สอง {#example-replica}

เซิร์ฟเวอร์ `tower` สำรองชุดข้อมูล `cache/appdata` เป็นรายการ ZFS กล่อง Unraid ตัวที่สองที่ `192.168.1.20` ซึ่งไม่มี BombVault มีพูลชื่อ `backup` และควรเก็บสำเนาที่คุณอ่านได้ทุกเมื่อ

1. เปิด **การสำรองข้อมูล** แล้ว `cache/appdata` แล้วแท็บ **การตั้งค่า** ของมัน ในการ์ด **เรพลิกา** เลือก **เพิ่มเซิร์ฟเวอร์ ZFS** ใต้ **ทำเรพลิกาไปที่**
2. กรอก `192.168.1.20` ผู้ใช้ `root` และพอร์ต `22` กล่องแสดงคีย์เรพลิกา บนกล่องตัวที่สอง วางมันใต้ **Users, root, SSH keys** แล้วกด **Apply** คีย์นี้ต่างจากคีย์ SSH ของโฮสต์ ดังนั้นให้เพิ่มแม้อันนั้นจะอยู่ที่นั่นแล้ว
3. ทดสอบการเชื่อมต่อ เลือกพูล `backup` และคงรากที่มันเสนอ `backup/bombvault-replica`
4. กลับที่การ์ด เซิร์ฟเวอร์ใหม่ถูกเลือกใต้ **ทำเรพลิกาไปที่** คง **เมื่อไร** ไว้ที่ **หลังสำรองทุกครั้ง** คง **เก็บไว้ที่ปลายทาง** ที่สแนปช็อตรายวัน 7 และรายสัปดาห์ 3 และตั้ง **เก็บไว้บนเซิร์ฟเวอร์นี้** เป็น `7`
5. กด **ทำเรพลิกาตอนนี้** การรันครั้งแรกส่งทุกอย่าง 300 GB ผ่านสาย 1 Gbit/s จึงใช้เวลาอย่างน้อย 40 นาที การ์ดและลิสต์การสำรองข้อมูลบอก **กำลังจำลอง** แล้ว **ทำเรพลิกาแล้ว** พร้อมเวลา การรันครั้งต่อไปส่งเฉพาะบล็อกที่เปลี่ยน

ตอนนี้ชุดข้อมูลอยู่ที่ `backup/bombvault-replica/tower/cache/appdata` บนกล่องตัวที่สอง แบบอ่านอย่างเดียว บนภาพรวม **นอกสถานที่** ของส่วน ZFS นับเรพลิกาเป็นสำเนานอกสถานที่

ถ้าจะเอาไฟล์เดียวจากวันอังคารที่แล้ว มีสามทาง

- **บนเซิร์ฟเวอร์นี้** เพราะ **เก็บไว้บนเซิร์ฟเวอร์นี้** เก็บเจ็ดสแนปช็อต

    ```
    cp /mnt/cache/appdata/.zfs/snapshot/bombvault-replica-20261103014100/plex/Preferences.xml /mnt/user/restore/
    ```

- **บนกล่องตัวที่สอง** ด้วย clone ของสแนปช็อตบนปลายทาง แท็บ **การสำรองข้อมูล** ของรายการแสดงคำสั่งพร้อมชื่อจริงของคุณเมื่อคุณคลิกแถว **เรพลิกา ZFS** ลบ clone ด้วย `zfs destroy` เมื่อเสร็จ
- **ด้วย mount** โดยเปิด **เมานต์แบบอ่านอย่างเดียวบนเซิร์ฟเวอร์** บนหน้าของเซิร์ฟเวอร์ ZFS หลังการรันครั้งถัดไป สำเนาจะเมานต์แบบอ่านอย่างเดียวอยู่บนกล่องตัวที่สอง

เวอร์ชันที่เก่ากว่าที่เรพลิกาเก็บยังมาจากการสำรอง ดังตัวอย่างถัดไป

### ตัวอย่าง: ไฟล์เดียวจากข้อมูลสำรอง ZFS {#example-zfs-file}

1. เปิด **การกู้คืน** เลือกไทล์ **ZFS** แล้วคลิก `cache/appdata`
2. เลือกข้อมูลสำรอง และใต้ **ชุดข้อมูล** เลือกชุดข้อมูลที่มีไฟล์
3. ใต้ **อะไร** เลือก **ไฟล์แต่ละไฟล์** และติ๊กไฟล์
4. ใต้ **ไปที่ไหน** เลือก **ไปยังโฟลเดอร์** และเลือกโฟลเดอร์ใต้ `/mnt` เช่น `user/restore` ไม่ต้องมีลิงก์ SSH และใช้ได้กับชุดข้อมูลที่ไม่มีอยู่แล้วด้วย
5. กด **กู้คืน** ไฟล์ไปลงโดยตรงในโฟลเดอร์นั้น โดยไม่มีพาธข้างบน

## สแนปช็อตที่ตกค้าง {#leftover-snapshots}

สแนปช็อตของการสำรองชื่อ `<dataset>@bombvault-<14 digits>` เช่น `cache/appdata@bombvault-20260924021500` (UTC) BombVault ลบมันทันทีหลังการสำรอง ถ้าล้มเหลว เช่นเพราะชุดข้อมูลไม่ว่างหรือ BombVault ถูกหยุด BombVault จะลบมัน

- ก่อนการสำรองครั้งถัดไปของรายการนั้น
- เมื่อ BombVault เริ่ม สำหรับทุกรายการ แม้ปิดโดเมนอยู่
- เมื่อคุณลบรายการ
- เมื่อคุณกด **ลบตอนนี้** บนรายการ ซึ่งแสดงว่าเหลือกี่อัน

ชื่อที่ตรงกับ `bombvault-` บวก 14 หลักพอดีเท่านั้นที่ถูกลบ สแนปช็อตเพื่อความปลอดภัย สแนปช็อตของคุณเอง และสแนปช็อตอัตโนมัติไม่ถูกแตะเลย ถ้าจะลบอันหนึ่งด้วยมือ

```
zfs destroy -r cache/appdata@bombvault-20260924021500
```

สแนปช็อตของเรพลิกาชื่อ `<dataset>@bombvault-replica-<14 digits>` และไม่ใช่ของตกค้าง มันอยู่บนต้นทางจนกว่าการรันเรพลิกาที่ใหม่กว่าจะแทนที่ หรือตราบเท่าที่ **เก็บไว้บนเซิร์ฟเวอร์นี้** เก็บมัน และบนปลายทางตราบเท่าที่การเก็บรักษาเก็บมัน ตัวกวาดไม่แตะมันเลย เพราะมันจับคู่เฉพาะ `bombvault-` ตามด้วย 14 หลักพอดี

## ความผิดปกติ {#anomalies}

ลูกที่ถูกทำให้ว่างแทบไม่เปลี่ยนยอดรวมของต้นไม้ขนาดใหญ่ การตรวจจับความผิดปกติจึงเฝ้าทุกชุดข้อมูลของรายการแยกกัน: ขนาด จำนวนไฟล์ ข้อมูลใหม่ และเวลาของ restic แต่ละอย่างมีประวัติของตัวเอง ประวัตินั้นเป็นของชื่อชุดข้อมูล จึงอยู่ต่อเมื่อต้นไม้ถูกสำรองโดยรายการอื่นภายหลัง

ชุดข้อมูลที่การรันก่อนหน้าสำรองได้และการรันนี้อ่านไม่ได้นับว่าถูกทำให้ว่าง ตราบที่การเลือกของรายการไม่เปลี่ยน ครอบคลุมคีย์ที่ไม่ได้โหลด ชุดข้อมูลที่ไม่ได้เมานต์ และชุดที่หายไปจากต้นไม้ ลูกที่คุณยกเว้นเองเปลี่ยนการเลือก ประวัติของมันจึงเริ่มใหม่แทน ขณะที่สิ่งที่พบเกี่ยวกับข้อมูลที่หายไปยังเปิดอยู่ การเก็บรักษาเก็บข้อมูลสำรองเก่าของชุดข้อมูลนั้นชุดเดียว และ prune ส่วนที่เหลือของต้นไม้ตามปกติ

ทุกชุดข้อมูลมีบรรทัดของตัวเองในการเฝ้าระวังของรายการ ซึ่งเปิดด้วย **การเฝ้าระวัง** บนหน้า **ความผิดปกติ** และอยู่บนแท็บ **ยืนยัน** ของรายการ สิ่งที่พบที่เปิดอยู่แสดงข้างแต่ละชุดข้อมูล ลิงก์ในสิ่งที่พบเปิดหน้าต่างกู้คืนบนข้อมูลสำรองล่าสุดที่ยังดีของชุดข้อมูล การรันจบหรือไม่ตัดสินสำหรับทั้งรายการ เพราะการรันสำเร็จหรือล้มเหลวทั้งก้อน

การตรวจเองอธิบายไว้ใต้ [ความผิดปกติ](anomalies.md) ผู้ช่วยที่เชื่อมต่อผ่าน [เซิร์ฟเวอร์ MCP](mcp.md) ลิสต์จุดกู้คืนของรายการ ZFS เริ่มการสำรองของมัน และอ่านสิ่งที่พบได้ แต่การยืนยันสิ่งหนึ่งทำที่หน้า **ความผิดปกติ**

## รหัสเหตุผล {#reason-codes}

หน้าของรายการ ประวัติการรัน และการแจ้งเตือนระบุปัญหาด้วยรหัสเหล่านี้อันใดอันหนึ่ง ส่วนใหญ่มีวิธีแก้อยู่ข้างบนหน้าด้วย

| รหัส | ความหมาย | ต้องทำอะไร |
|---|---|---|
| `ssh-missing` | ยังไม่ได้ตั้งค่าการเชื่อมต่อ SSH ในคอนเทนเนอร์นี้ | ตั้งลิงก์ SSH เหมือนการสำรอง VM |
| `host-placeholder` | Host SSH: Address ยังเป็นตัวยึด และ `host.docker.internal` ก็ไม่ตอบ | ตั้ง Host SSH: Address เป็น IP LAN ของเซิร์ฟเวอร์นี้ |
| `host-fallback` | Host SSH: Address ยังเป็นตัวยึด และ `host.docker.internal` ใช้ได้ | ไม่ต้องทำอะไร หรือตั้ง IP LAN |
| `ssh-unreachable` | เข้าถึงเซิร์ฟเวอร์ผ่าน SSH ไม่ได้ | ตรวจที่อยู่และพอร์ต และว่าเปิด SSH อยู่ |
| `ssh-auth` | เซิร์ฟเวอร์ปฏิเสธคีย์ของ BombVault | รันคำสั่งที่แสดงใต้ **การเชื่อมต่อกับเซิร์ฟเวอร์นี้** หนึ่งครั้งบนเซิร์ฟเวอร์ |
| `zfs-not-found` | โฮสต์ SSH ไม่มีคำสั่ง `zfs` | ชี้ Host SSH: Address ไปที่เครื่องที่เป็นเจ้าของพูล |
| `zfs-permission` | ผู้ใช้ SSH รันคำสั่ง zfs นี้ไม่ได้ | ใช้ root หรือดู [TrueNAS SCALE](#truenas) |
| `uri-mismatch` | `LIBVIRT_URI` ระบุโฮสต์หรือผู้ใช้ต่างจากฟิลด์ SSH | ทำให้ตรงกัน หรือล้างฟิลด์ SSH เพื่อให้ทั้งสองมาจาก URI |

| `propagation-missing` | mount ใหม่บนโฮสต์ไปไม่ถึงคอนเทนเนอร์ | ตั้ง Access Mode ของ Host Data เป็น Read/Write - Slave แล้วรีสตาร์ท BombVault |
| `invalid-name` | ชื่อชุดข้อมูลที่ BombVault ไม่ยอมรับ | เปลี่ยนชื่อชุดข้อมูล |
| `name-too-long` | ชุดข้อมูลในต้นไม้ยาวเกินไปสำหรับชื่อสแนปช็อต | เปลี่ยนชื่อ หรือเพิ่มชุดข้อมูลข้างใต้เป็นรายการ |
| `invalid-exclude` | รูปแบบการยกเว้นหรือลูกที่เว้นไว้ไม่เข้ากับรายการ | แก้รายการที่ข้อความระบุ ถ้าจะเว้นทั้งชุดข้อมูลลูก ให้ปิดมันแทนการเขียนรูปแบบ |
| `not-found` | ไม่มีชุดข้อมูลนั้นบนเซิร์ฟเวอร์ | ลบรายการ หรือสร้างชุดข้อมูลใหม่ ข้อมูลสำรองของมันยังกู้คืนได้ |
| `not-filesystem` | นี่คือ volume ไม่ใช่ระบบไฟล์ | ดู [Volume](#volumes) |
| `overlaps-item` | ชุดข้อมูลซ้อนทับรายการที่มีอยู่ | ดู [รายการไม่ซ้อนทับกัน](#overlap) |
| `docker-storage` | ต้นไม้มีที่เก็บ image ของ Docker | ดู [ที่เก็บข้อมูลของ Docker](#docker-storage) |
| `nothing-readable` | ไม่มีชุดข้อมูลในรายการที่อ่านได้ตอนนี้ | ดูรหัสของชุดข้อมูลที่ข้าม |

| `containers-busy` | การสำรองคอนเทนเนอร์ยังรันอยู่ตอนที่ต้องหยุดคอนเทนเนอร์ | เริ่มใหม่ทีหลัง การรันตามกำหนดรอเอง |

### ตรวจสิ่งที่คอนเทนเนอร์เห็น {#mountinfo}

**ทดสอบการเข้าถึงสแนปช็อต** บนแท็บการตั้งค่าของรายการทำสแนปช็อตจริงของต้นไม้ ค้นหามันภายใน BombVault สำหรับทุกชุดข้อมูล และลบมันอีกครั้ง เป็นวิธีที่เร็วที่สุดในการพิสูจน์เส้นทางทั้งหมดก่อนการรันตามกำหนดครั้งแรก

ถ้าจะดูเอง ให้รันบนเซิร์ฟเวอร์

```
docker exec BombVault grep zfs /proc/self/mountinfo
```

แต่ละบรรทัดคือหนึ่ง mount ภายในคอนเทนเนอร์ บรรทัดของชุดข้อมูลแสดงพาธของมันภายในคอนเทนเนอร์ (ใต้ `/host/user`) และชื่อชุดข้อมูล ฟิลด์ `master:N` บนบรรทัดนั้นหมายความว่า mount รับ mount ที่โฮสต์ทำภายหลัง ซึ่งการเข้าถึงสแนปช็อตต้องการ เมื่อไม่มี ให้ตั้ง Access Mode ของ Host Data เป็น Read/Write - Slave แล้วรีสตาร์ท BombVault

## TrueNAS SCALE {#truenas}

- เมื่อตั้ง `LIBVIRT_URI` (เหมือนการสำรอง VM บน TrueNAS) BombVault เอาโฮสต์ SSH ผู้ใช้ และพอร์ตสำหรับคำสั่ง zfs ของมันจาก URI สำหรับแต่ละตัวที่ไม่ได้ตั้งเอง ถ้าไม่มีการสำรอง VM ก็ไม่ต้องตั้งอะไร: `host.docker.internal` ไม่ resolve ในแอป TrueNAS BombVault จึงเข้าถึงโฮสต์ผ่านเกตเวย์เริ่มต้นของแอป ในฐานะ root ที่พอร์ต 22 ตั้ง `LIBVIRT_HOST`, `LIBVIRT_SSH_USER` และ `LIBVIRT_SSH_PORT` เมื่อต้องการที่อยู่หรือผู้ใช้อื่น ใน `environment` ของแอป
- เพิ่มคีย์ SSH ของโฮสต์จาก **การตั้งค่า, การเชื่อมต่อ, SSH ของโฮสต์** ให้ root ที่ **Credentials, Users** และเปิดบริการ SSH ที่ **System, Services** [เรพลิกา](#replica-push) ไปยัง TrueNAS นี้หรือเครื่องอื่นต้องมีคีย์เรพลิกาด้วย ซึ่งเป็นคนละอัน
- ผู้ใช้อื่นที่ไม่ใช่ root ต้องมีสิทธิ์บนชุดข้อมูลบนสุดของรายการ ซึ่งครอบคลุมทุกชุดข้อมูลข้างใต้

  ```
  zfs allow <user> snapshot,destroy,mount <dataset>
  ```

  การกู้คืนเข้าชุดข้อมูลใหม่ต้องมี `create` บนชุดข้อมูลเหนือมันด้วย และการตั้งคุณสมบัติที่เก็บไว้ต้องมีสิทธิ์สำหรับคุณสมบัติเหล่านั้น

  เซสชัน SSH ที่ไม่ใช่ root บน TrueNAS ไม่มี `/usr/sbin` ใน path BombVault จึงเรียก `/usr/sbin/zfs` โดยตรง
- **Host Data** ของแอปต้องเป็นพาธโฮสต์เหนือชุดข้อมูล เช่น `/mnt/tank` ไม่ใช่ ixVolume ด้วยพาธโฮสต์ แอปส่งต่อ mount ใหม่ของโฮสต์ไปยัง BombVault (`rslave`) ซึ่งการเข้าถึงสแนปช็อตต้องการ ดู [TrueNAS SCALE](getting-started.md#truenas) สำหรับการตั้งค่าแอปทั้งหมด
