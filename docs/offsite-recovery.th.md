# นอกสถานที่และการกู้คืน

การสำรองข้อมูลในเครื่องปกป้องคุณจาก container ที่สูญหายหรือการอัปเดตที่ผิดพลาด การจำลองข้อมูลนอกสถานที่และชุดกู้คืนที่ผ่านการทดสอบปกป้องคุณจากทั้งเครื่อง, แรนซัมแวร์ หรือไฟไหม้ หน้านี้ครอบคลุมการจำลองข้อมูลนอกสถานที่, การทำให้สำเนานั้นป้องกันการแทรกแซง, การพิสูจน์ว่าคุณกู้คืนได้ และการกู้คืนเมื่อ BombVault เองหายไป

## การจำลองข้อมูลนอกสถานที่

เก็บการสำรองข้อมูลในเครื่องที่เร็วไว้และคัดลอกไปยังตำแหน่งจัดเก็บอื่นอีกหนึ่งแห่งหรือมากกว่า คุณเลือกตำแหน่งจัดเก็บที่โดเมนจะถูกคัดลอกไปได้บนการ์ด **โดเมน** ใต้ **การตั้งค่า, ที่จัดเก็บ** โดยมีชิปหนึ่งอันต่อตำแหน่งจัดเก็บหนึ่งแห่ง (ดู [ตำแหน่งจัดเก็บ](storage-places.md#domains)) BombVault คัดลอกสแนปช็อตใหม่ไปที่นั่นด้วย `restic copy` แบบทำเท่าที่ทำได้ ดังนั้นการคัดลอกที่ล้มเหลวจึงไม่เคยทำให้การสำรองข้อมูลในเครื่องล้มเหลว ตำแหน่งจัดเก็บที่โดเมนจัดเก็บอยู่ไม่จำเป็นต้องอยู่ในเครื่อง ดู [โดเมนที่จัดเก็บในตำแหน่งจัดเก็บระยะไกล](#remote-primary-repositories)

- **หลายตำแหน่งจัดเก็บสำหรับคัดลอกต่อโดเมน** โดเมนหนึ่งคัดลอกไปยังหลายตำแหน่งจัดเก็บพร้อมกันได้ เช่น rest-server ที่บ้านเพื่อนและ bucket ของ B2 การเก็บรักษา คลาสพื้นที่จัดเก็บ append-only ขีดจำกัด และงบประมาณการเติบโตเป็นของตำแหน่งจัดเก็บ สำเนาแต่ละชุดจึงเป็นไปตามกฎของตำแหน่งจัดเก็บที่มันไปอยู่
- **ตารางเวลาการคัดลอกต่อโดเมน** (แก้ไขควบคู่กับตารางเวลาอื่น ๆ ทั้งหมดบน การตั้งค่า, กำหนดการ): ปล่อยว่างไว้เพื่อคัดลอกหลังการสำรองข้อมูลในเครื่องทุกครั้ง หรือตั้งจังหวะ (เช่น `weekly Sun 03:00`) เพื่อคัดลอกไม่บ่อยเท่าที่คุณสำรองข้อมูล **คัดลอกตอนนี้** ในแถวของโดเมนจะรันการคัดลอกตามต้องการ
- **การเก็บรักษาต่อตำแหน่งจัดเก็บ** ตำแหน่งจัดเก็บแต่ละแห่งมีกฎของตัวเอง ตำแหน่งจัดเก็บนอกสถานที่จึงเก็บสำเนาไว้นานขึ้นเป็นคลังเก็บได้ ตำแหน่งจัดเก็บที่ตั้งทุกกฎเป็นศูนย์จะไม่ตัดทิ้งเลย
- **ขีดจำกัดแบนด์วิดท์** ต่อตำแหน่งจัดเก็บ จำกัดอัตราการอัปโหลดและดาวน์โหลดของ restic เพื่อไม่ให้การคัดลอกใช้ WAN ของคุณจนเต็ม
- **ตัวบ่งชี้การจำลองข้อมูล** แสดงว่าโดเมนใดกำลังคัดลอกขณะที่ทำงาน (บนหน้าของมันและบนแดชบอร์ด) เป็นตัวบ่งชี้แบบทำงานอยู่ ไม่ใช่แถบเปอร์เซ็นต์ เพราะ `restic copy` ไม่เปิดเผยความคืบหน้าที่เครื่องอ่านได้

!!! note "กู้คืนจากที่ใดก็ได้"
    ทุก container, VM, ชุดไฟล์, แฟลช และการตั้งค่าแอป จะแสดงรายการสำรองข้อมูลของตัวเองเป็นไทม์ไลน์เดียวครอบคลุมทุกที่ที่การสำรองข้อมูลนั้นตั้งอยู่ การสำรองข้อมูลที่คัดลอกไปยัง B2 จะปรากฏเพียงครั้งเดียว โดยมีเครื่องหมายกำกับทุกที่ที่เก็บมันไว้ การกู้คืนจะเลือกที่แรกที่เข้าถึงได้ โดยเริ่มจากรีพอสิทอรีที่รายการนั้นถูกเขียนไว้ และคุณสามารถเลือกที่อื่นได้ทีละแถว ที่นอกสถานที่จะถูกอ่านก็ต่อเมื่อคุณเปิดดูเท่านั้น การลบที่จุดหนึ่งจะตรวจสอบจุดอื่นก่อนและบอกว่านั่นเป็นสำเนาสุดท้ายหรือไม่

## การจัดวางต่อรายการ {#placement}

การ์ดของแต่ละ container, VM และชุดไฟล์มีแถว **การจัดวาง** พร้อมสามส่วน:

- **ในเครื่อง** เขียนรายการไปยังรีพอสิทอรีที่แสดงอยู่ใต้ **จัดเก็บที่** และไม่คัดลอกไปที่ใดเลย ใช้สำหรับข้อมูลที่มีสำเนาที่สองอยู่แล้ว เช่น แชร์ที่อยู่บน NAS
- **ในเครื่อง + นอกสถานที่** เขียนไปที่นั่นด้วยเช่นกัน และคัดลอกไปยังปลายทางที่ทำเครื่องหมายไว้ใต้ **คัดลอกไปยัง** หนึ่งชิปต่อปลายทางนอกสถานที่หนึ่งแห่งของโดเมน ยกเลิกการทำเครื่องหมายชิปหนึ่งอัน แล้วปลายทางนั้นจะไม่ได้รับสิ่งใหม่จากรายการนี้อีก
- **นอกสถานที่เท่านั้น** เขียนรายการตรงไปยังตำแหน่งจัดเก็บที่อยู่ใต้ **ส่งไปยัง** ซึ่งเป็นตำแหน่งจัดเก็บใดก็ได้ที่ไม่ใช่ที่จัดเก็บหลักของโดเมน หากโดเมนถูกคัดลอกไปยังตำแหน่งจัดเก็บนั้นอยู่แล้ว รายการจะได้รีพอสิทอรีโดยตรงข้างสำเนาเหล่านั้น มิฉะนั้น BombVault จะสร้างรีพอสิทอรีสำหรับโดเมนที่นั่น

ตำแหน่งจะคงที่ตั้งแต่การสำรองข้อมูลครั้งแรกของรายการ เพราะ BombVault ไม่เคยย้ายการสำรองข้อมูลระหว่างรีพอสิทอรี ส่วนสำเนาสามารถเปลี่ยนแปลงได้ตลอดเวลา ปลายทางที่ไม่ได้รับรายการอีกต่อไปจะเก็บสำเนาที่มีอยู่ไว้และตัดแต่งให้เหลือตามการเก็บรักษาของตัวเองในการทำงานนอกสถานที่ครั้งถัดไปของโดเมน ส่วน **ลบที่ B2** บนการ์ดจะลบสำเนาเหล่านั้นทันที เมื่อสำเนาบางส่วนไม่มีอยู่ที่อื่นเลย การยืนยันจะแสดงรายการตามวันที่และขอให้พิมพ์ชื่อของรายการ ปลายทางแบบ append-only ไม่สามารถลบสิ่งใดออกได้

ใต้แถวนี้ การ์ดจะบอกว่ารายการนี้ไปที่ใดและมีอะไรอยู่จริง: มีกี่ไซต์ที่ถือครองมัน แต่ละปลายทางถูกพบล่าสุดเมื่อใด และเป็นไปตามกฎ 3-2-1 หรือไม่ ไซต์คือเซิร์ฟเวอร์ที่มีข้อมูลต้นฉบับ และตำแหน่งจัดเก็บแต่ละแห่งที่อยู่ที่สถานที่อื่น (ดู [นอกสถานที่](#off-the-premises-mark)) BombVault ตรวจสอบสำเนาและไซต์ แต่ไม่ตรวจสอบส่วน "สื่อสองชนิด" ของกฎ 3-2-1

### ค่าเริ่มต้นต่อโดเมน

การ์ด **โดเมน** ใต้ การตั้งค่า, ที่จัดเก็บ มีหนึ่งแถวต่อโดเมน **คัดลอกไปยัง** มีผลทันทีกับทุกรายการที่ไม่มีตัวเลือกของตัวเอง และกับโฟลเดอร์โปรเจกต์ของสแต็ก Compose ด้วย เมื่อโดเมนมีข้อมูลสำรองแล้ว **จัดเก็บที่** จะมีผลกับรายการใหม่ตอนสำรองข้อมูลครั้งแรก และการเปลี่ยนค่านี้ไม่ย้ายการสำรองข้อมูลใด ๆ ก่อนบันทึก แถวจะระบุชื่อทุกตำแหน่งจัดเก็บที่ได้หรือเสียรายการไปและจำนวนสแนปช็อตที่หมายถึง และคำถามยืนยันจะมีสวิตช์ **ใช้กับรายการที่ไม่มีการสำรองข้อมูล** ซึ่งจะนำทุกรายการที่ยังไม่มีข้อมูลสำรองไปใช้ค่าเริ่มต้นใหม่ด้วย **ข้อยกเว้น** จะแสดงรายการที่มีตัวเลือกของตัวเอง

การทำเครื่องหมายตำแหน่งจัดเก็บใหม่ใต้ **คัดลอกไปยัง** จะทำให้ตำแหน่งจัดเก็บนั้นได้รับทุกรายการที่ไม่ได้ตั้งเป็นในเครื่อง การยืนยันจะบอกว่ามีกี่รายการ และหากทราบ มีประวัติมากเพียงใด

### รีพอสิทอรีโดยตรง

การเลือกตำแหน่งจัดเก็บใต้ นอกสถานที่เท่านั้น ในกรณีที่โดเมนถูกคัดลอกไปที่นั่นอยู่แล้ว จะถามหนึ่งครั้ง แล้วสร้างรีพอสิทอรีโดยตรงข้างสำเนาเหล่านั้น เช่น `s3:https://s3.eu-central-003.backblazeb2.com/bucket/container-direct` และชี้รายการไปที่นั่น สำหรับปลายทางการคัดลอกที่ไม่มีตำแหน่งจัดเก็บ ตัวเลือกนี้จะเปิดกล่องโต้ตอบพร้อมที่อยู่ที่แนะนำและการทดสอบการเชื่อมต่อที่ไม่สร้างสิ่งใดขึ้นมา และ **สร้างและใช้งาน** จะสร้างรีพอสิทอรี รีพอสิทอรีโดยตรงจะใช้คีย์ คลาสพื้นที่จัดเก็บ ขีดจำกัด การตั้งค่า append-only และการเก็บรักษาของตำแหน่งจัดเก็บ และเปลี่ยนไปพร้อมกับตำแหน่งจัดเก็บนั้น เมื่อคีย์ใหม่ของตำแหน่งจัดเก็บเปิดมันไม่ได้ รีพอสิทอรีโดยตรงจะเก็บคีย์เดิมไว้และการบันทึกจะแจ้งเช่นนั้น สแนปช็อตของมันมีแท็ก `bv:direct` และทุกรอบการตัดแต่งอื่นจะเก็บพวกมันไว้ ดังนั้นรีพอสิทอรีโดยตรงที่ขาดการเชื่อมโยงกับตำแหน่งจัดเก็บของมันจะไม่มีวันเก่าลงตามกฎในเครื่อง คีย์ B2 ที่จำกัดไว้ที่โฟลเดอร์เดียวต้องครอบคลุมที่อยู่ของตำแหน่งจัดเก็บ ไม่ใช่แค่โฟลเดอร์ของโดเมน มิฉะนั้นจะเข้าไม่ถึงโฟลเดอร์ที่อยู่ข้างกัน

### นอกสถานที่ {#off-the-premises-mark}

สำเนาจะนับเป็นไซต์แยกของตัวเองก็ต่อเมื่อตำแหน่งจัดเก็บของสำเนานั้นอยู่ที่สถานที่อื่น ตำแหน่งจัดเก็บบนคลาวด์นับเสมอ และโฟลเดอร์บน Unraid นี้ไม่นับเลย สำหรับ NAS, rest-server หรือเซิร์ฟเวอร์ SFTP ให้ตอบ **อุปกรณ์อยู่ที่ไหน?** ในรายละเอียดของตำแหน่งจัดเก็บด้วย **ที่นี่ในบ้าน** หรือ **ที่สถานที่อื่น** คำตอบนี้นับเฉพาะไซต์และกฎ 3-2-1 บนการ์ดและแดชบอร์ดเท่านั้น ไม่เปลี่ยนแปลงสำเนาใด ๆ

### หลังการสร้างใหม่

ตัวเลือกสำเนาอยู่ในการตั้งค่าของ BombVault เอง หลังการสร้างใหม่ผ่าน Discover โดยไม่มี `/config` ที่กู้คืนมา ตัวเลือกเหล่านั้นจะหายไป และการคัดลอกทุกอย่างจะส่งรายการที่คุณเคยละไว้กลับไปที่ B2 อีกครั้ง การจำลองข้อมูลนอกสถานที่ของทุกโดเมนที่สร้างใหม่จึงหยุดชั่วคราว แดชบอร์ดจะแสดงเป็นสีเหลืองอำพัน และแถวของโดเมนบนการ์ดโดเมนจะเสนอ **ยืนยันค่าเริ่มต้น** พร้อมตัวอย่างของสิ่งที่การทำงานครั้งถัดไปจะคัดลอก และชื่อในสำเนาสำรองที่ไม่มีรายการที่ตรงกัน ซึ่งคุณสามารถละไว้ที่นั่นได้ มีแต่การยืนยันเท่านั้นที่จะยุติการหยุดชั่วคราว การนำเข้าไฟล์การตั้งค่าจะนำกฎและค่าเริ่มต้นกลับมาแต่ไม่ยุติการหยุดชั่วคราว

## โดเมนที่จัดเก็บในตำแหน่งจัดเก็บระยะไกล {#remote-primary-repositories}

โดเมนไม่จำเป็นต้องจัดเก็บในเครื่อง ขณะที่ตำแหน่งสำรองข้อมูลของโดเมนยังไม่มีข้อมูลสำรอง ให้เลือกตำแหน่งจัดเก็บระยะไกลใต้ **จัดเก็บที่** บนการ์ดโดเมน แล้วโดเมนจะสำรองข้อมูลตรงไปที่นั่น โดยไม่มีสำเนาในเครื่องและไม่มีขั้นตอนการคัดลอก จากนั้นรีพอสิทอรีระยะไกลจะเป็นสำเนาเดียว เว้นแต่โดเมนจะถูกคัดลอกไปยังตำแหน่งจัดเก็บอื่นด้วย ตำแหน่งจัดเก็บระยะไกลทุกแห่งมีมาตรการป้องกันชุดเดียวกัน:

- **การทดสอบการเชื่อมต่อ** ก่อนที่จะมีการเขียนสิ่งใด
- **ขีดจำกัดแบนด์วิดท์** สำหรับการสำรองข้อมูลเอง เป็นแฟล็ก `--limit-upload` และ `--limit-download` ชุดเดียวกับที่การคัดลอกใช้
- **การป้องกันแบบ append-only** ตรวจสอบด้วยการทดสอบการแทรกแซงเชิงรุกแบบเดียวกัน เมื่อเปิดไว้ BombVault จะไม่ตัดทิ้งรีพอสิทอรีนั้นเลย เพราะข้อมูลรับรองบนเครื่องนี้ต้องไม่สามารถลบสำเนาเดียวของข้อมูลสำรองได้
- **งบประมาณการเติบโต** ที่ดึงมาจากแนวโน้มขนาดชุดเดียวกับที่การ์ดที่จัดเก็บติดตามอยู่

โดเมนที่จัดเก็บในตำแหน่งจัดเก็บระยะไกลเป็นต้นทางของสำเนาของตัวเองเหมือนกับโดเมนในเครื่อง ดู [สำเนาระหว่างตำแหน่งจัดเก็บที่ใช้ข้อมูลรับรองต่างกัน](storage-places.md#different-credentials)

!!! note "ข้อมูลรับรองเป็นของตำแหน่งจัดเก็บ"
    ตำแหน่งจัดเก็บระยะไกลเก็บข้อมูลรับรองของตัวเอง ตำแหน่งจัดเก็บที่ตั้งค่าไว้ด้วยข้อมูลรับรองคลาวด์ที่ใช้ร่วมกันจะใช้ข้อมูลรับรองนั้นต่อไป จนกว่าจะเปลี่ยนการเข้าถึงในรายละเอียดของตำแหน่งจัดเก็บนั้น

### SMB และ WebDAV โดยไม่ต้องเมานต์บนโฮสต์ {#smb-webdav}

แบบฟอร์ม rclone ในหน้าต่าง **เพิ่มตำแหน่งจัดเก็บ** มีแบบฟอร์มสำหรับแชร์ของ Windows หรือ Samba และสำหรับเซิร์ฟเวอร์ WebDAV (Nextcloud, ownCloud, SharePoint หรือเซิร์ฟเวอร์อื่นใด) กรอกชื่อสั้น ๆ โฮสต์และแชร์ (SMB) หรือ URL และประเภทเซิร์ฟเวอร์ (WebDAV) ผู้ใช้ และรหัสผ่าน แล้ว BombVault จะเขียนส่วน rclone ให้คุณ rclone จะปกปิดรหัสผ่านเองก่อนจัดเก็บ การเพิ่มปลายทางที่ใช้ชื่อซึ่งมีอยู่แล้วจะแทนที่ส่วนนั้นแทนที่จะเพิ่มส่วนที่สอง

จากนั้นรีโมตใหม่จะแสดงในรายการรีโมตของแบบฟอร์ม ซึ่งคุณเลือกรีโมตนั้นให้กับตำแหน่งจัดเก็บได้ แชร์คือส่วนแรกของพาธ ไม่ใช่ส่วนหนึ่งของชื่อ

วิธีนี้ดีกว่าการเมานต์แชร์บน Unraid: restic ไม่แนะนำให้เก็บรีพอสิทอรีไว้บนแชร์ CIFS ที่เมานต์อยู่ และที่นี่ไม่มีการเมานต์ใด ๆ NFS ไม่อยู่ในแบบฟอร์มเพราะทั้ง restic และ rclone ไม่มีแบ็กเอนด์ NFS สำหรับ NFS ให้เมานต์ export บนโฮสต์แล้วเพิ่มเป็นตำแหน่งจัดเก็บด้วย **แชร์อื่น**

## นอกสถานที่แบบไม่เปลี่ยนแปลงได้ (append-only)

ตั้งแฟล็กรีพอสิทอรีนอกสถานที่เป็น append-only เพื่อให้แรนซัมแวร์หรือโฮสต์ที่ถูกบุกรุกไม่สามารถลบหรือเขียนทับการสำรองข้อมูลของคุณได้ ฝั่งไกล (`restic/rest-server` ที่ทำงานในโหมด `--append-only`) เป็นผู้ **บังคับใช้** BombVault เพียง **ตรวจสอบ** มันเท่านั้นและไม่เคยแสดงสีเขียวจากการอ้างการตั้งค่าเพียงอย่างเดียว

หน้าต่าง **เพิ่มตำแหน่งจัดเก็บ** มีชุดคำสั่งพร้อมวางสำหรับ rest-server ในโหมด append-only ที่มีผู้ใช้หนึ่งคนสำหรับ BombVault นี้ ที่ตำแหน่งจัดเก็บ rest-server ที่เปิด **append-only** ไว้ **ทดสอบ append-only** ในรายละเอียดของตำแหน่งจัดเก็บจะรันการทดสอบการแทรกแซงกับทุกพาธของโดเมน สำเนาที่เปิดอยู่ และรีพอสิทอรีที่ตำแหน่งจัดเก็บนั้น แล้วให้คำตอบเดียวสำหรับตำแหน่งจัดเก็บ ดังนั้นนอกสถานที่แบบ append-only จึงเข้าถึงได้โดยไม่ต้องแก้ไขไฟล์กำหนดค่าด้วยมือ

!!! note "การลบสำเร็จภายใต้ `/locks/` เป็นพฤติกรรมที่คาดไว้"
    append-only ไม่ได้แปลว่าไม่สามารถลบอะไรได้อีกเลย restic ต้องสร้างและปลดล็อกของตัวเอง ดังนั้น `/locks/` จึงยังคงเขียนและลบได้โดยเจตนา สแนปช็อตและข้อมูลที่อยู่เบื้องหลัง ซึ่งเป็นสิ่งที่แรนซัมแวร์มุ่งเป้า ไม่สามารถถูกลบได้ หากคุณทดสอบฝั่งปลายทางด้วยตนเอง การลบที่สำเร็จภายใต้ `/locks/` คือพฤติกรรมที่ถูกต้อง ไม่ใช่ช่องโหว่ของการป้องกัน

!!! warning "รีพอสิทอรีแบบไม่เปลี่ยนแปลงได้จะไม่เคยถูกตัดทิ้งจากเครื่องนี้"
    นอกสถานที่แบบไม่เปลี่ยนแปลงได้จะไม่เคยตัดสแนปช็อตเก่าโดยเจตนา ตั้ง **สัญญาณเตือนงบประมาณการเติบโต** ให้มันเพื่อให้คุณได้รับการแจ้งเตือนก่อนที่ขนาดรีพอสิทอรีจะโตเกินควบคุม

## การทดสอบการแทรกแซง

BombVault พิสูจน์การรับประกัน append-only เป็นระยะโดยการพยายามลบจริงกับรีพอสิทอรีนอกสถานที่ โดยเล็งไปที่อ็อบเจกต์ที่ไม่มีอยู่จริง:

- **ถูกปฏิเสธ** หมายถึงได้รับการปกป้อง
- **ยอมรับ** หมายถึงไม่ได้รับการปกป้อง
- ผลลัพธ์ **ที่ไม่สรุปแน่ชัด** (เซิร์ฟเวอร์เข้าถึงไม่ได้, ข้อผิดพลาดการยืนยันตัวตน) จะไม่เคยพลิกคำตัดสินที่จัดเก็บไว้

การพลิกจากได้รับการปกป้องเป็นไม่ได้รับการปกป้องจริงจะจุดสัญญาณเตือนครั้งเดียว

ที่ตำแหน่งจัดเก็บหนึ่ง **ทดสอบ append-only** จะตรวจทุกพาธของโดเมน สำเนาที่เปิดอยู่ และรีพอสิทอรีที่นั่นด้วยข้อมูลรับรองของแต่ละรายการ แล้วรวมผลเป็นคำตอบเดียว: หากมีรีพอสิทอรีเพียงแห่งเดียวที่ยอมรับการลบ ทั้งตำแหน่งจัดเก็บจะเป็น *ยอมรับการลบ*

## การซ้อม DR

BombVault มีการพิสูจน์สองระดับว่าการสำรองข้อมูลของคุณกู้คืนได้จริง ไม่ใช่แค่มีอยู่

- **การซ้อมตรวจสอบการกู้คืน (ในเครื่อง)** BombVault รัน `restic check --read-data-subset` เป็นระยะ (แบบมีขอบเขต, ไม่เคยเป็นการกู้คืนเต็มที่ทำให้ดิสก์เต็ม) และแสดงป้าย *last verified restorable* ต่อโดเมน จังหวะอยู่บน Settings, Schedules; ป้ายอยู่บน Settings, Integrity
- **การซ้อม DR (นอกสถานที่)** BombVault กู้คืนเป้าหมายจริงจากรีพอสิทอรีนอกสถานที่ลงในแซนด์บ็อกซ์ที่ใช้แล้วทิ้ง, ตรวจสอบทีละไฟล์และทีละไบต์ แล้วทำความสะอาด สิ่งนี้พิสูจน์ว่าคุณกู้คืนจากนอกสถานที่ได้ ไม่ใช่แค่ว่ารีพอสิทอรีตอบสนอง จะซ้อมเฉพาะตำแหน่งจัดเก็บที่สถานที่อื่นเท่านั้น เพราะสำเนาในบ้านหลังเดียวกันไม่ได้พิสูจน์อะไรเลยเมื่อบ้านทั้งหลังสูญหาย โดเมนที่คัดลอกไปยังหลายตำแหน่งดังกล่าวจะถูกซ้อมกับตำแหน่งหนึ่งต่อการรันตามกำหนดหนึ่งครั้งโดยวนตามลำดับ และแดชบอร์ดจะแสดงชื่อตำแหน่งจัดเก็บของการซ้อมครั้งล่าสุด

**สกอร์การ์ดการป้องกันแรนซัมแวร์** บนแดชบอร์ดจะรวมสิ่งนี้เป็นท่าที เขียว / เหลือง / แดง ต่อโดเมน พร้อมรายการตรวจสอบที่ประทับอายุ (ตั้งค่านอกสถานที่แล้ว, ตรวจสอบ append-only แล้ว, การจำลองข้อมูลเป็นปัจจุบัน, การซ้อมกู้คืนผ่าน, เปิดการเข้ารหัส, ตั้งกลยุทธ์การตัดทิ้ง) ทุกแถวสีแดงจะลิงก์ลึกไปยังวิธีแก้ไข และการ์ดจะเป็นสีเขียวเฉพาะเมื่อมีข้อเท็จจริงที่ตรวจสอบแล้ว

## แดชบอร์ดผู้รับ (ฝั่งรับ)

![ฝั่งผู้รับ ถูกเฝ้าดูแบบอ่านอย่างเดียว พร้อมการตรวจความสมบูรณ์ที่รันบนเครื่องนี้](assets/screenshots/receiver.png)

*ฝั่งผู้รับ ถูกเฝ้าดูแบบอ่านอย่างเดียว พร้อมการตรวจความสมบูรณ์ที่รันบนเครื่องนี้*

ทุกอย่างข้างต้นเป็นฝั่ง *ส่ง* บนเครื่องที่ **รับ** สำเนานอกสถานที่แบบไม่เปลี่ยนแปลงได้จาก BombVault อีกตัว แดชบอร์ดผู้รับให้คุณมีการเฝ้าติดตามแบบอิสระและอ่านอย่างเดียวของรีพอสิทอรีเหล่านั้นบนฮาร์ดแวร์ผู้รับ ดังนั้นความล้มเหลวแบบเงียบที่ฝั่งไกลจึงไม่ผ่านไปโดยไม่มีใครสังเกต

เปิดสวิตช์ **Receiver** ใน Settings เพื่อเผยแท็บ **Receiver** ปิดโดยค่าเริ่มต้น; เปิดเฉพาะบนเครื่องที่รับการสำรองข้อมูลนอกสถานที่แบบไม่เปลี่ยนแปลงได้จริงเท่านั้น จากนั้นลงทะเบียนรีพอสิทอรีที่ได้รับ (อ่านอย่างเดียว, เปิดด้วยคีย์ของอินสแตนซ์ผู้ส่ง) เพื่อให้ได้:

- **รายการสแนปช็อตที่จัดกลุ่มตามแหล่งที่มา** ดังนั้นคุณสามารถเห็นได้แน่ชัดว่า containers, VMs และชุดไฟล์ใดที่มาถึงแล้ว
- **เวลาที่ได้รับล่าสุด** ต่อแหล่ง ดังนั้นคุณจึงรู้ว่าแต่ละรายการสดใหม่แค่ไหน
- **`restic check` แบบอิสระ** ที่รันบนฮาร์ดแวร์ผู้รับ ดังนั้นความสมบูรณ์จึงได้รับการตรวจสอบ ณ ที่ที่ข้อมูลอยู่จริง ไม่ใช่แค่บนผู้ส่ง
- **dead-man's switch:** การแจ้งเตือนเมื่อแหล่งหนึ่งหยุดส่งภายในกรอบเวลาที่คุณตั้ง
- **การแจ้งเตือนความสมบูรณ์:** การแจ้งเตือนเมื่อการตรวจสอบที่ฝั่งรับล้มเหลว

Receiver เป็นแบบอ่านอย่างเดียวอย่างเคร่งครัด มันไม่เคยเขียนลงรีพอสิทอรีที่ได้รับ ดังนั้นจึงไม่มีทางทำลายการรับประกัน append-only ที่ผู้ส่งพึ่งพา

## ตัวอย่างใช้งานจริง: เครื่อง Unraid สองเครื่อง ตั้งแต่ต้นจนจบ

ด้านบนอธิบายชิ้นส่วนต่าง ๆ ตรงนี้คือการติดตั้งที่สมบูรณ์หนึ่งชุดพร้อมค่าจริง เพราะชิ้นส่วนจะประกอบง่ายขึ้นมากเมื่อเคยเห็นมันประกอบเสร็จสักครั้ง

สองเครื่อง: **TOWER** รันคอนเทนเนอร์และส่งข้อมูลสำรอง ส่วน **VAULT** รับและบังคับความไม่เปลี่ยนแปลง แทนที่ด้วยชื่อ ที่อยู่ และพาธแชร์ของคุณเอง

**1. บน VAULT ให้ตั้งเซิร์ฟเวอร์แบบเพิ่มได้อย่างเดียว** ใน BombVault บน TOWER เปิด *การตั้งค่า → ที่จัดเก็บ* คลิก **เพิ่มตำแหน่งจัดเก็บ** เลือก **rest-server** แล้วคลิก **แสดงชุดคำสั่ง** คัดลอกบล็อก **เทมเพลต Unraid** บันทึกบน VAULT เป็น `/boot/config/plugins/dockerMan/templates-user/my-rest-server.xml` จากนั้น *Docker → Add Container* แล้วเลือก **rest-server** จากรายการเทมเพลต ก่อนเริ่มทำงาน ให้เขียนบรรทัด `htpasswd` ที่แสดงลงใน `/mnt/user/appdata/rest-server/.htpasswd` บน VAULT รหัสผ่านจะแสดงเพียงครั้งเดียวและไม่ถูกเก็บไว้ ชุดคำสั่งได้ใส่รหัสผ่านและผู้ใช้ลงในแบบฟอร์มบน TOWER แล้ว จึงให้เปิดหน้าต่างนั้นค้างไว้ บรรทัด `htpasswd` มีรหัสผ่านเดียวกันที่แฮชด้วย bcrypt ให้แล้ว คุณจึงไม่ต้องแฮชอะไรเอง

    ปล่อย `--append-only` ไว้ในช่อง OPTIONS หากไม่มี VAULT ก็เป็นแค่แชร์ธรรมดาอีกครั้ง

**2. บน TOWER ให้เพิ่มตำแหน่งจัดเก็บ** ใส่ที่อยู่ของ VAULT คือ `http://VAULT:8000` ข้างผู้ใช้และรหัสผ่านที่ชุดคำสั่งกรอกไว้ แล้วคลิก **ทดสอบการเชื่อมต่อ** BombVault จะสร้างที่อยู่จากข้อมูลเหล่านั้น:

    rest:http://VAULT:8000/tower

ส่วนแรกของพาธคือผู้ใช้ htpasswd ในที่นี้คือ `tower` และแต่ละโดเมนจะได้โฟลเดอร์ของตัวเองอยู่ข้างใต้ เช่น `rest:http://VAULT:8000/tower/container` ตอบ **อุปกรณ์อยู่ที่ไหน?** ด้วย **ที่สถานที่อื่น** คลิก **เพิ่ม** แล้วทำเครื่องหมายตำแหน่งจัดเก็บนี้ใต้ **คัดลอกไปยัง** สำหรับโดเมนที่ควรไปที่นั่น

**3. บน TOWER ให้เปิด append-only** ใต้ **การป้องกัน** ในรายละเอียดของตำแหน่งจัดเก็บ แล้วคลิก **ทดสอบ append-only** การทดสอบจะตรวจทุกพาธของโดเมน สำเนา และรีพอสิทอรีที่ตำแหน่งจัดเก็บนั้น แล้วให้คำตอบเดียวสำหรับตำแหน่งจัดเก็บ ซึ่งต้องเป็น *ปฏิเสธการลบ* ความหมายของแต่ละผลลัพธ์:

| ผลลัพธ์ | เกิดอะไรขึ้น |
| --- | --- |
| **ปฏิเสธการลบ** | VAULT ปฏิเสธการลบ นี่คือสถานะที่ผ่านเพียงสถานะเดียว |
| **ยอมรับการลบ** | VAULT ยอมรับการลบ ไม่มี `--append-only` หรือถูกเอาออกไป |
| ข้อความแทนผลลัพธ์ | การทดสอบรันไม่ได้ ส่วนใหญ่เป็นเพราะที่อยู่ไม่ใช่อันที่ restic ใช้เอง หรือข้อมูลรับรองเปลี่ยนไป จะไม่มีการบันทึกและไม่มีการแจ้งเตือน |

**4. บน VAULT ให้ดูว่ามีอะไรเข้ามา** เปิด *ตั้งค่า → ตัวรับ* เปิดแท็บ **ตัวรับ** แล้วลงทะเบียนที่เก็บแบบอ่านอย่างเดียว

!!! warning "ตำแหน่งคือพาธ**ภายใน**คอนเทนเนอร์ เขียนแบบสัมพัทธ์กับจุดเมานต์ของโฮสต์"
    ให้ใส่ `user/appdata/rest-server/tower/container` **ไม่ใช่** `/mnt/user/appdata/…` BombVault ทำงานในคอนเทนเนอร์ที่ `/mnt` ของโฮสต์ถูกเมานต์ไว้ที่อื่น พาธสัมบูรณ์ของโฮสต์จึงไม่มีอยู่ในนั้น หากคุณวางลงไป BombVault จะบอกพาธสัมพัทธ์ที่ควรใช้แทน

    **APP_KEY ฝั่งส่ง** คือคีย์ของ TOWER ไม่ใช่ของ VAULT หาได้บน TOWER ที่ *ตั้งค่า → ระบบ*

**5. ถ้าต้องการ ให้ทำแบบสองทาง** ทำห้าขั้นตอนเดิมซ้ำในทิศทางกลับกัน: rest-server บน TOWER ที่รับสำเนาของ VAULT แล้วแต่ละเครื่องจะบังคับความไม่เปลี่ยนแปลงให้อีกเครื่อง และไม่มีเครื่องใดลบข้อมูลสำรองของอีกเครื่องได้

## การกู้คืนแบบมีคำแนะนำ

แท็บ **Recovery** โดยเฉพาะจะพาการติดตั้งใหม่หรือสร้างขึ้นใหม่ผ่านกรณีภัยพิบัติในที่เดียว:

1. **ตรวจสอบว่า BombVault อ่านการสำรองข้อมูลของคุณได้** (ปัญหาคีย์เข้ารหัสตั้งแต่ต้น)
2. **กู้คืนการตั้งค่าของ BombVault เอง** ดังนั้นพาธการสำรองข้อมูล, ปลายทางนอกสถานที่ และข้อมูลรับรองที่ขั้นตอนที่เหลือต้องการจะถูกเติมไว้ล่วงหน้า ระบบจะอ่านการสำรองข้อมูลการตั้งค่าจากตำแหน่งจัดเก็บที่แถว “สำรองข้อมูลตัวเอง” ระบุไว้ใต้ **จัดเก็บที่** หรือจากสำเนาของสำรองข้อมูลตัวเองใต้ **คัดลอกไปยัง** และแสดงตำแหน่งจัดเก็บนั้นพร้อมที่อยู่ หากต้องการอ่านจากตำแหน่งจัดเก็บอื่น ให้เปลี่ยนแถว “สำรองข้อมูลตัวเอง” ในขั้นตอนที่ 3 ก่อน การกู้คืนนำไปใช้ผ่านการรีสตาร์ทตัวเองผ่าน Docker socket ดังนั้นฐานข้อมูลการตั้งค่าที่กำลังทำงานจึงไม่เคยถูกเขียนทับภายใต้ handle ที่เปิดอยู่
3. **แนบการสำรองข้อมูลที่มีอยู่ของคุณ** ผ่านแถวของการ์ด **โดเมน**: ในแถวของแต่ละโดเมน ให้เลือกตำแหน่งจัดเก็บที่มีข้อมูลสำรองของโดเมนนั้นใต้ **จัดเก็บที่** และตำแหน่งจัดเก็บที่มีสำเนาใต้ **คัดลอกไปยัง** ตำแหน่งจัดเก็บที่ยังไม่มีแถวใดให้เลือก เช่น โฟลเดอร์แชร์ เซิร์ฟเวอร์ หรือบักเก็ตบนคลาวด์ จะเชื่อมต่อด้วย **เพิ่มตำแหน่งจัดเก็บ** ซึ่งเป็นหน้าต่างเดียวกับที่ การตั้งค่า, ที่จัดเก็บ จากนั้น **เชื่อมต่อและดูตัวอย่าง** จะตรวจสอบว่าอ่านข้อมูลสำรองได้
4. **ค้นพบ** containers, VMs, ชุดไฟล์ และชุดข้อมูล ZFS ที่จัดเก็บอยู่ในนั้น
5. **กู้คืน containers และ VMs ในครั้งเดียว** (ปล่อยให้หยุดไว้ เพื่อให้คุณเริ่มพวกมันอย่างตั้งใจ) และแสดงชุดไฟล์กับรายการ ZFS ให้กู้คืนทีละรายการ รายการ ZFS จะกลับมาในสถานะปิด ชุดกู้คืนของคุณอยู่ห่างเพียงคลิกเดียว

!!! note "สำเนานอกสถานที่รอหลังการสร้างใหม่"
    เมื่อขั้นตอนที่ 4 สร้างรายการขึ้นใหม่โดยไม่มีการตั้งค่าเดิม การจำลองข้อมูลนอกสถานที่ของโดเมนเหล่านั้นจะหยุดชั่วคราวจนกว่าค่าเริ่มต้นของการจัดวางจะได้รับการยืนยัน ดู [การจัดวางต่อรายการ](#placement)

!!! tip "การย้ายที่วางแผนไว้ เทียบกับ ภัยพิบัติ"
    การกู้คืนแบบมีคำแนะนำจะกู้คืนการตั้งค่าของ BombVault เองจากการสำรองข้อมูล สำหรับการย้ายไปยังเครื่องใหม่ที่ *วางแผนไว้* คุณสามารถนำการตั้งค่าของคุณไปได้โดยตรงด้วยการ์ด **Export and import settings** (ไฟล์ JSON ที่พกพาได้) แทน ดู [Configuration](configuration.md#portable-settings-export-and-import)

### กู้คืนจากรีพอสิทอรี BombVault อื่น

การ์ดแยกต่างหากบนแท็บ **Recovery** จะเปิดรีพอสิทอรีของอินสแตนซ์ BombVault *อื่น* (แชร์ที่เมานต์ภายใต้ `/mnt` หรือ URL ระยะไกล) ด้วย **`APP_KEY` ของอินสแตนซ์นั้น** ในเซสชันแบบครั้งเดียวและอ่านอย่างเดียว เรียกดู containers, VMs และชุดไฟล์ที่จัดเก็บอยู่ที่นั่น, เลือกสแนปช็อตและกู้คืนมัน แล้วอ็อบเจกต์ที่กู้คืนจะกลายเป็น container, VM หรือชุดไฟล์ในเครื่องปกติ ไม่มีอะไรถูกเขียนลงรีพอสิทอรีอื่นเลย และการตั้งค่าการสำรองข้อมูลของคุณเองยังคงไม่ถูกแตะต้อง (เซสชันอยู่ในหน่วยความจำและหมดอายุเอง) การย้าย container จากเซิร์ฟเวอร์ A ไปยังเซิร์ฟเวอร์ B ไม่ได้หมายถึงการชี้การตั้งค่ารีพอสิทอรีของคุณใหม่และย้อนกลับหลังจากนั้นอีกต่อไป การรวมกลุ่มเซิร์ฟเวอร์ต่อเซิร์ฟเวอร์แบบสดอยู่นอกขอบเขตอย่างชัดเจน นี่เป็นการดึงครั้งเดียวโดยเจตนา

## ชุดกู้คืนคีย์เข้ารหัส

นี่คือส่วนที่ทำให้การกู้คืนจากภัยพิบัติเป็นไปได้แม้ไม่มี BombVault ที่กำลังทำงาน

คลิกเดียวจะดาวน์โหลด **master key**, **รหัสผ่าน restic ที่ได้มา** และ **ตำแหน่งรีพอสิทอรีกับคำสั่งที่แน่นอน** ดังนั้นคุณสามารถกู้คืนได้ตรงด้วย restic CLI บนเครื่องใดก็ได้ การเตือนบนแดชบอร์ดจะจ้ำจี้จนกว่าคุณจะเก็บมันไว้แล้ว

!!! danger "เก็บชุดกู้คืนไว้นอกเซิร์ฟเวอร์"
    ชุดนี้มีความลับที่ถอดรหัสการสำรองข้อมูลของคุณ เก็บไว้ในที่ปลอดภัยและแยกจากเซิร์ฟเวอร์ (โปรแกรมจัดการรหัสผ่าน, สำเนาที่พิมพ์ไว้ในตู้เซฟ) หากคุณสูญเสียทั้ง BombVault และ `APP_KEY` โดยไม่มีชุดกู้คืน การสำรองข้อมูลที่เข้ารหัสไว้ของคุณจะไม่สามารถกู้คืนได้

!!! warning "สแนปช็อตล่าสุดไม่ใช่ตัวที่ควรกู้คืนเสมอไป"
    ตั้งแต่ restic 0.17 คำสั่ง `restic snapshots` แสดงขนาดของแต่ละสแนปช็อต หลังข้อมูลสูญหาย สแนปช็อตล่าสุดอาจเป็นตัวที่ถูกทำให้ว่าง จึงอย่ากู้คืนสแนปช็อตที่เล็กกว่าตัวก่อนหน้ามาก หลังโดนแรนซัมแวร์ อาจเป็นตัวที่ถูกเข้ารหัสซึ่งมีขนาดตามปกติ ถ้า BombVault ยังทำงานอยู่ ให้ดูหน้า **ความผิดปกติ** ก่อน หน้านั้นระบุการสำรองข้อมูลที่ดีล่าสุด การกู้คืนไม่ต้องใช้ข้อมูลความผิดปกติของ BombVault และการหยุดการเก็บรักษาชั่วคราวแค่เก็บสแนปช็อตไว้มากขึ้นเท่านั้น

### การปิดผนึกชุดกู้คืน

หากคุณเปิดการเข้ารหัส age สำหรับการส่งออกแบบธรรมดาไว้ (การตั้งค่า) ชุดกู้คืนจะถูกปิดผนึกด้วยเช่นกันและดาวน์โหลดเป็น `bombvault-recovery-kit.md.age` ไฟล์นี้อยู่ในรูปแบบ ASCII armor ไม่ใช่ไบนารี จึงยังเป็นข้อความธรรมดา การวางลงในตัวจัดการรหัสผ่านหรือการพิมพ์ออกมาใช้ได้เหมือนเดิมทุกอย่าง เพียงแต่อ่านเนื้อหาไม่ได้หากไม่มีคีย์ของคุณ

!!! warning "อย่าเก็บคีย์ age ไว้ในชุดกู้คืน"
    การเปิดชุดกู้คืนที่ปิดผนึกต้องใช้คีย์ age **ส่วนตัว** ของคุณ เก็บคีย์นั้นไว้ในที่ที่ไม่ขึ้นกับตัวชุดกู้คืนเอง มิฉะนั้นคุณจะมีสองสิ่งที่ต้องกู้คืนแทนที่จะเป็นสิ่งเดียว การปิดผนึกคุ้มค่าเมื่อชุดกู้คืนถูกเก็บไว้ในที่ที่คุณควบคุมได้ไม่เต็มที่ (ตัวจัดการรหัสผ่านที่ใช้ร่วมกัน โน้ตบนคลาวด์ หรือฉบับพิมพ์ในสำนักงาน) ส่วนชุดกู้คืนในตู้เซฟของคุณเองก็มีตู้เซฟปกป้องอยู่แล้ว

    เมื่อเปิดการเข้ารหัสไว้แต่ไม่ได้ตั้งค่าผู้รับที่ใช้ได้ การดาวน์โหลดจะถูกปฏิเสธทันที BombVault จะไม่หันไปส่งมอบมาสเตอร์คีย์เป็นข้อความธรรมดาแทนเด็ดขาด

### เมื่อไม่มีชุดกู้คืนอยู่ใกล้ตัว

รหัสผ่านไม่ได้ถูกเก็บไว้ที่ใดเลย แต่**คำนวณ**จาก `APP_KEY` ถ้ามีคีย์และเชลล์ คุณก็สร้างมันขึ้นมาเองได้

```sh
printf 'bombvault:restic-repo' \
  | openssl dgst -sha256 -mac HMAC -macopt hexkey:$APP_KEY -r \
  | cut -d' ' -f1
```

นี่คือ HMAC-SHA256 บนสตริงคงที่ `bombvault:restic-repo` โดยใช้ไบต์ดิบของ `APP_KEY` แบบเลขฐานสิบหกเป็นคีย์ และพิมพ์ออกมาเป็นอักขระฐานสิบหกตัวพิมพ์เล็ก 64 ตัว ค่าเดียวกันนี้อยู่ในชุดกู้คืน ระบุไว้เป็นรหัสผ่าน restic ที่อนุมานได้ ส่วนนี้มีไว้สำหรับวันที่ชุดกู้คืนอยู่คนละที่กับคุณ

!!! warning "สำหรับที่เก็บที่รับมา ให้ใช้คีย์ของอินสแตนซ์ฝั่งส่ง"
    ที่เก็บที่มาถึงที่นี่ผ่านการทำซ้ำนอกสถานที่ ถูกสร้างโดยเครื่องที่ส่งมันมา ด้วย `APP_KEY` **ของเครื่องนั้น** การอนุมานจากคีย์ของเครื่องผู้รับจะได้รหัสผ่านที่ restic ปฏิเสธ ซึ่งดูเหมือนที่เก็บเสียหายทุกประการทั้งที่ไม่ได้เสีย นี่คือสาเหตุที่พบบ่อยว่าทำไม `restic check` บนที่เก็บที่รับมาจึงถามรหัสผ่านซ้ำแล้วซ้ำเล่า

เนื่องจากคำจำกัดความการกู้คืนอยู่ **ภายใน** รีพอสิทอรีแต่ละตัว (`<repo>/def`, `<repo>/vm-def`) โฟลเดอร์รีพอสิทอรีที่คัดลอกมาจึงสมบูรณ์ในตัวเองอย่างเต็มที่ ดังนั้นชุดกู้คืนบวกกับรีพอสิทอรีจึงเป็นทุกสิ่งที่การกู้คืนแบบ bare-metal ต้องการ

## การเอาดัมป์ฐานข้อมูลกลับคืน {#database-dumps}

ดัมป์ฐานข้อมูลคือจุดกู้คืนของตัวเองในที่เก็บของคอนเทนเนอร์ มีป้าย `dbdump:<container>` และมีไฟล์เดียวคือ `/dbdump/<container>.sql` BombVault แสดงรายการ ดาวน์โหลด และนำเข้าให้ในหน้า **สำรองข้อมูล** ส่วนด้านล่างคือขั้นตอนเดียวกันด้วย restic เพียงอย่างเดียว สำหรับวันที่ไม่มี BombVault อยู่ด้วย

```sh
restic -r <repo> snapshots --tag dbdump:<container>
restic -r <repo> dump --tag dbdump:<container> latest /dbdump/<container>.sql > <container>.sql
```

ป้าย `dbversion:` และ `dbname:` บนดัมป์แต่ละอันบอกว่ามาจากเซิร์ฟเวอร์เวอร์ชันใดและมีฐานข้อมูลใดบ้าง ไฟล์ที่สมบูรณ์จะจบด้วย `-- PostgreSQL database cluster dump complete` หรือ `-- Dump completed`

นำเข้าไปยังคอนเทนเนอร์เวอร์ชันเดียวกันหรือใหม่กว่า (PostgreSQL) หรือเวอร์ชันหลักเดียวกัน (MySQL และ MariaDB) ที่เริ่มทำงานหนึ่งครั้งด้วยโฟลเดอร์ข้อมูลว่างเพื่อให้ตั้งค่าเริ่มต้นเสร็จแล้ว เครื่องโฮสต์ไม่ต้องมีไคลเอนต์ฐานข้อมูล เพราะคอนเทนเนอร์มีอยู่แล้ว

```sh
docker exec -i <container> sh -c 'exec psql -X -U "${POSTGRES_USER:-postgres}" -d postgres' < <container>.sql
docker exec -i <container> sh -c 'exec mariadb -uroot -p"$MARIADB_ROOT_PASSWORD"' < <container>.sql
docker exec -i <container> sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < <container>.sql
```

หากต้องการฐานข้อมูลเดียวจากดัมป์ทั้งก้อน MySQL และ MariaDB รับตัวเลือก `--one-database <name>` ในคำสั่งไคลเอนต์ ส่วนดัมป์ของ PostgreSQL มีหนึ่งส่วนต่อหนึ่งฐานข้อมูล แต่ละส่วนเริ่มด้วยบรรทัด `\connect <name>` ให้คัดลอกส่วนนั้นไปไว้ในไฟล์ของมันเอง แล้วนำเข้าด้วย `-d <name>` หลังจากสร้างฐานข้อมูลแล้ว

!!! warning "ดัมป์ที่ทำในฐานะ root พาผู้ใช้ของเซิร์ฟเวอร์มาด้วย"
    ดัมป์เต็มของ MySQL หรือ MariaDB ที่ทำในฐานะ root มีฐานข้อมูลระบบ `mysql` รวมอยู่ด้วย การนำเข้าจึงแทนที่บัญชีของเซิร์ฟเวอร์ใหม่ รวมถึงรหัสผ่านของ root ด้วยบัญชีจากดัมป์ ส่วนบน PostgreSQL ข้อความ `role ... already exists` สำหรับผู้ใช้ที่คอนเทนเนอร์สร้างเองนั้นเป็นเรื่องปกติและไม่เป็นอันตราย
