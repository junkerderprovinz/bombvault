# MCP 서버

BombVault에는 Model Context Protocol(MCP) 서버가 내장되어 있습니다. MCP는 Claude Code와 Claude Desktop 같은 AI 어시스턴트가 외부 도구에 접근할 때 쓰는 프로토콜입니다. 이를 통해 어시스턴트는 백업 상태를 읽을 수 있고, 허용하면 백업을 시작하거나 자신이 시작한 백업을 취소할 수 있습니다. 키를 만들거나 [OAuth 로그인](#oauth)을 켜기 전까지는 꺼져 있으며, 그동안 엔드포인트 `/mcp`는 모든 요청에 `404`로 응답합니다.

## 어시스턴트가 할 수 있는 일과 없는 일 {#tools}

| 도구 | 하는 일 | 종류 |
|---|---|---|
| `get_health` | 버전, 인스턴스 이름, 백업이 실행 중인지, 이 키에 허용된 것 | 읽기 |
| `get_status` | 섹션별 보호 상태: 마지막 성공 백업, 예상 간격, 검증과 오프사이트 점검, 다음 예약 실행, 앱이 한가해지기를 기다리는 백업. 컨테이너에는 최신 시작 테스트도 포함 | 읽기 |
| `get_coverage` | BombVault가 보호하는 것과 보호하지 않는 것, 각각의 이유 | 읽기 |
| `list_items` | 보호되는 모든 컨테이너, VM, 폴더 세트, 플래시 드라이브, 앱 설정. 일정, 백업할 때 멈추는 것, 마지막 백업과 걸린 시간이 함께 나옵니다. 데이터베이스 컨테이너에는 마지막 덤프도 붙습니다. ZFS 데이터세트도 마지막 점검 결과와 함께 나옵니다. 모든 항목에 마지막 복원 점검이, 컨테이너에는 마지막 시작 테스트 또는 테스트할 수 없는 이유가 붙습니다. 마지막 백업 이후 다른 설정으로 다시 만들어진 컨테이너는 무엇이 바뀌었는지 나옵니다 | 읽기 |
| `list_runs` | 실행 기록, 최신순. 섹션, 항목, 상태, 종류, 시간으로 거를 수 있습니다. 한 가지 때문에 느려진 백업은 그 원인을 알려 줍니다 | 읽기 |
| `list_restore_points` | 한 항목의 기본 저장소에 있는 복원 지점, 컨테이너라면 데이터베이스 덤프도 포함. ZFS 데이터세트는 백업마다 복원 지점이 하나이고, 그 아래 모든 데이터세트의 스냅샷이 들어 있습니다 | 읽기 |
| `get_activity` | 지금 실행 중인 것, 단계와 진행률 포함 | 읽기 |
| `get_storage_stats` | 한 섹션의 기본 저장소 크기 기록과 주간 증가량, 그리고 각 저장소가 있는 디스크나 원격 위치의 사용 공간, 여유 공간, 전체 공간 | 읽기 |
| `get_size_breakdown` | 컨테이너, VM, 폴더 세트의 최신 백업에서 어떤 폴더와 파일이 공간을 차지하는지, 그리고 마지막 백업이 각각 얼마나 추가했는지 | 읽기 |
| `list_anomalies` | BombVault가 백업에서 알아챈 이상 징후. 상태, 심각도, 섹션으로 거를 수 있고 열려 있는 것의 요약이 붙습니다 | 읽기 |
| `get_anomaly` | 그중 하나와 확인할 때 남긴 메모 | 읽기 |
| `start_backup` | 한 항목을 지금 백업합니다 | 시작 |
| `start_domain_backup` | 한 섹션의 보호 대상 항목을 모두 백업합니다 | 시작 |
| `start_backup_everything` | 전체 백업을 한 바퀴 실행합니다 | 시작 |
| `cancel_backup` | 이 키가 시작해 실행 중인 백업을 취소합니다 | 취소 |

다음은 웹 인터페이스에서만 할 수 있습니다. 모든 종류의 복원(데이터베이스 덤프의 다운로드, 저장, 가져오기 포함), 백업 삭제, prune, unlock, 점검과 훈련, 오프사이트 복제, 설정, 자격 증명과 MCP 키, 그리고 일정이나 웹 인터페이스 또는 다른 키가 시작한 백업의 취소입니다. 이상 징후를 확인하거나 예상된 것으로 표시하는 일도 마찬가지로 **이상 징후** 페이지에서 합니다. 도구의 응답에 서버에서 온 이름과 오류 메시지가 들어 있고, 그중 어느 것에든 어시스턴트를 조종하려고 쓴 글이 섞여 있을 수 있기 때문입니다. 그런 글에 속은 어시스턴트가 할 수 있는 일은 최악의 경우에도 아래 제한 안에서 백업을 시작하거나 자신이 시작한 백업을 취소하는 것뿐입니다.

항목의 기본 저장소가 원격(S3, REST, SFTP, rclone)이면 `list_restore_points`가 그곳에 연결하므로 호출에 시간이 걸릴 수 있습니다. 오프사이트 사본은 MCP로 나열할 수 없습니다. 이상 징후 검사가 무엇을 보는지는 [이상 징후](anomalies.md)에, ZFS 항목이 데이터세트마다 스냅샷을 하나씩 두는 방식은 [ZFS 데이터세트](zfs-datasets.md#contents)에 설명되어 있습니다.

## 시작한 백업이 하는 일 {#starting-backups}

어시스턴트의 백업은 웹 인터페이스가 시작하는 백업과 같습니다. 실행 중인 컨테이너는 백업이 끝날 때까지 멈추며, 함께 멈추도록 설정된 컨테이너도 같이 멈춥니다. graceful 방식의 VM은 종료되었다가 다시 시작됩니다. ZFS 데이터세트는 스냅샷을 찍는 동안 그 데이터세트에 지정된 컨테이너를 멈춥니다. 폴더 세트, 플래시 드라이브, 설정은 계속 동작합니다. 그다음 BombVault는 보존 정책을 적용하고 오프사이트 저장소로 복사할 수 있습니다. `list_items`는 어시스턴트에게 항목이 무엇을 멈추는지와 마지막 백업이 얼마나 걸렸는지를 알려 주고, 도구 설명은 무언가를 시작하기 전에 사용자에게 먼저 말하라고 요청합니다.

백업은 서비스를 멈추고 오래된 복원 지점을 밀어내므로, MCP를 통한 시작에는 제한이 있습니다.

- 키마다 시간당 12번의 백업 시작.
- 같은 항목, 같은 섹션, 전체 백업의 MCP 시작 사이에는 15분.
- 같은 항목의 MCP 시작은 24시간에 최대 4번.
- **보존 가드.** 섹션이 정해진 개수의 복원 지점을 보존할 때(일간, 주간, 월간 규칙 없이 "최근 N개 보존"만 있는 경우이며, 로컬이든 오프사이트 대상이든 같습니다), 새 백업이 생길 때마다 가장 오래된 것이 밀려납니다. 이때 BombVault는 최근 N-1개의 성공한 백업이 모두 MCP로 시작된 항목에 대해서는 MCP 시작을 거부합니다. 그래서 보존되는 묶음에는 일정이나 사용자가 만든 복원 지점이 언제나 적어도 하나 남습니다. "최근 1개 보존"에서는 어시스턴트가 그 항목을 전혀 백업할 수 없습니다. 다음 예약 백업이 다시 자리를 만듭니다. 연간 규칙만 있으면 올해의 복원 지점 하나만 남기므로 "최근 1개 보존"과 같게 칩니다.

섹션이나 전체 백업을 시작하면 제한에 걸린 항목은 빼고, 응답에서 그 이름을 알려 줍니다. 웹 인터페이스와 일정에는 이 제한이 적용되지 않습니다. 시간당 한도는 메모리에 있으므로 BombVault를 다시 시작하면 초기화됩니다.

[API](api.md#errors)와 [Home Assistant](api.md#home-assistant)를 통한 시작도 항목별 제한과 보존 가드에서 MCP를 통한 시작과 함께 계산됩니다.

## 켜기 {#switch-on}

1. **설정, 연동, MCP 서버**를 열고 **클라이언트 선택**을 누른 뒤 창에서 사용하는 클라이언트를 고르세요. 오른쪽 위의 검색으로 이름으로 찾을 수 있습니다. 목록에 없는 클라이언트는 **다른 클라이언트**로 연결합니다.
2. **키**에서 **새 키**와 제안된 이름(클라이언트 이름)을 그대로 두거나, 키를 어디에 쓰는지 알 수 있는 이름을 입력하세요. 예를 들어 "노트북의 Claude Code"처럼요. 클라이언트마다 키를 하나씩 두면 다른 키를 건드리지 않고 하나만 폐기할 수 있습니다. **기존 키**는 전에 만든 키를 클라이언트에 줍니다.
3. 백업을 시작할 수 있어야 하는 키에는 **백업 시작 허용**을 켜세요. 끄면 키는 읽기만 할 수 있습니다. 나중에 키의 **세부 정보**에서 바꿀 수 있고, 바꾼 내용은 다시 연결하지 않아도 어시스턴트의 다음 요청부터 적용됩니다.
4. **키 만들기**를 누르세요. 키는 한 번만 표시됩니다. BombVault는 지문만 보관하므로 키를 다시 보여 줄 수 없으니 지금 복사하세요. 클라이언트가 키를 쓰기 전에 창을 닫으면, 복사했다고 확인할 때까지 카드에 키가 계속 표시됩니다.

로그인 비밀번호가 없으면 웹 인터페이스 자체가 네트워크의 모든 사람에게 열려 있고, 열 수 있는 사람은 누구나 키도 만들 수 있습니다. 카드에도 그렇게 표시됩니다. 공개된 것처럼 보이는 이름(예: 리버스 프록시 뒤의 `bombvault.example.com`)으로 BombVault를 열었고 로그인 비밀번호가 설정되어 있지 않다면, 그 주소에서는 키를 만들거나 교체할 수 없습니다. 인터넷의 어떤 웹 페이지도 여러분의 브라우저가 키를 만들게 하지 못하도록 하기 위해서입니다. 로그인 비밀번호를 설정하거나, IP 주소 또는 `tower`, `tower.local` 같은 로컬 이름으로 BombVault를 여세요.

## 키와 키별 로그 {#keys}

**키 및 로그인한 클라이언트** 아래에서 각 키는 자기 행을 가집니다. 행에는 키 이름, 백업을 시작할 수 있는지 읽기만 하는지, 키의 마지막 네 글자, 만든 시각이나 마지막으로 교체한 시각, 클라이언트가 마지막으로 쓴 시각이 나옵니다. **세부 정보**는 창을 열어 키 이름을 바꾸고, 권한을 바꾸고, 키를 교체하거나 폐기할 수 있게 하며, 오늘 몇 번 호출했는지도 보여 줍니다. 폐기한 키는 폐기된 키 목록으로 옮겨지며, 기록의 어떤 실행도 그 키를 가리키지 않게 되면 거기서 영구 삭제할 수 있습니다.

행의 이름 옆에는 키를 만든 대상 클라이언트의 로고가 표시됩니다. **다른 클라이언트**로 만들었거나 카드가 클라이언트를 나열하기 전에 만든 키에는 대신 열쇠 아이콘이 표시됩니다.

키 세부 정보의 **로그**에는 그 키가 한 일이 보이며, 폐기된 키에는 자체 **로그** 버튼이 남습니다. 먼저 그 키가 시작한 백업이 상태와 함께 나오고, 대시보드 활동 로그의 해당 실행으로 가는 링크가 붙습니다. 그 아래에 호출이 최신순으로, 도구와 호출 결과와 함께 나옵니다. 거부된 호출에는 이유가 붙습니다. 키가 읽기 전용이거나, 보존 가드가 백업을 막았거나, 다른 백업이 이미 실행 중이었거나, 같은 항목, 섹션, 전체 백업이 몇 분 전에 웹 인터페이스 밖에서 시작되었거나, 키가 요청을 너무 많이 보낸 경우입니다. 취소에는 해당 실행으로 가는 링크가 붙습니다.

BombVault는 키마다 기록을 최대 30일 동안 보관합니다. 성공한 시작과 취소는 최신 500건, 이와 별도로 나머지 호출(읽기, 거부, 오류)은 최신 200건입니다. 실행 중인 백업을 계속 조회하거나 거부된 호출을 계속 재시도하는 어시스턴트가 있어도 그 백업의 시작 기록이 로그에서 밀려나지 않습니다. 호출마다 도구, 결과, 취소가 가리킨 실행을 저장합니다. 어시스턴트가 보낸 내용은 저장하지 않으며, 키나 그 지문도 저장하지 않습니다. 진단 번들에는 기록 개수만 들어가고, 설정 내보내기에는 기록이 빠집니다.

## 클라이언트 연결 {#clients}

**클라이언트 선택**은 모든 클라이언트를 **이 컴퓨터에서** 또는 **클라우드에서** 아래에 타일로 보여 주는 창을 열며, 오른쪽 위에 검색이 있습니다. 타일을 누르면 같은 창에서 그 클라이언트의 설정이 세 단계로 열립니다. 첫째는 키입니다. 둘째는 그 클라이언트용 구성으로, 카드를 연 주소가 들어 있고 복사 버튼, 구성이 있는 위치, BombVault 자체 인증서를 쓸 때 클라이언트가 그것을 신뢰하려면 필요한 것이 나옵니다. 셋째는 클라이언트의 첫 호출을 기다리는 단계입니다. 창이 키의 마지막 사용을 지켜보다가 그 호출이 들어오면 초록색으로 바뀝니다.

설정 안내는 키가 어떤 명령줄에도 남지 않게 합니다. 클라이언트가 환경 변수(`BOMBVAULT_MCP_KEY`), 가려진 입력 창, 자체 파일에서 키를 읽을 수 있으면 구성에는 그 이름만 적습니다. 그런 방법이 없는 클라이언트는 키가 구성 파일이나 설정에 들어가며, 설정 안내가 그렇다고 알려 줍니다. 클라이언트 문서가 모르는 인증서를 어떻게 다루는지 밝히지 않은 경우, 설정 안내는 그 단계를 클라이언트가 BombVault의 인증서를 거부할 때 할 일로 적습니다.

|---|---|---|
| AnythingLLM | 구성 파일 | 구성 파일 |
| Antigravity | 구성 파일 | 환경 변수 |
| Claude Code | 명령 | 키 파일 |
| Claude Desktop | 구성 파일 | 키 파일 |
| Cline | 구성 파일 | 구성 파일 |
| Codex CLI | 구성 파일 | 환경 변수 |
| Continue | 구성 파일 | `~/.continue/.env` |
| Copilot CLI | 구성 파일 | 구성 파일 |

### Claude Code {#claude-code}

Claude Code는 `mcp-remote`를 통해 BombVault에 접근하며, 이를 위해 그 컴퓨터에 Node.js가 필요합니다. 먼저 키를 한 줄로 적어 별도의 텍스트 파일에 저장하세요.

```text
X-API-Key: <your key>
```

그다음 카드에 나온 명령을 터미널에서 한 번 실행하되, 그 파일의 경로를 채워 넣으세요. 컴퓨터가 신뢰하는 인증서 뒤라면 다음과 같습니다.

```bash
claude mcp add bombvault --scope user -- npx -y mcp-remote@latest https://bombvault.example.com/mcp --header-file "<path of the file with your key>"
```

BombVault 자체 인증서를 쓸 때([TLS와 인증서](#tls) 참고)는 명령이 Node.js가 내려받은 인증서를 가리키게도 합니다.

```bash
claude mcp add bombvault --scope user -e "NODE_EXTRA_CA_CERTS=<path of the downloaded bombvault-cert.pem>" -- npx -y mcp-remote@latest https://192.168.1.10:3443/mcp --header-file "<path of the file with your key>"
```

Claude Code 안에서 `/mcp`로 연결을 확인하세요. `--scope user`는 모든 프로젝트에서 BombVault를 쓸 수 있게 합니다. Claude Code는 키 파일의 경로만 보관하므로, 키는 명령과 셸 기록에도, 프로세스 목록에도 나타나지 않습니다. 파일은 본인만 읽을 수 있는 곳에, 그리고 커밋하는 폴더 밖에 두세요. `@latest`는 `npx`가 최신 `mcp-remote`를 받아 오게 합니다. 전역으로 설치된 오래된 버전이 있으면 그것이 대신 쓰이는데, 그 버전은 `--header-file`을 모릅니다.

Claude Code용 `mcp-remote` 인자에 `${BOMBVAULT_MCP_KEY}`를 적지 마세요. Claude Code는 `mcp-remote`를 시작하기 전에 이런 참조를 자기 환경에서 채워 넣기 때문에, 키가 그 프로세스의 명령줄에 남고 컴퓨터의 다른 프로그램과 사용자가 읽을 수 있게 됩니다.

Node.js가 없고 컴퓨터가 신뢰하는 인증서 뒤에 있을 때만, Claude Code가 직접 연결할 수 있습니다. 프로젝트 폴더에 `.mcp.json`을 두세요.

```json
{
  "mcpServers": {
    "bombvault": {
      "type": "http",
      "url": "https://bombvault.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${BOMBVAULT_MCP_KEY}"
      }
    }
  }
}
```

`BOMBVAULT_MCP_KEY`는 Claude Code가 시작되는 곳에서 설정하세요. 예를 들면 `~/.claude/settings.json`의 `"env"` 아래나 셸 프로필이며, 프롬프트에 입력하지 말고 텍스트 편집기로 수정하세요. 여기서는 참조를 써도 안전합니다. Claude Code가 그것을 넘겨받을 두 번째 프로세스를 시작하지 않기 때문입니다. BombVault 자체 인증서는 이 방식으로는 동작하지 않습니다. Claude Code의 자체 연결은 `NODE_EXTRA_CA_CERTS`를 설정해도 그 인증서를 거부합니다. 키를 직접 적은 `.mcp.json`은 절대 커밋하지 마세요.

### Claude Desktop {#claude-desktop}

Claude Desktop은 `mcp-remote`를 통해 BombVault에 접근하며, 이를 위해 그 컴퓨터에 Node.js가 필요합니다. [Claude Code](#claude-code)에서 설명한 대로 먼저 키를 한 줄로 적어 별도의 텍스트 파일에 저장하세요. 구성 파일은 Claude Desktop의 **Settings, Developer, Edit Config**에서 엽니다. Windows에서는 `%APPDATA%\Claude\claude_desktop_config.json`, macOS에서는 `~/Library/Application Support/Claude/claude_desktop_config.json`에 있습니다. 카드에 나온 항목을 `"mcpServers"` 안에 이미 있는 서버 옆에 추가하고 Claude Desktop을 다시 시작하세요.

```json
{
  "mcpServers": {
    "bombvault": {
      "command": "npx",
      "args": ["-y", "mcp-remote@latest", "https://192.168.1.10:3443/mcp", "--header-file", "<path of the file with your key>"],
      "env": {
        "NODE_EXTRA_CA_CERTS": "<path of the downloaded bombvault-cert.pem>"
      }
    }
  }
}
```

- `NODE_EXTRA_CA_CERTS`는 BombVault 자체 인증서를 쓸 때만 필요합니다. 컴퓨터가 이미 신뢰하는 인증서 뒤라면 빼세요.
- `--allow-http`는 일반 `http://` 주소일 때만 추가됩니다.
- Windows에서는 경로를 슬래시로 적으세요. 예: `C:/Users/sam/bombvault-key.txt`. 백슬래시 하나는 JSON에서 유효하지 않기 때문입니다. 키 파일 경로에는 공백을 넣지 마세요. Windows의 Claude Desktop은 공백이 있는 경로를 `npx`에 두 조각으로 넘깁니다.
- 구성에는 키 파일 이름만 적히므로 키는 구성에도 프로세스 목록에도 나타나지 않습니다. 파일은 본인만 읽을 수 있는 곳에 두세요.

### 클라우드 클라이언트 {#cloud-clients}

ChatGPT, claude.ai의 Claude, Grok, Le Chat은 제공업체의 서버에서 BombVault를 호출하므로, BombVault가 공개적으로 신뢰받는 인증서와 함께 인터넷에서 닿을 수 있어야 합니다. 예를 들어 리버스 프록시 뒤에 두면 됩니다. Le Chat은 자체 서명 인증서를 거부합니다. 프록시의 로그인은 웹 인터페이스를 보호할 수 있지만, `/mcp`는 그 로그인 없이 BombVault까지 그대로 통과해야 합니다. 이 서비스들은 프록시에 로그인할 수 없고, BombVault가 그들의 키나 토큰을 직접 확인하기 때문입니다. Grok과 Le Chat은 고정된 키를 보내며, 버튼으로 다른 클라이언트처럼 설정됩니다. ChatGPT와, 대부분의 조직에서 claude.ai의 Claude는 다음에 설명하는 OAuth 로그인으로만 연결합니다.

### OAuth 로그인 {#oauth}

키를 받을 수 없는 클라이언트를 위해 BombVault는 스스로 OAuth 인증 서버가 됩니다. 클라이언트가 스스로를 등록하고 여러분을 BombVault 페이지로 보내면, 거기서 로그인 비밀번호(2단계 인증을 설정했다면 두 번째 요소도)로 로그인하고 허용합니다. 그러면 클라이언트는 이 BombVault의 MCP 엔드포인트에서만 쓸 수 있는 토큰을 받고, 스스로 갱신합니다.

1. **설정, 보안**에서 로그인 비밀번호를 설정하세요. 비밀번호가 없으면 동의를 물어볼 사람이 없으므로 BombVault는 로그인을 아예 제공하지 않습니다.
2. 브라우저가 신뢰하는 인증서로 BombVault를 https로 인터넷에서 닿을 수 있게 하세요. 보통은 리버스 프록시를 씁니다. 클라이언트는 자기 서버에서 `/mcp`, `/oauth/`, `/.well-known/`을 호출하므로, 자체 로그인이 있는 프록시는 이 세 경로를 BombVault까지 통과시켜야 합니다. `/oauth/authorize`의 동의 페이지는 여러분의 브라우저에서 열리므로 프록시 로그인 뒤에 있어도 됩니다. 프록시를 `TRUSTED_PROXY`에도 적으세요([구성](configuration.md) 참고). BombVault는 주소당 클라이언트 등록을 제한하는데, 이 설정이 없으면 모든 클라이언트가 프록시에서 오는 것처럼 보입니다.
3. MCP 카드에서 **OAuth 로그인**을 켜고 **공개 주소**를 입력하세요. 경로 없는 https 주소입니다. 예: `https://backup.example.com`. 모든 토큰이 이 주소에 묶이므로, 바꾸면 각 클라이언트가 다시 로그인해야 합니다.
4. **클라이언트 선택**에서 ChatGPT 또는 Claude를 고르세요. 창에 **커넥터 URL**이 표시됩니다. 공개 주소에 `/mcp`를 붙인 것이고, 그 클라이언트의 어디에 넣는지도 알려 줍니다. ChatGPT에서는 **Settings, Apps & Connectors, Advanced settings**에서 Developer mode를 켜고 **Create**를 고른 다음, 커넥터 URL을 MCP 서버 URL로 붙여 넣고 인증 방식은 OAuth를 고르세요. claude.ai에서는 **Settings, Connectors, Add custom connector**를 열고 커넥터 URL을 붙여 넣은 뒤, OAuth 클라이언트 ID와 비밀은 비워 두고 **Connect**를 고르세요.
5. 클라이언트가 동의 페이지를 엽니다. 누가 요청하는지, 답을 하면 어디로 돌아가는지, 처음에는 꺼져 있는 **백업 시작 허용** 스위치가 표시됩니다. **허용** 또는 **거부**를 고르세요.

로그인한 클라이언트마다 같은 목록에 로고와 함께 자기 행이 생깁니다. 클라이언트의 **세부 정보**에는 로그, **취소**, **백업 시작 허용**이 있으며, 키와 같은 제한을 받습니다. 취소하면 바로 효력이 생깁니다. 같은 클라이언트가 다시 로그인하면 새 허가가 이전 것을 대체하고, 30일 동안 아무도 쓰지 않은 허가는 만료됩니다. 키 10개와 별도로 클라이언트를 한 번에 최대 10개까지 로그인해 둘 수 있습니다.

동의 페이지는 등록된 클라이언트가 등록한 돌아갈 주소 중 하나를 정확히 지정한 요청만 받습니다. https이거나, 여러분의 컴퓨터에 있는 클라이언트라면 포트에 상관없이 루프백 주소입니다. PKCE(S256)를 쓰는 인증 코드 흐름만 받으며, 여러분의 답은 세션에 묶여 있어서 다른 웹사이트가 대신 보낼 수 없습니다. 액세스 토큰은 한 시간 동안 유효합니다. 갱신 토큰은 쓸 때마다 교체되고, 그 뒤에 다시 나타나는 갱신 토큰은 누군가 사본을 가지고 있다는 뜻이므로 그 허가를 폐기합니다. 응답이 닿지 못해 마지막 갱신을 30초 안에 되풀이하는 클라이언트에게는 새 토큰을 내줍니다. BombVault는 인터넷에서 클라이언트 메타데이터 문서를 가져오지 않으므로, 클라이언트는 동적 클라이언트 등록으로 등록합니다.

### 그 밖의 클라이언트 {#other-clients}

Streamable HTTP를 쓰는 클라이언트라면 모두 동작합니다.

- URL: 웹 인터페이스 주소에 `/mcp`를 붙입니다. 예: `https://192.168.1.10:3443/mcp`.
- 키는 `Authorization: Bearer <key>` 또는 `X-API-Key: <key>`로 보냅니다. 둘 다 보내면 같은 키여야 합니다.
- `Content-Type: application/json`과 `Accept: application/json, text/event-stream`을 붙인 `POST`.
- 요청마다 JSON-RPC 메시지 하나. 일괄 요청은 거부됩니다.
- 프로토콜 버전 2026-07-28, 2025-11-25, 2025-06-18, 2025-03-26.

## TLS와 인증서 {#tls}

BombVault는 스스로 만든 인증서로 HTTPS를 제공하며, 처음에 그 인증서에는 `localhost`, `127.0.0.1`, `::1`만 들어 있습니다. Claude Code와 `mcp-remote`는 LAN 주소에서 이를 거부합니다. 대부분의 Unraid 설치에 알맞은 순서로 해결 방법은 다음과 같습니다.

1. **MCP 카드에서 주소를 추가합니다.** 인증서에 없는 주소로 HTTPS를 통해 카드를 열면, 카드가 그렇다고 알려 주고 **이 주소를 인증서에 추가**를 제안합니다. BombVault가 그 주소를 더해 인증서를 다시 발급합니다(브라우저는 처음처럼 한 번 더 경고합니다). 그다음 **인증서 내려받기**를 누르세요. 안내에 나온 스니펫은 `NODE_EXTRA_CA_CERTS`를 내려받은 파일로 지정하므로, 클라이언트는 정확히 이 인증서만 신뢰합니다. 이는 이전에 내려받은 인증서로 설정한 모든 클라이언트가, 이 컴퓨터든 다른 컴퓨터든, 인증서가 다시 발급되는 즉시 새 파일을 받을 때까지 연결되지 않는다는 뜻이기도 합니다.
2. **신뢰받는 인증서를 가진 리버스 프록시**(Nginx Proxy Manager, SWAG, Caddy, Traefik). 그러면 클라이언트는 프록시의 인증서를 보므로 따로 할 일이 없고, 카드도 BombVault 자체 인증서에 대해 경고하지 않습니다.
3. **Tailscale.** 컨테이너 앞에 `tailscale serve`를 두거나 Unraid의 Tailscale 연동을 쓰면 신뢰받는 인증서가 붙은 `ts.net` 이름을 얻습니다.
4. **`HTTP_ONLY=true`**는 TLS를 종료하는 프록시 뒤나 완전히 믿을 수 있는 네트워크에서만 쓰세요. 웹 인터페이스 전체를 일반 HTTP로 바꾸고, 컨테이너 설정을 바꿔야 하며, 키를 암호화하지 않고 보냅니다.

`NODE_TLS_REJECT_UNAUTHORIZED=0`은 절대 설정하지 마세요. 그 Node.js 프로세스가 통신하는 모든 대상에 대해 인증서 검사를 끕니다.

리버스 프록시는 `Authorization`(또는 `X-API-Key`) 헤더를 그대로 넘겨야 하며(별도로 막지 않는 한 프록시는 그렇게 합니다), `/mcp`를 버퍼링하거나 바꿔 쓰면 안 됩니다. BombVault의 인증서도 확인하는 Nginx 또는 Nginx Proxy Manager용 location 블록은 다음과 같습니다.

```nginx
location /mcp {
    proxy_pass https://192.168.1.10:3443;
    proxy_ssl_verify on;
    proxy_ssl_trusted_certificate /data/bombvault-cert.pem;
    proxy_ssl_name localhost;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_set_header Host $host;
}
```

프록시 뒤에서는 모든 요청이 프록시의 주소를 달고 옵니다. 그러면 잘못 설정된 클라이언트 하나가 잘못된 키를 다섯 번 보내면 그 프록시 뒤의 모든 MCP 클라이언트가 1분 동안 잠깁니다. 클라이언트별로 세려면 프록시를 `TRUSTED_PROXY`에 적으세요([구성](configuration.md) 참고).

## 보안 모델 {#security}

- 활성 키가 없고 OAuth 로그인이 꺼져 있으면 `/mcp`는 `404`로 응답합니다.
- OAuth 로그인은 로그인 비밀번호가 설정되어 있는 동안에만 제공됩니다. 토큰, 코드, 클라이언트 비밀은 지문으로만 저장되며, 토큰은 발급된 주소에서만 동작합니다.
- 클라이언트는 한 주소에서 시간당 최대 10번 등록할 수 있고, BombVault는 아무도 로그인하지 않은 등록 클라이언트를 최대 100개까지 하루 동안 보관합니다. 잘못된 코드와 갱신 토큰은 잘못된 키와 같은 잠금에 합산됩니다.
- 구성 백업을 복원하거나 `APP_KEY`가 바뀌면 허가도 키처럼 동작합니다. 복원 후에는 모든 클라이언트가 다시 로그인해야 합니다.
- 예외 주소는 없습니다. `localhost`, Unraid 호스트, 리버스 프록시, `tailscale serve`에서 온 요청도 웹 인터페이스에 로그인 비밀번호가 없을 때조차 다른 요청과 똑같이 키가 필요합니다.
- 키는 지문으로만 저장되고, 한 번만 표시되며, 이름 변경, 교체, 폐기를 할 수 있습니다. 활성 키는 최대 10개이고, 각각 자기 **백업 시작 허용** 스위치가 있습니다.
- 키를 만들거나, 교체하거나, 권한을 바꾸거나, 폐기할 때마다 알림이 꺼져 있지 않은 한 요청이 온 주소와 함께 알림 채널로 알림이 갑니다.
- 주소당 분당 잘못된 키 5개까지이고 그 뒤에는 `429`입니다. 키마다 분당 120번의 요청과 시간당 12번의 백업 시작이며, 위의 대기 시간과 보존 가드가 더해집니다.
- 다른 출처의 브라우저 페이지에서 온 요청은 거부됩니다.
- 로그인 비밀번호가 없는 동안에는 공개된 것처럼 보이는 호스트 이름에서 키를 만들 수 없습니다.
- 어시스턴트가 시작한 모든 백업과, 그로 인한 prune 및 오프사이트 실행은 활동 로그, 오류 패널, 백업 알림에 키 이름과 함께 "via MCP"로 표시됩니다.
- 모든 도구 호출은 키의 id와 마지막 네 글자(이름은 절대 아님)와 함께 컨테이너 로그에 기록되고 `/metrics`(`bombvault_mcp_requests_total`, `bombvault_mcp_tool_calls_total`, `bombvault_mcp_active_keys`)에 집계됩니다.
- 구성 백업을 복원하면 모든 키가 폐기됩니다. 복원한 데이터베이스에는 저장한 뒤에 폐기한 키가 들어 있을 수 있기 때문입니다. 복원한 뒤에는 새 키를 만드세요.
- `APP_KEY`가 바뀌면(재설치하거나 다른 컨테이너로 복원할 때) 키가 동작하지 않습니다. 카드가 이를 감지해 키에 표시하며, **키 교체**를 누르면 키에 다시 쓸 수 있는 비밀이 생깁니다.
- 키는 비밀번호처럼 다루세요. 환경 변수, 프롬프트, 키 파일에서 키를 읽지 못하는 클라이언트는 키를 구성이나 설정에 평문으로 보관하며, 설정 안내가 그렇다고 알려 줍니다. 덜 믿는 컴퓨터에는 읽기 전용 키를 쓰는 편이 좋습니다.

## 밖으로 나가는 것 {#privacy}

어시스턴트가 읽은 것은 그 뒤에 있는 AI 제공업체로 갑니다. 항목 이름, 일정, 오류 메시지가 포함된 실행 기록, 복원 지점의 id와 시각, 데이터베이스 엔진 이름과 덤프 크기, 현재 활동, 저장소 수치, 보호 범위와 상태가 해당합니다. BombVault는 무언가 밖으로 나가기 전에 호스트 경로, 저장소 위치, 호스트 이름, 자격 증명, 훅 명령, 키를 제거합니다.

## 문제 해결 {#troubleshooting}

| 보이는 증상 | 의미 |
|---|---|
| `404` | 활성 키가 없고 OAuth 로그인이 꺼져 있거나, `/api/mcp` 같은 잘못된 경로입니다. 엔드포인트는 `/mcp`입니다. |
| `401` | 키가 없거나, 잘못 입력했거나, 폐기되었거나, 교체되었습니다. 프록시가 `Authorization` 헤더를 떨어뜨리고 있을 수 있습니다(`X-API-Key`를 써 보세요). 카드가 키를 더 이상 유효하지 않다고 표시하면 `APP_KEY`가 바뀐 것이니 키를 교체하세요. |
| `403` | 요청이 다른 출처의 브라우저 페이지에서 왔습니다. 데스크톱 클라이언트나 명령줄 클라이언트를 쓰세요. |
| GET에 `405` | 정상입니다. 엔드포인트는 `POST`만 받습니다. |
| `400` "Accept must contain both 'application/json' and 'text/event-stream'" | 클라이언트가 Streamable HTTP를 쓰기에는 너무 오래되었습니다. 업데이트하세요. |
| `400` "batch requests are not accepted" | 클라이언트가 JSON-RPC 일괄 요청을 보냅니다. 요청마다 메시지 하나를 보내세요. |
| `429` | 이 주소에서 잘못된 키가 너무 많았거나, 키 하나로 분당 120번이 넘는 요청이 왔습니다. 1분 기다리고, 어시스턴트가 반복에 갇혀 있지 않은지 확인하세요. |
| "certificate", "self-signed", "unable to verify" 오류 | 클라이언트가 BombVault의 인증서를 신뢰하지 않습니다. [TLS와 인증서](#tls)를 참고하세요. |
| `busy` | 다른 백업이나 유지 관리 작업이 그 섹션을 쥐고 있습니다. 끝난 뒤 다시 시도하세요. |
| `cooldown` | 이 항목, 섹션, 전체 백업이 15분이 지나기 전에 웹 인터페이스 밖에서 시작되었습니다. |
| `retention_guard` | MCP 백업을 하나 더 하면 "최근 N개 보존" 범위에 MCP로 만든 복원 지점만 남게 되거나, 항목이 지난 24시간 동안 이미 MCP로 백업을 4번 받았습니다(실패하거나 취소된 것 포함). 앞의 경우에는 다음 예약 백업이 자리를 만들고, 뒤의 경우에는 그 백업 중 가장 오래된 것으로부터 24시간 뒤에 항목이 다시 풀립니다. 어느 쪽이든 웹 인터페이스에서 시작할 수 있습니다. |
| `rate_limited` | 키가 이번 시간의 시작 12번을 모두 썼습니다. |
| 시작에서 `not_permitted` | 키가 읽기 전용입니다. 카드에서 **백업 시작 허용**을 켜세요. 다시 연결하지 않아도 됩니다. 취소에서는 그 실행을 이 키가 시작하지 않았다는 뜻입니다. |
| `domain_off` | 그 섹션이 **설정, 일반**에서 꺼져 있습니다. |
| `not_found` | 그 항목은 BombVault가 보호하지 않습니다. 먼저 웹 인터페이스에서 추가하세요. MCP는 구성을 만들지 않습니다. |
| 클라이언트가 인증 서버를 찾지 못함 | OAuth 로그인이 꺼져 있거나, 로그인 비밀번호가 없거나, 프록시가 `/.well-known/`을 BombVault까지 통과시키지 않습니다. |
| 동의 페이지가 돌아갈 주소가 등록되지 않았다고 함 | 클라이언트가 등록하지 않은 돌아갈 주소를 보냈습니다. 클라이언트에서 커넥터를 지우고 다시 추가하세요. |
| 로그인한 클라이언트가 `401`을 받음 | 허가가 폐기되었거나, 30일 동안 쓰지 않아 만료되었거나, 공개 주소가 바뀌었습니다. 클라이언트가 다시 로그인합니다. |

컨테이너에 환경 변수 `MCPGODEBUG`를 설정하지 마세요. MCP 라이브러리의 동작을 바꾸며, 값이 잘못되면 로그를 한 줄도 쓰기 전에 BombVault가 시작 단계에서 멈춥니다.
