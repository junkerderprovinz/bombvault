# Зовнішнє копіювання та відновлення

!!! note "Зовнішні копії чекають після перебудови"
    Коли Аварійний майстер або **Знайти резервні копії** відновлюють записи без старих налаштувань, зовнішні копії цих розділів призупиняються, доки не буде підтверджено їхнє типове значення. Див. [Після перебудови](#after-a-rebuild).

Локальні копії захищають від втраченого контейнера чи невдалого оновлення. Зовнішні копії та перевірений набір для відновлення захищають від втрати всієї машини, програми-вимагача чи пожежі. Ця сторінка охоплює місця призначення та зовнішні копії, захист копії від втручання, доказ того, що ви можете відновити дані, спарювання кількох серверів і повернення всього, коли самого BombVault уже немає.

## Зовнішні копії {#off-site-copies}

Залиште швидку локальну копію й додайте одне чи кілька місць призначення поза майданчиком. BombVault копіює туди нові резервні копії командою `restic copy` за принципом «найкращих зусиль», тож збій на зовнішньому боці ніколи не провалює локальну копію. У такому вигляді локальний репозиторій лишається основним, а зовнішній є копією, але основний репозиторій розділу взагалі не мусить бути локальним; про копіювання одразу в S3, rest-server тощо замість копіювання туди див. нижче [Віддалені основні репозиторії](#remote-primary-repositories).

- **Кілька місць призначення для розділу.** Кожен розділ (контейнери, віртуальні машини, flash, автобекап, папки та набори даних ZFS) може копіювати одразу в кілька зовнішніх місць призначення, тож можна, наприклад, паралельно тримати rest-server на машині друга й кошик S3. Картка **Місця призначення за розділами** на сторінці «Місця призначення» вмикає або вимикає кожен рядок від розділу до місця призначення.
- **Коли виконуються копії.** Картка **Копіювати** місця призначення задає **Коли копіювати**: **Після кожної резервної копії** або за власним планом, який збирає резервні копії й копіює у визначений час. У **Налаштування, Розклад, Зовнішні копії за розділами** **Виняток** дає одному розділу власний план копіювання. **Реплікувати зараз** у картці **Зовнішня копія** розділу в **Налаштування, Місця призначення** запускає копіювання на вимогу.
- **Зберігання** задається для кожного місця призначення в **Як довго зберігати**, тож зовнішні копії можна тримати довше як архів. Копія в зовнішньому полі розділу йде за карткою **Зовнішнє зберігання** в **Налаштування, Місця призначення**; залиште все нулями, щоб ніколи автоматично не обрізати зовнішні резервні копії.
- **Обмеження пропускної здатності** (**Зовнішня пропускна здатність** у **Налаштування, Місця призначення** або картка **Копіювати** місця призначення) обмежують швидкість передавання restic, щоб копії не забивали ваш WAN.
- Поки копіювання триває, заголовок стану в огляді каже **Триває копіювання у зовнішнє місце призначення**. Це індикатор активності, а не смуга відсотків, бо `restic copy` не дає машинозчитуваного прогресу.

!!! note "Відновлення з будь-якого місця"
    Кожен запис перелічує свої копії єдиною часовою шкалою по всіх місцях, де копія лежить, на вкладці **Резервні копії**. Копія, скопійована на B2, з'являється один раз, позначена кожним місцем, що її тримає. Відновлення бере перше місце, до якого може дістатися, починаючи з репозиторію, у який записано запис, а для кожної резервної копії ви можете вибрати інше місце. Зовнішні місця призначення читаються лише коли ви натискаєте **Перевірити**, бо перелік хмарного сховища займає час. Видалення в одному місці спершу перевіряє інші й каже, чи це була остання копія.

## Місця призначення {#destinations}

Місце призначення це місце, куди йдуть копії: локальна папка, спільний ресурс, ваш власний сервер чи хмарний сервіс. Його налаштовують один раз, і потім воно обслуговує кожен розділ. Відкрийте **Місця призначення** з їхньої плитки налаштувань або ввімкніть там **Показувати також у бічній панелі**, щоб закріпити.

**Додати місце призначення** відкриває вікно з чотирьох кроків:

1. **Провайдер.** Кожен сервіс перелічено з логотипом, із пошуком угорі праворуч у вікні, групами: сервіси зберігання з кошиками S3 (Backblaze B2, Wasabi, Cloudflare R2, Hetzner Object Storage, Amazon S3 та інші), ваш власний сервер S3 (Garage, SeaweedFS, RustFS, Silo, Ceph, JuiceFS, Versity S3 Gateway), ваш власний сервер і спільні ресурси (rest-server, Hetzner Storage Box, SFTP, SMB, WebDAV, змонтований шлях), хмарне сховище (OneDrive, Google Drive, Dropbox, pCloud, Nextcloud та решта, що підтримує rclone) і приймальні сервери вашої групи. Кожен каже, наскільки добре підходить для копій: хмарні диски гальмують під багатьма запитами, тож перша копія й очищення там тривають довше.
2. **Вхід.** Поля залежать від сервісу: ключ доступу для S3, користувач і пароль для WebDAV та SMB, пароль застосунку там, де двофакторний вхід блокує звичайний, відкритий SSH-ключ BombVault для SFTP і Storage Box або токен для сервісів, що входять через браузер. Для них вікно показує команду `rclone authorize`, яку треба виконати на комп'ютері з браузером; токен, який вона виводить, вставляють у поле. **Перевірити** перевіряє вхід, перш ніж щось збережеться. Потім вікно перелічує папки в місці призначення, з **Нова тека** для створення і вільним місцем там, де сервіс його повідомляє. Порожня папка найнадійніша; BombVault кладе в неї по одній папці на розділ.
3. **Захист.** Вікно прямо каже, що може сервіс. Rest-server у режимі append-only відмовляє у видаленні, і тест на втручання це перевіряє. Кошик S3 може тримати старі версії через версіювання й блокування об'єктів, чого BombVault поки не може перевірити. Хмарний диск узагалі не може відмовити у видаленні: хто потрапив на сервер, потрапляє й до цієї копії. Вмикайте **Захист від видалення (append-only)** лише там, де далекий бік справді відмовляє у видаленні; BombVault тоді ніколи не очищає там. **На випадок аварії** каже, що набір для відновлення містить для цього місця.
4. **Для яких розділів.** Виберіть розділи, що копіюються сюди. Перша копія приносить усю історію. Записи, які вибрали власні місця призначення, нового самі не отримують, і вікно їх називає.

Сервіси S3 працюють через власний бекенд S3 в restic, що й дозволяє застосувати клас зберігання та блокування об'єктів. Кожен інший сервіс працює через rclone, який постачає BombVault, і його remote потім з'являється в картці **Зовнішнє (rclone)** в **Налаштування, Місця призначення**. Експорт налаштувань несе місця призначення; з включеними обліковими даними він несе й їхній вхід.

Тека на цьому сервері всюди називається **Локально**: на сторінках місць призначення, у потоці, на записі та у «Відновленні». Якщо на цьому сервері кілька тек, кожна має власну назву. Місце призначення, яке створює поле зовнішньої копії розділу, називається за своїм місцем: останньою текою його адреси, а якщо її немає, його сервером; коли місце з такою назвою вже є, воно отримує номер. Назва, яку ви дали йому на його сторінці, лишається. Коли поряд стоять два місця з однаковою назвою, кожне додатково несе свій сервер або теку.

Кожне місце призначення має власну сторінку:

- **Підключення** з назвою, перемикачем **Доступний** (вимкнено означає, що BombVault більше сюди не пише, а записи, які копіюються сюди, завершуються чітким повідомленням, а не потрапляють кудись інде), папкою, стисненням, класом зберігання та **За межами майданчика**. **Змінити підключення** перевіряє й зберігає нову адресу чи вхід.
- **Облікові дані**: спільний набір або власний.
- **Захист від видалення**, з **Перевірити захист від видалення зараз** і тим, хто очищає цю копію.
- **Копіювати**: коли копіювати, а також обмеження вивантаження й завантаження.
- **Як довго зберігати**: **Коротко**, **Помірно**, **Довго** або **Власні значення**, з часовою шкалою того, які копії тримає правило. **Питати перед скороченням зберігання** питає, перш ніж коротше правило видалить копії, єдина копія яких тут.
- **Правила за розділами**: власний репозиторій, зберігання чи стиснення розділу в цьому місці. **Змінити правила** відкриває їх, а **Повернути налаштування місця призначення** повертає розділ.
- **Уже під цим місцем призначення**: розділи, чия введена вручну адреса лежить у папці цього місця. Перейняття одного лишає репозиторій там, де він є; вхід, клас зберігання та захист від видалення тоді беруться з місця. BombVault спершу перевіряє, що вхід місця відкриває репозиторій, і відмовляється ставити репозиторій append-only під місце, яке не є append-only.
- Посудина, що показує, наскільки заповнене місце, з позначкою, де воно заповнене, і скільки тижнів лишилося при зростанні останніх тижнів. Місце, що не повідомляє свій розмір, каже **Розмір невідомий**.

Приймальний сервер, який запускає інший екземпляр вашої групи, з'являється серед провайдерів як **З вашої групи**; див. [Приймальний сервер](#receiving-server).

### Переміщення та видалення {#move-remove}

- **Перемістити** забирає копію одного розділу в інше місце призначення з усією історією. Усе лишається на старому місці; BombVault там нічого не видаляє. Переміщення йде у фоні й може тривати довго: близько 9 хвилин на 100 ГБ між локальними дисками, години на повільному каналі. Огляд показує його, поки воно триває.
- **Видалити місце призначення** пропонує два способи. **Видалити місце призначення, залишити копії** припиняє запис туди й лишає копії на місці; ви зможете прочитати їх пізніше в **Відновлення, Зі старої папки резервних копій**. **Видалити місце призначення й стерти резервні копії там** спершу читає, що там збережено, і перелічує це: які копії зникнуть, які з них більше ніде немає і які репозиторії лишаються, бо захист від видалення відмовляє, записи ще копіюються прямо в них, інше місце чи розділ тримає там свої копії або їх не вдалося прочитати. Записи, які втратили б єдину копію, перелічено окремо, і їх буде збережено, доки ви не ввімкнете **Стерти й ці**. Ви підтверджуєте введенням назви місця, а видалення йде у фоні.
- Видалення резервних копій у місці призначення потребує пароля для входу та входу на самому екземплярі. Без пароля місце все одно можна видалити, лише його копії звідси стерти не можна.

## Розміщення для кожного запису {#placement}

Картка **Розклад і місце призначення** на вкладці «Налаштування» запису має ряд кнопок: **Локально** та по одній кнопці на кожне зовнішнє місце призначення розділу. Кнопки, що світяться, отримують копії запису.

- Коли **Локально** світиться, запис пишеться в репозиторій, показаний у **Збережено на**, і копіюється в кожне інше місце, що світиться. Погасіть місце, і воно не отримує нічого нового від цього запису. Лише «Локально» нікуди не копіює, що пасує даним, які вже мають другу копію, наприклад спільному ресурсу, що лежить на NAS.
- Коли **Локально** погашено, запис пишеться прямо в прямий репозиторій першого місця, що світиться, і звідти копіюється в інші. Уперше вікно створює цей прямий репозиторій.
- Одна кнопка лишається ввімкненою, бо копії потрібне місце, куди йти. Щоб залишити запис поза копіюванням, скористайтеся **Не копіювати**.

BombVault ніколи не переміщує копії між репозиторіями. Запис, що йде за своїм розділом, переходить разом з ним, коли змінюється типове значення розділу: його наступна копія потрапляє в нове місце, а наявні копії лишаються там, де були. Місце, вибране на самому записі, фіксується з його першої копії; картка **Репозиторій** на вкладці «Налаштування» називає його. Копії можна змінювати будь-коли. Місце, яке більше не отримує запис, зберігає наявні копії й обрізає їх за власним зберіганням під час наступного зовнішнього запуску розділу. З місць append-only видаляти не можна.

Місце, яке запис залишив, зберігає його копії. На вкладці **Резервні копії** запису та у «Відновленні» воно стоїть як **Лише старіші резервні копії**, відновлення все ще може читати з нього, а очищення там не чіпає ці копії.

**Дотримуватися типового** повертає запис із власним вибором до його розділу. Він спершу питає, каже, куди тоді йтимуть нові копії, і називає, що кожне місце перестає отримувати та що завантажив би наступний запуск.

Під рядом картка каже, куди йде запис і що там насправді є: скільки сайтів його тримають, коли кожне місце бачили востаннє і чи дотримано 3-2-1. Сайт це сервер з оригінальними даними, кожне зовнішнє місце призначення й кожен репозиторій, позначений **За межами майданчика**. BombVault перевіряє копії та сайти; частину 3-2-1 про «два носії» він не перевіряє.

### Типові значення для розділу {#placement-defaults}

Картка **Місця призначення за розділами** на сторінці «Місця призначення» малює типове значення кожного розділу як потік 3-2-1. Кожна лінія від розділу до місця призначення це перемикач, зокрема **Локально**, і так для кожного розділу, також для флешки, наборів даних ZFS і автобекапу. Клацання по лінії чи точці перемикає її одразу, без запитань; пунктирні лінії вимкнені. **Схема / Перемикачі** показує те саме рядами кнопок. Перемикач вирішує, куди йдуть нові копії. Записи без власного вибору та папки проєктів стеків Compose йдуть за ним одразу, тож їхня наступна копія потрапляє в нові місця. Уже збережені копії лишаються там, де були, і з них усе ще можна відновлювати. Flash, набори даних ZFS і автобекап копіюються у свою локальну теку, а звідти копіюються зовні. Їхню лінію до **Локально** теж можна вимкнути: тоді їхні копії йдуть прямо до їхніх зовнішніх місць призначення, а запис ZFS із реплікою й без жодного місця призначення надсилає лише свою репліку.

Коли **Локально** вимкнено, а ввімкнено лише зовнішні місця, розділ копіюється прямо в них, а репозиторій там BombVault вибирає сам. Контейнери, віртуальні машини та набори папок потрапляють у прямий репозиторій першого ввімкненого місця, описаний нижче, і звідти копіюються в інші. Флешка, набори даних ZFS і автобекап пишуть кожну копію в кожне ввімкнене місце, і кожне місце зберігає їх за власним зберіганням.

Розділ, у якого вимкнено всі лінії, показує **Без резервної копії**. Його записи не отримують копій і вважаються незахищеними.

Записи, що на своїй сторінці вибрали власні місця призначення, зберігають їх. Потік каже, скільки їх у розділі, наприклад **2 записи відрізняються**, і веде до них: до вкладки «Налаштування» запису, коли він один, і до списку, що показує, куди копіюється кожен, коли їх кілька. **Дотримуватися типового** там повертає запис.

Нове зовнішнє місце отримує кожен запис, не заданий як «Локально». Вікно, що його додає, каже, скільки це записів і, де відомо, скільки історії.

### Прямі репозиторії

Прямий репозиторій це місце, куди записи копіюються прямо у зовнішнє місце призначення. BombVault кладе його поруч із текою місця, додаючи до назви `-direct`, а коли місце лежить у корені свого бакета, свого remote або користувача rest-server, то в теку всередині нього з назвою розділу, наприклад `containers-direct`. У потоці на сторінці «Місця призначення» він створюється без запитань. Вимкнення «Локально» для одного запису, щоб місце без прямого репозиторію стало його домом, відкриває вікно із запропонованим розташуванням, наприклад `s3:https://s3.eu-central-003.backblazeb2.com/bucket/containers-direct`, і перевірку підключення, що нічого не створює. **Створити і використати** створює репозиторій і спрямовує запис на нього. Прямий репозиторій бере ключ місця, клас зберігання, обмеження, налаштування append-only і зберігання та змінюється разом з ними; картка «Сховища» показує його лише для читання. Коли новий ключ місця не може його відкрити, прямий репозиторій зберігає ключ, який має, і збереження про це каже. Запис на прямому репозиторії копіюється звідти в інші місця, що світяться, але ніколи в місце, якому репозиторій належить. Його знімки несуть мітку `bv:direct`, і кожен інший прохід зберігання їх залишає, тож прямий репозиторій, що втратив зв'язок зі своїм місцем, ніколи не старіє за локальними правилами. B2 досягається через його кінцеву точку S3, з ID ключа й ключем застосунку, введеними як облікові дані S3; ключ, обмежений власною папкою місця, не дістанеться до сусідньої папки, тож обмежте ключ папкою вище.

### Поза приміщенням

Місце призначення чи іменований репозиторій можна позначити **За межами майданчика**. Віддалені починають позначеними; вимкніть це для rest-server у тій самій будівлі. Позначка лише впливає на підрахунок сайтів і 3-2-1 на картках. Вона не змінює жодної копії.

Репліка ZFS це копія поза майданчиком, але не резервна копія з історією. Вона тримає лише знімки, які ви задали, а старі версії й окремі файли все одно беруться з копій. Вона йде з одного сервера ZFS прямо на інший, через SSH на сервер ZFS або на кінцеву точку отримання спареного екземпляра. Група спарювання несе лише запит. Див. [Репліка](zfs-datasets.md#replica).

### Після перебудови {#after-a-rebuild}

Вибір копіювання живе у власних налаштуваннях BombVault. Після перебудови через **Знайти резервні копії** або Аварійний майстер без відновлених налаштувань їх немає, а копіювання всього знову надіслало б на B2 записи, які ви залишили поза нею. Тому зовнішні копії кожного перебудованого розділу призупиняються. Огляд про це каже, а картка **Місця призначення за розділами** пропонує **Підтвердити значення за замовчуванням** з попереднім переглядом того, що скопіює наступний запуск, і з назвами в копіях, які не мають запису, які можна там виключити. Паузу завершує лише підтвердження; імпорт файла налаштувань повертає правила й типові значення, але паузу не завершує.

## Віддалені основні репозиторії {#remote-primary-repositories}

Власний шлях розділу не обмежений локальною текою: спрямуйте його прямо на restic remote (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`, `rclone:remote:bucket/path`), і BombVault копіюватиме прямо туди, без окремої локальної копії та кроку копіювання. Це інша форма, ніж зовнішні копії вище: там локальний репозиторій основний, а зовнішній є його архівом за принципом «найкращих зусиль»; тут віддалений репозиторій **є** основним і єдиною копією, якщо ви не копіюєте цей розділ ще й в інше місце призначення.

Шлях кожного розділу (Контейнери, Віртуальні машини, Flash, Автобекап, Папки, Набори даних ZFS) задається на сторінці місця призначення **Локально**: **Змінити** біля розділу в її картці **Підключення** відкриває вікно з перемикачем **Локально / Віддалено**:

- **Локально** показує звичний огляд тек.
- **Віддалено** замінює його простим полем URL і налаштуваннями підключення, які використовує зовнішнє місце, налаштованими натомість для цього основного. Звідти ви отримуєте:
    - **Перевірку з'єднання** зі справжнім шляхом, перш ніж на нього покладатися.
    - **Обмеження пропускної здатності** (вивантаження/завантаження), щоб запланована копія на віддалений основний не забивала ваш WAN: ті самі прапорці restic `--limit-upload`/`--limit-download`, що й у зовнішніх копіях, застосовані до самої копії.
    - **Захист append-only**, перевірений тим самим активним тестом на втручання (справжня проба DELETE проти далекого боку), що й зовнішні місця. Коли він увімкнений, BombVault відмовляється очищати репозиторій сам, бо за ним немає окремої локальної копії, а облікові дані на цій машині не повинні мати змоги видалити єдину копію.
    - **Сигнал бюджету зростання**, взятий із того самого тренду розміру репозиторію, який картка Сховище й так відстежує.

Нічого з цього не обов'язкове: введений вручну віддалений шлях без збережених налаштувань безпеки копіює без обмежень, придатний до очищення і без сигналу про бюджет. Налаштування безпеки існують на випадок, коли ви хочете захистів, які має зовнішня копія, без окремого місця призначення лише заради них.

!!! note "Облікові дані хмари та REST спільні"
    Віддалений основний автентифікується тими самими спільними хмарними обліковими даними в **Налаштування, Місця призначення**; окремого сховища облікових даних для основних репозиторіїв немає.

### SMB і WebDAV без монтування на хості {#smb-webdav}

Картка **Зовнішнє (rclone)** в **Налаштування, Місця призначення** має форму для спільного ресурсу Windows чи Samba та для сервера WebDAV (Nextcloud, ownCloud, SharePoint чи будь-якого іншого). Заповніть коротку назву, хост і ресурс (SMB) або URL і тип сервера (WebDAV), користувача й пароль, і BombVault напише розділ rclone за вас. rclone сам приховує пароль перед збереженням; додавання з уже наявною назвою замінює той розділ, а не додає другий. **Додати місце призначення** пропонує SMB і WebDAV як провайдерів з тими самими полями.

Форма відповідає готовим розташуванням, наприклад `rclone:nas:backups`. Використовуйте його як шлях розділу чи місце призначення й додайте підпапку, якщо хочете (`rclone:nas:backups/bombvault`). Спільний ресурс це перший сегмент шляху, а не частина назви.

Це кращий шлях, ніж монтувати ресурс в Unraid: restic не радить тримати репозиторій на змонтованому ресурсі CIFS, а тут нічого не монтується. NFS у формі немає, бо ні в restic, ні в rclone немає бекенду NFS; для NFS змонтуйте експорт на хості й користуйтеся ним як локальною текою.

## Захист від видалення (append-only)

Увімкніть захист від видалення для зовнішнього місця призначення, щоб програма-вимагач чи скомпрометований хост не могли видалити чи переписати ваші копії. Далекий бік (`restic/rest-server`, що працює в режимі `--append-only`) **забезпечує** його. BombVault лише **перевіряє** його і ніколи не показує зеленого лише за твердженням конфігурації. Папка на цьому сервері не може відмовити у видаленні, бо хто керує BombVault, керує й папкою, тож локальні місця цього перемикача не пропонують.

Перемикач належить місцю призначення: розділ, що копіює туди, бере його від місця призначення, тому вмикайте його на сторінці місця призначення в розділі **Місця призначення**. Запланована перевірка **Перевірити захист від видалення** запускається лише доти, доки якийсь розділ копіює до місця призначення з увімкненим перемикачем. Інша сторона має запускатися з `--append-only`; в образі `restic/rest-server`, на TrueNAS, як і на будь-якому іншому хості Docker, це вказується у змінній `OPTIONS`.

Найшвидший шлях до копії append-only це спарений BombVault із [приймальним сервером](#receiving-server): він запускає rest-server за вас, у режимі append-only.

!!! note "Успішне видалення в `/locks/` очікуване"
    Append-only не означає, що більше нічого не можна видалити. restic має створювати та знімати власні блокування, тому `/locks/` навмисно лишається доступним для запису й видалення. Знімки та дані за ними, тобто саме те, на що націлений шифрувальник, видалити неможливо. Якщо ви самі перевірите віддалену сторону, успішне видалення в `/locks/` є правильною поведінкою, а не дірою в захисті.

!!! warning "Репозиторії append-only ніколи не очищаються з цієї машини"
    Місце append-only ніколи не очищає старі резервні копії звідси; очищення це справа далекого боку. Задайте для нього **сигнал про бюджет зростання**, щоб вас попередили, поки розмір репозиторію не вийшов з-під контролю.

## Тест на втручання

BombVault періодично доводить гарантію append-only, справді намагаючись видалити щось у зовнішньому репозиторії, націлившись на неіснуючий об'єкт. **Перевірити захист від видалення зараз** на сторінці місця запускає це на вимогу, а **Перевірити захист від видалення** в **Налаштування, Перевірка, Автоматичні перевірки** запускає це за розкладом.

Вимкнена копія не перевіряється, і місце призначення про це повідомляє. Перевірка підключення для неї й далі працює, бо лише читає, тож копію можна перевірити до ввімкнення.

- **Відмовлено** означає захищено.
- **Прийнято** означає не захищено.
- **Непереконливий** результат (сервер недоступний, помилка автентифікації) ніколи не перевертає збережений вердикт.

Справжнє перекидання із захищеного на незахищене спричиняє єдине сповіщення.

## Тренування DR

BombVault пропонує два рівні доказу того, що ваші резервні копії справді можна відновити, а не лише наявні.

- **Тренування перевірки відновлення (локальні).** BombVault періодично запускає `restic check --read-data-subset` (обмежено, ніколи не повне відновлення, що забиває диск). Періодичність живе в **Налаштування, Перевірка, Автоматичні перевірки**, а картка **Перевірити резервні копії** на тій самій плитці показує результат.
- **Пробне відновлення (зовнішнє).** BombVault відновлює справжню ціль із зовнішнього репозиторію в герметичну пісочницю, перевіряє її файл за файлом і байт за байтом, а потім прибирає. Це доводить, що ви можете відновитися із зовнішньої копії, а не лише що репозиторій відповідає.

Картка **Стан захисту** в огляді зводить це за розділом у чотири перевірки: актуальна копія на цьому сервері, зовнішня копія, захист від видалення там і пробне відновлення звідти. Клац на розділі показує подробиці, а картка зеленіє лише на перевірених фактах.

## Спарювання екземплярів {#pairing}

Кілька BombVault працюють разом як одна група: показують стан захисту одне одного, беруть на себе ролі одне для одного й можуть зберігати ключ одне одного. Екземпляр приєднується до групи дванадцятьма словами.

На першому екземплярі відкрийте **Налаштування, Спарювання** і натисніть **Згенерувати фразу**. Три картки кроків показують, як це відбувається. Дванадцять слів з'являються у вікні з кнопкою **Копіювати**. На кожному іншому екземплярі відкрийте те саме місце, натисніть **Ввести фразу** і вставте чи введіть їх, або натисніть **Вставити** у цьому вікні. Слово, якого немає в списку, називається з його позицією під час введення, а останнє слово несе контрольну суму, тож хибно введене чи поміняне слово ловиться, перш ніж щось спарюється. Генеруйте фразу лише на одному екземплярі: два екземпляри, що обидва її згенерують, утворюють дві окремі групи. Якщо за хвилину ніхто не з'являється, сторінка пропонує два виходи: показати слова знову, щоб ввести їх там, або ввести слова іншого екземпляра й приєднатися до його групи за один крок. Спарювання працює без пароля для входу, але задайте його: без нього будь-хто, хто може відкрити вебінтерфейс, може прочитати слова й через групу просити ролі, що видають пароль restic екземплярів у ній. Картка спарювання про це каже, доки пароль не задано. З паролем повторний показ фрази його питає. **Покинути групу** знову виводить екземпляр. Картка **Екземпляри** на сторінці спарювання перелічує учасників групи; картинка про те, хто що для кого робить, лежить на сторінці «Екземпляри».

Будь-хто, хто знає ці слова, може приєднатися до групи, тож ставтеся до них як до пароля.

**Як учасники знаходять одне одного.** Кожен екземпляр дізнається власну адресу в мережі з вашого браузера в мить, коли ви входите, і вона перелічена в **Відомі адреси** в картці **Цей екземпляр** на сторінці спарювання разом з тими, які екземпляр знайшов сам; виправте її там, якщо перед ним стоїть зворотний проксі чи незвичний порт. У тій самій мережі учасники оголошують цю адресу мультикастом і говорять напряму, а там, де мультикаст не може перетнути мережу контейнерів, як-от типовий міст Docker, екземпляр натомість шукає інших у власній підмережі підписаним викликом, на який може відповісти лише учасник групи, тож спарювання все одно завершується за секунди без реле. Якщо нічого не знайдено, **Не можете його знайти?** приймає одну адресу вручну, для іншої підмережі чи нестандартного порту. Екземпляри в різних мережах ідуть через реле, яке вибирають в одному ряду з чотирьох у картці **Реле** на тій самій сторінці; кожна форма має картинку:

- **Реле проєкту** (типове): `parleyport.halleluja.design`, те саме реле, яким користується KnightLoader. Нічого налаштовувати не треба.
- **Власне реле**: контейнер [**ParleyPort**](https://github.com/junkerderprovinz/parleyport) із Unraid Community Apps (також у **Налаштування, Застосунки**). Уведіть його адресу на кожному екземплярі, який має його використовувати.
- **Екземпляр BombVault**: один із ваших екземплярів, уже доступний ззовні, з увімкненим **Працювати як реле**. Цей екземпляр тоді відповідає за `/relay/connect` на власній адресі, за зворотним проксі та сертифікатом, які вже має, і впускає лише вашу групу. Уведіть його адресу на кожному екземплярі, який має його використовувати.
- **Без реле**: учасники знаходять одне одного автоматично лише в одній мережі, і більше ніде.

**Що бачить реле.** Кнопка з тією самою назвою поруч із чотирма формами показує це для вибраної форми. Кожен виклик між учасниками запечатується AES-256-GCM під ключем, виведеним із дванадцяти слів, і цей ключ ніколи не залишає ваші екземпляри. Реле дізнається хеш, що групує з'єднання, для якого екземпляра повідомлення, його розмір і коли воно проходить. Прямий виклик у локальній мережі запечатується так само й до того ж підписується, тож ніщо не залежить від самопідписаного сертифіката, який подає екземпляр. Виклики, що щось видають (відповіді на ролі, пароль restic, входи приймача, депозити ключів), також підписуються ключем учасника, що їх надсилає, закріпленим при першій зустрічі; див. [Модель безпеки](configuration.md#security-model).

**Що подорожує групою.** Стан захисту на сторінці «Екземпляри», запит перевірити один розділ зараз, запити ролей і відповіді на них, пропозиції місць призначення і те, що потрібно приймачу чи стягувачу, щойно його роль дозволено: розташування репозиторіїв іншого екземпляра та його пароль restic. Дані копій ніколи; вони й далі йдуть прямо на бекенди restic. І не APP_KEY: пароль restic відкриває репозиторії цього екземпляра і більше нічого, ні його збережені секрети, ні сеанси, ні коди видачі.

**Записи від часів до спарювання.** Екземпляри, додані токеном флоту, а також отримані репозиторії й джерела стягування, налаштовані за APP_KEY іншого екземпляра, лишаються після оновлення й позначені **Спарувати знову**. Вони продовжують працювати: під час першого запуску BombVault замінює кожен збережений APP_KEY виведеним з нього паролем restic. Спаріть обидва екземпляри, потім відредагуйте запис і виберіть його екземпляр. До цього такі записи стоять у картці **Без екземпляра** на сторінці «Екземпляри».

Єдине місце, де APP_KEY усе ще вводять вручну, це [Зі старої папки резервних копій](#restore-from-another-bombvault-repo), на випадок, коли іншого екземпляра вже немає й він не може відповісти в групі.

## Екземпляри та ролі {#roles}

Сторінка **Екземпляри** (плитка налаштувань, яку можна закріпити на бічній панелі) показує групу як мережу того, хто що для кого робить, з карткою для цього екземпляра й карткою для кожного іншого учасника, телефонів Android і серверів ZFS. **Спарювання** внизу праворуч веде на сторінку спарювання. Які частини ввімкнено, задається в **Налаштування, Екземпляри, Кілька серверів**: **Екземпляри**, **Приймач** і **Стягування**.

Кожна картка показує стан захисту учасника та його ролі плитками. Роль це те, що один екземпляр робить для іншого:

- **Приймач** тримає зовнішні копії цього сервера в rest-server у режимі append-only. Цей сервер надсилає після кожної копії й нічого там видалити не може, навіть якщо хтось його перейме.
- **Стягувач** стягує копії цього сервера за власним розкладом. Цей сервер для цього не мусить бути ввімкнений.
- **Сервер ZFS** приймає репліки ZFS цього сервера. Кожен запис ZFS вибирає його в **Репліка** у своїх налаштуваннях.
- **Зберігач ключа** тримає запечатану копію набору для відновлення цього сервера. Див. [Зберігач ключа](#key-keeper).

Увімкнення ролі надсилає запит, і нічого не починається, доки хтось на іншому екземплярі не натисне **Дозволити**. Запит показано на картці того екземпляра як значок, а його **Деталі** перелічують його з **Дозволити** та **Відхилити**; дозволену роль можна там будь-коли відкликати. Пунктирна лінія в мережі це роль, що ще чекає. Екземпляр на BombVault 9.x не може відповісти на запит, тож роль там активна, щойно ви її вмикаєте, а запит від екземпляра 9.x чекає тут на **Дозволити**.

**Деталі** на картці відкривають решту: отримані репозиторії та джерела стягування цього учасника, пропозиції місць призначення, спостереження, **Видалити** та **Забути ключ**.

## Приймач і стягувач {#receiver}

![Отримана зовнішня копія в деталях екземпляра, що спостерігається лише для читання, з перевіркою цілісності, запущеною на цьому обладнанні.](assets/screenshots/receiver.png)

*Отримана зовнішня копія в деталях екземпляра, що спостерігається лише для читання, з перевіркою цілісності, запущеною на цьому обладнанні.*

На машині, що **отримує** копії append-only від іншого BombVault, отримані репозиторії дають незалежне спостереження лише для читання на приймальному обладнанні, тож тихий збій на далекому кінці не лишається непоміченим. Увімкніть **Приймач** в **Налаштування, Екземпляри**, потім відкрийте **Деталі** відправного екземпляра на сторінці «Екземпляри» й додайте отриманий репозиторій (лише для читання, відкривається паролем restic відправного екземпляра, який він отримує через [групу спарювання](#pairing)). Ви отримуєте:

- **Інвентар за джерелом**, щоб бачити точно, які контейнери, віртуальні машини та набори папок прибули.
- **Востаннє отримано** для кожного джерела, щоб знати, наскільки свіже кожне.
- **Незалежний `restic check`**, що запускається на приймальному обладнанні, тож цілісність перевіряється там, де дані фактично лежать, а не лише на відправнику.
- **Запобіжник:** сповіщення, коли джерело перестає надсилати протягом заданого вами вікна.
- **Сповіщення про цілісність:** сповіщення, коли перевірка на приймальному боці не проходить.

Приймач строго лише для читання. Він ніколи не пише в отриманий репозиторій, тож ніколи не може порушити гарантію append-only, на яку спирається відправник.

Стягувач працює навпаки: з увімкненим **Стягування** екземпляр читає копії іншого учасника у власний репозиторій за власним розкладом. Його джерела також стоять у деталях цього учасника.

### Приймальний сервер {#receiving-server}

Приймальна машина також може запускати rest-server, на який копіюють інші. Він налаштовується, коли ви вперше дозволяєте запит **Приймач**, що його потребує: вікно каже, що серверу потрібен приймальний сервер, і просить папку на спільному ресурсі, з **Нова тека** для створення, та порт (8000, якщо його не займає інший контейнер). Далі BombVault:

1. відмовляється, якщо контейнер з іменем `rest-server` уже існує або порт зайнятий іншим контейнером;
2. завантажує `restic/rest-server` і запускає його через сокет Docker у режимі append-only з приватними репозиторіями та файлом логінів у теці;
3. записує його шаблон Unraid на flash-накопичувач, тож контейнер залишається придатним до редагування на вкладці Docker, або пропонує шаблон на завантаження, коли flash-накопичувач недоступний;
4. запускає проти нього тест на втручання і показує, чи відмовляє він у видаленні.

Екземпляри вашої групи тоді знаходять сервер серед провайдерів у **З вашої групи** під назвою приймальної машини, а роль **Приймач** пропонує його як безпечний вибір. Кожен екземпляр отримує власний логін, коли вперше використовує сервер, і пише там лише у власну папку. З увімкненим **Приймач** у **Налаштування, Екземпляри** **Приймальний сервер** на картці цього екземпляра знову відкриває сервер. Його вікно перелічує логіни в **Партнери з логіном**, а **Відкликати логін** забирає один; те, що цей екземпляр уже скопіював, лишається в папці. Налаштування також створює один **Логін поза групою**, пароль якого вікно показує один раз.

Екземпляр, який дістається до приймальної машини лише через реле, не може користуватися сервером, бо реле не несе копій. Спершу додайте адресу приймальної машини на сторінці спарювання. Коли BombVault працює на власній IP-адресі (наприклад на br0), заповніть **Адреса для партнерів (необов'язково)**, бо сервер слухає на адресі хоста.

## Повний приклад: дві машини Unraid, від початку до кінця

Усе вище описує частини. Це одне повне налаштування, бо частини легше скласти, коли побачите їх складеними один раз.

Дві машини: **TOWER** запускає контейнери й надсилає копії; **VAULT** їх приймає й забезпечує append-only. Підставте власні назви, адреси та шляхи спільних ресурсів.

**1. Спаріть дві машини.** На TOWER відкрийте **Налаштування, Спарювання**, натисніть **Згенерувати фразу** і введіть дванадцять слів на VAULT у **Ввести фразу**. Спершу задайте пароль для входу на обох.

**2. На TOWER попросіть VAULT стати приймачем.** На сторінці «Екземпляри» увімкніть **Приймач** на картці VAULT, виберіть розділи й **Приймальний сервер VAULT** як місце та надішліть запит.

**3. На VAULT дозвольте.** Сторінка «Екземпляри» VAULT показує запит на картці TOWER. Натисніть **Дозволити**. Уперше VAULT просить папку для свого приймального сервера, наприклад `user/appdata/rest-server`, запускає rest-server у режимі append-only і запускає проти нього тест на втручання.

**4. Знову на TOWER.** Відтоді TOWER копіює на VAULT після кожної копії, а нове місце призначення з'являється на сторінці «Місця призначення» TOWER із захистом від видалення.

Що відповідає тест на втручання:

| Результат | Що сталося |
| --- | --- |
| **захищено** | VAULT відмовив у видаленні. Це єдиний успішний стан. |
| **не захищено** | VAULT прийняв видалення. `--append-only` відсутній або був видалений. |
| **невизначено** | Ні те, ні інше. Зазвичай адреса не та, яку використовує сам restic, або змінилися облікові дані. Нічого не записується і жоден сигнал не подається. |

**5. За бажанням стежте за тим, що надходить.** Увімкніть **Приймач** у **Налаштування, Екземпляри** на VAULT, відкрийте **Деталі** TOWER і додайте отриманий репозиторій. VAULT отримує пароль restic від TOWER через групу; ніхто не вводить ключ.

**6. Зробіть це взаємним.** Повторіть кроки в іншому напрямку: VAULT просить TOWER стати його приймачем. Кожна машина тоді забезпечує append-only для іншої, і жодна не може видалити копії іншої.

Rest-server, який ви запускаєте вручну, теж підходить: додайте його через **Додати місце призначення** як rest-server, з користувачем і паролем з його `.htpasswd`, і ввімкніть захист від видалення. Лишіть `--append-only` у його опціях; без нього далекий бік знову звичайний спільний ресурс.

!!! warning "Локальний шлях це шлях усередині контейнера"
    Там, де BombVault просить папку на цьому сервері, вводьте її відносно монтування хоста, наприклад `user/appdata/rest-server/bombvault-containers`, а не `/mnt/user/appdata/...`. BombVault працює в контейнері, де `/mnt` хоста змонтовано в іншому місці; абсолютного шляху хоста всередині немає. Якщо ви вставите такий, BombVault підкаже відносний шлях, який слід використати.

## Аварійний майстер {#emergency}

**Аварійний майстер** повертає сервер, якого вже немає або який налаштували заново. Він починається на сторінці «Відновлення» в **Аварія** і з **Відновити з резервної копії** на вітальній сторінці нового встановлення. Він виконується в чотири кроки: **Доступ**, **Налаштування**, **Вибір** і **Відновлення**.

1. **Доступ.** Покажіть BombVault ключ старих копій одним із трьох способів:
    - **Завантажити набір для відновлення**: файл, який ви завантажили під час налаштування. Він містить ключ і кожне місце призначення, а решту BombVault заповнює з нього. Набір, запечатаний age, просить ідентичність, для якої запечатаний; її використовують один раз і не зберігають.
    - **Через групу**: екземпляр вашої групи тримає ключ як депозит. Вам потрібні дванадцять слів групи, ваш код видачі та людина на тому екземплярі. Див. [Зберігач ключа](#key-keeper).
    - **Ввести ключ**: `APP_KEY` старого сервера і де лежать його копії.

    BombVault тоді пробує ключ на кожному місці призначення й каже для кожного, чи воно читається, не знайдене, заблоковане іншим ключем, недосяжне чи досі без входу. Нічого ще не збережено, а ключ лишається в пам'яті обмежений час. **Перейняти ключ** змушує цей сервер відтепер писати копії цим ключем; **Скасувати перейняття** повертає його власний ключ, доки не виконається перша копія. Сервер, що вже має власні копії, відмовляє в перейнятті й відсилає до [Зі старої папки резервних копій](#restore-from-another-bombvault-repo). **Зберегти облікові дані** зберігає входи, які набір несе для віддалених місць призначення, і питає, перш ніж замінити входи, які цей сервер уже має.
2. **Налаштування.** **Повернути налаштування** відновлює власні налаштування BombVault з найновішого автобекапу: місця призначення, облікові дані, розклади та правила. BombVault перезапускається, щоб їх застосувати, через сокет Docker, тож жива база налаштувань ніколи не перезаписується під відкритим дескриптором, а майстер після цього продовжує сам. Вхід цього сервера лишається: ви й далі входите тим паролем, яким користуєтеся зараз. Секрети, які зберігав старий сервер і які не можна перейняти, перелічено, щоб ви могли ввести їх знову.
3. **Вибір.** BombVault переглядає ваші копії та перелічує знайдені контейнери, віртуальні машини, набори папок і набори даних ZFS. Найновішу резервну копію усюди вибрано наперед. Те, що цей сервер ще має, починається вимкненим, бо відновлення його замінило б. Набори папок після перебудови вже не знають, звідки вони, тож потрапляють у вибрану вами папку.
4. **Відновлення.** Усе вибране повертається за один раз, залишене зупиненим, якщо ви хочете запустити кожен контейнер і віртуальну машину самі, що найнадійніше після повної втрати. Потім завантажте новий набір для відновлення: старий належить попередньому встановленню.

!!! tip "Планова міграція проти катастрофи"
    Аварійний майстер відновлює власні налаштування BombVault з копії. Для *запланованого* переходу на нову машину можна натомість перенести конфігурацію напряму карткою **Експорт / імпорт налаштувань** (портативний файл JSON). Див. [Конфігурація](configuration.md#portable-settings-export-and-import).

### Зі старої папки резервних копій {#restore-from-another-bombvault-repo}

**Зі старої папки резервних копій** у **Інші джерела** на сторінці «Відновлення» відкриває репозиторій *іншого* екземпляра BombVault (спільний ресурс, змонтований у `/mnt`, або віддалену адресу) з набором для відновлення цього екземпляра чи його введеним `APP_KEY`, у одноразовому сеансі лише для читання. Переглядайте контейнери, віртуальні машини, набори папок і набори даних ZFS, що там збережені, виберіть резервну копію і відновіть її, і відновлений об'єкт стане звичайним локальним контейнером, віртуальною машиною чи набором папок. У інший репозиторій ніколи нічого не пишеться, а ваші власні налаштування копіювання лишаються недоторканими (сеанс живе в пам'яті й закінчується сам). Перенесення контейнера з сервера A на сервер B не означає перенаправлення ваших налаштувань і повернення їх згодом. Це вікно одноразове: воно відкриває сеанс, відновлює вибране й забуває інший екземпляр. Якщо вам потрібна постійна домовленість, за якої ця машина за розкладом стягує резервні копії іншого екземпляра у власний репозиторій, це роль **Стягувач** на сторінці «Екземпляри».

Під рядком контейнера, чиєї мережі немає на цьому сервері, наприклад мережі `br0` з Unraid на звичайному Docker-хості, з'являється вибір мережі. BombVault створює його у вибраній мережі разом з іншими мережами. Фіксована IP-адреса та MAC-адреса належали старій мережі й відкидаються, тому їх видає нова мережа.

## Зберігач ключа {#key-keeper}

Зберігач ключа це екземпляр вашої групи, що тримає запечатану копію набору для відновлення цього сервера. Сам він копію відкрити не може. Якщо цей сервер колись буде втрачено, нове встановлення, що приєднується до вашої групи, просить копію в зберігача й відкриває її вашим кодом видачі.

1. На сторінці «Екземпляри» ввімкніть **Зберігач ключа** на картці екземпляра, який має його тримати, і виберіть **Передати на зберігання**. Для передачі потрібен пароль для входу.
2. Цей сервер один раз показує **Код видачі**: двадцять літер і цифр у чотирьох групах по п'ять. Запишіть його й підтвердіть **Код записано**. Цей сервер не зберігає код, лише те, що потрібно, щоб запечатати для нього депозит.
3. Зберігач тепер тримає депозит, і цей сервер поновлює його, коли набір змінюється. **Депозит ключа** на картці цього екземпляра перелічує **Депозит цього сервера** з кожним зберігачем і його станом, а також **Депозити, які зберігає цей сервер** для інших. **Створити новий код** замінює код; кожен зберігач переходить на новий, коли отримує новий депозит.

Того дня вам потрібні три речі: дванадцять слів вашої групи, код видачі та доступ до інтерфейсу зберігача, де хтось має натиснути **Дозволити**. В Аварійному майстрі виберіть **Через групу**, виберіть депозит, попросіть його й введіть код видачі. Код використовується на новому сервері й не надсилається зберігачу. На зберігачі запит показано в **Депозит ключа** з тим, хто просить, чи цей екземпляр бачили там раніше і як часто він просив; **Дозволити** видає запечатану копію, і дозвіл потребує пароля для входу. Нове встановлення має 30 хвилин, щоб забрати її після «Дозволити», запит, на який ніхто не відповів, закінчується за добу, а екземпляр, що просить надто часто, мусить чекати годину.

Без коду ніхто не може відкрити копію, зберігач теж. Якщо код втрачено, створіть новий, поки цей сервер ще працює; якщо сервера вже немає, набір для відновлення та введений APP_KEY усе ще працюють. Зберігач може видалити депозит у будь-який час, і власник тоді мусить попросити знову.

## Набір для відновлення {#recovery-kit}

Це та частина, яка робить аварійне відновлення можливим навіть коли немає запущеного BombVault.

**Завантажити набір для відновлення** в картці **На випадок аварії** в **Налаштування, Відновлення** дає вам **ключ**, **виведений пароль restic**, кожне **місце призначення** з репозиторієм кожного розділу, входи, які потрібні новому встановленню, щоб їх досягти, і **точні команди restic**, щоб відновлювати прямо через restic CLI на будь-якій машині. Потрібен пароль для входу. Набір друкує ключ і з вимкненим шифруванням, бо визначення контейнерів і віртуальних машин завжди запечатано ним. Після перейняття він друкує перейнятий ключ резервних копій і APP_KEY цього сервера, який новому встановленню потрібен лише для повернення налаштувань. Картка **Збережіть свій набір для відновлення** в огляді нагадує, доки ви його не збережете.

!!! danger "Зберігайте набір для відновлення поза сервером"
    Набір містить секрет, що розшифровує ваші копії. Зберігайте його в безпечному місці окремо від сервера (менеджер паролів, друкована копія в сейфі). Якщо ви втратите і BombVault, і `APP_KEY` без набору для відновлення і без депозиту ключа, ваші зашифровані копії не відновити.

!!! warning "Найновіший знімок не завжди той, який слід відновлювати"
    Починаючи з restic 0.17, `restic snapshots` показує розмір кожного знімка. Після втрати даних найновішим знімком може бути спорожнілий, тож не відновлюйте знімок, набагато менший за попередні. Після програми-вимагача це може бути зашифрований знімок звичайного розміру. Якщо BombVault ще працює, спершу перевірте його сторінку «Аномалії»: вона називає останню справну копію, а вікно відновлення вибирає її наперед. Відновленню не потрібні жодні дані BombVault про аномалії, а пауза зберігання лише тримає більше знімків.

### Запечатування набору

Якщо ви ввімкнули **Шифрувати експорти за допомогою age** в **Налаштування, Система**, набір також запечатується ним і завантажується як `bombvault-recovery-kit.md.age`. Він броньований ASCII, а не двійковий, тож це все ще звичайний текст: вставлення в менеджер паролів чи друк працюють так само, як раніше, просто вміст нечитабельний без вашого ключа.

!!! warning "Не зберігайте ключ age всередині набору"
    Щоб відкрити запечатаний набір, потрібен ваш **приватний** ключ age. Зберігайте його там, де він не залежить від самого набору, інакше відновлювати доведеться дві речі замість однієї. Запечатування варте того, коли набір зберігається там, що ви не повністю контролюєте (спільний менеджер паролів, хмарні нотатки, роздруківка в офісі); набір у вашому власному сейфі вже захищений сейфом.

    З увімкненим шифруванням і без налаштованого придатного отримувача завантаження просто відхиляється. BombVault ніколи не відкочується до видачі головного ключа у відкритому вигляді.

### Якщо набору немає під рукою

Пароль ніде не зберігається, він **обчислюється** з ключа копій, тож ви можете відтворити його самі, маючи лише ключ і оболонку:

```sh
printf 'bombvault:restic-repo' \
```

Це HMAC-SHA256 над фіксованим рядком `bombvault:restic-repo`, з ключем у вигляді сирих байтів шістнадцяткового `APP_KEY`, виведений як 64 шістнадцяткові символи в нижньому регістрі. Те саме значення є в наборі, перелічене як виведений пароль restic; це на той день, коли набору немає поруч. На сервері, що перейняв копії іншого, використовуйте перейнятий ключ резервних копій, який є старим APP_KEY того сервера.

!!! warning "Для отриманого репозиторію беріть ключ ВІДПРАВНОГО примірника"
    Репозиторій, що потрапив сюди через зовнішню копію, створила машина, яка його надіслала, з **її** ключем. Виведення з ключа приймальної машини дає пароль, який restic відхилить, що читається точно як пошкоджений репозиторій, але ним не є. Це звичайна причина, чому `restic check` на отриманому репозиторії знову й знову просить пароль.

Оскільки визначення для відновлення живуть **усередині** кожного репозиторію (`<repo>/def`, `<repo>/vm-def`), скопійована тека репозиторію повністю самодостатня, тож набір плюс репозиторій, це все, що потрібно для відновлення на голому залізі.

## Як дістати дамп бази даних назад {#database-dumps}

Дамп бази даних це власна точка відновлення в репозиторії контейнерів з міткою `dbdump:<container>`, що тримає єдиний файл `/dbdump/<container>.sql`. BombVault перелічує, завантажує й імпортує їх на вкладці **Резервні копії** контейнера; нижче ті самі кроки лише через restic, на той день, коли BombVault немає.

```sh
restic -r <repo> snapshots --tag dbdump:<container>
restic -r <repo> dump --tag dbdump:<container> latest /dbdump/<container>.sql > <container>.sql
```

Мітки `dbversion:` і `dbname:` на кожному дампі кажуть, з якої версії сервера його взято і які бази він містить. Повний файл закінчується рядком `-- PostgreSQL database cluster dump complete` або `-- Dump completed`.

Імпортуйте його в контейнер тієї самої чи новішої версії (PostgreSQL) або тієї самої основної версії (MySQL і MariaDB), один раз запущений із порожньою текою даних, щоб він розгорнувся. Клієнт бази даних на хості не потрібен, він є в контейнері:

```sh
docker exec -i <container> sh -c 'exec psql -X -U "${POSTGRES_USER:-postgres}" -d postgres' < <container>.sql
docker exec -i <container> sh -c 'exec mariadb -uroot -p"$MARIADB_ROOT_PASSWORD"' < <container>.sql
docker exec -i <container> sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < <container>.sql
```

Для однієї бази з повного дампа MySQL і MariaDB приймають `--one-database <name>` у команді клієнта. У дампі PostgreSQL на кожну базу припадає свій розділ, що починається рядком `\connect <name>`: скопіюйте потрібний розділ в окремий файл і імпортуйте його з `-d <name>` після створення бази.

!!! warning "Дамп, знятий під root, несе із собою користувачів сервера"
    Повний дамп MySQL або MariaDB, знятий під root, містить системну базу `mysql`, тож його імпорт замінює облікові записи нового сервера, разом із паролем root, на записи з дампа. У PostgreSQL повідомлення `role ... already exists` про користувача, якого створив сам контейнер, очікуване і безпечне.
