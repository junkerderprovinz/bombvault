# Configuración

Esta página trata de las variables de entorno del contenedor, los montajes que aporta la plantilla, el modelo de seguridad, la copia de VMs por SSH y la configuración de las copias externas. Dónde van las copias se configura dentro de la app como **destinos**, no con variables de entorno.

## Variables de entorno {#environment-variables}

| Variable | Obligatoria | Descripción |
|---|---|---|
| `APP_KEY` | **Sí** | Secreto hexadecimal de 32 bytes (64 caracteres hex) del que se deriva la contraseña del repositorio restic. Genéralo con `openssl rand -hex 32`. Guárdalo bien: perderlo deja las copias cifradas irrecuperables. |
| `LIBVIRT_HOST` | Para VMs y conjuntos de datos ZFS | Host Unraid al que se llega por SSH para copiar VMs y conjuntos de datos ZFS (campo de la plantilla **SSH del host: Dirección**, por defecto `host.docker.internal`). La plantilla rellena de antemano el marcador `192.168.x.x`, que cuenta como no definido. Usa la IP de LAN de tu Unraid, necesaria en una red personalizada `br0.x`. Cuando `host.docker.internal` no se resuelve, como en una app de TrueNAS, y `LIBVIRT_URI` tampoco nombra ningún host, BombVault usa la puerta de enlace predeterminada del contenedor y el registro de arranque la nombra. |
| `LIBVIRT_SSH_PORT` | No | Puerto SSH del host para copiar VMs y conjuntos de datos ZFS (campo de la plantilla **SSH del host: Puerto**, por defecto `22`). |
| `LIBVIRT_SSH_USER` | No | Usuario SSH en el host para copiar VMs y conjuntos de datos ZFS (campo de la plantilla **SSH del host: Usuario**, por defecto `root`). |
| `LIBVIRT_URI` | No | URI de conexión completa de libvirt, usada **tal cual** en lugar de construir una a partir de las tres variables `LIBVIRT_*` anteriores (que entonces se ignoran para la cadena de conexión). Sin definir por defecto. Hace falta en TrueNAS Scale, cuyo libvirtd escucha en un socket no estándar que la forma construida no puede expresar: `qemu+ssh://<user>@<truenas-host>/system?socket=/run/truenas_libvirt/libvirt-sock`. Consulta la [guía de copias de VMs](vm-backup-ssh-setup.md#truenas-scale). Cuando es una URI `qemu+ssh://`, cada una de `LIBVIRT_HOST`, `LIBVIRT_SSH_USER` y `LIBVIRT_SSH_PORT` que no esté definida se toma de ella, también para los propios comandos SSH de BombVault (transferencia de NVRAM, conjuntos de datos ZFS). |
| `PORT` | No | Puerto HTTP (por defecto `3000`. Solo se usa con `HTTP_ONLY=true`). |
| `HTTPS_PORT` | No | Puerto HTTPS (por defecto `3443`. La plantilla lo publica 1:1, así que la interfaz web responde en `https://<ip>:3443`). |
| `HTTP_ONLY` | No | Pon `true` para desactivar el listener HTTPS autofirmado y servir solo HTTP sin cifrar (para usar detrás de un proxy inverso que termine TLS). |
| `BIND_HOST` | No | Dirección en la que escucha la interfaz web (por defecto `0.0.0.0`, todas las interfaces). Déjala sin definir en el contenedor, cuyos puertos publicados necesitan todas las interfaces. `127.0.0.1` sirve para una ejecución fuera de Docker. La comprobación de salud pregunta a la misma dirección. |
| `TRUSTED_PROXY` | No | Direcciones o rangos CIDR separados por comas del proxy inverso delante de BombVault (por ejemplo `192.168.20.11` o `10.0.0.0/8`). Solo de esos saltos se cree `X-Forwarded-For`, y entonces el limitador de acceso cuenta los fallos por cliente real en lugar de meter a todos los de detrás del proxy en un mismo cubo. Sin definir (el valor por defecto) no se fía de nadie: una cabecera creída sin condiciones dejaría que cualquier llamante eligiera su propio cubo. |
| `HOST_SOURCE_ROOT` | No | La ruta del host montada como **Host Data** (por defecto `/mnt`). BombVault traduce los orígenes de los bind mount que informa Docker a rutas bajo este montaje. Cámbiala solo si montaste otra raíz del host. |
| `HOST_MOUNT_ROOT` | No | Dónde se monta Host Data dentro del contenedor (por defecto `/host/user`). En TrueNAS Host Data se monta en su propia ruta del host, así que esta y `HOST_SOURCE_ROOT` nombran esa ruta, por ejemplo `/mnt/tank` (consulta [TrueNAS SCALE](getting-started.md#truenas)). |
| `DATA_ROOT_SEGMENTS` | No | Nombres de segmentos de ruta separados por comas que marcan el origen de un bind mount como datos a copiar (por defecto `appdata`, según la convención de Unraid `/mnt/user/appdata/<container>`). El bind mount de un contenedor se selecciona automáticamente para la copia cuando CUALQUIER segmento de la lista aparece como segmento completo de la ruta de su origen en el host. Por ejemplo `DATA_ROOT_SEGMENTS=appdata,config` también recoge un bind `.../config`. La coincidencia ignora mayúsculas y minúsculas, así que el valor por defecto también cubre `/DATA/AppData/<container>` de ZimaOS. Consulta [Detección del origen de la copia](#backup-source-detection) para las otras formas, siempre activas, de encontrar la carpeta de datos de un contenedor. |
| `PLATFORM` | No | Fuerza la plataforma en la que BombVault se considera en ejecución, en lugar de detectarla: `unraid`, `generic` o `truenas` (sin definir por defecto: detecta Unraid buscando su marcador `dockerMan` bajo el montaje del flash, y si no `generic`. Un valor no reconocido también vuelve a `generic`, y se registra). Defínela explícitamente en un host Docker genérico o en TrueNAS Scale en vez de confiar en la detección exclusiva de Unraid. El archivo compose genérico lo hace. Cambia la convención de reserva de appdata, los destinos de restauración predeterminados entre instancias y si se intentan siquiera los pasos de notificación y plugin acompañante exclusivos de Unraid (consulta `internal/platform`). |
| `BOMBVAULT_SELF_CONTAINER` | No | El nombre del propio contenedor de BombVault, para que nunca se copie (y por tanto se detenga) a sí mismo. |
| `BACKUP_MAX_HOURS` | No | Horas máximas de reloj que una ejecución de copia puede mantener el bloqueo de su sección antes de cancelarse a la fuerza (una protección para que una ejecución atascada no pueda bloquear la sección para siempre). Vacío (el valor por defecto) usa `48`. Súbelo para copias en la nube muy grandes o lentas (una ejecución cancelada en el límite falla con `context deadline exceeded`). Pon `0` para desactivar el límite por completo. Una poda se mantiene bajo el mismo límite, y una comprobación o una poda se ejecuta mientras restic siga informando de progreso. |
| `BACKUP_STALL_HOURS` | No | Horas que una copia puede estar **sin ningún progreso** antes de cancelarse. Vacío (el valor por defecto) usa `2`. Pon `0` para no cancelar nunca por estancamiento. Es la más fina de las dos protecciones y normalmente la que salta: vigila si todavía pasa algo en lugar de cuánto ha durado la ejecución, así que una copia lenta pero sana de varios terabytes se deja en paz mientras una atascada en un recurso compartido que no responde se detiene en horas en lugar de días. Se registra un aviso tras 30 minutos de silencio, antes de cancelar nada. El escaneo cuenta como progreso: restic no escribe bytes mientras recorre un árbol grande, y esa fase se vigila por sus totales de archivos y bytes en lugar de por los bytes escritos. Las dos variables son independientes, y `BACKUP_MAX_HOURS` sigue acotando las fases posteriores a la copia en sí (retención, estadísticas, copia externa), donde no hay contadores que vigilar. |
| `DB_DUMP_MAX_HOURS` | No | Horas que puede ejecutarse un volcado automático de base de datos antes de detenerse. Vacío (el valor por defecto) usa `6`. Los valores permitidos son de `1` a `48`, y el límite se mantiene una hora por debajo de `BACKUP_MAX_HOURS` (a la mitad cuando esta es inferior a dos horas), de modo que un volcado largo se corta por su propio límite y se informa como tal en lugar de arrastrar consigo a la copia. Un volcado sin progreso se detiene antes, tras `BACKUP_STALL_HOURS`. Un volcado detenido falla por sí solo y la copia del contenedor continúa. En Unraid, añádela al contenedor de BombVault con **Add another Path, Port, Variable**. |
| `TZ` | No | Zona horaria del planificador (por ejemplo `Europe/Berlin`). **Si la dejas sin definir, todos los calendarios se ejecutan en UTC**: uno fijado a las 02:30 se dispara entonces a las 02:30 UTC y no según tu reloj. En Unraid nunca la defines tú: el sistema pasa su propia zona horaria a cada contenedor. El registro de arranque dice a qué zona se resolvió. Una zona con horario de verano se salta una ejecución en primavera y ejecuta una dos veces en otoño, mientras que UTC no hace ninguna de las dos cosas pero se desfasa una hora respecto a tu reloj dos veces al año. |
| `DATA_DIR` | No | Dónde guarda BombVault su base de datos, claves y cachés (por defecto `/config`). Déjala como está en el contenedor. Importa cuando ejecutas el binario fuera de Docker. |
| `FLASH_DIR`, `FLASH_TEMPLATES_DIR` | No | Dónde se montan dentro del contenedor la unidad flash y sus plantillas de Docker (por defecto `/host/boot` y `/host/boot/config/plugins/dockerMan/templates-user`). Siguen el montaje `/boot` de la plantilla, así que déjalas sin definir. |

## Montajes {#mounts}

Monta el socket de Docker, el flash (`/boot`) y la raíz de **Host Data** (`/mnt`) como se muestra en la plantilla de CA. Los *orígenes* y los *destinos* de las copias viven ambos bajo Host Data, y se monta como **slave** para que un recurso remoto que se monte después de que arranque el contenedor (por ejemplo bajo `/mnt/remotes`) se vuelva visible sin reiniciar.

En TrueNAS, Host Data es una ruta de conjunto de datos como `/mnt/tank`, nunca un ixVolume. Los datos que una app guarda en un ixVolume quedan fuera y no se copian. Consulta [TrueNAS SCALE](getting-started.md#truenas).

Las copias de conjuntos de datos ZFS necesitan también este modo: el host monta la instantánea de un conjunto de datos solo después de que el contenedor haya arrancado. Consulta [Conjuntos de datos ZFS](zfs-datasets.md).

Los repositorios locales usan por defecto `/mnt/user/bombvault/{container,vms,flash,config,files,zfs}`, creados en la primera copia. Son las **carpetas propias** de las secciones y forman el destino **Local**. En su página, en **Destinos**, la tarjeta **Conexión** cambia la carpeta de cada sección.

La carpeta propia de una sección también puede estar en un destino que ya tienes, como un NAS o un bucket S3: **Usar como carpeta propia** en la página de ese destino la mueve allí y antes dice qué pasa con las copias ya hechas. Consulta [La carpeta propia de una sección](offsite-recovery.md#own-folder).

Las carpetas de los repositorios locales se quedan en los modos `0755` y `0644`, para que un usuario de sincronización sin privilegios de root por SMB no quede fuera, y los repositorios están cifrados, así que esto no expone nada. Las definiciones de recuperación viven dentro de cada repositorio, así que una carpeta copiada está completa por sí sola. El repositorio de la autocopia sigue siendo legible solo para root.

!!! note "Comprobación de la integración con el host"
    La tarjeta **Integración con el host** del resumen (añádela en **Personalizar**) sondea cada montaje y cada CLI (socket de Docker, libvirt, restic, qemu-img, rclone) e informa de lo que falte.

## Detección del origen de la copia {#backup-source-detection}

Para cada contenedor, BombVault selecciona automáticamente qué bind mounts y volúmenes con nombre copiar. Una ruta se recoge cuando se cumple cualquiera de estas condiciones (siempre puedes cambiar el resultado en la tarjeta **Carpetas a copiar** de la pestaña Ajustes del contenedor):

- **Coincidencia de segmento de raíz de datos:** el origen en el host del bind contiene uno de los segmentos de `DATA_ROOT_SEGMENTS` como componente completo de la ruta (por defecto solo `appdata`).
- **Los volúmenes con nombre de Docker** se incluyen siempre, ya que no tienen un equivalente desechable y no hay nada que filtrar, **pero solo cuando la ruta real de almacenamiento del volumen en el host es alcanzable a través del montaje de Host Data**, igual que cualquier otra ruta del host que copia BombVault. El controlador de volúmenes local predeterminado de Docker guarda un volumen bajo la raíz de datos del propio demonio (`/var/lib/docker/volumes/<name>/_data` salvo que la hayas personalizado. Compruébalo con `docker info -f '{{.DockerRootDir}}'`), que no queda cubierta por el montaje estrecho de un único directorio de Host Data que usa por defecto el `docker-compose.yml` genérico. Un volumen inalcanzable se omite en silencio, no es un error. Para copiar de verdad volúmenes con nombre en un host genérico, apunta Host Data (y `HOST_SOURCE_ROOT`) a un ancestro común que cubra también la raíz de datos de Docker. El comentario de Host Data del archivo compose explica el compromiso (Unraid lo esquiva montando todo `/mnt`, su propia convención universal de nivel superior, por la misma razón).
- **Directorio del proyecto Docker Compose:** si el contenedor lleva la etiqueta estándar `com.docker.compose.project.working_dir` (la pone automáticamente `docker compose up`), ese directorio también se añade, tanto si algún bind coincidió con un segmento de raíz de datos como si no.
- **Etiqueta `bombvault.data` para forzar:** pon la etiqueta `bombvault.data=true` en un contenedor para incluir todos sus bind mounts, para una disposición que ninguna de las dos convenciones anteriores capta (por ejemplo un único bind `/srv/plex/config` sin proyecto Compose). Cualquier valor no vacío distinto de `false` cuenta como verdadero. Una etiqueta ausente o `bombvault.data=false` no cambia nada.
- **Etiqueta `bombvault.dbdump`:** pon `bombvault.dbdump=false` en un contenedor para desactivar su volcado automático de base de datos (`0`, `no` y `off` hacen lo mismo), o nombra el motor (`postgres`, `mysql`, `mariadb`) para volcar un contenedor que BombVault no reconoce por sí solo. La etiqueta prevalece sobre el interruptor de la tarjeta **Base de datos** de la pestaña Ajustes del contenedor, que es la manera de hacerlo en Unraid.

## Modelo de seguridad {#security-model}

!!! warning "Control equivalente a root sobre el host"
    A través del socket de Docker, BombVault puede detener, eliminar y recrear contenedores y leer y escribir appdata, y para la copia de VMs inicia sesión en el host por SSH (`qemu+ssh://`, root por defecto) para ejecutar `virsh`. Cualquiera que pueda llegar a su interfaz web tiene en la práctica root en el host.

### Inicio de sesión {#login}

- **Protección opcional con contraseña** (tarjeta **Contraseña** en **Ajustes, Seguridad**): pon una contraseña para exigir inicio de sesión, bórrala para desactivarlo. Desactivado por defecto para uso en una LAN de confianza. La contraseña se guarda con Argon2id sobre un pepper con clave derivada de `APP_KEY`, así que un `/config` copiado no vale nada sin la clave y es lento de atacar con ella. Una contraseña nueva necesita al menos 12 caracteres. Una más corta ya existente sigue funcionando hasta que se cambie. Las sesiones están firmadas (HMAC derivado de `APP_KEY`) y cambiar la contraseña las invalida. Los inicios de sesión se limitan a cinco fallos por minuto y cliente. Cambiar o borrar la contraseña pide la **Contraseña actual** y, con la verificación en dos pasos activada, el código.
- **Algunas cosas necesitan una contraseña.** Descargar el kit de recuperación, el informe de error y el ZIP de una copia del flash, exportar una copia del flash o una autocopia, depositar la clave en un guardián de claves, permitir que se entregue un depósito, crear un código de recuperación nuevo, borrar las copias de un destino, exportar ajustes con credenciales, la verificación en dos pasos y las claves de acceso se rechazan hasta que se define una contraseña de acceso, y requieren iniciar sesión en la propia instancia.
- **Un destino no muestra ninguna contraseña.** Un destino puede llevar unas credenciales, como en `rest:https://user:password@host/repo`, y cada página y cada respuesta de la API lo muestran como `rest:https://[redacted]@host/repo`, con o sin contraseña de acceso. Si cambias la ruta que hay detrás, la contraseña guardada se mantiene. Para que el destino apunte a otro servidor, escribe el destino entero con su contraseña, porque una contraseña oculta se queda con su servidor.
- **Verificación en dos pasos** (**Ajustes, Seguridad**): un código de tiempo de una app autenticadora además de la contraseña, más ocho códigos de recuperación de un solo uso entregados una vez al activarla. El secreto compartido se guarda cifrado con `APP_KEY`, y volver a desactivar el factor requiere un código vigente.
- **Las claves de acceso** (WebAuthn) tienen su propia tarjeta una vez definida una contraseña, junto a la contraseña y nunca en su lugar, así que quitar todas las claves de acceso no deja fuera a nadie. Necesitan un nombre de dominio real y un certificado en el que confíe el navegador. El `https://<ip>:3443` predeterminado es justo lo que WebAuthn rechaza, y la tarjeta lo dice en lugar de ofrecer un botón que falla. Con la verificación en dos pasos activada, una clave de acceso tiene que comprobar tu PIN, tu huella o tu cara, o el inicio de sesión pide también el código.
- **Una restauración de la configuración** (**Recuperar ajustes** en el Asistente de emergencia) termina todas las sesiones, elimina todas las claves de acceso y revoca todos los tokens de API y claves de MCP, porque los ajustes restaurados podrían traer de vuelta algunos que se eliminaron después de guardarlos. Inicia sesión con la contraseña y vuelve a configurar tus claves de acceso en **Ajustes, Seguridad**.
- **Una contraseña olvidada** se restablece en la página de inicio de sesión. **¿Has olvidado la contraseña?** hace que BombVault escriba un código de 12 caracteres, en tres grupos de cuatro, en el registro de su contenedor (en Unraid: pestaña Docker, icono de BombVault, **Logs**). Ese código y una contraseña nueva te dan acceso. El restablecimiento también desactiva la verificación en dos pasos, elimina todas las claves de acceso, revoca todos los tokens de API, claves de MCP e inicios de sesión OAuth, termina todas las demás sesiones, cierra la sesión de todos los teléfonos emparejados y desactiva el emparejamiento de teléfonos. Después la página lista lo que se fue. Un código es válido durante 10 minutos, y los intentos errados no lo gastan. Los tokens del widget y de las métricas se quedan, porque solo leen.
- **Quien pueda leer el registro del contenedor puede restablecer la contraseña.** Eso es root en el host, pero también un visor de registros como Dozzle, cualquier contenedor al que se haya dado el socket de Docker (basta con solo lectura) y un enviador de registros que reenvíe la salida de los contenedores. Dáselos solo a personas en las que confiarías con la contraseña. Quien solo llega a la interfaz web nunca ve el código.

### Teléfonos y miembros del grupo {#phones-and-members}

- **Los teléfonos emparejados llegan a una lista permitida.** Un teléfono que conoce las doce palabras del grupo inicia sesión sin la contraseña, siempre que **Los teléfonos pueden emparejarse con las doce palabras del grupo** esté activado en la tarjeta **App de Android** de **Ajustes, Seguridad**. Su sesión llega solo a lo que muestra la app: el resumen, las ejecuciones, las copias para consultar, iniciar y restaurar, las anomalías para leer y la página Instancias para consultar. Los destinos y los comandos le llegan sin sus direcciones ni secretos, y una restauración que reemplaza el original copia antes el estado actual. Una restauración en una carpeta solo acepta una carpeta nueva o vacía dentro de la carpeta de restauración, y un teléfono no puede mirar en ninguna otra carpeta. Todo lo demás responde que necesita un inicio de sesión en la propia instancia: claves, kit de recuperación, depósitos de claves, ajustes, borrado de copias. Un restablecimiento de contraseña desactiva el emparejamiento de teléfonos hasta que lo vuelvas a activar. Un teléfono quitado de la página Instancias, o con **Consultar esta instancia** desactivado en sus detalles, pierde su sesión al instante, y un teléfono quitado que vuelve a abrir su app regresa desactivado.
- **Fuera de casa un teléfono abre páginas por el repetidor.** Cada petición de la página se sella con la clave del grupo, que el repetidor no puede leer ni cambiar, y se firma con una clave propia del teléfono que el servidor fijó la primera vez que se la pidió al teléfono. El servidor ejecuta una petición una sola vez y solo mientras es reciente. Responde únicamente a un teléfono listado en la página Instancias mientras el emparejamiento de teléfonos está activado, y solo con una sesión que él mismo dio a ese teléfono, así que cerrar sesión en todas partes y un restablecimiento de contraseña también terminan estas páginas. El servidor firma cada respuesta, y la app comprueba la firma con la clave que fijó para ese servidor y avisa cuando la clave cambia. Una página así llega a la misma lista permitida que un teléfono emparejado, con o sin contraseña de acceso, más el estado de inicio de sesión que la página lee primero. Iniciar y cerrar sesión, el restablecimiento de contraseña y las descargas se quedan en la propia dirección del servidor, y una respuesta tiene un tope de 16 MB.
- **Los miembros firman lo que piden.** Las solicitudes de rol y sus respuestas, las ofertas de almacenamiento, la entrega de una contraseña de restic a un receptor o recolector, los inicios de sesión de receptor y los depósitos de claves se firman con una clave de cada miembro, que una instancia fija la primera vez que ve a ese miembro. Una llamada firmada con otra clave se rechaza. **Olvidar la clave** en los detalles de una instancia descarta la clave fijada, para el caso en que la conocida aquí no sea la propia del miembro. Al miembro se le vuelve a pedir su clave en su siguiente llamada firmada. Los miembros con BombVault 9.x no firman y los puede suplantar cualquiera que tenga las palabras, como en la 9.9. Una solicitud de rol o una oferta de almacenamiento de un miembro con la 10.4 o anterior se rechaza hasta que ese miembro se actualice.
- **Las doce palabras son una contraseña.** Quien las tiene se une al grupo, ve el estado de protección de los miembros y puede pedir roles, que una persona de la otra instancia aún tiene que permitir. Sin contraseña de acceso, cualquiera que pueda abrir la interfaz web puede leerlas, y la tarjeta de emparejamiento lo dice hasta que se define una contraseña.

### Claves {#keys}

- **APP_KEY hace dos cosas.** Sella lo que guarda esta instalación (contraseñas, credenciales, tokens) y es la clave de las copias: de ella se deriva la contraseña de restic, y con ella se sellan las definiciones de contenedores y VMs.
- **Una clave adoptada se guarda aparte.** Cuando el Asistente de emergencia adopta las copias de otro servidor, esta instalación sigue sellando con su propia APP_KEY y guarda la clave del otro servidor como su **clave de las copias**, sellada como cualquier otro secreto. El kit de recuperación imprime entonces ambas. Si APP_KEY se cambia después, la clave de las copias ya no se puede abrir: BombVault deja de copiar y lo dice en **Necesita atención**, en lugar de escribir con la clave equivocada. Vuelve a subir el kit de recuperación en **Restauración, Emergencia**, o vuelve a poner APP_KEY. Consulta [Asistente de emergencia](offsite-recovery.md#emergency).
- **El cifrado** está activado por defecto (**Cifrar las copias** en la tarjeta **Cifrado** de **Ajustes, Seguridad**). Las copias las cifra restic con la contraseña derivada de la clave de las copias.
- **Depósitos de claves.** Un guardián de claves de tu grupo guarda una copia sellada del kit de recuperación de este servidor que él mismo no puede abrir. Solo la abre el código de recuperación de 20 caracteres, y el guardián lo entrega únicamente después de que alguien allí pulse **Permitir**. Consulta [Guardián de claves](offsite-recovery.md#key-keeper).

### Red {#network}

- **Los cambios necesitan JSON.** Una petición que cambia algo debe enviar `Content-Type: application/json` y no debe estar marcada como entre sitios por el navegador, de modo que una página de otro sitio no pueda hacer que tu navegador cambie ajustes en una dirección de la LAN. Un script que maneja la API envía esa cabecera. Cualquier otra cosa se rechaza con `415`.
- Como la puerta es opcional, cuando no está definida toda la interfaz y la API (incluidos los destinos, las rutas de prueba de manipulación y las rutas de restauración) son accesibles para cualquiera que pueda llegar al puerto. Define una contraseña de acceso en cuanto uses copias externas, copias append-only o cifrado.
- Ejecuta BombVault solo en una red de confianza y no expuesta. Para el acceso remoto ponlo detrás de un proxy inverso que añada autenticación y TLS. Las respuestas llevan cabeceras de seguridad básicas (CSP, `nosniff`, `X-Frame-Options`, `Referrer-Policy`).
- Detrás de un proxy inverso cada petición lleva la dirección del proxy, así que sin `TRUSTED_PROXY` el limitador de acceso cuenta a todos los clientes en un mismo cubo y los fallos de un atacante te bloquean a ti también. Nombra el proxy en `TRUSTED_PROXY` para recuperar el recuento por cliente.
- Un proxy inverso delante de BombVault tiene que dejar pasar la cabecera `Authorization` o `X-API-Key` hasta `/mcp` y no debe almacenar en búfer sus respuestas, o los asistentes no pueden conectarse. Consulta [Servidor MCP](mcp.md#tls).
- El endpoint MCP `/mcp` responde `404` hasta que existe una clave o se activa el inicio de sesión con OAuth, y pide a cada cliente su clave o token incluso con la contraseña de acceso desactivada. Ninguna dirección está exenta, ni siquiera `localhost`. No tiene herramientas de restauración ni de borrado, y restaurar una copia de la configuración revoca todas las claves. Consulta [Servidor MCP](mcp.md#security).
- Con `HTTP_ONLY=true` la cookie de sesión pierde su marca `Secure` (tiene que perderla para funcionar por HTTP sin cifrar), así que activa la contraseña solo detrás de un proxy que termine TLS si te importa la confidencialidad.
- La conexión SSH de la copia de VMs confía en la clave del host en la primera conexión (TOFU) y la fija a partir de ahí. Verifica la clave del host por otro canal si el camino del contenedor al host no es de confianza.
- **Los enlaces no salen del montaje.** Una copia o una restauración in situ se detiene con un mensaje cuando un enlace por encima de su ruta sale del montaje del host, porque un contenedor que escribe en su propio recurso compartido podría colocar uno. Un destino cuyo host o remoto de rclone empieza por un guion se rechaza del mismo modo, al guardar y en la siguiente ejecución, porque `ssh` o `rclone` lo leerían como una opción.

## Servidor MCP {#mcp-server}

El servidor MCP no necesita ninguna variable de entorno. Lo activas creando una clave en **Ajustes, Integraciones, Servidor MCP**, y responde en `/mcp` en el mismo puerto que la interfaz web (por ejemplo `https://192.168.1.10:3443/mcp`). Sin una clave activa esa ruta responde `404`. Los clientes, los certificados y los límites se describen en [Servidor MCP](mcp.md).

## Copia de VMs por SSH {#vm-backup-over-ssh}

BombVault copia VMs KVM/libvirt **sin montar ninguna ruta de libvirt**. Ejecuta `virsh` en el host por SSH (`qemu+ssh://`), así que nunca puede afectar al VM Manager de tu host.

Montar el socket de libvirt del host en un contenedor es frágil en Unraid: el VM Manager es dueño de esas rutas, y cambiar "Enable VMs" puede dejar a libvirt sin poder arrancar. La clave SSH concede root en el host, el mismo nivel de confianza que el socket de Docker que BombVault ya usa.

Configuración rápida:

1. **Ajustes, Integraciones, SSH del host:** copia la clave pública que se muestra.
2. Añádela al `/root/.ssh/authorized_keys` de Unraid (también se persiste en el flash para que sobreviva a los reinicios).
3. Haz clic en **Probar conexión**.

La plantilla añade `--add-host=host.docker.internal:host-gateway` para que el contenedor pueda llegar al host. Pon `LIBVIRT_HOST` a la IP de LAN de tu Unraid si ese nombre no se resuelve (por ejemplo cuando el contenedor se ejecuta en una red personalizada `br0.x`). Si cambiaste el puerto SSH de Unraid, pon `LIBVIRT_SSH_PORT` a juego. Las **instantáneas en vivo** necesitan además el agente invitado de qemu en la VM y el disco en `/mnt/cache` (no en `/mnt/user`).

!!! important "Guía completa de configuración de VMs y redes"
    La guía completa paso a paso (activar SSH, autorización persistente de la clave, enrutamiento en redes personalizadas y VLAN, método por VM y solución de problemas en el host) es la [guía de copias de VMs](vm-backup-ssh-setup.md).

## Configuración de copias externas {#off-site-setup}

Las copias externas van a **destinos**. Abre **Destinos** desde su mosaico de ajustes (o ánclalo a la barra lateral) y elige **Añadir destino**. Consulta [Copias externas y recuperación](offsite-recovery.md) para el flujo completo (protección contra borrado, pruebas de manipulación y simulacros de DR). En resumen:

- **Backends:** SMB/CIFS y WebDAV mediante rclone sin montaje en el host, NFS (monta la exportación en el host y úsala como carpeta local), backends nativos de restic sin rclone (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`), o cualquier remoto de rclone (`rclone:<remote>:<bucket>/path`). Backblaze B2 no tiene aquí un backend nativo: llega a él mediante su endpoint S3 (`s3:https://s3.<region>.backblazeb2.com/<bucket>/<path>`) con el ID de clave y la clave de aplicación como credenciales S3.
- **Las credenciales** se guardan cifradas, como una lista de credenciales guardadas en la tarjeta **Credenciales** de **Ajustes, Destinos**. Una estrella marca la predeterminada, que se usa donde no se haya elegido ninguna. La página propia de un destino elige la que usa en su tarjeta **Credenciales**. Consulta [Credenciales](offsite-recovery.md#sign-ins).
- **Los destinos SSH no necesitan nada instalado en el otro lado.** `sftp:` solo necesita un servidor SSH. Añade la clave pública de **Ajustes, Integraciones, SSH del host** (también en `/config/ssh/id_ed25519.pub`) al `~/.ssh/authorized_keys` del usuario de destino, o deja que **Añadir clave** en **Añadir destino** la ponga allí con la contraseña de la cuenta.
- **rest-server con un certificado autofirmado:** pon su certificado, o el de la autoridad que lo firmó, como archivo PEM en la carpeta `certs` de la carpeta de datos de BombVault (`/config/certs` en el contenedor, `appdata/bombvault/certs` en Unraid). Las copias, las réplicas y la prueba de protección contra borrado confían en él sin reiniciar.
- **Copia externa:** BombVault copia las instantáneas nuevas con `restic copy` en la medida de lo posible, encima de un primario (normalmente local). La tarjeta **Copiar** de un destino fija si copia **Después de cada copia** o según un calendario propio, y **Ajustes, Calendario, Copias externas por sección** da a una sección su propio calendario de copia. **Replicar ahora** está en la fila de la sección en la tarjeta **Copias externas** de **Ajustes, Destinos**.
- **Varios destinos por sección:** la tarjeta **Destinos por sección** de la página Destinos activa o desactiva con un clic cada línea de una sección a un destino, **Local** incluido. Una sección con solo destinos externos copia directamente a ellos, y una con todas las líneas desactivadas no se copia. Las **Reglas por sección** de un destino dan a una sección su propio repositorio, retención o compresión allí.
- **Destino por elemento:** cada contenedor, VM y conjunto de carpetas ilumina **Local** y los destinos que reciben sus copias, en la tarjeta **Calendario y destino** de su pestaña Ajustes. Los elementos sin elección propia siguen a su sección. Consulta [Destino por elemento](offsite-recovery.md#placement).
- **Retención:** cada destino conserva las copias según su tarjeta **Cuánto tiempo conservar**, y una sección puede conservar allí sus propios valores en **Reglas por sección**. Eso incluye la copia en el campo externo de una sección. Todo a cero nunca recorta las instantáneas de un destino.
- **Límites de ancho de banda:** limita la velocidad de subida y bajada de restic en la tarjeta **Ancho de banda externo** de **Ajustes, Destinos**, o por destino en su tarjeta **Copiar**. Introduces KiB/s, y el campo muestra la misma velocidad en MB/s y Mbit/s.
- **Primero el streaming:** en la tarjeta **Streaming** de la página Destinos, elige los servidores multimedia (Plex, Jellyfin y Emby vienen preseleccionados por el nombre de la imagen), la velocidad de envío a partir de la cual cuenta como streaming, el límite de subida mientras hay streaming y cuánto tiempo después de un streaming vuelve el límite normal.
- **Clase de almacenamiento frío y de archivo (S3):** para un destino S3, elige en su página un nivel legible para restaurar (Standard, Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier Instant Retrieval). Los remotos de rclone fijan su clase en la configuración de rclone.
- **Carpeta propia en un destino en lugar de local:** la carpeta propia de una sección puede estar en uno de los destinos anteriores, sin copia local y sin paso de copia. Consulta [La carpeta propia de una sección](offsite-recovery.md#own-folder).

## Anomalías {#anomalies}

La detección de anomalías no necesita ninguna variable de entorno. Se configura en la tarjeta **Anomalías** de **Ajustes, Verificación**, descrita en [Anomalías](anomalies.md#settings).

## Ajustes portátiles (exportar e importar) {#portable-settings-export-and-import}

La tarjeta **Exportar / importar ajustes** de **Ajustes, Sistema** escribe toda tu configuración de BombVault (ajustes de las secciones, destinos, calendarios, retención, notificaciones) en un archivo JSON portátil que puedes importar en otra instancia, de modo que mudarte a un equipo nuevo o clonar una configuración no obligue a volver a introducirlo todo a mano. La importación muestra una vista previa y pide confirmación, y nunca toca tus datos ni tu historial de copias. Los enlaces del archivo a destinos o repositorios que ya no existen se dejan fuera, y la vista previa los nombra. Mientras se ejecuta una réplica ZFS, una importación se rechaza antes de escribir nada.

!!! warning "La exportación puede contener credenciales"
    Tú eliges si incluir en el archivo las credenciales de las copias externas, de las notificaciones y del broker MQTT. Con las credenciales incluidas, la exportación es tan sensible como tu kit de recuperación, así que guárdala en un lugar seguro. Sin ellas, el archivo contiene solo ajustes no secretos.

!!! warning "La APP_KEY no viaja con el archivo"
    Los repositorios están cerrados con una contraseña derivada de la `APP_KEY`, y el archivo no la contiene. Para una mudanza planificada, da al equipo nuevo la `APP_KEY` antigua en su plantilla, o recupera la clave con el kit de recuperación en **Emergencia**. Con otra clave, los repositorios responden con una contraseña incorrecta. No se pierde nada, y al poner la clave correcta se vuelven a abrir.
