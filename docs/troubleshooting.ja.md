# トラブルシューティング

短い FAQ です。VM を SSH 経由で扱うときのホスト側のトラブルシューティングの完全な表（permission-denied、ホスト鍵の検証、足りないテンプレート変数など）は、[SSH 経由の VM バックアップガイド](vm-backup-ssh-setup.md)を参照してください。

## 何かがうまくつながっていない {#something-is-not-wired-up-correctly}

概要の**カスタマイズ**で、**ホスト統合**カードを追加してください。ホスト統合のチェックは、すべてのマウントと CLI（Docker ソケット、libvirt、restic、qemu-img、rclone）を調べて足りないものを報告し、**今すぐ確認**でもう一度実行できます。不具合だと考える前に、まずここから始めてください。マウントが足りない、ホストに到達できないといったことはすぐに表示されます。

## Web UI に到達できない {#i-cannot-reach-the-web-ui}

BombVault は、標準でポート `3443` の HTTPS（自己署名証明書）で動くので、`https://<your-unraid-ip>:3443` を開いてください。自己署名証明書の警告を受け入れるか、自分の証明書を使うリバースプロキシの背後に BombVault を置きます。`HTTP_ONLY=true` で動かしている場合は、代わりにポート `3000` の通常の HTTP で提供されます（TLS を終端するプロキシの背後で使うことを想定しています）。

## APP_KEY をなくした {#i-lost-my-app_key}

`APP_KEY` は restic リポジトリのパスワードを導出します。それがなく、リカバリーキットもなく、グループ内の鍵の預け入れもないと、暗号化されたバックアップは復元できません。そのため、概要には、ダウンロードするまで**リカバリーキットを保存してください**が表示されます。[オフサイトと復旧](offsite-recovery.md#recovery-kit)を参照してください。バックアップを頼りにする前に、`openssl rand -hex 32` で鍵を生成して、サーバーの外に保管してください。

## ログインパスワードを忘れた {#i-forgot-the-login-password}

ログインページで**パスワードをお忘れですか？**を選びます。BombVault が 12 文字のコードをコンテナのログに書き込みます（Unraid では、Docker タブの BombVault アイコンから**ログ**）。10 分以内に、そのコードを新しいパスワードとともに入力してください。リセットでは、二段階認証がオフになり、すべてのパスキーが削除され、すべての API トークン、MCP キー、OAuth サインインが取り消され、ほかのすべてのセッションが終了し、スマートフォンのペアリングがオフになります。パスキーは **設定、セキュリティ** で追加し直し、スマートフォンのペアリングもそこでもう一度オンにして、まだ必要な場所では新しいトークンとキーを作成してください。[セキュリティモデル](configuration.md#login)を参照してください。

## バックアップが止まり、鍵を開けなくなったと表示される {#backups-stopped-and-say-the-key-can-no-longer-be-opened}

このサーバーは、緊急ウィザードでほかのサーバーのバックアップ鍵を引き継いでいて、そのあとで `APP_KEY` が変更されました。引き継いだ鍵は古い APP_KEY で封じられているため、BombVault は開けず、間違った鍵で書き込む代わりに、何もバックアップしません。概要の**要対応**にそのことが書かれています。APP_KEY を元の値に戻すか、復元ページの**緊急**でリカバリーキットをもう一度アップロードしてください。

## スマートフォンがログインページに着く {#a-phone-lands-on-the-login-page}

ペアリング済みのスマートフォンがグループ経由でセッションを得るのは、**設定、セキュリティ** で**グループの12個の単語でスマートフォンをペアリングできる**がオンのあいだだけです。パスワードをリセットするとオフになります。サーバーより古いアプリも、更新するまでセッションを得られません。アドレスで追加したサーバーは、常にパスワードを求めます。インスタンスのページから削除したスマートフォンは、アプリをもう一度開くと、オフの状態で戻ってきます。詳細の**モニタリング**で**このインスタンスを照会**をオンにすると、入れるようになります。

## VM バックアップが接続できない {#vm-backup-will-not-connect}

VM バックアップは、SSH 経由で libvirt と通信します。マウントは使いません。

- ホストで SSH が有効になっていて、BombVault の公開鍵が `/root/.ssh/authorized_keys` で承認されていることを確認してください（設定、連携、ホスト SSH に鍵と**接続をテスト**ボタンがあります）。
- カスタムの `br0.x` ネットワークでは、`LIBVIRT_HOST` を Unraid の LAN IP に設定してください（そこではコンテナが `host.docker.internal` 経由でホストに届きません）。**Settings, Docker, Host access to custom networks** を有効にします。
- Unraid の SSH ポートを変更した場合は、`LIBVIRT_SSH_PORT` を合わせてください。
- TrueNAS では、TrueNAS 自身の libvirt ソケットで `LIBVIRT_URI` を設定し、アプリに `SETPCAP` ケーパビリティを与え、**Credentials, Users** で root に鍵を追加してください（[TrueNAS SCALE](getting-started.md#truenas)を参照）。
- 手順を追った完全な診断（到達性のテスト、VLAN のルーティング、`Permission denied (publickey)`、`Host key verification failed`）は、[SSH 経由の VM バックアップガイド](vm-backup-ssh-setup.md)にあります。

## VM のライブスナップショットが実行されなかった {#a-live-vm-snapshot-did-not-run}

ライブスナップショットには、`/mnt/user` ではなく `/mnt/cache`（または `/mnt/diskX`）にあるディスクが必要です。VM に qemu ゲストエージェントがあればスナップショットは静止した状態で取られ、なければクラッシュ整合のスナップショットになります。シャットダウン済みの VM では、ライブは自動でグレースフルに切り替わります。グレースフルなバックアップは VM をシャットダウンし、ディスクをバックアップしてから再起動するので、常に整合しています。ゲストがシャットダウンするのを最大 10 分待ち、強制的に電源を切ることはないので、アップデートをインストール中の Windows ゲストが途中で切られることはありません。それでも動いているゲストはそのままにされ、そのバックアップは理由とともに失敗します。

## バックアップが「repository is already locked」で失敗した {#a-backup-failed-with-repository-is-already-locked}

これは通常、コンテナが操作の途中で更新または再起動されたときに残った、孤立した restic のロックです。BombVault は、孤立していると証明できるロックを検出し、強制的に解除して、自動で一度だけ再試行します。それでも解消しない場合は、**設定、検証** の**バックアップをチェック**カードを開き、該当するセクションの行の**その他**の下にある**ロック解除**で、古くなったロックを手動で外してください。本当の問題は、隠されずに表面に出ます。再起動のあと BombVault は、そのようなロックが 10 分間更新されなくなるまで待ちます。まだ動いている restic（たとえば同じリポジトリを使う 2 つ目の BombVault）は、ロックを 5 分ごとに更新します。

## バックアップのあとにオフサイトコピーが実行されなかった {#my-off-site-copy-did-not-happen-after-a-backup}

オフサイトの複製は設計上ベストエフォートなので、オフサイトの不具合でローカルのバックアップが失敗することはありません。保存先がいつコピーするかを確認してください。その**コピー**カードに**バックアップのたびに**と書かれているか、独自のプランが書かれており、**設定、スケジュール、セクションごとのオフサイトコピー**でセクションに専用のプランを与えられます。すぐに実行するには、**設定、保存先** の**オフサイトコピー**カードにあるセクションの行の**今すぐ複製**を使い、概要のステータス欄を見てください。実行中は**オフサイトコピー実行中**と表示されます。失敗したコピーは**要対応**に表示されます。

## rest-server の証明書が信頼されない {#a-rest-servers-certificate-is-not-trusted}

restic は知らない証明書を拒否し、エラーには置く場所が示されます。rest-server の自己署名証明書、またはそれに署名した認証局の証明書を、PEM ファイルとして BombVault のデータフォルダーの `certs` フォルダー（コンテナ内では `/config/certs`、Unraid では `appdata/bombvault/certs`）にコピーして、もう一度テストしてください。再起動は不要です。

## バックアップが、ホストデータの外のデータをバックアップしなかったと言う {#data-outside-host-data}

コンテナが、BombVault がホストデータ経由で読み取れないフォルダーにデータを置いています。バックアップは、定義と、届くすべてのフォルダーを保存し、アクティビティログのその行をオレンジ色にして、除外したフォルダーを示します。よくあるのは 2 つです。TrueNAS の `/mnt/.ix-apps` の下の ixVolume と、compose スタックのデータベースボリュームなど、`/var/lib/docker/volumes` の下の名前付き Docker ボリュームです。コンテナの**設定**タブの**バックアップ対象フォルダ**カードには、そのようなフォルダーが、コンテナ内のパスとホストのパスとともに、赤い印付きで一覧されます。

匿名の Docker ボリュームは報告されません。Docker は、イメージが宣言していて誰もマップしなかったフォルダーに対して、自動で作成し、64 桁の 16 進数の名前を付けて `/var/lib/docker/volumes` の下に置きます。通常はキャッシュなので、バックアップは緑のままで、カードにはそれが匿名であるというメモとともに一覧されるだけです。

- **そのデータをバックアップしたい場合。** フォルダーを、ホストデータの下のホストのパス（たとえば appdata 共有の中のフォルダー）にマップすると、次のバックアップに含まれます。
- **必要ない場合。** 同じタブの**除外パターン**カードに、2 つのパスのどちらかを 1 行として追加します。コンテナ内のパス（たとえば `/cache`）か、警告が示すホストのパス（たとえば `/var/lib/docker/volumes/jellyfin_cache/_data`）です。次のバックアップから、警告はそのフォルダーを対象外にし、フィールドの下のプレビューがその理由を示します。その上位のフォルダーの行でも機能しますが、名前だけの指定や `/` は機能しません。

## バックアップが「延期」と表示される {#deferred-backups}

コンテナのアプリが使用中だったため、バックアップは待機し、自動でやり直されます。アクティビティログの行には、理由と次の試行の時刻が書かれています。コンテナの**設定**タブの**アプリが使用中のとき**カードにも同じことと、待機がいつ終わるかが書かれています。何もする必要はありません。すぐにバックアップするには、**今すぐバックアップ**を使ってください。自分で開始したバックアップは、終了コード 75 の場合も含め、決して待機しません。

- **独自のチェック。** アプリが使用中のあいだ、**バックアップ前コマンド**が終了コード 75 で終わるようにします。たとえば `[ "$(cat /tmp/players)" = 0 ] || exit 75` です。0 以外のほかのコードは、これまでどおりバックアップを失敗させるので、壊れたスクリプトは**要対応**に表示されます。
- **Plex、Jellyfin、Emby に問い合わせが行かない。** BombVault はまずコンテナ自身のアドレスでサーバーに問い合わせ、応答がなければコンテナ内で curl か wget を実行します。どちらもないイメージは、自分自身を通して問い合わせることができません。その場合、ログにそう書かれます。**サーバーが応答しないときはバックアップする**がオンなら、そのバックアップはそのまま実行され、オフなら待機します。
- **Jellyfin または Emby が拒否する。** **API キー**を確認してください。サーバーのダッシュボードの API キーで作成します。
- **Plex が拒否する。** BombVault は、`/config` にマウントされたフォルダーの `Preferences.xml` からトークンを読み取ります。一度もサインインしていないサーバーにはトークンがなく、トークンなしでのアクセスを許可している場所でしか応答しません。
- **一時停止した映画のせいで、バックアップが一晩中待たされる。** **一時停止中のセッションを無視するまで (分)** を、たとえば 30 に設定してください。
- **トラフィックのチェックがバックアップを通さない。** **使用中とみなす値 (KiB/s)** を、誰も使っていないときにコンテナが送信する量より上げてください。BombVault の起動直後は、チェックが、コンテナを**静かな状態の継続時間 (分)** の分だけ観察するまで待ちます。
- **バックアップが夜に実行されない。** 時間帯を設定すると、試行はその中でしか行われません。期限が時間帯の外に来た待機は、それでも期限で終わります。

## 大きなバックアップがメモリ不足で強制終了された {#a-large-backup-was-killed-for-running-out-of-memory}

**設定、システム** の**パフォーマンス**カードにある**バックアップごとのメモリ上限 (MiB, 0 = なし)** を、コンテナが使える量よりかなり低く設定してください。上限に近づくと restic はより頻繁にメモリを解放し、多少の速度を失いますが、バックアップは強制終了される代わりに遅くなります。

## 復元が開始前に中止された {#a-restore-aborted-before-it-started}

何かが停止または削除される前に、復元は事前の競合チェックを行い、コンテナの固定 IP と公開ホストポートが空いているかを確認します。ほかのコンテナがすでにどちらかを使っている場合は、中途半端な復元を残す代わりに、分かりやすい対処の書かれたメッセージとともに中止します。競合するポートや IP を空けてから、やり直してください。

コンテナのネットワークが存在しない場合（たとえば TrueNAS のアプリが削除されたため）は、復元チェックがそのネットワークの名前を示し、復元は何かを変更する前に拒否されます。TrueNAS で同じ名前でアプリを再インストールしてネットワークを作り直してから、データを復元してください。

## 通常のエクスポートがファイルを書き出さずに失敗した {#a-plain-export-failed-instead-of-writing-a-file}

**設定、システム** で **age でエクスポートを暗号化**がオンなのに、有効な受信者が設定されていない場合、エクスポートは平文を書き出す代わりに、分かりやすいエラーで失敗します。有効な受信者（age の公開鍵または SSH の公開鍵）を追加するか、エクスポートが平文でよければ暗号化をオフにしてください。[通常のエクスポート](backups.md#exports)を参照してください。

## データベースダンプが失敗した {#a-database-dump-failed}

失敗したダンプが、その周りのバックアップを失敗させることはありません。独立した失敗した実行として記録され、理由に直すべき点が書かれます。

- **ログインが拒否された。** ダンプは、コンテナ自身のパスワード変数（`POSTGRES_PASSWORD`、`MARIADB_ROOT_PASSWORD`、`MYSQL_ROOT_PASSWORD`、またはその `_FILE` 版）でサインインします。データベースのコンテナでそれらを確認してください。コンテナ自身のユーザーが読めないシークレットを指す `_FILE` 変数も、同じように失敗します。
- **権限が足りない。** ランダムな root パスワードだと、ダンプはアプリのユーザーとしてしかサインインできず、そのデータベース 1 つしか対象にならず、MySQL 8.4 以降では完全に拒否されることがあります。コンテナに本物の root パスワードを設定するか、そのダンプをオフにしてください。
- **システムテーブルのアップグレードが必要。** MariaDB は、システムテーブルが古いバージョンのものだとダンプを拒否します（エラー 1558）。変数 `MARIADB_AUTO_UPGRADE=1` を追加してコンテナを再起動するか、コンテナ内で一度 `mariadb-upgrade` を実行してください。
- **ダンプツールがない。** `pg_dump`、`mysqldump`、`mariadb-dump` のない、軽量なイメージや自作のイメージはダンプできません。公式イメージを使うか、ダンプをオフにしてください。
- **時間の制限。** ダンプには `DB_DUMP_MAX_HOURS`（標準は 6）、その周りのバックアップには `BACKUP_MAX_HOURS` が適用され、進捗のないダンプは `BACKUP_STALL_HOURS` のあとに打ち切られます。最後のものの通常の原因は、アプリケーションが保持しているロックです。作動したほうの上限を引き上げるか、アプリケーションが静かなときにダンプしてください。
- **コンテナが一時停止中か再起動中。** ダンプは動いているサーバーと通信します。コンテナが再起動を繰り返している場合は、そのコンテナ自身のログに理由が書かれています。
- **壊れたダンプを削除できなかった。** BombVault が完了できなかったダンプは、再び削除されます。その削除が失敗すると、ダンプは壊れたものとして印が付いたまま一覧に残り、そこで削除できます。

## インポートが失敗した {#an-import-failed}

インポートは、コンテナを停止し、そのデータフォルダーを脇に移し、その場所にイメージが空のフォルダーを作るようにします。インポート自体の前の手順が失敗した場合は、古いフォルダーが自動で戻されます。インポートが失敗した場合は、コンテナは新しいフォルダーを保持し、古いものはその隣に `<data folder>.bombvault-before-import-<timestamp>` として残ります。実行のエラーメッセージに、正確なパスが示されます。

それ自体がデータセットであるデータフォルダー（TrueNAS など）は、名前を変更できません。その場合インポートは、フォルダーをそのままにして、その中身を隣の保持用フォルダーに移すので、上位のデータセットにその分の空きが必要です。インポートは、コンテナを停止する前にそれを確認します。

手動で元に戻すには、コンテナを停止し、現在のデータフォルダーの名前を変えてどけ、保持されたフォルダーの名前を元の名前に戻して、コンテナを起動します。データセットの場合は、フォルダーの名前を変える代わりに、中身を移動します。Unraid では、Shares タブのファイルマネージャーで行えます。

## ZFS データセットのバックアップが失敗した、またはデータセットをスキップした {#zfs-datasets}

すべての問題には括弧内の理由コードが付いており、[ZFS データセット](zfs-datasets.md#reason-codes)ページに、そのすべてと対処が載っています。特に多い 3 つを挙げます。

- **`snapshot-loop`**：ホストデータが新しいマウントを通さないため、スナップショットが BombVault に届きませんでした。コンテナを編集し、ホストデータのアクセスモードを Read/Write - Slave にして、BombVault を再起動してください。
- **`key-not-loaded`**：鍵が読み込まれていない暗号化データセットはスキップされます。`zfs load-key` で鍵を読み込み、データセットをマウントしてください。次のバックアップに含まれます。
- **`ssh-auth`**：サーバーが BombVault の鍵を拒否しました。バックアップページの**接続を表示**で開く **このサーバーへの ZFS 接続**に、承認するコマンドが表示されます。サーバーで一度実行してください。

## 項目が「学習中 N/10」のまま {#an-entry-stays-at-learning-n10}

異常チェックの多くは、項目の成功したバックアップが 10 回たまってから始まり、**想定どおりと印を付ける**のあとと、項目の選択範囲が変わったあとは、カウントが最初からやり直しになります。スケジュールされていない項目は学習せず、appdata のないコンテナは学習するものがなく、そのバッジにもそう表示されます。異常ページの**学習の進み具合**には、項目ごとの 10 分割のリングが表示されます。

## 1 つの項目の古いバックアップを、保持ルールが削除しなくなった {#retention-stopped-deleting-old-backups-of-one-entry}

未処理の重大な異常が、それらを保持しています。項目のソースがほぼ空、急に縮小した、または 1 回のバックアップでデータの大半が保存し直されました。項目のバッジから異常を開いてください。データが足りない、または暗号化されている場合は、リンクされた最後の正常なバックアップから先に復元します。そのあと異常を確認済みにするか、変更があなたによるものなら想定どおりと印を付けると、次の実行でいつもどおり整理されます。保持のプレビューは、そのような項目を保持されるものとして示します。ZFS 項目では、異常に挙げられたデータセットだけが古いバックアップを保持し、ツリーのほかのデータセットはいつもどおり整理されます。

## 手動のプルーンが、いくつかの項目を残したと言う {#manual-prune-says-some-entries-were-kept}

原因は同じです。プルーンは、そのような異常のある項目の古いバックアップには手を付けず、メッセージに項目の名前を示します。それ以外はいつもどおり整理されます。

## バックアップが「on no mounted pool or share」で失敗する {#no-mounted-pool}

Unraid では `/mnt` はメモリ上にあるため、プールがマウントされていないそこのフォルダーは、次の再起動で消え、プールが戻ると隠れてしまいます。BombVault は、そこにバックアップやフラッシュ ZIP を書き込むことを拒否します。以前の書き込みによるリポジトリがすでにそのフォルダーにある場合も同じです。プールをマウントして、もう一度バックアップを実行してください。

## 履歴のインポートが、リポジトリを読み取れなかったと言う {#history-import-says-a-repository-could-not-be-read}

アップグレードのあと、BombVault は各リポジトリから、以前のバックアップのサイズを一度読み取ります。そのとき到達できなかったリポジトリ（停止していたオフサイトの保存先や、マウントされていなかった共有など）は、**設定、検証** の**異常**カードに数えられ、1 日 1 回やり直されます。その間、その項目は新しいバックアップから学習します。

## ディスク容量の警告が Unraid のダッシュボードと合わない {#the-disk-space-warning-does-not-match-the-unraid-dashboard}

Unraid のユーザー共有（`/mnt/user`）では、空き容量は 1 台のディスクではなく、アレイ全体のものです。SFTP、Hetzner Storage Box、SMB、WebDAV、クラウドドライブなど、BombVault が rclone 経由で届くリモートの保存先は、相手側が空き容量を報告したときに測定され、手で入力した `sftp:` アドレスも同じです。S3、B2、REST のリポジトリには数値がありません。その保存先には**サイズ不明**と表示され、**異常**カードには測定されないものとして一覧されます。

## AI アシスタントが接続できない {#an-ai-assistant-cannot-connect}

[MCP サーバーのページ](mcp.md#troubleshooting)に、MCP エンドポイントの各ステータスコードと各拒否の意味と、その対処が一覧されています。

## コンテナが再起動を繰り返す、または不健全に見える {#the-container-keeps-restarting-or-looks-unhealthy}

BombVault は、自分自身の `/api/health` から、正常か異常かを報告します。エンジンが固まった場合は、自動復旧ツール（Autoheal など）が自動で再起動できます。根本の原因は、コンテナのログと**ホスト統合**カードで確認してください。

## 保存先が保存を拒否する {#location-refused}

BombVault は、保存先を保存する前に確認し、拒否には理由が 1 文で書かれます。よくあるものは次のとおりです。

- **「This location lies inside another repository or target, or contains one.」**（この場所はほかのリポジトリまたは保存先の中にあるか、それを含んでいます。）リポジトリの中のリポジトリは、両方を壊してしまいます。メッセージには、もう一方の場所が示されます。別のフォルダーを選ぶか、先にそちらを削除してください。
- **自分で設定したリポジトリである。** その場所が、**リポジトリ**の下の行のどれかであるか、その中や周りにあります。別の場所を選ぶか、先にそのリポジトリを削除してください。
- **セクションの専用フォルダーと同じ場所。** セクションの専用フォルダーへのコピーは、実行のたびにバックアップを自分自身にコピーすることになるので、拒否されます。別の場所を選ぶか、[セクションの専用フォルダー](offsite-recovery.md#own-folder)を参照してください。
- **「That is not an off-site target of this domain」**（これはこのドメインのオフサイトの保存先ではありません）は、削除された保存先へのリンクから出ました。現在のバージョンは、開始時とインポート時にこれを消します。まだ表示される場合は、BombVault を更新してください。
- **完全なホストのパス**（`/mnt/user/backups` など）。BombVault はコンテナで動くので、ホストデータより下のパス `user/backups` を求めます。メッセージには、入力すべきパスが示されます。

## リモートの保存先が、リポジトリがなくなったと言う {#repository-gone}

バックアップがあった保存先が、突然リポジトリを持たなくなっても、新しい空のリポジトリは自動では作られません。ディスクが戻ったときに、本物を隠してしまうからです。ディスクがマウントされなかった rest-server が通常の原因なので、ディスクをもう一度マウントして、バックアップまたはコピーをもう一度実行してください。古いリポジトリを意図的に空にしたか削除した場合にだけ、保存先のページで**ここに新しいリポジトリを作成**を押してください。その保存先のすべてのセクションに対して、一度にやり直します。

## クラウドのサインインの期限が切れた {#cloud-sign-in-expired}

テストまたは次のコピーで、サインインの期限が切れたと表示されます。保存先のページの**接続を変更**で、サインインし直します。

- **Box、Jottacloud など、一度きりのリフレッシュトークンを使うもの：** BombVault は、rclone が更新したトークンを、再起動をまたいでもリカバリーキットの中でも保持します。古い設定のバックアップから復元したあとは、その中のトークンが使えなくなっていることがあるので、もう一度サインインしてください。リポジトリはそのままです。
- **iCloud Drive：** Apple は 30 日後にサインインを終了します。`rclone config` で新しいトラストトークンとクッキーが必要です。
- **OneDrive：** 複数のドライブがある場合、サインインはどれを使うかを尋ねるので、選択のない保存先は、選ぶまで使えません。OneDrive Business と Google Drive については、[保存先](offsite-recovery.md#destinations)の整理されたデータに関する注意を参照してください。

## 「前回のバックアップのオフサイトコピーがまだ実行中です」 {#copy-still-running}

その前のバックアップは完了していて、そのコピーがまだ進行中のため、そのセクションの新しいバックアップが止まっています。ステータス欄に**オフサイトコピー実行中**と表示されなくなるまで待ってください。バックアップを開始するボタンも、待機中は同じことを表示します。新しい保存先への最初のコピーには数時間かかることがあります。[S3 の例](offsite-recovery.md#example-s3)を参照してください。

## 転送先に新しいスナップショットがあるため、ZFS レプリカが止まる {#replica-target-newer}

転送先に、このサーバーと共有する最新のものより新しいスナップショットがあります。たとえば、ここでデータセットがロールバックされたか、転送先のコピーが変更されたためです。レプリカカードと実行履歴の**転送先の戻し先**に、そのスナップショットが示されます。実行が示す各データセットについて、転送先でそのスナップショットまで `zfs rollback -r` を実行してから、**今すぐ複製**を押してください。[スナップショットが残る期間](zfs-datasets.md#replica-retention)を参照してください。

## Unraid スナップショットのある VM が失敗し、ファイル名が示される {#vm-chain}

BombVault は各ディスクのバッキングチェーンをたどり、その中のすべてのファイルをバックアップします。最後までたどれないチェーンは、ディスクの一部を省く代わりにバックアップを失敗させ、メッセージにファイル名が示されます。そのファイルが `/mnt` の下に存在し、スナップショットが VM Manager にまだ一覧されていることを確認してください。ホストデータの外のファイルは、まったく読み取れません。[Unraid スナップショットのある VM](vm-backup-ssh-setup.md#unraid-snapshots)を参照してください。

## 再構築のあと、オフサイトコピーが判断を待っている {#copies-paused}

**バックアップを検出**や、設定を復元しない緊急ウィザードのあと、またはセクションがこのデータベースより前の自分のバックアップを見つけたときは、そのセクションのオフサイトコピーが待機します。BombVault は、どの項目を対象から外していたかをもう知らないからです。**要対応**と保存先のページが、それについて尋ねます。続けるには**このサーバーのものとして引き継ぐ**を押し、その前にセクションのルールを見るには**先にルールを確認**を押してください。設定ファイルのインポートが、判断を代わりに下すことはありません。[再構築のあと](offsite-recovery.md#after-a-rebuild)を参照してください。

## 通知が届かない {#notifications-do-not-arrive}

**設定、通知** の**テスト送信**から始めてください。カードの下の行に、何が起きたかが表示されます。

- **何も送られない。** **通知する**を確認してください。**なし**だとメッセージは送られず（Healthchecks の URL への ping だけは送られます）、**失敗時のみ**だと、成功した実行は静かなままです。**スケジュール実行をまとめて通知**がオンだと、スケジュールされた実行は、終わりに 1 通のまとめを送ります。
- **新しいアドレス。** Matrix、Gotify、メールのサーバーを変えると、フィールドはトークンやパスワードをもう一度求め、新しいアドレスは入力したときにだけ保存されます。BombVault は、古いシークレットを新しい場所に送りません。
- **Gotify** が、サーバーにアプリトークンを拒否されたと言う場合：Gotify のアプリケーションから、もう一度コピーしてください。**サーバー URL** は、`/message` を含まない基本アドレスです。
- **Webhook：** **Webhook 形式**がサービスに合っているか確認してください。Discord のアドレスには **Discord**、ntfy には **ntfy** が必要です。
- **Unraid 通知**はホスト SSH 接続経由で動くので、**設定、連携** で先にそれをテストしてください。ほかのプラットフォームではオフのままで、カードにもそう書かれます。
- **通知メールがまったく届かない。** **暗号化**をポートと照らし合わせてください。通常は 587 で **STARTTLS**、465 で **TLS (implicit)** です。

Healthchecks の ping はこれらのどれにも依存しません。[Healthchecks](notifications.md#healthchecks)を参照してください。

## Android アプリがサーバーを開けない {#android-cannot-open}

開始画面のサーバーのカードに、理由が表示されます。

- **未接続：** サーバーのアドレスにもリレーにも応答がありません。**リレーなし**の場合、アプリはサーバー自身のアドレスでしか届きません。
- **証明書を確認：** サーバーが、信頼したものとは別の証明書を示しています。アプリは新しいものを信頼したあとにしか開かないので、変更が自分によるものか確認してください。
- **サインインが必要です：** アドレスで追加したサーバーは、パスワードを求めます。[スマートフォンがログインページに着く](#a-phone-lands-on-the-login-page)も参照してください。
- **鍵が変わった：** 開始画面に新しい鍵のフィンガープリントが表示され、ページはそれを信頼したあとにしか開きません。[外出先で](android.md#away)を参照してください。

## ほかのユーザーがローカルリポジトリを読めない {#repository-permissions}

ローカルリポジトリは、SMB 経由の同期ユーザーなど、ほかのユーザーが読めるままです。10.4.1 より前は、プルーン、タグ、プル、セクションの移動、削除、スタックのバックアップが書いたファイルが、次の夜まで読めないままになることがありました。BombVault を更新すると、すぐに読めるようになります。セルフバックアップのリポジトリは、BombVault の設定を保持しているため、意図的に root だけが読めるままです。

## まだ解決しない？ {#still-stuck}

- [設定](configuration.md)と[オフサイトと復旧](offsite-recovery.md)のページを通して読んでください。
- **設定、情報** の**ヘルプ**カードの**バグ報告**は、GitHub の issue 用の ZIP をダウンロードします。ホストのチェック、すべてのシークレットを取り除いた設定、最近の実行、次のスケジュール、コンテナが最後に起動してからの最近のログが入っています。各データベースの最後のダンプ、マウントつきの ZFS 項目、未処理の異常、MCP キーの数も含まれます。パスワード、トークン、rclone の設定は取り除かれ、バンドル自身のマニフェストにもそう書かれます。ログインパスワードが必要です。コンテナが再起動するクラッシュの場合は、`docker logs` を見てください。
- [Unraid のサポートスレッド](https://forums.unraid.net/topic/199509-support-junkerderprovinz-bombvault/)で質問してください。
- [GitHub の issue](https://github.com/junkerderprovinz/bombvault/issues) を作成してください。
