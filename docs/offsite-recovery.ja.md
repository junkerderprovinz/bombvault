# オフサイトと復旧

!!! note "再構築のあと、オフサイトコピーは待機します"
    緊急ウィザードまたは**バックアップを検出**が、古い設定なしで項目を再構築した場合、それらのセクションのオフサイトコピーは、既定が確認されるまで一時停止します。[再構築のあと](#after-a-rebuild)を参照してください。

ローカルのバックアップは、コンテナを失ったり、更新に失敗したりしたときに守ってくれます。オフサイトコピーと、テスト済みのリカバリーキットは、マシン全体の故障、ランサムウェア、火災から守ってくれます。このページでは、保存先とオフサイトコピー、コピーを改ざんされにくくする方法、復元できることの証明、複数のサーバーのペアリング、そして BombVault 自体が失われたときにすべてを取り戻す方法を説明します。

## オフサイトコピー {#off-site-copies}

高速なローカルバックアップはそのままに、設置場所の外にある保存先を 1 つ以上追加します。BombVault は、新しいスナップショットを `restic copy` でベストエフォートでそこへコピーするので、オフサイトの不具合でローカルのバックアップが失敗することはありません。この形では、各セクションが最初に自分の専用フォルダーに書き込み、オフサイトのリポジトリはそのコピーです。専用フォルダーはこのサーバー上にある必要はありません。S3 や rest-server などの保存先の中に置く方法は、[セクションの専用フォルダー](#own-folder)を参照してください。

- **セクションごとに複数の保存先。** 各セクション（コンテナ、VM、フラッシュ、セルフバックアップ、フォルダー、ZFS データセット）は、複数のオフサイトの保存先に同時にコピーできます。たとえば、友人のマシンにある rest-server と S3 バケットを並行して持てます。保存先のページの**セクションごとの保存先**カードで、セクションから保存先への各行をオンまたはオフにします。
- **コピーが実行されるタイミング。** 保存先の**コピー**カードの**コピーのタイミング**で、**バックアップのたび**か、スナップショットをまとめて決まった時刻にコピーする専用のプランを設定します。**設定、スケジュール、セクションごとのオフサイトコピー**の**例外**で、1 つのセクションに専用のコピープランを与えられます。
- **オフサイトコピーカード。** **設定、保存先** で、オフサイトコピーを持つすべてのセクションに、**オフサイトコピー**の中の 1 行があり、**接続をテスト**、コピーをすぐに開始する**今すぐ複製**、**セットアップ**または**編集**があります。セクションのコピーのその他の設定は、そこからウィンドウで開きます。
- **保持**は、保存先ごとに**保持期間**で設定するので、オフサイトコピーをアーカイブとして長く保てます。セクションのオフサイトフィールドにあるコピーも、ほかのコピーと同じようにそれに従い、セクションは**セクションごとのルール**で独自の値を保てます。すべてゼロにすると、オフサイトのスナップショットは一切整理されません。[保持期間](#keep)を参照してください。
- **帯域幅の制限**（**設定、保存先** の**オフサイト帯域幅**、または保存先の**コピー**カード）は、restic のアップロードとダウンロードの速度を制限して、コピーが WAN を埋め尽くさないようにします。restic が受け取る単位の KiB/s で入力し、入力中は各フィールドに同じ速度が MB/s と Mbit/s でも表示されます。2048 なら約 2.0 MB/s（16.8 Mbit/s）と表示されます。
- **圧縮**は、**オフ**、**自動**（restic の標準）、**最大**のどれかで、保存先ごとに、また 1 つのセクションならそこのルールの下で設定します。バックアップ、コピー、プルーンはそれに従って書き込み、リカバリーキットにもそれが書かれるので、通常の restic でも同じように書き込み続けられます。
- **ストリーミング優先。** Plex、Jellyfin、Emby などのメディアサーバーがストリーミングしているあいだ、コピーは低い制限でアップロードされ、ストリームが終わって数分後に通常に戻ります。保存先のページの**ストリーミング**カードには、**ストリーミング中はオフサイトコピーを減速**、**メディアサーバー**（選ぶまでは、イメージ名に Plex、Jellyfin、Emby を含むコンテナ）、**ストリーミングとみなす値 (Mbit/s)**、**ストリーミング中のアップロード制限 (KiB/s)**、**通常に戻るまで (分)** があります。BombVault は Docker からトラフィックを読み取るため、ホストネットワーク上のメディアサーバーは測定できません。REST、S3、B2、Azure、Google Cloud、Swift、HTTP 経由の rclone は、コピーの途中で減速します。SFTP とローカルまたはマウントされたフォルダーは、次のコピーの手順で低い制限を適用します。
- **コールドストレージ（S3）。** S3 の保存先は、restic がすぐに読み取れる、より安価な**ストレージクラス**を使えます。たとえば Standard-IA、One Zone-IA、Intelligent-Tiering、Glacier Instant Retrieval です。Glacier Flexible Retrieval と Deep Archive は、restic が復元できないため除かれています。rclone のリモートは、rclone の設定でクラスを決めます。
- **増加予算。** セクションのコピーウィンドウの**増加予算（GB、0 = オフ）**は、リポジトリがそのサイズを超えて増えたときにアラームを出します。何も削除しないので、ここからは何もプルーンされない append-only のコピーに向いています。
- コピーの実行中、概要のステータス欄には**オフサイトコピー実行中**と表示されます。`restic copy` は機械で読める進捗を出さないため、パーセントのバーではなく、動作中の表示です。

!!! note "どの場所からでも復元できます"
    すべての項目は、**バックアップ**タブに、バックアップがあるすべての場所をまたいだ 1 つのタイムラインとして、バックアップを一覧します。B2 にコピーされたバックアップは、それを持つ各場所の印とともに 1 回だけ表示されます。復元は、届く最初の場所から行われ、項目が書き込む先のリポジトリが最初で、スナップショットごとに別の場所を選べます。オフサイトの保存先は、クラウドストレージの一覧取得に時間がかかるため、**チェック**をクリックしたときにだけ読み取られます。1 か所での削除は、先にほかの場所を確認し、それが最後のコピーかどうかを伝えます。[復元](restore.md)を参照してください。

## 保存先 {#destinations}

保存先は、バックアップの行き先です。ローカルフォルダー、共有、自分のサーバー、クラウドサービスなどがあります。一度設定すると、すべてのセクションに使えます。設定のタイルから**保存先**を開くか、そこで**サイドバーにも表示**をオンにして固定します。

![保存先のページ：保存先の一覧と、どのセクションがどこへ行くかの流れ。](assets/screenshots/storage/locations-dark.png#only-dark)
![保存先のページ：保存先の一覧と、どのセクションがどこへ行くかの流れ。](assets/screenshots/storage/locations-light.png#only-light)

**保存先を追加**を押すと、4 つの手順のウィンドウが開きます。

1. **プロバイダー。** すべてのサービスがロゴ付きで、ウィンドウの右上の検索とともに、グループ別に一覧されます。このサーバーに接続されたディスクや共有の**ローカル**、**NAS またはサーバー**（rest-server、Hetzner Storage Box、SFTP、SMB、WebDAV など）、**S3 サービス**（Backblaze B2、Wasabi、Cloudflare R2、Hetzner Object Storage、Amazon S3 など）、自分の S3 サーバー（Garage、SeaweedFS、RustFS、Silo、Ceph、JuiceFS、Versity S3 Gateway）、**クラウドストレージ**（OneDrive、Google Drive、Dropbox、pCloud、Nextcloud、そのほか rclone が対応するもの）、そしてグループの受信サーバーである**グループから**です。それぞれに、バックアップへの向き不向きが書かれています。クラウドドライブは多くのリクエストで遅くなるので、最初のバックアップとプルーンに時間がかかります。どのタイルにもないサービスには、**独自の rclone 設定**の下の **Rclone** タイルで、rclone.conf から貼り付けたリモートを使えます。
2. **サインイン。** フィールドはサービスによって異なります。S3 ならアクセスキー、WebDAV と SMB ならユーザーとパスワード、二段階認証が通常のものをブロックする場合はアプリパスワード、SFTP と Storage Box なら BombVault の SSH 公開鍵、ブラウザー経由でサインインするサービスならトークンです。後者の場合、ウィンドウにブラウザーのあるコンピューターで実行する `rclone authorize` コマンドが表示され、それが出力するトークンをフィールドに入力します。そのサービスの[保存済みの認証情報](#sign-ins)がすでにあれば、**新しいキー**の代わりに**保存済みの認証情報**でそれを選べます。**接続をテスト**は、何かを保存する前にサインインを確認します。そのあと、ウィンドウに保存先のフォルダーが一覧され、**新しいフォルダー**で作成でき、サービスが報告する場合は空き容量も表示されます。空のフォルダーが最も安全です。BombVault はその中に、セクションごとに 1 つのフォルダーを置きます。
3. **保護。** ウィンドウは、そのサービスにできることを率直に伝えます。append-only モードの rest-server は削除を拒否し、改ざんテストがそれを確認します。S3 バケットは、バージョニングとオブジェクトロックで古いバージョンを残せますが、BombVault はまだそれを確認できません。クラウドドライブは削除をまったく拒否できません。サーバーに入った人は、そのコピーにも入れてしまいます。**削除に対する保護(append-only)**をオンにするのは、相手側が本当に削除を拒否する場合だけにしてください。そうすると BombVault はそこをプルーンしません。**緊急時のために**には、リカバリーキットがこの保存先について何を保持するかが書かれています。
4. **対象セクション。** ここにバックアップするセクションを選びます。最初のコピーは、履歴全体を持っていきます。専用の保存先を選んだ項目は、新しいものを自動では受け取らず、ウィンドウにその名前が示されます。

![保存先を追加：最初の手順。すべてのプロバイダーがタイルとして並ぶ。](assets/screenshots/storage/add-providers-dark.png#only-dark)
![保存先を追加：最初の手順。すべてのプロバイダーがタイルとして並ぶ。](assets/screenshots/storage/add-providers-light.png#only-light)

![保存先を追加：テストに成功したあとのサインインの手順。](assets/screenshots/storage/add-signin-dark.png#only-dark)
![保存先を追加：テストに成功したあとのサインインの手順。](assets/screenshots/storage/add-signin-light.png#only-light)

サービスによっては、サインインでもう少し多くの項目を求められます。

- **SFTP と Storage Box。** **鍵を追加**は、**アカウントのパスワード**を使って、BombVault の公開鍵をサーバーに置きます。このパスワードはその 1 回のサインインにだけ使われ、どこにも保持されません。手動で行うためのコマンドが、その下に表示されます。テストでは**サーバーの鍵**がフィンガープリントとともに表示されます。BombVault はそれを記憶し、のちにサーバーが別のものを示した場合は、そのサーバーを拒否します。
- **単一のバケット用の S3 キー**（Cloudflare R2 のオブジェクトトークンや、スコープを絞った AWS キーなど）は、ほかのバケットを一覧できないことがあります。**バケット**にバケット名を入力すると、テストとフォルダー一覧がそのバケットを開きます。
- **S3 のリージョンとアドレス。** リージョンは、それを含むエンドポイント（AWS、Backblaze B2、Hetzner、Scaleway、OVH、Wasabi）から読み取られます。Garage は自身の標準リージョンで始まり、IDrive e2 はダッシュボードに表示されるエンドポイントを求めます。R2 のダッシュボードのように、バケットを付けて貼り付けたアドレスは、サーバーとバケットを自動入力します。フォルダーブラウザーから作ったバケットは、フォームが指定するリージョンに作られます。
- **ストレージクラス。** ピッカーにはサービスが受け付けるクラスだけが表示され、**詳細設定**には新しいバケットの形を決めるオプションだけが表示されます。
- **Google Drive と OneDrive。** 整理されたデータは、ゴミ箱やごみ箱（そこにあると容量の割り当てに数えられ続けます）に送られずに、完全に削除されます。Google の共有ドライブは、**詳細設定**にあります。
- **共有を一覧しない SMB サーバー**では、**共有名**に 1 つの名前を入力すると、テストがその共有を直接開きます。
- **FTP** は**暗号化**を求めます。**なし**、**明示的 TLS (FTPES)**、**暗黙的 TLS (FTPS、ポート 990)** です。
- **OneDrive と Zoho WorkDrive。** サインインが複数のドライブやワークスペースを開く場合、ウィンドウがバックアップの行き先を尋ねます。
- **自己署名証明書の rest-server。** 証明書を PEM ファイルとして、BombVault のデータフォルダーの `certs` フォルダー（コンテナ内では `/config/certs`、Unraid では `appdata/bombvault/certs`）に置きます。バックアップ、コピー、削除に対する保護のテストは、再起動なしでそれを信頼します。

S3 サービスは restic 自身の S3 バックエンドを通るので、ストレージクラスとオブジェクトロックが適用されます。rest-server には restic が直接接続します。それ以外のサービスはすべて、BombVault が同梱する rclone を通り、その rclone 設定のセクションは、保存先のページの **rclone.conf** カードに、シークレットを隠した形で表示されます。設定のエクスポートには保存先が含まれ、認証情報を含めると、そのサインインも含まれます。

コンテナ、VM、フォルダーのバックアップをすでに持つ保存先（たとえば、削除してもう一度追加したもの）を保存すると、それらのセクションに、チェックの入っていないコピーとして追加されます。チェックを入れるまで何もコピーされませんが、**復元**には古いバックアップがすぐに表示されます。

このサーバー上のフォルダーは、保存先のページ、流れ、項目、復元のどこでも**ローカル**と呼ばれます。このサーバー上に複数のフォルダーがある場合は、それぞれの名前で呼ばれます。セクションのオフサイトフィールドが設定する保存先は、その場所（アドレスの最後のフォルダー、なければそのサーバー）の名前が付き、同じ名前の保存先がすでにあれば番号が付きます。どの保存先も、**接続**カードの**名前**フィールドで名前を変更でき、複数のセクションが共有するバケットフォルダーや、セクションのオフサイトフィールドが示すコピーも同様で、付けた名前はそのまま残ります。同じ名前の 2 つの保存先が並ぶ場合は、それぞれにサーバーまたはフォルダーが付きます。

### 保存先のページ {#location-page}

すべての保存先には、専用のページがあります。その保存先に当てはまるカードだけが、次の順で表示されます。

![保存先のページ：専用フォルダー、接続、認証情報。](assets/screenshots/storage/location-page-dark.png#only-dark)
![保存先のページ：専用フォルダー、接続、認証情報。](assets/screenshots/storage/location-page-light.png#only-light)

- **専用フォルダー**：最初にここへバックアップを書き込むセクション。この保存先のサインイン、保護、制限がそれらに適用されます。**専用フォルダーにする**は、より多くのセクションの専用フォルダーをここへ移し、**変更**は 1 つをまた別の場所へ移します。[セクションの専用フォルダー](#own-folder)を参照してください。
- **ここに直接バックアップ**：専用フォルダーの代わりに、この場所へ直接バックアップする項目を持つ各セクションと、その項目数。このようなダイレクトリポジトリは、設定のすべてをこの保存先から引き継ぎます。もう何もバックアップしていないものには、その旨が表示され、**削除**で一覧から外せます。その場所のバックアップは残ります。[ダイレクトリポジトリ](#direct-repositories)を参照してください。
- **接続**：**名前**、スイッチ**利用可能**（オフにすると、BombVault はもうここに書き込まず、ここへバックアップする項目は、別の場所に着地する代わりに、分かりやすいメッセージとともに失敗します）、フォルダー、**圧縮**、**ストレージクラス**、**施設外**。**ローカル**の保存先では、**ここにある専用フォルダー**の下に各セクションのフォルダーが一覧されます。**接続を変更**は、新しいアドレスまたはサインインをテストして保存します。ほかの場所が同じ保存済みの認証情報でサインインしている場合、ウィンドウがそう伝え、ここでの変更は、共有しているものを書き換える代わりに、この保存先に専用の認証情報を与えます。
- **認証情報**：どの保存済みの認証情報を使うか（**使用する認証情報**）、ほかにどの保存先が使うか（**ほかの使用先**）、そして認証情報のウィンドウを開く**編集**。[認証情報](#sign-ins)を参照してください。
- **rclone.conf**：rclone を通る保存先について、この保存先の rclone 設定のセクション。
- **削除に対する保護**：**削除に対する保護(append-only)**、**削除に対する保護なしで承認**、**削除に対する保護を今すぐテスト**、そして BombVault がここのコピーと専用フォルダーを、この保存先の**保持期間**カード、または**セクションごとのルール**にあるセクション独自の値に従って整理するのか、相手側に任せるのかを示す**整理する側**。ローカルフォルダーでは、オフにできる保護がある場合にだけこのカードが表示されます。[削除に対する保護](#delete-protection-append-only)を参照してください。
- **コピー**：**コピーのタイミング**と、**アップロード制限 (KiB/s)**、**ダウンロード制限 (KiB/s)**。専用フォルダーしか持たず、コピーを持たない保存先では、制限は**帯域幅**というカードとして表示されます。
- **保持期間**：**短め**、**標準**、**長め**、**カスタム値**と、ルールがどのバックアップを保持するかのタイムライン。[保持期間](#keep)を参照してください。
- **すでにこの保存先の下にあります**：手入力したアドレスがこの保存先のフォルダー内にあるセクション。引き継ぐと、リポジトリはその場所のままになります。サインイン、ストレージクラス、削除に対する保護は、そのあと保存先から引き継がれます。BombVault はまず、保存先のサインインがリポジトリを開けることを確認し、append-only のリポジトリを、append-only ではない保存先の下に置くことは拒否します。
- **セクションごとのルール**：この保存先での、1 つのセクションの専用のリポジトリ、保持、圧縮。**ルールを変更**でそれらを開き、**保存先の設定に戻す**でセクションを元に戻します。サインイン、帯域幅、コピーが実行されるタイミングは、常に保存先から引き継がれます。
- 保存先がどれだけいっぱいかを示す容器と、満杯になる位置の印、直近数週間の増加ペースで残り何週間かが表示されます。サイズを報告しない保存先には**サイズ不明**と表示されます。

**移動**と**保存先を削除**はページの操作の中にあり、[移動と削除](#move-remove)で説明しています。

バックアップがあった遠隔の保存先が、突然リポジトリを持たなくなった場合（ディスクがマウントされなかった rest-server など）、新しい空のリポジトリは自動では作られません。バックアップまたはコピーがリポジトリのないことに気づいた時点で、そのページにそう表示されます。ディスクをもう一度マウントしてください。古いリポジトリを意図的に空にした場合は、**ここに新しいリポジトリを作成**で、保存先とそのリポジトリのすべてのセクションに対して、一度にやり直します。

グループの別のインスタンスが動かす受信サーバーは、プロバイダーの中に**グループから**として表示されます。[受信サーバー](#receiving-server)を参照してください。

BombVault は、起動のたびに保存先を確認します。あなたの判断が要らないもの、たとえばなくなったコピーやリポジトリへのリンク、セクションの専用フォルダーへのコピー、コピーがなくなったダイレクトリポジトリなどを自動で直し、直したものごとにログに 1 行を書きます。安全な直し方がないものは、ログに書かれるだけです。

### 保持期間 {#keep}

バックアップをどれだけ保持するかは、保存先ごとに、その**保持期間**カードで設定します。ルールは、その保存先にあるコピーと専用フォルダーに適用され、**ローカル**の保存先も含みます。セクションは、1 つの保存先で**セクションごとのルール**の下に独自の値を持てて、そのセクションについては、保存先のカードより優先されます。

ルールは、設定した範囲まで遡って、日、週、月、年ごとに 1 つのバックアップを保持し、残りは各バックアップまたはコピーのあとに整理されます。

| プリセット | 最新のバックアップ | 日 | 週 | 月 | 年 |
|---|---|---|---|---|---|
| **短め** | 0 | 7 | 4 | 3 | 0 |
| **標準** | 0 | 7 | 4 | 6 | 2 |
| **長め** | 0 | 14 | 8 | 12 | 3 |

**カスタム値**では、5 つの数を自分で設定します。0 はその数をオフにし、すべての数が 0 のルールはすべてを保持します。カードの点は、40 個のサンプルバックアップのうち、ルールがどれを保持するかを示し、最新が右端です。図は BombVault がそこにあるバックアップを読み取る前に描かれるので、サンプルはすべての保存先で同じです。サンプルは今日から遡って数えるので、残る点の数は日付によって変わります。

**保持を減らす前に確認する**は、標準でオンで、保持するバックアップが減る変更を保存する前に確認し、新しいルールが 40 個のサンプルのうち何個を削除するかを伝えます。すべての保存先に適用されます。**セクションごとのルール**の**保存先の設定に戻す**も、同じ質問をします。

削除に対する保護のある保存先は、このマシンから整理されることがありません。古いバックアップを保持するか手放すかは、相手側が自身のルールで決めます。項目に、データ消失に関する重大な異常が未処理のあいだは、確認済みにするまで、保持ルールはその項目の古いバックアップを残します。[異常](anomalies.md)を参照してください。

次の実行が実際に何を削除するかを見るには、**設定、保存先** の**プレビュー**を開きます。**次回の実行で削除されるもの**が、リポジトリごと、項目ごとに、リストアポイントの名前とともに一覧されます。ロックを取らず、何も変更しません。

![標準を選んだ保持期間：点は、40 個のサンプルバックアップのうちどれが残るかを示す。](assets/screenshots/storage/keep-dark.png#only-dark)
![標準を選んだ保持期間：点は、40 個のサンプルバックアップのうちどれが残るかを示す。](assets/screenshots/storage/keep-light.png#only-light)

#### 例：標準が残すもの {#example-retention}

コンテナは、2024 年 10 月 1 日から毎晩 03:00 にバックアップされていて、2026 年 11 月 4 日（水）には 765 個のバックアップがあります。保存先は**標準**に設定されています。日 7、週 4、月 6、年 2 です。

それぞれの数は、その日、週、月、年の最新のバックアップを保持し、複数の数が選ぶバックアップは 1 回だけ保持されます。週は月曜から日曜までです。

| ルール | 選ばれるバックアップ | 新たに加わるもの |
|---|---|---|
| 日 7 | 11/4、11/3、11/2、11/1、10/31、10/30、10/29 | 7 個すべて |
| 週 4 | 11/4、11/1、10/25、10/18 | 10/25、10/18 |
| 月 6 | 11/4、10/31、9/30、8/31、7/31、6/30 | 9/30、8/31、7/31、6/30 |
| 年 2 | 11/4、2025/12/31 | 2025/12/31 |

これで、765 個のうち 14 個が残ります。最も古いのは 2025 年 12 月 31 日のもので、今日の時点で 10 か月強遡れます。重複排除のおかげで、フルバックアップ 1 回分と、その間の変更分をわずかに上回る程度の容量しか使いません。

**年**は、もう一度見る価値があります。これは、バックアップのある暦年を、今年から数えます。そして今年の最新のバックアップは今日のものです。そのため 1 年目はほかの数に何も加えず、2 年目で前年の最後のバックアップが加わります。ルールで遡れる期間が 1 年を通して変わるのは、このためです。同じバックアップを各プリセットで見ると次のようになります。

| プリセット | 今日残るバックアップ | 今日の最も古いバックアップ | 1 年を通して遡れる期間 |
|---|---|---|---|
| **短め** | 10 | 2026 年 9 月 30 日 | 1 か月から 2 か月 |
| **標準** | 14 | 2025 年 12 月 31 日 | 早春は約 4 か月、12 月 31 日にはまる 1 年 |
| **長め** | 30 | 2024 年 12 月 31 日 | 1 月 1 日に 1 年、12 月 31 日に 2 年 |

**標準**から**短め**にすると、**保持を減らす前に確認する**によって、先に確認が出ます。確認には、図の 40 個のバックアップのうち新しいルールで何個が削除されるかが示されます。この数はサンプルから出ているので、日付によって変わり、自分のバックアップを数えたものではありません。この例のバックアップでは、8 月 31 日、7 月 31 日、6 月 30 日、2025 年 12 月 31 日が削除されます。**それでも保存**でルールが適用され、次のプルーンが、その保存先からそれらを完全に削除します。

この保存先で、コンテナをほかより長く保持したい場合は、**セクションごとのルール**の**ルールを変更**を押して**コンテナ**を選び、**コンテナのルール**で**カスタム値**を、たとえば日 14、週 8、月 12、年 2 に設定します。ほかのセクションは引き続き保存先のカードに従い、**保存先の設定に戻す**でコンテナを戻せます。

### 認証情報 {#sign-ins}

認証情報は、BombVault が S3 サービスや rest-server に使うキーまたはパスワードです。認証情報は 1 つの一覧で、**設定、保存先** の**認証情報**カードにあり、各行に、どの保存先が使っているか（**使用先**）が表示されます。

- **保存先を追加するときに保存されます。** 保存先を追加すると、入力したキーが認証情報として保存されます。同じサービスの次の保存先は、**新しいキー**の代わりに**保存済みの認証情報**でそれを選べ、あとでそれを変更すると、それを使うすべての保存先に適用されます。
- **既定。** 星印が既定の認証情報を示します。手入力したアドレス、取得元、新規インストールでの復旧など、認証情報を選んでいない場所では、それが使われます。**既定にする**で、星印を別のものに移せます。
- **編集とテスト。** **編集**は、ここからでも、保存先の**認証情報**カードからでも、認証情報の 1 つのウィンドウを開きます。**テスト**は、何かを保存する前に、入力したもので、それを使うすべての保存先にサインインします。**保存**で保存されます。
- **削除。** 認証情報を削除できるのは、それを使う保存先や取得元がないときだけで、既定のものは最後の 1 つとしてしか削除できません。行に、まだ何が使っているかが表示されます。
- **保存先の接続を変更しても**、ほかの場所が共有している認証情報は書き換えられません。代わりに、その保存先に専用の認証情報が与えられ、ウィンドウは、事前にその認証情報が共有されていることを伝えます。共有しているものをすべての場所で変えるには、**認証情報**カードで編集してください。

![認証情報カード：保存済みの認証情報ごとに、それを使うものと、既定の星印。](assets/screenshots/storage/signins-dark.png#only-dark)
![認証情報カード：保存済みの認証情報ごとに、それを使うものと、既定の星印。](assets/screenshots/storage/signins-light.png#only-light)

このサーバー上のフォルダーには認証情報は不要です。SMB、WebDAV、SFTP、Storage Box、クラウドドライブは、自分のものを rclone 設定に保持していて、保存先の **rclone.conf** カードに表示されるので、この一覧には現れません。

### SMB、WebDAV、そのほかの rclone リモート {#smb-webdav}

Windows や Samba の共有と WebDAV サーバー（Nextcloud、ownCloud、SharePoint、そのほか）は、**保存先を追加**の**NAS またはサーバー**にあるプロバイダーのタイルです。ホストと共有（SMB）、またはアドレスとサーバーの種類（WebDAV）、ユーザー、パスワードを入力すると、BombVault が rclone のセクションを書きます。rclone は、保存する前にパスワードを難読化します。

どのタイルにもないサービスには、**独自の rclone 設定**の下の **Rclone** タイルで、rclone.conf から貼り付けたリモートを使えます。それらは BombVault がすでに持っているリモートに追加され、置き換えることはなく、暗号化して保存されます。セクションをその 1 つにバックアップするには、そのセクションのオフサイトのリポジトリとして `rclone:<remote>:<folder>` を入力します。たとえば `rclone:nas:backups/bombvault` です。共有やバケットは最初のパスのセグメントで、名前の一部ではありません。

これは、共有を Unraid にマウントするより良い方法です。restic は、マウントされた CIFS 共有にリポジトリを置くことをすすめておらず、ここでは何もマウントされません。NFS には、restic にも rclone にも NFS バックエンドがないため、タイルがありません。NFS では、エクスポートをホストにマウントして、ローカルフォルダーとして使ってください。

### 移動と削除 {#move-remove}

- **移動**は、1 つのセクションのコピーを、履歴全体とともに別の保存先に移します。古い場所にはすべてが残り、BombVault はそこで何も削除しません。移動はバックグラウンドで実行され、時間がかかることがあります。ローカルディスク間なら 100 GB あたり約 9 分、遅い回線では数時間です。実行中は概要に表示されます。
- **保存先を削除**には 2 つの方法があります。**保存先を削除し、バックアップは残す**は、そこへの書き込みを止め、バックアップはそのままにします。あとで **復元、古いバックアップフォルダーから** で読み取れます。**保存先を削除し、そこのバックアップも削除する**は、まずそこに保存されているものを読み取って一覧します。どのバックアップが消えるか、そのうち他のどこにもないもの、そして削除に対する保護が拒否する、項目がまだ直接バックアップしている、ほかの保存先やセクションがそこにコピーを置いている、読み取れなかった、といった理由で残るリポジトリです。唯一のバックアップを失う項目は別に一覧され、**これらも削除する**をオンにしない限り残されます。保存先の名前を入力して確認すると、削除がバックグラウンドで実行されます。
- これは、あらゆる種類の保存先で動作します。複数のセクションが使うもの、1 つのセクション用に設定した保存先、自分で設定したリポジトリ、セクションが自身のバックアップを書き込むフォルダーです。削除されたリポジトリにバックアップしていた項目は、再びセクションに従い、そこを指していたセクションの既定も同様です。セクションのフォルダーは、すべてのセクションに必要なので、単純には削除できません。ウィンドウが、セクションの移動先のフォルダーを尋ね、各セクションはその下で自身のフォルダー名を保ちます。
- 保存先のバックアップを削除するには、ログインパスワードと、そのインスタンスでのサインインが必要です。パスワードがなくても保存先自体は削除できますが、そのバックアップをここから削除することはできません。

### 例：Backblaze B2 へのオフサイトコピー {#example-s3}

コンテナとセルフバックアップを、サーバーが壊れても一緒に失われないよう、Backblaze B2 にも置きたいとします。同じ手順は、Wasabi、Hetzner Object Storage、そのほかのほとんどの S3 サービスにも当てはまります。

1. **B2 で、**近くのリージョンに `tower-backups` のようなプライベートバケットを作成します。**Application Keys** で、そのバケットに限定した読み書きのキーを作成し、キー ID とアプリケーションキーを控えます。B2 はアプリケーションキーを一度だけ表示します。バケットのライフサイクルを、最後のバージョンのみ保持にしてください。そうしないと、B2 は整理されたデータを非表示のバージョンとして保持し、その分が請求されます。
2. **プロバイダー。** BombVault で**保存先**を開き、**保存先を追加**を押して、**S3 サービス**の**Backblaze B2** を選びます。
3. **サインイン。** キー ID を**アクセスキー ID**、アプリケーションキーを**シークレットアクセスキー**として入力します。**エンドポイント**にバケットのエンドポイント（たとえば `s3.eu-central-003.backblazeb2.com`）を入力すると、BombVault がそこからリージョンを読み取ります。このキーは 1 つのバケットしか開かないので、**バケット**に `tower-backups` を入力します。
4. **接続をテスト。** **接続できました**と表示され、バケットのフォルダーが一覧されるはずです。**新しいフォルダー**を押して `bombvault` と名付けます。BombVault はその中に、`bombvault/containers` のように、セクションごとに 1 つのフォルダーを置きます。
5. **保護。** ウィンドウには、B2 はオブジェクトロックで古いバージョンを保持できるが、BombVault はそれを確認できないという説明が出ます。バケットが本当に削除を拒否するのでない限り、**削除に対する保護(append-only)**はオフのままにして、BombVault が保存先の保持ルールでプルーンできるようにします。
6. **対象セクション。** **コンテナ**と**セルフバックアップ**にチェックを入れます。セルフバックアップは設定を保持しているので、新しいインストールがそれを取り戻せます。ウィンドウには、最初のコピーが持っていく項目の数と、分かる場合は履歴の量が表示されます。
7. **保存先を保存**を押します。

最初のコピーは、次のバックアップのあとに実行されます。今すぐ始めるには、**設定、保存先** を開き、**オフサイトコピー**のセクションの行の**今すぐ複製**を押します。ステータス欄には**オフサイトコピー実行中**と表示されます。最初のコピーは履歴全体を持っていくので、100 Mbit/s の上り回線で 200 GB なら約 4 時間半かかります。以降のコピーは、新しいものだけを送ります。

回線を空けておくには、保存先のページを開いて、**コピー**カードの**アップロード制限 (KiB/s)** を、たとえば `5120` に設定します。これは約 5.0 MB/s（41.9 Mbit/s）と表示されます。ついでに、同じページの**保持期間**も確認してください。

うまくいったかを確認するには、概要の**保護ステータス**で**オフサイト**が**コピーは最新**になっていることと、コンテナの**バックアップ**タブで、スナップショットが 2 つ目の場所として `tower-backups` を示していることを見てください。そのあと、**設定、復元** の**リカバリーキットをダウンロード**をもう一度押してください。キットには、新しい保存先とそのサインインが載っているからです。

**Cloudflare R2 も同じ手順です。** キーの代わりにオブジェクトトークンを使います。R2 のダッシュボードに表示される、バケット付きの S3 アドレスを貼り付けると、BombVault がサーバーとバケットを自動入力します。

### 例：自分で動かす rest-server {#example-rest-server}

append-only モードの rest-server は削除を拒否するので、サーバーが乗っ取られても、そこにあるコピーは残ります。友人の家やガレージなどにある 2 台目のマシンで十分です。ペアリング済みの BombVault が設定してくれることもあります。[受信サーバー](#receiving-server)を参照してください。任意の Docker ホストで手動で動かすには：

```sh
docker run -d --name rest-server --restart unless-stopped \
  -p 8000:8000 \
  -v /mnt/user/backups/rest-server:/data \
  -e OPTIONS="--append-only --private-repos" \
  restic/rest-server
docker exec -it rest-server create_user bombvault
```

最後の行はパスワードを尋ね、データフォルダーの `.htpasswd` ファイルにユーザーを書き込みます。

1. BombVault で**保存先を追加**を押し、**NAS またはサーバー**の **rest-server** を選びます。
2. ユーザーをフォルダーとしたアドレス（たとえば `http://192.168.2.20:8000/bombvault`）と、**ユーザー名**、**パスワード**を入力します。**接続をテスト**を押します。
3. **保護**で、**削除に対する保護(append-only)**をオンにします。BombVault はそこをプルーンせず、相手側に任せます。
4. セクションにチェックを入れて、**保存先を保存**を押します。
5. 最初のコピーができたら、保存先のページを開いて**削除に対する保護を今すぐテスト**を押します。BombVault はテスト用のオブジェクトを削除しようとします。カードに**直近：削除が拒否されました**と表示され、概要の**削除に対する保護**が**確認済み**になるはずです。**直近：削除は拒否されませんでした**と表示される場合は、`--append-only` が足りません。

このコピーをここからプルーンするものは何もないので、セクションのウィンドウ（**オフサイトコピー**のその行の**編集**で開きます）で**増加予算（GB、0 = オフ）**を設定して、ディスクがいっぱいになる前に知らせてもらいましょう。自己署名証明書の場合は、上の `certs` に関する注意を参照してください。

## セクションの専用フォルダー {#own-folder}

すべてのセクションには専用フォルダーがあります。これは、バックアップが最初に書き込まれるリポジトリです。ほかの保存先へのコピーは、そこから送られます。新規インストールでは、専用フォルダーはこのサーバー上の `/mnt/user/bombvault` の下にあり、まとめて**ローカル**の保存先になります。

専用フォルダーは、すでにある保存先（NAS、rest-server、S3 バケットなど）の中に置くこともできます。その場合、セクションはそこに直接バックアップし、間にローカルコピーはなく、専用フォルダーはその保存先のサインイン、削除に対する保護、帯域幅の制限に従います。BombVault はバックアップのたびに、その保存先の**保持期間**カードに従って専用フォルダーを整理し、**セクションごとのルール**にあるセクション独自の値はカードより優先されます。保存先は、その**専用フォルダー**カードにセクションを一覧し、**セクションごとの保存先**は、その保存先をセクションの拠点として表示します。

### 専用フォルダーを移動する {#move-own-folder}

1. 専用フォルダーを置きたい保存先を開き、**専用フォルダーにする**か、その**専用フォルダー**カードの**セクションを追加**を選びます。複数のセクションを一度に移すには、ローカルの保存先の**接続**カードにある**ここにある専用フォルダー**の横の**専用フォルダーを移動**を選びます。
2. **セクション**でセクションを、**移動先**で場所を選びます。**別の場所**には、このホスト上のフォルダーか、手入力したリモートリポジトリのアドレスを、保存済みの認証情報からのサインインとともに指定できます。
3. **実行される内容**を読みます。セクションごとに、新しいバックアップがどこへ行くか、新しい場所にすでにあるコピーが専用フォルダーになるか、どのバックアップが先にコピーされるかが書かれています。
4. **作成済みのバックアップをコピー**は標準でオンです。オフにすると、古いバックアップはそのままの場所に残り、そこから復元できます。
5. **切り替え**を選びます。新しい場所の**保持期間**カードで残るものが、今のセクションのルールより少ない場合、BombVault は先に**保持を減らしますか?** と尋ねます。そこで**そのセクションの現在の値をセクションごとのルールに残す**を選ぶと今の値を引き継ぎ、**それでも保存**を選ぶとそのまま進み、**戻る**を選ぶとすべて元のままです。バックアップを先にコピーする必要がある場合、BombVault はそれをコピーしてから専用フォルダーを切り替えます。すでにそこにある場合は、切り替える前にそれを確認します。

移動のあと、新しいバックアップは移動した専用フォルダーに行きます。**ローカル**をオフにして、コピーに直接バックアップしていたセクションも同じです。新しい場所にすでにあったコピーが専用フォルダーになり、そこへのコピーは終わります。そのコピーが、セクションの保持ルールより長くバックアップを保持していた場合、セクションは、どちらかのルールが保持するものをすべて保持するので、どれも失われません。

移動を進められない場合は、**実行される内容**の下の枠にウィンドウが理由を書きます。古いバックアップのコピーだけが障害になっているときは、**作成済みのバックアップをコピー**をオフにすると、それなしで専用フォルダーを移動できます。

セクションには常に専用フォルダーが必要です。それを持つ保存先を削除する場合は、セクションの移動先フォルダーを尋ねられます。[移動と削除](#move-remove)を参照してください。新しいバックアップが通り過ぎる専用フォルダー（セクションがコピーに直接バックアップしているため）は、保存先が使用先を一覧する場所で **(オフ)** と印が付きます。

#### 例：コンテナを NAS へ移す {#example-own-folder}

キャッシュプールがいっぱいになってきました。`nas` という保存先があり、2 台目のマシンの SMB 共有です。コンテナのセクションには、このサーバーの専用フォルダーに 61 個のバックアップがあり、Backblaze B2 にコピーされています。

1. **保存先**を開いて `nas` を開き、**専用フォルダーにする**を押します。
2. **セクション**で**コンテナ**にチェックを入れます。
3. **実行される内容**を読みます。コンテナの新しいバックアップは `nas` のフォルダーへ行くこと、ローカルにある 61 個のバックアップが先にそこへコピーされること、コピーが Backblaze B2 へ続くこと、保護、帯域幅の制限、増加アラームは `nas` から引き継がれることが書かれています。
4. **作成済みのバックアップをコピー**はオンのままにして、**切り替え**を押します。

BombVault はバックアップをバックグラウンドでコピーしてから、専用フォルダーを切り替えます。`nas` のページには、**専用フォルダー**にコンテナが一覧され、セクションに従う項目は `nas` を拠点として示し、次のバックアップはそこに着地して、B2 へのコピーは `nas` から送られます。これからは `nas` の**保持期間**カードがこのフォルダーを整理します。このサーバー上の古いフォルダーはそのまま残り、BombVault はそこで何も削除しません。

### リモートアドレスを手入力する {#remote-primary-repositories}

ローカルの保存先の**接続**カードは、セクションの専用フォルダーのリモートアドレスも引き続き受け付けます。セクションの横の**変更**が、**ローカル / リモート**のスイッチ付きのウィンドウを開きます。**リモート**は、`s3:...`、`rest:http://host:8000/repo`、`sftp:user@host:/repo`、`rclone:remote:bucket/path` のような restic のアドレスを受け付けます。**リモートプライマリの安全設定**は、接続テスト、アップロードとダウンロードの制限、オフサイトの保存先と同じ改ざんテストつきの append-only 保護、増加予算のアラームを追加します。

そのようなアドレスは、既定の認証情報でサインインします。持っている保存先のフォルダー内にある場合は、その保存先のページの**すでにこの保存先の下にあります**にセクションが一覧され、引き継ぐと、保存先のサインイン、ストレージクラス、削除に対する保護が与えられます。**専用フォルダーにする**で専用フォルダーを保存先の中に移すほうが簡単です。何かを変更する前に、ウィンドウが作成済みのバックアップを確認してくれるからです。

## 項目ごとの配置 {#placement}

項目の設定タブにある**スケジュールと保存先**カードには、ボタンの並びがあります。**ローカル**と、セクションのオフサイトの保存先ごとに 1 つのボタンです。点灯しているボタンが、その項目のバックアップを受け取ります。

- **ローカル**が点灯していると、項目は**保存先**に示されるリポジトリに書き込まれ、点灯しているほかのすべての保存先にコピーされます。保存先を消灯すると、その項目から新しいものを受け取らなくなります。ローカルだけならどこにもコピーしません。NAS 上にある共有など、すでに 2 つ目のコピーがあるデータに向いています。
- **ローカル**が消灯していると、項目は、点灯している最初の保存先のダイレクトリポジトリに直接書き込まれ、そこから点灯しているほかの保存先にコピーされます。最初のときは、ダイアログがそのダイレクトリポジトリを作成します。
- ボタンの 1 つは点灯したままになります。バックアップには行き先が必要だからです。項目をバックアップから外すには、**バックアップしない**を使います。

BombVault が、リポジトリ間でバックアップを移動することはありません。セクションに従う項目は、セクションの既定が変わるとそれに追従します。次のバックアップは新しい場所に着地し、すでにあるバックアップはそのままの場所に残ります。項目自身で選んだ保存先は、最初のバックアップから固定されます。設定タブの**リポジトリ**カードがそれを示します。コピーはいつでも変えられます。項目を受け取らなくなった保存先は、すでにあるコピーを保持し、セクションの次のオフサイト実行で、自身の保持に合わせて整理します。append-only の保存先からは削除できません。

項目が離れた場所は、そのバックアップを保持します。項目の**バックアップ**タブと**復元**では、**以前のバックアップのみ**と表示され、そこからの復元はまだ読み取れ、そこでのプルーンはそれらのバックアップに手を付けません。

**既定に従う**は、独自の選択をしている項目をセクションに戻します。先に確認を求め、その後新しいバックアップがどこへ行くか、各保存先が何を受け取らなくなるか、次の実行で何がアップロードされるかを示します。

並びの下には、カードに、項目がどこへ行くか、実際にそこに何があるかが書かれます。いくつの拠点がそれを保持しているか、各保存先が最後に確認された時刻、3-2-1 を満たしているかどうかです。拠点とは、元のデータのあるサーバー、各オフサイトの保存先、**施設外**と印の付いた各リポジトリです。BombVault はコピーと拠点を確認します。3-2-1 の「2 種類のメディア」の部分は確認しません。

### セクションごとの既定 {#placement-defaults}

保存先のページの**セクションごとの保存先**カードは、すべてのセクションの既定を、3-2-1 の流れとして描きます。セクションから保存先への各線はスイッチで、フラッシュドライブ、ZFS データセット、セルフバックアップを含むすべてのセクションの**ローカル**も同様です。線や点をクリックするとすぐ切り替わり、破線はオフです。セクションの**ローカル**をオフにするときだけは、そのセクションがコピーに直接バックアップするようになるため、先に既定カードと同じダイアログで確認されます。**キャンセル**は、すべてを元のままにします。**グラフ / スイッチ**は、同じ内容をボタンの行として表示します。スイッチは、新しいバックアップの行き先を決めます。独自の選択をしていない項目と、Compose スタックのプロジェクトフォルダーはすぐに追従するので、次のバックアップは新しい場所に行きます。すでに保存されたバックアップはそのままの場所にあり、そこから引き続き復元できます。フラッシュ、ZFS データセット、セルフバックアップは、ローカルフォルダーにバックアップし、そのバックアップからオフサイトにコピーします。**ローカル**への線もオフにできます。その場合、それらのバックアップはオフサイトの保存先に直接行き、レプリカがあって保存先が 1 つもない ZFS 項目は、レプリカを送るだけです。

**ローカル**がオフで、オフサイトの保存先だけがオンの場合、セクションはそこへ直接バックアップし、BombVault がそこのリポジトリを自分で選びます。コンテナ、VM、フォルダーセットは、下で説明する、オンの最初の保存先のダイレクトリポジトリに行き、そこからほかにコピーされます。フラッシュドライブ、ZFS データセット、セルフバックアップは、オンのすべての保存先に各バックアップを書き込み、各保存先はそれぞれの保持で保持します。

すべての線がオフのセクションには、**未バックアップ**と表示されます。その項目はバックアップされず、未保護として数えられます。

ページで独自の保存先を選んだ項目は、それを保ちます。流れには、セクションの中にそういう項目がいくつあるか（たとえば **2 件が異なります**）が示され、そこへ案内されます。1 つなら項目の設定タブへ、複数ならそれぞれのバックアップ先の一覧へです。そこの**既定に従う**で、項目を戻せます。

新しいオフサイトの保存先は、ローカルに設定されていないすべての項目を受け取ります。追加するウィンドウには、いくつの項目か、分かる場合は履歴の量が示されます。

### ダイレクトリポジトリ {#direct-repositories}

ダイレクトリポジトリは、項目がオフサイトの保存先に直接バックアップする場所です。BombVault は、それを保存先のフォルダーの隣に、名前に `-direct` を付けて置きます。保存先がバケット、そのリモート、rest-server のユーザーのルートにある場合は、その中に `containers-direct` のようにセクションの名前を付けたフォルダーを置きます。ストレージのページの流れでは、確認なしに作成されます。1 つの項目だけ Local をオフにして、ダイレクトリポジトリのない保存先が拠点になる場合は、提案される場所（たとえば `s3:https://s3.eu-central-003.backblazeb2.com/bucket/containers-direct`）と、何も作成しない接続テストを含むダイアログが開きます。**作成して使う**はリポジトリを作成し、項目をそこへ向けます。ダイレクトリポジトリには、独自の設定がありません。保存先のスイッチ、認証情報、ストレージクラス、制限、append-only の設定、保持に従い、それらとともに変わります。保存先のページの**ここに直接バックアップ**に、そこへ直接バックアップする各セクションと項目数とともに一覧されます。もう何もバックアップしていないものには、そこでその旨が表示され、削除できます。その場所のバックアップは残ります。保存先の新しいキーでそれを開けない場合、ダイレクトリポジトリは持っているキーを保ち、保存時にそう伝えます。ダイレクトリポジトリ上の項目は、そこからほかの点灯している保存先にコピーされ、そのリポジトリが属する保存先にはコピーされません。そのスナップショットにはタグ `bv:direct` が付き、ほかのすべての保持処理がそれを残すので、保存先とのつながりを失ったダイレクトリポジトリが、ローカルのルールで古くなることはありません。B2 は S3 エンドポイント経由で、キー ID とアプリケーションキーを S3 キーとして入力して届きます。保存先自身のフォルダーに限定したキーは、その隣のフォルダーには届かないので、代わりにその上のフォルダーに限定してください。

### 施設外 {#off-the-premises}

保存先やリポジトリには、**施設外**の印を付けられます。リモートのものは最初から印が付いています。同じ建物内の rest-server では、これをオフにします。この印は、カードでの拠点と 3-2-1 の数え方にだけ影響します。コピーは何も変わりません。

ZFS レプリカは、設置場所の外のコピーですが、履歴のあるバックアップではありません。設定した数のスナップショットしか保持せず、古いバージョンと単一のファイルは、引き続きバックアップから取り出します。ZFS サーバーから、もう一方のサーバーへ、SSH 経由で ZFS サーバーに、またはペアリング済みのインスタンスの受信エンドポイントに、直接送られます。ペアリンググループはリクエストを運ぶだけです。[レプリカ](zfs-datasets.md#replica)を参照してください。

### 再構築のあと {#after-a-rebuild}

コピーの選択は、BombVault 自身の設定の中にあります。**バックアップを検出**や、設定を復元しない緊急ウィザードで再構築したあとは、それらは失われ、すべてをコピーすると、除外していた項目が再び B2 に送られてしまいます。そのため、再構築されたすべてのセクションのオフサイトコピーは一時停止します。概要にそう表示され、**セクションごとの保存先**カードに**既定を確認**が表示されます。次の実行でコピーされるもののプレビューと、項目のないバックアップにある名前も表示され、そこで外せます。一時停止を終わらせるのは、確認だけです。設定ファイルのインポートは、ルールと既定は戻しますが、一時停止は終わらせません。

## 削除に対する保護(append-only) {#delete-protection-append-only}

オフサイトの保存先に削除に対する保護をオンにすると、ランサムウェアや侵害されたホストが、バックアップを削除したり書き換えたりできなくなります。相手側（`--append-only` モードで動く `restic/rest-server`）が**強制**します。BombVault は**確認**するだけで、設定上の主張だけで緑にすることは決してありません。このサーバー上のフォルダーは、削除を拒否できません。BombVault を制御する人がフォルダーも制御するからで、そのためローカルの保存先にはこのスイッチがありません。

スイッチは保存先に属します。そこへコピーするセクションはそれを保存先から引き継ぐので、**保存先**の保存先のページでオンにしてください。スケジュールされた**削除保護のチェック**は、スイッチがオンの保存先へコピーしているセクションがあるあいだだけ実行されます。相手側は `--append-only` で起動する必要があります。`restic/rest-server` イメージでは、TrueNAS でもほかの Docker ホストでも、`OPTIONS` 変数に入れます。

OneDrive などのクラウドドライブのように、削除をまったく拒否できない場所もあります。そこに意図的にコピーを置く場合は、保存先のページで**削除に対する保護なしで承認**をオンにします。すると概要は、承認された保存先にしかコピーしないセクションの、欠けている削除に対する保護を、承認されたリスクとして、琥珀色のドットではなくグレーのリングで表示し、セクションの色はほかのチェックに従います。ほかには何も変わりません。そこのバックアップは引き続き削除でき、BombVault は引き続き保存先の保持ルールでプルーンし、削除に対する保護がオンになると、このスイッチは消えます。別の場所に移されたコピーは、承認を失います。削除に対する保護をオンにしても、承認は消えます。

append-only のコピーへの最短の道は、[受信サーバー](#receiving-server)を持つペアリング済みの BombVault です。append-only モードの rest-server を、代わりに動かしてくれます。

!!! note "`/locks/` の下での削除の成功は想定どおりです"
    append-only は、何も二度と削除できないという意味ではありません。restic は自身のロックを取って解放する必要があるため、`/locks/` は設計上、書き込みと削除ができます。ランサムウェアが狙うスナップショットとその裏のデータは、削除できません。相手側を自分で調べるとき、`/locks/` の下での削除が成功するのは正しい動作で、保護の穴ではありません。

!!! warning "append-only のリポジトリは、このマシンからは決してプルーンされません"
    append-only の保存先では、ここから古いスナップショットをプルーンすることはありません。プルーンは相手側の仕事です。リポジトリのサイズが膨れ上がる前に知らせてもらえるよう、**増加予算のアラーム**を設定してください。

## 改ざんテスト {#tamper-test}

BombVault は、存在しないオブジェクトを狙って、オフサイトのリポジトリに実際に削除を試みることで、append-only の保証を定期的に証明します。保存先のページの**削除に対する保護を今すぐテスト**で必要なときに実行でき、**設定、検証、自動チェック** の**削除保護のチェック**でスケジュール実行されます。

**削除保護のチェック**をオフにしても、隙間が隠れることはありません。削除に対する保護があるのに一度もテストされていない保存先は「未証明、チェックはオフ」と表示され、削除に対する保護のない保存先は、どちらの場合も「なし」と表示されます。

スイッチがオフのコピーはテストされず、保存先にその旨が表示されます。接続テストは読み取りだけなので、それでも実行されます。そのため、コピーをオンにする前に確認できます。

- **拒否された**は、保護されているという意味です。
- **承認された**は、保護されていないという意味です。
- **判定不能**な結果（サーバーに届かない、認証エラー）が、保存された判定を変えることは決してありません。

保護されている状態から保護されていない状態に本当に変わったときは、アラートが 1 回出ます。

## DR ドリル {#dr-drills}

BombVault は、バックアップが単に存在するだけでなく、実際に復元できることを示す、2 つのレベルの証明を提供します。

- **復元検証ドリル（ローカル）。** BombVault は定期的に `restic check --read-data-subset` を実行します（範囲が限られていて、ディスクを埋め尽くす完全な復元は決して行いません）。実行間隔は **設定、検証、自動チェック** で設定し、同じタイルの**バックアップをチェック**カードに結果が表示されます。
- **テスト復元（オフサイト）。** BombVault は、オフサイトのリポジトリから実際の対象を、隔離されたサンドボックスに復元し、ファイル単位、バイト単位で検証して、そのあと片付けます。これは、リポジトリが応答するだけでなく、オフサイトから復旧できることを証明します。

概要の**保護ステータス**カードは、これをセクションごとに 4 つのチェックにまとめます。このサーバー上の最新のバックアップ、オフサイトのコピー、そこでの削除に対する保護、そこからのテスト復元です。セクションをクリックすると詳細が表示され、カードが緑になるのは、検証された事実があるときだけです。削除に対する保護なしで承認した保存先は、警告ではなく、承認されたリスクとして数えられます。

## インスタンスのペアリング {#pairing}

複数の BombVault が 1 つのグループとして連携します。互いの保護状況を表示し、互いのためにロールを担い、互いの鍵を保管できます。インスタンスは 12 個の単語でグループに加わります。

![3 つの手順カードがあるペアリングページ。](assets/screenshots/offsite/pairing-dark.png#only-dark)
![3 つの手順カードがあるペアリングページ。](assets/screenshots/offsite/pairing-light.png#only-light)

最初のインスタンスで **設定、ペアリング** を開き、**フレーズを作成**を押します。3 つの手順カードで進め方が示されます。12 個の単語が、**コピー**ボタンのあるウィンドウに表示されます。ほかのすべてのインスタンスで同じ場所を開き、**フレーズを入力**を押して、貼り付けるか入力するか、そのウィンドウの**貼り付け**を押します。リストにない単語は、入力中にその位置とともに指摘され、最後の単語にはチェックサムがあるので、入力ミスや入れ替わった単語は、ペアリングされる前に見つかります。フレーズは 1 つのインスタンスでだけ作成してください。両方が作成した 2 つのインスタンスは、別々の 2 つのグループになります。1 分間誰も現れなければ、ページに 2 つの方法が出ます。単語をもう一度表示してそちらで入力するか、もう一方のインスタンスの単語を入力して、一度にそのグループに加わるかです。ペアリングはログインパスワードなしでも動きますが、設定してください。ないと、Web 画面を開ける人なら誰でも単語を読め、グループ経由で、そのインスタンスの restic パスワードを渡すロールを求められます。パスワードが設定されるまで、ペアリングカードにそう表示されます。パスワードがある場合、フレーズをもう一度表示するにはそれが必要です。**グループを抜ける**で、インスタンスをもう一度外せます。ペアリングページの**インスタンス**カードに、グループのメンバーが一覧されます。誰が誰のために何をしているかの図は、インスタンスのページにあります。

単語を知っている人は誰でもグループに加われるので、パスワードのように扱ってください。

**メンバーがどのように互いに届くか。** 各インスタンスは、サインインした瞬間にブラウザーから、ネットワーク上の自分のアドレスを知り、ペアリングページの**このインスタンス**カードの**既知のアドレス**に、インスタンス自身が見つけたものとともに一覧されます。リバースプロキシや特殊なポートが前にある場合は、そこで修正してください。同じネットワークでは、メンバーはそのアドレスをマルチキャストで知らせ合って直接通信します。Docker の標準のブリッジのように、マルチキャストがコンテナのネットワークを越えられない場所では、インスタンスが代わりに自分のサブネットでほかを探します。グループのメンバーだけが答えられる署名付きの呼び出しを使うので、リレーなしでも、ペアリングは数秒で完了します。何も見つからなければ、**見つかりませんか?**で、別のサブネットや標準でないポートのために、アドレスを 1 つ手動で指定できます。別のネットワークにあるインスタンスは、リレーを通ります。同じページの**リレー**カードにある 4 つの形から選びます。それぞれに図があります。

- **プロジェクトのリレー**（標準）：`parleyport.halleluja.design`。KnightLoader も使っているリレーです。設定は不要です。
- **自分のリレー**：Unraid Community Apps の [**ParleyPort**](https://github.com/junkerderprovinz/parleyport) コンテナ（**設定、アプリ** にもあります）。それを使うすべてのインスタンスに、そのアドレスを入力します。
- **BombVaultインスタンス**：すでに外から到達できる自分のインスタンスの 1 つで、**リレーとして機能させる**をオンにしたもの。そのインスタンスは、すでにあるリバースプロキシと証明書の背後で、自身のアドレスの `/relay/connect` で応答し、グループだけを通します。それを使うすべてのインスタンスに、そのアドレスを入力します。
- **リレーなし**：メンバーは同じネットワーク内でだけ、自動で互いを見つけ、それ以外では見つけられません。

**リレーに見えるもの。** 4 つの形の横にある同名のボタンが、選んだ形についてこれを表示します。メンバー間のすべての呼び出しは、12 個の単語から導出した鍵の AES-256-GCM で封じられ、その鍵があなたのインスタンスから出ることはありません。リレーが知るのは、接続をグループ化するハッシュ、メッセージがどのインスタンス宛てか、その大きさ、通過する時刻です。ローカルネットワークでの直接の呼び出しも同じように封じられ、署名もされるので、インスタンスが提供する自己署名証明書には何も依存しません。何かを渡す呼び出し（ロールの応答、restic パスワード、レシーバーのログイン、鍵の預け入れ）は、それを送るメンバーの鍵でも署名され、最初に見たときに固定されます。[セキュリティモデル](configuration.md#security-model)を参照してください。

**グループを通って運ばれるもの。** インスタンスのページの保護状況、1 つのセクションを今すぐチェックするリクエスト、ロールのリクエストとその応答、保存先の提供、そしてレシーバーや取得側がロールを許可されたあとに必要とするもの、つまり相手のインスタンスのリポジトリの場所とその restic パスワードです。バックアップデータは決して運ばれません。それは引き続き restic のバックエンドに直接行きます。APP_KEY も運ばれません。restic パスワードが開けるのはそのインスタンスのリポジトリだけで、保存されたシークレット、セッション、リカバリーコードは開けません。

**ペアリング前からあった項目。** フリートトークンで追加されたインスタンスと、相手のインスタンスの APP_KEY で設定された受信リポジトリと取得元は、アップデート後も残り、**再度ペアリング**と印が付きます。これらは動作し続けます。BombVault は最初の起動時に、保存されたそれぞれの APP_KEY を、そこから導出した restic パスワードに置き換えます。両方のインスタンスをペアリングしてから、項目を編集してそのインスタンスを選んでください。それまでは、そのような項目はインスタンスのページの**インスタンスなし**カードにあります。

APP_KEY を手動で受け取る唯一の場所は、[古いバックアップフォルダーから](#restore-from-another-bombvault-repo)です。もう一方のインスタンスが失われていて、グループの中で答えられない場合のためです。

## インスタンスとロール {#roles}

**インスタンス**のページ（サイドバーに固定できる設定のタイル）は、グループを、誰が誰のために何をするかのネットワークとして、このインスタンスのカードと、ほかのすべてのメンバー、Android スマートフォン、ZFS サーバーのカードとともに表示します。右下の**ペアリング**でペアリングページへ移動します。どの部分がオンかは **設定、インスタンス、複数のサーバー** で設定します。**インスタンス**、**レシーバー**、**取得**です。

![インスタンスのページ：ネットワークとしてのグループと、ロールのタイルがあるインスタンスごとのカード。1 つは非アクティブ。](assets/screenshots/offsite/instances-dark.png#only-dark)
![インスタンスのページ：ネットワークとしてのグループと、ロールのタイルがあるインスタンスごとのカード。1 つは非アクティブ。](assets/screenshots/offsite/instances-light.png#only-light)

各カードには、メンバーの保護状況と、そのロールがタイルとして表示されます。ロールとは、1 つのインスタンスがほかのインスタンスのために担うことです。

- **レシーバー**は、このサーバーのオフサイトコピーを、append-only モードの rest-server に保管します。このサーバーはバックアップのたびに送信し、乗っ取られても、そこで何も削除できません。
- **取得側**は、このサーバーのバックアップを自身のスケジュールで取得します。そのために、このサーバーが起動している必要はありません。
- **ZFS サーバー**は、このサーバーの ZFS レプリカを受け取ります。各 ZFS 項目は、設定の**レプリカ**でこれを選びます。
- **鍵の保管側**は、このサーバーのリカバリーキットの封じた写しを保管します。[鍵の保管側](#key-keeper)を参照してください。

ロールをオンにするとリクエストが送られ、もう一方のインスタンスの誰かが**許可**を押すまで、何も始まりません。リクエストはそのインスタンスのカードにバッジとして表示され、その**詳細**に**許可**と**拒否**とともに一覧されます。許可されたロールは、そこでいつでも取り消せます。ネットワーク図の破線は、まだ待機中のロールです。BombVault 9.x のインスタンスはリクエストに答えられないので、そこではロールをオンにするとすぐに有効になり、9.x のインスタンスからのリクエストは、こちらで**許可**を待ちます。

カードの**詳細**は、残りを開きます。そのメンバーの受信リポジトリと取得元、保存先の提供、モニタリング、**削除**、**キーを忘れる**です。

メンバーは、グループ経由で、自身のオフサイトストレージを別のメンバーに提供できます。もう一方の管理者は、メンバーの**詳細**でその提供を見て、承諾または拒否します。承諾すると、保存済みの認証情報と通常の保存先が、自分で入力した保存先と同じ確認のあとに作成されます。この方法で運ばれるのは接続の詳細だけで、バックアップデータは決して運ばれません。**今すぐ確認**は、メンバーに 1 つのセクションのリポジトリを検証するよう頼みます。ページの何かで、別のマシンのバックアップ、復元、削除を開始することはできません。

シャットダウンされたインスタンスと、アプリを閉じたスマートフォンは、カードが灰色の**非アクティブ**として、最後に見られた時刻とともに残り、**削除**するまでネットワーク図で薄く表示されます。このサーバーが起動した直後は、グループが戻るまで、そのようなカードに**確認中**と表示されます。**削除**は、どの部分がオンかに関係なく、そのようなカードで使え、そのメンバーの未処理のリクエスト、使われていない ZFS 受信スロット、待機中の鍵のリクエストも終わらせます。ペアリングページの**インスタンス**カードも、これらのメンバーを**非アクティブ**として一覧します。

## レシーバーと取得側 {#receiver}

別の BombVault から append-only のコピーを**受け取る**マシンでは、受信したリポジトリによって、受信側のハードウェア上で独立した読み取り専用のモニタリングができ、相手側での静かな失敗が見過ごされません。**設定、インスタンス** で**レシーバー**をオンにし、インスタンスのページで送信側のインスタンスの**詳細**を開いて、受信リポジトリを追加します（読み取り専用で、送信側の restic パスワードで開きます。これは[ペアリンググループ](#pairing)経由で受け取ります）。次のものが得られます。

- **ソースごとの一覧。** どのコンテナ、VM、フォルダーセットが着いたかを正確に確認できます。
- ソースごとの**最終受信**。それぞれがどれだけ新しいかが分かります。
- 受信側のハードウェアで実行される**独立した `restic check`**。送信側だけでなく、データが実際にある場所で整合性が検証されます。
- **デッドマンスイッチ：** 設定した期間内にソースが送信しなくなったときのアラート。
- **整合性アラート：** 受信側のチェックが失敗したときのアラート。

レシーバーは厳密に読み取り専用です。受信したリポジトリに書き込むことは決してないので、送信側が頼りにする append-only の保証を壊すことはありません。

取得側は逆に働きます。**取得**をオンにすると、インスタンスが別のメンバーのバックアップを自身のスケジュールで、ソースごとに自分専用のリポジトリへ読み取るので、このマシン自身のバックアップとして数えられることはありません。そのソースも、そのメンバーの詳細に表示されます。リポジトリの場所、保持するバックアップの種類、取得の頻度です。restic パスワードはグループ経由で届き、APP_KEY が届くことはなく、相手側は追加の設定が不要で、起動している必要もありません。ソースは読み取られるだけで、それぞれの側が自身のサインインを保ちます。`rclone:` のソースは拒否されます。rclone がこのインスタンスのリモートでそれに届いてしまうからです。

### 受信サーバー {#receiving-server}

受信側のマシンは、ほかのマシンがコピーする先の rest-server を動かすこともできます。**レシーバー**のリクエストがそれを求めているときに、最初に許可すると設定されます。ウィンドウに、サーバーには受信サーバーが必要であると表示され、共有上のフォルダー（作成用の**新しいフォルダー**付き）と、ポート（ほかのコンテナが使っていなければ 8000）を尋ねます。BombVault はそのあと、次のことを行います。

1. `rest-server` という名前のコンテナがすでにある場合、またはほかのコンテナがそのポートを使っている場合は拒否します。
2. `restic/rest-server` を取得し、Docker ソケット経由で、プライベートリポジトリとフォルダー内のログインファイル付きの append-only モードで起動します。
3. その Unraid テンプレートをフラッシュドライブに書き込むので、コンテナは Docker タブで編集可能なままになります。フラッシュドライブに届かない場合は、テンプレートをダウンロードとして提供します。
4. それに対して改ざんテストを実行し、削除を拒否するかどうかを表示します。

グループのインスタンスは、そのサーバーを、プロバイダーの**グループから**の下に、受信マシンの名前で見つけ、**レシーバー**のロールは、それを安全な選択として提案します。各インスタンスは、サーバーを最初に使うときに専用のログインを受け取り、そこでは自身のフォルダーにだけ書き込みます。**設定、インスタンス** で**レシーバー**をオンにしていれば、このインスタンスのカードの**受信サーバー**で、そのサーバーをもう一度開けます。そのウィンドウの**ログインを持つパートナー**にログインが一覧され、**ログインを取り消す**で 1 つを取り消せます。そのインスタンスがすでにコピーしたものは、フォルダーに残ります。セットアップでは、パスワードがウィンドウに一度だけ表示される**グループ外のログイン**も 1 つ作成されます。

リレー経由でしか受信マシンに届かないインスタンスは、サーバーを使えません。リレーはバックアップを運ばないからです。先にペアリングページで受信マシンのアドレスを追加してください。BombVault が自身の IP アドレス（たとえば br0 上）で動いている場合は、サーバーがホストのアドレスで待ち受けているので、**パートナー用アドレス**を入力してください。

## 例：2 台の Unraid をペアリングする {#worked-example-two-unraid-boxes-end-to-end}

これは、上の部分を完全に組み合わせた 1 つのセットアップです。組み合わさった形を一度見ると、組み立てやすくなるからです。

2 台のマシン：**TOWER** はコンテナを動かし、バックアップを送ります。**VAULT** はそれを受け取り、append-only を強制します。名前、アドレス、共有のパスは自分のものに置き換えてください。

**1. 2 台をペアリングする。** TOWER で **設定、ペアリング** を開き、**フレーズを作成**を押して、VAULT の**フレーズを入力**で 12 個の単語を入力します。先に両方でログインパスワードを設定してください。

**2. TOWER で、VAULT にレシーバーになるよう頼む。** インスタンスのページで、VAULT のカードの**レシーバー**をオンにし、セクションと、場所として **VAULT の受信サーバー**を選んで、リクエストを送ります。

**3. VAULT で許可する。** VAULT のインスタンスのページに、TOWER のカードにリクエストが表示されます。**許可**を押します。最初のときは、VAULT が受信サーバー用のフォルダー（たとえば `user/appdata/rest-server`）を尋ね、rest-server を append-only モードで起動し、それに対して改ざんテストを実行します。

**4. TOWER に戻る。** それ以降、TOWER はバックアップのたびに VAULT へコピーし、新しい保存先が、その削除に対する保護とともに TOWER の保存先のページに現れます。

改ざんテストの答えは次のとおりです。

| 結果 | 何が起きたか |
| --- | --- |
| **保護済み** | VAULT が削除を拒否しました。これだけが合格の状態です。 |
| **保護されていません** | VAULT が削除を受け付けました。`--append-only` が足りないか、外されています。 |
| **判定不能** | どちらでもありません。通常は、URL が restic 自身が使うものではないか、認証情報が変わっています。何も記録されず、アラートも出ません。 |

**5. 必要なら、届くものを見守る。** VAULT の **設定、インスタンス** で**レシーバー**をオンにし、TOWER の**詳細**を開いて、受信リポジトリを追加します。VAULT は TOWER の restic パスワードをグループ経由で受け取ります。誰も鍵を入力しません。

**6. 相互にする。** 逆の方向にも同じ手順を繰り返します。VAULT が TOWER にレシーバーになるよう頼みます。すると各マシンが相手のために append-only を強制し、どちらも相手のバックアップを削除できません。

手動で動かす rest-server も使えます。**保存先を追加**で rest-server として、`.htpasswd` のユーザーとパスワードで追加し、削除に対する保護をオンにします。そのオプションには `--append-only` を残してください。ないと、相手側はまた普通の共有に戻ります。

!!! warning "ローカルパスは、コンテナの中のパスです"
    BombVault がこのサーバー上のフォルダーを尋ねるときは、`/mnt/user/appdata/...` ではなく、`user/appdata/rest-server/bombvault-containers` のように、ホストのマウントからの相対パスで入力してください。BombVault はコンテナで動いており、ホストの `/mnt` は別の場所にマウントされています。ホストの絶対パスは、その中には存在しません。貼り付けた場合は、BombVault が代わりに使う相対パスを教えてくれます。

## 緊急ウィザード {#emergency}

**緊急ウィザード**は、失われた、またはセットアップし直したサーバーを取り戻します。**復元**ページの**緊急**から、そして新規インストールのウェルカムページの**バックアップから復元**から始まります。4 つの手順で進みます。**アクセス**、**設定**、**選択**、**復元**です。

1. **アクセス。** 古いバックアップの鍵を、3 つの方法のどれかで BombVault に示します。
    - **リカバリーキットをアップロード**：セットアップ中にダウンロードしたファイル。鍵とすべての保存先が入っていて、BombVault がそこから残りを入力します。age で暗号化したキットは、暗号化に使った識別子を求めます。一度だけ使われ、保存されません。
    - **グループ経由**：グループのインスタンスが鍵を預け入れとして保管しています。グループの 12 個の単語、取り出しコード、そしてそのインスタンスにいる人が必要です。[鍵の保管側](#key-keeper)を参照してください。
    - **鍵を入力**：古いサーバーの `APP_KEY` と、そのバックアップの場所。

    BombVault はそのあと、すべての保存先でその鍵を試し、それぞれについて、読み取れる、見つからない、別の鍵でロックされている、到達できない、まだ認証情報が足りない、のどれかを伝えます。まだ何も保存されておらず、鍵は限られた時間だけメモリに残ります。**鍵を引き継ぐ**は、このサーバーが今後その鍵でバックアップを書くようにします。**引き継ぎを取り消す**は、最初のバックアップが実行されるまで、自身の鍵に戻します。すでに自分のバックアップがあるサーバーは、引き継ぎを拒否し、代わりに[古いバックアップフォルダーから](#restore-from-another-bombvault-repo)を案内します。**認証情報を保存**は、キットが持つリモートの保存先の認証情報を保存し、このサーバーにすでにある認証情報を置き換える前に確認します。
2. **設定。** **設定を戻す**は、最新のセルフバックアップから、BombVault 自身の設定を復元します。保存先、認証情報、スケジュール、ルールです。BombVault はそれを適用するために、Docker ソケット経由で再起動するので、稼働中の設定データベースが開いたハンドルのまま上書きされることはなく、ウィザードはその後、自分で続行します。このサーバーのログインは残ります。今使っているパスワードでサインインし続けます。古いサーバーが保存していて引き継げなかったシークレットは一覧されるので、入力し直せます。復元はすべてのセッションを終了し、パスキーを削除するので、あとで設定し直してください。
3. **選択。** BombVault はバックアップを調べ、見つかったコンテナ、VM、フォルダーセット、ZFS データセットを一覧します。最新のスナップショットがすべてで最初から選択されています。このサーバーにまだあるものは、復元すると置き換えてしまうので、最初はオフです。フォルダーセットは、再構築のあと元の場所を知らないので、選んだフォルダーに入ります。
4. **復元。** 選択したすべてが一度に戻ります。コンテナと VM を自分で 1 つずつ起動したい場合は、停止したままにでき、全損のあとには最も安全です。そのあと新しいリカバリーキットをダウンロードしてください。古いものは以前のインストールのものです。

![緊急ウィザードの最初の手順。3 つの入口がある。](assets/screenshots/offsite/emergency-dark.png#only-dark)
![緊急ウィザードの最初の手順。3 つの入口がある。](assets/screenshots/offsite/emergency-light.png#only-light)

### 例：リカバリーキットから新しいサーバーへ {#example-emergency}

サーバー TOWER がディスクごと壊れました。23 個のコンテナと 2 つの VM があり、それらとセルフバックアップを Backblaze B2 にコピーしていました。パスワードマネージャーに `bombvault-recovery-kit.md` があり、Unraid の入った新しいマシンがあります。古い `APP_KEY` はなくなっていますが、必要ありません。

1. 新しいマシンに **BombVault をインストール**し、新規インストールと同じように、新しい `APP_KEY` を与えます。VM を戻したい場合は、VM の復元に必要なので、**設定、連携、ホスト SSH** で VM の接続を設定してください。
2. **ウィザードを開始。** **BombVault へようこそ**で**バックアップから復元**を選びます。復元ページで、**緊急**の**緊急ウィザードを開始**を選びます。
3. **アクセス。** **リカバリーキットをアップロード**を選んで、ファイルをドロップします。BombVault はすべての保存先でその鍵を試し、たとえば **リカバリーキットを読み取りました。この鍵で、2 か所の保存先のうち 0 か所を開けます。** のように伝えます。ローカルフォルダーはディスクが壊れたので**見つかりません**、Backblaze B2 は**認証情報なし**と表示されます。
4. **認証情報を保存。** キットには、リモートの保存先のサインインが入っています。**認証情報を保存**を押すと、保存先が再び試されるので、Backblaze B2 は**読み取り可**になります。
5. **鍵を引き継ぐ。** このサーバーは今後、古い鍵でバックアップを書くので、新しいバックアップは古いものに合います。テンプレートには、自身の `APP_KEY` が残ります。**引き継ぎを取り消す**は、最初のバックアップが実行されるまで使えます。
6. **設定。** B2 から最新のセルフバックアップを読み取る**設定を戻す**を選びます。BombVault はそれを適用するために再起動し、ウィザードは自分で続行します。保存先、スケジュール、ルールが戻り、このサーバーのパスワードでサインインし続けます。ウィザードが一覧するシークレット（通知の設定など）は、入力し直してください。
7. **選択。** **バックアップはどこにありますか？**を、オフサイトのコピーにします。ローカルのものは古いサーバーとともに失われたからです。BombVault は、23 個のコンテナと 2 つの VM を、最新のスナップショットが選択された状態で一覧します。どれについても別のものを選べます。
8. **復元。** 全損のあとには最も安全な**終了後は停止したままにする**をオンにして、開始します。**実行される内容**に、何が戻るかが書かれます。結果の行には、たとえば **25 件を復元し、0 件が失敗しました。必要に応じて「バックアップ」から起動してください。** と表示されます。
9. **仕上げ。** まずデータベースを起動し、次にそれを使うアプリを起動します。**設定、復元** を開いて、新しいリカバリーキットをダウンロードします。古いものは以前のインストールのものだからです。概要の**要対応**を確認し、すべてが動いたら**今すぐすべてバックアップ**を一度実行してください。

セルフバックアップもない場合は、**スキップ：セルフバックアップがありません**を選びます。すると保存先はキットだけから作られ、スケジュールとルールは設定し直すことになり、セクションの既定を確認するまで、オフサイトコピーは一時停止します。[再構築のあと](#after-a-rebuild)を参照してください。

!!! tip "計画的な移行と災害"
    緊急ウィザードは、バックアップから BombVault 自身の設定を復元します。新しいマシンへの*計画的な*移行なら、代わりに**設定のエクスポート / インポート**カード（持ち運べる JSON ファイル）で、設定を直接引き継げます。[設定](configuration.md#portable-settings-export-and-import)を参照してください。

### 古いバックアップフォルダーから {#restore-from-another-bombvault-repo}

復元ページの**ほかの取得元**にある**古いバックアップフォルダーから**は、*別の* BombVault インスタンスのリポジトリ（`/mnt` の下にマウントされた共有、またはリモートアドレス）を、そのインスタンスのリカバリーキットか、入力した `APP_KEY` で、一度きりの読み取り専用セッションで開きます。そこに保存されたコンテナ、VM、フォルダーセット、ZFS データセットを参照し、スナップショットを選んで復元すると、復元されたものは通常のローカルのコンテナ、VM、フォルダーセットになります。もう一方のリポジトリには一切書き込まれず、自分のバックアップ設定にも触れません（セッションはメモリ上にあり、自動で期限切れになります）。サーバー A からサーバー B へコンテナを移すのに、設定を向け直して、あとで元に戻す必要はありません。このウィンドウは一度きりのものです。セッションを開き、選んだものを復元して、もう一方のインスタンスを忘れます。代わりに、このマシンがスケジュールで別のインスタンスのスナップショットを自分のリポジトリに取り込み続ける恒常的な仕組みが必要なら、インスタンスのページの**取得側**ロールがそれです。

このサーバーにネットワークが存在しないコンテナ（たとえば、通常の Docker ホストにおける Unraid の `br0` ネットワーク）には、その行の下にネットワークの選択が表示されます。BombVault は、選んだネットワークと、そのほかのネットワークとともに、それを作成します。固定 IP と MAC アドレスは古いネットワークのものだったので破棄され、新しいネットワークが割り当てます。

## 鍵の保管側 {#key-keeper}

鍵の保管側は、このサーバーのリカバリーキットの封じた写しを保管する、グループのインスタンスです。自分ではその写しを開けません。このサーバーがもし失われたら、グループに加わった新しいインストールが保管側に写しを求め、取り出しコードで開きます。

![取り出しコードのウィンドウ：20 文字を 4 つのグループに分けて、一度だけ表示。](assets/screenshots/offsite/recovery-code-dark.png#only-dark)
![取り出しコードのウィンドウ：20 文字を 4 つのグループに分けて、一度だけ表示。](assets/screenshots/offsite/recovery-code-light.png#only-light)

1. インスタンスのページで、保管してほしいインスタンスのカードの**鍵の保管側**をオンにして、**預け入れる**を選びます。預け入れにはログインパスワードが必要です。
2. このサーバーは**取り出しコード**を一度だけ表示します。4 つのグループに分けた、5 文字ずつの 20 個の英数字です。書き留めて、**コードを書き留めました**で確認してください。このサーバーはコードを保存せず、それ用に預け入れを封じるのに必要なものだけを保存します。
3. 保管側は今、預け入れを保管していて、このサーバーはキットが変わるたびにそれを更新します。このインスタンスのカードの**鍵の預け入れ**には、**このサーバーの預け入れ**が各保管側とその状態とともに、ほかの人のためには**このサーバーが保管している預け入れ**が一覧されます。**新しいコードを作成**はコードを置き換えます。各保管側は、新しい預け入れを受け取ると新しいものに切り替わります。

その日に必要なのは 3 つです。グループの 12 個の単語、取り出しコード、そして誰かが**許可**を押す必要がある、保管側の画面へのアクセスです。緊急ウィザードで**グループ経由**を選び、預け入れを選んで要求し、取り出しコードを入力します。コードは新しいサーバーで使われ、保管側に送られることはありません。保管側では、リクエストが**鍵の預け入れ**の下に、誰が求めているか、そのインスタンスがそこで以前に見られたことがあるか、何回求めたかとともに表示されます。**許可**で封じた写しが渡され、許可にはログインパスワードが必要です。新しいインストールは、許可のあと 30 分で受け取る必要があり、誰も応答しなかったリクエストは 1 日で失効し、頻繁に求めすぎるインスタンスは 1 時間待たされます。

コードがなければ、保管側を含め誰も写しを開けません。コードをなくした場合は、このサーバーがまだ動いているうちに、新しいものを作ってください。サーバーがすでにない場合でも、リカバリーキットと入力した APP_KEY はまだ使えます。保管側は預け入れをいつでも削除でき、その場合、所有者はもう一度求める必要があります。

## リカバリーキット {#recovery-kit}

これは、BombVault が動いていなくても、災害復旧を可能にするものです。

**設定、復元** の**緊急時用**カードにある**リカバリーキットをダウンロード**は、**鍵**、**導出された restic パスワード**、各セクションのリポジトリを持つすべての**保存先**、新しいインストールがそれらに届くために必要なサインイン、そして**restic の正確なコマンド**を渡します。そのため、どのマシンでも restic の CLI で直接復元できます。ログインパスワードが必要です。キットは、暗号化をオフにしていても鍵を印字します。コンテナと VM の定義は、常にそれで封じられているからです。引き継ぎのあとは、引き継いだバックアップ鍵と、このサーバーの APP_KEY が印字されます。後者は、新しいインストールが設定を戻すためにだけ必要です。概要の**リカバリーキットを保存してください**カードは、保存するまで知らせ続けます。

!!! danger "リカバリーキットはサーバーの外に保管してください"
    キットには、バックアップを復号するシークレットが入っています。サーバーとは別の安全な場所に保管してください（パスワードマネージャー、金庫に入れた印刷物など）。BombVault と `APP_KEY` の両方を失い、リカバリーキットも鍵の預け入れもない場合、暗号化されたバックアップは復元できません。

!!! warning "最新のスナップショットが、復元すべきものとは限りません"
    restic 0.17 以降、`restic snapshots` は各スナップショットのサイズを表示します。データ消失のあとでは、最新のスナップショットが空になったものかもしれないので、その前のものよりはるかに小さいスナップショットは復元しないでください。ランサムウェアのあとでは、通常のサイズのまま暗号化されたものかもしれません。BombVault がまだ動いているなら、先に**異常**ページを確認してください。最後の正常なバックアップが示され、復元ウィンドウがそれを最初から選びます。復元に BombVault の異常データは不要で、保持の一時停止が行うのは、より多くのスナップショットを残すことだけです。

### キットを暗号化する {#sealing-the-kit}

**設定、システム** で **age でエクスポートを暗号化**をオンにしている場合、キットもそれで暗号化され、`bombvault-recovery-kit.md.age` としてダウンロードされます。バイナリではなく ASCII アーマー形式なので、まだプレーンテキストです。パスワードマネージャーに貼り付けたり、印刷したりするのは以前とまったく同じで、鍵がなければ内容は読めません。

!!! warning "age の鍵をキットの中に保管しないでください"
    暗号化されたキットを開くには、age の**秘密**鍵が必要です。キット自体に依存しない場所に保管してください。そうしないと、復旧するものが 1 つではなく 2 つになります。暗号化が役立つのは、キットを完全には管理できない場所（共有のパスワードマネージャー、クラウドのメモ、オフィスでの印刷物）に保管するときです。自分の金庫にあるキットは、金庫がすでに守っています。

    暗号化がオンで、使える受信者が設定されていない場合、ダウンロードは完全に拒否されます。BombVault がマスターキーを平文で渡すことは決してありません。

### キットが手元にない場合 {#if-you-do-not-have-the-kit-to-hand}

パスワードはどこにも保存されておらず、バックアップの鍵から**計算**されます。そのため、鍵とシェルだけで自分で再現できます。

```sh
printf 'bombvault:restic-repo'   | openssl dgst -sha256 -mac HMAC -macopt hexkey:$APP_KEY -r   | cut -d' ' -f1
```

これは、固定の文字列 `bombvault:restic-repo` に対する HMAC-SHA256 で、16 進数の `APP_KEY` の生のバイトをキーとし、小文字の 16 進数 64 文字で出力されます。同じ値は、導出された restic パスワードとして、キットにも載っています。これは、キットが手元にない日のためのものです。ほかのサーバーのバックアップを引き継いだサーバーでは、引き継いだバックアップ鍵、つまりそのサーバーの古い APP_KEY を使ってください。

!!! warning "受信したリポジトリには、送信側のインスタンスの鍵を使ってください"
    オフサイトコピーでここに届いたリポジトリは、それを送ったマシンが**その**鍵で作りました。受信側のマシンの鍵から導出すると、restic が拒否するパスワードになり、これは壊れたリポジトリとまったく同じに見えますが、そうではありません。受信したリポジトリで `restic check` が何度もパスワードを求める、よくある理由です。

復旧用の定義は各リポジトリの**中**にある（`<repo>/def`、`<repo>/vm-def`）ため、コピーしたリポジトリのフォルダーはそれだけで完結しており、キットとリポジトリがあれば、ベアメタルの復元に必要なものはすべてそろいます。

## データベースダンプを取り戻す {#database-dumps}

データベースダンプは、コンテナのリポジトリ内にある独立したリストアポイントで、タグ `dbdump:<container>` が付き、単一のファイル `/dbdump/<container>.sql` を保持しています。BombVault は、コンテナの**バックアップ**タブで、それを一覧し、ダウンロードし、インポートします。以下は、BombVault がない日のための、restic だけを使った同じ手順です。

```sh
restic -r <repo> snapshots --tag dbdump:<container>
restic -r <repo> dump --tag dbdump:<container> latest /dbdump/<container>.sql > <container>.sql
```

各ダンプのタグ `dbversion:` と `dbname:` は、どのサーバーバージョンのものか、どのデータベースを保持しているかを示します。完全なファイルは、`-- PostgreSQL database cluster dump complete` または `-- Dump completed` で終わります。

同じかそれ以降のバージョン（PostgreSQL）、または同じメジャーバージョン（MySQL と MariaDB）のコンテナへ、空のデータフォルダーで一度起動して初期化されたあとにインポートします。ホストにデータベースクライアントは不要で、コンテナにあります。

```sh
docker exec -i <container> sh -c 'exec psql -X -U "${POSTGRES_USER:-postgres}" -d postgres' < <container>.sql
docker exec -i <container> sh -c 'exec mariadb -uroot -p"$MARIADB_ROOT_PASSWORD"' < <container>.sql
docker exec -i <container> sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < <container>.sql
```

完全なダンプから単一のデータベースだけを取り出すには、MySQL と MariaDB ではクライアントのコマンドに `--one-database <name>` を付けます。PostgreSQL のダンプには、データベースごとに 1 つのセクションがあり、それぞれ `\connect <name>` の行で始まります。そのセクションを別のファイルにコピーし、データベースを作成してから `-d <name>` でインポートします。

!!! warning "root のダンプには、サーバーのユーザーが含まれます"
    root で取った MySQL または MariaDB の完全なダンプには、`mysql` システムデータベースが含まれるため、インポートすると、新しいサーバーのアカウントが、root のパスワードも含めて、ダンプのものに置き換えられます。PostgreSQL では、コンテナが作成したユーザーについて `role ... already exists` と出るのは想定どおりで、害はありません。
