# オフサイトと復旧

!!! note "再構築後、オフサイトのコピーは待機します"
    緊急ウィザードまたは **バックアップを検出** が以前の設定なしで項目を再構築すると、それらのセクションのオフサイトコピーは、既定を確認するまで一時停止します。[再構築のあと](#after-a-rebuild)を参照してください。

ローカルバックアップは、コンテナの喪失や不良な更新からあなたを守ります。オフサイトコピーとテスト済みのリカバリーキットは、マシン全体、ランサムウェア、または火災からあなたを守ります。このページでは、保存先とオフサイトコピー、そのコピーを改ざん不能にすること、復元できることの証明、複数のサーバーのペアリング、そして BombVault 自身が失われたときにすべてを取り戻す方法を扱います。

## オフサイトコピー {#off-site-copies}

高速なローカルバックアップを保ちつつ、敷地外の保存先をひとつ以上追加します。BombVault はベストエフォート方式で `restic copy` により新しいバックアップをそこへコピーするため、オフサイトの不調でローカルバックアップが失敗することはありません。この形ではローカルリポジトリが主でオフサイトリポジトリはコピーですが、セクションの主リポジトリはローカルである必要はまったくありません。コピーする代わりに S3 や rest-server などへ直接バックアップする方法は、下の[リモートの主リポジトリ](#remote-primary-repositories)を参照してください。

- **セクションごとに複数の保存先。** 各セクション（コンテナ、VM、フラッシュ、セルフバックアップ、フォルダー、ZFS データセット）は、複数のオフサイト保存先へ同時にコピーできます。そのため、たとえば友人のマシン上の rest-server と S3 バケットを並行して保てます。保存先ページの **セクションごとの保存先** カードで、セクションから保存先への各線をオンまたはオフに切り替えます。
- **コピーが実行されるタイミング。** 保存先の **コピー** カードの **コピーのタイミング** で、**バックアップのたびに**、またはバックアップを集めて決まった時刻にコピーする独自のプランを選びます。**設定、スケジュール、セクションごとのオフサイトコピー** の **例外** では、1 つのセクションに独自のコピープランを設定できます。**設定、保存先** の各セクションの **オフサイトコピー** カードにある **今すぐ複製** は、コピーをオンデマンドで開始します。
- **保持** は保存先ごとに **保持期間** で設定するため、オフサイトのコピーをアーカイブとして長く保てます。セクションのオフサイト欄にあるコピーは **設定、保存先** の **オフサイトの保持** カードに従います。すべてゼロのままにすると、オフサイトのバックアップを自動整理しません。
- **帯域幅制限**（**設定、保存先** の **オフサイト帯域幅**、または保存先の **コピー** カード）は、restic のアップロード/ダウンロードレートに上限を設け、コピーが WAN を飽和させないようにします。
- コピーの実行中は、概要のステータス見出しに **オフサイトコピー実行中** と表示されます。`restic copy` は機械可読な進捗を公開しないため、これはパーセント表示のバーではなく、動作中を示す表示です。

!!! note "どの場所からでも復元"
    各項目は、その **バックアップ** タブで、バックアップがあるすべての場所をまたぐ 1 本のタイムラインとしてバックアップを一覧します。B2 にコピーしたバックアップは 1 回だけ表示され、それを保持している各場所が付記されます。復元は、項目の書き込み先リポジトリから順に、到達できる最初の場所を使い、バックアップごとに別の場所を選べます。クラウドストレージの一覧取得には時間がかかるため、オフサイトの保存先は **確認** をクリックしたときにだけ読み込まれます。ある場所で削除する前に、ほかの場所を確認し、それが最後のコピーだったかどうかを知らせます。

## 保存先 {#destinations}

保存先とは、バックアップの送り先です。ローカルフォルダー、共有、自分のサーバー、クラウドサービスなどがあります。一度設定すれば、すべてのセクションで使えます。設定のタイルから **保存先** を開くか、そこで **サイドバーにも表示** をオンにして固定します。

**保存先を追加** は、4 つのステップのウィンドウを開きます。

1. **プロバイダー。** すべてのサービスがロゴ付きで、ウィンドウの右上に検索欄があり、グループごとに表示されます。S3 バケットを持つストレージサービス（Backblaze B2、Wasabi、Cloudflare R2、Hetzner Object Storage、Amazon S3 など）、自分の S3 サーバー（Garage、SeaweedFS、RustFS、Silo、Ceph、JuiceFS、Versity S3 Gateway）、自分のサーバーと共有（rest-server、Hetzner Storage Box、SFTP、SMB、WebDAV、マウント済みのパス）、クラウドストレージ（OneDrive、Google Drive、Dropbox、pCloud、Nextcloud、そのほか rclone が対応するもの）、そしてグループの受信サーバーです。それぞれ、バックアップにどれだけ向いているかが示されます。クラウドドライブは多数のリクエストで遅くなるため、最初のバックアップと整理に時間がかかります。
2. **サインイン。** 入力欄はサービスによって異なります。S3 ならアクセスキー、WebDAV と SMB ならユーザーとパスワード、2 要素認証が通常のパスワードを拒否する場合はアプリパスワード、SFTP と Storage Box なら BombVault の公開 SSH 鍵、ブラウザー経由でサインインするサービスならトークンです。後者の場合、ウィンドウにはブラウザーのあるコンピューターで実行する `rclone authorize` コマンドが表示され、出力されたトークンを入力欄に貼り付けます。**テスト** は、何かを保存する前にサインインを確認します。続いてウィンドウは保存先のフォルダーを一覧し、**新しいフォルダー** で作成でき、サービスが報告する場合は空き容量も表示します。空のフォルダーが最も安全です。BombVault はその中にセクションごとに 1 つのフォルダーを作ります。
3. **保護。** ウィンドウは、そのサービスに何ができるかをはっきり伝えます。追記専用モードの rest-server は削除を拒否し、改ざんテストがそれを確認します。S3 バケットはバージョニングとオブジェクトロックで古いバージョンを保持できますが、BombVault はまだそれを確認できません。クラウドドライブは削除を拒否することがそもそもできません。サーバーに入り込んだ人は、そのコピーにも入り込めます。**削除に対する保護(append-only)** は、相手側が本当に削除を拒否する場合にだけオンにしてください。BombVault はそこでは整理を一切行いません。**緊急時のために** は、この保存先についてリカバリーキットが何を保持するかを示します。
4. **対象セクション。** ここにバックアップするセクションを選びます。最初のコピーは履歴全体を引き継ぎます。独自の保存先を選んだ項目には新しい保存先が自動では加わらず、ウィンドウがそれらの名前を挙げます。

一部のサービスでは、サインインのときにもう少し入力が必要です。

- **SFTP と Storage Box。** **鍵を追加** は、**アカウントのパスワード** を使って BombVault の公開鍵をサーバーに登録します。パスワードはその 1 回のサインインにだけ使われ、どこにも保存されません。手作業で登録するためのコマンドがその下に表示されます。テストでは **サーバーの鍵** がフィンガープリント付きで表示されます。BombVault はそれを記憶し、後でサーバーが別の鍵を示すとそのサーバーを拒否します。
- **単一のバケット用の S3 キー**（Cloudflare R2 のオブジェクトトークンや、範囲を限定した AWS キーなど）は、ほかのバケットを一覧できないことがあります。**バケット** にバケット名を入力すると、テストとフォルダーの一覧がそのバケットを開きます。
- **共有を一覧しない SMB サーバー** では、**共有** にいずれかの共有の名前を入力します。テストはその共有を直接開きます。
- **FTP** では **暗号化** を選びます。**なし**、**明示的 TLS (FTPES)**、**暗黙的 TLS (FTPS、ポート 990)** のいずれかです。
- **OneDrive と Zoho WorkDrive。** 1 回のサインインで複数のドライブやワークスペースが開く場合は、バックアップをどれに送るかをウィンドウが尋ねます。
- **自己署名証明書を使う rest-server。** 証明書を PEM ファイルとして、BombVault のデータフォルダーの `certs` フォルダー（コンテナ内では `/config/certs`、Unraid では `appdata/bombvault/certs`）に置きます。バックアップ、コピー、削除に対する保護のテストは、再起動なしでその証明書を信頼します。

S3 サービスは restic 自身の S3 バックエンドを通るため、ストレージクラスとオブジェクトロックを適用できます。それ以外のサービスはすべて BombVault に同梱の rclone を通り、そのリモートは **設定、保存先** の **オフサイト (rclone)** カードに表示されます。設定のエクスポートには保存先が含まれ、認証情報を含める場合はそのサインインも含まれます。

このサーバー上のフォルダーは、保存先のページ、フロー、項目、復元のどこでも **ローカル** と呼ばれます。このサーバーに複数のフォルダーがある場合は、それぞれが固有の名前で表示されます。セクションのオフサイト欄が作る保存先は、その場所の名前、つまりアドレスの最後のフォルダー、フォルダーがなければサーバー名が付き、同じ名前の保存先がすでにあれば番号が付きます。保存先のページで付けた名前はそのまま残ります。同じ名前の保存先が並ぶ場合は、それぞれにサーバーまたはフォルダーが添えられます。

各保存先には専用のページがあります。

- **接続**: 名前、スイッチ **利用可能**（オフにすると BombVault はここに書き込まなくなり、ここにバックアップする項目は別の場所に入ることなく明確なメッセージで失敗します）、フォルダー、圧縮、ストレージクラス、**施設外**。**接続を変更** は、新しいアドレスまたはサインインをテストして保存します。
- **認証情報**: 共有のセットか、専用のセットです。
- **削除に対する保護**: **削除に対する保護を今すぐテスト** と、このコピーを誰が整理するかを示します。
- **コピー**: コピーのタイミングと、アップロードおよびダウンロードの制限です。
- **保持期間**: **短め**、**標準**、**長め**、または **カスタム値**。ルールが保持するバックアップのタイムライン付きです。**保持を減らす前に確認する** は、より短いルールによって、唯一のコピーがここにあるバックアップが削除される前に確認します。
- **セクションごとのルール**: この保存先における、1 つのセクション独自のリポジトリ、保持、圧縮です。**ルールを変更** で開き、**保存先の設定に戻す** でセクションを元に戻します。
- **すでにこの保存先の下にあります**: 手入力したアドレスが、この保存先のフォルダー内にあるセクションです。引き継ぐとリポジトリはそのままの場所に残り、サインイン、ストレージクラス、削除に対する保護は保存先から取得されます。BombVault はまず、保存先のサインインでリポジトリを開けることを確認し、追記専用でない保存先の下に追記専用のリポジトリを置くことは拒否します。
- 保存先がどれだけ埋まっているかを示す容器。満杯になる位置の目印と、直近数週間の増加ペースであと何週間残っているかを表示します。サイズを報告しない保存先には **サイズ不明** と表示されます。

バックアップを保持していたリモートの保存先から急にリポジトリがなくなっても、たとえば rest-server のディスクがマウントされなかった場合でも、新しい空のリポジトリが自動で作られることはありません。バックアップかコピーがリポジトリの消失に気づいた時点で、その保存先のページに表示されます。ディスクをマウントし直してください。古いリポジトリを意図して空にした場合は、**ここに新しいリポジトリを作成** で最初からやり直せます。その保存先のすべてのセクションと名前付きのリポジトリが、まとめて対象になります。

グループの別のインスタンスが運用する受信サーバーは、プロバイダーの中に **グループから** として表示されます。[受信サーバー](#receiving-server)を参照してください。

### 移動と削除 {#move-remove}

- **移動** は、1 つのセクションのコピーを履歴ごと別の保存先へ移します。すべては古い場所に残り、BombVault はそこで何も削除しません。移動はバックグラウンドで実行され、時間がかかることがあります。ローカルディスク間では 100 GB あたり約 9 分、低速な回線では数時間です。実行中は概要に表示されます。
- **保存先を削除** には 2 つの方法があります。**保存先を削除し、バックアップは残す** は、そこへの書き込みを止め、バックアップはそのまま残します。あとで **復元、古いバックアップフォルダーから** で読み取れます。**保存先を削除し、そこのバックアップも削除する** は、まずそこに保存されている内容を読み取って一覧します。どのバックアップが消えるか、そのうちほかのどこにもないものはどれか、削除に対する保護が拒否する、項目がまだ直接バックアップしている、別の保存先またはセクションがそこにコピーを置いている、あるいは読み取れなかったために残るリポジトリはどれかが示されます。唯一のバックアップを失う項目は別に挙げられ、**これらも削除する** をオンにしない限り残されます。保存先の名前を入力して確認し、削除はバックグラウンドで実行されます。
- これはどの種類の保存先でも使えます。複数のセクションが使う保存先、1 つのセクション用に設定した保存先、自分で作成したリポジトリ、セクションが自分のバックアップを書き込むフォルダーのいずれも対象です。削除したリポジトリにバックアップしていた項目は、再びセクションに従います。そこを指していたセクションの既定も同じです。セクションのフォルダーは、どのセクションにも必要なので、そのままでは削除できません。そのためウィンドウで、セクションの移動先フォルダーを尋ねます。各セクションは、その下に自分のフォルダー名を保ちます。
- 保存先のバックアップを削除するには、ログインパスワードと、そのインスタンスへのサインインが必要です。パスワードがなくても保存先自体は削除できますが、そのバックアップをここから削除することはできません。

## 項目ごとの配置 {#placement}

項目の設定タブにある **スケジュールと保存先** カードには、ボタンの列があります。**ローカル** と、セクションのオフサイト保存先ごとに 1 つのボタンです。点灯しているボタンが、その項目のバックアップを受け取ります。

- **ローカル** が点灯していると、項目は **保存先** の下に表示されるリポジトリに書き込まれ、点灯しているほかのすべての保存先にコピーされます。保存先を消灯すると、この項目からは何も新しく届きません。ローカルのみの場合はどこにもコピーされません。たとえば NAS 上にある共有のように、すでに 2 つ目のコピーがあるデータに向いています。
- **ローカル** が消灯していると、項目は最初に点灯している保存先のダイレクトリポジトリに直接書き込まれ、そこから点灯しているほかの保存先にコピーされます。初回はダイアログがそのダイレクトリポジトリを作成します。
- ボタンは 1 つ必ず点灯したままになります。バックアップには送り先が必要だからです。項目をバックアップから外すには、**バックアップしない** を使います。

BombVault はバックアップをリポジトリ間で移動しません。セクションに従う項目は、セクションの既定が変わるとそれに合わせて移ります。次のバックアップは新しい場所に入り、すでにあるバックアップはそのまま残ります。項目自体で選んだ場所は最初のバックアップの時点で固定され、設定タブの **リポジトリ** カードにその名前が表示されます。コピーはいつでも変更できます。項目を受け取らなくなった保存先は、すでにあるコピーを保持し、セクションの次のオフサイト実行時に自身の保持ルールに合わせて整理します。追記専用の保存先からは削除できません。

項目が離れた場所は、そのバックアップを保持します。項目の **バックアップ** タブと **復元** では **以前のバックアップのみ** と表示され、復元は引き続きそこから読み取れ、そこでの整理はそれらのバックアップに手を付けません。

**既定に従う** は、独自の選択をした項目をセクションに戻します。先に確認を求め、以後の新しいバックアップの送り先を示し、各保存先が受け取らなくなるものと、次の実行でアップロードされるものを挙げます。

列の下に、カードは項目の送り先と実際にあるものを示します。何か所が保持しているか、各保存先が最後に確認された時刻、3-2-1 を満たしているかどうかです。1 か所とは、元のデータを持つサーバー、各オフサイト保存先、そして **施設外** と印が付いた各リポジトリです。BombVault はコピーと場所を確認しますが、3-2-1 の「2 種類のメディア」の部分は確認しません。

### セクションごとの既定 {#placement-defaults}

保存先ページの **セクションごとの保存先** カードは、各セクションの既定を 3-2-1 のフローとして描きます。セクションから保存先へのどの線もスイッチで、**ローカル** も含まれ、フラッシュ、ZFS データセット、セルフバックアップを含むすべてのセクションで同じです。線または点をクリックすると、確認なしですぐに切り替わります。破線はオフです。**グラフ / スイッチ** は、同じ内容をボタンの列として表示します。スイッチは、新しいバックアップの送り先を決めます。独自の選択がない項目と Compose スタックのプロジェクトフォルダーはすぐに従い、次のバックアップは新しい場所に入ります。すでに保存されたバックアップはそのまま残り、そこから引き続き復元できます。フラッシュ、ZFS データセット、セルフバックアップは、ローカルフォルダーへバックアップし、そのバックアップからオフサイトへコピーします。**ローカル** への線もオフにでき、その場合バックアップは直接オフサイトの保存先へ送られます。レプリカがあり保存先がまったくない ZFS 項目は、レプリカだけを送ります。

**ローカル** がオフでオフサイトの保存先だけがオンの場合、セクションはそれらへ直接バックアップし、そこでのリポジトリは BombVault が自ら選びます。コンテナ、VM、フォルダーセットは、後述のとおり最初にオンの保存先のダイレクトリポジトリに入り、そこからほかへコピーされます。フラッシュ、ZFS データセット、セルフバックアップは、オンのすべての保存先に各バックアップを書き込み、各保存先は自身の保持ルールで保持します。

すべての線がオフのセクションには **バックアップなし** と表示されます。その項目はバックアップを受け取らず、保護されていないものとして数えられます。

自分のページで独自の保存先を選んだ項目は、それを保ちます。フローはセクション内の該当数を **2 件の項目が異なります** のように示し、それらへ案内します。1 件なら項目の設定タブへ、複数なら各項目の送り先を示す一覧へ移ります。そこで **既定に従う** を押すと項目が戻ります。

新しいオフサイト保存先は、ローカルに設定されていないすべての項目を受け取ります。追加するウィンドウには、何個の項目になるか、わかる場合はどれだけの履歴になるかが表示されます。

### ダイレクトリポジトリ

ダイレクトリポジトリは、項目がオフサイトの保存先へ直接バックアップする場所です。BombVault は保存先のフォルダーの隣に、名前へ `-direct` を付けて置きます。保存先がバケット、リモート、または rest-server ユーザーのルートにある場合は、その中にセクション名を付けたフォルダー（たとえば `containers-direct`）として置きます。保存先ページのフローでは、確認なしで作成されます。1 つの項目だけローカルをオフにして、ダイレクトリポジトリのない保存先をその項目の拠点にすると、推奨の場所（たとえば `s3:https://s3.eu-central-003.backblazeb2.com/bucket/containers-direct`）と、何も作成しない接続テストを備えたダイアログが開きます。**作成して使用** はリポジトリを作成し、項目をそこへ向けます。ダイレクトリポジトリは保存先の鍵、ストレージクラス、制限、追記専用の設定、保持を引き継ぎ、それらと一緒に変わります。リポジトリカードでは読み取り専用で表示されます。保存先の新しい鍵でそれを開けない場合、ダイレクトリポジトリは持っている鍵を保ち、保存時にそれが通知されます。ダイレクトリポジトリにある項目は、そこから点灯しているほかの保存先にコピーされ、そのリポジトリが属する保存先にコピーされることはありません。そのバックアップにはタグ `bv:direct` が付き、ほかのあらゆる保持処理がそれを残すため、保存先とのつながりを失ったダイレクトリポジトリがローカルのルールで古くなることはありません。B2 へは S3 エンドポイント経由で接続し、キー ID とアプリケーションキーを S3 の認証情報として入力します。保存先専用のフォルダーに限定したキーでは隣のフォルダーに届かないため、代わりにその上のフォルダーに限定してください。

### 施設外

保存先または名前付きリポジトリには **施設外** の印を付けられます。リモートのものは印が付いた状態で始まります。同じ建物内の rest-server ではオフにしてください。この印はカード上の場所の数と 3-2-1 の判定にだけ使われます。どのコピーも変更しません。

ZFS レプリカは施設外のコピーですが、履歴のあるバックアップではありません。設定した数のスナップショットだけを保持し、古いバージョンや個別のファイルは引き続きバックアップから取得します。1 台の ZFS サーバーからもう 1 台へ直接、SSH で ZFS サーバーへ、またはペアリングしたインスタンスの受信エンドポイントへ送られます。ペアリンググループは要求を運ぶだけです。[レプリカ](zfs-datasets.md#replica)を参照してください。

### 再構築のあと {#after-a-rebuild}

コピーの選択は BombVault 自身の設定に保存されています。復元した設定なしで **バックアップを検出** または緊急ウィザードによる再構築を行うと、それらは失われ、すべてをコピーすると、除外していた項目まで B2 に再び送られてしまいます。そのため、再構築したすべてのセクションのオフサイトコピーは一時停止します。概要がそれを知らせ、**セクションごとの保存先** カードは **既定を確認** を提供します。次の実行で何がコピーされるかのプレビューと、項目のないバックアップ内の名前が表示され、そこで除外できます。一時停止を解除するのは確認だけです。設定ファイルをインポートするとルールと既定は戻りますが、一時停止は解除されません。

## リモートの主リポジトリ {#remote-primary-repositories}

セクション独自のパスはローカルフォルダーに限りません。restic のリモート（`s3:...`、`rest:http://host:8000/repo`、`sftp:user@host:/repo`、`rclone:remote:bucket/path`）を直接指定すると、BombVault は別個のローカルコピーもコピー手順もなしに、そこへ直接バックアップします。これは上のオフサイトコピーとは異なる形です。あちらではローカルリポジトリが主で、オフサイトリポジトリはそのベストエフォートのアーカイブです。こちらではリモートリポジトリが主**そのもの**であり、そのセクションを別の保存先にもコピーしない限り、唯一のコピーです。

各セクション（コンテナ、VM、フラッシュ、セルフバックアップ、バックアップ対象フォルダ、ZFS データセット）のパスは、**ローカル** 保存先のページで設定します。**接続** カードでセクションの横にある **変更** を押すと、**ローカル / リモート** のスイッチがあるウィンドウが開きます。

- **ローカル** は、おなじみのフォルダーブラウザーを表示します。
- **リモート** は、それをプレーンな URL 欄と、オフサイト保存先が使うのと同じ接続設定に置き換えます。ここでは、この主リポジトリ用に設定します。ここから次のものが得られます。
    - 実際のパスに対する**接続テスト**。頼りにする前に確認できます。
    - リモートの主リポジトリへのスケジュールされたバックアップが WAN を飽和させないようにする**帯域幅制限**（アップロード/ダウンロード）。オフサイトコピーが使うのと同じ restic の `--limit-upload`/`--limit-download` フラグを、バックアップ自体に適用します。
    - オフサイト保存先と同じアクティブな改ざんテスト（相手側への実際の DELETE プローブ）で検証される**追記専用の保護**。オンにすると、BombVault はリポジトリ自体の整理を拒否します。背後に別個のローカルコピーがなく、このマシンの認証情報でバックアップの唯一のコピーを削除できてはならないためです。
    - ストレージカードがすでに追跡しているリポジトリサイズの推移から算出される**増加予算アラーム**。

これらはいずれも必須ではありません。保存された安全設定のない手入力のリモートパスへのバックアップは、帯域幅無制限、整理可能、予算アラームなしで行われます。安全設定は、そのためだけに別の保存先を用意することなく、オフサイトコピーと同じ保護がほしいときのためにあります。

!!! note "クラウドと REST の認証情報は共有されます"
    リモートの主リポジトリは、**設定、保存先** にある共有のクラウド認証情報で認証します。主リポジトリ専用の認証情報ストアはありません。

### ホストマウントなしの SMB と WebDAV {#smb-webdav}

**設定、保存先** の **オフサイト (rclone)** カードには、Windows または Samba の共有と、WebDAV サーバー（Nextcloud、ownCloud、SharePoint、そのほか何でも）用のフォームがあります。短い名前、ホストと共有（SMB）または URL とサーバーの種類（WebDAV）、ユーザー、パスワードを入力すると、BombVault が rclone のセクションを書き込みます。rclone は保存前にパスワード自体を難読化します。すでにある名前で追加すると、2 つ目を足す代わりにそのセクションが置き換えられます。**保存先を追加** でも、SMB と WebDAV が同じ入力欄を持つプロバイダーとして提供されます。

フォームは完成した場所を返します。たとえば `rclone:nas:backups` です。それをセクションのパスまたは保存先として使い、必要ならサブフォルダーを追加します（`rclone:nas:backups/bombvault`）。共有はパスの最初の要素であり、名前の一部ではありません。

これは Unraid に共有をマウントするよりよい方法です。restic はマウントした CIFS 共有にリポジトリを置くことを推奨しておらず、ここでは何もマウントしません。NFS は restic にも rclone にも NFS バックエンドがないため、フォームにはありません。NFS の場合は、ホストでエクスポートをマウントし、ローカルフォルダーとして使ってください。

## 削除に対する保護 (append-only)

ランサムウェアや侵害されたホストがバックアップを削除したり書き換えたりできないよう、オフサイト保存先で削除に対する保護をオンにします。相手側（`--append-only` モードで動く `restic/rest-server`）がそれを**強制**します。BombVault はそれを**検証**するだけで、設定上の主張だけでは決して緑を表示しません。このサーバー上のフォルダーは削除を拒否できません。BombVault を操作できる人はそのフォルダーも操作できるため、ローカルの保存先にはこのスイッチがありません。

このスイッチは保存先に属します。そこへコピーするセクションは保存先から引き継ぐので、**保存先** にあるその保存先のページでオンにします。スケジュールされた **削除保護のチェック** は、スイッチがオンの保存先へコピーするセクションがある間だけ実行されます。相手側は `--append-only` 付きで起動する必要があります。`restic/rest-server` イメージでは、TrueNAS でも他の Docker ホストでも、これを変数 `OPTIONS` に入れます。

追記専用のコピーに最も早く到達する方法は、[受信サーバー](#receiving-server)を持つペアリング済みの BombVault です。rest-server を追記専用モードで代わりに動かします。

!!! note "`/locks/` 配下での削除成功は想定どおりです"
    追記専用は、何も削除できないという意味ではありません。restic は自身のロックを取得して解放する必要があるため、`/locks/` は設計上、書き込みも削除もできます。ランサムウェアが狙うスナップショットとその背後のデータは削除できません。相手側を自分で試す場合、`/locks/` 配下での削除成功は正しい動作であり、保護の穴ではありません。

!!! warning "追記専用のリポジトリはこのマシンから整理されません"
    追記専用の保存先は、ここから古いバックアップを整理することはありません。整理は相手側の仕事です。リポジトリのサイズが膨らむ前に通知を受けられるよう、**増加予算アラーム**を設定してください。

## 改ざんテスト

BombVault は、存在しないオブジェクトを対象にオフサイトリポジトリへ実際に削除を試みることで、追記専用の保証を定期的に証明します。保存先のページの **削除に対する保護を今すぐテスト** はオンデマンドで実行し、**設定、検証、自動チェック** の **削除保護のチェック** はスケジュールで実行します。

オフになっているコピーはテストされず、保存先にそう表示されます。接続テストは読み取るだけなので引き続き使え、オンにする前にコピーを確認できます。

- **拒否**は保護されていることを意味します。
- **受理**は保護されていないことを意味します。
- **判定不能**の結果（サーバー到達不能、認証エラー）が、保存された判定を覆すことは決してありません。

保護状態から非保護状態への実際の反転は、単一のアラートを発火させます。

## DR ドリル

BombVault は、バックアップが単に存在するだけでなく、実際に復元可能であることについて、2 段階の証明を提供します。

- **復元検証ドリル（ローカル）。** BombVault は定期的に `restic check --read-data-subset` を実行します（範囲を限定し、ディスクを埋め尽くす完全な復元は行いません）。頻度は **設定、検証、自動チェック** にあり、同じタイルの **バックアップをチェック** カードに結果が表示されます。
- **試験復元（オフサイト）。** BombVault は実際のターゲットをオフサイトリポジトリから隔離されたサンドボックスへ復元し、ファイル単位・バイト単位で検証してから後始末をします。これは、リポジトリが応答するだけでなく、オフサイトから復旧できることの証明になります。

概要の **保護ステータス** カードは、これをセクションごとに 4 つのチェックにまとめます。このサーバー上の最新のバックアップ、オフサイトのコピー、そこでの削除に対する保護、そこからの試験復元です。セクションをクリックすると詳細が表示され、カードは検証された事実に基づく場合にのみ緑になります。

## インスタンスのペアリング {#pairing}

複数の BombVault が 1 つのグループとして連携し、互いの保護ステータスを表示し、互いのために役割を担い、互いの鍵を保管できます。インスタンスは 12 個の単語でグループに参加します。

最初のインスタンスで **設定、ペアリング** を開き、**フレーズを作成** を押します。3 つのステップカードが手順を示します。12 個の単語が、**コピー** ボタンのあるウィンドウに表示されます。他のすべてのインスタンスで同じ場所を開き、**フレーズを入力** を押して、それらを貼り付けるか入力するか、そのウィンドウの **貼り付け** を押します。リストにない単語は入力中にその位置とともに示され、最後の単語はチェックサムを兼ねているため、入力ミスや単語の入れ替わりはペアリングが成立する前に検出されます。フレーズは 1 つのインスタンスでのみ作成してください。両方のインスタンスが作成すると、2 つの別々のグループができてしまいます。1 分たっても誰も現れない場合、ページは 2 つの逃げ道を示します。単語をもう一度表示してあちらで入力するか、もう一方のインスタンスの単語を入力して 1 回の手順でそのグループに参加するかです。ペアリングはログインパスワードなしでも動作しますが、設定してください。ないと、Web インターフェースを開ける人なら誰でも単語を読み取り、グループを通じて、グループ内のインスタンスの restic パスワードを引き渡す役割を要求できます。パスワードが設定されるまで、ペアリングカードがそのことを知らせます。パスワードがあれば、フレーズの再表示にもパスワードが求められます。**グループを抜ける** で、インスタンスをグループから外せます。ペアリングページの **インスタンス** カードにはグループのメンバーが一覧されます。誰が誰のために何をするかの図は、インスタンスページにあります。

単語を知っている人は誰でもグループに参加できるため、パスワードと同じように扱ってください。

**メンバー同士が互いに到達する方法。** 各インスタンスは、サインインした瞬間にブラウザーから自身のネットワーク上のアドレスを知り、インスタンス自身が見つけたものと合わせて、ペアリングページの **このインスタンス** カードにある **既知のアドレス** に表示されます。リバースプロキシや特殊なポートが手前にある場合は、そこで修正してください。同じネットワーク上では、メンバーがそのアドレスをマルチキャストで知らせて直接通信します。Docker の既定のブリッジのようにマルチキャストがコンテナネットワークを越えられない場所では、インスタンスは代わりに自身のサブネット内でほかのメンバーを探し、グループのメンバーだけが応答できる署名付きの呼び出しを使うため、リレーなしでも数秒でペアリングが完了します。何も見つからない場合、**見つかりませんか?** で、別のサブネットや標準外のポートのために、アドレスを 1 つ手入力できます。異なるネットワーク上のインスタンスはリレーを経由し、リレーは同じページの **リレー** カードで 4 つが 1 列に並んだ中から選びます。それぞれの形式に図が付いています。

- **プロジェクトのリレー**（既定）: `parleyport.halleluja.design`。KnightLoader も使うリレーです。設定は不要です。
- **自分のリレー**: Unraid Community Apps の [**ParleyPort**](https://github.com/junkerderprovinz/parleyport) コンテナ（**設定、アプリ** にもあります）です。使うすべてのインスタンスで、そのアドレスを入力してください。
- **BombVaultインスタンス**: 外部からすでに到達可能で **リレーとして機能させる** をオンにした自分のインスタンスです。そのインスタンスは、すでにあるリバースプロキシと証明書の背後で、自身のアドレスの `/relay/connect` で応答し、あなたのグループだけを通します。使うすべてのインスタンスで、そのアドレスを入力してください。
- **リレーなし**: メンバーは同じネットワーク上でのみ自動的に互いを見つけ、それ以外では見つけません。

**リレーに見えるもの。** 4 つの形式の横にある同名のボタンで、選んだ形式について確認できます。メンバー間のすべての呼び出しは、12 個の単語から導出した鍵で AES-256-GCM により封印され、その鍵があなたのインスタンスの外へ出ることはありません。リレーが知るのは、接続をまとめるハッシュ、メッセージの宛先のインスタンス、そのサイズ、通過する時刻です。ローカルネットワーク上の直接の呼び出しも同じように封印され、さらに署名されるため、インスタンスが提供する自己署名証明書には何も依存しません。何かを引き渡す呼び出し（役割への回答、restic パスワード、受信側のログイン、鍵の預け入れ）は、さらに送信側メンバーの鍵で署名され、その鍵は初めて見たときに固定されます。[セキュリティモデル](configuration.md#security-model)を参照してください。

**グループ経由で流れるもの。** インスタンスページの保護ステータス、1 つのセクションを今すぐ確認する要求、役割の要求とその回答、ストレージの提案、そして役割が許可されたあとに受信側や取得側が必要とするもの（相手のインスタンスのリポジトリの場所とその restic パスワード）です。バックアップデータは決して流れず、引き続き restic のバックエンドへ直接送られます。APP_KEY も流れません。restic パスワードはそのインスタンスのリポジトリを開くだけで、保存されたシークレット、セッション、リカバリーコードは開きません。

**ペアリング前のエントリ。** フリートトークンで追加されたインスタンス、および相手インスタンスの APP_KEY で設定された受信リポジトリと取得ソースは、アップデート後も残り、**再度ペアリング** と表示されます。これらは引き続き動作します。最初の起動時に、BombVault は保存されている各 APP_KEY を、そこから導出した restic パスワードに置き換えます。両方のインスタンスをペアリングしてから、エントリを編集してそのインスタンスを選んでください。それまで、こうしたエントリはインスタンスページの **インスタンスなし** カードに並びます。

APP_KEY を手動で受け付ける唯一の場所は[古いバックアップフォルダーから](#restore-from-another-bombvault-repo)で、相手のインスタンスが失われてグループ内で応答できない場合のためのものです。

## インスタンスと役割 {#roles}

**インスタンス** ページ（サイドバーに固定できる設定タイル）は、グループを「誰が誰のために何をするか」のネットワークとして表示し、このインスタンスのカード、ほかの各メンバー、Android スマートフォン、ZFS サーバーのカードを並べます。右下の **ペアリング** からペアリングページへ移動できます。どの部分をオンにするかは **設定、インスタンス、複数のサーバー** で設定します。**インスタンス**、**レシーバー**、**取得** です。

各カードにはメンバーの保護ステータスと、その役割がタイルとして表示されます。役割とは、あるインスタンスがほかのインスタンスのために行うことです。

- **レシーバー** は、このサーバーのオフサイトコピーを追記専用モードの rest-server に保持します。このサーバーはバックアップのたびに送信し、たとえ誰かに乗っ取られても、そこでは何も削除できません。
- **取得側** は、このサーバーのバックアップを独自のスケジュールで取得します。そのためにこのサーバーが起動している必要はありません。
- **ZFS サーバー** は、このサーバーの ZFS レプリカを受け取ります。各 ZFS 項目は設定の **レプリカ** で選びます。
- **鍵の保管側** は、このサーバーのリカバリーキットを封印したコピーとして保管します。[鍵の保管側](#key-keeper)を参照してください。

役割をオンにすると要求が送られ、相手のインスタンスで誰かが **許可** を押すまで何も始まりません。要求はそのインスタンスのカードにバッジとして表示され、その **詳細** に **許可** と **拒否** 付きで一覧されます。許可された役割は、そこでいつでも取り消せます。ネットワーク図の破線は、まだ待機中の役割です。BombVault 9.x のインスタンスは要求に応答できないため、そこではオンにした時点で役割が有効になり、9.x のインスタンスからの要求は、こちらで **許可** を待ちます。

カードの **詳細** は、残りを開きます。そのメンバーの受信リポジトリと取得ソース、ストレージの提案、モニタリング、**削除**、**キーを忘れる** です。

シャットダウンしたインスタンスや、アプリを閉じたスマートフォンは、灰色の **非アクティブ** としてカードが残り、最後に確認された時刻が表示されます。ネットワーク図では、**削除** するまで薄く表示されます。このサーバーの起動直後は、グループが戻るまでそうしたカードに **確認中** と表示されます。そうしたカードでは、どの部分がオンになっていても **削除** が使え、そのメンバーの未処理の要求、使われていない ZFS 受信枠、待機中の鍵の要求も終了します。ペアリングページの **インスタンス** カードにも、これらのメンバーは **非アクティブ** として並びます。

## レシーバーと取得側 {#receiver}

![インスタンスの詳細に表示された受信済みのオフサイトコピー。読み取り専用で監視され、このハードウェア上で整合性チェックが実行されています。](assets/screenshots/receiver.png)

*インスタンスの詳細に表示された受信済みのオフサイトコピー。読み取り専用で監視され、このハードウェア上で整合性チェックが実行されています。*

別の BombVault から追記専用のコピーを**受信**するマシンでは、受信リポジトリが、受信側ハードウェア上で独立した読み取り専用のモニタリングを提供するため、相手側で起きた静かな障害を見逃しません。**設定、インスタンス** で **レシーバー** をオンにし、インスタンスページで送信元インスタンスの **詳細** を開いて、受信リポジトリを追加します（読み取り専用で、送信元インスタンスの restic パスワードで開きます。このパスワードは[ペアリンググループ](#pairing)経由で取得されます）。次のものが得られます。

- **ソース別のインベントリ**。どのコンテナ、VM、フォルダーセットが届いたかを正確に確認できます。
- ソースごとの**最終受信**。それぞれがどれだけ新しいかがわかります。
- 受信側ハードウェアで実行される**独立した `restic check`**。整合性が送信側だけでなく、データが実際にある場所で検証されます。
- **デッドマンスイッチ**。設定した時間内にソースが送信をやめると、アラートが出ます。
- **整合性アラート**。受信側のチェックが失敗すると、アラートが出ます。

レシーバーは厳密に読み取り専用です。受信リポジトリには書き込まないため、送信側が頼りにしている追記専用の保証を壊すことは決してありません。

取得側はその逆の動きをします。**取得** をオンにすると、インスタンスは別のメンバーのバックアップを独自のスケジュールで、ソースごとの専用リポジトリに読み込みます。そのため、それらがこのマシン自身のバックアップとして数えられることはありません。そのソースも、そのメンバーの詳細に並びます。

### 受信サーバー {#receiving-server}

受信側のマシンは、ほかのインスタンスがコピー先にする rest-server も動かせます。最初に、それを求める **レシーバー** の要求を許可したときに設定されます。ウィンドウは、このサーバーには受信サーバーが必要であると伝え、共有上のフォルダー（**新しいフォルダー** で作成できます）とポート（別のコンテナが使っていなければ 8000）を尋ねます。その後、BombVault は次のことを行います。

1. `rest-server` という名前のコンテナがすでにある、または別のコンテナがそのポートを使っている場合は拒否します。
2. `restic/rest-server` を取得し、Docker ソケット経由で、追記専用モード、プライベートリポジトリ、フォルダー内のログインファイル付きで起動します。
3. Unraid テンプレートをフラッシュドライブに書き込み、コンテナを Docker タブで編集可能なままにします。フラッシュドライブに届かない場合は、テンプレートをダウンロードとして提供します。
4. それに対して改ざんテストを実行し、削除を拒否するかどうかを表示します。

グループのインスタンスは、そのサーバーをプロバイダーの **グループから** の下に、受信側マシンの名前で見つけ、**レシーバー** の役割はそれを安全な選択肢として提案します。各インスタンスは、そのサーバーを初めて使うときに専用のログインを受け取り、そこでは自身のフォルダーにだけ書き込みます。**設定、インスタンス** で **レシーバー** がオンのとき、このインスタンスのカードの **受信サーバー** でサーバーをもう一度開けます。そのウィンドウは、**ログインを持つパートナー** の下にログインを一覧し、**ログインを取り消す** でそのうちの 1 つを取り消します。そのインスタンスがすでにコピーしたものはフォルダーに残ります。設定時には **グループ外のログイン** も 1 つ作成され、そのパスワードはウィンドウに一度だけ表示されます。

リレー経由でしか受信側マシンに到達できないインスタンスは、サーバーを使えません。リレーはバックアップを運ばないためです。先に、ペアリングページで受信側マシンのアドレスを追加してください。BombVault が独自の IP アドレス（たとえば br0）で動いている場合は、サーバーがホストのアドレスで待ち受けるため、**パートナー向けのアドレス** を入力してください。

## 通しの例：2 台の Unraid ボックス、最初から最後まで

ここまでは部品の説明でした。ここでは完全なセットアップを 1 つ示します。部品は、一度組み上がった姿を見るほうが組み立てやすいからです。

2 台のボックスがあります。**TOWER** はコンテナを動かしてバックアップを送り、**VAULT** はそれを受け取って追記専用を強制します。名前、アドレス、共有パスは自分のものに置き換えてください。

**1. 2 台のボックスをペアリングする。** TOWER で **設定、ペアリング** を開き、**フレーズを作成** を押して、VAULT の **フレーズを入力** に 12 個の単語を入力します。先に両方でログインパスワードを設定してください。

**2. TOWER で、VAULT にレシーバーになるよう依頼する。** インスタンスページで、VAULT のカードの **レシーバー** をオンにし、セクションと、保存先として **VAULT の受信サーバー** を選んで、要求を送ります。

**3. VAULT で許可する。** VAULT のインスタンスページに、TOWER のカード上の要求が表示されます。**許可** を押します。初回は VAULT が受信サーバー用のフォルダー（たとえば `user/appdata/rest-server`）を尋ね、追記専用モードで rest-server を起動し、それに対して改ざんテストを実行します。

**4. TOWER に戻る。** それ以降、TOWER はバックアップのたびに VAULT へコピーし、新しい保存先が TOWER の保存先ページに、その削除に対する保護とともに表示されます。

改ざんテストの結果の意味は次のとおりです。

| 結果 | 起きたこと |
| --- | --- |
| **保護あり** | VAULT が削除を拒否しました。これが唯一の合格状態です。 |
| **保護なし** | VAULT が削除を受け入れました。`--append-only` がないか、削除されています。 |
| **判定不能** | どちらでもありません。たいていは URL が restic 自身の使うものと違うか、認証情報が変わっています。何も記録されず、アラートも出ません。 |

**5. 必要なら、届くものを監視する。** VAULT で **設定、インスタンス** の **レシーバー** をオンにし、TOWER の **詳細** を開いて受信リポジトリを追加します。VAULT は TOWER の restic パスワードをグループ経由で受け取るため、鍵を入力する人はいません。

**6. 相互にする。** 逆方向でも同じ手順を繰り返します。VAULT が TOWER に、自分のレシーバーになるよう依頼します。これで各ボックスが相手のために追記専用を強制し、どちらも相手のバックアップを削除できません。

手動で運用している rest-server も使えます。**保存先を追加** で rest-server として追加し、`.htpasswd` のユーザーとパスワードを入力して、削除に対する保護をオンにします。そのオプションには `--append-only` を残してください。ないと、相手側はふたたび通常の共有になります。

!!! warning "ローカルパスはコンテナ内部のパスです"
    BombVault がこのサーバー上のフォルダーを求めるときは、`/mnt/user/appdata/...` ではなく、ホストのマウントからの相対パス（たとえば `user/appdata/rest-server/bombvault-containers`）で入力してください。BombVault はコンテナ内で動作しており、ホストの `/mnt` は別の場所にマウントされているため、ホストの絶対パスはそこには存在しません。貼り付けた場合、BombVault は代わりに使うべき相対パスを知らせます。

## 緊急ウィザード {#emergency}

**緊急ウィザード** は、失われたサーバーや設定し直したサーバーを復旧します。**復元** ページの **緊急** から始まり、新規インストールのようこそページの **バックアップから復元** からも始められます。4 つのステップで進みます。**アクセス**、**設定**、**選択**、**復元** です。

1. **アクセス。** 以前のバックアップの鍵を BombVault に示します。方法は 3 つです。
    - **リカバリーキットをアップロード**: セットアップ中にダウンロードしたファイルです。鍵とすべての保存先が含まれ、BombVault はそこから残りを入力します。age で封印されたキットは、封印時に指定した ID を求めます。それは一度だけ使われ、保存されません。
    - **グループ経由**: グループのインスタンスが、鍵を預け入れとして保管しています。グループの 12 個の単語、取り出しコード、そのインスタンスにいる誰かが必要です。[鍵の保管側](#key-keeper)を参照してください。
    - **鍵を入力**: 以前のサーバーの `APP_KEY` と、そのバックアップの場所です。

    BombVault は続いて、すべての保存先でその鍵を試し、それぞれについて、読み取り可能、見つからない、別の鍵でロックされている、到達できない、サインインがまだ足りない、のいずれかを伝えます。まだ何も保存されておらず、鍵は限られた時間だけメモリ内に残ります。**鍵を引き継ぐ** は、このサーバーが今後その鍵でバックアップを書き込むようにします。**引き継ぎを取り消す** は、最初のバックアップが実行されるまで、サーバー自身の鍵に戻します。すでに独自のバックアップを持つサーバーは引き継ぎを拒否し、[古いバックアップフォルダーから](#restore-from-another-bombvault-repo)を案内します。**認証情報を保存** は、リモートの保存先についてキットが持つサインインを保存し、このサーバーにすでにあるサインインを置き換える前に確認します。
2. **設定。** **設定を戻す** は、最新のセルフバックアップから BombVault 自身の設定を復元します。保存先、認証情報、スケジュール、ルールです。BombVault は適用のために再起動します。Docker ソケット経由で行われるため、動作中の設定データベースが開いたハンドルの下で上書きされることはなく、そのあとウィザードは自動的に続行します。このサーバーのログインは維持されるため、今使っているパスワードでサインインし続けます。以前のサーバーが保存していて引き継げなかったシークレットは一覧されるため、もう一度入力できます。復元はすべてのセッションを終了してパスキーを削除するので、後でパスキーを設定し直してください。
3. **選択。** BombVault はバックアップを調べ、見つかったコンテナ、VM、フォルダーセット、ZFS データセットを一覧します。最新のバックアップは、どこでもあらかじめ選択されています。このサーバーにまだあるものはオフで始まります。復元すると置き換えてしまうためです。再構築のあと、フォルダーセットは元の場所を覚えていないため、選んだフォルダーに入ります。
4. **復元。** 選択したものがすべて一度に戻ります。各コンテナと VM を自分で起動したい場合は停止したままにでき、全損のあとはそれが最も安全です。その後、新しいリカバリーキットをダウンロードしてください。古いものは以前のインストールのものです。

!!! tip "計画的な移行と障害"
    緊急ウィザードは、バックアップから BombVault 自身の設定を復元します。新しいマシンへの*計画的な*移行では、代わりに **設定のエクスポート / インポート** カード（ポータブルな JSON ファイル）で設定を直接持ち込めます。[設定](configuration.md#portable-settings-export-and-import)を参照してください。

### 古いバックアップフォルダーから {#restore-from-another-bombvault-repo}

復元ページの **ほかの取得元** にある **古いバックアップフォルダーから** は、*別の* BombVault インスタンスのリポジトリ（`/mnt` 配下にマウントした共有、またはリモートアドレス）を、そのインスタンスのリカバリーキットまたは入力した `APP_KEY` で、一度きりの読み取り専用セッションとして開きます。そこに保存されているコンテナ、VM、フォルダーセット、ZFS データセットを参照し、バックアップを選んで復元すると、復元されたオブジェクトは通常のローカルのコンテナ、VM、フォルダーセットになります。相手のリポジトリには何も書き込まれず、自分のバックアップ設定には触れません（セッションはメモリ上にあり、自動的に失効します）。サーバー A からサーバー B へコンテナを移すために、設定を向け直して、あとで元に戻す必要はありません。このウィンドウは一度きりです。セッションを開き、選んだものを復元し、相手のインスタンスを忘れます。そうではなく、このマシンがほかのインスタンスのバックアップをスケジュールで自身のリポジトリに取得し続ける常設の仕組みがほしい場合は、インスタンスページの **取得側** の役割がそれです。

ネットワークがこのサーバーに存在しないコンテナ（たとえば通常の Docker ホスト上の Unraid の `br0` ネットワーク）は、その行の下にネットワークの選択を表示します。BombVault は選んだネットワーク上に、ほかのネットワークとともにそれを作成します。固定 IP と MAC アドレスは古いネットワークのものだったため破棄され、新しいネットワークが割り当てます。

## 鍵の保管側 {#key-keeper}

鍵の保管側とは、このサーバーのリカバリーキットを封印したコピーとして保持する、グループ内のインスタンスです。保管側はそのコピーを自分では開けません。このサーバーが失われたとき、グループに参加した新しいインストールが保管側にコピーを求め、取り出しコードで開きます。

1. インスタンスページで、保管するインスタンスのカードの **鍵の保管側** をオンにし、**預け入れる** を選びます。預け入れにはログインパスワードが必要です。
2. このサーバーは **取り出しコード** を一度だけ表示します。英数字 20 文字を 5 文字ずつ 4 つのグループにしたものです。書き留めて、**コードを書き留めました** で確認します。このサーバーはコードを保存せず、それ向けの預け入れを封印するのに必要なものだけを保持します。
3. これで保管側が預け入れを保持し、このサーバーはキットが変わるたびにそれを更新します。このインスタンスのカードの **鍵の預け入れ** は、**このサーバーの預け入れ** に各保管側とその状態を、**このサーバーが保管している預け入れ** にはほかのサーバーのものを一覧します。**新しいコードを作成** はコードを置き換え、各保管側は新しい預け入れを受け取った時点で新しいコードに切り替わります。

その日に必要なものは 3 つあります。グループの 12 個の単語、取り出しコード、そして保管側の画面へのアクセスで、そこでは誰かが **許可** を押す必要があります。緊急ウィザードで **グループ経由** を選び、預け入れを選んで要求し、取り出しコードを入力します。コードは新しいサーバーで使われ、保管側には送られません。保管側では、要求が **鍵の預け入れ** の下に、誰が要求しているか、そのインスタンスが以前そこで見られたことがあるか、何回要求したかとともに表示されます。**許可** は封印されたコピーを引き渡し、許可にはログインパスワードが必要です。新しいインストールは、許可のあと 30 分以内に受け取る必要があります。誰も応答しない要求は 1 日で失効し、頻繁に要求しすぎるインスタンスは 1 時間待たされます。

コードがなければ、保管側を含めて誰もコピーを開けません。コードを失くした場合は、このサーバーがまだ動いているうちに新しいものを作成してください。サーバーがすでに失われている場合でも、リカバリーキットと入力した APP_KEY は使えます。保管側は預け入れをいつでも削除でき、所有者はそのあと改めて要求する必要があります。

## リカバリーキット {#recovery-kit}

これは、BombVault が動いていなくても災害復旧を可能にする部品です。

**設定、復元** の **緊急時用** カードにある **リカバリーキットをダウンロード** は、**鍵**、**導出された restic パスワード**、各セクションのリポジトリを含むすべての**保存先**、新しいインストールがそれらに到達するために必要なサインイン、そして**正確な restic コマンド**を提供します。そのため、任意のマシンで restic CLI から直接復元できます。ログインパスワードが必要です。コンテナと VM の定義は常にこの鍵で封印されるため、キットは暗号化がオフの場合でも鍵を出力します。引き継ぎのあとは、引き継いだバックアップ鍵とこのサーバーの APP_KEY を出力します。後者は新しいインストールが設定を戻すためだけに必要です。保存するまで、概要の **リカバリーキットを保存してください** カードがリマインドします。

!!! danger "リカバリーキットはサーバーの外に保管してください"
    キットには、バックアップを復号する秘密が含まれています。サーバーとは別の安全な場所（パスワードマネージャー、金庫に入れた印刷物など）に保管してください。BombVault と `APP_KEY` の両方を失い、リカバリーキットも鍵の預け入れもない場合、暗号化されたバックアップは復旧できません。

!!! warning "最新のスナップショットが復元すべきものとは限りません"
    restic 0.17 以降、`restic snapshots` は各スナップショットのサイズを表示します。データ消失のあとでは、最新のスナップショットが空にされたものである可能性があるため、それ以前のものよりはるかに小さいスナップショットは復元しないでください。ランサムウェアのあとでは、通常のサイズのまま暗号化されたものである可能性があります。BombVault がまだ動いているなら、まずその **異常** ページを確認してください。最後に正常だったバックアップが示され、復元ウィンドウはそれをあらかじめ選択します。復元に BombVault の異常データは必要なく、保持の一時停止は常により多くのスナップショットを残すだけです。

### キットの封印

**設定、システム** の **age でエクスポートを暗号化** をオンにしている場合、キットも同じ方法で封印され、`bombvault-recovery-kit.md.age` としてダウンロードされます。バイナリではなく ASCII アーマー形式なので、引き続きプレーンテキストです。パスワードマネージャーへの貼り付けや印刷は以前とまったく同じように使え、内容があなたの鍵なしでは読めないだけです。

!!! warning "age の鍵をキットの中に保管しないでください"
    封印されたキットを開くには age の**秘密**鍵が必要です。キット自体に依存しない場所に保管してください。そうしないと、復旧すべきものが 1 つではなく 2 つになります。封印が役立つのは、キットを自分で完全には管理できない場所（共有のパスワードマネージャー、クラウドのメモ、オフィスに置いた印刷物）に保管する場合です。自分の金庫にあるキットは、すでに金庫が守っています。

    暗号化がオンで使える受信者が設定されていない場合、ダウンロードはきっぱり拒否されます。BombVault がマスターキーを平文で渡すことに戻ることは決してありません。

### 手元にキットがないとき

パスワードはどこにも保存されておらず、バックアップの鍵から**計算**されます。そのため、鍵とシェルだけで自分で再現できます。

```sh
printf 'bombvault:restic-repo' \
  | openssl dgst -sha256 -mac HMAC -macopt hexkey:$APP_KEY -r \
  | cut -d' ' -f1
```

これは固定文字列 `bombvault:restic-repo` に対する HMAC-SHA256 で、16 進の `APP_KEY` の生のバイト列を鍵とし、小文字 16 進 64 文字で出力されます。同じ値がキットにも、導出された restic パスワードとして記載されています。これは、キットが手元にない日のためのものです。ほかのサーバーのバックアップを引き継いだサーバーでは、引き継いだバックアップ鍵、つまりそのサーバーの以前の APP_KEY を使ってください。

!!! warning "受信したリポジトリには、送信側のインスタンスの鍵を使います"
    オフサイトコピーでここに届いたリポジトリは、送信したマシンが**そちらの**鍵で作成したものです。受信側のマシンの鍵から導出すると、restic が拒否するパスワードになり、これは破損したリポジトリとまったく同じように見えますが、破損ではありません。受信したリポジトリでの `restic check` が何度もパスワードを求める、よくある原因はこれです。

リカバリー定義は各リポジトリの**内側**に存在するため（`<repo>/def`、`<repo>/vm-def`）、コピーされたリポジトリフォルダーは完全に自己完結しています。つまり、キットとリポジトリがあれば、ベアメタル復元に必要なものはすべて揃います。

## データベースダンプを取り戻す {#database-dumps}

データベースダンプは、コンテナのリポジトリ内にある独立した復元ポイントで、タグは `dbdump:<container>`、単一のファイル `/dbdump/<container>.sql` を保持しています。BombVault はそれらをコンテナの **バックアップ** タブで一覧、ダウンロード、インポートします。以下は、BombVault がない日のために、restic だけで行う同じ手順です。

```sh
restic -r <repo> snapshots --tag dbdump:<container>
restic -r <repo> dump --tag dbdump:<container> latest /dbdump/<container>.sql > <container>.sql
```

各ダンプのタグ `dbversion:` と `dbname:` は、どのサーバーバージョンから取られたか、どのデータベースを含むかを示します。完全なファイルは `-- PostgreSQL database cluster dump complete` または `-- Dump completed` で終わります。

同じかそれより新しいバージョン（PostgreSQL）、あるいは同じメジャーバージョン（MySQL と MariaDB）のコンテナに取り込みます。コンテナは空のデータフォルダーで一度起動し、初期化を済ませておきます。ホストにデータベースクライアントは要りません。コンテナが持っています。

```sh
docker exec -i <container> sh -c 'exec psql -X -U "${POSTGRES_USER:-postgres}" -d postgres' < <container>.sql
docker exec -i <container> sh -c 'exec mariadb -uroot -p"$MARIADB_ROOT_PASSWORD"' < <container>.sql
docker exec -i <container> sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < <container>.sql
```

全体のダンプから 1 つのデータベースだけを入れる場合、MySQL と MariaDB はクライアントのコマンドに `--one-database <name>` を取ります。PostgreSQL のダンプはデータベースごとに区画があり、それぞれ `\connect <name>` の行で始まります。その区画を別ファイルにコピーし、データベースを作ってから `-d <name>` で取り込んでください。

!!! warning "root で取ったダンプはサーバーの利用者も連れてくる"
    root で取った MySQL や MariaDB の完全なダンプにはシステムデータベース `mysql` が入っているため、取り込むと新しいサーバーのアカウントが、root のパスワードも含めてダンプのものに置き換わります。PostgreSQL では、コンテナ自身が作った利用者に対する `role ... already exists` は想定どおりで害はありません。
