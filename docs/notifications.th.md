# การแจ้งเตือน

BombVault แจ้งให้คุณรู้ได้เมื่อการสำรองข้อมูลล้มเหลว เมื่อสำเร็จ เมื่อมีอันที่ล่าช้า และสรุปสัปดาห์ละครั้งว่าเป็นอย่างไรบ้าง ทุกอย่างตั้งค่าที่ **การตั้งค่า, การแจ้งเตือน** สิ่งที่ BombVault ส่งนอกเหนือจากการสำรองแต่ละครั้งอยู่ในการ์ด **การแจ้งเตือน** และข้อความไปที่ไหนอยู่ในการ์ด **ช่องทาง** แต่ละช่องทางตัดสินเองว่าจะแจ้งเมื่อไร และการตรวจของ Healthchecks ก็เป็นช่องทางหนึ่งด้วย

![การตั้งค่า, การแจ้งเตือน ที่กรอกช่องทาง Gotify แล้ว](assets/screenshots/notifications/gotify-light.png#only-light)

## อะไรที่ทำให้ส่งข้อความ {#what}

สวิตช์ในการ์ด **การแจ้งเตือน** ใช้กับทุกช่องทาง

- **สรุปการรันตามกำหนดเวลา**: หนึ่งข้อความต่อหนึ่งรอบตามกำหนด เช่น *สำเร็จ 42 จาก 45* แทนที่จะส่งหนึ่งข้อความต่อคอนเทนเนอร์หรือ VM การสำรองที่คุณเริ่มด้วยมือยังส่งข้อความของตัวเอง เกสต์ที่ค้าง การเก็บรักษาที่ล้มเหลว หรืองบการเติบโตที่เกิน จะส่งทันทีแม้เปิดการสรุปอยู่
- **แจ้งเตือนเมื่ออัปเดต container**: หนึ่งข้อความต่อคอนเทนเนอร์ที่ **อัปเดตคอนเทนเนอร์หลังสำรองข้อมูลสำเร็จ** ย้ายไปใช้ image ที่ใหม่กว่า คุณจะได้ตรวจดูว่ายังทำงานปกติ
- **รายงานข้อมูลสำรองที่ล่าช้า**: วันละครั้งเวลา 09:00 BombVault ตรวจว่ามีการสำรองที่เปิดอยู่และล่าช้าหรือไม่ หมายถึงเก่ากว่าสองเท่าของกำหนดการ และส่งหนึ่งข้อความต่อกรณี พร้อมระบุชื่อรายการที่ล่าช้า การสำรองที่สำเร็จครั้งถัดไปจะล้างมัน
- **สรุปประจำสัปดาห์**: สรุปหนึ่งครั้งต่อสัปดาห์ มีจำนวนรอบ ข้อมูลสำรองใหม่ ส่วนไหนล่าช้า สำเนานอกสถานที่ยังใหม่อยู่หรือไม่ และความล้มเหลวอันดับต้น ๆ กำหนดการของมันเป็นปุ่มเหมือนกำหนดการอื่น และ **ปิด** จะปิดมัน ดู [ตารางเวลา](schedules.md#plans)

ช่องทางจะแจ้งความสำเร็จด้วยหรือไม่ ตั้งที่ช่องทางนั้นใต้ **แจ้งเตือน** ความผิดปกติแบบไหนส่งข้อความตั้งได้ที่ **การตั้งค่า, ยืนยัน** ดู [ความผิดปกติ](anomalies.md) การสำรองที่เลื่อนออกไปส่งหนึ่งข้อความเมื่อเริ่มรอ และอีกหนึ่งข้อความเมื่อการรอสิ้นสุด ไม่ใช่หนึ่งข้อความต่อการลองแต่ละครั้ง

## ช่องทาง {#channels}

**เพิ่มช่องทาง** ที่ด้านล่างของการ์ด **ช่องทาง** มี **การแจ้งเตือน Unraid**, **ntfy**, **Gotify**, **Discord**, **Slack**, **Matrix**, **อีเมล (SMTP)**, **Apprise**, **Webhook** และ **Healthchecks** ให้เลือก เพิ่มได้มากเท่าที่ต้องการ ชนิดเดียวกันสองอันก็ได้ เช่น หัวข้อ ntfy หนึ่งอันสำหรับความล้มเหลว และอีกอันสำหรับทุกอย่าง ช่องทางใหม่เริ่มแบบปิดอยู่ จึงถูกบันทึกไว้ก่อนที่คุณจะกรอกฟิลด์

ทุกช่องทางมี

- สวิตช์ของตัวเอง ปิดได้โดยไม่เสียค่าในฟิลด์
- **แจ้งเตือน**: **ไม่เลย**, **เฉพาะเมื่อล้มเหลว** หรือ **เมื่อสำเร็จและล้มเหลว** ช่องทางใหม่เริ่มที่ **เฉพาะเมื่อล้มเหลว** การสำรองที่สำเร็จแต่ข้ามบางอย่างไปก็ส่งถึงช่องทางที่รับเฉพาะความล้มเหลวด้วย
- **ชื่อ** ไม่บังคับ และแสดงแทนชนิดของช่องทาง สะดวกเมื่อมีชนิดเดียวกันสองอัน
- **ส่งทดสอบ** ส่งข้อความทดสอบผ่านช่องทางนี้ โดยใช้ค่าตามที่อยู่ในฟอร์มตอนนั้น ไม่ว่าจะบันทึกแล้วหรือไม่ บรรทัดใต้ช่องทางจะบอกว่าบริการรับไว้หรือไม่ และถ้าไม่รับ เพราะอะไร
- **ลบช่องทาง** ปุ่มถังขยะข้าง ๆ

แต่ละช่องทางส่งแยกกันและมีเวลาจำกัดของตัวเอง โฮสต์หนึ่งที่ไม่ตอบจึงไม่ทำให้ช่องอื่นช้าลง เมื่อบริการล้มเหลวแบบที่ลองใหม่แล้วอาจหาย ช่องทางจะลองได้สูงสุดสามครั้ง การแจ้งเตือนเรื่องการสำรองล่าช้า งบประมาณ หรือความผิดปกติที่ไม่มีช่องทางไหนรับไว้จะถูกลองส่งอีกครั้งภายหลัง สรุปประจำสัปดาห์ก็เช่นกัน

| ช่องทาง | ฟิลด์ | หมายเหตุ |
|---|---|---|
| **การแจ้งเตือน Unraid** | ไม่มี | ส่งไปยังระบบแจ้งเตือนของ Unraid เอง ซึ่งส่งต่อไป Pushover อีเมล หรือ Discord ได้ ทำงานผ่านการเชื่อมต่อ SSH จาก **การตั้งค่า, การเชื่อมต่อ, SSH ของโฮสต์** คีย์นั้นจึงต้องได้รับอนุญาต บน TrueNAS และโฮสต์อื่นจะไม่ส่งอะไร และช่องทางจะบอกเหตุผล |
| **ntfy** | **URL ของหัวข้อ**, **โทเค็นการเข้าถึง (ไม่บังคับ)** | ที่อยู่ลงท้ายด้วยหัวข้อของคุณ ต้องใช้โทเค็นเฉพาะหัวข้อที่ป้องกันไว้ |
| **Gotify** | **URL ของเซิร์ฟเวอร์**, **โทเค็นแอป**, **ลำดับความสำคัญเมื่อล้มเหลว**, **ลำดับความสำคัญเมื่อสำเร็จ** | ลำดับความสำคัญมีค่า 0 ถึง 10 เริ่มที่ 8 เมื่อล้มเหลวและ 5 เมื่อสำเร็จ |
| **Discord** | **URL ของ Webhook** | ที่อยู่ของ webhook จากการตั้งค่าของช่อง Discord |
| **Slack** | **URL ของ Webhook** | ที่อยู่ของ incoming webhook ของแอป Slack ของคุณ |
| **Matrix** | **URL ของ Homeserver**, **โทเค็นการเข้าถึง**, **ID ห้อง** | บัญชีเจ้าของโทเค็นต้องอยู่ในห้องนั้น |
| **อีเมล (SMTP)** | **โฮสต์ SMTP**, **พอร์ต**, **การเข้ารหัส**, **ชื่อผู้ใช้**, **รหัสผ่าน**, **ที่อยู่ผู้ส่ง**, **ที่อยู่ผู้รับ** | **การเข้ารหัส** เป็น **STARTTLS**, **TLS (implicit)** หรือ **None** |
| **Apprise** | **URL ของ Apprise API**, **แท็ก (ไม่บังคับ)**, **ที่อยู่ Apprise (ไม่บังคับ)** | ชี้ไปที่ endpoint `/notify/<key>` ของคอนเทนเนอร์ Apprise API ของคุณเพื่อเข้าถึงบริการกว่า 100 รายการ และแท็กเลือกชุดย่อยของปลายทางของคีย์นั้น หรือใส่ที่อยู่ Apprise บรรทัดละหนึ่งอัน เช่น `tgram://` สำหรับ Telegram หรือ `pover://` สำหรับ Pushover แล้วให้ URL ของ API ลงท้ายด้วย `/notify` โดยไม่มีคีย์ |
| **Webhook** | **URL ของ Webhook**, **เมธอด**, **ส่วนหัว**, **เนื้อหา** | คำขอที่คุณกำหนดเอง ดู [Webhook](#webhook) |
| **Healthchecks** | **URL ping** | ดู [Healthchecks](#healthchecks) |

ความลับอย่างโทเค็น รหัสผ่าน SMTP และค่าของส่วนหัว webhook ถูกเก็บแบบเข้ารหัส และเซิร์ฟเวอร์ไม่ส่งกลับมาให้หน้าเว็บเลย ใต้ความลับที่บันทึกแล้ว ช่องจะแสดง **บันทึกแล้ว เว้นช่องว่างไว้เพื่อคงค่าเดิม** เมื่อคุณเปลี่ยนปลายทางของช่องทาง BombVault จะไม่ส่งความลับเก่าไปยังที่ใหม่ ช่องจะแสดง **ที่อยู่ใหม่จะถูกบันทึกเมื่อคุณป้อนข้อมูลนี้อีกครั้ง**

การตั้งค่าจากเวอร์ชันก่อนมีรายการช่องทางจะถูกย้ายมาตอนเริ่มครั้งแรก โดยไม่มีอะไรหาย แต่ละช่องทางที่คุณเคยกรอกไว้จะกลายเป็นรายการของตัวเอง พร้อมตัวเลือก **แจ้งเตือน** เดิมของคุณ webhook ที่ตั้งรูปแบบเป็น Discord, Slack, Gotify หรือ ntfy จะกลายเป็นช่องทางชนิดนั้น ส่วน webhook แบบ Generic JSON ยังคงส่ง `title`, `message` และ `ok` ผ่าน **เนื้อหา** ของมัน สวิตช์ Unraid กลายเป็นช่องทาง Unraid และ URL ของ Healthchecks พร้อมข้อยกเว้นกลายเป็นช่องทาง Healthchecks

### Webhook {#webhook}

ช่องทาง **Webhook** ส่งคำขอ HTTP หนึ่งครั้งไปยังที่อยู่ใดก็ได้ **เมธอด** เป็น GET, POST หรือ PUT **เพิ่มส่วนหัว** เพิ่มแถวใต้ **ส่วนหัว** และค่าของส่วนหัวถูกเก็บเป็นความลับ ส่วนหัว `Authorization` จึงใส่ไว้ที่นี่ได้อย่างปลอดภัย **เนื้อหา** ถูกส่งตามที่คุณเขียนทุกตัวอักษร โดยเติมตัวแทนเหล่านี้ให้

| ตัวแทน | กลายเป็น |
|---|---|
| `%%title%%` | หัวเรื่องของข้อความ |
| `%%body%%` | ตัวข้อความ |
| `%%ok%%` | `true` หรือ `false` เมื่อล้มเหลว |
| `%%event%%` | สิ่งที่เกิดขึ้น เช่น `container.failed` |
| `%%severity%%` | `info`, `success`, `warning`, `failure` หรือ `critical` |
| `%%importance%%` | ระดับของ Unraid สำหรับเรื่องนั้น: `normal`, `warning` หรือ `alert` |
| `%%link%%` | ลิงก์ที่เกี่ยวกับข้อความ ว่างเมื่อไม่มี |
| `%%key%%` | ส่วน เช่น `container` หรือ `VM` |
| `%%time%%` | เวลาแบบ UTC เช่น `2026-11-09T03:00:00Z` |
| `%%source%%` | `BombVault` |

ตัวแทนใช้ได้ในที่อยู่และในค่าของส่วนหัวด้วย และแต่ละค่าจะถูก escape ให้เหมาะกับตำแหน่งที่อยู่ เป็น JSON เมื่อส่วนหัว `Content-Type` บอกว่าเป็น JSON และเป็นค่า query ในที่อยู่ webhook ใหม่เริ่มต้นพร้อมส่วนหัวนั้น และส่ง `{"title":"%%title%%","message":"%%body%%","ok":%%ok%%}` ชื่อที่ BombVault ไม่รู้จักจะคงไว้ตามที่เขียน คำที่พิมพ์ผิดจึงเห็นได้ในข้อความ ปล่อย **เนื้อหา** ว่างไว้ถ้าไม่ต้องการส่งเนื้อหา

## Healthchecks {#healthchecks}

บริการอย่าง [Healthchecks.io](https://healthchecks.io) ส่งสัญญาณเตือนเมื่อ BombVault หยุดเช็กอิน เพิ่มช่องทาง **Healthchecks** และวาง **URL ping** ของการตรวจนั้น แล้ว BombVault จะ ping มันตลอดวงจรของการสำรองทุกครั้ง ตอนเริ่ม แล้วตอนสำเร็จหรือด้วย `/fail` ช่องทางนี้ไม่มีตัวเลือก **แจ้งเตือน** เพราะการตรวจต้องได้ ping ตอนสำเร็จจึงจะเป็นสีเขียวต่อไป ส่วนที่ไม่มีที่ให้สำรองไปนับว่าล้มเหลว การตรวจของมันจึงเป็นสีแดงแทนที่จะได้รับสัญญาณว่าสำเร็จ

ส่วนที่ใช้ URL เดียวกันจะใช้การตรวจเดียวกัน เมื่อการสำรองของส่วนหนึ่งล้มเหลว การสำรองที่สำเร็จของส่วนอื่นจะ ping `/fail` ด้วยและระบุชื่อรายการนั้น การตรวจจึงเป็นสีแดงจนกว่ารายการนั้นจะสำรองสำเร็จอีกครั้ง หรือคุณรับทราบความล้มเหลวนั้นใต้ **ต้องดูแล**

ส่วนหนึ่ง ping ที่อยู่ของตัวเองได้ **ข้อยกเว้น** ในช่องทาง Healthchecks เพิ่มหนึ่งรายการ แล้วบรรทัดจะบอกว่า **ส่วนอื่นทั้งหมด ping URL นี้** เมื่อกด **ส่งทดสอบ** ในช่องทางนี้ แต่ละการตรวจจะได้รายการหนึ่งในบันทึกของมัน โดยสถานะของมันยังเหมือนเดิม

## ตัวอย่าง: Gotify บนโทรศัพท์ {#example-gotify}

คุณรัน Gotify ที่ `https://gotify.example.com` และอยากให้ความล้มเหลวดังบนโทรศัพท์ ส่วนความสำเร็จมาแบบเงียบ ๆ

1. ใน Gotify เปิด **Apps** สร้างแอปพลิเคชันชื่อ `BombVault` แล้วคัดลอกโทเค็นของมัน
2. ใน BombVault เปิด **การตั้งค่า, การแจ้งเตือน** แล้วเปิด **สรุปการรันตามกำหนดเวลา** คืนที่มีการสำรอง 45 รายการจะส่งหนึ่งข้อความแทน 45 ข้อความ
3. ใน **ช่องทาง** กด **เพิ่มช่องทาง** แล้วเลือก **Gotify**
4. กรอก `https://gotify.example.com` ใน **URL ของเซิร์ฟเวอร์** BombVault เติม `/message` ให้เอง
5. วางโทเค็นใน **โทเค็นแอป**
6. ตั้ง **แจ้งเตือน** เป็น **เมื่อสำเร็จและล้มเหลว** คง **ลำดับความสำคัญเมื่อล้มเหลว** ไว้ที่ 8 และ **ลำดับความสำคัญเมื่อสำเร็จ** ไว้ที่ 5 แอป Android ของ Gotify ถือว่า 8 ขึ้นไปเป็นระดับสูง จึงมีเพียงความล้มเหลวที่มีเสียง
7. เปิดสวิตช์ของช่องทางแล้วกด **ส่งทดสอบ** บรรทัดใต้ช่องทางจะบอกว่า Gotify รับไว้หรือไม่ และถ้าโทเค็นถูกปฏิเสธก็จะระบุไว้ตรง ๆ

รอบตามกำหนดครั้งถัดไปจะส่งสรุปหนึ่งข้อความที่ลำดับความสำคัญ 5 หรือที่ 8 ถ้ามีอะไรในนั้นล้มเหลว

## ตัวอย่าง: ntfy แบบไม่ต้องมีบัญชี {#example-ntfy}

ntfy ไม่ต้องมีบัญชีสำหรับหัวข้อสาธารณะ เลือกชื่อหัวข้อที่เดายาก เพราะใครที่รู้ชื่อก็อ่านได้

1. ใน **ช่องทาง** กด **เพิ่มช่องทาง** แล้วเลือก **ntfy**
2. กรอกที่อยู่ของหัวข้อใน **URL ของหัวข้อ** เช่น `https://ntfy.sh/bombvault-tower-7f3k` หรือหัวข้อบนเซิร์ฟเวอร์ ntfy ของคุณเอง ปล่อย **โทเค็นการเข้าถึง (ไม่บังคับ)** ว่างไว้สำหรับหัวข้อสาธารณะ
3. สมัครรับหัวข้อเดียวกันในแอป ntfy เปิดสวิตช์ของช่องทาง แล้วกด **ส่งทดสอบ**

BombVault ส่งข้อความเป็นเนื้อหา โดยมีหัวเรื่องอยู่ในส่วนหัว `Title` ความล้มเหลวส่งด้วยลำดับความสำคัญสูงและแท็ก `warning` จึงเด่นขึ้นในแอป และ VM ที่ค้างอยู่จะส่งเป็นระดับเร่งด่วน
