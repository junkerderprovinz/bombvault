# البدء

تقود هذه الصفحة من جهاز Unraid جديد إلى أول نسخة احتياطية.

## المتطلبات

| المتطلب | ملاحظات |
|---|---|
| **Unraid 6.12+** | الإصدارات الأقدم غير مُختبَرة. Unraid هو الهدف الأساسي، لكن BombVault يعمل أيضًا على مضيف Docker عادي وعلى TrueNAS Scale (يُنظر [مضيف Docker عام](#generic-docker-host) و[TrueNAS SCALE](#truenas)). |
| **موقع مستودع restic** | مسار محلي (يُنصح به: المصفوفة أو الكاش)، أو SMB، أو NFS، أو أي خلفية rclone. |
| **مقبس Docker** | يركّبه القالب تلقائياً (`/var/run/docker.sock`). |
| **Unraid flash** (`/boot`) | يركّبه القالب بالكامل تلقائياً (`/boot` إلى `/host/boot`). يشغّل نسخ الفلاش الاحتياطي ويتيح لحاوية مُستعادة أن تظهر من جديد كتطبيق Unraid عادي وقابل للتحرير. |
| **KVM VMs** (اختياري) | يتحدث نسخ الـ VM الاحتياطي إلى libvirt عبر SSH، دون تركيب libvirt. يُعدّ تحت **الإعدادات، التكاملات، SSH المضيف** (يُنظر [الإعدادات](configuration.md)). |
| **مجموعات بيانات ZFS** (اختياري) | اتصال SSH نفسه الذي تستخدمه نسخ الـ VM الاحتياطية، و`zfs` على المضيف، وHost Data مربوطًا كـ `/mnt` بوضع الوصول Read/Write - Slave، وهو الافتراضي في القالب. يُنظر [مجموعات بيانات ZFS](zfs-datasets.md). |
| **تطبيق Android** (اختياري) | Android 10 أو أحدث، مقترنًا بخوادم على الإصدار 9.7.0 أو أحدث. يُنظر [تطبيق Android](android.md). |

## التثبيت على Unraid

أسهل مسار هو **Community Applications**.

1. فتح تبويب **Apps** في Unraid.
2. البحث عن **BombVault**.
3. النقر على **Install**، وضبط المتغيرات المطلوبة (أدناه)، ثم التطبيق.

!!! tip "تثبيت القالب يدوياً"
    لإضافة القالب يدوياً:

    1. الانتقال إلى **Docker, Add Container, Template repositories** وإضافة:
       ```
       https://github.com/junkerderprovinz/unraid-apps
       ```
    2. البحث عن **BombVault** في Templates.
    3. ضبط المتغيرات المطلوبة والنقر على **Apply**.

## مضيف Docker عام {#generic-docker-host}

لست على Unraid؟ يعمل BombVault أيضًا كحاوية عادية على أي مضيف Docker. ولـ TrueNAS SCALE خطوات خاصة به تحت [TrueNAS SCALE](#truenas).

1. احصل من المستودع على الملف [`deploy/docker-compose.generic.yml`](https://github.com/junkerderprovinz/bombvault/blob/main/deploy/docker-compose.generic.yml) الجاهز للتحرير.
2. ضبط `APP_KEY` (يُنظر أدناه) وتوجيه وحدة Host Data إلى جذر البيانات الحقيقي. تعليقات الملف تشرح الأمرين.
3. `docker compose up -d`، ثم فتح `https://<ip-المضيف>:3443/`.

ما الذي يختلف عن Unraid:

- **لا يوجد قسم Flash.** لا توجد ذاكرة إقلاع لالتقاطها أو استعادتها، لذا لا عمل لقسم Flash هنا. بدلًا من ذلك، عندما يصل Host Data إلى `/etc` على المضيف، تعرض **إضافة** في صفحة النسخ الاحتياطية **إعدادات النظام** كاقتراح مجلد: مجموعة مجلدات `/etc` مبدئية تُراجع وتُعدَّل قبل الحفظ.
- **لا توجد إشعارات Unraid الأصلية.** قنوات الإشعارات الخاصة بـ BombVault (webhook، تنبيهات فشل النسخ خارج الموقع وغيرها) تعمل كالمعتاد؛ ويُتخطّى فقط الإرسال الخاص بنظام إشعارات Unraid، إذ لا وجود لمثل هذا النظام هنا.
- **نسخ الأجهزة الافتراضية اختياري ويحتاج مضيف libvirtd منفصلًا يمكن بلوغه عبر SSH.** تُراجع الكتلة المعلّقة في ملف compose. المضيف العام لا يحمل في ذاته أي مدير للأجهزة الافتراضية.
- **لا توجد أداة للوحة Dashboard.** BombVault Widget إضافة لـ Unraid، لذا تُتخطّى هذه الخطوة أيضًا.
- **العثور على بيانات الحاوية.** من دون اصطلاح `appdata` في Unraid، يُعثر على مجلد بيانات الحاوية من المقاطع الواردة في `DATA_ROOT_SEGMENTS`، ومن وحدات Docker المسمّاة، ومن مجلد العمل لمشروع Compose، ومن التسمية `bombvault.data` (يُنظر [اكتشاف مصادر النسخ الاحتياطي](configuration.md#backup-source-detection)). لا تصل الوحدات المسمّاة والإعداد المسبق `/etc` إلا إلى المسارات داخل تركيب Host Data، لذا يُوجَّه Host Data إلى مجلد أب مشترك يشمل أيضًا جذر بيانات Docker.
- **`PLATFORM`.** يُضبط على `generic` أو `truenas`. إن تُرك غير مضبوط، يتعرّف BombVault على Unraid من علامته الخاصة على تركيب الفلاش ويعامل أي شيء آخر كمضيف عام، وتُتخطّى الخطوات الخاصة بـ Unraid بدلًا من تجربتها وفشلها.

### TrueNAS SCALE {#truenas}

BombVault ليس في كتالوج تطبيقات TrueNAS بعد، لذا يُثبَّت كتطبيق مخصص: **Apps, Discover Apps**، ثم **Install via YAML** في القائمة بجانب **Custom App**. يضبط ملف YAML أدناه الأشياء نفسها التي يضبطها مدخل الكتالوج في مجلد `truenas-apps` في المستودع. يُستبدل `tank` باسم الـ pool المستخدَم، ويُملأ `APP_KEY` كما يشرح القسم التالي.

```yaml
services:
  bombvault:
    image: junkerderprovinz/bombvault:latest
    hostname: bombvault
    restart: unless-stopped
    cap_drop: [ALL]
    cap_add: [CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETPCAP, SETUID]
    environment:
      APP_KEY: ""
      PLATFORM: truenas
      HOST_SOURCE_ROOT: /mnt/tank
      HOST_MOUNT_ROOT: /mnt/tank
      # لنسخ الـ VM الاحتياطي:
      # LIBVIRT_URI: qemu+ssh://root@<truenas-ip>/system?socket=/run/truenas_libvirt/libvirt-sock
    volumes:
      - /mnt/tank/apps/bombvault:/config
      - /var/run/docker.sock:/var/run/docker.sock
      - type: bind
        source: /mnt/tank
        target: /mnt/tank
        bind:
          propagation: rslave
    ports:
      - "30528:3443"
```

ثم يُفتح `https://<truenas-ip>:30528/`. ما ورد تحت [ما الذي يختلف عن Unraid](#generic-docker-host) ينطبق هنا أيضاً، وعلى TrueNAS:

- **الصلاحيات (capabilities).** يحتاج BombVault الصلاحيات الست المذكورة أعلاه. تفشل نسخ الـ VM الاحتياطية من دون `SETPCAP`.
- **Host Data** مسار مضيف على مجموعة بيانات، هنا `/mnt/tank`، مركَّب على المسار نفسه داخل التطبيق. لهذا يذكره `HOST_SOURCE_ROOT` و`HOST_MOUNT_ROOT` كلاهما. ويمرر `rslave` عمليات التركيب التي يجريها المضيف لاحقاً، وهذا ما تحتاجه نسخ مجموعات بيانات ZFS.
- **البيانات في ixVolume لا تُنسخ احتياطياً.** التطبيق الذي تخزينه ixVolume يحفظ بياناته تحت `/mnt/.ix-apps`، خارج Host Data. يحفظ BombVault تعريف التطبيق فقط، ويذكر التشغيل المجلدات التي تركها. لكل تطبيق يُراد نسخ بياناته يُختار تخزين **Host Path** على مجموعة بيانات تحت Host Data.
- **نسخ الـ VM ومجموعات بيانات ZFS** تصل إلى TrueNAS عبر SSH بصفة root. تُفعَّل خدمة SSH تحت **System, Services**، ويُضاف المفتاح العام من **الإعدادات، التكاملات، SSH المضيف** إلى المستخدم root تحت **Credentials, Users**. وتحتاج نسخ الـ VM أيضاً إلى `LIBVIRT_URI` كما في الأعلى، لأن libvirtd في TrueNAS يستمع على مقبس خاص به. وإذا لم يُضبط `LIBVIRT_URI` ولا `LIBVIRT_HOST`، يستخدم BombVault البوابة الافتراضية للتطبيق كمضيف، لأن `host.docker.internal` لا يُحَلّ في تطبيق TrueNAS. يشرح [دليل نسخ الـ VM](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md#truenas-scale) التفاصيل، بما فيها الـ VMs على zvols.
- **النسخة المتماثلة لـ ZFS تستخدم مفتاحاً آخر.** النسخة المتماثلة على خادم ZFS ثانٍ تسجّل الدخول بالمفتاح الذي يعرضه مربع حوار النسخة المتماثلة، لا بمفتاح SSH المضيف. يُضاف ذلك المفتاح على الخادم المستقبِل.
- **التطبيق المحذوف يعود على خطوتين.** يُعاد تثبيته أولاً في TrueNAS بالاسم نفسه، فيُنشئ ذلك شبكته من جديد، ثم تُستعاد بياناته في BombVault. وحتى ذلك الحين يبلّغ فحص ما قبل الاستعادة عن الشبكة المفقودة، وترفض الاستعادة قبل أن تغيّر أي شيء.
- **بجانب الأصل** تُنشئ حاوية Docker عادية. تعمل، لكن شاشة Apps في TrueNAS لا تعرضها.
- **تفريغات قواعد البيانات** تعمل على تركيبات مجموعات البيانات. الاستيراد إلى مجلد بيانات هو نفسه مجموعة بيانات مستقلة ينقل المحتويات القديمة إلى مجلد بجانبه، لذا تحتاج مجموعة البيانات الأعلى إلى مساحة لها.

## الإعداد المطلوب الوحيد

المتغير الوحيد الذي يجب ضبطه هو `APP_KEY`، وهو سر سداسي عشري بحجم 32 بايت (64 حرفاً سداسياً عشرياً) يُستخدم لاشتقاق كلمة مرور مستودع restic.

يُنشأ على أي جهاز:

```bash
openssl rand -hex 32
```

تُلصق النتيجة في حقل `APP_KEY` في القالب (Unraid)، أو في متغير البيئة `APP_KEY` في `docker-compose.yml` (مضيف Docker عام).

!!! danger "يجب ألا يضيع APP_KEY"
    فقدان `APP_KEY` يجعل النسخ الاحتياطية المشفّرة غير قابلة للاسترداد. يُحفظ في مكان آمن ومنفصل عن الخادم. بمجرد تشغيل BombVault تُضبط كلمة مرور لتسجيل الدخول وتُنزَّل **حقيبة الاستعادة** تحت **الإعدادات، استعادة** (يُنظر [النسخ خارج الموقع والتعافي](offsite-recovery.md#recovery-kit)). تحوي المفتاح وكل وجهة وأوامر restic.

يركّب القالب أيضاً مقبس Docker والفلاش (`/boot`) وجذر **Host Data** (`/mnt`) تلقائياً. تعيش *مصادر* النسخ الاحتياطي و*وجهاته* كلاهما ضمن Host Data. للمرجع الكامل للمتغيرات وإعداد النسخ خارج الموقع، يُنظر [الإعدادات](configuration.md).

## التشغيل الأول

![نظرة عامة بعد أول نسخة احتياطية: ما يحتاج إلى اهتمام، وحماية كل قسم، والوجهات، والسجل.](assets/screenshots/dashboard.png)

*نظرة عامة بعد أول نسخة احتياطية: ما يحتاج إلى اهتمام، وحماية كل قسم، والوجهات، والسجل.*

1. تُفتح واجهة الويب على `https://<your-unraid-ip>:3443` (شهادة موقّعة ذاتياً بشكل افتراضي). يفتح التثبيت الجديد على **مرحبًا في BombVault**، التي تسرد ما وجده BombVault على الخادم.
2. يُختار **هيا بنا**. تعرض نظرة عامة بعدها بطاقة **الخطوات الأولى** بثلاث خطوات:
    1. **اختيار الأقسام**: تفعيل ما ينسخه BombVault احتياطياً (Containers وVMs وFlash والمجلدات ومجموعات بيانات ZFS والنسخ الذاتي). يفتح **اختيار** قائمة عناصر القسم، حيث يستبعد **إيقاف الجدول مؤقتًا** عنصراً. الأقسام المفعّلة هنا تعمل كل ليلة، ويمكن تغيير ذلك تحت **الإعدادات، الجدول الزمني**.
    2. **إضافة وجهة**: إلى أين تذهب النسخ الاحتياطية. يكفي مجلد محلي للبدء. والأكثر أماناً وجهة ثانية خارج المقر، مثل Storage Box أو Backblaze B2. المستودعات المحلية تكون افتراضياً `/mnt/user/bombvault/{container,vms,flash,config,files,zfs}` وتُنشأ عند أول نسخة احتياطية.
    3. **أول نسخة احتياطية**: بعدها تعمل تلقائياً كل ليلة.
3. تُفتح **النسخ الاحتياطية** لرؤية كل العناصر في قائمة واحدة. يبدأ **نسخ الكل احتياطياً الآن** تشغيلاً على كل الأقسام المفعّلة، وينسخ **نسخ احتياطي الآن** في صفحة عنصر ما ذلك العنصر وحده.

سبق استخدام BombVault؟ تفتح **الاستعادة من نسخة احتياطية** في صفحة الترحيب صفحة الاستعادة، حيث يعيد **معالج الطوارئ** إعدادات خادم مفقود وحاوياته وVMs ومجلداته. يُنظر [النسخ خارج الموقع والتعافي](offsite-recovery.md#emergency).

!!! tip "اختياري: اختيار ترتيب النسخ الاحتياطي"
    إذا كان يجب دائماً نسخ بعض الحاويات احتياطياً قبل غيرها (مثلاً قاعدة بيانات قبل التطبيق الذي يستخدمها)، تُفتح بطاقة **الترتيب** تحت **الإعدادات، الجدول الزمني** وتُسحب الحاويات إلى التسلسل المطلوب. تتبعه عندئذٍ عمليات التشغيل المجدولة والنسخ الاحتياطي الشامل؛ وأي شيء يُترك غير مرتَّب يُنسخ احتياطياً بالأكثر تأخّراً أولاً.

!!! note "فحص تكامل المضيف"
    تستطلع بطاقة **تكامل المضيف** في نظرة عامة كل نقطة تركيب وواجهة سطر أوامر (مقبس Docker، libvirt، restic، qemu-img، rclone) وتبلّغ عن أي أجزاء ناقصة، حتى يمكن التأكد من أن الحاوية موصولة بشكل صحيح قبل الاعتماد عليها. وتنتظر تحت **تخصيص** إلى أن تُضاف.

## التنقل في الواجهة {#navigation}

![الإعدادات كبلاطات، وبجانبها بطاقات البلاطة المختارة. كل تغيير يُكتب فور إجرائه.](assets/screenshots/settings.png)

*الإعدادات كبلاطات، وبجانبها بطاقات البلاطة المختارة. كل تغيير يُكتب فور إجرائه.*

في الشريط الجانبي خمسة عناصر: **نظرة عامة**، و**الحالات الشاذة** (ما دام اكتشاف الحالات الشاذة مفعّلًا)، و**النسخ الاحتياطية**، و**الاستعادة**، وتحت **تسجيل الخروج** الإعدادات. يطفو الإجراء الرئيسي للصفحة في أسفل اليمين، ويضم **المزيد** الإجراءات النادرة. وعلى الهاتف يضم الشريط نظرة عامة والنسخ الاحتياطية والاستعادة والإعدادات، ويضم **المزيد** الباقي.

تستخدم الصفحات والإعدادات عرض النافذة كاملاً. وتحتفظ النافذة بأزرارها في أسفلها، ويكون الزر الذي يتقدم إلى الأمام على اليمين. وعلى الهاتف يُبقي أسفل النافذة الذي فيه أكثر من ثلاثة أزرار على طريق الخروج والإجراء الرئيسي، ويضع الباقي تحت **المزيد**.

- **النسخ الاحتياطية** تسرد كل حاوية وVM ومجموعة مجلدات والفلاش وكل مجموعة بيانات ZFS والنسخ الذاتي كعناصر. تختار البلاطات فوق القائمة نوعاً، ويضيّق **عوامل التصفية** و**ترتيب** و**بحث** النتائج. لكل عنصر صفحة خاصة بثلاثة تبويبات: **النسخ الاحتياطية** و**الإعدادات** و**تحقق**. ويقود زر رجوع على يسار أيقونة العنصر إلى القائمة.
- **الاستعادة** صفحة واحدة لكل شيء: يُختار قسم، ويُبحث عن عنصر، وتُختار نسخة احتياطية. ومن هنا أيضاً يبدأ معالج الطوارئ والمصادر الأخرى.
- **الإعدادات** أربع عشرة بلاطة: عام، المظهر، الجدول الزمني، الوجهات، استعادة، الإشعارات، تحقق، الأمان، المثيلات، الاقتران، التكاملات، التطبيقات، النظام، معلومات. يبحث `/` أو Ctrl+K فيها كلها، وبالأسماء التي كانت للصفحات في الإصدارات السابقة أيضاً. تُسحب البلاطات إلى ترتيب خاص تحت **المظهر**. وحيث يضيّق عمود من البلاطات بجانب الصفحة عليها، كما في نافذة بعرض نحو 1200 بكسل، تصير البلاطات شريطاً فوق الصفحة يُمرَّر جانبياً. ويعرض الهاتف الشريط نفسه.
- **الوجهات** و**المثيلات** بلاطتا إعدادات لهما صفحتان خاصتان. يثبّتهما **العرض أيضًا في الشريط الجانبي** على بلاطتهما في الشريط الجانبي.

لا زر حفظ في أي مكان ولا شيء ينفتح عند النقر: للأمور النادرة بطاقة خاصة أو نافذة، والشروح في فقاعات (i). بعد التحديث تفتح ملاحظات الإصدار بنفسها، وتعلّم نقاط خضراء ما تغيّر. ينقرها المرء فتختفي. ويعدّ **الجديد** في بطاقة الإصدار تحت **الإعدادات، معلومات** ما لم تره بعد، ويفتح ملاحظات الإصدار وقائمة بكل تغيير مع **الانتقال إلى هناك**، كتبويبين في نافذة واحدة.

## البناء من الكود المصدري {#build-from-source}

BombVault ملف تنفيذي ثابت واحد مكتوب بـ Go، يقدّم واجهة JSON API وواجهة React مضمَّنة. تُبنى الواجهة أولًا، ثم يُشغَّل الملف التنفيذي:

```bash
npm --prefix web ci
npm --prefix web run build     # يكتب web/dist الذي يضمّنه الملف التنفيذي
export APP_KEY=$(openssl rand -hex 32)
go test ./...                  # اختبارات الوحدات والتكامل، مع دورة restic حقيقية ذهابًا وإيابًا
golangci-lint run ./...
go run ./cmd/bombvault         # يقدّم https://localhost:3443 بشهادة موقّعة ذاتيًا
```

بناء الواجهة مطلوب أيضًا لـ `go run`. لا يتتبع المستودع تحت `web/dist` إلا ملف علامة فارغًا، لذا من دون `npm --prefix web run build` لا يضمّن الملف التنفيذي شيئًا ويجيب بـ `500 SPA index not found`، وهذا متوقع. لا يمكن اختبار Docker وlibvirt وUnraid في CI، لذا تُفحص نقاط التركيب وrestic واتصال SSH الخاص بالـ VM على مضيف حقيقي باستخدام بطاقة **تكامل المضيف** في نظرة عامة (أو `GET /api/spike`) قبل فتح pull request.
