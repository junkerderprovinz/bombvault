# תחילת העבודה

הדף הזה מוביל אותך מתיבת Unraid חדשה לגיבוי הראשון שלך.

## דרישות {#requirements}

| דרישה | הערות |
|---|---|
| **Unraid 6.12+** | גרסאות מוקדמות יותר לא נבדקו. Unraid הוא היעד העיקרי, אבל BombVault רצה גם על מארח Docker רגיל ועל TrueNAS Scale (ראו [מארח Docker כללי](#generic-docker-host) ו-[TrueNAS SCALE](#truenas)). |
| **מיקום מאגר restic** | נתיב מקומי (מומלץ: המערך או המטמון שלך), SMB,‏ NFS, או כל backend של rclone. |
| **שקע Docker** | מעוגן אוטומטית על ידי התבנית (`/var/run/docker.sock`). |
| **Flash של Unraid** (`/boot`) | מעוגן במלואו אוטומטית על ידי התבנית (`/boot` אל `/host/boot`). מפעיל את גיבוי ה-flash ומאפשר לקונטיינר ששוחזר להופיע שוב כאפליקציית Unraid רגילה וניתנת לעריכה. |
| **מכונות KVM** (בהסכמה) | גיבוי מכונות וירטואליות מדבר עם libvirt דרך SSH, בלי עיגון של libvirt. מגדירים אותו תחת **הגדרות, אינטגרציות, SSH למארח** (ראו [הגדרות](configuration.md)). |
| **מערכי נתונים של ZFS** (בהסכמה) | אותו קישור SSH כמו גיבויי VM, `zfs` במארח, ו-Host Data ממופה כ-`/mnt` עם מצב גישה Read/Write - Slave, ברירת המחדל בתבנית. ראו [מערכי נתונים של ZFS](zfs-datasets.md). |
| **אפליקציית Android** (אופציונלית) | Android 10 ומעלה, מצומדת לשרתים בגרסה 9.7.0 ומעלה. ראו [אפליקציית Android](android.md). |

## התקנה ב-Unraid {#install-on-unraid}

הדרך הקלה ביותר היא **Community Applications**.

1. פותחים את הלשונית **Apps** ב-Unraid.
2. מחפשים **BombVault**.
3. לוחצים **Install**, קובעים את המשתנים הנדרשים (להלן) ומחילים.

!!! tip "התקנת תבנית ידנית"
    אם מעדיפים להוסיף את התבנית ביד:

    1. עוברים אל **Docker, Add Container, Template repositories** ומוסיפים:
       ```
       https://github.com/junkerderprovinz/unraid-apps
       ```
    2. מחפשים **BombVault** בתבניות.
    3. קובעים את המשתנים הנדרשים ולוחצים **Apply**.

## מארח Docker כללי {#generic-docker-host}

לא ב-Unraid? BombVault רצה גם כקונטיינר רגיל על כל מארח Docker. ל-TrueNAS SCALE יש צעדים משלו תחת [TrueNAS SCALE](#truenas).

1. מורידים את [`deploy/docker-compose.generic.yml`](https://github.com/junkerderprovinz/bombvault/blob/main/deploy/docker-compose.generic.yml) המוכן לעריכה מהמאגר.
2. קובעים `APP_KEY` (ראו להלן) ומכוונים את נפח Host Data לשורש הנתונים האמיתי שלך. ההערות בקובץ עוברות על שניהם.
3. `docker compose up -d`, ואז פותחים `https://<host-ip>:3443/`.

מה שונה מ-Unraid:

- **אין תחום Flash.** אין USB אתחול לתפוס או לשחזר, ולכן לתחום Flash אין מה לעשות כאן. במקום זה, כש-Host Data מגיע ל-`/etc` של המארח, **הוספה** בדף הגיבויים מציעה **תצורת המערכת** כהצעת תיקייה: ערכת תיקיות `/etc` להתחלה שבודקים וערכים לפני שמירה.
- **אין התראות מקוריות של Unraid.** ערוצי ההתראות של BombVault עצמה (webhook, התראות כשל מחוץ לאתר וכו') עובדים כרגיל. רק הדחיפה הייחודית ל-Unraid למערכת ההתראות המקורית שלו מדולגת, כי אין מערכת כזו לדחוף אליה.
- **גיבוי VM בהסכמה וצריך מארח libvirtd נפרד שאפשר להגיע אליו דרך SSH.** ראו את הבלוק המוער בקובץ ה-compose. אין מנהל VM מובנה במארח Docker כללי עצמו.
- **אין וידג'ט ללוח מחוונים.** BombVault Widget הוא תוסף של Unraid, ולכן גם הצעד הזה מדולג.
- **מציאת הנתונים של קונטיינר.** בלי מוסכמת `appdata` של Unraid, תיקיית הנתונים של קונטיינר נמצאת מהמקטעים ב-`DATA_ROOT_SEGMENTS`, מ-volumes בעלי שם של Docker, מתיקיית העבודה של פרויקט Compose ומהתווית `bombvault.data` (ראו [זיהוי מקורות הגיבוי](configuration.md#backup-source-detection)). volumes בעלי שם והפריסה המוגדרת מראש של `/etc` מגיעים רק לנתיבים בתוך עיגון Host Data, ולכן מכוונים את Host Data לאב קדמון משותף שמכסה גם את שורש הנתונים של Docker.
- **`PLATFORM`.** קובעים אותו ל-`generic` או ל-`truenas`. אם הוא לא מוגדר, BombVault מזהה את Unraid לפי הסימון שלה בעיגון ה-flash ומתייחסת לכל השאר כגנרי, והצעדים של Unraid בלבד מדולגים במקום להיות מנוסים ולהיכשל.

### TrueNAS SCALE {#truenas}

BombVault עדיין לא בקטלוג האפליקציות של TrueNAS, ולכן מתקינים אותה כאפליקציה מותאמת: **Apps, Discover Apps**, ואז **Install via YAML** בתפריט לצד **Custom App**. ה-YAML שלהלן קובע את אותם דברים כמו הערך בקטלוג בתיקיית `truenas-apps` של המאגר. מחליפים את `tank` במאגר שלך וממלאים את `APP_KEY` כפי שהסעיף הבא מתאר.

```yaml
services:
  bombvault:
    image: junkerderprovinz/bombvault:latest
    hostname: bombvault
    restart: unless-stopped
    cap_drop: [ALL]
    cap_add: [CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETPCAP, SETUID, SYS_CHROOT]
    environment:
      APP_KEY: ""
      PLATFORM: truenas
      HOST_SOURCE_ROOT: /mnt/tank
      HOST_MOUNT_ROOT: /mnt/tank
      # For VM backups:
      # LIBVIRT_URI: qemu+ssh://root@<truenas-ip>/system?socket=/run/truenas_libvirt/libvirt-sock
    volumes:
      - /mnt/tank/apps/bombvault:/config
      - /var/run/docker.sock:/var/run/docker.sock
      - type: bind
        source: /mnt/tank
        target: /mnt/tank
        bind:
          propagation: rslave
    ports:
      - "30528:3443"
```

ואז פותחים `https://<truenas-ip>:30528/`. מה שמפורט תחת [מה שונה מ-Unraid](#generic-docker-host) חל גם כאן, וב-TrueNAS:

- **יכולות.** BombVault צריכה את שבע שלמעלה. גיבויי VM נכשלים בלי `SETPCAP`, ובלי `SYS_CHROOT` כל קונטיינר נעצר לאורך כל הגיבוי שלו במקום להיקרא מתצלום.
- **Host Data** הוא נתיב מארח על מערך נתונים, כאן `/mnt/tank`, מעוגן באותו נתיב בתוך האפליקציה. לכן `HOST_SOURCE_ROOT` ו-`HOST_MOUNT_ROOT` שניהם מציינים אותו. `rslave` מעביר הלאה את העיגונים שהמארח עושה מאוחר יותר, מה שגיבויי מערכי נתונים של ZFS צריכים.
- **נתונים ב-ixVolume אינם מגובים.** אפליקציה שהאחסון שלה הוא ixVolume שומרת את הנתונים שלה תחת `/mnt/.ix-apps`, מחוץ ל-Host Data. BombVault שומרת רק את ההגדרה של האפליקציה, והריצה מציינת את התיקיות שהשאירה בחוץ. לכל אפליקציה שרוצים לגבות את הנתונים שלה בוחרים אחסון **Host Path** על מערך נתונים מתחת ל-Host Data.
- **גיבויי VM ומערכי נתונים של ZFS** מגיעים ל-TrueNAS דרך SSH כ-root. מפעילים את שירות ה-SSH תחת **System, Services**, ומוסיפים את המפתח הציבורי מ**הגדרות, אינטגרציות, SSH למארח** למשתמש root תחת **Credentials, Users**. גיבויי VM צריכים גם את `LIBVIRT_URI` כמו למעלה, כי libvirtd של TrueNAS מאזין על שקע משלו. כש-`LIBVIRT_URI` ו-`LIBVIRT_HOST` שניהם לא מוגדרים, BombVault משתמשת בשער ברירת המחדל של האפליקציה כמארח, כי `host.docker.internal` לא נפתר באפליקציית TrueNAS. [מדריך גיבוי VM](vm-backup-ssh-setup.md#truenas-scale) מכסה את הפרטים, כולל מכונות על zvols.
- **רפליקת ZFS משתמשת במפתח אחר.** רפליקה בשרת ZFS שני נכנסת עם המפתח שחלון הרפליקה מציג, לא עם מפתח ה-Host SSH. מוסיפים אותו בשרת המקבל.
- **אפליקציה שנמחקה חוזרת בשני שלבים.** מתקינים אותה מחדש ב-TrueNAS באותו שם קודם, מה שיוצר את הרשת שלה שוב, ואז משחזרים את הנתונים שלה ב-BombVault. עד אז בדיקת השחזור מדווחת על הרשת החסרה, והשחזור מסרב לפני שהוא משנה משהו.
- **לצד המקור** יוצר קונטיינר Docker רגיל. הוא רץ, אבל מסך האפליקציות של TrueNAS לא מציג אותו.
- **גיבויי SQL של מסד הנתונים** עובדים על עיגוני מערכי נתונים. ייבוא לתיקיית נתונים שהיא מערך נתונים בפני עצמו מעביר את התוכן הישן לתיקייה לצדה, ולכן למערך הנתונים שמעליה צריך מקום בשבילו.

### ZimaOS,‏ CasaOS ומארחים אחרים {#other-hosts}

- **ZimaOS ו-CasaOS:** מוסיפים את [החנות הקהילתית](https://github.com/junkerderprovinz/zimaos-apps#install) ומתקינים ממנה את BombVault. היא רצה שם כ-`PLATFORM=generic` עם Host Data על `/DATA`. ZimaOS שומר נתוני אפליקציות ב-`/DATA/AppData/<app>`, ש-BombVault מוצאת בעצמה, כי `DATA_ROOT_SEGMENTS` מתאים ל-`appdata` בכל רישיות.
- **MOS:** מתקינים את BombVault מ-[MOS Hub](https://mos-official.net/apps.html?search=BombVault). היא רצה שם כ-`PLATFORM=generic` עם Host Data על `/mnt/cache`.
- **Synology:** ב-Container Manager יוצרים פרויקט מקובץ ה-compose (DSM 7.2 ומעלה).
- **Proxmox:** מריצים אותה במכונה וירטואלית או בקונטיינר LXC שיש בו Docker.

בלי הערות, קובץ ה-compose הכללי קצר. מחליפים את `./data` בתיקיית המארח שמחזיקה את הנתונים של הקונטיינרים שלך, קובעים את `HOST_SOURCE_ROOT` לאותו נתיב וממלאים את `APP_KEY`:

```yaml
services:
  bombvault:
    image: junkerderprovinz/bombvault:latest
    restart: unless-stopped
    hostname: bombvault
    container_name: bombvault
    volumes:
      - ./config:/config
      - /var/run/docker.sock:/var/run/docker.sock
      - ./data:/host/user
    environment:
      APP_KEY: ""
      PLATFORM: generic
      HOST_SOURCE_ROOT: /host/user
    ports:
      - "3443:3443"
```

כדי לגבות גם volumes בעלי שם של Docker, מעגנים תיקייה שמחזיקה גם את הנתונים שלך וגם את שורש הנתונים של Docker (`docker info -f '{{.DockerRootDir}}'`, בדרך כלל `/var/lib/docker`), כמו שהתבנית של Unraid מעגנת את כל `/mnt`.

## ההגדרה היחידה הנדרשת {#the-one-required-setting}

המשתנה היחיד שחייבים לקבוע הוא `APP_KEY`, סוד הקסדצימלי של 32 בייטים (64 תווים הקסדצימליים) שמשמש לגזירת סיסמת מאגר ה-restic.

יוצרים אחד בכל מחשב:

```bash
openssl rand -hex 32
```

מדביקים את התוצאה בשדה `APP_KEY` של התבנית (Unraid), או במשתנה הסביבה `APP_KEY` ב-`docker-compose.yml` (מארח Docker כללי).

!!! danger "אל תאבדו את ה-APP_KEY"
    איבוד `APP_KEY` הופך גיבויים מוצפנים לבלתי ניתנים לשחזור. שומרים אותו במקום בטוח ונפרד מהשרת. ברגע ש-BombVault רצה, קובעים סיסמת התחברות ומורידים את **ערכת השחזור** תחת **הגדרות, שחזור** (ראו [מחוץ לאתר והתאוששות](offsite-recovery.md#recovery-kit)). היא מחזיקה את המפתח, כל יעד ואת פקודות restic.

התבנית גם מעגנת בשבילך את שקע Docker, את ה-flash (`/boot`) ואת שורש **Host Data** (`/mnt`). *מקורות* ו*יעדים* של גיבוי נמצאים שניהם תחת Host Data. למדריך המלא של המשתנים ולהגדרת מחוץ לאתר, ראו [הגדרות](configuration.md).

## הפעלה ראשונה {#first-run}

![דף הברוכים הבאים של התקנה חדשה, עם מה ש-BombVault מצאה בשרת.](assets/screenshots/getting-started/welcome-dark.png#only-dark)
![דף הברוכים הבאים של התקנה חדשה, עם מה ש-BombVault מצאה בשרת.](assets/screenshots/getting-started/welcome-light.png#only-light)

1. פותחים את ממשק הרשת בכתובת `https://<your-unraid-ip>:3443` (תעודה חתומה בעצמה מהקופסה). התקנה חדשה נפתחת ב**ברוכים הבאים ל-BombVault**, שמפרט מה ש-BombVault מצאה בשרת.
2. בוחרים **בואו נתחיל**. הסקירה מציגה אז את הכרטיס **צעדים ראשונים** עם שלושה צעדים:
    1. **בחירת תחומים**: מפעילים מה ש-BombVault מגבה (קונטיינרים, VMs, Flash, תיקיות, מערכי נתונים של ZFS, גיבוי עצמי). **בחירה** פותחת את הרשימה של הפריטים בתחום, שבה **השהיית התזמון** משאירה אחד בחוץ. התחומים שמפעילים כאן רצים כל לילה, ושמשנים תחת **הגדרות, לוח זמנים**.
    2. **הוספת יעד**: מקום שני לגיבויים. לכל תחום כבר יש תיקייה בשרת הזה, `/mnt/user/bombvault/{container,vms,flash,config,files,zfs}`, שנוצרת בגיבוי הראשון. הבטוח ביותר הוא יעד שני מחוץ למקום, כמו Storage Box או Backblaze B2.
    3. **גיבוי ראשון**: אחרי זה הוא רץ מעצמו כל לילה. הכרטיס נשאר עד שהגיבוי הראשון הסתיים.
3. פותחים **גיבויים** כדי לראות כל פריט ברשימה אחת. **גיבוי הכול עכשיו** מתחיל ריצה על כל התחומים המופעלים, ו**גיבוי עכשיו** בדף של פריט מגבה רק אותו.

![הכרטיס צעדים ראשונים עם שלושת הצעדים שלו, השני פתוח.](assets/screenshots/getting-started/first-steps-dark.png#only-dark)
![הכרטיס צעדים ראשונים עם שלושת הצעדים שלו, השני פתוח.](assets/screenshots/getting-started/first-steps-light.png#only-light)

כבר השתמשת ב-BombVault? **שחזור מגיבוי** בדף הברוכים הבאים פותח את דף השחזור, שבו **אשף החירום** מחזיר את ההגדרות, הקונטיינרים, המכונות והתיקיות של שרת שאבד. ראו [מחוץ לאתר והתאוששות](offsite-recovery.md#emergency).

!!! tip "אופציונלי: בחירת סדר גיבוי"
    אם חלק מהקונטיינרים צריכים תמיד להיות מגובים לפני אחרים (למשל מסד נתונים לפני האפליקציה שמשתמשת בו), פותחים את הכרטיס **סדר** תחת **הגדרות, לוח זמנים** וגוררים אותם לרצף הרצוי. ריצות מתוזמנות והגיבוי המלא עוקבים אחריו אז. כל מה שלא סודר מגובה לפי מי שהכי מאחר.

## דוגמה: גיבוי הקונטיינר הראשון שלך, מקצה לקצה {#example-first-backup}

זה עובר על תיבת Unraid חדשה עם כמה קונטיינרים, ביניהם `plex`, עד שהגיבוי הראשון הסתיים ואתה יודע איפה למצוא אותו. זה לוקח כעשר דקות ועוד זמן הגיבוי הראשון.

1. **התקנה.** בלשונית **Apps** של Unraid מחפשים **BombVault** ולוחצים **Install**.
2. **קביעת המפתח.** במחשב מריצים `openssl rand -hex 32` ומדביקים את 64 התווים בשדה `APP_KEY` של התבנית. שומרים עותק במנהל הסיסמאות שלך עכשיו, לפני כל דבר אחר. לוחצים **Apply**.
3. **פתיחה.** עוברים אל `https://<your-unraid-ip>:3443` ומקבלים את התעודה החתומה בעצמה. **ברוכים הבאים ל-BombVault** מפרט מה שהיא מצאה, כמו 12 קונטיינרים, 2 מכונות וירטואליות וכונן ה-flash.
4. **בואו נתחיל.** הסקירה נפתחת עם הכרטיס **צעדים ראשונים**.
5. **בחירת תחומים.** **קונטיינרים** מופעל מההתחלה. מפעילים מה עוד שרוצים, כמו **Flash**. **בחירה** פותחת את רשימת הקונטיינרים שנמצאו, ו**השהיית התזמון** משאירה אחד בחוץ, למשל קונטיינר בדיקה שלא אכפת לך ממנו. תחומים מופעלים רצים כל לילה בגיבוי המלא.
6. **הוספת יעד.** לכל תחום כבר יש תיקייה משלו בשרת הזה, מתחת ל-`/mnt/user/bombvault`, ולכן לגיבוי הראשון יש לאן ללכת. הצעד הזה מוסיף מקום שני, והבטוח ביותר הוא מחוץ למקום. אפשר לעשות אותו עכשיו עם [דוגמת ה-S3](offsite-recovery.md#example-s3), או לחזור אליו אחרי שהגיבוי הראשון הסתיים. הכרטיס נשאר עד אז.
7. **גיבוי ראשון.** פותחים **גיבויים** ולוחצים **גיבוי הכול עכשיו**, או מחכים ללילה. הטבעת בראש הסטטוס הופכת לטבעת התקדמות וסופרת את הפריטים, כמו **גיבוי מתבצע עכשיו: 3 מתוך 12**. כל קונטיינר נעצר בזמן שהנתונים שלו נקראים ומופעל שוב מיד אחר כך. קונטיינר שהנתונים שלו על ZFS למטה רק כמה שניות של תצלום. הגיבוי הראשון קורא הכול, ולכן הוא לוקח הכי הרבה זמן. הבאים שומרים רק מה ששונה.
8. **בדיקה.** כשהטבעת אומרת **הכול גובה**, פותחים **היסטוריה** בסקירה: לכל קונטיינר יש שורה ירוקה ב**ריצות**. פותחים **גיבויים**, לוחצים על `plex` ומסתכלים בלשונית **גיבויים** שלו: התצלום הראשון שם, עם **מקומי** כמקום שמחזיק אותו. כמה דקות אחר כך לשונית **אימות** שלו מציגה את בדיקת השחזור, ששחזרה מדגם מהגיבוי וקראה אותו בחזרה.
9. **הגנה על המפתח.** פותחים **הגדרות, אבטחה** וקובעים סיסמת התחברות. ואז פותחים **הגדרות, שחזור** ולוחצים **הורדת ערכת שחזור** ב**לשעת חירום**. שומרים את הקובץ מחוץ לשרת, לצד עותק ה-`APP_KEY` משלב 2. התזכורת **שמירת ערכת השחזור** בסקירה נעלמת ברגע שלוחצים **שמרתי אותה בבטחה**.

מעכשיו הקונטיינרים מגובים כל לילה. צעדים טובים הבאים, בסדר הזה: [יעד מחוץ לאתר](offsite-recovery.md#example-s3), כדי ששרת מת לא ייקח איתו את הגיבויים, אחר כך [התראות](notifications.md), כדי שכשל יגיע אליך, ואז מבט ב[לוחות זמנים](schedules.md) אם 03:00 לא מתאים לך.

![ראש הסטטוס בזמן שהגיבוי הראשון רץ, עם טבעת ההתקדמות והתחנות שלה.](assets/screenshots/getting-started/status-ring-light.png#only-light)

!!! note "בדיקת שילוב מארח"
    הכרטיס **שילוב מארח** בסקירה בודק כל עיגון וכל CLI (שקע Docker,‏ libvirt,‏ restic,‏ qemu-img,‏ rclone) ומדווח על חלקים חסרים, כך שאפשר לוודא שהקונטיינר מחובר נכון לפני שסומכים עליו. הוא מחכה תחת **התאמה אישית** עד שמוסיפים אותו.

## למצוא את הדרך {#navigation}

![ההגדרות כאריחים, עם הכרטיסים של האריח הנבחר לצדם. כל שינוי נכתב כשעושים אותו.](assets/screenshots/getting-started/settings-rail-dark.png#only-dark)
![ההגדרות כאריחים, עם הכרטיסים של האריח הנבחר לצדם. כל שינוי נכתב כשעושים אותו.](assets/screenshots/getting-started/settings-rail-light.png#only-light)

בסרגל הצד יש חמישה ערכים: **סקירה**, **חריגות** (כל עוד זיהוי החריגות פועל), **גיבויים**, **שחזור** ו, מתחת ל**התנתק**, **הגדרות**. הפעולה הראשית של דף צפה בפינה הימנית התחתונה, ו**עוד** מחזיק את הנדירות. בטלפון הסרגל מחזיק סקירה, גיבויים, שחזור והגדרות, ו**עוד** מחזיק את השאר.

דפים והגדרות משתמשים בכל רוחב החלון. חלון שומר את הכפתורים שלו בתחתית, כשזה שמתקדם נמצא בצד ימין. בטלפון, תחתית עם יותר משלושה כפתורים שומרת את דרך היציאה ואת הפעולה הראשית ושמה את האחרים תחת **עוד**.

![בטלפון, הסרגל בתחתית עם עוד פתוח.](assets/screenshots/getting-started/phone-more-dark.png#only-dark)
![בטלפון, הסרגל בתחתית עם עוד פתוח.](assets/screenshots/getting-started/phone-more-light.png#only-light)

- **סקירה** מראה אם הכול מגובה ומה דורש אותך. ראו [סקירה](overview.md).
- **גיבויים** מפרט כל קונטיינר, מכונה וירטואלית, ערכת תיקיות, את כונן ה-flash, כל מערך נתונים של ZFS ואת הגיבוי העצמי כפריטים. אריחים מעל הרשימה בוחרים סוג, ו**מסננים**, **מיון** ו**חיפוש** מצמצמים אותה. לכל פריט יש דף משלו עם שלוש לשוניות: **גיבויים**, **הגדרות** ו**אימות**. כפתור חזרה משמאל לסמל הפריט מוביל לרשימה. ראו [גיבויים ופריטים](backups.md).
- **שחזור** הוא דף אחד לכל דבר: בוחרים תחום, מחפשים פריט ובוחרים גיבוי. גם אשף החירום והמקורות האחרים מתחילים כאן. ראו [שחזור](restore.md).
- **הגדרות** הן ארבעה עשר אריחים: כללי, מראה, לוח זמנים, יעדים, שחזור, התראות, אימות, אבטחה, מופעים, צימוד, אינטגרציות, אפליקציות, מערכת ומידע. ראו [הגדרות](settings.md). מקישים `/` או Ctrl+K כדי לחפש בכולן, גם לפי השמות שהיו לדפים בגרסאות קודמות. גוררים את האריחים לסדר שלך תחת **מראה**. במקום שעמודת אריחים לצד הדף הייתה מכווצת אותו, כמו בחלון ברוחב של כ-1200 פיקסלים, האריחים הופכים לרצועה מעל הדף שנגללת הצידה. טלפון מציג את אותה רצועה.
- **יעדים** ו**מופעים** הם אריחי הגדרות עם דפים משלהם. **הצגה גם בסרגל הצד** באריח שלהם מצמידה אותם לסרגל הצד.

לשום דבר אין כפתור שמירה ושום דבר לא נפתח בקיפול: לדברים נדירים יש כרטיס משלהם או חלון, והסברים נמצאים בבועות ה-(i). אחרי עדכון נפתח חלון מעצמו עם כרטיס לכל גרסה מאז הגרסה האחרונה שלך, ונקודות ירוקות מסמנות מה השתנה. לחיצה מסתירה נקודה. **חדש** בכרטיס הגרסה תחת **הגדרות, מידע** סופר מה עוד לא ראית ופותח את החלון הזה שוב, עם הערות כל גרסה והשינויים שלה עם **מעבר לשם**.

## בנייה ממקור {#build-from-source}

BombVault היא קובץ הרצה סטטי יחיד ב-Go שמגיש API של JSON וממשק React מוטמע. בונים קודם את הממשק, ואז מריצים את הקובץ:

```bash
npm --prefix web ci
npm --prefix web run build     # writes web/dist, which the binary embeds
export APP_KEY=$(openssl rand -hex 32)
go test ./...                  # unit and integration tests, with a real restic round trip
golangci-lint run ./...
go run ./cmd/bombvault         # serves https://localhost:3443 with a self-signed certificate
```

בניית הממשק נחוצה גם ל-`go run`. המאגר עוקב רק אחרי סימון ריק תחת `web/dist`, ולכן בלי `npm --prefix web run build` הקובץ לא מטמיע כלום ועונה `500 SPA index not found`, מה שמצופה. אי אפשר לבדוק Docker, libvirt ו-Unraid ב-CI, ולכן בודקים עיגונים, restic וקישור ה-SSH למכונות על מארח אמיתי עם הכרטיס **שילוב מארח** בסקירה (או `GET /api/spike`) לפני שפותחים pull request.
