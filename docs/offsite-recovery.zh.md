# 异地与恢复

!!! note "重建后异地副本会等待"
    当应急向导或**发现备份**在没有旧设置的情况下重建条目时，这些分区的异地副本会暂停，直到它们的默认值得到确认。参见[重建之后](#after-a-rebuild)。

本地备份保护你免受容器丢失或糟糕更新的影响。异地副本和经过测试的恢复工具包保护你免受整台机器损毁、勒索软件或火灾的影响。本页涵盖目标和异地副本、让副本防篡改、证明你能还原、配对多台服务器，以及在 BombVault 本身消失时找回一切。

## 异地副本 {#off-site-copies}

保留快速的本地备份，再添加一个或多个场外目标。BombVault 用 `restic copy` 尽力而为地把新快照复制到那里，因此异地的小故障绝不会让本地备份失败。这种形式下本地仓库仍是主仓库，异地仓库是副本，但分区的主仓库根本不必是本地的；若想直接备份到 S3、rest-server 之类而不是复制过去，参见下文的[远程主仓库](#remote-primary-repositories)。

- **每个分区多个目标。** 每个分区（容器、虚拟机、闪存、自我备份、文件夹和 ZFS 数据集）可以同时复制到多个异地目标，所以你可以并行保留比如朋友机器上的一个 rest-server 和一个 S3 存储桶。目标页面上的**按分区划分的目标**卡片可以打开或关闭从分区到目标的每一行。
- **复制何时运行。** 目标的**复制**卡片设定**复制时机**：**每次备份之后**，或者按它自己的计划，在固定时间收集快照并复制。在**设置、计划、按领域的异地副本**下，**例外**可以给某个分区单独的复制计划。**设置、目标**下分区的**异地副本**卡片中的**立即复制**会按需启动一次复制。
- **保留**按目标在**保留多久**下设置，所以你可以把异地副本保留得更久作为归档。分区异地字段中的副本遵循**设置、目标**下**异地保留**卡片的设置；保持全为零则永不自动裁剪异地快照。
- **带宽限制**（**设置、目标**下的**异地带宽**，或目标的**复制**卡片）限制 restic 的上传/下载速率，让复制不会占满你的 WAN。
- 复制进行时，概览的状态头会显示**正在异地复制**。它是活动指示，而不是百分比进度条，因为 `restic copy` 不提供机器可读的进度。

!!! note "从任意位置还原"
    每个条目在其**备份**标签页上，把它的备份列成一条贯穿备份所在的所有位置的时间线。复制到 B2 的备份只出现一次，并标出保存它的每个位置。还原会取它能访问到的第一个位置，从条目写入的仓库开始，你也可以为每个快照选择另一个位置。异地目标只有在你点击**检查**时才会读取，因为列出云存储需要一些时间。在某一处删除时会先检查其他位置，并说明这是否是最后一份副本。

## 目标 {#destinations}

目标是备份存放的地方：本地文件夹、共享、你自己的服务器或云服务。它只需设置一次，之后为每个分区服务。从它的设置磁贴打开**目标**，或在那里打开**同时显示在侧边栏**来固定它。

**添加目标**会打开一个分四步的窗口：

1. **服务商。** 每个服务都带着它的徽标列出，上方有搜索，并分组：带 S3 存储桶的存储服务（Backblaze B2、Wasabi、Cloudflare R2、Hetzner Object Storage、Amazon S3 等）、你自己的 S3 服务器（Garage、SeaweedFS、RustFS、Silo、Ceph、JuiceFS、Versity S3 Gateway）、你自己的服务器和共享（rest-server、Hetzner Storage Box、SFTP、SMB、WebDAV、已挂载的路径）、云存储（OneDrive、Google Drive、Dropbox、pCloud、Nextcloud 以及 rclone 支持的其余服务），以及你组里的接收服务器。每一项都会说明它适合备份的程度：云盘在大量请求下会变慢，所以首次备份和清理在那里耗时更长。
2. **登录。** 字段取决于服务：S3 的访问密钥，WebDAV 和 SMB 的用户和密码，两步登录挡住普通密码时使用的应用密码，SFTP 和 Storage Box 用的 BombVault 公共 SSH 密钥，或通过浏览器登录的服务所用的令牌。对这些服务，窗口会显示一条 `rclone authorize` 命令，供你在有浏览器的电脑上运行；它打印出的令牌填入该字段。**测试**会在保存任何内容之前检查登录。窗口随后列出目标上的文件夹，**新建文件夹**用于创建一个，服务报告了可用空间的地方也会显示。空文件夹最安全；BombVault 会在其中为每个分区放一个文件夹。
3. **保护。** 窗口会直白地说明该服务能做什么。append-only 模式的 rest-server 会拒绝删除，篡改测试会检查这一点。S3 存储桶可以通过版本控制和对象锁保留旧版本，这是 BombVault 暂时无法检查的。云盘根本无法拒绝删除：谁进入了服务器，也就进入了那份副本。只有在远端确实拒绝删除时才打开**防删除保护（append-only）**；之后 BombVault 绝不会在那里清理。**应对紧急情况**会说明恢复工具包为该目标保存了什么。
4. **针对哪些分区。** 选择备份到这里的分区。首次复制会带上全部历史。选择了自己目标的条目不会自动获得新目标，窗口会点出它们。

S3 服务通过 restic 自己的 S3 后端运行，这正是能应用存储类别和对象锁的原因。其他所有服务都通过 BombVault 自带的 rclone 运行，它的远程随后出现在**设置、目标**下的**异地 (rclone)** 卡片中。设置导出会带上这些目标；包含凭据时，也会带上它们的登录信息。

每个目标都有自己的页面：

- **连接**，包括名称、开关**可用**（关闭意味着 BombVault 不再写入这里，备份到这里的条目会以明确的消息失败，而不是落到别处）、文件夹、压缩、存储类别和**场所之外**。**更改连接**会测试并保存新的地址或登录。
- **凭据**：共享的凭据集或它自己的凭据集。
- **防删除保护**，带有**立即测试防删除保护**以及谁来清理这份副本。
- **复制**：何时复制，以及上传和下载限制。
- **保留多久**：**短**、**均衡**、**长**或**自定义值**，并附有一条显示规则保留哪些备份的时间线。**减少保留前先询问**会在更短的规则要删除仅有一份副本在这里的备份之前先询问。
- **按分区划分的规则**：某个分区在这个目标上的专属仓库、保留或压缩。**更改规则**会打开它们，**恢复为目标的设置**让分区恢复原样。
- **已在此目标下**：手动输入的地址位于该目标某个文件夹内的分区。接管其中一个会让仓库留在原处；登录、存储类别和防删除保护随后来自目标。BombVault 会先检查目标的登录能打开该仓库，并拒绝把 append-only 仓库放到非 append-only 的目标之下。
- 一个容器图，显示目标有多满，标出写满的位置，以及按最近几周的增速还剩多少周。不报告大小的目标显示**大小未知**。

你组里另一个实例运行的接收服务器会作为服务商出现在**来自你的组**下；参见[接收服务器](#receiving-server)。

### 移动与移除 {#move-remove}

- **移动**会把一个分区的副本连同全部历史带到另一个目标。一切都留在旧位置；BombVault 不会在那里删除任何东西。移动在后台运行，可能很久：本地磁盘之间每 100 GB 约 9 分钟，慢速链路上则要数小时。概览在它运行时会显示出来。
- **移除目标**有两种方式。**移除目标，保留备份**停止向那里写入，并让备份留在原处；之后你可以在**恢复、从旧的备份文件夹**下读取它们。**移除目标并删除其中的备份**会先读取那里存的内容并列出：哪些备份会消失，其中哪些在别处没有，以及哪些仓库会保留，原因是删除保护拒绝、条目仍直接备份到它们、另一个目标或分区在那里保存着自己的副本，或无法读取。会失去唯一备份的条目单独列出，除非你勾选**同时删除这些**，否则会被保留。你通过输入目标的名称来确认，删除在后台运行。
- 删除某个目标上的备份需要登录密码和在实例本机登录。没有密码时仍可移除该目标，只是无法从这里删除它的备份。

## 每个条目的存放位置 {#placement}

条目设置标签页上的**计划和目标**卡片有一排按钮：**本地**，以及分区的每个异地目标各一个。点亮的按钮会接收条目的备份。

- **本地**点亮时，条目写入**存放于**下显示的仓库，并复制到其他每个点亮的目标。把某个目标调暗，它就不再从这个条目得到任何新内容。只有本地则不复制到任何地方，适合已经有第二份副本的数据，比如存放在 NAS 上的共享。
- **本地**熄灭时，条目直接写入第一个点亮目标的直连仓库，并从那里复制到其他点亮的目标。第一次时，一个对话框会创建这个直连仓库。
- 总有一个按钮保持点亮，因为备份需要一个去处。要把条目排除在备份之外，请使用**不备份**。

位置从条目的首次备份起就固定，因为 BombVault 绝不会在仓库之间移动备份；设置标签页上的**仓库**卡片会写明它。副本可以随时更改。不再接收某个条目的目标会保留已有的副本，并在该分区下一次异地运行时按自己的保留策略裁剪。无法从 append-only 目标中删除。

这一排按钮下方，卡片会说明条目去了哪里以及实际有什么：有多少个地点保存着它、每个目标上次看到是什么时候，以及 3-2-1 是否满足。一个地点指有原始数据的服务器、每个异地目标，以及每个标有**场所之外**的仓库。BombVault 检查副本和地点；它不检查 3-2-1 中的“两种介质”。

### 每个分区的默认值 {#placement-defaults}

目标页面上的**按分区划分的目标**卡片是每个分区的默认值。图中每条线都是一份副本，点击线或圆点即可开启或关闭；虚线表示已关闭。**图 / 开关**用成排按钮显示同样的内容。这些副本会立即作用于每个没有自己选择的条目，以及 Compose 堆栈的项目文件夹。目标在新条目首次备份时生效；更改它不会移动任何备份。保存之前，BombVault 会点出每个增加或失去条目的目标，以及这意味着多少个快照。

备份到其所属分区之外的条目列在**自行选择**卡片中，每个都带有**遵循默认**。之后新的备份会去往该分区的目标，之前的则留在原处。

新的异地目标会接收每个没有设为本地的条目。添加它的窗口会说明有多少条目，以及在已知时有多少历史。

### 直接仓库

为某个条目关闭本地，使没有直连仓库的目标成为它的归宿，会打开一个对话框，旁边有建议的位置，例如 `s3:https://s3.eu-central-003.backblazeb2.com/bucket/containers-direct`，以及一次不创建任何东西的连接测试。**创建并使用**会创建该仓库并把条目指向它。直连仓库采用目标的密钥、存储类别、限制、append-only 设置和保留，并随它们变化；仓库卡片以只读方式显示它。当目标的新密钥无法打开它时，直连仓库保留它现有的密钥，保存时会这样说明。直连仓库上的条目从那里复制到其他点亮的目标，绝不会复制到该仓库所属的目标。它的快照带有标签 `bv:direct`，其他每一轮保留都会保留它们，所以与其目标失去关联的直连仓库绝不会按本地规则老化。B2 通过它的 S3 端点访问，密钥 ID 和应用密钥作为 S3 凭据输入；仅限于目标自己文件夹的密钥够不到旁边的文件夹，所以请把密钥限制在上一级文件夹。

### 场外

目标或命名仓库可以标为**场所之外**。远程的默认带有该标记；对同一栋楼里的 rest-server 请把它关掉。这个标记只影响卡片上对地点和 3-2-1 的计数。它不改变任何副本。

ZFS 副本是场所之外的一份拷贝，但不是带历史的备份。它只保留你设定的快照，旧版本和单个文件仍来自备份。它从一台 ZFS 服务器直接到另一台，通过 SSH 到 ZFS 服务器，或到已配对实例的接收端点。配对组只携带请求。参见[副本](zfs-datasets.md#replica)。

### 重建之后 {#after-a-rebuild}

复制选择存放在 BombVault 自己的设置里。通过**发现备份**或没有还原设置的应急向导重建之后，它们已经不在了，而复制所有内容会把你排除的条目再次送到 B2。因此每个被重建分区的异地副本都会暂停。概览会这样说明，**按分区划分的目标**卡片则提供**确认默认值**，并附上下一次运行会复制什么的预览，以及没有条目的备份中的名称，你可以在那里把它们排除。只有确认才能结束暂停；导入设置文件会带回规则和默认值，但不会结束暂停。

## 远程主仓库 {#remote-primary-repositories}

分区自己的路径不限于本地文件夹：把它直接指向 restic 远程（`s3:...`、`rest:http://host:8000/repo`、`sftp:user@host:/repo`、`rclone:remote:bucket/path`），BombVault 就会直接备份到那里，没有单独的本地副本，也没有复制步骤。这与上面的异地副本是不同的形式：在那里，本地仓库是主仓库，异地仓库是它的尽力而为的归档；在这里，远程仓库**就是**主仓库，除非你同时把这个分区复制到另一个目标，否则它就是唯一的副本。

每个分区（容器、虚拟机、闪存、自我备份、文件夹、ZFS 数据集）的路径在**本地文件夹**目标的页面上设置：在其**连接**卡片中，分区旁的**更改**会打开一个带有**本地 / 远程**开关的窗口：

- **本地** 显示熟悉的文件夹浏览器。
- **远程**把它换成一个普通的 URL 字段，以及异地目标使用的连接设置，只是这次是为这个主仓库配置。从那里你可以得到：
    - **一次连接测试**，在你真正依赖它之前，对着实际路径跑一遍。
    - **带宽限制**（上传/下载），让发往远程主仓库的计划备份不会占满你的 WAN：与异地复制所用的相同的 `--limit-upload`/`--limit-download` restic 参数，应用于备份本身。
    - **append-only 保护**，由异地目标所用的同一个主动篡改测试（对远端发起一次真实的 DELETE 探测）验证。开启后，BombVault 拒绝自己清理该仓库，因为它背后没有单独的本地副本，而且这台机器上的凭据不应能删除备份的唯一副本。
    - **增长预算告警**，取自存储卡片本就在跟踪的那条仓库大小趋势。

这些都不是必需的：手动输入的远程路径如果没有保存任何安全设置，就会不限速、可清理、也没有预算告警地备份。安全设置是为你想要异地副本所得到的保护、又不想为此单独建一个目标的情形准备的。

!!! note "云与 REST 凭据是共用的"
    远程主仓库使用**设置、目标**下共享的云凭据进行认证；主仓库没有单独的凭据存储。

### 无需主机挂载的 SMB 和 WebDAV {#smb-webdav}

**设置、目标**下的**异地 (rclone)** 卡片有一个用于 Windows 或 Samba 共享以及 WebDAV 服务器（Nextcloud、ownCloud、SharePoint 或任何其他服务器）的表单。填写一个简短的名称、主机和共享（SMB）或 URL 和服务器类型（WebDAV）、用户和密码，BombVault 就会替你写出 rclone 的段落。rclone 会在存储之前自己混淆密码；用已有的名称添加会替换该段落，而不是再添加第二个。**添加目标**也提供 SMB 和 WebDAV 作为服务商，字段相同。

表单会给出完成后的位置，例如 `rclone:nas:backups`。把它用作分区的路径或目标，需要的话再加一个子文件夹（`rclone:nas:backups/bombvault`）。共享是路径的第一段，不属于名称的一部分。

这比在 Unraid 上挂载共享更好：restic 不建议把仓库放在挂载的 CIFS 共享上，而这里什么都没有挂载。表单里没有 NFS，因为 restic 和 rclone 都没有 NFS 后端；对于 NFS，请在主机上挂载导出，并当作本地文件夹使用。

## 防删除保护（append-only）

为异地目标打开防删除保护，勒索软件或被入侵的主机就无法删除或重写你的备份。远端（以 `--append-only` 模式运行的 `restic/rest-server`）**强制执行**它。BombVault 只负责**验证**，绝不会仅凭配置声明就显示绿色。本服务器上的文件夹无法拒绝删除，因为控制 BombVault 的人同样控制这个文件夹，所以本地目标不提供这个开关。

获得 append-only 副本最快的方式是一个已配对、带有[接收服务器](#receiving-server)的 BombVault：它会替你以 append-only 模式运行 rest-server。

!!! note "`/locks/` 下删除成功是预期行为"
    append-only 并不意味着什么都不能再删除。restic 必须获取并释放自己的锁，因此 `/locks/` 有意保持可写和可删除。快照以及其背后的数据，也就是勒索软件真正会盯上的东西，无法被删除。如果你自己去探测远端，`/locks/` 下成功的删除是正确行为，而不是防护的漏洞。

!!! warning "append-only 仓库绝不会从这台机器清理"
    append-only 目标绝不会从这里清理旧快照；清理是远端的事。请为它设置**增长预算告警**，以便在仓库大小失控之前收到提醒。

## 篡改测试

BombVault 会定期通过真正对异地仓库尝试一次删除（针对一个不存在的对象）来证明 append-only 保证。目标页面上的**立即测试防删除保护**会按需运行它，**设置、验证、自动检查**下的**检查删除保护**则按计划运行。

- **被拒绝**意味着受保护。
- **被接受**意味着未受保护。
- **不确定**的结果（服务器不可达、认证错误）绝不会翻转已存储的判定。

一次真实的从受保护到未受保护的翻转会触发一条告警。

## DR 演练

BombVault 提供两个层级的证明，证明您的备份确实可还原，而不仅仅是存在。

- **还原验证演练（本地）。** BombVault 定期运行 `restic check --read-data-subset`（有限度，绝不是占满磁盘的完整还原）。频率设在**设置、验证、自动检查**下，同一磁贴上的**检查备份**卡片显示结果。
- **试还原（异地）。** BombVault 把异地仓库中的一个真实目标还原到密封的沙箱中，逐文件、逐字节验证，然后清理。这证明你能从异地恢复，而不只是仓库有响应。

概览上的**保护状态**卡片按分区把这些汇总为四项检查：本服务器上的当前备份、异地副本、那里的删除保护，以及从那里做的试还原。点一下分区会显示详情，卡片只有在事实经过验证时才会变绿。

## 配对实例 {#pairing}

几个 BombVault 作为一个组协同工作：它们显示彼此的保护状态，互相承担角色，也可以保管彼此的密钥。实例用十二个单词加入组。

在第一个实例上打开**设置、配对**，按**生成口令**。三张步骤卡片展示过程。十二个单词会出现在一个带有**复制**按钮的窗口中。在其他每个实例上打开同一处，按**输入口令**，粘贴或输入它们，或按该窗口中的**粘贴**。不在列表中的单词会在你输入时连同其位置被点名，最后一个单词带有校验和，所以输错或调换的单词会在任何配对发生之前被发现。只在一个实例上生成口令：两个实例都生成就会形成两个独立的组。如果一分钟后没人出现，页面提供两条出路：再次显示这些单词以便在那边输入，或者输入另一个实例的单词，一步加入它的组。没有登录密码也能配对，但请设置一个：没有它，任何能打开网页界面的人都能读到这些单词，并通过组请求会交出组内实例 restic 密码的角色。在设置密码之前，配对卡片会一直这样提醒。有密码时，再次显示口令会要求输入它。**退出组**会让实例再次离开。

知道这些单词的任何人都能加入群组，所以要把它们当作密码对待。

**成员如何找到彼此。** 每个实例在你登录的那一刻从你的浏览器得知自己在网络上的地址，它与实例自己发现的地址一起列在配对页面的**已知地址**下；如果前面有反向代理或不寻常的端口，请在那里更正。在同一网络上，成员通过组播宣告该地址并直接通信；在组播无法穿过容器网络的地方，比如 Docker 的默认网桥，实例会改为用只有组成员才能应答的签名调用在自己的子网中寻找其他成员，所以配对即使没有中继也能在几秒内完成。如果什么都没找到，**找不到吗？**可以手动输入一个地址，用于另一个子网或非标准端口。位于不同网络的实例通过中继，在同一页面选择；它的四种形式各配有一幅图：

- **项目中继**（默认）：`parleyport.halleluja.design`，也是 KnightLoader 使用的中继。无需任何设置。
- **自建中继**：来自 Unraid Community Apps 的 [**ParleyPort**](https://github.com/junkerderprovinz/parleyport) 容器（也在**设置、应用**下），或你已经可以从外部访问、并开启了**作为中继运行**的某个实例。该实例随后在自己的地址上以 `/relay/connect` 应答，位于它已有的反向代理和证书之后，并且只放你的组进来。请在每个要使用它的实例上输入中继的地址。
- **不用中继**：成员会在同一网络中自动找到彼此，别处都不行。

**中继能看到什么。** 成员之间的每次调用都用 AES-256-GCM 封存，密钥由十二个单词派生，并且这个密钥绝不会离开你的实例。中继只知道一个把连接归组的哈希、消息是发给哪个实例的、有多大以及何时经过。局分区网中的直接调用以同样方式封存并且额外签名，所以不依赖实例提供的自签名证书。交出内容的调用（角色答复、restic 密码、接收端登录、密钥托管副本）还会用发送它们的成员的密钥签名，该密钥在第一次见到时被固定；参见[安全模型](configuration.md#security-model)。

**哪些内容经过组传递。** 实例页面上的保护状态、立即检查某个分区的请求、角色请求及其答复、存储提议，以及角色被允许后接收端或拉取端所需的内容：另一个实例的仓库位置和它的 restic 密码。备份数据绝不会；它仍然直接送往 restic 后端。APP_KEY 也不会：restic 密码只能打开那个实例的仓库，别无其他，打不开它存储的机密、会话或取回码。

**配对之前的条目。** 用舰队令牌添加的实例，以及用另一个实例的 APP_KEY 设置的已接收仓库和拉取来源，在更新后仍然保留并标为**重新配对**。它们继续工作：BombVault 在第一次启动时，会把每个存储的 APP_KEY 替换为由它派生的 restic 密码。把两个实例配对，然后编辑该条目并选择它的实例。在此之前，这类条目放在实例页面的**无实例**卡片中。

唯一仍需手动输入 APP_KEY 的地方是[从旧的备份文件夹](#restore-from-another-bombvault-repo)，用于另一个实例已经消失、无法在组中应答的情形。

## 实例与角色 {#roles}

**实例**页面（一个可固定到侧边栏的设置磁贴）把组显示为谁为谁做什么的网络，有一张本实例的卡片，以及每个其他成员、Android 手机和 ZFS 服务器各一张卡片。**配对实例**浮在右下角。哪些部分开启，在**设置、实例、多台服务器**下设置：**实例**、**接收端**和**拉取**。

每张卡片以磁贴形式显示成员的保护状态和它的角色。角色是一个实例为另一个实例做的事：

- **接收端**把这台服务器的异地副本保存在 append-only 模式的 rest-server 中。这台服务器在每次备份后发送，并且无法删除那里的任何东西，即使有人接管了它。
- **拉取端**按自己的计划拉取这台服务器的备份。这台服务器不必为此处于开机状态。
- **ZFS 服务器**接收这台服务器的 ZFS 副本。每个 ZFS 条目在其设置的**副本**下选择它。
- **密钥保管端**保存这台服务器恢复工具包的一份封存副本。参见[密钥保管端](#key-keeper)。

打开一个角色会发出请求，在另一个实例上有人按下**允许**之前什么都不会开始。请求在那个实例的卡片上显示为一个徽章，它的**详情**用**允许**和**拒绝**列出它；已允许的角色可以随时在那里撤销。网络中的虚线表示仍在等待的角色。运行 BombVault 9.x 的实例无法应答请求，所以角色在那里一打开就生效，而来自 9.x 实例的请求会在这里等待**允许**。

卡片上的**详情**会打开其余内容：该成员的已接收仓库和拉取来源、存储提议、监控、**移除**和**忘记密钥**。

## 接收端与拉取端 {#receiver}

![实例详情中的已接收异地副本，以只读方式监控，并在这台硬件上运行完整性检查。](assets/screenshots/receiver.png)

*实例详情中的已接收异地副本，以只读方式监控，并在这台硬件上运行完整性检查。*

在**接收**另一个 BombVault 的 append-only 副本的机器上，已接收的仓库在接收硬件上提供独立的只读监控，这样远端的静默故障就不会被忽略。在**设置、实例**下打开**接收端**，然后在实例页面上打开发送实例的**详情**，添加已接收的仓库（只读，用发送实例的 restic 密码打开，该密码通过[配对组](#pairing)获得）。你会得到：

- **按来源的清单**，让你能确切看到哪些容器、虚拟机和文件夹集已经到达。
- 每个来源的**最后接收**，让你知道每个来源有多新。
- 在接收硬件上运行的**独立 `restic check`**，因此完整性在数据实际所在之处得到验证，而不仅仅在发送方。
- **一个死人开关：** 当某个来源在您设定的时间窗内停止发送时发出告警。
- **完整性告警：** 当接收侧的一次检查失败时发出告警。

接收端严格只读。它绝不会写入已接收的仓库，因此绝不会破坏发送方所依赖的 append-only 保证。

拉取端则反过来：打开**拉取**后，实例按自己的计划把另一个成员的备份读入自己的仓库。它的来源同样列在该成员的详情中。

### 接收服务器 {#receiving-server}

接收机器也可以运行其他实例复制到的 rest-server。它在你第一次允许一个要求它的**接收端**请求时设置：窗口说明该服务器需要一台接收服务器，并要求一个共享上的文件夹（用**新建文件夹**创建一个）和一个端口（除非有别的容器占用，否则为 8000）。BombVault 随后：

1. 如果已存在名为 `rest-server` 的容器，或其他容器占用了该端口，则拒绝；
2. 拉取 `restic/rest-server`，通过 Docker 套接字以 append-only 模式启动，使用私有仓库，并在该文件夹中放置登录文件；
3. 把它的 Unraid 模板写入闪存，让该容器仍可在 Docker 标签页中编辑；如果无法访问闪存，则提供模板下载；
4. 对它运行篡改测试，并显示它是否拒绝删除。

你组里的实例随后会在服务商中的**来自你的组**下找到该服务器，以接收机器命名，而**接收端**角色会把它作为安全的选择提供出来。每个实例在第一次使用该服务器时得到自己的登录，并且只写入那里属于自己的文件夹。在**设置、实例**下打开**接收端**后，本实例卡片上的**接收服务器**会再次打开该服务器。它的窗口在**持有登录信息的伙伴**下列出登录，**撤销登录信息**会收回一个；该实例已经复制的内容仍留在文件夹中。设置还会创建一个**组外登录信息**，窗口只会显示一次它的密码。

只能通过中继到达接收机器的实例无法使用该服务器，因为中继不携带备份。请先在配对页面添加接收机器的地址。当 BombVault 运行在它自己的 IP 地址上（例如在 br0 上）时，请填写**给伙伴使用的地址（可选）**，因为服务器监听的是主机的地址。

## 完整示例：两台 Unraid，从头到尾

以上描述的是各个部分。这是一套完整的设置，因为各部分在你见过一次组装好的样子之后更容易拼起来。

两台机器：**TOWER** 运行容器并推送备份；**VAULT** 接收它们并强制执行 append-only。请换成你自己的名称、地址和共享路径。

**1. 把两台机器配对。** 在 TOWER 上打开**设置、配对**，按**生成口令**，然后在 VAULT 上的**输入口令**下输入这十二个单词。先在两台上都设置登录密码。

**2. 在 TOWER 上请 VAULT 做接收端。** 在实例页面上，打开 VAULT 卡片上的**接收端**，选择分区，把**VAULT 的接收服务器**作为存放位置，然后发送请求。

**3. 在 VAULT 上允许它。** VAULT 的实例页面在 TOWER 的卡片上显示该请求。按**允许**。第一次时，VAULT 会为它的接收服务器询问一个文件夹，例如 `user/appdata/rest-server`，以 append-only 模式启动 rest-server，并对它运行篡改测试。

**4. 回到 TOWER。** 从此 TOWER 在每次备份后复制到 VAULT，新的目标连同它的删除保护出现在 TOWER 的目标页面上。

篡改测试的答复含义：

| 结果 | 发生了什么 |
| --- | --- |
| **受保护** | VAULT 拒绝了删除。这是唯一通过的状态。 |
| **未受保护** | VAULT 接受了一次删除。`--append-only` 缺失或已被移除。 |
| **无法判定** | 两者都不是。通常是 URL 与 restic 自己使用的不一致，或者凭据已更改。不会记录任何结果，也不会触发告警。 |

**5. 如果你想的话，监视到达的内容。** 在 VAULT 的**设置、实例**下打开**接收端**，打开 TOWER 的**详情**并添加已接收的仓库。VAULT 通过组获得 TOWER 的 restic 密码；没有人需要输入密钥。

**6. 让它成为双向的。** 按相反方向重复这些步骤：VAULT 请 TOWER 做它的接收端。每台机器随后都为对方强制执行 append-only，谁都无法删除对方的备份。

你手动运行的 rest-server 同样可行：用**添加目标**把它作为 rest-server 添加，用户和密码取自它的 `.htpasswd`，并打开防删除保护。请在它的选项中保留 `--append-only`；没有它，远端又成了普通共享。

!!! warning "本地路径是容器内部的路径"
    在 BombVault 询问这台服务器上的文件夹的地方，请相对于主机挂载输入，例如 `user/appdata/rest-server/bombvault-containers`，而不是 `/mnt/user/appdata/...`。BombVault 运行在容器中，主机的 `/mnt` 挂载在别处；主机的绝对路径在容器内并不存在。如果你粘贴了这样的路径，BombVault 会告诉你应改用的相对路径。

## 应急向导 {#emergency}

**应急向导**会找回已经消失或重新设置过的服务器。它从**恢复**页面的**紧急**下开始，也可以从全新安装的欢迎页上的**从备份恢复**开始。它分四步进行：**访问**、**设置**、**选择**和**还原**。

1. **访问。** 用以下三种方式之一向 BombVault 出示旧备份的密钥：
    - **上传恢复工具包**：你在设置时下载的文件。它包含密钥和每个目标，BombVault 从中填入其余内容。用 age 封存的工具包会要求它所封存的身份；该身份只使用一次，不会被存储。
    - **通过组**：你组里的一个实例把密钥作为托管副本保存。你需要组的十二个单词、你的取回码，以及那个实例上的一个人。参见[密钥保管端](#key-keeper)。
    - **输入密钥**：旧服务器的 `APP_KEY`，以及它的备份所在的位置。

    BombVault 随后在每个目标上尝试该密钥，并对每一个说明它是可读、未找到、被另一个密钥锁住、无法访问，还是仍缺少登录信息。目前还没有保存任何内容，密钥只会在内存中保留有限的时间。**接管密钥**让这台服务器此后用该密钥写入备份；**撤销接管**会回到它自己的密钥，直到第一次备份运行为止。已经有自己备份的服务器会拒绝接管，并指向[从旧的备份文件夹](#restore-from-another-bombvault-repo)。**保存登录信息**会存下工具包为远程目标携带的登录信息，并在替换这台服务器已有的登录信息之前询问。
2. **设置。** **恢复设置**从最新的自我备份还原 BombVault 自己的设置：目标、凭据、计划和规则。BombVault 会通过 Docker 套接字重启以应用它们，因此运行中的设置数据库不会在打开的句柄下被覆盖，向导随后会自行继续。这台服务器的登录保持不变：你继续用现在使用的密码登录。旧服务器存储的、无法接管的机密会被列出，这样你可以重新输入。
3. **选择。** BombVault 查看你的备份，并列出它找到的容器、虚拟机、文件夹集和 ZFS 数据集。最新的快照在各处都被预先选中。这台服务器仍有的内容起初是关闭的，因为还原会替换它。重建之后，文件夹集不再知道它们来自哪里，所以它们会放入你选择的一个文件夹。
4. **还原。** 所选的一切一次性回来，如果你想自己启动每个容器和虚拟机，则保持停止，这在彻底丢失之后最安全。之后下载新的恢复工具包：旧的属于之前的安装。

!!! tip "计划性迁移与灾难"
    应急向导从备份中还原 BombVault 自己的设置。对于*有计划的*迁移到新机器，你可以改用**导出 / 导入设置**卡片（一个可移植的 JSON 文件）直接带上你的配置。参见[配置](configuration.md#portable-settings-export-and-import)。

### 从旧的备份文件夹 {#restore-from-another-bombvault-repo}

还原页面**其他来源**下的**从旧的备份文件夹**会用该实例的恢复工具包或输入的 `APP_KEY`，在一次性的只读会话中打开*另一个* BombVault 实例的仓库（挂载在 `/mnt` 下的共享，或远程地址）。浏览存放在那里的容器、虚拟机、文件夹集和 ZFS 数据集，选择一个快照并还原它，被还原的对象会成为普通的本地容器、虚拟机或文件夹集。绝不会向另一个仓库写入任何内容，你自己的备份设置也保持不变（会话存在于内存中并自行过期）。把容器从服务器 A 迁到服务器 B，并不意味着重新指向你的设置、之后再还原它们。这个窗口是一次性的：它打开一个会话，还原你选的内容，然后忘记另一个实例。如果你想要一种长期的安排，由这台机器按计划把另一个实例的快照拉进自己的仓库，那就是实例页面上的**拉取端**角色。

如果容器的网络在此服务器上不存在，例如普通 Docker 主机上的 Unraid `br0` 网络，它的行下方会出现网络选择。BombVault 会在你选择的网络上创建它，并保留其他网络。固定 IP 地址和 MAC 地址属于旧网络，因此会被去掉，由新网络分配。

## 密钥保管端 {#key-keeper}

密钥保管端是你组里保存这台服务器恢复工具包封存副本的实例。它自己无法打开该副本。如果这台服务器丢失，加入你组的新安装会向保管端索取该副本，并用你的取回码打开它。

1. 在实例页面上，打开应保管它的实例卡片上的**密钥保管端**，选择**托管**。托管需要登录密码。
2. 这台服务器只会显示一次**取回码**：二十个字母和数字，分成四组，每组五个。把它写下来，并用**我已记下取回码**确认。这台服务器不存储该码，只存储为它封存托管副本所需的内容。
3. 保管端现在持有托管副本，并且工具包变化时这台服务器会更新它。此实例卡片上的**托管副本**列出每个保管端及其状态下的**这台服务器的托管副本**，以及为其他实例保管的**这台服务器保管的托管副本**。**生成新取回码**会替换该码；每个保管端在收到新的托管副本时切换到新码。

到那一天你需要三样东西：组的十二个单词、取回码，以及保管端界面的访问权限，那里需要有人按下**允许**。在应急向导中选择**通过组**，挑选托管副本，索取它并输入取回码。该码在新服务器上使用，不会发送给保管端。在保管端上，请求显示在**托管副本**下，写明谁在请求、该实例以前在那里是否见过，以及它请求的次数；**允许**会交出封存副本，允许需要登录密码。新安装在允许之后有 30 分钟来领取，无人应答的请求一天后失效，请求过于频繁的实例必须等待一小时。

没有这个码，谁也打不开该副本，保管端也不例外。如果码丢了，请趁这台服务器还在运行时生成新码；如果服务器已经没了，恢复工具包和输入的 APP_KEY 仍然有效。保管端可以随时删除托管副本，之后所有者必须重新索取。

## 恢复工具包 {#recovery-kit}

这是使灾难恢复在没有运行中的 BombVault 时也能实现的那一环。

**设置、还原**下**应急用**卡片中的**下载恢复工具包**会给你**密钥**、**派生的 restic 密码**、每个**目标**以及各分区的仓库、新安装访问它们所需的登录信息，以及**精确的 restic 命令**，这样你可以在任何机器上直接用 restic CLI 还原。它需要登录密码。即使关闭加密，工具包也会印出密钥，因为容器和虚拟机的定义始终用它封存。接管之后，它会印出接管来的备份密钥以及这台服务器的 APP_KEY，后者新安装只在找回设置时才需要。概览上的**保存你的恢复工具包**卡片会一直提醒你，直到你保存好它。

!!! danger "将恢复工具包存放在服务器之外"
    工具包包含解密你备份的机密。请把它存放在安全且与服务器分离的地方（密码管理器、保险柜里的打印件）。如果你同时丢失了 BombVault 和 `APP_KEY`，又没有恢复工具包和密钥托管副本，你的加密备份就无法恢复。

!!! warning "最新的快照不一定是应该恢复的那个"
    自 restic 0.17 起，`restic snapshots` 会显示每个快照的大小。数据丢失后，最新的快照可能是被清空的那个，所以不要还原一个比之前的小得多的快照。遭遇勒索软件后，它可能是大小正常、但已被加密的那个。如果 BombVault 仍在运行，请先看它的**异常**页面：它会点出最近一次良好的备份，还原窗口会预先选中它。还原不需要 BombVault 的任何异常数据，保留暂停只会多保留快照。

### 密封恢复工具包

如果你在**设置、系统**下打开了**使用 age 加密导出**，工具包也会用它封存，并以 `bombvault-recovery-kit.md.age` 的形式下载。它是 ASCII 封装而不是二进制，所以仍是纯文本：粘贴到密码管理器或打印的做法与以前完全一样，只是没有你的密钥就无法读取其内容。

!!! warning "不要把 age 密钥存放在工具包里"
    打开密封的工具包需要您的 age **私钥**。请把它存放在不依赖工具包本身的地方，否则您要恢复的东西就从一样变成了两样。当工具包存放在您无法完全掌控的地方（共享的密码管理器、云笔记、办公室里的打印件）时，密封才有价值；放在您自己保险箱里的工具包已经有保险箱保护了。

    在加密开启却没有配置可用收件人时，下载会被直接拒绝。BombVault 绝不会退回到以明文交出主密钥。

### 手边没有恢复包时

密码不存储在任何地方，它是由备份的密钥**计算**出来的，所以只需密钥和一个 shell，你就能自己重现它：

```sh
printf 'bombvault:restic-repo' \
```

这是对固定字符串 `bombvault:restic-repo` 的 HMAC-SHA256，以十六进制 `APP_KEY` 的原始字节为密钥，打印为 64 个小写十六进制字符。工具包中也有同样的值，列为派生的 restic 密码；这是为工具包不在你身边的那一天准备的。在接管了另一台服务器备份的服务器上，请使用接管来的备份密钥，也就是那台服务器原来的 APP_KEY。

!!! warning "对于接收到的仓库，请用「发送方」实例的密钥"
    通过异地副本到达这里的仓库，是由发送它的机器用**它的**密钥创建的。用接收机器的密钥派生会得到 restic 会拒绝的密码，这读起来与仓库损坏一模一样，其实并不是。这正是接收仓库上的 `restic check` 为什么一再索要密码的常见原因。

由于恢复定义存放在每个仓库**内部**（`<repo>/def`、`<repo>/vm-def`），被复制的仓库文件夹是完全自包含的，因此工具包加上仓库就是一次裸机还原所需的全部。

## 取回数据库转储 {#database-dumps}

数据库转储是容器仓库中独立的一个还原点，标签为 `dbdump:<container>`，包含单个文件 `/dbdump/<container>.sql`。BombVault 在容器的**备份**标签页上列出、下载和导入它们；下面是只用 restic 的相同步骤，供 BombVault 不在时使用。

```sh
restic -r <repo> snapshots --tag dbdump:<container>
restic -r <repo> dump --tag dbdump:<container> latest /dbdump/<container>.sql > <container>.sql
```

每个转储上的 `dbversion:` 和 `dbname:` 标签说明它来自哪个服务器版本、包含哪些数据库。完整的文件以 `-- PostgreSQL database cluster dump complete` 或 `-- Dump completed` 结尾。

把它导入一个相同或更新版本（PostgreSQL）、或相同大版本（MySQL 和 MariaDB）的容器，该容器要先用空数据目录启动一次完成初始化。宿主机不需要数据库客户端，容器里就有：

```sh
docker exec -i <container> sh -c 'exec psql -X -U "${POSTGRES_USER:-postgres}" -d postgres' < <container>.sql
docker exec -i <container> sh -c 'exec mariadb -uroot -p"$MARIADB_ROOT_PASSWORD"' < <container>.sql
docker exec -i <container> sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < <container>.sql
```

若只想从完整转储里取一个数据库，MySQL 和 MariaDB 的客户端命令接受 `--one-database <name>`。PostgreSQL 的转储每个数据库一段，每段以一行 `\connect <name>` 开头：把那一段复制成单独的文件，先创建数据库，再用 `-d <name>` 导入。

!!! warning "以 root 取的转储会带上服务器的用户"
    以 root 取的 MySQL 或 MariaDB 完整转储包含系统数据库 `mysql`，导入它会把新服务器的账号，连同 root 的密码，替换为转储里的那些。在 PostgreSQL 上，针对容器自己创建的用户出现 `role ... already exists` 属于预期，无害。
