# Funcționalități

Tot ce salvează BombVault stă într-o singură listă, fiecare element are o pagină proprie, restaurările pornesc de la o singură pagină, iar setările sunt plăci. Nu există un mod avansat de pornit; lucrurile rare au un card sau o fereastră a lor. Această pagină grupează întregul set de funcționalități.

## Sfera backupului

![Lista Copii de rezervă: fiecare element cu ultimele rulări sub formă de bandă, o stare și acțiunile lui.](assets/screenshots/containers.png)

*Lista Copii de rezervă: fiecare element cu ultimele rulări sub formă de bandă, o stare și acțiunile lui.*

| Secțiune | Ce se salvează |
|---|---|
| **Containere** | Directorul appdata plus definiția containerului (imagine, variabile de mediu, porturi, etichete, volume). Implicit întregul director appdata; cardul **Foldere de salvat** din fila **Setări** a containerului bifează exact ce foldere acoperă copia, cu un număr în direct al căilor, o listă cu ce ai lăsat deoparte și un comutator **Sari peste folderele cache (CACHEDIR.TAG)**. |
| **VM-uri** | Imaginea (imaginile) de disc a VM-ului, definiția XML și NVRAM-ul UEFI (oprire controlată sau instantaneu live, prin SSH). Instantaneele live revin automat la o copie controlată dacă instantaneul nu poate fi creat, așa că o copie de VM nu se oprește pur și simplu cu o eroare. Cu **Doar blocurile modificate** pornit, un VM în execuție cu discuri qcow2 este citit prin punctele de control libvirt, astfel încât o copie citește doar blocurile scrise de la precedenta, iar fiecare copie de rezervă se restaurează totuși singură pe întreg discul. Discurile de pe zvol-uri ZFS sunt transmise cu `zfs send` pe aceeași legătură SSH, așa că un VM ale cărui discuri sunt zvol-uri este salvat ca un singur VM. Starea unui vTPM cu pass-through este salvată lângă NVRAM când XML-ul domeniului îi indică calea. Un vTPM emulat, pe care TrueNAS îl configurează pentru oaspeții Windows 11, nu publică acea cale, așa că ține la îndemână cheia de recuperare a unui astfel de oaspete. Vezi [ghidul de backup VM](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md). |
| **Flash** | Întregul flash USB (`/boot`): sistemul de operare, licența, configurația array-ului, partajările, rețeaua și configurația plugin-urilor. Restaurarea este o descărcare `.zip` și nu suprascrie niciodată flash-ul activ. |
| **Auto-backup** | Propriul `/config` al BombVault (baza de date de setări, datele de autentificare ale destinațiilor, perechea de chei SSH libvirt), captat cu SQLite `VACUUM INTO`, astfel încât o bază de date în mod WAL nu este niciodată captată în mijlocul unei scrieri. Revine prin Asistentul de urgență, care repornește BombVault, așa că baza de date activă nu este niciodată suprascrisă sub un handle deschis. |
| **Foldere** | Seturi de foldere: orice folder de pe server (o partajare, documentele tale, o bibliotecă foto), fiecare cu tipare de excludere opționale. **Adaugă** de pe pagina Copii de rezervă listează partajările găsite și primește orice alt folder. Seturile de foldere au tot ce au celelalte secțiuni: programări, retenție, copii off-site, verificări și exerciții de restaurare. |
| **Seturi de date ZFS** | Un set de date împreună cu fiecare set de date de sub el, citit dintr-un singur instantaneu ZFS, astfel încât toate provin din același moment, și salvat cu restic ca un folder: deduplicat, navigabil, cu fișiere individuale restaurabile. Seturile copil noi se alătură singure, copiii individuali pot fi lăsați deoparte, iar un copil care nu poate fi citit este sărit și numit. Opțional, containerele sunt oprite sau o comandă rulează doar pe durata instantaneului. Volumele nu sunt incluse: volumul unui VM este salvat cu VM-ul, iar un volum fără VM nu este încă salvat. Un element ZFS poate păstra și o replică exactă pe blocuri pe un al doilea server ZFS. Vezi [Seturi de date ZFS](zfs-datasets.md). |

## Copii de rezervă și paginile elementelor {#backups}

- **O singură listă.** Containerele, VM-urile, seturile de foldere, unitatea flash, seturile de date ZFS și Auto-backup stau într-o singură listă la **Copii de rezervă**. Plăcile de deasupra aleg un fel, iar **Filtre**, **Sortare** și **Caută** o restrâng. Sortarea merge după nume, stare, ultima copie, dimensiune sau programare, în ambele sensuri, iar căutarea găsește un container după nume, imagine sau IP.
- **Ultimele rulări sub formă de bandă.** Un rând își arată ultimele paisprezece rulări ca pătrățele mici și o singură stare. Tot restul despre el se află în balonul de informații de lângă nume.
- **Selectezi ca într-un manager de fișiere.** Ctrl+clic, Shift+clic și Ctrl+A aleg rânduri, o apăsare lungă face asta pe telefon, iar fiecare rând are un meniu la clic dreapta. O selecție poate fi salvată sau pusă pe pauză și reluată în programare. Mai multe elemente se restaurează împreună pe pagina Restaurare.
- **Adaugă** deschide o fereastră pentru ce nu poate ghici BombVault: un folder sau un set de date ZFS. Containerele, VM-urile și unitatea flash apar singure. Pe o gazdă fără Unraid, fereastra oferă **Configurația sistemului**, un set de foldere `/etc` de pornire pe care îl revizuiești înainte de salvare.
- **Fără copie de rezervă** lasă un element deoparte intenționat. Atunci nu mai contează ca neprotejat, iar **Nu mai exclude** îl aduce înapoi.
- **Mai mult** pe pagina Copii de rezervă conține **Descoperă copii de rezervă**, care reconstruiește elementele din ce păstrează destinațiile (de exemplu după o instalare nouă), și **Restaurează stack-ul** pentru proiectele Compose.
- **O pagină pentru fiecare element**, cu trei file sub un antet care îi numește starea și îi conține acțiunile:
    - **Copii de rezervă** listează copiile de rezervă cu o bară pe zi, destinațiile care le păstrează și dumpurile bazelor de date.
    - **Setări** conține programarea și destinația, depozitul, folderele de salvat, tiparele de excludere, alte containere de oprit, comenzile dinainte și de după, dumpurile bazelor de date și numele anterioare. Programarea și destinația urmează valoarea implicită a secțiunii până când elementul primește una proprie.
    - **Verificare** arată verificările, dimensiunea pe foldere, monitorizarea anomaliilor elementului și rulările lui recente.
- **Marchezi și compari.** O copie de rezervă poate purta o etichetă a ta, iar **Compară cu altă copie** listează fișierele apărute, dispărute sau modificate între două dintre ele. Un VM compară imaginile de disc și spune cât din ele diferă.
- **Exportă** scrie o copie de rezervă, toate copiile de rezervă ale unui element sau un container ori un VM așa cum sunt chiar acum în folderul de export de pe server, ca tar, zip sau ca depozit restic propriu.

## Restaurare

![Pagina Restaurare: alegi o secțiune, cauți un element și alegi o copie de rezervă.](assets/screenshots/recovery.png)

*Pagina Restaurare: alegi o secțiune, cauți un element și alegi o copie de rezervă.*

- **O singură pagină.** **Restaurare** listează secțiunile ca plăci. Cauți ce vrei înapoi și alegi o copie de rezervă dintr-o listă cu cea mai nouă sus; cea recomandată este marcată, iar după o anomalie este ultima dinaintea ei. **Deschide elementul** duce la pagina elementului, iar o restaurare în curs apare la **În desfășurare**.
- **O singură fereastră pentru orice fel.** Întreabă în pași: ce **Copie de rezervă** (cea recomandată este preselectată), ce **Sursă** (cea locală este cea mai rapidă), **Ce** (tot, sau fișierele și folderele alese de tine) și **Unde**. O scenă arată ținta aleasă, iar **Ce se întâmplă** spune în cuvinte înainte să pornești.
- **Mai multe deodată.** Pe pagina Restaurare, Ctrl+clic, Shift+clic, Ctrl+A, o apăsare lungă sau **Selectează** aleg elemente, iar **Restaurare** deschide o singură fereastră pentru toate. Fiecare ia cea mai nouă copie de rezervă a sa, sau cea mai nouă dintr-un moment pe care îl alegi pentru toate, și ajunge lângă original sau îl înlocuiește. Restaurările rulează una după alta, iar fiecare rând arată cum a mers a lui. Unitatea flash vine ca ZIP de descărcat. Seturile de date ZFS și Auto-backup se restaurează pe rând.
- **Lângă original este implicit.** Un container revine ca al doilea container numit `<nume>-restored`, cu porturi proprii, în timp ce originalul continuă să ruleze. Discurile și NVRAM-ul unui VM ajung într-un folder numit `<folder>-restored` lângă original, fără un al doilea VM. Un set de foldere revine ca `<cale>-restored`. Copia apare la Copii de rezervă ca exclusă până când o adaugi în programare.
- **Înlocuirea originalului face mai întâi o copie.** Cu **Fă mai întâi o copie a stării actuale**, pornit implicit, BombVault salvează ce există acum înainte să înlocuiască, ca să te poți întoarce. Dacă acea copie eșuează, restaurarea nu pornește. Înlocuirea îți cere să tastezi numele elementului.
- **Într-un folder** scrie doar fișierele, pentru răsfoire. Un set de date ZFS poate fi restaurat și **Într-un set de date nou**, iar unitatea flash revine ca **Descarcă ca ZIP**.
- **Containerele sunt reinstalate automat.** Definiția containerului este reaplicată prin API-ul Docker, așa că el reapare în fila Docker din Unraid exact cum era.
- **GPU-ul, limitele și legăturile revin.** Un container restaurat își primește înapoi limitele de resurse, driverul de jurnale, setările DNS, legăturile vechi și GPU-ul sau runtime-ul (`--gpus`, `--runtime=nvidia`). Pe o gazdă fără acel driver GPU sau runtime, restaurarea spune asta și oferă **Restaurează fără GPU și runtime**, și după restaurarea mai multor containere sau a unui stack. O legătură către un container care lipsește, sau care e oprit când pornește cel restaurat, este omisă, iar istoricul rulărilor o menționează.
- **VM-urile sunt recreate automat.** XML-ul este reimportat prin SSH, așa că VM-ul reapare în VM Manager cu discul și NVRAM-ul UEFI reatașate, chiar și după ce VM-ul a fost șters.
- **Restaurarea flash este o descărcare `.zip`.** Se transmite către browserul tău ca `flash-<id>.zip`, gata de introdus în creatorul de USB Unraid. `/boot`-ul în execuție nu este atins niciodată.
- **Un plugin pe rând.** Fereastra de restaurare flash listează plugin-urile din fiecare copie flash cu versiunea și dimensiunea lor și pune înapoi în flash-ul activ doar unul: fișierul lui `.plg`, folderul lui de sub `config/plugins` și fișierele de pachet pe care le conține copia. Nimic altceva de pe flash nu se schimbă. Unraid instalează plugin-ul la următoarea pornire sau imediat, la **Plugins, Install Plugin**.
- **Export zip programat al flash-ului.** După fiecare copie flash, poți scrie opțional copia de rezervă ca un `.zip` simplu într-un folder ales de tine (un singur `flash-latest.zip` suprascris sau un istoric rulant). Este cardul **Export zip flash** din fila Setări a elementului flash. Îndreapt-o către un folder Syncthing sau rclone ca backupul tău de USB bootabil să părăsească automat serverul.
- **Verificare de conflicte înainte de zbor.** Înainte ca ceva să fie oprit sau eliminat, restaurarea verifică dacă IP-ul static al containerului și porturile publicate ale gazdei sunt libere și se oprește cu un mesaj clar în loc să lase o restaurare pe jumătate terminată.
- **Verificări înainte de restaurare.** Fereastra verifică mai întâi dacă depozitul răspunde, dacă cheia stocată îl deschide, dacă punctul de restaurare există și dacă ținta are loc pentru ce scrie restaurarea. Pornirea rămâne blocată cât timp o verificare eșuează, iar (i) din buton spune care.
- **Ce schimbă restaurarea.** Înainte să confirmi, fereastra arată ce face restaurarea față de ce există acum: fișiere noi, înlocuite și neschimbate, cu lista la cerere, și fișierele din țintă care nu sunt în copie și rămân unde sunt. Pentru containere și VM-uri compară și setările pe care le recreează restaurarea cu cele în execuție: imagine și etichetă, porturi, nume de variabile și volume, sau memorie, vCPU, discuri și rețea. restic calculează asta ca simulare din dimensiune și data modificării, fără să citească fișierele; un arbore foarte mare se oprește după 30 de secunde și spune asta. O restaurare de stack verifică și planifică fiecare membru și îl numește pe cel care o blochează.
- **Foldere partajate.** O restaurare pe loc numește fiecare alt container, pornit sau nu, al cărui montaj ajunge într-un folder în care scrie, de exemplu "această cale este folosită și de nextcloud-db". Avertizează și nu blochează.
- **Restaurarea unui set de date ZFS.** Restaurează un set de date al unui element la locul lui (după un instantaneu ZFS de siguranță care rămâne până îl ștergi), într-un folder, într-un set de date nou sau doar fișierele alese de tine, ori fiecare set de date al unei copii într-un folder. Un set de date nu este niciodată readus la o stare anterioară sau înlocuit.
- **Restaurarea păstrează starea de rulare.** Un container sau VM care rula la copie revine pornit; unul oprit rămâne oprit. Bifează **Lasă oprit după aceea** ca să-l recreezi fără să-l pornești.
- **Restaurarea unui stack întreg.** Containerele din același proiect Docker Compose cu cel puțin doi membri salvați formează un stack. **Restaurează stack-ul** de la **Mai mult** pe pagina Copii de rezervă reconstruiește fiecare membru din ultima lui copie, apoi îi pornește opțional în ordinea `depends_on`.
- **Progres în direct, anulare și feedback de ocupat.** O restaurare lungă arată o bară de procente în direct și poate fi anulată cu o confirmare adaptată tipului. O restaurare anulată este înregistrată ca *anulată*, nu eșuată. Fereastra poate fi închisă; progresul apare și la Restaurare.
- **Asistentul de urgență.** Pentru un server pierdut sau reinstalat, cu kitul de recuperare, prin grup sau cu cheia tastată. Vezi [Off-site și recuperare](offsite-recovery.md#emergency).
- **Dintr-un folder vechi de copii de rezervă.** O sesiune doar în citire deschide depozitul altui BombVault cu kitul de recuperare al acelei instanțe sau cu `APP_KEY` tastat, ca să poți aduce un container de pe serverul A pe serverul B fără să-ți atingi propriile setări. Vezi [Off-site și recuperare](offsite-recovery.md#restore-from-another-bombvault-repo).
- **Proprietățile ZFS revin.** Fiecare backup ZFS păstrează proprietățile setate local ale fiecărui set de date, cum ar fi compresia, dimensiunea înregistrării, cota și sensibilitatea la majuscule. O restaurare într-un set de date nou îl creează cu ele, iar o restaurare într-unul existent le arată și le setează doar dacă ceri. Vezi [Seturi de date ZFS](zfs-datasets.md#new-dataset).
- **Importă din plugin-ul Appdata.Backup.** La **Alte surse** pe pagina Restaurare, îndreaptă BombVault către folderul de copii al plugin-ului. Fiecare arhivă de container devine un punct de restaurare al containerului ei, datat cu momentul în care l-a făcut plugin-ul. Arhivele importate înainte sunt sărite, iar arhivele în sine sunt doar citite. Containerul are nevoie mai întâi de o copie în BombVault, ca restaurarea să aibă definiția lui. Retenția lasă în pace punctele de restaurare importate, așa că șterge-l tu când nu mai ai nevoie de unul.

## Stocare și programare

- Backupuri incrementale, deduplicate prin restic, așa că nici măcar discurile mari de VM nu umflă depozitul.
- **Destinații.** Folderele locale și locurile off-site stau într-o singură listă pe pagina **Destinații**, pe care o deschizi din placa ei de setări sau o fixezi în bara laterală. Fiecare destinație are o pagină proprie cu conexiunea, credențialele, protecția la ștergere, setările de copiere, retenția și regulile pe secțiuni, plus un vas care arată cât de plină este și când se umple, la ritmul de creștere din ultimele săptămâni. Vezi [Destinații](offsite-recovery.md#destinations).
- **Feluri de stocare:** o cale locală, partajări SMB și servere WebDAV (Nextcloud, ownCloud, SharePoint) prin rclone fără montare pe gazdă, NFS (montează exportul pe Unraid și folosește-l ca folder local), backenduri restic native fără rclone (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`) sau orice remote rclone prin `rclone:<remote>:<bucket>/path`. Toate credențialele sunt stocate criptat.
- **Destinațiile SSH nu necesită nimic instalat pe partea îndepărtată.** `sftp:` cere doar un server SSH, așa că un Raspberry Pi gol (fără Docker, fără restic) funcționează ca destinație off-site. Cheile gazdei sunt fixate automat la primul contact.
- **3-2-1 ca imagine.** Cardul **Destinații pe secțiuni** desenează ce secțiune este salvată unde. Fiecare linie de la o secțiune la o destinație este un comutator, iar **Grafic / Comutatoare** dă același lucru ca simple butoane. Elementele care se salvează în altă parte decât secțiunea lor stau la **Alegere proprie**, fiecare cu **Urmează setarea implicită**.
- **Copie off-site (local + la distanță).** Păstrează copia locală rapidă și adaugă una sau mai multe destinații off-site, copiate cu `restic copy` pe bază de best-effort (un sughiț off-site nu face niciodată să eșueze copia locală). O copiere transferă doar pachetele de date pe care destinația nu le are încă. Cardul **Copiază** al fiecărei destinații stabilește **Când se copiază** (**După fiecare copie de rezervă** sau după un plan propriu) și lățimea de bandă, iar o secțiune poate copia după un plan propriu la **Setări, Programare**.
- **Mai multe destinații pe secțiune.** Fiecare secțiune poate copia simultan în mai multe destinații off-site. **Regulile pe secțiuni** ale unei destinații dau unei secțiuni propria retenție, compresie sau propriul depozit acolo, în timp ce autentificarea, credențialele, lățimea de bandă și momentul vin de la destinație.
- **Mută istoricul unei secțiuni.** **Mută** pe o destinație duce copia unei secțiuni, cu tot istoricul ei, la altă destinație. Locul vechi păstrează tot; BombVault nu șterge nimic acolo.
- **Depozite denumite.** Cardul **Depozite** de la **Setări, Destinații** notează locațiile copiilor tale o singură dată, o cale locală sau orice remote restic cu propriul set de credențiale, ca să fie alese drept locul unui element. Un rând arată câte elemente îl folosesc, iar un depozit pe care îl folosește un element sau o valoare implicită nu poate fi mutat sau șters, pentru că BombVault nu mută niciodată o copie deja scrisă.
- **Mai multe seturi de credențiale.** Credențialele cloud partajate se aplică implicit peste tot, dar orice destinație poate folosi în schimb un set denumit (**Seturi suplimentare de credențiale** la **Setări, Destinații**, sau **Credențiale** pe pagina destinației), așa că un bucket Hetzner S3 și un server Garage local pot funcționa unul lângă altul, fiecare cu cheia lui.
- **Amplasare per element.** Cardul **Programare și destinație** din fila Setări a unui element are un rând de butoane, **Local** și câte unul pentru fiecare destinație off-site, iar cele aprinse primesc copiile lui. O partajare care stă deja pe un NAS nu mai trebuie să meargă și la B2. Locul este fixat din prima copie, copiile se pot schimba oricând, iar cardul spune câte locuri păstrează elementul și dacă 3-2-1 este îndeplinit. Vezi [Amplasare per element](offsite-recovery.md#placement).
- **Ordine manuală a copiilor.** Cardul **Ordine** de la **Setări, Programare** stabilește ordinea exactă în care sunt salvate containerele și VM-urile. Rulările programate și copia totală o urmează; orice lași neordonat păstrează ordinea celor mai restante mai întâi, iar o copie singulară rămâne neschimbată.
- **Retenția ca o axă a timpului.** Fiecare destinație păstrează copiile după **Cât timp se păstrează**: **Scurt**, **Echilibrat**, **Lung** sau **Valori proprii** pentru ultimele copii, zile, săptămâni, luni și ani, curățate automat. Axa arată ce copii păstrează o regulă. **Întreabă înainte de a păstra mai puțin** întreabă înainte ca o regulă mai scurtă să șteargă copii mai vechi al căror unic exemplar este acolo. O secțiune își poate păstra propriile valori la o destinație, la **Reguli pe secțiuni**.
- **Compresie per depozit:** Oprit, Automată (implicitul restic) sau Maximă, setată pe fiecare destinație și, pentru o secțiune, la regulile ei de acolo. Copiile, copiile off-site și curățarea scriu cu ea, iar kitul de recuperare o numește, așa că restic simplu poate continua să scrie la fel.
- **Programările se citesc ca propoziții**, de exemplu *Săptămânal duminica la 04:00*, și se editează chiar din acea propoziție. **Setări, Programare** le conține pe toate: banda **Săptămâna** cu fiecare rulare planificată de luni până duminică, **Backup total** cu o comandă înainte și una după, **Programări pe secțiuni**, **Copii externe pe secțiuni** și **Elemente programate**. **La fiecare N zile** funcționează și pentru exercițiul de restaurare, testul de manipulare și rezumatul săptămânal.
- **O secțiune cu plan propriu iese din copia totală.** Butonul **Excepție** de la **Programări pe secțiuni** dă unei secțiuni un plan propriu, iar acea secțiune rulează apoi la ora ei și nu mai rulează încă o dată în copia totală, așa că nimic nu este salvat de două ori. **Copiază tot acum** tot ia fiecare secțiune pornită. Cu **Programări proprii pe elemente** pornit, un container, VM, set de foldere sau set de date ZFS poate primi un plan propriu pe pagina lui și iese și el din copia totală.
- **Actualizează containerele după o copie reușită.** Un singur comutator la **Setări, Programare, Actualizări după backup**, oprit implicit, trage o imagine nouă abia după ce copia dinaintea ei s-a încheiat. Un singur container poate fi setat altfel pe pagina lui.
- **Așteaptă până aplicația este inactivă.** Un container poate lăsa copia lui programată să aștepte cât timp aplicația este ocupată, cel mult numărul de ore stabilit, și să pornească de îndată ce aplicația este inactivă. Un server media contează ca inactiv când nu face streaming, orice alt container când CPU-ul și traficul rămân sub limitele din cardul **Inactivitate înainte de copie** de la **Setări, Programare** câteva minute (pe rețeaua gazdei contează doar CPU-ul). Copia care așteaptă apare în jurnalul de activitate și pe container cu motivul și termenul ei. Nu ține niciun blocaj, așa că celelalte containere merg înainte. Copiile manuale nu așteaptă niciodată. Membrii unui stack Compose scadenți în aceeași rulare așteaptă împreună, iar o așteptare continuă cu termenul ei după o repornire. Oprirea containerelor renunță la fiecare copie în așteptare, iar oprirea programării lor renunță la cele pe care rulările ei le-au ținut în urmă. Scăderea numărului de ore scurtează o așteptare deja începută.
- **Limite de lățime de bandă off-site.** Limitează rata de upload/download restic ca să nu satureze copiile WAN-ul tău, în cardul **Lățime de bandă externă** de la **Setări, Destinații** și per destinație în cardul ei **Copiază**.
- **Întâi streamingul.** Cât timp un server media precum Plex, Jellyfin sau Emby face streaming, copiile off-site se încarcă la o limită mai mică și revin la cea normală la câteva minute după încheierea stream-ului. BombVault citește din Docker traficul de ieșire al serverelor media. REST, S3, B2, Azure, Google Cloud, Swift și rclone peste HTTP încetinesc în mijlocul unei copieri; SFTP și folderele locale sau montate preiau limita mai mică la următorul pas de copiere. Un server media din rețeaua gazdei nu poate fi măsurat. Este cardul **Streaming** de pe pagina Destinații.
- **Clasă de stocare la rece și de arhivă (S3).** Pentru o destinație S3 poți alege clasa de stocare, limitată la nivelurile din care se poate restaura (Standard, Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier Instant Retrieval), ca prețul de arhivă să nu strice în tăcere o restaurare. Nivelurile de arhivă profundă care cer mai întâi o dezghețare asincronă (Glacier Flexible, Deep Archive) sunt lăsate deoparte, pentru că restic nu poate citi din ele. Doar backendurile S3 native; remote-urile rclone își setează clasa în configurația rclone.
- **Folderele de backup rămân copiabile în afara stației.** După fiecare backup BombVault relaxează arborele depozitului local la directoare `0755` / fișiere `0644` (depozitele sunt criptate, deci nimic nu este expus) astfel încât un utilizator de sincronizare non-root prin SMB să nu fie blocat. Definițiile de recuperare se află în interiorul fiecărui depozit, deci un folder de depozit copiat este complet autonom.

## Perspectivă, verificare și monitorizare

- **Prezentarea.** Începe cu un antet de stare și patru carduri: **Necesită atenție**, **Stare protecție**, **Destinații** cu o prognoză a momentului în care se umple fiecare și **Istoric** cu rulările și jurnalul. Inelul din antet arată cât este protejat și devine un inel de progres cu stațiile lui cât timp rulează o copie. Mai multe carduri așteaptă la **Personalizează**: **Anomalii**, **Fără backup**, **Calendar**, **Stocare**, **Prezentare generală**, **Statistici** și **Integrare gazdă**. Fiecare card poate fi mutat, redimensionat și ascuns, iar aranjamentul se salvează în browser.
- **Un singur număr peste tot.** Fiecare card numără la fel elementele secțiunilor pornite.
- **Pauză din element.** **Pune programarea pe pauză** scoate un element din programare și din copia totală, iar **Reia programarea** îl aduce înapoi. Setează același comutator ca **În programare** din fila Setări a elementului, așa că cele două sunt mereu de acord. Un element pus pe pauză poartă o insignă gri **Programare oprită**, iar **Copiază acum** funcționează în continuare.
- **Stare protecție.** Fiecare secțiune are patru verificări: o copie actuală pe acest server, o copie off-site, protecția la ștergere acolo și o restaurare de probă de acolo. O copie întârziată devine roșie în loc să se ascundă într-un jurnal, iar un clic pe o secțiune arată detaliile.
- **Calendar.** Ultimele 90 de zile, un pătrățel pe zi cu rezultatul copiei din acea zi. Un clic pe o zi arată rândurile ei din jurnal, la Istoric.
- **Timpul rulării peste tot.** Fiecare rulare se citește `început, sfârșit (durată)`, iar fiecare element își are propria listă **Rulări recente** în fila Verificare.
- **Dimensiunea depozitului și tendința de deduplicare.** Cardul **Stocare** arată cât ocupă fiecare secțiune și cât de bine se deduplică datele.
- **Exerciții de verificare a restaurării.** BombVault dovedește periodic că copiile tale se pot restaura (`restic check --read-data-subset`, limitat), configurat la **Setări, Verificare, Verificări automate**. Cardul **Verifică copiile de rezervă** de pe aceeași placă arată rezultatul pe secțiune și conține **Deblochează** și **Curăță** la **Mai mult**.
- **Verificarea restaurării după prima copie.** Când se încheie prima copie a unui element, BombVault restaurează un eșantion din ea (până la 100 de fișiere și 256 MiB) într-un folder temporar de sub folderul de restaurare, pune restic să citească înapoi fiecare fișier față de hash-urile lui și compară dimensiunile cu copia. Un fișier prea mare pentru eșantion, de exemplu un disc de VM, își are citiți înapoi primii 64 MiB. Fila Verificare a elementului arată rezultatul, un eșec pleacă drept notificare, iar **Verifică restaurarea** rulează aceeași verificare pe cea mai nouă copie oricând vrei. Copiile următoare nu o repetă.
- **Test de pornire.** Verificarea octeților nu arată că aplicația revine. **Test de pornire** în fila Verificare a unui container restaurează cea mai nouă copie a lui într-o copie izolată și o pornește: un nume care începe cu `bombvault-test-`, o rețea Docker internă proprie, fără porturi publicate și fără drum spre LAN, 1 CPU și 2 GiB de memorie, iar datele într-un folder temporar de sub folderul de restaurare. Testul trece când verificarea de sănătate a containerului raportează sănătos sau, fără una, când primul port expus răspunde din interiorul acelei rețele sau, fără niciuna, când containerul continuă să ruleze. Containerul original nu este niciodată oprit sau modificat, iar copia, rețeaua și datele ei sunt șterse după aceea, inclusiv după o repornire a BombVault în mijlocul unui test. Containerele din rețeaua gazdei, cele privilegiate, cele cu dispozitive și cele care au nevoie de alt container sunt arătate ca netestabile. Pornește **Test de pornire** la **Setări, Verificare, Verificări automate** ca să testezi câte un container pe rulare, cel testat cel mai demult primul. Copia nu poartă niciuna dintre etichetele originalului și rulează fără capabilitățile, opțiunile de securitate, sysctl-urile și cgroup parent pe care le adaugă originalul. Un container care le cere eșuează la test, iar rezultatul numește cu ce a rulat copia fără.
- **Operațiuni care se vindecă singure.** Un lock restic dovedit orfan (lăsat de o repornire în mijlocul unei operațiuni) este curățat forțat și reîncercat o dată, automat. Retenția este stabilă ca identitate (curățată per element, imună la schimbări de cale sau de gazdă), iar un eșec al retenției trimite o notificare.
- **Avertismente pe care scanarea folderelor nu le vede.** Asistentul de excluderi răspunde la o întrebare de dimensiune. Unele dintre cele mai costisitoare greșeli de backup nu sunt întrebări de dimensiune, așa că el poartă și avertismente specifice fiecărei aplicații despre felul în care își stochează datele. Cel pentru care există: Immich păstrează albumele, fețele și datele fiecărei fotografii într-o bază de date PostgreSQL care rulează într-un container *separat*, așa că un backup la nivel de fișier al containerului Immich restaurează pozele fără nimic din toate acestea, iar restaurarea pare să fi reușit. Avertismentul apare indiferent dacă se oferă sau nu vreo excludere, inclusiv pe un container fără nimic selectat pentru scanare, pentru că avertismentul este adevărat în orice caz.
- **Not backed up (acoperire).** Un card din prezentare care numește tot ce este pe server și nu e acoperit de nicio copie programată, cu motivul pentru fiecare: niciodată adăugat în BombVault, prezent dar nu în programare, propria programare setată pe oprit sau nicio programare pornită nicăieri. Starea protecției răspunde la altă întrebare, anume dacă copiile care *sunt* programate au rulat la timp, și nu poate vedea containerul pe care nu l-a configurat nimeni. Containerele sunt citite din lista Docker activă, nu din rândurile proprii ale BombVault, pentru că un element fără rând este exact cel care trebuie numit. O secțiune oprită de tine și un element marcat **Fără copie de rezervă** sunt lăsate în afara numărului, pentru că a fost alegerea ta.
- **Previzualizarea retenției.** Cardul **Previzualizare** de la **Setări, Destinații** arată ce urmează să șteargă rularea următoare, înainte să se întâmple: per depozit și per element, cu punctele de restaurare numite. Nu ia niciun blocaj pe depozit și nu schimbă nimic, așa că răspunde chiar și cât timp rulează o copie. Retenția oprită spune asta în loc să arate o listă goală, un depozit append-only este etichetat ca atare (retenția nu rulează acolo deloc), iar un depozit care nu a putut fi atins este numit în loc să lipsească în tăcere.
- **Anomalii.** Fiecare copie a unui container, VM, set de foldere, dump de bază de date, a unității flash și din Auto-backup este comparată cu istoricul propriu al elementului. Verificările privesc datele noi pe care le-a stocat o rulare, față de cele mai mari cantități obișnuite ale copiilor recente și față de ritmul obișnuit pe oră; o copie care a stocat din nou cea mai mare parte a datelor, ceea ce include fișierele redenumite și rescrise; dimensiunea sursei și numărul de fișiere raportate de restic pentru fiecare element și fiecare dump de bază de date; timpul de copiere al restic însuși; seriile de eșecuri și eșecurile intermitente; verificările de restaurare care nu mai trec; și spațiul liber al depozitelor locale, SFTP și rclone, proiectat din creșterea depozitului. Un element învață din primele 10 copii, în timp ce o sursă aproape goală, o rescriere a majorității datelor și eșecurile sunt verificate de la început. Sensibilitatea (Strictă, Echilibrată, Permisivă) și gravitatea minimă care trimite o notificare se stabilesc global în cardul **Anomalii** de la **Setări, Verificare** și pot fi schimbate per element în fila lui Verificare. Avertismentele se închid singure când cauza dispare; constatările critice despre date pierdute și un disc care se umple rămân până le confirmi, iar o constatare confirmată nu este ridicată din nou până când cauza a dispărut o dată. **Marchează ca așteptată** face normal un nivel nou după 10 copii, dar nu oprește niciodată verificarea sursei aproape goale, iar o selecție schimbată începe singură istoricul elementului de la zero. Cât timp o sursă este aproape goală, s-a micșorat brusc sau cea mai mare parte a datelor ei a fost stocată din nou, retenția păstrează copiile vechi ale elementului până confirmi constatarea sau o marchezi ca așteptată, iar constatarea trimite la ultima copie bună. O notificare pleacă o dată pe episod, iar eșecurile și verificările de restaurare care notifică deja nu sunt raportate de două ori. Ce nu face: depozitele S3, B2 și REST nu au o cifră de spațiu liber, pe partajarea de utilizator Unraid spațiul liber este al întregului array, iar copiile făcute înainte de restic 0.17 nu poartă istoric de dimensiuni. Elementele ZFS sunt verificate și ele, set de date cu set de date: fiecare set de date dintr-un arbore are istoricul lui, unul golit sau care nu mai putea fi citit contează ca date pierdute, și se păstrează doar copiile vechi ale acelui set de date. Cum este urmărit un element ZFS set de date cu set de date este descris la [Seturi de date ZFS](zfs-datasets.md#anomalies), iar un asistent poate citi constatările deschise prin [serverul MCP](mcp.md#tools). O constatare despre dimensiunea sau numărul de fișiere al unei surse este datată la prima copie în care a apărut, iar **Compară cu copia anterioară** listează folderele în care fișierele au dispărut, au apărut sau s-au schimbat, cu o notă când aproape tot se află într-un index de căutare, un cache sau miniaturi pe care aplicația le reconstruiește singură.
- **Pagina Anomalii.** Plăcile **Critică**, **Avertismente** și **Observații** aleg o gravitate, cu constatările deschise și închise deasupra listei. O constatare oferă întâi remedierea ei, iar detaliile arată valoarea ca o curbă peste intervalul obișnuit. Când nu e nimic deschis, un inel pe element arată cât de departe a învățat detecția ce este normal.
- **Excluderi recomandate per aplicație.** Pentru imaginile cunoscute (Plex, Jellyfin, Emby, Sonarr, Radarr, Lidarr, Readarr, Prowlarr, Immich, Nextcloud, PhotoPrism și Tautulli, de la linuxserver, hotio, binhex sau editorul oficial), asistentul de excludere din cardul **Modele de excludere** oferă folderele pe care aplicația le umple singură din nou: cache-uri, jurnale, imagini de previzualizare și postere. Fiecare intrare spune ce conține, oricare poate fi oprită, și nimic nu este exclus până apeși **Exclude selecția**.
- **Raport de eroare.** **Raport de eroare** din cardul **Ajutor** de la **Setări, Info** descarcă un ZIP redactat pentru o problemă GitHub: verificarea integrării gazdei, configurația ta cu fiecare secret eliminat, rulările recente, ce urmează în programare și jurnalul recent. Poartă și cum a mers ultimul dump al fiecărei baze de date, elementele ZFS cu montările pe care le vede containerul, anomaliile deschise și câte chei MCP există (niciodată numele lor). Parolele, tokenurile, configurația rclone, credențialele de notificare și orice parolă încorporată într-o locație de depozit sunt toate eliminate, iar pachetul spune asta în propriul manifest, pentru că un fișier de suport nu trebuie confundat niciodată cu o copie de rezervă a configurației. Cere o parolă de conectare din același motiv ca kitul de recuperare. Jurnalul pe care îl poartă este ieșirea acestui container de la ultima pornire; pentru o cădere care a repornit containerul, `docker logs` rămâne locul unde se uită.
- **Kitul de recuperare.** **Descarcă kitul de recuperare** la **Setări, Restaurare** îți dă cheia, parola restic derivată și locațiile și comenzile exacte ale depozitelor, ca să poți restaura fără un BombVault care rulează. Cere o parolă de conectare. Vezi [Off-site și recuperare](offsite-recovery.md#recovery-kit).
- **Exportă și importă setările.** Cardul **Exportă / importă setările** de la **Setări, Sistem** scrie întreaga ta configurație (setări de secțiune, destinații, programări, retenție, notificări) într-un fișier JSON portabil, așa că mutarea pe o stație nouă sau clonarea unei configurații nu înseamnă reintroducerea totul manual. Alegi dacă incluzi credențialele off-site și de notificare; cu ele, fișierul este la fel de sensibil ca kitul tău de recuperare. Importul arată o previzualizare și cere confirmare și nu îți atinge niciodată datele sau istoricul de backup.
- **Notificări.** Webhook (Discord / Slack / Gotify / ntfy), Matrix, Healthchecks.io, email (SMTP), un server [Apprise API](https://github.com/caronc/apprise-api) găzduit propriu și sistemul de notificări nativ al Unraid. Politică per copie: niciodată / la eșec / mereu. O rulare programată de multe elemente poate trimite un singur rezumat *N din M elemente reușite*. Healthchecks primește tot ciclul de viață (`/start`, apoi succes sau `/fail`) ori de câte ori este setat un URL.
- **Rezumat săptămânal.** Un mesaj pe săptămână prin aceleași canale: numărul de rulări, cât de multe date noi de copie au venit, dacă off-site este la zi și principalele eșecuri. Oprit implicit, cu cadența lui la **Setări, Notificări**, așa că și o săptămână liniștită este raportată ca atare.
- **Prometheus `/metrics`.** Opt-in (implicit oprit, token bearer opțional) în cardul **Servicii** de la **Setări, Integrări**, pentru Grafana sau Uptime Kuma. Expune starea, dimensiunile și marcajele de timp ale copiilor, fără secrete sau căi în etichete.
- **API HTTP, Home Assistant și mDNS.** Scripturile și panourile primesc un API sub `/api/v1` cu tokenuri denumite, doar în citire sau cu voie să pornească copii. Home Assistant găsește BombVault prin descoperirea MQTT, ca un dispozitiv cu senzori și, dacă permiți, câte un buton de copie pe secțiune. Iar BombVault se anunță în rețea ca `bombvault.local`. Vezi [API și integrări](api.md).
- **Spațiu liber și săptămâni până la umplere.** Depozitele locale, depozitele SFTP și destinațiile SMB sau WebDAV care îl raportează își arată spațiul liber și câte săptămâni rămân la creșterea actuală. Depozitele S3, B2 și REST spun „Dimensiune necunoscută”, pentru că acele backenduri nu o raportează.
- **Dimensiune pe foldere.** În fila Verificare a unui container, VM sau set de foldere, **Dimensiune pe dosar** arată ce foldere și fișiere ocupă spațiul în cea mai nouă copie și cât din fiecare a adus ultima copie nou sau modificat, un nivel pe rând. BombVault o citește din indexul depozitului fără să citească fișierele și o ține la zi după fiecare copie, odată ce ai deschis-o.
- **De ce a fost lentă o copie.** Cât rulează o copie, BombVault urmărește cât de ocupate sunt procesorul, discurile și rețeaua. Când o copie durează mult mai mult decât de obicei și un singur lucru a fost clar la limită, rularea o spune, de exemplu „Discul țintă disk1 a fost ocupat 98%” sau „BombVault a folosit 100% din limita de procesor a containerului său”. Altfel nu spune nimic.
- **Modificat de la ultima copie.** Un container recreat cu altă imagine, alte porturi, variabile sau volume de la ultima sa copie primește un semn lângă nume. (i)-ul lui arată ce s-a schimbat, variabilele doar după nume. Este doar o notă și dispare la următoarea copie.

## Protecție împotriva ransomware

- **Protecție la ștergere (append-only).** Pornește-o pentru o destinație off-site, ca ransomware-ul sau o gazdă compromisă să nu poată șterge sau rescrie copiile tale. Partea îndepărtată (un `restic/rest-server` în modul `--append-only`) o impune; BombVault doar o verifică și nu arată niciodată verde pe baza unei simple afirmații de configurare. Un folder de pe acest server nu poate refuza ștergerea, așa că destinațiile locale nu oferă comutatorul.
- **Test de manipulare.** BombVault dovedește periodic garanția append-only încercând efectiv o ștergere în depozitul off-site (țintită la un obiect inexistent): refuzată înseamnă protejat, acceptată înseamnă neprotejat. Un rezultat neconcludent nu schimbă niciodată verdictul stocat. **Testează acum protecția împotriva ștergerii** pe pagina unei destinații îl rulează la cerere.
- **Configurare ghidată.** **Adaugă destinație** te duce de la furnizor prin autentificare, un test de conexiune și folder până la un cuvânt sincer despre protecția la ștergere și secțiunile care se salvează acolo.
- **Exerciții DR (off-site).** Restaurarea de probă pune o țintă reală din depozitul off-site într-un sandbox izolat, o verifică fișier cu fișier și octet cu octet, apoi curăță. Vezi [Off-site și recuperare](offsite-recovery.md).
- **Stare protecție.** Cardul din prezentare verifică fiecare secțiune pentru o copie actuală, o copie off-site, protecție la ștergere acolo și o restaurare de probă de acolo. Devine verde doar pe fapte verificate.
- **Alarmă pentru bugetul de creștere.** Pentru o destinație append-only (unde copiile de rezervă vechi nu sunt niciodată curățate de aici), stabilește un buget de dimensiune și fii alertat înainte să scape de sub control.
- **Ștergerea cere o parolă.** Ștergerea copiilor de la o destinație cere o parolă de conectare și o autentificare chiar pe instanță, așa că nici un telefon împerecheat, nici o interfață deschisă nu o pot face.
- **Împerechere prin frază.** Instanțele se alătură unui grup prin douăsprezece cuvinte: creezi fraza pe una, o tastezi pe următoarea. Membrii din aceeași rețea vorbesc direct, ceilalți printr-un releu (releul proiectului, al tău sau niciunul), iar fiecare apel dintre ei este criptat end-to-end. Grupul poartă starea de protecție pe pagina Instanțe, cererile de roluri, ofertele de stocare și ce are nevoie un receptor sau un preluator odată ce rolul i-a fost permis, niciodată date de copie și niciodată APP_KEY. Vezi [Off-site și recuperare](offsite-recovery.md#pairing).
- **Instanțe și roluri.** Pornește **Instanțe** la **Setări, Instanțe, Mai multe servere** pentru o pagină cu un card pentru fiecare instanță a grupului tău, aceasta inclusiv: adresa ei, dacă este conectată și protecția fiecărei secțiuni cu ultima ei copie. Rolurile ei stau pe card ca plăci: **Receptor**, **Preluator**, **Server ZFS** și **Păstrător de cheie**. Un rol începe abia după ce cineva de pe cealaltă instanță apasă **Permite**, iar grupul se arată ca o rețea cu cine ce face pentru cine. **Verifică acum** cere unui membru să verifice depozitul unei secțiuni. Nimic de pe pagină nu poate porni o copie, o restaurare sau să șteargă ceva pe altă stație. Vezi [Instanțe și roluri](offsite-recovery.md#roles).
- **Oferte de stocare.** Un membru poate oferi propria stocare off-site altui membru prin grup. Celălalt administrator vede oferta la **Detalii** ale membrului, pe pagina Instanțe, și o acceptă sau o refuză; acceptarea creează un set obișnuit de credențiale și o destinație. Pe această cale circulă doar detalii de conexiune, niciodată date de copie.
- **Depozite primite (partea care primește).** Pe stația care primește copii off-site append-only de la alt BombVault, pornește **Receptor** la **Setări, Instanțe** și adaugă depozitul primit la **Detalii** ale membrului care trimite, doar în citire (deschis cu parola restic a instanței care trimite, care sosește prin grupul de împerechere). Vezi inventarul copiilor de rezervă grupat pe sursă, când a sosit ultima oară fiecare sursă, și poți rula un `restic check` independent pe hardware-ul care primește. Te alertează când o sursă nu mai trimite într-o fereastră stabilită de tine (un comutator de om mort) sau când o verificare de integritate eșuează. Strict doar în citire, deci nu scrie niciodată în depozitul primit, și oprit implicit. Vezi [Off-site și recuperare](offsite-recovery.md#receiver).
- **Preluare de la altă instanță (partea care preia).** Imaginea în oglindă a unei copii off-site: în loc ca această stație să-și trimită copiile de rezervă, le preia pe ale altcuiva. Pornește **Preluare** la **Setări, Instanțe**, apoi adaugă o sursă la **Detalii** ale celuilalt membru: locația depozitului lui, ce fel de copie conține și cât de des să preia. Parola lui restic vine prin grup, niciodată APP_KEY. Partea îndepărtată nu configurează nimic în plus și nu trebuie să ruleze. Depozitul sursă este doar citit: este deschis ca să se verifice parola, listat și numit drept sursă a copiei, și nu este niciodată inițializat, deblocat, curățat sau scris. Fiecare parte își păstrează propriile credențiale, iar o sursă `rclone:` este refuzată, pentru că rclone ar ajunge la ea cu remote-urile acestei instanțe. Vezi [Off-site și recuperare](offsite-recovery.md#receiver).
- **Păstrător de cheie.** O altă instanță a grupului tău poate păstra o copie sigilată a kitului de recuperare al acestui server, pe care o deschide doar codul tău de deblocare de 20 de caractere și pe care o predă doar după ce cineva de acolo apasă **Permite**. Vezi [Păstrătorul de cheie](offsite-recovery.md#key-keeper).

## Exporturi în clar

- **Export de container și de VM.** **Exportă containerul** și **Exportă VM-ul** de la **Mai mult** pe pagina unui element scriu o copie navigabilă, fără instrumente, lângă depozit: folderele de salvat ale containerului așa cum sunt chiar acum plus șablonul lui Unraid, sau imaginile de disc ale VM-ului plus definiția lui, restaurabile cu `virsh define` plus discul, fără BombVault sau restic. **Exportă** pe o copie de rezervă scrie o copie stocată la fel, ca tar, zip sau ca depozit restic propriu. restic rămâne motorul; aceasta este o copie suplimentară de conveniență.
- **Criptează exporturile simple (age).** Exporturile stau în afara restic, deci sunt implicit text simplu. Pornește **Criptează exporturile cu age** la **Setări, Sistem** și adaugă unul sau mai mulți destinatari (o cheie publică age sau o cheie publică SSH). Fiecare export (inclusiv ZIP-ul flash) este apoi sigilat pentru acei destinatari, iar îl decriptezi mai târziu în afara stației cu cheia privată corespunzătoare. Ca regulă de siguranță, cu criptarea pornită și fără niciun destinatar valid, un export eșuează cu o eroare clară în loc să scrie vreodată text simplu.
- **Și kitul de recuperare este sigilat.** Cu aceeași setare activată, kitul se descarcă drept `bombvault-recovery-kit.md.age`. Este în format ASCII armor, nu binar, așa că rămâne text lizibil: îl poți lipi în continuare într-un manager de parole sau îl poți tipări, adică exact scopul kitului. Se aplică aceeași regulă de siguranță: cu criptarea activată și niciun destinatar utilizabil, descărcarea este refuzată în loc să predea cheia principală în clar. Un lucru de făcut corect când activezi asta: ai nevoie de cheia ta privată age ca să deschizi kitul, așa că păstrează acea cheie într-un loc care nu depinde de kitul însuși.

## Asistenți IA (MCP) {#mcp}

BombVault are un server MCP încorporat, așa că un asistent precum Claude Code sau Claude Desktop poate citi starea copiilor, acoperirea, istoricul rulărilor, punctele de restaurare și activitatea curentă. Cu o cheie care permite asta, asistentul poate porni și o copie a unui element, a unei secțiuni sau a tuturor și poate anula copiile pe care le-a pornit. Restaurările, ștergerile, curățarea și setările rămân în interfața web. Fiecare client primește propria cheie la **Setări, Integrări, Server MCP**; o cheie este arătată o singură dată, stocată doar ca amprentă și poate fi redenumită, înlocuită sau revocată oricând. Pornirile sunt limitate pe oră și pe element, iar o gardă de retenție împiedică copiile asistentului să-ți împingă propriile puncte de restaurare afară dintr-o politică „păstrează ultimele N”. Fiecare rulare pornită de un asistent este marcată „via MCP” cu numele cheii. Vezi [Server MCP](mcp.md). Dumpurile bazelor de date și [seturile de date ZFS](zfs-datasets.md) se numără printre elementele și punctele de restaurare pe care le citește, și poate lista anomaliile observate de BombVault.

## Aplicații și însoțitori {#apps}

- **Aplicația Android.** Toate serverele grupului tău pe telefon, cu jurnalul de activitate al tuturor pe un singur ecran. Se împerechează cu grupul tău prin cod QR și deschide fiecare server deja autentificat, cu o sesiune care ajunge doar la ce arată aplicația. Vezi [Aplicația Android](android.md).
- **Server receptor.** Stația care primește copii off-site rulează un rest-server append-only, configurat prima dată când permite o cerere **Receptor**, și îl oferă celorlalte instanțe ale grupului tău, fiecare cu o autentificare proprie. Vezi [Server receptor](offsite-recovery.md#receiving-server).
- **Setări, Aplicații.** O pagină care începe cu aplicația Android, cu APK-ul pentru versiunea pe care o rulează serverul și un cod QR pentru el, urmată de un card pentru fiecare însoțitor. Cardul ParleyPort oferă șablonul său Unraid, copiază comanda Docker care îl pornește și duce la depozitul său și la setările releului de la Împerechere. Cardul BombVault Widget oferă șablonul și depozitul său și instalează sau elimină pluginul prin conexiunea SSH la gazdă.
- **BombVault Widget.** O dală pe Dashboard-ul Unraid cu jurnalul de activitate al BombVault și următoarea rulare programată. Fără o conexiune SSH la gazdă, cardul îți dă adresa `.plg` de instalat la **Plugins, Install Plugin**, iar pluginul poate fi eliminat de acolo ca oricare altul.
- **Jurnal de activitate încorporabil.** Generează un token doar în citire în cardul **Widget pentru dashboard** de la **Setări, Integrări** și primești o adresă pentru orice panou care arată un iframe, precum Homepage, Organizr sau Heimdall: o pagină mică cu doar jurnalul de activitate în direct. Tokenul oferă acel jurnal și nimic altceva, iar **Dezactivează** îl revocă pe loc. Pagina încorporată este doar în engleză.

## Altele

- **Oprește o copie în curs.** Cât timp o rulare este activă, **Anulează copia** stă lângă progresul ei. Rularea este înregistrată ca *anulată*, nu eșuată. Oprirea este sigură, pentru că restic își scrie instantaneul ultimul, așa că o rulare întreruptă lasă date nereferențiate și niciun instantaneu.
- **Salvează mai multe deodată.** Alege elemente în lista Copii de rezervă și salvează selecția. Lotul rulează pe server, deci continuă chiar dacă închizi fila sau pierzi conexiunea. BombVault nu își salvează niciodată (și deci nu își oprește) propriul container.
- **Copii de rezervă pe pagina elementului** cu o listă de puncte de restaurare, ștergere per copie de rezervă, o etichetă a ta și o comparație între două copii de rezervă.
- **Întreținerea depozitului per secțiune** în cardul **Verifică copiile de rezervă** de la **Setări, Verificare**: o verificare (`restic check`) și, la **Mai mult**, **Deblochează** (șterge un lock rămas) și **Curăță** (aplică la cerere politica de retenție când există una, altfel doar recuperează spațiu).
- **Progres pentru verificări, verificări de restaurare și curățare.** Cât timp rulează una dintre ele, jurnalul de activitate și cardul **Verifică copiile de rezervă** arată cât a numărat restic, de exemplu *12 din 47 de pachete*, cu timpul rămas în acel pas odată ce există destule date ca să fie estimat. restic numără aici pachete, instantanee și fișiere de index, nu octeți, așa că asta arată bara; înainte de prima numărătoare rulează fără număr.
- **Dumpuri automate ale bazelor de date.** Containerele PostgreSQL, MySQL și MariaDB recunoscute (imaginile oficiale, PostGIS, TimescaleDB, pgvector, pgautoupgrade, imaginile de bază de date ale Immich, MariaDB de la linuxserver, yobasystems și jc21 și mysql-server de la Oracle) sunt dumpate înaintea fiecărei copii, de pe serverul care rulează. Containerele care doar seamănă cu o bază de date primesc aceeași opțiune în cardul **Bază de date** din fila lor Setări, oprită până o alegi. Dumpul curge direct în depozit ca punct de restaurare propriu, lângă copia fișierelor, și nu este scris niciodată pe disc. Credențialele vin din variabilele proprii ale containerului, inclusiv secretele `*_FILE`, și nu îl părăsesc niciodată. Cardul arată dacă folderul de date al bazei de date este salvat oprit, copiat în execuție sau deloc salvat. Un dump eșuat nu face să eșueze copia: apare ca o rulare eșuată cu motivul ei și un indiciu cum se repară, și trimite o notificare. Dumpurile nu sunt reîncărcate niciodată automat. Descarcă unul (simplu sau comprimat), salvează-l într-un folder, importă-l cu un clic într-o bază de date nou pornită sau adu-l cu CLI-ul restic. Oprește-l per container cu eticheta `bombvault.dbdump=false` sau pentru toate containerele cu **Copii SQL automate ale bazelor de date** la **Setări, General**. Detecția anomaliilor urmărește și dimensiunea fiecărui dump, iar un asistent poate lista dumpurile unui container prin [serverul MCP](mcp.md#tools).
- **Comenzi înainte și după, per container.** Comenzi shell rulate în container (de exemplu golirea unui cache); o comandă care eșuează înainte de copie o oprește. Bazele de date recunoscute sunt dumpate automat, deci nu au nevoie de comandă.
- **Oprește alte containere în timpul copiei, cu repornire condiționată de sănătate.** Numește containerele dependente (de exemplu o bază de date) la **Oprește alte containere** ca să fie oprite cât timp acesta este salvat. După aceea BombVault le readuce în ordinea `depends_on` din Compose și, implicit, așteaptă ca fiecare să raporteze sănătos (sau pornit, dacă nu are verificare de sănătate) înainte să pornească containerele care depind de el, astfel încât o dependență precum Pi-hole, o bază de date sau un gateway VPN să fie cu adevărat sus înaintea serviciilor care au nevoie de ea, în loc ca acelea să revină cu *connection refused*. Așteptarea este limitată de un timeout per container (implicit 120 de secunde), ca un container lent sau niciodată sănătos să nu poată bloca rularea; atât așteptarea, cât și timeout-ul se află la **Repornire după backup** în cardul **Ordine** de la **Setări, Programare** (oprește așteptarea pentru o repornire simultană). Aceeași repornire ordonată și condiționată de sănătate învelește și actualizarea imaginii de după copie, așa că într-o zi în care sosește o actualizare dependentele sunt ținute oprite pe toată durata recreării și aduse înapoi, condiționat de sănătate, abia când s-a terminat.
- **Tipare de excludere per container.** Listează subdirectoare de sărit în interiorul unui volum salvat, câte unul pe linie. Scrie căile așa cum le vezi în interiorul containerului; o previzualizare live arată la ce se rezolvă fiecare linie și avertizează când o linie nu ar exclude nimic.
- **Actualizează după o copie reușită (oprit implicit).** Pornește **Actualizează containerele după o copie de rezervă reușită** la **Setări, Programare, Actualizări după backup** sau setează altfel un singur container pe pagina lui, iar BombVault trage cea mai nouă imagine și recreează containerul, dar doar când există efectiv o imagine mai nouă, ca să existe întâi un punct de restaurare proaspăt. Extra opționale: o notificare per container actualizat și **Elimină imaginea veche după o actualizare** (o imagine de bază folosită de alte containere nu este niciodată ștearsă). După actualizare BombVault cere și Unraid să reverifice starea de actualizare a acelui container, astfel încât bannerul învechit *update available* din fila Docker să se șteargă singur în loc să rămână (actualizările Unraid trec direct prin API-ul Docker, așa că starea lui din cache și, pe unele versiuni, un digest din cache ar continua altfel să arate bannerul). Este best-effort, nu afectează niciodată copia, este pornit implicit și se comută cu **Reîmprospătează starea actualizărilor Unraid după actualizarea unui container** în același card.
- **Restaurare într-un folder alternativ** pentru clonare sau inspecție.
- **Ce este nou după o actualizare.** Notele de lansare apar o dată pe versiune nouă, servite din note încorporate în binar, deci fereastra funcționează offline. Punctele verzi marchează fiecare schimbare pe pagina ei, iar **Noutăți** din cardul Versiune de la **Setări, Info** deschide lista cu toate, fiecare cu **Mergi acolo**.
- **Info.** **Setări, Info** conține **Versiune** (BombVault, GlimStone, restic și rclone, cu **Caută actualizări**), **Ajutor** cu **Manual** și **Raport de eroare**, **Noutăți** și **Despre BombVault**.
- **HTTPS din start** (auto-semnat sau adu-ți propriul certificat în spatele unui reverse proxy).
- **Healthcheck Docker.** Containerul raportează sănătos/nesănătos din propriul `/api/health`, astfel încât un instrument de auto-vindecare îl poate reporni dacă motorul se blochează vreodată.
- **42 de limbi** cu un selector cu steaguri la **Setări, Aspect**.
- **Setările se salvează singure.** Mută un comutator sau părăsește un câmp și schimbarea este scrisă imediat, cu o scurtă licărire pe control și un tremur dacă serverul o refuză. Câteva locuri păstrează un buton Salvează pentru că salvarea lor pe jumătate ar fi nesigură, de exemplu caseta cu configurația rclone, editorul setului de credențiale și parola de conectare.
- **Notificări liniștite.** La **Setări, Aspect** poți reduce la tăcere confirmările de rutină, astfel încât doar eșecurile să te mai întrerupă. Asta nu atinge canalele de notificare.
- **Fă-l să arate cum vrei.** **Setări, Aspect** stabilește **Tema** (Întunecată, Luminoasă sau a sistemului), culorile (un accent sau *Mod curcubeu* cu o paletă de opt), colțurile (rotunde, moi sau pătrate), animația (oprită, discretă, sălbatică sau furtună) și ordinea plăcilor de setări. BombVault păstrează aspectul pe server, iar un browser care vine prima dată îl preia. Când sistemul tău cere mai puțină mișcare, aceasta câștigă mereu.
