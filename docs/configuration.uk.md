# Конфігурація

Ця сторінка охоплює змінні середовища контейнера, монтування, які дає шаблон, модель безпеки, копіювання віртуальних машин через SSH та налаштування зовнішніх копій. Куди йдуть копії, налаштовується всередині застосунку як **місця призначення**, а не через змінні середовища.

## Змінні середовища {#environment-variables}

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `APP_KEY` | **Так** | Секрет із 32 байтів у шістнадцятковому записі (64 шістнадцяткові символи), з якого виводиться пароль репозиторію restic. Згенеруйте командою `openssl rand -hex 32`. Зберігайте його в надійному місці: втрата робить зашифровані копії невідновлюваними. |
| `LIBVIRT_HOST` | Для віртуальних машин і наборів даних ZFS | Хост Unraid, до якого звертаються через SSH для копій віртуальних машин і наборів даних ZFS (поле шаблону **Host SSH: Address**, типово `host.docker.internal`). Шаблон підставляє заглушку `192.168.x.x`, яка вважається незаданою. Використовуйте IP вашого Unraid у локальній мережі, він обов'язковий у користувацькій мережі `br0.x`. Коли `host.docker.internal` не розв'язується, як у застосунку TrueNAS, і `LIBVIRT_URI` теж не називає хост, BombVault використовує шлюз контейнера за замовчуванням, і журнал завантаження його називає. |
| `LIBVIRT_SSH_PORT` | Ні | Порт SSH хоста для копій віртуальних машин і наборів даних ZFS (поле шаблону **Host SSH: Port**, типово `22`). |
| `LIBVIRT_SSH_USER` | Ні | Користувач SSH на хості для копій віртуальних машин і наборів даних ZFS (поле шаблону **Host SSH: User**, типово `root`). |
| `LIBVIRT_URI` | Ні | Повний URI підключення до libvirt, що використовується **як є** замість побудови з трьох змінних `LIBVIRT_*` вище (які тоді ігноруються для рядка підключення). Типово не задано. Потрібен на TrueNAS Scale, чий libvirtd слухає нестандартний сокет, який форма складеного рядка виразити не може: `qemu+ssh://<user>@<truenas-host>/system?socket=/run/truenas_libvirt/libvirt-sock`. Див. [посібник із копіювання віртуальних машин](vm-backup-ssh-setup.md#truenas-scale). Якщо це URI `qemu+ssh://`, кожна зі змінних `LIBVIRT_HOST`, `LIBVIRT_SSH_USER` і `LIBVIRT_SSH_PORT`, яка не задана, береться з нього, зокрема й для власних команд SSH BombVault (перенесення NVRAM, набори даних ZFS). |
| `PORT` | Ні | Порт HTTP (типово `3000`. Використовується лише з `HTTP_ONLY=true`). |
| `HTTPS_PORT` | Ні | Порт HTTPS (типово `3443`. Шаблон публікує його один до одного, тож вебінтерфейс відповідає на `https://<ip>:3443`). |
| `HTTP_ONLY` | Ні | Задайте `true`, щоб вимкнути самопідписаний слухач HTTPS і віддавати лише звичайний HTTP (для роботи за зворотним проксі, який завершує TLS). |
| `BIND_HOST` | Ні | Адреса, на якій слухає вебінтерфейс (типово `0.0.0.0`, усі інтерфейси). У контейнері залиште її незаданою, бо опублікованим портам потрібні всі інтерфейси. `127.0.0.1` підходить для запуску поза Docker. Перевірка працездатності питає ту саму адресу. |
| `TRUSTED_PROXY` | Ні | Адреси або діапазони CIDR зворотного проксі перед BombVault через кому (наприклад `192.168.20.11` або `10.0.0.0/8`). Лише від цих вузлів `X-Forwarded-For` приймається на віру, а обмежувач входу тоді рахує невдачі за справжнім клієнтом, а не звалює всіх, хто за проксі, в один кошик. Якщо не задано (типово), не довіряється нікому: заголовок, який приймається безумовно, дозволив би будь-кому, хто викликає, вибрати свій кошик. |
| `HOST_SOURCE_ROOT` | Ні | Шлях хоста, підключений як **Host Data** (типово `/mnt`). BombVault перекладає джерела bind-монтувань, про які повідомляє Docker, у шляхи всередині цього монтування. Змінюйте, лише якщо ви підключили інший корінь хоста. |
| `HOST_MOUNT_ROOT` | Ні | Де Host Data змонтовано всередині контейнера (типово `/host/user`). У TrueNAS Host Data монтується за власним шляхом хоста, тому і ця змінна, і `HOST_SOURCE_ROOT` називають цей шлях, наприклад `/mnt/tank` (див. [TrueNAS SCALE](getting-started.md#truenas)). |
| `DATA_ROOT_SEGMENTS` | Ні | Назви сегментів шляху через кому, за якими джерело bind-монтування вважається даними для копіювання (типово `appdata`, за угодою Unraid `/mnt/user/appdata/<container>`). Bind-монтування контейнера вибирається для копіювання автоматично, коли БУДЬ-ЯКИЙ перелічений сегмент зустрічається як цілий сегмент шляху його джерела на хості. Наприклад, `DATA_ROOT_SEGMENTS=appdata,config` підхоплює і bind `.../config`. Зіставлення не враховує регістр, тож значення за замовчуванням охоплює й `/DATA/AppData/<container>` у ZimaOS. Інші, завжди ввімкнені способи знайти папку даних контейнера див. у розділі [Визначення джерела копії](#backup-source-detection). |
| `PLATFORM` | Ні | Примусово задає, на якій платформі BombVault вважає себе працюючим, замість автовизначення: `unraid`, `generic` або `truenas` (типово не задано: Unraid визначається за маркером `dockerMan` у точці монтування флешки, інакше `generic`. Нерозпізнане значення теж зводиться до `generic` із записом у журнал). Задавайте явно на звичайному хості Docker або TrueNAS Scale, а не покладайтеся на автоперевірку лише для Unraid. Загальний файл compose робить це. Змінює угоду запасного варіанта для appdata, значення за замовчуванням для цілей відновлення між екземплярами та те, чи пробуються взагалі кроки сповіщень і супутніх плагінів лише для Unraid (див. `internal/platform`). |
| `BOMBVAULT_SELF_CONTAINER` | Ні | Ім'я самого контейнера BombVault, щоб він ніколи не копіював (і тим самим не зупиняв) сам себе. |
| `BACKUP_MAX_HOURS` | Ні | Максимум годин реального часу, протягом яких один запуск копіювання може тримати блокування свого розділу, перш ніж його примусово скасують (захист, щоб застряглий запуск не заблокував розділ назавжди). Якщо порожньо (типово), використовується `48`. Збільште для дуже великих чи повільних хмарних копій (запуск, скасований за межею, завершується помилкою `context deadline exceeded`). Задайте `0`, щоб повністю вимкнути межу. Очищення підпорядковується тій самій межі, а перевірка чи очищення йде, поки restic продовжує повідомляти про хід. |
| `BACKUP_STALL_HOURS` | Ні | Скільки годин копія може **взагалі не просуватися**, перш ніж її скасують. Якщо порожньо (типово), використовується `2`. Задайте `0`, щоб ніколи не скасовувати через застій. Це тонший із двох захистів, і зазвичай спрацьовує саме він: він стежить, чи відбувається щось, а не скільки часу забрав запуск, тож повільна, але здорова копія на кілька терабайтів лишається в спокої, а застрягла на спільному ресурсі, що не відповідає, зупиняється за години, а не за дні. Попередження пишеться в журнал після 30 хвилин тиші, перш ніж щось скасовується. Сканування вважається просуванням: restic не пише байти, поки обходить велике дерево, і цю фазу відстежують за підсумками файлів і байтів, а не за записаними байтами. Ці дві змінні незалежні, а `BACKUP_MAX_HOURS` і далі обмежує фази після самої копії (зберігання, статистика, зовнішня копія), де немає лічильників для спостереження. |
| `DB_DUMP_MAX_HOURS` | Ні | Скільки годин може йти один автоматичний дамп бази даних, перш ніж його зупинять. Якщо порожньо (типово), використовується `6`. Допустимі значення від `1` до `48`, а межа тримається на годину нижче за `BACKUP_MAX_HOURS` (на половині від нього, якщо той менший за дві години), тож довгий дамп обривається за власною межею і так і повідомляється, а не тягне за собою копію. Дамп, який не просувається, зупиняється раніше, через `BACKUP_STALL_HOURS`. Зупинений дамп завершується помилкою сам по собі, а копія контейнера триває. В Unraid додайте її до контейнера BombVault через **Add another Path, Port, Variable**. |
| `TZ` | Ні | Часовий пояс для планувальника (наприклад `Europe/Berlin`). **Якщо залишити незаданим, кожен розклад іде за UTC**: заданий на 02:30 тоді спрацює о 02:30 UTC, а не за вашим настінним годинником. В Unraid ви самі його ніколи не задаєте: система передає свій часовий пояс у кожен контейнер. Журнал завантаження каже, який пояс визначився. Пояс із переходом на літній час пропускає один запуск навесні й виконує один двічі восени, а UTC не робить ні того, ні іншого, але двічі на рік розходиться з вашим годинником на годину. |
| `DATA_DIR` | Ні | Де BombVault зберігає свою базу даних, ключі та кеші (типово `/config`). У контейнері не чіпайте. Важливо під час запуску бінарного файла поза Docker. |
| `FLASH_DIR`, `FLASH_TEMPLATES_DIR` | Ні | Де флешка та її шаблони Docker змонтовано всередині контейнера (типово `/host/boot` і `/host/boot/config/plugins/dockerMan/templates-user`). Вони слідують монтуванню `/boot` шаблону, тому залиште їх незаданими. |

## Монтування {#mounts}

Підключіть сокет Docker, флешку (`/boot`) і корінь **Host Data** (`/mnt`), як показано в шаблоні CA. І *джерела*, і *призначення* копій лежать усередині Host Data, і він монтується як **slave**, щоб віддалений спільний ресурс, який монтується після запуску контейнера (наприклад у `/mnt/remotes`), став видимий без перезапуску.

У TrueNAS Host Data — це шлях набору даних на кшталт `/mnt/tank`, але ніколи не ixVolume. Дані, які застосунок зберігає в ixVolume, лежать поза ним і не копіюються. Див. [TrueNAS SCALE](getting-started.md#truenas).

Копіям наборів даних ZFS теж потрібен цей режим: хост монтує знімок набору даних лише після запуску контейнера. Див. [Набори даних ZFS](zfs-datasets.md).

Локальні репозиторії типово лежать у `/mnt/user/bombvault/{container,vms,flash,config,files,zfs}` і створюються під час першої копії. Це **власні теки** розділів, і разом вони утворюють місце призначення **Локально**. На його сторінці в **Місця призначення** картка **Підключення** змінює папку кожного розділу.

Власна тека розділу може лежати й в уже наявному у вас місці призначення, наприклад NAS або бакеті S3: **Використати як власну теку** на сторінці цього місця переносить її туди й спершу каже, що станеться з уже зробленими копіями. Див. [Власна тека розділу](offsite-recovery.md#own-folder).

Папки локальних репозиторіїв лишаються з режимами `0755` і `0644`, щоб користувач синхронізації без прав root через SMB не був замкнений ззовні, а репозиторії зашифровані, тож це нічого не розкриває. Визначення для відновлення лежать усередині кожного репозиторію, тому скопійована папка повна сама по собі. Репозиторій автобекапу лишається читабельним лише для root.

!!! note "Перевірка інтеграції з хостом"
    Картка **Інтеграція з хостом** в огляді (додайте її через **Налаштувати**) перевіряє кожне монтування й кожну утиліту командного рядка (сокет Docker, libvirt, restic, qemu-img, rclone) і повідомляє, чого бракує.

## Визначення джерела копії {#backup-source-detection}

Для кожного контейнера BombVault автоматично вибирає, які bind-монтування та іменовані томи копіювати. Шлях підхоплюється, коли виконується будь-яка з таких умов (результат завжди можна перевизначити в картці **Папки для резервного копіювання** на вкладці контейнера «Налаштування»):

- **Збіг із сегментом кореня даних:** джерело bind-монтування на хості містить один із сегментів `DATA_ROOT_SEGMENTS` як цілу частину шляху (типово лише `appdata`).
- **Іменовані томи Docker** включаються завжди, бо в них немає одноразового аналога й фільтрувати нічого, **але лише коли реальний шлях зберігання тома на хості сам досяжний через монтування Host Data**, як і будь-який інший шлях хоста, який копіює BombVault. Драйвер локальних томів Docker за замовчуванням зберігає том у власному корені даних демона (`/var/lib/docker/volumes/<name>/_data`, якщо ви не змінювали. Перевірте командою `docker info -f '{{.DockerRootDir}}'`), який не охоплюється вузьким монтуванням Host Data з одного каталогу, що його загальний `docker-compose.yml` використовує типово. Недосяжний том мовчки пропускається, це не помилка. Щоб насправді копіювати іменовані томи на звичайному хості, спрямуйте Host Data (і `HOST_SOURCE_ROOT`) на спільного предка, який охоплює й корінь даних Docker. Коментар про Host Data у файлі compose пояснює компроміс (Unraid обходить це, монтуючи весь `/mnt`, свою універсальну угоду верхнього рівня, з тієї самої причини).
- **Каталог проєкту Docker Compose:** якщо в контейнера є стандартна мітка `com.docker.compose.project.working_dir` (її ставить `docker compose up` автоматично), цей каталог теж додається, незалежно від того, чи збігся якийсь bind із сегментом кореня даних.
- **Перевизначення міткою `bombvault.data`:** задайте мітку `bombvault.data=true` на контейнері, щоб включити всі його bind-монтування, для розкладки, яку не ловить жодна з угод вище (наприклад єдиний bind `/srv/plex/config` без проєкту Compose). Будь-яке непорожнє значення, окрім `false`, вважається істинним. Відсутня мітка або `bombvault.data=false` нічого не змінюють.
- **Мітка `bombvault.dbdump`:** задайте `bombvault.dbdump=false` на контейнері, щоб вимкнути його автоматичний дамп бази даних (`0`, `no` і `off` роблять те саме), або назвіть рушій (`postgres`, `mysql`, `mariadb`), щоб робити дамп контейнера, який BombVault сам не розпізнає. Мітка важливіша за перемикач у картці **База даних** на вкладці контейнера «Налаштування», і в Unraid робити потрібно саме так.

## Модель безпеки {#security-model}

!!! warning "Керування хостом на рівні root"
    Через сокет Docker BombVault може зупиняти, видаляти та перестворювати контейнери й читати та записувати appdata, а для копій віртуальних машин він входить на хост через SSH (`qemu+ssh://`, типово root), щоб запускати `virsh`. Будь-хто, хто може достукатися до його вебінтерфейсу, фактично отримує root на хості.

### Вхід {#login}

- **Необов'язковий захист паролем** (картка **Пароль** в **Налаштування, Безпека**): задайте пароль, щоб вимагати вхід, очистіть його, щоб вимкнути. Типово вимкнено для використання в довіреній локальній мережі. Пароль зберігається з Argon2id поверх перцю, прив'язаного до `APP_KEY`, тож скопійований `/config` марний без ключа і повільно ламається навіть із ним. Новому паролю потрібно щонайменше 12 символів. Наявний коротший продовжує працювати, поки його не змінять. Сеанси підписані (HMAC, виведений із `APP_KEY`), і зміна пароля робить їх недійсними. Входи обмежено п'ятьма невдачами на хвилину на клієнта. Щоб змінити чи прибрати пароль, потрібен **Поточний пароль** і, якщо ввімкнено двофакторну автентифікацію, код.
- **Дещо вимагає пароля.** Завантаження набору для відновлення, звіту про помилку та ZIP копії флешки, експорт копії флешки чи автобекапу, передача ключа зберігачу ключа, дозвіл видати переданий на зберігання ключ, створення нового коду відновлення, видалення копій у місці призначення, експорт налаштувань з обліковими даними, двофакторна автентифікація та ключі доступу відхиляються, поки не задано пароль для входу, і для них потрібен вхід на самому екземплярі.
- **Місце призначення не показує пароль.** Місце призначення може містити облікові дані, як у `rest:https://user:password@host/repo`, і кожна сторінка та кожна відповідь API показують його як `rest:https://[redacted]@host/repo`, з паролем для входу або без нього. Якщо змінити шлях за ним, збережений пароль лишається. Щоб спрямувати місце призначення на інший сервер, введіть його повністю разом із паролем, бо прихований пароль лишається зі своїм сервером.
- **Двофакторна автентифікація** (**Налаштування, Безпека**): часовий код із застосунку-автентифікатора поверх пароля плюс вісім одноразових кодів відновлення, які видаються один раз під час її ввімкнення. Спільний секрет зберігається зашифрованим через `APP_KEY`, а щоб знову вимкнути фактор, потрібен чинний код.
- **Ключі доступу** (WebAuthn) стоять на своїй картці, щойно задано пароль, поруч із паролем і ніколи не замість нього, тож видалення всіх ключів доступу нікого не замикає ззовні. Їм потрібні справжнє доменне ім'я та сертифікат, якому довіряє браузер. Типова адреса `https://<ip>:3443` — саме те, що WebAuthn відхиляє, і картка так і каже, а не пропонує кнопку, яка не спрацює. За ввімкненої двофакторної автентифікації ключ доступу має перевірити ваш PIN, відбиток пальця чи обличчя, інакше вхід просить ще й код.
- **Відновлення конфігурації** (**Повернути налаштування** в аварійному майстрі) завершує всі сеанси, видаляє всі ключі доступу й відкликає всі токени API та ключі MCP, бо відновлені налаштування могли б повернути ті, що були видалені після їх збереження. Увійдіть із паролем і налаштуйте ключі доступу заново в **Налаштування, Безпека**.
- **Забутий пароль** скидається на сторінці входу. **Забули пароль?** змушує BombVault записати код із 12 символів, трьома групами по чотири, у журнал свого контейнера (в Unraid: вкладка Docker, значок BombVault, **Журнали**). Цей код і новий пароль вас упускають. Скидання також вимикає двофакторну автентифікацію, видаляє всі ключі доступу, відкликає всі токени API, ключі MCP та входи OAuth, завершує всі інші сеанси, виводить із сеансу всі спарені телефони й вимикає спарювання телефонів. Сторінка після цього перелічує, що зникло. Код діє 10 хвилин, а хибні спроби його не витрачають. Токени віджета й метрик лишаються, бо вони лише читають.
- **Скинути пароль може будь-хто, хто може читати журнал контейнера.** Це root на хості, але також переглядач журналів на кшталт Dozzle, будь-який контейнер з доступом до сокета Docker (достатньо лише читання) і відправник журналів, що пересилає вивід контейнерів. Давайте це лише тим, кому довірили б і сам пароль. Той, хто сягає лише вебінтерфейсу, код ніколи не бачить.

### Телефони та учасники групи {#phones-and-members}

- **Спарені телефони сягають списку дозволеного.** Телефон, який знає дванадцять слів групи, входить без пароля, поки ввімкнено **Телефони можна спарювати за дванадцятьма словами групи** в картці **Застосунок для Android** в **Налаштування, Безпека**. Його сеанс сягає лише того, що показує застосунок: огляд, запуски, копії для перегляду, запуску й відновлення, аномалії для читання та сторінка «Екземпляри» для перегляду. Місця призначення й команди доходять до нього з видаленими адресами та секретами, а відновлення, яке замінює оригінал, спершу копіює поточний стан. Відновлення в папку приймає лише нову або порожню папку всередині папки відновлення, а зазирнути в іншу папку телефон не може. На все інше сервер відповідає, що потрібен вхід на самому екземплярі: ключі, набір для відновлення, передача ключів на зберігання, налаштування, видалення копій. Скидання пароля вимикає спарювання телефонів, поки ви не ввімкнете його знову. Телефон, видалений зі сторінки «Екземпляри» або з вимкненим **Опитувати цей екземпляр** в його подробицях, одразу втрачає сеанс, а видалений телефон, який знову відкриває свій застосунок, повертається вимкненим.
- **Поза домом телефон відкриває сторінки через реле.** Кожен запит сторінки запечатується ключем групи, який реле не може ні прочитати, ні змінити, і підписується власним ключем телефона, який сервер закріпив, коли вперше спитав телефон. Сервер виконує запит один раз і лише поки він свіжий. Він відповідає лише телефону, перерахованому на сторінці «Екземпляри», поки спарювання телефонів увімкнено, і лише сеансом, який сам дав цьому телефону, тож вихід усюди й скидання пароля завершують і ці сторінки. Сервер підписує кожну відповідь, а застосунок перевіряє підпис за ключем, який закріпив для цього сервера, і попереджає, коли ключ змінюється. Така сторінка сягає того самого списку дозволеного, що й спарений телефон, з паролем для входу або без нього, плюс стану входу, який сторінка читає першим. Вхід і вихід, скидання пароля та завантаження лишаються на власній адресі сервера, а одна відповідь обмежена 16 МБ.
- **Учасники підписують те, про що просять.** Запити ролей і відповіді на них, пропозиції сховища, видача пароля restic приймачу чи стягувачу, входи приймача та передача ключів на зберігання підписуються ключем кожного учасника, який екземпляр закріплює, коли вперше бачить цього учасника. Виклик, підписаний іншим ключем, відхиляється. **Забути ключ** в подробицях екземпляра скидає закріплений ключ на випадок, якщо відомий тут не власний ключ учасника. Ключ в учасника запитується знову під час його наступного підписаного виклику. Учасники на BombVault 9.x не підписують, і будь-хто, хто знає слова, може видати себе за них, як у 9.9. Запит ролі або пропозиція сховища від учасника на версії 10.4 чи старішій відхиляється, поки цей учасник не оновиться.
- **Дванадцять слів — це пароль.** Будь-хто, хто їх знає, вступає до групи, бачить стан захисту учасників і може запитувати ролі, які людина на іншому екземплярі все ж має дозволити. Без пароля для входу будь-хто, хто може відкрити вебінтерфейс, може їх прочитати, і картка спарювання про це пише, поки пароль не задано.

### Ключі {#keys}

- **APP_KEY робить дві речі.** Він запечатує те, що зберігає ця установка (паролі, облікові дані, токени), і він же ключ копій: з нього виводиться пароль restic, і ним запечатані визначення контейнерів та віртуальних машин.
- **Узятий ключ зберігається окремо.** Коли аварійний майстер бере копії іншого сервера, ця установка продовжує запечатувати своїм APP_KEY, а ключ іншого сервера зберігає як свій **ключ копій**, запечатаний як будь-який інший секрет. Набір для відновлення тоді друкує обидва. Якщо APP_KEY потім змінити, ключ копій більше не відкриється: BombVault припиняє копіювання й повідомляє про це в **Потребує уваги**, а не пише неправильним ключем. Завантажте набір для відновлення заново в **Відновлення, Аварія** або поверніть APP_KEY. Див. [Аварійний майстер](offsite-recovery.md#emergency).
- **Шифрування** типово ввімкнено (**Шифрувати копії** в картці **Шифрування** в **Налаштування, Безпека**). Копії шифрує restic із паролем, виведеним з ключа копій.
- **Передача ключів на зберігання.** Зберігач ключа у вашій групі тримає запечатану копію набору для відновлення цього сервера, яку сам відкрити не може. Відкриває її лише код відновлення з 20 символів, і зберігач видає її, лише коли хтось у нього натисне **Дозволити**. Див. [Зберігач ключа](offsite-recovery.md#key-keeper).

### Мережа {#network}

- **Зміни вимагають JSON.** Запит, який щось змінює, має надсилати `Content-Type: application/json` і не повинен бути позначений браузером як міжсайтовий, тож сторінка на іншому сайті не може змусити ваш браузер змінювати налаштування за адресою в локальній мережі. Скрипт, який керує API, надсилає цей заголовок. Усе інше відхиляється з `415`.
- Оскільки захист вмикається за бажанням, поки його не задано, увесь інтерфейс і API (зокрема місця призначення, маршрути тесту на підробку та маршрути відновлення) доступні кожному, хто сягає порту. Задайте пароль для входу, щойно використовуються зовнішні копії append-only або шифрування.
- Запускайте BombVault лише в довіреній мережі, недоступній ззовні. Для віддаленого доступу поставте його за зворотний проксі, який додає автентифікацію та TLS. Відповіді несуть базові заголовки безпеки (CSP, `nosniff`, `X-Frame-Options`, `Referrer-Policy`).
- За зворотним проксі кожен запит несе адресу проксі, тому без `TRUSTED_PROXY` обмежувач входу рахує всіх клієнтів в одному кошику, і невдачі зловмисника блокують і вас. Назвіть проксі в `TRUSTED_PROXY`, щоб повернути підрахунок за клієнтами.
- Зворотний проксі перед BombVault має пропускати заголовок `Authorization` або `X-API-Key` до `/mcp` і не повинен буферизувати його відповіді, інакше помічники не зможуть підключитися. Див. [Сервер MCP](mcp.md#tls).
- Кінцева точка MCP `/mcp` відповідає `404`, поки не з'явиться ключ або не ввімкнено вхід через OAuth, і просить у кожного клієнта ключ або токен навіть за вимкненого пароля для входу. Жодна адреса не виключена, навіть `localhost`. У ній немає інструментів відновлення й видалення, а відновлення копії конфігурації відкликає всі ключі. Див. [Сервер MCP](mcp.md#security).
- З `HTTP_ONLY=true` cookie сеансу втрачає прапорець `Secure` (інакше за звичайним HTTP вона б не працювала), тому вмикайте пароль за проксі, що завершує TLS, лише якщо важлива конфіденційність.
- SSH-з'єднання для копій віртуальних машин довіряє ключу хоста під час першого підключення (TOFU) і потім закріплює його. Перевірте ключ хоста іншим шляхом, якщо шлях від контейнера до хоста не довірений.
- **Посилання не виводять за межі монтування.** Копія або відновлення на місці зупиняється з повідомленням, якщо посилання вище його шляху веде за межі монтування хоста, бо контейнер, який пише у власний спільний ресурс, міг би його підкинути. Місце призначення, у якого хост або remote rclone починається з дефіса, відхиляється так само, під час збереження й під час наступного запуску, бо `ssh` або `rclone` прочитали б його як параметр.

## Сервер MCP {#mcp-server}

Серверу MCP не потрібна змінна середовища. Ви вмикаєте його, створивши ключ у **Налаштування, Інтеграції, Сервер MCP**, і він відповідає за адресою `/mcp` на тому самому порту, що й вебінтерфейс (наприклад `https://192.168.1.10:3443/mcp`). Без активного ключа цей шлях відповідає `404`. Клієнти, сертифікати й обмеження описано на сторінці [Сервер MCP](mcp.md).

## Копіювання віртуальних машин через SSH {#vm-backup-over-ssh}

BombVault копіює віртуальні машини KVM/libvirt **без монтування будь-якого шляху libvirt**. Він запускає `virsh` на хості через SSH (`qemu+ssh://`), тому ніколи не може вплинути на VM Manager вашого хоста.

Монтувати сокет libvirt хоста в контейнер в Unraid крихко: ці шляхи належать VM Manager, а перемикання «Enable VMs» може залишити libvirt нездатним запуститися. Ключ SSH дає root на хості, той самий рівень довіри, що й сокет Docker, який BombVault уже використовує.

Швидке налаштування:

1. **Налаштування, Інтеграції, SSH хоста:** скопіюйте показаний відкритий ключ.
2. Додайте його до `/root/.ssh/authorized_keys` в Unraid (також зберігається на флешку, щоб пережити перезавантаження).
3. Натисніть **Перевірити з'єднання**.

Шаблон додає `--add-host=host.docker.internal:host-gateway`, щоб контейнер міг сягнути хоста. Задайте `LIBVIRT_HOST` рівним IP вашого Unraid у локальній мережі, якщо це ім'я не розв'язується (наприклад коли контейнер працює в користувацькій мережі `br0.x`). Якщо ви змінили порт SSH в Unraid, задайте `LIBVIRT_SSH_PORT` відповідно. Для **живих знімків** потрібні ще гостьовий агент qemu у віртуальній машині та диск на `/mnt/cache` (не на `/mnt/user`).

!!! important "Повний посібник з налаштування віртуальних машин і мережі"
    Повний покроковий посібник (увімкнення SSH, постійна авторизація ключа, маршрутизація для користувацької мережі та VLAN, метод для окремої віртуальної машини й усунення несправностей на боці хоста) — це [посібник із копіювання віртуальних машин](vm-backup-ssh-setup.md).

## Налаштування зовнішніх копій {#off-site-setup}

Зовнішні копії йдуть у **місця призначення**. Відкрийте **Місця призначення** з її плитки налаштувань (або закріпіть у бічній панелі) і виберіть **Додати місце призначення**. Повний порядок роботи (захист від видалення, тест на підробку та DR-перевірки) див. у розділі [Зовнішні копії та відновлення](offsite-recovery.md). Коротко:

- **Бекенди:** SMB/CIFS і WebDAV через rclone без монтування на хості, NFS (змонтуйте експорт на хості й використовуйте його як локальну папку), власні бекенди restic без rclone (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`) або будь-який віддалений ресурс rclone (`rclone:<remote>:<bucket>/path`). У Backblaze B2 тут немає власного бекенда: звертайтеся до нього через його кінцеву точку S3 (`s3:https://s3.<region>.backblazeb2.com/<bucket>/<path>`), вказавши ID ключа та ключ застосунку як облікові дані S3.
- **Облікові дані** зберігаються зашифрованими одним списком збережених облікових даних у картці **Облікові дані** в **Налаштування, Місця призначення**. Зірочка позначає типові, які використовуються скрізь, де нічого не вибрано. Сторінка самого місця вибирає, які використовувати, у своїй картці **Облікові дані**. Див. [Облікові дані](offsite-recovery.md#sign-ins).
- **Цілям SSH на дальній стороні нічого встановлювати не потрібно.** Для `sftp:` потрібен лише сервер SSH. Додайте відкритий ключ із **Налаштування, Інтеграції, SSH хоста** (він також лежить у `/config/ssh/id_ed25519.pub`) до `~/.ssh/authorized_keys` цільового користувача або дозвольте **Додати ключ** у **Додати місце призначення** покласти його туди з паролем облікового запису.
- **rest-server із самопідписаним сертифікатом:** покладіть його сертифікат або сертифікат центру, який його підписав, як файл PEM у теку `certs` у теці даних BombVault (`/config/certs` у контейнері, `appdata/bombvault/certs` в Unraid). Копії, копіювання та тест захисту від видалення довіряють йому без перезапуску.
- **Зовнішня копія:** BombVault копіює нові знімки через `restic copy` за можливості, поверх (зазвичай локального) основного. Картка **Копіювати** місця задає, чи копіює воно **Після кожної копії** чи за власним планом, а **Налаштування, Розклад, Зовнішні копії за розділами** дає одному розділу власний план копіювання. **Реплікувати зараз** стоїть у рядку розділу картки **Зовнішні копії** в **Налаштування, Місця призначення**.
- **Кілька місць призначення для розділу:** картка **Місця призначення за розділами** на сторінці місць призначення вмикає й вимикає кожну лінію від розділу до місця одним клацанням, **Локально** теж. Розділ лише із зовнішніми місцями копіює прямо в них, а розділ з усіма вимкненими лініями не копіюється. **Правила за розділами** місця дають одному розділу там власний репозиторій, зберігання чи стиснення.
- **Розміщення для окремого запису:** кожен контейнер, віртуальна машина й набір папок підсвічує **Локально** та місця, які отримують його копії, у картці **Розклад і місце призначення** на його вкладці «Налаштування». Записи без власного вибору слідують своєму розділу. Див. [Розміщення для окремого запису](offsite-recovery.md#placement).
- **Зберігання:** кожне місце призначення зберігає копії за своєю карткою **Як довго зберігати**, а розділ може тримати там власні значення в **Правила за розділами**. Це стосується й копії в полі зовнішнього зберігання розділу. Усі нулі ніколи не обрізають знімки місця.
- **Обмеження смуги:** обмежте швидкість вивантаження й завантаження restic у картці **Зовнішня пропускна здатність** в **Налаштування, Місця призначення** або для кожного місця в його картці **Копіювати**. Ви вводите KiB/s, а поле показує ту саму швидкість у МБ/с і Мбіт/с.
- **Спершу трансляція:** у картці **Стрімінг** на сторінці місць призначення виберіть медіасервери (Plex, Jellyfin та Emby вибрано наперед за іменем образу), швидкість надсилання, з якої вважається, що йде трансляція, ліміт вивантаження під час трансляції та як скоро після трансляції повертається звичайний ліміт.
- **Холодний та архівний клас зберігання (S3):** для місця призначення S3 виберіть на його сторінці рівень, з якого можна відновити (Standard, Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier Instant Retrieval). Віддалені ресурси rclone задають свій клас у конфігурації rclone.
- **Власна тека в місці призначення замість локальної:** власна тека розділу може лежати в одному з місць призначення вище, без локальної копії та без кроку копіювання. Див. [Власна тека розділу](offsite-recovery.md#own-folder).

## Аномалії {#anomalies}

Виявленню аномалій не потрібна змінна середовища. Воно налаштовується в картці **Аномалії** в **Налаштування, Перевірка** й описане на сторінці [Аномалії](anomalies.md#settings).

## Переносні налаштування (експорт та імпорт) {#portable-settings-export-and-import}

Картка **Експорт / імпорт налаштувань** в **Налаштування, Система** записує всю вашу конфігурацію BombVault (налаштування розділів, місця призначення, розклади, зберігання, сповіщення) у переносний файл JSON, який можна імпортувати на іншому екземплярі, тож переїзд на новий сервер чи клонування налаштування не означає введення всього заново вручну. Імпорт показує попередній перегляд і просить підтвердження та ніколи не чіпає дані ваших копій чи історію. Посилання у файлі на місця призначення або репозиторії, яких більше немає, пропускаються, а попередній перегляд їх називає. Поки йде репліка ZFS, імпорт відхиляється, перш ніж щось записано.

!!! warning "Експорт може містити облікові дані"
    Ви самі вибираєте, чи включати у файл облікові дані зовнішніх копій, сповіщень та брокера MQTT. З увімкненими обліковими даними експорт так само чутливий, як ваш набір для відновлення, тож зберігайте його в надійному місці. Без них файл містить лише несекретні налаштування.

!!! warning "APP_KEY не переїжджає разом із файлом"
    Репозиторії замкнені паролем, виведеним з `APP_KEY`, а у файлі його немає. Під час запланованого переїзду задайте новому серверу старий `APP_KEY` у його шаблоні або перенесіть ключ за допомогою набору для відновлення в **Аварія**. З іншим ключем репозиторії відповідають, що пароль неправильний. Нічого не втрачається, і правильний ключ знову їх відкриває.
