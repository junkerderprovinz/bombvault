# Конфігурація

Ця сторінка охоплює змінні середовища контейнера, монтування, які надає шаблон, модель безпеки, резервне копіювання VM через SSH і налаштування зовнішнього копіювання. Куди йдуть резервні копії, задається всередині застосунку як **місця призначення**, а не змінними середовища.

## Змінні середовища

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `APP_KEY` | **Так** | 32-байтовий шістнадцятковий секрет (64 шістнадцяткові символи), що використовується для виведення пароля репозиторію restic. Згенеруйте командою `openssl rand -hex 32`. Бережіть його: його втрата робить зашифровані резервні копії невідновлюваними. |
| `LIBVIRT_HOST` | Для VM | Хост Unraid, до якого звертаються через SSH для резервного копіювання VM (за замовчуванням `host.docker.internal`; шаблон попередньо заповнює заповнювач LAN-IP). Використовуйте свою LAN IP Unraid, обов'язково в кастомній мережі `br0.x`. Використовується й для копій наборів даних ZFS (поле шаблону **Host SSH: Address**); заповнювач `192.168.x.x` вважається незаданим. |
| `LIBVIRT_SSH_PORT` | Ні | Порт SSH хоста для резервного копіювання VM (за замовчуванням `22`). Поле шаблону **Host SSH: Port**, також для наборів даних ZFS. |
| `LIBVIRT_SSH_USER` | Ні | Користувач SSH на хості для резервного копіювання VM (за замовчуванням `root`). Поле шаблону **Host SSH: User**, також для наборів даних ZFS. |
| `LIBVIRT_URI` | Ні | Повний URI з'єднання libvirt, використовується **дослівно** замість побудови його з трьох наведених вище змінних `LIBVIRT_*` (які тоді ігноруються для рядка з'єднання). За замовчуванням не задано. Потрібен на TrueNAS Scale, чий libvirtd слухає на нестандартному сокеті, який побудована форма виразити не може: `qemu+ssh://<user>@<truenas-host>/system?socket=/run/truenas_libvirt/libvirt-sock`. Див. розділ про TrueNAS Scale в [docs/vm-backup-ssh-setup.md](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md). Якщо це URI `qemu+ssh://`, кожна зі змінних `LIBVIRT_HOST`, `LIBVIRT_SSH_USER` і `LIBVIRT_SSH_PORT`, яку не задано, береться з нього, зокрема для власних SSH-команд BombVault (передавання NVRAM, набори даних ZFS). |
| `PORT` | Ні | Порт HTTP (за замовчуванням `3000`; використовується лише з `HTTP_ONLY=true`). |
| `HTTPS_PORT` | Ні | Порт HTTPS (за замовчуванням `3443`; шаблон публікує його 1:1, тож WebUI відповідає на `https://<ip>:3443`). |
| `HTTP_ONLY` | Ні | Задайте `true`, щоб вимкнути самопідписаний слухач HTTPS і подавати лише звичайний HTTP (для використання за зворотним проксі, що термінує TLS). |
| `BIND_HOST` | Ні | Адреса, на якій слухає WebUI (за замовчуванням `0.0.0.0`, усі інтерфейси). У контейнері не задавайте її: опублікованим портам потрібні всі інтерфейси; `127.0.0.1` підходить для запуску поза Docker. Healthcheck звертається до тієї самої адреси. |
| `TRUSTED_PROXY` | Ні | Розділені комами адреси або діапазони CIDR зворотного проксі перед BombVault (наприклад, `192.168.20.11` або `10.0.0.0/8`). Лише з цих вузлів заголовку `X-Forwarded-For` вірять, і тоді обмежувач входу рахує невдачі за реальним клієнтом, а не зсипає всіх за проксі в одне відро. Не задано (типово) означає не довіряти нікому: беззастережно прийнятий заголовок дозволив би кожному обрати собі відро. |
| `HOST_SOURCE_ROOT` | Ні | Шлях хоста, змонтований як **Host Data** (за замовчуванням `/mnt`). BombVault перекладає джерела bind-монтувань, які повідомляє Docker, у шляхи під цим монтуванням. Змінюйте лише якщо ви змонтували інший корінь хоста. |
| `DATA_ROOT_SEGMENTS` | Ні | Розділені комами назви сегментів шляху, які позначають джерело bind-монтування як дані резервного копіювання (за замовчуванням `appdata`, відповідно до конвенції Unraid `/mnt/user/appdata/<container>`). Bind-монтування контейнера автоматично вибирається для резервного копіювання, якщо БУДЬ-ЯКИЙ із перелічених сегментів з'являється як повний сегмент шляху в його джерелі на хості, наприклад `DATA_ROOT_SEGMENTS=appdata,config` також підхоплює прив'язку `.../config`. Див. [Виявлення джерел резервного копіювання](#backup-source-detection) для інших, завжди активних способів, якими знаходиться папка даних контейнера. |
| `PLATFORM` | Ні | Примусово задає платформу, на якій BombVault вважає себе запущеним, замість автовизначення: `unraid`, `generic` або `truenas` (за замовчуванням не задано: автоматично визначає Unraid, перевіряючи наявність його маркера `dockerMan` під flash-монтуванням, інакше `generic`; нерозпізнане значення також повертається до `generic`, з записом у журнал). Задавайте її явно на звичайному хості Docker або TrueNAS Scale, замість того щоб покладатися на автовизначення, яке працює лише для Unraid: саме так і робить загальний compose-файл. Змінює конвенцію запасного шляху appdata, типові значення місця призначення відновлення при міжекземплярному відновленні та чи взагалі виконуються кроки сповіщення й плагіна-компаньйона, доступні лише на Unraid (див. `internal/platform`). |
| `BOMBVAULT_SELF_CONTAINER` | Ні | Назва самого контейнера BombVault, тож він ніколи не робить резервну копію (і тому не зупиняє) сам себе. |
| `BACKUP_MAX_HOURS` | Ні | Максимальна кількість реальних годин, протягом яких окремий запуск резервного копіювання може утримувати блокування свого розділу, перш ніж його буде примусово скасовано (запобіжник, щоб завислий запуск не міг заблокувати розділ назавжди). Порожнє (за замовчуванням) використовує `48`. Підніміть його для дуже великих чи повільних хмарних резервних копій (запуск, скасований на межі, завершується помилкою `context deadline exceeded`). Задайте `0`, щоб вимкнути обмеження повністю. |
| `BACKUP_STALL_HOURS` | Ні | Години, протягом яких резервне копіювання може **зовсім не просуватися**, перш ніж його буде скасовано. Порожнє (за замовчуванням) означає `2`; задайте `0`, щоб ніколи не скасовувати через зависання. Це тонший із двох запобіжників і зазвичай саме він спрацьовує: він стежить за тим, чи ще щось відбувається, а не за тим, скільки триває запуск, тож повільне, але справне резервне копіювання на кілька терабайт лишається в спокої, а зависле на спільному ресурсі, що не відповідає, зупиняється за години, а не за дні. Попередження записується в журнал після 30 хвилин тиші, ще до будь-якого скасування. Сканування вважається просуванням: restic не пише байтів, поки обходить велике дерево, і ця фаза відстежується за його підсумками файлів і байтів, а не за записаними байтами. Дві змінні незалежні, і `BACKUP_MAX_HOURS` і далі обмежує фази після самого резервного копіювання (зберігання, статистика, зовнішнє копіювання), де немає лічильників для спостереження. |
| `DB_DUMP_MAX_HOURS` | Ні | Години, які один автоматичний дамп бази даних може виконуватися до зупинки. Порожнє (усталено) означає `6`; дозволені значення від `1` до `48`, і межа тримається на годину нижче за `BACKUP_MAX_HOURS` (на половині його, якщо він менший за дві години), щоб довгий дамп обривався власною межею і так і повідомлявся, а не тягнув за собою все резервне копіювання. Дамп, що перестав просуватися, зупиняється раніше, через `BACKUP_STALL_HOURS`. Зупинений дамп зараховується як невдалий сам по собі, а резервне копіювання контейнера триває. На Unraid змінну додають до контейнера BombVault через **Add another Path, Port, Variable**. |
| `TZ` | Ні | Часовий пояс для планувальника (наприклад `Europe/Berlin`). **Якщо не задано, усі розклади виконуються за UTC**: розклад на 02:30 запуститься о 02:30 UTC, а не за місцевим часом. В Unraid це ніколи не задається вручну: система передає власний часовий пояс у кожен контейнер. Журнал запуску показує, який пояс було визначено. Пояс із переходом на літній час пропускає один запуск навесні й виконує один двічі восени, а UTC не робить ні того, ні іншого, зате двічі на рік зсувається на годину відносно вашого годинника. |

## Монтування

Змонтуйте сокет Docker, flash (`/boot`) і корінь **Host Data** (`/mnt`), як показано в шаблоні CA. Як *джерела*, так і *місця призначення* резервних копій живуть під Host Data, і воно монтується **slave**, тож віддалений спільний ресурс, який монтується після запуску контейнера (наприклад під `/mnt/remotes`), стає видимим без перезапуску.

Копіям наборів даних ZFS теж потрібен цей режим: хост монтує знімок набору даних лише після запуску контейнера. Див. [Набори даних ZFS](zfs-datasets.md).

Локальні репозиторії типово лежать у `/mnt/user/bombvault/{container,vms,flash,config,files,zfs}` і створюються під час першої копії. Вони утворюють місце призначення **Локальна тека**. На його сторінці в **Місця призначення** картка **Підключення** змінює теку кожного розділу, а вікно, яке вона відкриває, має перемикач **Локально / Віддалено**: шлях розділу може бути віддаленим restic (`s3:...`, `rest:...`, `sftp:...`, `rclone:...`) замість локальної теки, і копія йде просто туди без окремої локальної копії; див. [Віддалені основні репозиторії](offsite-recovery.md#remote-primary-repositories).

!!! note "Перевірка інтеграції з хостом"
    Картка **Інтеграція з хостом** в огляді (додайте її через **Налаштувати**) тестує кожне монтування та CLI (сокет Docker, libvirt, restic, qemu-img, rclone) і повідомляє про будь-які відсутні частини.

## Визначення джерел резервної копії {#backup-source-detection}

Для кожного контейнера BombVault автоматично вибирає, які bind-монтування та іменовані томи копіювати. Шлях підхоплюється, коли виконується будь-що з наведеного нижче (результат завжди можна змінити в картці **Папки для резервного копіювання** на вкладці «Налаштування» контейнера):

- **Збіг із сегментом кореня даних:** джерело bind-монтування на хості містить один із сегментів `DATA_ROOT_SEGMENTS` як повну складову шляху (типово лише `appdata`).
- **Іменовані томи Docker** долучаються завжди, бо одноразового відповідника в них немає і фільтрувати нічого, **але тільки якщо справжній шлях зберігання тому на хості сам досяжний через монтування Host Data**, так само як будь-який інший шлях хоста, що його копіює BombVault. Типовий драйвер локальних томів кладе том під корінь даних самого демона, тобто `/var/lib/docker/volumes/<назва>/_data`, якщо це не змінено (перевірте командою `docker info -f '{{.DockerRootDir}}'`). Це місце НЕ покрите вузьким монтуванням Host Data з одного каталогу, яке типово використовує звичайний `docker-compose.yml`. Недосяжний том мовчки пропускається, це не помилка. Щоб іменовані томи на звичайному хості справді копіювалися, спрямуйте Host Data (і `HOST_SOURCE_ROOT`) на спільного предка, що охоплює також корінь даних Docker: компроміс описано в коментарі Host Data у файлі compose (Unraid обходить це, монтуючи з тієї самої причини весь `/mnt`, власну універсальну домовленість верхнього рівня).
- **Каталог проєкту Docker Compose:** якщо контейнер несе звичну мітку `com.docker.compose.project.working_dir` (її автоматично ставить `docker compose up`), цей каталог додається теж, незалежно від того, чи збіглося якесь bind-монтування із сегментом кореня даних.
- **Перевизначення міткою `bombvault.data`:** поставте контейнеру мітку `bombvault.data=true`, щоб долучити ВСІ його bind-монтування, для розкладки, якої не ловить жодна з двох домовленостей вище (наприклад одиничне монтування `/srv/plex/config` без проєкту Compose). Будь-яке непорожнє значення, окрім `false`, вважається істинним; відсутня мітка або `bombvault.data=false` не змінюють нічого.
- **Мітка `bombvault.dbdump`:** задайте `bombvault.dbdump=false` на контейнері, щоб вимкнути його автоматичний дамп бази даних (`0`, `no` і `off` роблять те саме), або назвіть рушій (`postgres`, `mysql`, `mariadb`), щоб зробити дамп контейнера, який BombVault сам не розпізнає. Мітка переважає перемикач у картці **База даних** на вкладці «Налаштування» контейнера, а в Unraid це єдиний спосіб.

## Модель безпеки {#security-model}

!!! warning "Root-рівний контроль над хостом"
    Через сокет Docker BombVault може зупиняти, видаляти та відтворювати контейнери й читати/писати appdata, а для резервного копіювання VM він входить на хост через SSH (`qemu+ssh://`, root за замовчуванням), щоб виконати `virsh`. Кожен, хто має доступ до його вебінтерфейсу, фактично має root на хості.

### Вхід {#login}

- **Необов'язковий захист паролем** (картка **Пароль** у **Налаштування, Безпека**): задайте пароль, щоб вимагати вхід, очистьте його, щоб вимкнути. За замовчуванням вимкнено для використання в довіреній локальній мережі. Пароль зберігається через Argon2id поверх перцю, прив'язаного до `APP_KEY`, тож скопійований `/config` без ключа марний, а з ключем повільний для атаки. Новий пароль має містити щонайменше 12 символів; наявний коротший працює, доки його не змінять. Сеанси підписані (HMAC, виведений із `APP_KEY`), а зміна пароля їх анулює; входи обмежені п'ятьма невдалими спробами на хвилину для одного клієнта.
- **Дещо потребує пароля.** Завантаження набору для відновлення та звіту про помилку, передача ключа зберігачу ключа, дозвіл видати депозит, створення нового коду видачі, видалення резервних копій у місці призначення, експорт налаштувань з обліковими даними, двофакторна автентифікація та ключі доступу відхиляються, доки не задано пароль для входу, і вимагають входу на самому екземплярі.
- **Двофакторна автентифікація** (**Налаштування, Безпека**): тимчасовий код із застосунку-автентифікатора поверх пароля, плюс вісім одноразових резервних кодів, які видаються один раз, коли її вмикають. Спільний секрет зберігається зашифрованим за допомогою `APP_KEY`, а щоб знову вимкнути цей чинник, потрібен чинний код.
- **Ключі доступу** (WebAuthn) розміщені на окремій картці, щойно задано пароль, і діють разом із паролем, а не замість нього, тож видалення всіх ключів доступу нікого не замикає. Їм потрібне справжнє доменне ім'я і сертифікат, якому довіряє браузер. Типовий `https://<ip>:3443`, це саме те, що WebAuthn відхиляє, і картка так і каже, замість того щоб пропонувати кнопку, яка не спрацює.
- **Забутий пароль** скидається на сторінці входу. **Забули пароль?** змушує BombVault записати в журнал свого контейнера код із 12 символів, трьома групами по чотири (в Unraid: вкладка Docker, значок BombVault, **Logs**). Цей код і новий пароль впускають вас. Скидання також вимикає двофакторну автентифікацію, видаляє кожен ключ доступу, відкликає кожен токен API, ключ MCP і вхід через OAuth, завершує всі інші сеанси, виводить із системи кожен спарений телефон і вимикає спарювання телефонів; сторінка потім перелічує, що зникло. Код чинний 10 хвилин, а хибні спроби його не витрачають. Токени віджетів і метрик лишаються, бо вони лише читають.
- **Хто може читати журнал контейнера, може скинути пароль.** Це root на хості, але також переглядач журналів на кшталт Dozzle, будь-який контейнер, якому дано сокет Docker (достатньо лише читання), і відправник журналів, що пересилає вивід контейнерів. Давайте їх лише тим, кому довірили б пароль. Той, хто має доступ лише до вебінтерфейсу, коду ніколи не бачить.

### Телефони та учасники групи {#phones-and-members}

- **Спарені телефони сягають переліку дозволеного.** Телефон, що знає дванадцять слів групи, входить без пароля, поки ввімкнено **Телефони можна спарювати за дванадцятьма словами групи** на картці **Застосунок для Android** у **Налаштування, Безпека**. Його сеанс сягає лише того, що показує застосунок: огляд, запуски, резервні копії для перегляду, запуск і відновлення, аномалії для читання та сторінка «Екземпляри» для перегляду. Місця призначення й команди доходять до нього з вилученими адресами та секретами, а відновлення, що замінює оригінал, спершу створює копію поточного стану. На все інше сервер відповідає, що потрібен вхід на самому екземплярі: ключі, набір для відновлення, депозити ключів, налаштування, видалення резервних копій. Скидання пароля вимикає спарювання телефонів, доки ви не ввімкнете його знову.
- **Учасники підписують те, що запитують.** Запити ролей і відповіді на них, видача пароля restic приймачу чи стягувачу, входи приймача й депозити ключів підписуються ключем кожного учасника, який екземпляр фіксує, коли вперше бачить цього учасника. Виклик, підписаний іншим ключем, відхиляється. **Забути ключ** у деталях екземпляра скидає зафіксований ключ на випадок, коли відомий тут ключ не належить самому учаснику; наступного підписаного виклику у учасника знову запитають ключ. Учасники на BombVault 9.x не підписують і їх може видавати за себе будь-хто, хто знає слова, як і в 9.9.
- **Дванадцять слів, це пароль.** Хто їх має, той приєднується до групи, бачить стан захисту учасників і може просити ролі, які людина на іншому екземплярі все одно має дозволити. Без пароля для входу їх може прочитати кожен, хто може відкрити вебінтерфейс, і картка спарювання про це каже, доки пароль не задано.

### Ключі {#keys}

- **APP_KEY робить дві речі.** Він запечатує те, що зберігає це встановлення (паролі, облікові дані, токени), і він є ключем резервних копій: з нього виводиться пароль restic, ним же запечатано визначення контейнерів і VM.
- **Перейнятий ключ тримають окремо.** Коли Аварійний майстер перейняв резервні копії іншого сервера, це встановлення й далі запечатує власним APP_KEY, а ключ іншого сервера зберігає як свій **ключ резервних копій**, запечатаний, як і кожен інший секрет. Набір для відновлення тоді друкує обидва. Якщо APP_KEY потім змінити, ключ резервних копій більше не відкрити: BombVault перестає копіювати й каже про це в **Потребує уваги**, замість того щоб писати не тим ключем. Завантажте набір для відновлення знову в **Відновлення, Аварія** або поверніть APP_KEY. Див. [Аварійний майстер](offsite-recovery.md#emergency).
- **Шифрування** типово ввімкнено (**Шифрувати копії** в картці **Шифрування** у **Налаштування, Безпека**). Restic шифрує резервні копії паролем, виведеним із ключа резервних копій.
- **Депозити ключів.** Зберігач ключа у вашій групі тримає запечатану копію набору для відновлення цього сервера, яку сам не може відкрити. Відкриває її лише 20-символьний код видачі, а зберігач видає її тільки після того, як хтось у нього натисне **Дозволити**. Див. [Зберігач ключа](offsite-recovery.md#key-keeper).

### Мережа {#network}

- **Зміни лише в JSON.** Запит, який щось змінює, має надсилати `Content-Type: application/json` і не повинен бути позначений браузером як міжсайтовий, тож сторінка на іншому сайті не може змусити ваш браузер змінювати налаштування за адресою в локальній мережі. Скрипт, що працює з API, надсилає цей заголовок; усе інше відхиляється з `415`.
- Оскільки захисний бар'єр необов'язковий, без пароля весь інтерфейс і API (зокрема місця призначення, маршрути тесту на втручання та маршрути відновлення) доступні кожному, хто дістанеться порту. Задайте пароль для входу, щойно почнете користуватися зовнішніми копіями, append-only або шифруванням.
- Запускайте BombVault лише в довіреній, не виставленій назовні мережі. Для віддаленого доступу поставте його за зворотним проксі, що додає автентифікацію та TLS. Відповіді несуть базові заголовки безпеки (CSP, `nosniff`, `X-Frame-Options`, `Referrer-Policy`).
- За зворотним проксі кожен запит несе адресу проксі, тож без `TRUSTED_PROXY` обмежувач рахує всіх клієнтів разом, і невдачі зловмисника блокують і вас. Вкажіть проксі в `TRUSTED_PROXY`, щоб повернути підрахунок за клієнтами.
- Зворотний проксі перед BombVault має передавати заголовок `Authorization` або `X-API-Key` на `/mcp` і не повинен буферизувати відповіді, інакше асистенти не зможуть підключитися. Див. [Сервер MCP](mcp.md#tls).
- Кінцева точка MCP `/mcp` відповідає `404`, доки не створено ключ або не ввімкнено вхід через OAuth, і вимагає від кожного клієнта ключ або токен навіть за вимкненого пароля входу; жодна адреса не виняток, навіть `localhost`. Інструментів відновлення чи видалення в неї немає, а відновлення резервної копії конфігурації відкликає всі ключі. Див. [Сервер MCP](mcp.md#security).
- З `HTTP_ONLY=true` cookie сесії втрачає свій прапорець `Secure` (мусить, щоб працювати через звичайний HTTP), тож вмикайте пароль за проксі, що термінує TLS, лише якщо конфіденційність має значення.
- З'єднання SSH для резервного копіювання VM довіряє ключу хоста під час першого з'єднання (TOFU) і закріплює його після цього. Перевірте ключ хоста поза каналом, якщо ваш шлях від контейнера до хоста не є довіреним.

## Сервер MCP {#mcp-server}

Серверу MCP не потрібна змінна середовища. Ви вмикаєте його, створивши ключ у **Налаштування, Інтеграції, Сервер MCP**, і він відповідає за шляхом `/mcp` на тому самому порту, що й вебінтерфейс (наприклад, `https://192.168.1.10:3443/mcp`). Без активного ключа цей шлях відповідає `404`. Клієнтів, сертифікати й обмеження описано на сторінці [Сервер MCP](mcp.md).

## Резервне копіювання VM через SSH

BombVault робить резервні копії віртуальних машин KVM/libvirt **без монтування будь-якого шляху libvirt**. Він виконує `virsh` на хості через SSH (`qemu+ssh://`), тож він ніколи не може вплинути на ваш хостовий VM Manager.

Монтувати сокет libvirt хоста в контейнер на Unraid ненадійно: цими шляхами володіє VM Manager, і перемикання "Enable VMs" може залишити libvirt нездатним запуститися. SSH-ключ дає root на хості, це той самий рівень довіри, що й у сокета Docker, який BombVault уже використовує.

Швидке налаштування:

1. **Налаштування, Інтеграції, SSH хоста:** скопіюйте показаний публічний ключ.
2. Додайте його до `/root/.ssh/authorized_keys` в Unraid (також збережений на flash, тож він переживає перезавантаження).
3. Натисніть **Перевірити з'єднання**.

Шаблон додає `--add-host=host.docker.internal:host-gateway`, тож контейнер може дістатися до хоста. Задайте `LIBVIRT_HOST` на свою LAN IP Unraid, якщо ця назва не розв'язується (наприклад коли контейнер працює в кастомній мережі `br0.x`). Якщо ви змінили порт SSH Unraid, задайте `LIBVIRT_SSH_PORT` відповідно. **Живі знімки** додатково потребують гостьового агента qemu у VM і диска на `/mnt/cache` (не `/mnt/user`).

!!! important "Повний посібник з налаштування VM і мережі"
    Повний покроковий посібник (увімкнення SSH, стійка авторизація ключа, маршрутизація в кастомній мережі та VLAN, метод для кожної VM і усунення несправностей на боці хоста) живе за адресою [docs/vm-backup-ssh-setup.md](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md) на GitHub.

## Налаштування зовнішнього копіювання

Зовнішні копії йдуть у **місця призначення**. Відкрийте **Місця призначення** з їхньої плитки налаштувань (або закріпіть на бічній панелі) і виберіть **Додати місце призначення**. Повний процес (захист від видалення, тест на втручання та тренування DR) див. у [Зовнішнє копіювання та відновлення](offsite-recovery.md). Коротко:

- **Бекенди:** SMB/CIFS і WebDAV через rclone без монтування на хості, NFS (змонтуйте експорт на хості й користуйтеся ним як локальною текою), рідні бекенди restic без rclone (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`) або будь-який rclone remote (`rclone:<remote>:<bucket>/path`). Backblaze B2 тут не має рідного бекенду: підключайтеся до нього через його кінцеву точку S3 (`s3:https://s3.<region>.backblazeb2.com/<bucket>/<path>`), указавши ID ключа й ключ застосунку як облікові дані S3.
- **Облікові дані** зберігаються зашифрованими, або як спільні хмарні облікові дані, або як іменований набір. Обидва є картками в **Налаштування, Місця призначення**, а власна сторінка місця призначення вибирає потрібний набір у **Облікові дані**.
- **Цілі SSH не потребують нічого встановленого на дальньому боці.** `sftp:` потребує лише SSH-сервера. Додайте публічний ключ з **Налаштування, Інтеграції, SSH хоста** (також за адресою `/config/ssh/id_ed25519.pub`) до `~/.ssh/authorized_keys` цільового користувача.
- **Зовнішня копія:** BombVault копіює нові знімки командою `restic copy` за принципом «найкращих зусиль» поверх (зазвичай локального) основного репозиторію. Картка **Копіювати** місця призначення визначає, чи копіює воно **Після кожної резервної копії**, чи за власним планом, а **Налаштування, Розклад, Зовнішні копії за областями** дає одному розділу власний план копіювання. **Реплікувати зараз** лежить у картці **Зовнішня копія** кожного розділу в **Налаштування, Місця призначення**.
- **Кілька місць призначення для розділу:** картка **Місця призначення за розділами** на сторінці «Місця призначення» вмикає або вимикає кожен рядок від розділу до місця призначення. **Правила за розділами** місця призначення дають одному розділу там власний репозиторій, зберігання чи стиснення.
- **Розміщення для кожного запису:** кожен контейнер, віртуальна машина, набір папок і набір даних ZFS підсвічує **Локально** та місця призначення, що отримують його копії, у картці **Розклад і місце призначення** на його вкладці «Налаштування». Записи без власного вибору йдуть за своїм розділом. Див. [Розміщення для кожного запису](offsite-recovery.md#placement).
- **Зберігання:** кожне місце призначення тримає копії за своєю карткою **Як довго зберігати**, а розділ може мати там власні значення в **Правила за розділами**. Копія в зовнішньому полі розділу тримає правила картки **Зовнішнє зберігання** в **Налаштування, Місця призначення**, де для окремих розділів є **Правила зберігання за джерелом** (залиште все нулями, щоб ніколи автоматично не обрізати зовнішні знімки).
- **Обмеження пропускної здатності:** обмежте швидкість передавання restic у картці **Зовнішня пропускна здатність** у **Налаштування, Місця призначення** або для окремого місця призначення в його картці **Копіювати**.
- **Спершу стрімінг:** у картці **Стрімінг** на сторінці «Місця призначення» виберіть медіасервери (Plex, Jellyfin і Emby вибрано наперед за назвою образу), швидкість надсилання, від якої це вважається стрімінгом, обмеження вивантаження під час нього та через який час після стріму повертається звичайне обмеження.
- **Холодний і архівний клас зберігання (S3):** для місця призначення S3 виберіть на його сторінці рівень, придатний для відновлення (Standard, Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier Instant Retrieval). Віддалені rclone задають свій клас у конфігурації rclone.
- **Віддалений основний замість локального:** власний шлях розділу сам може бути одним із наведених вище бекендів, без локальної копії та кроку реплікації. Про перемикач **Локально / Віддалено** та його налаштування пропускної здатності, append-only і бюджету зростання див. [Віддалені основні репозиторії](offsite-recovery.md#remote-primary-repositories).

## Аномалії {#anomalies}

Виявлення аномалій налаштовується в картці **Аномалії** в **Налаштування, Перевірка**. Кожен елемент керування зберігається, щойно ви його змінюєте, а три під перемикачем приховані, поки виявлення вимкнено.

| Параметр | Типово | Що робить |
|---|---|---|
| **Виявляти аномалії** | Увімкнено | Порівнює кожну копію з власною історією запису. Якщо вимкнути, нічого нового не перевіряється, а пункт **Аномалії** зникає з бічної панелі; картка все ще веде до попередніх знахідок. |
| **Чутливість** | Збалансована | Сувора повідомляє і про менші зміни, Мʼяка лише про великі. |
| **Надсилати сповіщення для** | Лише критичні знахідки | Мінімальна важливість, за якої повідомлення надсилається каналами, налаштованими в Сповіщення. Повторні збої копій і дампів та невдалі планові перевірки відновлення вже надсилають власне повідомлення й не надсилаються двічі. |
| **Зберігати старі копії, коли джерело різко зменшилося або було перезаписане** | Увімкнено | Поки запис має відкриту знахідку про майже порожнє джерело, різке зменшення або повторне збереження більшості його даних, зберігання та очищення не чіпають старі копії цього запису. Підтвердьте знахідку або позначте її як очікувану, щоб їх відпустити. |

Кожен запис може мати власну чутливість і мінімум сповіщень. Задайте їх на вкладці **Цілісність** запису або на сторінці «Аномалії» в **Спостереження**. Для запису ZFS вони діють на кожен набір даних його дерева.

## Портативні налаштування (експорт та імпорт) {#portable-settings-export-and-import}

Картка **Експорт / імпорт налаштувань** у **Налаштування, Система** записує всю вашу конфігурацію BombVault (налаштування розділів, місця призначення, розклади, зберігання, сповіщення) у портативний файл JSON, який можна імпортувати на іншому екземплярі, тож перехід на нову машину чи клонування установки не означає ручного введення всього заново. Імпорт показує попередній перегляд і просить підтвердження та ніколи не чіпає ваші резервні дані чи історію.

!!! warning "Експорт може містити облікові дані"
    Ви вибираєте, чи включати зовнішні облікові дані, облікові дані сповіщень і MQTT-брокера у файл. З включеними обліковими даними експорт настільки ж чутливий, як ваш набір для відновлення, тож зберігайте його в безпечному місці. Без них файл містить лише несекретні налаштування.
