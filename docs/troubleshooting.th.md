# การแก้ปัญหา

FAQ สั้น ๆ สำหรับตารางแก้ปัญหาฝั่งโฮสต์ของ VM ผ่าน SSH ฉบับเต็ม (permission-denied, การตรวจคีย์โฮสต์, ตัวแปรเทมเพลตที่ขาด และอื่น ๆ) ดู [คู่มือการสำรอง VM ผ่าน SSH](vm-backup-ssh-setup.md)

## มีอะไรเชื่อมต่อไม่ถูกต้อง {#something-is-not-wired-up-correctly}

เพิ่มการ์ด **การผสานรวมโฮสต์** ลงในภาพรวมใต้ **ปรับแต่ง** การตรวจการผสานรวมโฮสต์ตรวจทุก mount และ CLI (Docker socket, libvirt, restic, qemu-img, rclone) และรายงานส่วนที่ขาด และ **ตรวจสอบเดี๋ยวนี้** รันอีกครั้ง เริ่มที่นี่ก่อนจะสรุปว่าเป็นบั๊ก: mount ที่ขาดหรือโฮสต์ที่เข้าไม่ถึงจะปรากฏทันที

## เข้าหน้าเว็บไม่ได้ {#i-cannot-reach-the-web-ui}

BombVault ให้บริการ HTTPS ทันทีที่พอร์ต `3443` (ใบรับรองที่เซ็นเอง) ให้เปิด `https://<your-unraid-ip>:3443` ยอมรับคำเตือนใบรับรองที่เซ็นเอง หรือวาง BombVault หลัง reverse proxy ที่มีใบรับรองของคุณเอง ถ้าคุณรันด้วย `HTTP_ONLY=true` มันจะให้บริการ HTTP ธรรมดาที่พอร์ต `3000` แทน (สำหรับใช้หลัง proxy ที่ยุติ TLS)

## ทำ APP_KEY หาย {#i-lost-my-app_key}

`APP_KEY` สร้างรหัสผ่านที่เก็บ restic ถ้าไม่มีมัน ไม่มีชุดกู้คืน และไม่มีการฝากคีย์ในกลุ่มของคุณ ข้อมูลสำรองที่เข้ารหัสจะกู้คืนไม่ได้ นี่คือเหตุที่ภาพรวมแสดง **บันทึกชุดกู้คืนของคุณ** จนกว่าคุณจะดาวน์โหลด ดู [นอกสถานที่และการกู้คืน](offsite-recovery.md#recovery-kit) สร้างคีย์ด้วย `openssl rand -hex 32` และเก็บไว้นอกเซิร์ฟเวอร์ก่อนจะพึ่งการสำรองใด ๆ

## ลืมรหัสผ่านเข้าสู่ระบบ {#i-forgot-the-login-password}

เลือก **ลืมรหัสผ่าน?** ที่หน้าเข้าสู่ระบบ BombVault เขียนรหัส 12 ตัวอักษรลงบันทึกคอนเทนเนอร์ของมัน (บน Unraid: แท็บ Docker ไอคอน BombVault **Logs**) พิมพ์รหัสนั้นพร้อมรหัสผ่านใหม่ภายใน 10 นาที การรีเซ็ตยังปิดการยืนยันตัวตนสองขั้นตอน ลบทุกพาสคีย์ เพิกถอนทุกโทเคน API คีย์ MCP และการลงชื่อเข้าใช้ OAuth จบทุกเซสชันอื่น และปิดการจับคู่โทรศัพท์ เพิ่มพาสคีย์อีกครั้งที่ **การตั้งค่า, ความปลอดภัย** เปิดการจับคู่โทรศัพท์กลับที่นั่น และสร้างโทเคนและคีย์ใหม่ในที่ที่ยังต้องใช้ ดู [โมเดลความปลอดภัย](configuration.md#login)

## การสำรองข้อมูลหยุดและบอกว่าเปิดคีย์ไม่ได้อีก {#backups-stopped-and-say-the-key-can-no-longer-be-opened}

เซิร์ฟเวอร์นี้รับคีย์สำรองของเซิร์ฟเวอร์อื่นมาในตัวช่วยฉุกเฉิน และ `APP_KEY` ถูกเปลี่ยนภายหลัง คีย์ที่รับมาถูกปิดผนึกด้วย APP_KEY เดิม BombVault จึงเปิดไม่ได้และไม่สำรองอะไรแทนที่จะเขียนด้วยคีย์ที่ผิด **ต้องดูแล** บนภาพรวมบอกไว้ ตั้ง APP_KEY กลับเป็นค่าเดิม หรืออัปโหลดชุดกู้คืนอีกครั้งที่หน้าการกู้คืนใต้ **ฉุกเฉิน**

## โทรศัพท์ไปโผล่ที่หน้าเข้าสู่ระบบ {#a-phone-lands-on-the-login-page}

โทรศัพท์ที่จับคู่แล้วได้เซสชันผ่านกลุ่มเฉพาะขณะที่เปิด **โทรศัพท์จับคู่ด้วยคำสิบสองคำของกลุ่มได้** ใต้ **การตั้งค่า, ความปลอดภัย** การรีเซ็ตรหัสผ่านปิดมัน แอปที่เก่ากว่าเซิร์ฟเวอร์ก็ไม่ได้เซสชันจนกว่าจะอัปเดต เซิร์ฟเวอร์ที่เพิ่มด้วยที่อยู่จะขอรหัสผ่านเสมอ โทรศัพท์ที่ถูกลบจากหน้าอินสแตนซ์จะกลับมาในสถานะปิดเมื่อแอปเปิดอีก เปิด **สอบถามอินสแตนซ์นี้** ใต้ **การเฝ้าระวัง** ในรายละเอียดของมันเพื่อให้เข้าได้

## การสำรอง VM เชื่อมต่อไม่ได้ {#vm-backup-will-not-connect}

การสำรอง VM คุยกับ libvirt ผ่าน SSH ไม่ใช่ผ่าน mount

- ยืนยันว่า SSH เปิดอยู่บนโฮสต์และกุญแจสาธารณะของ BombVault ได้รับอนุญาตใน `/root/.ssh/authorized_keys` (การตั้งค่า, การเชื่อมต่อ, SSH ของโฮสต์ แสดงกุญแจและปุ่ม **ทดสอบการเชื่อมต่อ**)
- บนเครือข่าย `br0.x` แบบกำหนดเอง ให้ตั้ง `LIBVIRT_HOST` เป็น IP LAN ของ Unraid (คอนเทนเนอร์เข้าถึงโฮสต์ผ่าน `host.docker.internal` ที่นั่นไม่ได้) เปิด **Settings, Docker, Host access to custom networks**
- ถ้าคุณเปลี่ยนพอร์ต SSH ของ Unraid ให้ตั้ง `LIBVIRT_SSH_PORT` ให้ตรงกัน
- บน TrueNAS ตั้ง `LIBVIRT_URI` ด้วย socket libvirt ของ TrueNAS เอง ให้แอปมีความสามารถ `SETPCAP` และเพิ่มคีย์ให้ root ที่ **Credentials, Users** (ดู [TrueNAS SCALE](getting-started.md#truenas))
- การวินิจฉัยทีละขั้นแบบเต็ม (ทดสอบการเข้าถึง การกำหนดเส้นทาง VLAN `Permission denied (publickey)` `Host key verification failed`) อยู่ใน [คู่มือการสำรอง VM ผ่าน SSH](vm-backup-ssh-setup.md)

## สแนปช็อต VM แบบสดไม่รัน {#a-live-vm-snapshot-did-not-run}

สแนปช็อตแบบสดต้องให้ดิสก์อยู่บน `/mnt/cache` (หรือ `/mnt/diskX`) ไม่ใช่ `/mnt/user` ถ้ามี qemu guest agent ใน VM สแนปช็อตจะหยุดการเขียนชั่วคราวก่อนถ่าย และถ้าไม่มี สแนปช็อตจะอยู่ในสภาพเดียวกับตอนเครื่องดับกะทันหัน (crash-consistent) บน VM ที่ปิดอยู่ แบบสดจะถอยไปเป็นแบบนุ่มนวลโดยอัตโนมัติ การสำรองแบบนุ่มนวลปิด VM สำรองดิสก์ แล้วเริ่มใหม่ จึงสอดคล้องกันเสมอ มันรอให้เกสต์ปิดนานถึงสิบนาทีและไม่บังคับปิดเลย เกสต์ Windows ที่กำลังติดตั้งอัปเดตจึงไม่ถูกตัดกลางคัน เกสต์ที่ยังรันอยู่หลังจากนั้นจะถูกปล่อยไว้ และการสำรองนั้นล้มเหลวพร้อมเหตุผล

## การสำรองล้มเหลวด้วย "repository is already locked" {#a-backup-failed-with-repository-is-already-locked}

โดยมากเป็นล็อก restic ที่ถูกทิ้งไว้เมื่อคอนเทนเนอร์ถูกอัปเดตหรือรีสตาร์ทกลางการทำงาน BombVault ตรวจพบล็อกที่ถูกทิ้งแน่ ๆ ล้างแบบบังคับ และลองใหม่หนึ่งครั้งโดยอัตโนมัติ ถ้ายังเป็นอยู่ เปิดการ์ด **ตรวจสอบข้อมูลสำรอง** ใต้ **การตั้งค่า, ยืนยัน** แล้วเลือก **ปลดล็อก** ใต้ **เพิ่มเติม** ในแถวของส่วนที่ได้รับผลเพื่อล้างล็อกค้างด้วยมือ ปัญหาจริงยังโผล่ขึ้นมาและไม่ถูกซ่อน หลังรีสตาร์ท BombVault รอจนล็อกนั้นไม่ถูกต่ออายุสิบนาที restic ที่ยังรันอยู่ เช่นใน BombVault ตัวที่สองบนที่เก็บเดียวกัน ต่ออายุล็อกของมันทุกห้านาที

## สำเนานอกสถานที่ไม่เกิดหลังการสำรอง {#my-off-site-copy-did-not-happen-after-a-backup}

การทำสำเนานอกสถานที่เป็นแบบ best-effort โดยออกแบบ ปัญหานอกสถานที่จึงไม่ทำให้การสำรองในเครื่องล้มเหลว ตรวจว่าปลายทางคัดลอกเมื่อไร: การ์ด **คัดลอก** ของมันบอก **หลังสำรองทุกครั้ง** หรือระบุกำหนดการของตัวเอง และ **การตั้งค่า, ตารางเวลา, สำเนานอกสถานที่รายส่วน** ให้ส่วนหนึ่งมีกำหนดการของตัวเองได้ ใช้ **จำลองตอนนี้** ในแถวของส่วนในการ์ด **สำเนานอกสถานที่** ใต้ **การตั้งค่า, ปลายทางที่จัดเก็บ** เพื่อรันตามสั่ง และดูส่วนหัวสถานะของภาพรวม ซึ่งบอก **กำลังคัดลอกไปนอกสถานที่** ขณะรัน การคัดลอกที่ล้มเหลวปรากฏใต้ **ต้องดูแล**

## ใบรับรองของ rest-server ไม่ได้รับความเชื่อถือ {#a-rest-servers-certificate-is-not-trusted}

restic ปฏิเสธใบรับรองที่ไม่รู้จัก และข้อผิดพลาดบอกว่าจะวางที่ไหน คัดลอกใบรับรองที่เซ็นเองของ rest-server หรือของผู้ออกที่เซ็น เป็นไฟล์ PEM ลงในโฟลเดอร์ `certs` ของโฟลเดอร์ข้อมูลของ BombVault (`/config/certs` ในคอนเทนเนอร์ `appdata/bombvault/certs` บน Unraid) แล้วทดสอบอีกครั้ง ไม่ต้องรีสตาร์ท

## การสำรองบอกว่าข้อมูลนอก Host Data ไม่ถูกสำรอง {#data-outside-host-data}

คอนเทนเนอร์เก็บข้อมูลไว้ในโฟลเดอร์ที่ BombVault อ่านผ่าน Host Data ไม่ได้ การสำรองบันทึกคำจำกัดความและทุกโฟลเดอร์ที่เข้าถึงได้ ทำให้บรรทัดของมันในบันทึกกิจกรรมเป็นสีส้ม และระบุโฟลเดอร์ที่เว้นไว้ สองกรณีที่พบบ่อย: ixVolume บน TrueNAS ใต้ `/mnt/.ix-apps` และวอลุ่ม Docker แบบมีชื่อใต้ `/var/lib/docker/volumes` เช่นวอลุ่มฐานข้อมูลของสแตก compose การ์ด **โฟลเดอร์ที่สำรองข้อมูล** บนแท็บ **การตั้งค่า** ของคอนเทนเนอร์ลิสต์โฟลเดอร์แบบนั้นแต่ละอันพร้อมพาธภายในคอนเทนเนอร์และพาธบนโฮสต์ ทำเครื่องหมายสีแดง

วอลุ่ม Docker แบบไม่มีชื่อจะไม่ถูกรายงาน Docker สร้างเองสำหรับโฟลเดอร์ที่ image ประกาศแต่ไม่มีใครแมป ตั้งชื่อด้วยเลขฐานสิบหก 64 หลัก และเก็บไว้ใต้ `/var/lib/docker/volumes` มักเป็นแคช การสำรองจึงยังเป็นสีเขียวและการ์ดแค่ลิสต์มัน พร้อมหมายเหตุว่าไม่มีชื่อ

- **คุณต้องการสำรองข้อมูลนั้น** แมปโฟลเดอร์ไปยังพาธโฮสต์ใต้ Host Data เช่นโฟลเดอร์ใน share appdata ของคุณ แล้วการสำรองครั้งถัดไปจะรวมมัน
- **คุณไม่ต้องการ** เพิ่มพาธอันใดอันหนึ่งของมันเป็นบรรทัดในการ์ด **รูปแบบการยกเว้น** บนแท็บเดียวกัน: พาธภายในคอนเทนเนอร์ เช่น `/cache` หรือพาธบนโฮสต์ที่คำเตือนระบุ เช่น `/var/lib/docker/volumes/jellyfin_cache/_data` ตั้งแต่การสำรองครั้งถัดไป คำเตือนจะเว้นโฟลเดอร์นั้น และตัวอย่างใต้ช่องบอกเหตุผล บรรทัดสำหรับโฟลเดอร์ที่อยู่เหนือขึ้นไปก็ใช้ได้ ชื่อเปล่า ๆ หรือ `/` ใช้ไม่ได้

## การสำรองบอกว่าเลื่อนไว้ {#deferred-backups}

แอปของคอนเทนเนอร์ไม่ว่าง การสำรองของมันจึงรอและลองใหม่เอง บรรทัดในบันทึกกิจกรรมบอกเหตุผลและเวลาลองครั้งถัดไป การ์ด **เมื่อแอปไม่ว่าง** บนแท็บ **การตั้งค่า** ของคอนเทนเนอร์บอกเหมือนกันและบอกว่าการรอจบเมื่อไร ไม่ต้องทำอะไร ถ้าจะสำรองทันที ใช้ **สำรองข้อมูลเดี๋ยวนี้**: การสำรองที่คุณเริ่มเองไม่เคยรอ แม้ด้วยรหัสออก 75

- **การตรวจของคุณเอง** ทำให้ **คำสั่งก่อนการสำรองข้อมูล** ออกด้วยรหัส 75 ขณะที่แอปไม่ว่าง เช่น `[ "$(cat /tmp/players)" = 0 ] || exit 75` รหัสอื่นที่ไม่ใช่ 0 ทำให้การสำรองล้มเหลวเหมือนเดิม สคริปต์ที่พังจึงยังปรากฏใต้ **ต้องดูแล**
- **ไม่เคยถาม Plex, Jellyfin หรือ Emby** BombVault ถามเซิร์ฟเวอร์ที่ที่อยู่ของคอนเทนเนอร์เองก่อน และเมื่อไม่ตอบ จะรัน curl หรือ wget ภายในคอนเทนเนอร์ image ที่ไม่มีทั้งสองอย่างถามผ่านตัวมันเองไม่ได้ บันทึกจะบอกไว้ เมื่อเปิด **สำรองข้อมูลเมื่อเซิร์ฟเวอร์ไม่ตอบ** การสำรองแบบนั้นรันอยู่ดี เมื่อปิดมันรอ
- **Jellyfin หรือ Emby ปฏิเสธ** ตรวจ **คีย์ API** สร้างในแดชบอร์ดของเซิร์ฟเวอร์ใต้ API keys
- **Plex ปฏิเสธ** BombVault อ่านโทเคนจาก `Preferences.xml` ในโฟลเดอร์ที่เมานต์ที่ `/config` เซิร์ฟเวอร์ที่ไม่เคยลงชื่อเข้าใช้ไม่มี และตอบเฉพาะที่ที่อนุญาตให้เข้าถึงโดยไม่มีมัน
- **หนังที่หยุดค้างทำให้การสำรองรอทั้งคืน** ตั้ง **ไม่นับเซสชันที่หยุดชั่วคราวหลังจาก (นาที)** เช่น 30
- **การตรวจทราฟฟิกไม่ปล่อยให้การสำรองผ่านเลย** เพิ่ม **ไม่ว่างตั้งแต่ (KiB/s)** ให้สูงกว่าที่คอนเทนเนอร์ส่งขณะไม่มีใครใช้ หลัง BombVault เริ่มทันที การตรวจรอจนได้ดูคอนเทนเนอร์ครบ **เงียบนาน (นาที)** นาที
- **การสำรองไม่เคยรันตอนกลางคืน** เมื่อตั้งช่วงเวลา การลองเกิดเฉพาะภายในนั้น การรอที่ถึงเส้นตายนอกช่วงยังจบที่เส้นตาย

## การสำรองขนาดใหญ่ถูกฆ่าเพราะหน่วยความจำหมด {#a-large-backup-was-killed-for-running-out-of-memory}

ตั้ง **ขีดจำกัดหน่วยความจำต่อการสำรองข้อมูล (MiB, 0 = ไม่จำกัด)** ในการ์ด **ประสิทธิภาพ** ใต้ **การตั้งค่า, ระบบ** ให้ต่ำกว่าที่คอนเทนเนอร์ใช้ได้พอสมควร ใกล้ขีดจำกัด restic คืนหน่วยความจำบ่อยขึ้น ซึ่งเสียความเร็วบ้าง การสำรองจึงช้าลงแทนที่จะถูกฆ่า

## การกู้คืนยกเลิกก่อนเริ่ม {#a-restore-aborted-before-it-started}

ก่อนหยุดหรือลบอะไร การกู้คืนรันการตรวจความขัดแย้งล่วงหน้า: มันยืนยันว่า IP คงที่และพอร์ตโฮสต์ที่เผยแพร่ของคอนเทนเนอร์ว่าง ถ้าคอนเทนเนอร์อื่นถืออันใดอยู่แล้ว มันยกเลิกพร้อมข้อความที่ชัดเจนและทำตามได้ แทนที่จะทิ้งการกู้คืนที่ทำค้างครึ่งทาง ปล่อยพอร์ตหรือ IP ที่ขัดแย้ง แล้วลองใหม่

ถ้าเครือข่ายของคอนเทนเนอร์ไม่มีอยู่ เช่นเพราะแอป TrueNAS ของมันถูกลบ การตรวจกู้คืนจะบอกชื่อเครือข่ายและการกู้คืนปฏิเสธก่อนเปลี่ยนอะไร ติดตั้งแอปใหม่ใน TrueNAS ด้วยชื่อเดียวกัน ซึ่งสร้างเครือข่ายอีกครั้ง แล้วกู้คืนข้อมูลของมัน

## การส่งออกแบบธรรมดาล้มเหลวแทนที่จะเขียนไฟล์ {#a-plain-export-failed-instead-of-writing-a-file}

ถ้าเปิด **เข้ารหัสการส่งออกด้วย age** ใต้ **การตั้งค่า, ระบบ** แต่ไม่ได้ตั้งผู้รับที่ใช้ได้ การส่งออกจะล้มเหลวพร้อมข้อผิดพลาดที่ชัดเจนแทนที่จะเขียนข้อความธรรมดา เพิ่มผู้รับที่ใช้ได้ (กุญแจสาธารณะ age หรือ SSH) หรือปิดการเข้ารหัสถ้าคุณตั้งใจให้การส่งออกเป็นข้อความธรรมดา ดู [การส่งออกแบบธรรมดา](backups.md#exports)

## ดัมป์ฐานข้อมูลล้มเหลว {#a-database-dump-failed}

ดัมป์ที่ล้มเหลวไม่ทำให้การสำรองรอบข้างล้มเหลว มันถูกบันทึกเป็นการรันที่ล้มเหลวของตัวเอง และเหตุผลบอกว่าต้องแก้อะไร

- **การเข้าสู่ระบบถูกปฏิเสธ** ดัมป์ลงชื่อเข้าใช้ด้วยตัวแปรรหัสผ่านของคอนเทนเนอร์เอง (`POSTGRES_PASSWORD`, `MARIADB_ROOT_PASSWORD`, `MYSQL_ROOT_PASSWORD` หรือรุ่น `_FILE` ของมัน) ตรวจมันบนคอนเทนเนอร์ฐานข้อมูล ตัวแปร `_FILE` ที่ชี้ไปยังความลับซึ่งผู้ใช้ของคอนเทนเนอร์เองอ่านไม่ได้ก็ล้มเหลวแบบเดียวกัน
- **สิทธิ์ไม่พอ** ด้วยรหัสผ่าน root แบบสุ่ม ดัมป์ลงชื่อเข้าใช้ได้เฉพาะในฐานะผู้ใช้แอป จึงได้ฐานข้อมูลเดียวนั้น และ MySQL 8.4 ขึ้นไปอาจปฏิเสธเลย ให้รหัสผ่าน root จริงแก่คอนเทนเนอร์ หรือปิดดัมป์สำหรับมัน
- **ตารางระบบต้องอัปเกรด** MariaDB ปฏิเสธการดัมป์เมื่อตารางระบบมาจากเวอร์ชันเก่า (ข้อผิดพลาด 1558) เพิ่มตัวแปร `MARIADB_AUTO_UPGRADE=1` แล้วรีสตาร์ทคอนเทนเนอร์ หรือรัน `mariadb-upgrade` ภายในมันหนึ่งครั้ง
- **ไม่มีเครื่องมือดัมป์** image แบบ slim หรือสร้างเองที่ไม่มี `pg_dump`, `mysqldump` หรือ `mariadb-dump` ดัมป์ไม่ได้ ใช้ image ทางการ หรือปิดดัมป์
- **ขีดจำกัดเวลา** ดัมป์ได้ `DB_DUMP_MAX_HOURS` (6 โดยค่าเริ่มต้น) การสำรองรอบข้างได้ `BACKUP_MAX_HOURS` และดัมป์ที่หยุดคืบหน้าจะถูกตัดหลัง `BACKUP_STALL_HOURS` สาเหตุปกติของอันสุดท้ายคือล็อกที่แอปพลิเคชันถืออยู่ เพิ่มขีดจำกัดที่ทำงาน หรือดัมป์ตอนที่แอปพลิเคชันเงียบ
- **คอนเทนเนอร์หยุดชั่วคราวหรือกำลังรีสตาร์ท** ดัมป์คุยกับเซิร์ฟเวอร์ที่กำลังรัน ถ้าคอนเทนเนอร์รีสตาร์ทไม่หยุด บันทึกของมันเองบอกเหตุผล
- **ลบดัมป์ที่เสียหายไม่ได้** ดัมป์ที่ BombVault ทำไม่เสร็จจะถูกลบอีกครั้ง เมื่อการลบนั้นล้มเหลว ดัมป์ยังอยู่ในรายการโดยทำเครื่องหมายว่าเสียหาย และคุณลบมันที่นั่นได้

## การนำเข้าล้มเหลว {#an-import-failed}

การนำเข้าหยุดคอนเทนเนอร์ ย้ายโฟลเดอร์ข้อมูลไปข้าง ๆ และให้ image สร้างโฟลเดอร์ว่างแทน ถ้าขั้นตอนก่อนการนำเข้าเองล้มเหลว โฟลเดอร์เดิมจะถูกวางกลับโดยอัตโนมัติ ถ้าการนำเข้าล้มเหลว คอนเทนเนอร์เก็บโฟลเดอร์ใหม่ไว้ และอันเดิมอยู่ข้าง ๆ เป็น `<data folder>.bombvault-before-import-<timestamp>` ข้อความผิดพลาดของการรันบอกพาธที่แน่นอน

โฟลเดอร์ข้อมูลที่เป็นชุดข้อมูลของตัวเอง เช่นบน TrueNAS เปลี่ยนชื่อไม่ได้ การนำเข้าจึงปล่อยโฟลเดอร์ไว้ที่เดิมและย้ายเนื้อหาของมันไปไว้ในโฟลเดอร์ที่เก็บไว้ข้าง ๆ ชุดข้อมูลด้านบนจึงต้องมีที่พอสำหรับมัน การนำเข้าตรวจเรื่องนั้นก่อนหยุดคอนเทนเนอร์

ถ้าจะวางกลับด้วยมือ: หยุดคอนเทนเนอร์ เปลี่ยนชื่อโฟลเดอร์ข้อมูลปัจจุบันให้พ้นทาง เปลี่ยนชื่อโฟลเดอร์ที่เก็บไว้กลับเป็นชื่อเดิม แล้วเริ่มคอนเทนเนอร์ สำหรับชุดข้อมูล ให้ย้ายเนื้อหาแทนการเปลี่ยนชื่อโฟลเดอร์ บน Unraid ตัวจัดการไฟล์ทำเรื่องนี้ได้จากแท็บ Shares

## การสำรองชุดข้อมูล ZFS ล้มเหลวหรือข้ามชุดข้อมูล {#zfs-datasets}

ทุกปัญหามีรหัสเหตุผลในวงเล็บ และหน้า [ชุดข้อมูล ZFS](zfs-datasets.md#reason-codes) ลิสต์ทั้งหมดพร้อมวิธีแก้ สามอย่างที่พบบ่อยที่สุด

- **`snapshot-loop`**: สแนปช็อตไปไม่ถึง BombVault เพราะ Host Data ไม่ส่ง mount ใหม่ผ่านเข้ามา แก้ไขคอนเทนเนอร์ ตั้ง Access Mode ของ Host Data เป็น Read/Write - Slave แล้วรีสตาร์ท BombVault
- **`key-not-loaded`**: ชุดข้อมูลที่เข้ารหัสซึ่งไม่ได้โหลดคีย์จะถูกข้าม โหลดคีย์ด้วย `zfs load-key` แล้วเมานต์ชุดข้อมูล การสำรองครั้งถัดไปจะรวมมัน
- **`ssh-auth`**: เซิร์ฟเวอร์ปฏิเสธคีย์ของ BombVault **การเชื่อมต่อ ZFS กับเซิร์ฟเวอร์นี้** ที่เปิดด้วย **ดูการเชื่อมต่อ** บนหน้าการสำรองข้อมูล แสดงคำสั่งที่อนุญาตมัน รันหนึ่งครั้งบนเซิร์ฟเวอร์

## รายการค้างที่ "กำลังเรียนรู้ N/10" {#an-entry-stays-at-learning-n10}

การตรวจความผิดปกติส่วนใหญ่เริ่มหลังการสำรองสำเร็จ 10 ครั้งของรายการ และการนับเริ่มใหม่หลัง **ทำเครื่องหมายว่าคาดไว้แล้ว** และหลังการเลือกของรายการเปลี่ยน รายการที่ไม่ได้อยู่ในตารางเวลาไม่เรียนรู้ และคอนเทนเนอร์ที่ไม่มี appdata ไม่มีอะไรให้เรียนรู้ ซึ่งป้ายของมันบอกไว้ **ความคืบหน้าการเรียนรู้** บนหน้าความผิดปกติแสดงวงแหวนสิบส่วนต่อรายการ

## การเก็บรักษาหยุดลบข้อมูลสำรองเก่าของรายการหนึ่ง {#retention-stopped-deleting-old-backups-of-one-entry}

ความผิดปกติระดับร้ายแรงที่เปิดอยู่เก็บไว้: ต้นทางของรายการแทบว่าง หดลงมาก หรือการสำรองหนึ่งครั้งเก็บข้อมูลส่วนใหญ่ซ้ำอีกครั้ง เปิดความผิดปกติจากป้ายบนรายการ ถ้าข้อมูลหายหรือถูกเข้ารหัส ให้กู้คืนจากข้อมูลสำรองล่าสุดที่ยังดีซึ่งลิงก์ไว้ก่อน แล้วยืนยันความผิดปกติ หรือทำเครื่องหมายว่าคาดไว้แล้วถ้าการเปลี่ยนแปลงเป็นของคุณ และการรันครั้งถัดไป prune ตามปกติ ตัวอย่างการเก็บรักษาทำเครื่องหมายรายการแบบนั้นว่าเก็บไว้ สำหรับรายการ ZFS มีเฉพาะชุดข้อมูลที่ความผิดปกติระบุเท่านั้นที่เก็บข้อมูลสำรองเก่า ชุดข้อมูลอื่นของต้นไม้ถูก prune ตามปกติ

## prune ด้วยมือบอกว่าเก็บบางรายการไว้ {#manual-prune-says-some-entries-were-kept}

สาเหตุเดียวกัน: prune ปล่อยข้อมูลสำรองเก่าของรายการที่มีความผิดปกติแบบนั้นไว้และระบุชื่อรายการในข้อความ อย่างอื่นถูก prune ตามปกติ

## การสำรองล้มเหลวด้วย "on no mounted pool or share" {#no-mounted-pool}

บน Unraid `/mnt` อยู่ในหน่วยความจำ โฟลเดอร์ในนั้นที่ไม่มี pool เมานต์อยู่จึงหายไปเมื่อรีบูตครั้งถัดไป และถูกซ่อนไว้เมื่อ pool กลับมา BombVault ไม่ยอมเขียนข้อมูลสำรองหรือ ZIP ของแฟลชลงที่นั่น แม้ในโฟลเดอร์นั้นจะมีที่เก็บจากการเขียนครั้งก่อนอยู่แล้วก็ตาม เมานต์ pool แล้วรันการสำรองอีกครั้ง

## การนำเข้าประวัติบอกว่าอ่านที่เก็บไม่ได้ {#history-import-says-a-repository-could-not-be-read}

หลังการอัปเกรด BombVault อ่านขนาดของการสำรองก่อนหน้าจากแต่ละที่เก็บหนึ่งครั้ง ที่เก็บที่เข้าไม่ถึงตอนนั้น เช่นปลายทางนอกสถานที่ที่ล่มหรือ share ที่ไม่ได้เมานต์ จะถูกนับในการ์ด **ความผิดปกติ** ใต้ **การตั้งค่า, ยืนยัน** และลองใหม่วันละครั้ง รายการของมันเรียนรู้จากการสำรองใหม่ในระหว่างนั้น

## คำเตือนพื้นที่ดิสก์ไม่ตรงกับแดชบอร์ด Unraid {#the-disk-space-warning-does-not-match-the-unraid-dashboard}

บน user share ของ Unraid (`/mnt/user`) พื้นที่ว่างคือของทั้งอาร์เรย์ ไม่ใช่ของดิสก์เดียว ปลายทางที่จัดเก็บระยะไกลที่ BombVault เข้าถึงผ่าน rclone เช่น SFTP, Hetzner Storage Box, SMB, WebDAV หรือไดรฟ์คลาวด์ จะถูกวัดเมื่อฝั่งไกลรายงานพื้นที่ว่าง เช่นเดียวกับที่อยู่ `sftp:` ที่พิมพ์เอง ที่เก็บ S3, B2 และ REST ไม่มีตัวเลข: ปลายทางของมันบอก **ไม่ทราบขนาด** และการ์ด **ความผิดปกติ** ลิสต์มันว่าไม่ได้วัด

## ผู้ช่วย AI เชื่อมต่อไม่ได้ {#an-ai-assistant-cannot-connect}

[หน้าเซิร์ฟเวอร์ MCP](mcp.md#troubleshooting) ลิสต์ความหมายของแต่ละรหัสสถานะและการปฏิเสธของ endpoint MCP และสิ่งที่ต้องทำ

## คอนเทนเนอร์รีสตาร์ทไม่หยุดหรือดูไม่แข็งแรง {#the-container-keeps-restarting-or-looks-unhealthy}

BombVault รายงาน healthy/unhealthy จาก `/api/health` ของมันเอง เครื่องมือซ่อมตัวเอง (เช่น Autoheal) รีสตาร์ทมันอัตโนมัติได้ถ้าเอนจินค้างขึ้นมา ตรวจบันทึกคอนเทนเนอร์และการ์ด **การผสานรวมโฮสต์** เพื่อหาสาเหตุเบื้องหลัง

## ปลายทางที่จัดเก็บไม่ยอมบันทึก {#location-refused}

BombVault ตรวจปลายทางก่อนบันทึก และการปฏิเสธบอกเหตุผลเป็นประโยค ที่พบบ่อย

- **"This location lies inside another repository or target, or contains one."** ที่เก็บในที่เก็บจะทำให้เสียทั้งสอง ข้อความระบุอีกที่หนึ่ง เลือกโฟลเดอร์อื่น หรือลบอันนั้นก่อน
- **เป็นที่เก็บที่คุณตั้งไว้** ปลายทางเป็นหนึ่งในแถวใต้ **ที่เก็บข้อมูล** หรืออยู่ข้างในหรือรอบมัน เลือกที่อื่น หรือลบที่เก็บนั้นก่อน
- **ที่เดียวกับโฟลเดอร์ของตัวเองของส่วน** สำเนาบนโฟลเดอร์ของตัวเองของส่วนจะคัดลอกข้อมูลสำรองของมันทับตัวเองทุกรอบ จึงถูกปฏิเสธ เลือกที่อื่น หรือดู [โฟลเดอร์ของตัวเองของส่วน](offsite-recovery.md#own-folder)
- **"That is not an off-site target of this domain"** มาจากลิงก์ไปยังปลายทางที่ถูกลบ เวอร์ชันปัจจุบันล้างสิ่งเหล่านี้ตอนเริ่มและในการนำเข้า ถ้ายังเห็นอยู่ ให้อัปเดต BombVault
- **พาธโฮสต์เต็ม** เช่น `/mnt/user/backups` BombVault รันในคอนเทนเนอร์ จึงต้องการพาธใต้ Host Data คือ `user/backups` และข้อความบอกอันที่ต้องกรอก

## ปลายทางระยะไกลบอกว่าที่เก็บหายไป {#repository-gone}

ปลายทางที่เคยมีข้อมูลสำรองแล้วจู่ ๆ ไม่มีที่เก็บ จะไม่ได้ที่เก็บใหม่ที่ว่างเปล่าขึ้นมาเอง เพราะอันนั้นจะบังอันจริงเมื่อดิสก์กลับมา rest-server ที่ดิสก์ไม่ได้เมานต์เป็นสาเหตุปกติ เมานต์ดิสก์อีกครั้งแล้วรันการสำรองหรือการคัดลอกอีกหนึ่งครั้ง เฉพาะเมื่อคุณล้างหรือลบที่เก็บเดิมโดยตั้งใจ ให้กด **สร้างที่เก็บข้อมูลใหม่ตรงนี้** บนหน้าของปลายทาง มันเริ่มใหม่สำหรับทุกส่วนของปลายทางนั้นพร้อมกัน

## การลงชื่อเข้าใช้คลาวด์หมดอายุ {#cloud-sign-in-expired}

การทดสอบหรือการคัดลอกครั้งถัดไปจะบอกว่าการลงชื่อเข้าใช้หมดอายุ **เปลี่ยนการเชื่อมต่อ** บนหน้าของปลายทางลงชื่อเข้าใช้ใหม่

- **Box, Jottacloud และอื่น ๆ ที่ใช้ refresh token แบบครั้งเดียว:** BombVault เก็บโทเค็นที่ rclone รีเฟรชไว้ รวมถึงข้ามการรีสตาร์ทและในชุดกู้คืน หลังการกู้คืนจากข้อมูลสำรองการตั้งค่าที่เก่ากว่า โทเค็นในนั้นอาจหมดแล้ว ให้ลงชื่อเข้าใช้อีกครั้ง ที่เก็บยังอยู่ตามเดิม
- **iCloud Drive:** Apple จบการลงชื่อเข้าใช้หลัง 30 วัน ต้องใช้ trust token และคุกกี้ใหม่จาก `rclone config`
- **OneDrive:** การลงชื่อเข้าใช้ที่มีหลายไดรฟ์ถามว่าจะใช้อันไหน ปลายทางที่ไม่ได้เลือกจึงใช้ไม่ได้จนกว่าคุณจะเลือก สำหรับ OneDrive Business และ Google Drive ดูหมายเหตุเรื่องข้อมูลที่ถูกตัดใต้ [ปลายทางที่จัดเก็บ](offsite-recovery.md#destinations)

## "The off-site copy of the last backup is still running" {#copy-still-running}

การสำรองก่อนหน้าเสร็จแล้ว และสำเนาของมันยังอยู่ระหว่างทาง ซึ่งบล็อกการสำรองใหม่ของส่วนนั้น รอจนส่วนหัวสถานะไม่บอก **กำลังคัดลอกไปนอกสถานที่** อีก ปุ่มที่เริ่มการสำรองก็บอกเหมือนกันขณะรอ สำเนาแรกไปยังปลายทางใหม่ใช้เวลาหลายชั่วโมงได้ ดู [ตัวอย่าง S3](offsite-recovery.md#example-s3)

## เรพลิกา ZFS หยุดเพราะปลายทางมีสแนปช็อตใหม่กว่า {#replica-target-newer}

ปลายทางมีสแนปช็อตใหม่กว่าอันใหม่สุดที่มันใช้ร่วมกับเซิร์ฟเวอร์นี้ เช่นเพราะชุดข้อมูลที่นี่ถูก rollback หรือสำเนาบนปลายทางถูกเปลี่ยน การ์ดเรพลิกาและประวัติการรันระบุสแนปช็อตใต้ **ย้อนปลายทางกลับไปที่** รัน `zfs rollback -r` ไปยังสแนปช็อตนั้นบนปลายทาง สำหรับแต่ละชุดข้อมูลที่การรันระบุ แล้วกด **จำลองตอนนี้** ดู [สแนปช็อตอยู่นานแค่ไหน](zfs-datasets.md#replica-retention)

## VM ที่มีสแนปช็อต Unraid ล้มเหลวและระบุไฟล์ {#vm-chain}

BombVault ตามห่วงโซ่ backing ของแต่ละดิสก์และสำรองทุกไฟล์ในนั้น ห่วงโซ่ที่ตามไปจนสุดไม่ได้ทำให้การสำรองล้มเหลว แทนที่จะเว้นดิสก์บางส่วนไว้ และข้อความระบุไฟล์ ตรวจว่าไฟล์มีอยู่ใต้ `/mnt` และสแนปช็อตยังลิสต์อยู่ใน VM Manager ไฟล์นอก Host Data อ่านไม่ได้เลย ดู [VM ที่มีสแนปช็อต Unraid](vm-backup-ssh-setup.md#unraid-snapshots)

## สำเนานอกสถานที่รอการตัดสินใจของคุณหลังการสร้างใหม่ {#copies-paused}

หลัง **ค้นหาการสำรองข้อมูล** หรือตัวช่วยฉุกเฉินที่ไม่ได้กู้คืนการตั้งค่า หรือเมื่อส่วนหนึ่งพบข้อมูลสำรองของตัวเองจากก่อนฐานข้อมูลนี้ สำเนานอกสถานที่ของส่วนนั้นจะรอ เพราะ BombVault ไม่รู้แล้วว่าคุณเว้นรายการไหนไว้ **ต้องดูแล** และหน้าของปลายทางที่จัดเก็บจะถามเรื่องนี้ กด **รับเป็นข้อมูลสำรองของเซิร์ฟเวอร์นี้** เพื่อทำต่อ หรือ **ตรวจสอบกฎก่อน** เพื่อดูกฎของส่วนนั้นก่อนตัดสินใจ การนำเข้าไฟล์การตั้งค่าไม่ได้ตัดสินใจแทนคุณ ดู [หลังสร้างใหม่](offsite-recovery.md#after-a-rebuild)

## การแจ้งเตือนไม่มาถึง {#notifications-do-not-arrive}

เริ่มด้วย **ส่งทดสอบ** ใต้ **การตั้งค่า, การแจ้งเตือน** บรรทัดใต้การ์ดบอกว่าเกิดอะไรขึ้น

- **ไม่มีอะไรถูกส่งเลย** ตรวจ **แจ้งเตือน** ถ้าเป็น **ไม่เคย** จะไม่มีข้อความออกไป มีแค่การ ping ไปยัง URL ของ Healthchecks และถ้าเป็น **เฉพาะเมื่อล้มเหลว** การรันที่ดีจะเงียบ เมื่อเปิด **สรุปการรันตามกำหนดเวลา** การรันตามกำหนดส่งหนึ่งข้อความสรุปตอนจบ
- **ที่อยู่ใหม่** หลังคุณเปลี่ยนเซิร์ฟเวอร์ของ Matrix, Gotify หรืออีเมล ช่องจะขอโทเคนหรือรหัสผ่านอีกครั้ง และที่อยู่ใหม่จะถูกบันทึกเมื่อคุณพิมพ์เท่านั้น BombVault ไม่ส่งความลับเก่าไปยังที่ใหม่
- **Gotify** บอกว่าเซิร์ฟเวอร์ปฏิเสธโทเคนแอป: คัดลอกใหม่จากแอปพลิเคชันใน Gotify **URL ของเซิร์ฟเวอร์** คือที่อยู่ฐาน ไม่มี `/message`
- **Webhook:** ตรวจว่า **รูปแบบ Webhook** ตรงกับบริการ ที่อยู่ Discord ต้องใช้ **Discord** และ ntfy ต้องใช้ **ntfy**
- **การแจ้งเตือน Unraid** ทำงานผ่านการเชื่อมต่อ SSH ของโฮสต์ ดังนั้นทดสอบอันนั้นก่อนที่ **การตั้งค่า, การเชื่อมต่อ** บนแพลตฟอร์มอื่นมันปิดอยู่ และการ์ดบอกไว้
- **อีเมลแจ้งเตือนไม่เคยมา** ตรวจ **การเข้ารหัส** เทียบกับพอร์ต มักเป็น **STARTTLS** ที่ 587 หรือ **TLS (implicit)** ที่ 465

ping ของ Healthchecks ไม่ขึ้นกับสิ่งเหล่านี้ ดู [Healthchecks](notifications.md#healthchecks)

## แอป Android เปิดเซิร์ฟเวอร์ไม่ได้ {#android-cannot-open}

หน้าจอเริ่มต้นบอกเหตุผลที่การ์ดของเซิร์ฟเวอร์

- **ไม่ได้เชื่อมต่อ:** ทั้งที่อยู่ของเซิร์ฟเวอร์และรีเลย์ไม่ตอบ เมื่อเป็น **ไม่ใช้รีเลย์** แอปเข้าถึงเซิร์ฟเวอร์ได้ที่ที่อยู่ของมันเองเท่านั้น
- **ตรวจสอบใบรับรอง:** เซิร์ฟเวอร์แสดงใบรับรองอื่นนอกจากที่คุณเชื่อถือ แอปเปิดมันหลังจากคุณเชื่อถืออันใหม่เท่านั้น ดังนั้นให้แน่ใจว่าการเปลี่ยนแปลงเป็นของคุณ
- **ต้องลงชื่อเข้าใช้:** เซิร์ฟเวอร์ที่เพิ่มด้วยที่อยู่ขอรหัสผ่าน ดู [โทรศัพท์ไปโผล่ที่หน้าเข้าสู่ระบบ](#a-phone-lands-on-the-login-page) ด้วย
- **คีย์เปลี่ยน:** หน้าจอเริ่มต้นแสดงลายนิ้วมือของคีย์ใหม่ และหน้าเปิดหลังจากคุณเชื่อถือมันเท่านั้น ดู [เมื่อไม่อยู่บ้าน](android.md#away)

## ผู้ใช้อื่นอ่านที่เก็บในเครื่องไม่ได้ {#repository-permissions}

ที่เก็บในเครื่องยังอ่านได้สำหรับผู้ใช้อื่น เช่นผู้ใช้ซิงก์ผ่าน SMB ก่อน 10.4.1 ไฟล์ที่ prune, แท็ก, pull, การย้ายส่วน, การลบ หรือการสำรองสแตกเขียนอาจอ่านไม่ได้จนถึงคืนถัดไป อัปเดต BombVault แล้วจะอ่านได้ทันที ที่เก็บของการสำรองตัวเองอ่านได้เฉพาะ root โดยตั้งใจ เพราะมีการตั้งค่าของ BombVault

## ยังติดอยู่ใช่ไหม {#still-stuck}

- อ่านหน้า [การกำหนดค่า](configuration.md) และ [นอกสถานที่และการกู้คืน](offsite-recovery.md) ฉบับเต็ม
- **รายงานบั๊ก** ในการ์ด **ความช่วยเหลือ** ใต้ **การตั้งค่า, ข้อมูล** ดาวน์โหลด ZIP สำหรับ issue บน GitHub: การตรวจโฮสต์ การกำหนดค่าของคุณโดยลบทุกความลับ การรันล่าสุด สิ่งที่ตั้งเวลาไว้ถัดไป และบันทึกล่าสุดนับจากที่คอนเทนเนอร์เริ่มครั้งล่าสุด มันยังมีดัมป์ล่าสุดของแต่ละฐานข้อมูล รายการ ZFS พร้อม mount ของมัน ความผิดปกติที่เปิดอยู่ และจำนวนคีย์ MCP ที่มี รหัสผ่าน โทเคน และการกำหนดค่า rclone ถูกลบออก และชุดนี้บอกไว้ในแมนิเฟสต์ของมันเอง ต้องมีรหัสผ่านเข้าสู่ระบบ สำหรับการแครชที่ทำให้คอนเทนเนอร์รีสตาร์ท ดู `docker logs`
