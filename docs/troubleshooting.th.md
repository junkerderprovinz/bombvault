# การแก้ปัญหา

FAQ สั้นๆ สำหรับตารางการแก้ปัญหาฝั่งโฮสต์ของ VM ผ่าน SSH ฉบับเต็ม (permission-denied, host-key verification, ตัวแปรเทมเพลตที่ขาดหายไป และอื่นๆ) ดู [คู่มือการสำรองข้อมูล VM ผ่าน SSH](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md) บน GitHub

## มีบางอย่างเชื่อมต่อไม่ถูกต้อง

เพิ่มการ์ด **การผสานรวมโฮสต์** ลงในภาพรวมใต้ **ปรับแต่ง** การตรวจสอบการผสานรวมโฮสต์ตรวจสอบทุกการเมานต์และ CLI (Docker socket, libvirt, restic, qemu-img, rclone) และรายงานส่วนที่ขาดหายไป และ **ตรวจสอบเดี๋ยวนี้** รันอีกครั้ง เริ่มที่นี่ก่อนสันนิษฐานว่าเป็นบั๊ก: การเมานต์ที่หายไปหรือโฮสต์ที่เข้าถึงไม่ได้จะปรากฏทันที

## ฉันเข้าถึงเว็บ UI ไม่ได้

BombVault ให้บริการ HTTPS พร้อมใช้งานทันทีบนพอร์ต `3443` (ใบรับรองแบบ self-signed) ดังนั้นเปิด `https://<your-unraid-ip>:3443` ยอมรับคำเตือนใบรับรองแบบ self-signed หรือวาง BombVault ไว้หลัง reverse proxy ด้วยใบรับรองของคุณเอง หากคุณรันด้วย `HTTP_ONLY=true` มันจะให้บริการ HTTP ธรรมดาบนพอร์ต `3000` แทน (มีไว้สำหรับใช้หลัง proxy ที่ terminate TLS)

## ฉันทำ APP_KEY หาย

`APP_KEY` ใช้สร้างรหัสผ่านของรีพอสิทอรี restic หากไม่มีมัน ไม่มีชุดกู้คืน และไม่มีสำเนาที่ฝากไว้ในกลุ่มของคุณ ข้อมูลสำรองที่เข้ารหัสจะกู้คืนไม่ได้ นี่คือเหตุผลที่ภาพรวมแสดง **บันทึกชุดกู้คืนของคุณ** จนกว่าคุณจะดาวน์โหลด ดู [Off-site & recovery](offsite-recovery.md#recovery-kit) สร้างคีย์ด้วย `openssl rand -hex 32` และเก็บไว้นอกเซิร์ฟเวอร์ก่อนจะพึ่งพาการสำรองข้อมูลใด ๆ

## ฉันลืมรหัสผ่านเข้าสู่ระบบ

เลือก **ลืมรหัสผ่าน?** บนหน้าเข้าสู่ระบบ BombVault เขียนรหัส 12 ตัวอักษรลงในบันทึกของ container (ใน Unraid: แท็บ Docker ไอคอน BombVault แล้วเลือก **Logs**) พิมพ์รหัสนั้นพร้อมรหัสผ่านใหม่ภายใน 10 นาที การรีเซ็ตยังปิดการยืนยันตัวตนสองขั้นตอน ลบพาสคีย์ทั้งหมด เพิกถอนโทเค็น API คีย์ MCP และการลงชื่อเข้าใช้ผ่าน OAuth ทั้งหมด สิ้นสุดเซสชันอื่นทั้งหมด และปิดการจับคู่โทรศัพท์ เพิ่มพาสคีย์อีกครั้งใต้ **การตั้งค่า, ความปลอดภัย** เปิดการจับคู่โทรศัพท์กลับที่นั่น และสร้างโทเค็นและคีย์ใหม่ในที่ที่ยังต้องใช้ ดู [โมเดลความปลอดภัย](configuration.md#login)

## การสำรองข้อมูลหยุดและบอกว่าเปิดคีย์ไม่ได้อีกแล้ว

เซิร์ฟเวอร์นี้รับช่วงคีย์ข้อมูลสำรองของเซิร์ฟเวอร์อื่นในตัวช่วยฉุกเฉิน และ `APP_KEY` ถูกเปลี่ยนหลังจากนั้น คีย์ที่รับช่วงถูกปิดผนึกด้วย APP_KEY เดิม BombVault จึงเปิดไม่ได้และไม่สำรองอะไรเลย แทนที่จะเขียนด้วยคีย์ที่ผิด **ต้องดูแล** บนภาพรวมระบุเรื่องนี้ ตั้ง APP_KEY กลับเป็นค่าเดิม หรืออัปโหลดชุดกู้คืนอีกครั้งบนหน้าการกู้คืนใต้ **ฉุกเฉิน**

## โทรศัพท์ไปลงที่หน้าเข้าสู่ระบบ

โทรศัพท์ที่จับคู่ได้เซสชันผ่านกลุ่มเฉพาะตราบที่ **โทรศัพท์จับคู่ด้วยคำสิบสองคำของกลุ่มได้** เปิดอยู่ใต้ **การตั้งค่า, ความปลอดภัย** การรีเซ็ตรหัสผ่านปิดมัน แอปที่เก่ากว่าเซิร์ฟเวอร์ก็ไม่ได้เซสชันจนกว่าจะอัปเดต เซิร์ฟเวอร์ที่เพิ่มด้วยที่อยู่จะถามรหัสผ่านเสมอ โทรศัพท์ที่ถูกลบออกจากหน้าอินสแตนซ์จะกลับมาในสถานะปิดเมื่อเปิดแอปอีกครั้ง หากต้องการให้เข้ามาได้ ให้เปิด **สอบถามอินสแตนซ์นี้** ใต้ **การเฝ้าระวัง** ในรายละเอียดของโทรศัพท์

## การสำรองข้อมูล VM เชื่อมต่อไม่ได้

การสำรองข้อมูล VM ติดต่อ libvirt ผ่าน SSH ไม่เคยผ่านการเมานต์

- ยืนยันว่า SSH ถูกเปิดใช้งานบนโฮสต์และคีย์สาธารณะของ BombVault ได้รับอนุญาตใน `/root/.ssh/authorized_keys` (การตั้งค่า, การเชื่อมต่อ, SSH ของโฮสต์ แสดงคีย์และปุ่ม **ทดสอบการเชื่อมต่อ**)
- บนเครือข่าย `br0.x` ที่กำหนดเอง ให้ตั้ง `LIBVIRT_HOST` เป็น LAN IP ของ Unraid ของคุณ (container ไม่สามารถเข้าถึงโฮสต์ผ่าน `host.docker.internal` ที่นั่นได้) เปิดใช้งาน **Settings, Docker, Host access to custom networks**
- หากคุณเปลี่ยนพอร์ต SSH ของ Unraid ให้ตั้ง `LIBVIRT_SSH_PORT` ให้ตรง
- บน TrueNAS ให้ตั้ง `LIBVIRT_URI` ด้วยซ็อกเก็ต libvirt ของ TrueNAS เอง ให้ capability `SETPCAP` แก่แอป และเพิ่มคีย์ให้ root ใน **Credentials, Users** (ดู [TrueNAS SCALE](getting-started.md#truenas))
- การวินิจฉัยทีละขั้นตอนฉบับเต็ม (การทดสอบการเข้าถึง, การกำหนดเส้นทาง VLAN, `Permission denied (publickey)`, `Host key verification failed`) อยู่ใน [คู่มือการสำรองข้อมูล VM ผ่าน SSH](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md)

## สแนปช็อต VM ขณะทำงานไม่ได้รัน

สแนปช็อตขณะทำงานต้องการ qemu guest agent ที่ติดตั้งใน VM และดิสก์อยู่บน `/mnt/cache` (หรือ `/mnt/diskX`) ไม่ใช่ `/mnt/user` บน VM ที่ปิดอยู่ ขณะทำงานจะย้อนกลับไปใช้แบบราบรื่นโดยอัตโนมัติ การสำรองข้อมูลแบบราบรื่นจะปิด VM, สำรองข้อมูลดิสก์ แล้วรีสตาร์ทมัน ดังนั้นจึงสอดคล้องเสมอ มันรอให้ guest ปิดเครื่องนานสูงสุดสิบนาทีและไม่เคยบังคับปิด guest ที่เป็น Windows ซึ่งกำลังติดตั้งอัปเดตจึงไม่ถูกตัดกลางทาง guest ที่ยังทำงานอยู่หลังจากนั้นจะถูกปล่อยไว้ตามเดิม และการสำรองข้อมูลครั้งนั้นจะล้มเหลวพร้อมเหตุผล

## การสำรองข้อมูลล้มเหลวด้วย "repository is already locked"

โดยปกติคือล็อก restic กำพร้าที่เหลือจากตอนที่ container ถูกอัปเดตหรือรีสตาร์ทกลางการดำเนินการ BombVault ตรวจพบล็อกที่พิสูจน์ได้ว่าเป็นกำพร้า ล้างด้วยการบังคับ และลองใหม่หนึ่งครั้งโดยอัตโนมัติ หากยังอยู่ เปิดการ์ด **ตรวจสอบข้อมูลสำรอง** ใต้ **การตั้งค่า, ยืนยัน** แล้วเลือก **ปลดล็อก** ใต้ **เพิ่มเติม** ในแถวของส่วนที่ได้รับผลกระทบ เพื่อล้างล็อกที่ค้างด้วยมือ ปัญหาจริงยังปรากฏออกมา ไม่ถูกซ่อน หลังรีสตาร์ท BombVault รอจนล็อกเช่นนั้นผ่านไปสิบนาทีโดยไม่มีการรีเฟรช restic ที่ยังรันอยู่ เช่นใน BombVault ตัวที่สองบนรีพอสิทอรีเดียวกัน รีเฟรชล็อกของมันทุกห้านาที

## สำเนานอกสถานที่ของฉันไม่เกิดขึ้นหลังการสำรองข้อมูล

การจำลองนอกสถานที่เป็นแบบทำเท่าที่ทำได้โดยการออกแบบ ปัญหานอกสถานที่จึงไม่ทำให้การสำรองในเครื่องล้มเหลว ตรวจว่าปลายทางคัดลอกเมื่อไร: การ์ด **คัดลอก** ของมันบอก **หลังการสำรองข้อมูลทุกครั้ง** หรือระบุแผนของตัวเอง และ **การตั้งค่า, ตารางเวลา, สำเนานอกสถานที่รายส่วน** ให้ส่วนหนึ่งมีแผนของตัวเองได้ ใช้ **จำลองตอนนี้** ในการ์ดสำเนานอกสถานที่ของส่วนใต้ **การตั้งค่า, ปลายทาง** เพื่อรันตามต้องการ และดูส่วนหัวสถานะของภาพรวมซึ่งบอกว่า **กำลังคัดลอกไปนอกสถานที่** ขณะรัน การคัดลอกที่ล้มเหลวแสดงใต้ **ต้องดูแล**

## ใบรับรองของ rest-server ไม่ได้รับความเชื่อถือ

restic ปฏิเสธใบรับรองที่มันไม่รู้จัก และข้อความแสดงข้อผิดพลาดจะบอกว่าต้องวางใบรับรองไว้ที่ไหน คัดลอกใบรับรองแบบ self-signed ของ rest-server หรือใบรับรองของผู้ออกใบรับรองที่ลงนามให้มัน เป็นไฟล์ PEM ไปไว้ในโฟลเดอร์ `certs` ของโฟลเดอร์ข้อมูลของ BombVault (`/config/certs` ใน container และ `appdata/bombvault/certs` บน Unraid) แล้วทดสอบอีกครั้ง ไม่ต้องรีสตาร์ท

## การสำรองข้อมูลขนาดใหญ่ถูกปิดเพราะหน่วยความจำไม่พอ

ตั้ง **ขีดจำกัดหน่วยความจำต่อการสำรองข้อมูล (MiB, 0 = ไม่จำกัด)** ในการ์ด **ประสิทธิภาพ** ใต้ **การตั้งค่า, ระบบ** ให้ต่ำกว่าหน่วยความจำที่ container ใช้ได้พอสมควร เมื่อใกล้ขีดจำกัด restic จะคืนหน่วยความจำบ่อยขึ้น ซึ่งทำให้ช้าลงบ้าง การสำรองข้อมูลจึงช้าลงแทนที่จะถูกปิด

## การกู้คืนถูกยกเลิกก่อนที่จะเริ่ม

ก่อนที่จะมีการหยุดหรือลบอะไร การกู้คืนจะรันการตรวจสอบความขัดแย้งก่อนเริ่ม: มันตรวจสอบว่า IP แบบสแตติกและพอร์ตโฮสต์ที่เผยแพร่ของ container ว่างอยู่ หาก container อื่นถือครองอันหนึ่งอยู่แล้ว มันจะยกเลิกพร้อมข้อความที่ชัดเจนและนำไปปฏิบัติได้แทนที่จะทิ้งการกู้คืนที่ทำค้างไว้ครึ่งทาง ปลดพอร์ตหรือ IP ที่ขัดแย้ง แล้วลองใหม่

หากเครือข่ายของ container ไม่มีอยู่ เช่น เพราะแอป TrueNAS ของมันถูกลบไปแล้ว การตรวจก่อนการกู้คืนจะระบุชื่อเครือข่ายนั้น และการกู้คืนจะปฏิเสธก่อนที่จะเปลี่ยนแปลงอะไร ให้ติดตั้งแอปใหม่ใน TrueNAS ด้วยชื่อเดิม ซึ่งจะสร้างเครือข่ายขึ้นใหม่ แล้วจึงกู้คืนข้อมูลของมัน

## การส่งออกแบบธรรมดาล้มเหลวแทนที่จะเขียนไฟล์

หาก **เข้ารหัสการส่งออกด้วย age** เปิดอยู่ใต้ **การตั้งค่า, ระบบ** แต่ไม่มีผู้รับที่ถูกต้อง การส่งออกจะล้มเหลวพร้อมข้อผิดพลาดที่ชัดเจนแทนที่จะเขียนข้อความธรรมดา เพิ่มผู้รับที่ถูกต้อง (คีย์สาธารณะ age หรือคีย์สาธารณะ SSH) หรือปิดการเข้ารหัสหากตั้งใจให้การส่งออกเป็นข้อความธรรมดา ดู [Features](features.md)

## การดัมป์ฐานข้อมูลล้มเหลว

ดัมป์ที่ล้มเหลวไม่เคยทำให้การสำรองข้อมูลรอบตัวมันล้มเหลว มันถูกบันทึกเป็นการทำงานที่ล้มเหลวของตัวเอง และเหตุผลจะบอกว่าต้องแก้อะไร

- **ถูกปฏิเสธการเข้าสู่ระบบ** ดัมป์เข้าสู่ระบบด้วยตัวแปรรหัสผ่านของคอนเทนเนอร์เอง (`POSTGRES_PASSWORD`, `MARIADB_ROOT_PASSWORD`, `MYSQL_ROOT_PASSWORD` หรือรุ่น `_FILE` ของตัวแปรเหล่านี้) ตรวจสอบที่คอนเทนเนอร์ฐานข้อมูล ตัวแปร `_FILE` ที่ชี้ไปยังความลับซึ่งผู้ใช้ของคอนเทนเนอร์เองอ่านไม่ได้ ก็ล้มเหลวแบบเดียวกัน
- **สิทธิ์ไม่พอ** เมื่อรหัสผ่าน root เป็นแบบสุ่ม ดัมป์จะเข้าสู่ระบบได้เพียงในฐานะผู้ใช้ของแอป จึงได้เฉพาะฐานข้อมูลนั้นฐานเดียว และ MySQL 8.4 ขึ้นไปอาจปฏิเสธไปเลย ให้ตั้งรหัสผ่าน root จริงให้คอนเทนเนอร์ หรือปิดการดัมป์ของมัน
- **ตารางระบบต้องอัปเกรด** MariaDB จะปฏิเสธการดัมป์เมื่อตารางระบบของมันมาจากเวอร์ชันที่เก่ากว่า (ข้อผิดพลาด 1558) ให้เพิ่มตัวแปร `MARIADB_AUTO_UPGRADE=1` แล้วรีสตาร์ทคอนเทนเนอร์ หรือรัน `mariadb-upgrade` ภายในคอนเทนเนอร์หนึ่งครั้ง
- **ไม่มีเครื่องมือดัมป์** อิมเมจแบบบางหรือที่สร้างเองซึ่งไม่มี `pg_dump`, `mysqldump` หรือ `mariadb-dump` จะดัมป์ไม่ได้ ให้ใช้อิมเมจทางการ หรือปิดการดัมป์
- **ขีดจำกัดเวลา** ดัมป์หนึ่งครั้งได้ `DB_DUMP_MAX_HOURS` (ค่าเริ่มต้น 6) การสำรองข้อมูลรอบตัวมันได้ `BACKUP_MAX_HOURS` และดัมป์ที่หยุดคืบหน้าจะถูกตัดหลังจาก `BACKUP_STALL_HOURS` กรณีหลังมักเกิดจากล็อกที่แอปพลิเคชันถืออยู่ ให้เพิ่มขีดจำกัดที่ทำงาน หรือดัมป์ตอนที่แอปพลิเคชันว่าง
- **คอนเทนเนอร์ถูกพักหรือกำลังรีสตาร์ท** ดัมป์คุยกับเซิร์ฟเวอร์ที่กำลังทำงาน ถ้าคอนเทนเนอร์รีสตาร์ทซ้ำๆ บันทึกของมันเองจะบอกเหตุผล
- **ลบดัมป์ที่เสียหายไม่ได้** ดัมป์ที่ BombVault ทำไม่สำเร็จจะถูกลบทิ้ง เมื่อการลบนั้นล้มเหลว ดัมป์จะค้างอยู่ในรายการพร้อมเครื่องหมายว่าเสียหาย และคุณลบมันได้จากตรงนั้น

## การนำเข้าล้มเหลว

การนำเข้าจะหยุดคอนเทนเนอร์ ย้ายโฟลเดอร์ข้อมูลไปไว้ข้างๆ แล้วให้อิมเมจสร้างโฟลเดอร์เปล่าขึ้นแทนที่ ถ้าขั้นตอนก่อนการนำเข้าจริงล้มเหลว โฟลเดอร์เดิมจะถูกวางกลับเองโดยอัตโนมัติ ถ้าการนำเข้าเองล้มเหลว คอนเทนเนอร์จะเหลือโฟลเดอร์ใหม่ไว้ ส่วนโฟลเดอร์เดิมจะอยู่ข้างๆ ในชื่อ `<โฟลเดอร์ข้อมูล>.bombvault-before-import-<เวลา>` ข้อความแสดงข้อผิดพลาดของการทำงานจะบอกเส้นทางที่แน่นอน

โฟลเดอร์ข้อมูลที่เป็นชุดข้อมูลในตัวเอง เช่นบน TrueNAS เปลี่ยนชื่อไม่ได้ ในกรณีนี้การนำเข้าจะคงโฟลเดอร์ไว้ที่เดิมและย้ายเนื้อหาไปไว้ในโฟลเดอร์ที่เก็บไว้ข้าง ๆ ชุดข้อมูลที่อยู่เหนือขึ้นไปจึงต้องมีที่ว่างพอสำหรับเนื้อหานั้น การนำเข้าจะตรวจเรื่องนี้ก่อนหยุดคอนเทนเนอร์

วิธีวางกลับด้วยมือ: หยุดคอนเทนเนอร์ เปลี่ยนชื่อโฟลเดอร์ข้อมูลปัจจุบันให้พ้นทาง เปลี่ยนชื่อโฟลเดอร์ที่เก็บไว้กลับเป็นชื่อเดิม แล้วเริ่มคอนเทนเนอร์ สำหรับชุดข้อมูล ให้ย้ายเนื้อหาแทนการเปลี่ยนชื่อโฟลเดอร์ บน Unraid ตัวจัดการไฟล์ในแท็บ Shares ทำสิ่งนี้ได้

## การสำรองชุดข้อมูล ZFS ล้มเหลวหรือข้ามชุดข้อมูลไป {#zfs-datasets}

ทุกปัญหามีรหัสเหตุผลในวงเล็บเหลี่ยม และหน้า [ชุดข้อมูล ZFS](zfs-datasets.md#reason-codes) มีรายการทั้งหมดพร้อมวิธีแก้ สามกรณีที่พบบ่อยที่สุด:

- **`snapshot-loop`**: สแนปช็อตไปไม่ถึง BombVault เพราะ Host Data ไม่ส่งต่อการเมานต์ใหม่ แก้ไขคอนเทนเนอร์ ตั้ง Access Mode ของ Host Data เป็น Read/Write - Slave แล้วรีสตาร์ต BombVault
- **`key-not-loaded`**: ชุดข้อมูลที่เข้ารหัสและยังไม่ได้โหลดคีย์จะถูกข้าม โหลดคีย์ด้วย `zfs load-key` แล้วเมานต์ชุดข้อมูล การสำรองครั้งถัดไปจะรวมเข้าไปด้วย
- **`ssh-auth`**: เซิร์ฟเวอร์ปฏิเสธคีย์ของ BombVault **การเชื่อมต่อ ZFS กับเซิร์ฟเวอร์นี้** ที่เปิดด้วย **ดูการเชื่อมต่อ** บนหน้าการสำรองข้อมูล แสดงคำสั่งที่อนุญาตมัน รันครั้งเดียวบนเซิร์ฟเวอร์

## รายการค้างที่ "กำลังเรียนรู้ N/10"

การตรวจความผิดปกติส่วนใหญ่เริ่มหลังการสำรองสำเร็จ 10 ครั้งของรายการ และการนับเริ่มใหม่หลัง **ทำเครื่องหมายว่าคาดไว้แล้ว** และหลังการเลือกของรายการเปลี่ยน รายการที่ไม่ได้ตั้งตารางเวลาไม่เรียนรู้ และ container ที่ไม่มี appdata ไม่มีอะไรให้เรียนรู้ ซึ่งป้ายของมันบอกไว้ **ความคืบหน้าการเรียนรู้** บนหน้าความผิดปกติแสดงวงแหวนสิบส่วนต่อรายการ

## การเก็บรักษาเลิกลบข้อมูลสำรองเก่าของรายการหนึ่ง

ความผิดปกติระดับวิกฤตที่เปิดอยู่เก็บมันไว้: ต้นทางของรายการเกือบว่าง หดลงมาก หรือการสำรองหนึ่งครั้งเก็บข้อมูลส่วนใหญ่ซ้ำอีกครั้ง เปิดความผิดปกติจากป้ายบนรายการ หากข้อมูลหายไปหรือถูกเข้ารหัส ให้กู้คืนจากข้อมูลสำรองที่ดีล่าสุดที่ลิงก์ไว้ก่อน จากนั้นรับทราบความผิดปกติ หรือทำเครื่องหมายว่าคาดไว้แล้วหากการเปลี่ยนแปลงเป็นของคุณ แล้วการรันครั้งถัดไปจะตัดทิ้งตามปกติ ตัวอย่างการเก็บรักษาทำเครื่องหมายรายการเช่นนั้นว่าถูกเก็บไว้ สำหรับรายการ ZFS เฉพาะชุดข้อมูลที่ระบุในความผิดปกติเก็บข้อมูลสำรองเก่าไว้ และชุดข้อมูลอื่นของทรีถูกตัดทิ้งตามปกติ

## การตัดทิ้งด้วยมือบอกว่าบางรายการถูกเก็บไว้

สาเหตุเดียวกัน: การตัดทิ้งไม่แตะข้อมูลสำรองเก่าของรายการที่มีความผิดปกติเช่นนั้นและระบุชื่อรายการในข้อความ ส่วนอื่นทั้งหมดถูกตัดทิ้งตามปกติ

## การนำเข้าประวัติแจ้งว่าอ่านรีโพสิทอรีไม่ได้

หลังการอัปเกรด BombVault อ่านขนาดของข้อมูลสำรองก่อนหน้าจากแต่ละรีพอสิทอรีหนึ่งครั้ง รีพอสิทอรีที่เข้าถึงไม่ได้ในตอนนั้น เช่นปลายทางนอกสถานที่ที่ล่มหรือแชร์ที่ไม่ได้เมานต์ จะถูกนับในการ์ด **ความผิดปกติ** ใต้ **การตั้งค่า, ยืนยัน** และลองใหม่วันละครั้ง รายการของมันเรียนรู้จากข้อมูลสำรองใหม่ในระหว่างนี้

## คำเตือนพื้นที่ดิสก์ไม่ตรงกับแดชบอร์ดของ Unraid

บนแชร์ผู้ใช้ของ Unraid (`/mnt/user`) พื้นที่ว่างเป็นของทั้งอาร์เรย์ ไม่ใช่ของดิสก์ลูกเดียว รีโพสิทอรีระยะไกลจะวัดได้ผ่าน rclone remote ที่รายงานพื้นที่ว่างเท่านั้น รีโพสิทอรี S3, B2, REST และ SFTP ไม่มีค่า และแสดงเป็นไม่ได้วัดในการ์ด **ความผิดปกติ**

หน้า [เซิร์ฟเวอร์ MCP](mcp.md#troubleshooting) อธิบายว่ารหัสสถานะและการปฏิเสธแต่ละแบบของปลายทาง MCP หมายถึงอะไร และควรทำอย่างไร

## container รีสตาร์ทซ้ำๆ หรือดูไม่สมบูรณ์

BombVault รายงาน healthy/unhealthy จาก `/api/health` ของตัวเอง เครื่องมือซ่อมตัวเอง (เช่น Autoheal) รีสตาร์ทมันโดยอัตโนมัติได้หากเอนจินค้าง ตรวจบันทึกของ container และการ์ด **การผสานรวมโฮสต์** เพื่อหาสาเหตุเบื้องหลัง
