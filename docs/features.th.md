# คุณสมบัติ

ทุกอย่างที่ BombVault สำรองข้อมูลอยู่ในรายการเดียว ทุกรายการมีหน้าของตัวเอง การกู้คืนเริ่มจากหน้าเดียว และการตั้งค่าเป็นไทล์ ไม่มีโหมดขั้นสูงให้เปิด สิ่งที่ใช้ไม่บ่อยมีการ์ดหรือหน้าต่างของตัวเอง หน้านี้จัดกลุ่มชุดฟีเจอร์ทั้งหมด

## ขอบเขตการสำรองข้อมูล

![รายการการสำรองข้อมูล: ทุกรายการพร้อมการทำงานล่าสุดเป็นแถบ หนึ่งสถานะ และการดำเนินการของมัน](assets/screenshots/containers.png)

*รายการการสำรองข้อมูล: ทุกรายการพร้อมการทำงานล่าสุดเป็นแถบ หนึ่งสถานะ และการดำเนินการของมัน*

| ส่วน | สิ่งที่ถูกบันทึก |
|---|---|
| **Containers** | ไดเรกทอรี appdata พร้อมคำจำกัดความของ container (อิมเมจ, env vars, พอร์ต, ป้ายกำกับ, โวลุ่ม) โดยค่าเริ่มต้นคือไดเรกทอรี appdata ทั้งหมด การ์ด **โฟลเดอร์ที่สำรองข้อมูล** บนแท็บ **การตั้งค่า** ของ container ติ๊กได้ว่าการสำรองครอบคลุมโฟลเดอร์ใดบ้าง พร้อมจำนวนพาธแบบสด รายการสิ่งที่คุณเว้นไว้ และสวิตช์ **ข้ามโฟลเดอร์แคช (CACHEDIR.TAG)** |
| **VMs** | อิมเมจดิสก์ของ VM, คำจำกัดความ XML และ UEFI NVRAM (ปิดเครื่องอย่างนุ่มนวลหรือสแนปช็อตสด ผ่าน SSH) สแนปช็อตสดจะถอยกลับไปเป็นการสำรองแบบนุ่มนวลโดยอัตโนมัติหากสร้างสแนปช็อตไม่ได้ ดังนั้นการสำรอง VM จะไม่จบลงด้วยข้อผิดพลาดเฉย ๆ เมื่อเปิด **เฉพาะบล็อกที่เปลี่ยน** VM ที่กำลังรันและมีดิสก์ qcow2 จะถูกอ่านผ่านจุดตรวจของ libvirt การสำรองแต่ละครั้งจึงอ่านเฉพาะบล็อกที่เขียนตั้งแต่ครั้งก่อน และข้อมูลสำรองทุกชุดยังกู้คืนดิสก์ทั้งหมดได้ด้วยตัวเอง ดิสก์บน zvol ของ ZFS จะถูกสตรีมด้วย `zfs send` ผ่านลิงก์ SSH เดียวกัน VM ที่ดิสก์เป็น zvol จึงถูกสำรองเป็น VM เดียว สถานะของ vTPM แบบ passthrough จะถูกบันทึกไว้ข้าง NVRAM เมื่อ XML ของโดเมนระบุพาธของมัน vTPM แบบจำลองที่ TrueNAS ตั้งให้กับ Windows 11 ไม่เปิดเผยพาธนั้น ดังนั้นให้เก็บรหัสกู้คืนของระบบ guest นั้นไว้ใกล้มือ ดู[คู่มือการสำรอง VM](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md) |
| **Flash** | แฟลช USB ทั้งหมด (`/boot`): OS, ลิขสิทธิ์, การตั้งค่าอาร์เรย์, แชร์, การตั้งค่าเครือข่ายและปลั๊กอิน การกู้คืนคือการดาวน์โหลด `.zip` และไม่เขียนทับแฟลชที่ใช้งานอยู่เลย |
| **สำรองข้อมูลตัวเอง** | `/config` ของ BombVault เอง (ฐานข้อมูลการตั้งค่า, ข้อมูลเข้าสู่ระบบของปลายทาง, คู่คีย์ SSH ของ libvirt) ทำสแนปช็อตด้วย SQLite `VACUUM INTO` เพื่อไม่ให้ฐานข้อมูลโหมด WAL ถูกจับกลางการเขียน จะกลับมาผ่านตัวช่วยฉุกเฉิน ซึ่งรีสตาร์ท BombVault ฐานข้อมูลที่ใช้งานอยู่จึงไม่ถูกเขียนทับขณะมี handle เปิดอยู่ |
| **โฟลเดอร์** | ชุดโฟลเดอร์: โฟลเดอร์ใดก็ได้บนเซิร์ฟเวอร์ (แชร์, เอกสารของคุณ, คลังภาพถ่าย) แต่ละชุดมีรูปแบบการยกเว้นได้ตามต้องการ **เพิ่ม** บนหน้าการสำรองข้อมูลแสดงรายการแชร์ที่พบและรับโฟลเดอร์อื่นใดก็ได้ ชุดโฟลเดอร์มีทุกอย่างที่ส่วนอื่นมี: ตารางเวลา, การเก็บรักษา, สำเนานอกสถานที่, การตรวจสอบ และการซ้อมกู้คืน |
| **ชุดข้อมูล ZFS** | ชุดข้อมูลหนึ่งพร้อมทุกชุดข้อมูลที่อยู่ข้างใต้ อ่านจากสแนปช็อต ZFS ครั้งเดียวเพื่อให้ทั้งหมดมาจากช่วงเวลาเดียวกัน และเก็บด้วย restic เหมือนโฟลเดอร์: ขจัดข้อมูลซ้ำ เรียกดูได้ กู้คืนไฟล์เดี่ยวได้ ชุดข้อมูลลูกใหม่เข้าร่วมเอง ลูกบางตัวเว้นได้ และลูกที่อ่านไม่ได้จะถูกข้ามและระบุชื่อ ตามต้องการสามารถหยุด container หรือรันคำสั่งเฉพาะช่วงสั้น ๆ ของสแนปช็อต โวลุ่มไม่รวมอยู่ด้วย: โวลุ่มของ VM ถูกสำรองไปกับ VM ส่วนโวลุ่มที่ไม่มี VM ยังไม่ถูกสำรอง รายการ ZFS ยังเก็บเรพลิกาแบบตรงทุกบล็อกบนเซิร์ฟเวอร์ ZFS เครื่องที่สองได้ ดู[ชุดข้อมูล ZFS](zfs-datasets.md) |

## การสำรองข้อมูลและหน้าของรายการ {#backups}

- **รายการเดียว** Containers, VMs, ชุดโฟลเดอร์, แฟลชไดรฟ์, ชุดข้อมูล ZFS และสำรองข้อมูลตัวเองอยู่ในรายการเดียวใต้ **การสำรองข้อมูล** ไทล์เหนือรายการเลือกชนิด และ **ตัวกรอง**, **เรียงลำดับ** และ **ค้นหา** ช่วยจำกัดให้แคบลง การเรียงลำดับทำได้ตามชื่อ สถานะ การสำรองล่าสุด ขนาด หรือตารางเวลา ทั้งสองทิศทาง และการค้นหาหา container ได้จากชื่อ อิมเมจ หรือ IP
- **การทำงานล่าสุดเป็นแถบ** แถวแสดงการทำงานล่าสุดสิบสี่ครั้งเป็นสี่เหลี่ยมเล็ก ๆ และหนึ่งสถานะ ส่วนที่เหลือเกี่ยวกับแถวนั้นอยู่ในบับเบิลข้อมูลข้างชื่อ
- **เลือกแบบตัวจัดการไฟล์** Ctrl+คลิก, Shift+คลิก และ Ctrl+A เลือกแถว การกดค้างทำสิ่งเดียวกันบนโทรศัพท์ และทุกแถวมีเมนูคลิกขวา ส่วนที่เลือกสำรองได้ กู้คืนจากข้อมูลสำรองล่าสุดได้ หรือหยุดชั่วคราวและทำต่อในตารางเวลาได้
- **เพิ่ม** เปิดหน้าต่างเดียวสำหรับสิ่งที่ BombVault เดาไม่ได้: โฟลเดอร์หรือชุดข้อมูล ZFS Containers, VMs และแฟลชไดรฟ์ปรากฏเอง บนโฮสต์ที่ไม่มี Unraid หน้าต่างจะเสนอ **การกำหนดค่าระบบ** ซึ่งเป็นชุดโฟลเดอร์ `/etc` ตั้งต้นที่คุณตรวจก่อนบันทึก
- **ไม่สำรองข้อมูล** เว้นรายการไว้โดยตั้งใจ รายการนั้นจะไม่นับว่าไม่ได้รับการปกป้องอีกต่อไป และ **ยกเลิกการยกเว้น** นำกลับมา
- **เพิ่มเติม** บนหน้าการสำรองข้อมูลมี **ค้นหาการสำรองข้อมูล** ซึ่งสร้างรายการขึ้นใหม่จากสิ่งที่ปลายทางเก็บไว้ (เช่นหลังติดตั้งใหม่) และ **กู้คืนสแตก** สำหรับโปรเจกต์ Compose
- **หนึ่งหน้าสำหรับทุกรายการ** มีสามแท็บใต้ส่วนหัวที่บอกสถานะและมีการดำเนินการของมัน:
    - **การสำรองข้อมูล** แสดงข้อมูลสำรองพร้อมแถบต่อวัน ปลายทางที่เก็บมัน และดัมป์ฐานข้อมูล
    - **การตั้งค่า** มีตารางเวลาและปลายทาง รีพอสิทอรี โฟลเดอร์ที่สำรองข้อมูล รูปแบบการยกเว้น container อื่นที่ต้องหยุด คำสั่งก่อนและหลัง ดัมป์ฐานข้อมูล และชื่อเดิม ตารางเวลาและปลายทางตามค่าเริ่มต้นของส่วนจนกว่ารายการจะมีของตัวเอง
    - **ความสมบูรณ์** แสดงการตรวจสอบ ขนาดตามโฟลเดอร์ การเฝ้าติดตามความผิดปกติของรายการ และการทำงานล่าสุด
- **ทำเครื่องหมายและเปรียบเทียบ** ข้อมูลสำรองมีแท็กของคุณเองได้ และ **เปรียบเทียบกับข้อมูลสำรองอื่น** แสดงไฟล์ที่เพิ่ม หายไป หรือเปลี่ยนระหว่างสองชุด VM จะเปรียบเทียบอิมเมจดิสก์และบอกว่าต่างกันมากแค่ไหน
- **ส่งออก** เขียนข้อมูลสำรอง ข้อมูลสำรองทุกชุดของรายการ หรือ container หรือ VM ตามที่เป็นอยู่ตอนนี้ ลงในโฟลเดอร์ส่งออกบนเซิร์ฟเวอร์ เป็น tar, zip หรือรีพอสิทอรี restic ของตัวเอง

## การกู้คืน

![หน้าการกู้คืน: เลือกส่วน ค้นหารายการ แล้วเลือกข้อมูลสำรอง](assets/screenshots/recovery.png)

*หน้าการกู้คืน: เลือกส่วน ค้นหารายการ แล้วเลือกข้อมูลสำรอง*

- **หนึ่งหน้า** **การกู้คืน** แสดงส่วนต่าง ๆ เป็นไทล์ ค้นหาสิ่งที่ต้องการนำกลับมาแล้วเลือกข้อมูลสำรองจากรายการที่ล่าสุดอยู่บนสุด อันที่แนะนำมีเครื่องหมาย และหลังความผิดปกติคืออันสุดท้ายก่อนหน้านั้น **เปิดรายการ** นำไปยังหน้าของรายการ และการกู้คืนที่กำลังทำแสดงอยู่ใต้ **กำลังทำงานอยู่**
- **หนึ่งหน้าต่างสำหรับทุกชนิด** ถามเป็นขั้น: **ข้อมูลสำรอง** ใด (อันที่แนะนำถูกเลือกไว้ก่อน) **แหล่ง** ใด (ในเครื่องเร็วที่สุด) **อะไร** (ทั้งหมด หรือไฟล์และโฟลเดอร์ที่คุณเลือก) และ **ไปที่ไหน** ฉากแสดงปลายทางที่เลือก และ **จะเกิดอะไรขึ้น** บอกเป็นคำพูดก่อนเริ่ม
- **ข้างต้นฉบับคือค่าเริ่มต้น** Container กลับมาเป็น container ที่สองชื่อ `<ชื่อ>-restored` พร้อมพอร์ตของตัวเอง ขณะที่ต้นฉบับยังทำงานต่อ ดิสก์และ NVRAM ของ VM ไปอยู่ในโฟลเดอร์ชื่อ `<โฟลเดอร์>-restored` ข้างต้นฉบับ โดยไม่มี VM ตัวที่สอง ชุดโฟลเดอร์กลับมาเป็น `<พาธ>-restored` สำเนานี้แสดงใต้การสำรองข้อมูลว่าถูกยกเว้นจนกว่าคุณจะเพิ่มเข้าตารางเวลา
- **แทนที่ต้นฉบับสำรองก่อน** เมื่อเปิด **สำรองสถานะปัจจุบันก่อน** ซึ่งเปิดไว้เป็นค่าเริ่มต้น BombVault จะสำรองสิ่งที่มีอยู่ตอนนี้ก่อนแทนที่ เพื่อให้ย้อนกลับได้ หากการสำรองนั้นล้มเหลว การกู้คืนจะไม่เริ่ม การแทนที่ขอให้คุณพิมพ์ชื่อของรายการ
- **ไปยังโฟลเดอร์** เขียนเฉพาะไฟล์ สำหรับเรียกดู ชุดข้อมูล ZFS กู้คืน **ไปยังชุดข้อมูลใหม่** ได้ด้วย และแฟลชไดรฟ์กลับมาเป็น **ดาวน์โหลดเป็น ZIP**
- **Containers ถูกติดตั้งใหม่โดยอัตโนมัติ** คำจำกัดความของ container จะถูกเล่นซ้ำผ่าน Docker API ดังนั้น container จึงปรากฏขึ้นอีกครั้งในแท็บ Docker ของ Unraid เหมือนเดิมทุกประการ
- **GPU ขีดจำกัด และลิงก์กลับมา** container ที่กู้คืนจะได้ขีดจำกัดทรัพยากร ไดรเวอร์บันทึก การตั้งค่า DNS ลิงก์แบบเดิม และ GPU หรือรันไทม์ (`--gpus`, `--runtime=nvidia`) กลับมา บนโฮสต์ที่ไม่มีไดรเวอร์ GPU หรือรันไทม์นั้น การกู้คืนจะแจ้งและเสนอ **กู้คืนโดยไม่มี GPU และรันไทม์** รวมถึงหลังจากกู้คืนหลาย container หรือ stack ลิงก์ไปยัง container ที่ไม่มีอยู่ หรือหยุดอยู่ตอนที่ container ที่กู้คืนเริ่มทำงาน จะถูกตัดออก และประวัติการทำงานจะบอกไว้
- **VMs ถูกสร้างขึ้นใหม่โดยอัตโนมัติ** XML ถูกนำเข้าใหม่ผ่าน SSH เพื่อให้ VM ปรากฏอีกครั้งใน VM Manager พร้อมดิสก์และ UEFI NVRAM ที่เชื่อมต่อกลับ แม้ว่า VM จะถูกลบไปแล้ว
- **การกู้คืนแฟลชเป็นการดาวน์โหลด `.zip`** มันจะสตรีมไปยังเบราว์เซอร์ของคุณเป็น `flash-<id>.zip` พร้อมสำหรับวางลงในตัวสร้าง USB ของ Unraid ส่วน `/boot` ที่กำลังทำงานอยู่จะไม่ถูกแตะต้อง
- **ทีละปลั๊กอิน** หน้าต่างกู้คืนแฟลชแสดงปลั๊กอินในข้อมูลสำรองแฟลชแต่ละชุดพร้อมเวอร์ชันและขนาด และนำกลับเข้าแฟลชที่ใช้งานอยู่เพียงตัวเดียว: ไฟล์ `.plg` โฟลเดอร์ของมันใต้ `config/plugins` และไฟล์แพ็กเกจที่ข้อมูลสำรองมี ไม่มีอย่างอื่นบนแฟลชที่เปลี่ยน Unraid ติดตั้งปลั๊กอินเมื่อบูตครั้งถัดไป หรือทันทีที่ **Plugins, Install Plugin**
- **ส่งออก zip ของแฟลชตามตารางเวลา** หลังการสำรองแฟลชทุกครั้ง จะเขียนข้อมูลสำรองเป็น `.zip` ธรรมดาลงโฟลเดอร์ที่คุณเลือกได้ (`flash-latest.zip` ไฟล์เดียวที่เขียนทับ หรือประวัติแบบหมุนเวียน) คือการ์ด **ส่งออก ZIP ของแฟลช** บนแท็บการตั้งค่าของรายการแฟลช ชี้ไปที่โฟลเดอร์ Syncthing หรือ rclone เพื่อให้ข้อมูลสำรอง USB สำหรับบูตออกจากเซิร์ฟเวอร์โดยอัตโนมัติ
- **การตรวจสอบความขัดแย้งก่อนเริ่ม** ก่อนที่จะมีการหยุดหรือลบอะไร การกู้คืนจะตรวจสอบว่า IP แบบสแตติกและพอร์ตโฮสต์ที่เผยแพร่ของ container ว่างอยู่ และยกเลิกพร้อมข้อความที่ชัดเจนแทนที่จะทิ้งการกู้คืนที่ทำค้างไว้ครึ่งทาง
- **ตรวจก่อนการกู้คืน** หน้าต่างตรวจก่อนว่ารีพอสิทอรีตอบสนอง คีย์ที่เก็บไว้เปิดมันได้ จุดกู้คืนมีอยู่ และปลายทางมีที่พอสำหรับสิ่งที่การกู้คืนเขียน ปุ่มเริ่มยังคงล็อกขณะมีการตรวจที่ล้มเหลว และ (i) ในปุ่มบอกว่าอันไหน
- **สิ่งที่การกู้คืนเปลี่ยน** ก่อนยืนยัน หน้าต่างแสดงว่าการกู้คืนทำอะไรเทียบกับที่มีอยู่ตอนนี้: ไฟล์ใหม่ ที่ถูกแทนที่ และที่ไม่เปลี่ยน พร้อมรายการเมื่อขอ และไฟล์ที่ปลายทางซึ่งไม่อยู่ในข้อมูลสำรองและจะคงอยู่ สำหรับ container และ VM ยังเปรียบเทียบการตั้งค่าที่การกู้คืนสร้างใหม่กับที่กำลังรัน: อิมเมจและแท็ก พอร์ต ชื่อตัวแปรและโวลุ่ม หรือหน่วยความจำ vCPU ดิสก์ และเครือข่าย restic คำนวณสิ่งนี้เป็นการรันทดลองจากขนาดและเวลาแก้ไขโดยไม่อ่านไฟล์ ทรีที่ใหญ่มากจะหยุดหลัง 30 วินาทีและบอกไว้ การกู้คืนสแตกตรวจและวางแผนทุกสมาชิกและระบุตัวที่ขวาง
- **โฟลเดอร์ที่ใช้ร่วมกัน** การกู้คืนที่ตำแหน่งเดิมจะระบุชื่อคอนเทนเนอร์อื่นทุกตัว ไม่ว่าจะทำงานอยู่หรือไม่ ที่การผูกเมานต์เข้าไปถึงโฟลเดอร์ที่การกู้คืนเขียนลงไป เช่น "nextcloud-db ก็ใช้พาธนี้อยู่ด้วย" เป็นเพียงคำเตือนและไม่บล็อก
- **การกู้คืนชุดข้อมูล ZFS** กู้คืนชุดข้อมูลหนึ่งของรายการเข้าที่เดิม (หลังสแนปช็อตความปลอดภัยของ ZFS ที่คงอยู่จนกว่าคุณจะลบ) ไปยังโฟลเดอร์ ไปยังชุดข้อมูลใหม่ หรือเฉพาะไฟล์ที่คุณเลือก หรือทุกชุดข้อมูลของข้อมูลสำรองไปยังโฟลเดอร์ ชุดข้อมูลจะไม่ถูกย้อนกลับหรือแทนที่เลย
- **การกู้คืนคงสถานะการทำงาน** Container หรือ VM ที่กำลังรันตอนสำรองจะกลับมาในสถานะรัน ส่วนที่หยุดอยู่ยังคงหยุด ติ๊ก **ให้หยุดไว้หลังจากนั้น** เพื่อสร้างใหม่โดยไม่เริ่มทำงาน
- **กู้คืนทั้งสแตก** Container จากโปรเจกต์ Docker Compose เดียวกันที่มีสมาชิกที่สำรองข้อมูลแล้วอย่างน้อยสองตัวรวมเป็นสแตก **กู้คืนสแตก** ใต้ **เพิ่มเติม** บนหน้าการสำรองข้อมูลสร้างทุกสมาชิกใหม่จากข้อมูลสำรองล่าสุด แล้วเริ่มตามลำดับ `depends_on` ได้ตามต้องการ
- **ความคืบหน้าแบบสด การยกเลิก และการแจ้งว่ากำลังยุ่ง** การกู้คืนที่ใช้เวลานานแสดงแถบเปอร์เซ็นต์สดและยกเลิกได้ด้วยการยืนยันที่ตรงกับชนิด การกู้คืนที่ยกเลิกถูกบันทึกเป็น *ยกเลิก* ไม่ใช่ล้มเหลว ปิดหน้าต่างได้ ความคืบหน้ายังแสดงใต้การกู้คืนด้วย
- **ตัวช่วยฉุกเฉิน** สำหรับเซิร์ฟเวอร์ที่หายไปหรือตั้งค่าใหม่ ด้วยชุดกู้คืน ผ่านกลุ่ม หรือด้วยคีย์ที่พิมพ์เอง ดู [Off-site & recovery](offsite-recovery.md#emergency)
- **จากโฟลเดอร์ข้อมูลสำรองเก่า** เซสชันแบบอ่านอย่างเดียวเปิดรีพอสิทอรีของ BombVault อีกเครื่องด้วยชุดกู้คืนของอินสแตนซ์นั้นหรือ `APP_KEY` ที่พิมพ์เอง เพื่อให้คุณดึง container จากเซิร์ฟเวอร์ A ไปเซิร์ฟเวอร์ B โดยไม่แตะการตั้งค่าของตัวเอง ดู [Off-site & recovery](offsite-recovery.md#restore-from-another-bombvault-repo)
- **คุณสมบัติ ZFS กลับมาด้วย** ข้อมูลสำรอง ZFS ทุกชุดเก็บคุณสมบัติที่ตั้งไว้เฉพาะของแต่ละชุดข้อมูล เช่น การบีบอัด ขนาดเรคคอร์ด โควตา และการแยกตัวพิมพ์ใหญ่เล็ก การกู้คืนไปยังชุดข้อมูลใหม่จะสร้างชุดข้อมูลด้วยคุณสมบัติเหล่านั้น ส่วนการกู้คืนไปยังชุดข้อมูลที่มีอยู่จะแสดงคุณสมบัติและตั้งค่าเมื่อคุณสั่งเท่านั้น ดู [ชุดข้อมูล ZFS](zfs-datasets.md#new-dataset)
- **นำเข้าจากปลั๊กอิน Appdata.Backup** ใต้ **แหล่งอื่น** บนหน้าการกู้คืน ชี้ BombVault ไปที่โฟลเดอร์ข้อมูลสำรองของปลั๊กอิน ไฟล์เก็บถาวรของแต่ละ container กลายเป็นจุดกู้คืนของ container นั้น ลงวันที่ตามที่ปลั๊กอินสร้าง ไฟล์ที่นำเข้าแล้วจะถูกข้าม และตัวไฟล์เก็บถาวรถูกอ่านเท่านั้น Container ต้องมีการสำรองใน BombVault หนึ่งครั้งก่อน เพื่อให้การกู้คืนมีคำจำกัดความของมัน การเก็บรักษาไม่แตะจุดกู้คืนที่นำเข้า ดังนั้นลบเองเมื่อไม่ต้องการ

## การจัดเก็บและการตั้งตารางเวลา

- การสำรองข้อมูลแบบเพิ่มส่วนและขจัดข้อมูลซ้ำผ่าน restic ดังนั้นแม้แต่ดิสก์ VM ขนาดใหญ่ก็ไม่ทำให้รีพอสิทอรีบวมขึ้น
- **ปลายทาง** โฟลเดอร์ในเครื่องและที่นอกสถานที่อยู่ในรายการเดียวบนหน้า **ปลายทาง** ซึ่งเปิดจากไทล์การตั้งค่าของมันหรือปักหมุดไว้ที่แถบด้านข้าง แต่ละปลายทางมีหน้าของตัวเองพร้อมการเชื่อมต่อ ข้อมูลรับรอง การป้องกันการลบ การตั้งค่าการคัดลอก การเก็บรักษา และกฎแยกตามส่วน และภาชนะที่แสดงว่าเต็มแค่ไหนและจะเต็มเมื่อใดตามอัตราการเติบโตของไม่กี่สัปดาห์ที่ผ่านมา ดู [ปลายทาง](offsite-recovery.md#destinations)
- **ชนิดของที่จัดเก็บ:** พาธในเครื่อง, แชร์ SMB และเซิร์ฟเวอร์ WebDAV (Nextcloud, ownCloud, SharePoint) ผ่าน rclone โดยไม่ต้องเมานต์บนโฮสต์, NFS (เมานต์ export บน Unraid แล้วใช้เป็นโฟลเดอร์ในเครื่อง), แบ็กเอนด์ restic ดั้งเดิมโดยไม่ใช้ rclone (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`) หรือรีโมต rclone ใดก็ได้ผ่าน `rclone:<remote>:<bucket>/path` ข้อมูลรับรองทั้งหมดถูกเก็บแบบเข้ารหัส
- **ปลายทาง SSH ไม่ต้องติดตั้งอะไรที่ฝั่งไกล** `sftp:` ต้องการเพียงเซิร์ฟเวอร์ SSH ดังนั้น Raspberry Pi เปล่า ๆ (ไม่มี Docker ไม่มี restic) ใช้เป็นปลายทางนอกสถานที่ได้ host key จะถูกปักหมุดโดยอัตโนมัติเมื่อติดต่อครั้งแรก
- **3-2-1 เป็นภาพ** การ์ด **ปลายทางแยกตามส่วน** วาดว่าส่วนใดถูกสำรองไปที่ไหน ทุกเส้นจากส่วนไปยังปลายทางเป็นสวิตช์ และ **กราฟ / สวิตช์** ให้สิ่งเดียวกันเป็นปุ่มธรรมดา รายการที่สำรองไปที่อื่นนอกจากส่วนของตัวเองอยู่ใต้ **การเลือกเอง** แต่ละรายการมี **ใช้ตามค่าเริ่มต้น**
- **การคัดลอกนอกสถานที่ (ในเครื่อง + ระยะไกล)** เก็บข้อมูลสำรองในเครื่องที่เร็วไว้และเพิ่มปลายทางนอกสถานที่หนึ่งแห่งหรือมากกว่า คัดลอกด้วย `restic copy` แบบทำเท่าที่ทำได้ (ปัญหานอกสถานที่จะไม่ทำให้การสำรองในเครื่องล้มเหลว) การคัดลอกส่งเฉพาะแพ็กข้อมูลที่ปลายทางยังไม่มี การ์ด **คัดลอก** ของแต่ละปลายทางกำหนด **คัดลอกเมื่อไร** (**หลังการสำรองข้อมูลทุกครั้ง** หรือแผนของตัวเอง) และแบนด์วิดท์ และส่วนหนึ่งคัดลอกตามแผนของตัวเองได้ใต้ **การตั้งค่า, ตารางเวลา**
- **หลายปลายทางต่อส่วน** แต่ละส่วนคัดลอกไปยังหลายปลายทางนอกสถานที่พร้อมกันได้ **กฎแยกตามส่วน** ของปลายทางให้ส่วนหนึ่งมีการเก็บรักษา การบีบอัด หรือรีพอสิทอรีของตัวเองที่นั่น ส่วนการเข้าสู่ระบบ ข้อมูลรับรอง แบนด์วิดท์ และจังหวะเวลามาจากปลายทาง
- **ย้ายประวัติของส่วน** **ย้าย** บนปลายทางนำสำเนาของส่วนหนึ่งพร้อมประวัติทั้งหมดไปยังปลายทางอื่น ที่เก่าเก็บทุกอย่างไว้ BombVault ไม่ลบอะไรที่นั่น
- **รีพอสิทอรีที่ตั้งชื่อ** การ์ด **ที่เก็บข้อมูล** ใต้ **การตั้งค่า, ปลายทาง** จดตำแหน่งข้อมูลสำรองของคุณครั้งเดียว เป็นพาธในเครื่องหรือรีโมต restic ใดก็ได้พร้อมชุดข้อมูลรับรองของตัวเอง ให้เลือกเป็นตำแหน่งของรายการ แถวแสดงว่ามีกี่รายการชี้มาที่มัน และรีพอสิทอรีที่รายการหรือค่าเริ่มต้นใช้อยู่จะย้ายหรือลบไม่ได้ เพราะ BombVault ไม่เคยย้ายข้อมูลสำรองที่เขียนไปแล้ว
- **หลายชุดข้อมูลรับรอง** ข้อมูลรับรองคลาวด์ที่ใช้ร่วมกันใช้ทุกที่เป็นค่าเริ่มต้น แต่ปลายทางใดก็ใช้ชุดที่ตั้งชื่อแทนได้ (**ชุดข้อมูลรับรองเพิ่มเติม** ใต้ **การตั้งค่า, ปลายทาง** หรือ **ข้อมูลรับรอง** บนหน้าของปลายทาง) ดังนั้นบักเก็ต Hetzner S3 กับเซิร์ฟเวอร์ Garage ในเครื่องทำงานเคียงกันได้ โดยแต่ละอันมีคีย์ของตัวเอง
- **การจัดวางต่อรายการ** การ์ด **ตารางเวลาและปลายทาง** บนแท็บการตั้งค่าของรายการมีแถวปุ่ม **ในเครื่อง** และหนึ่งปุ่มต่อปลายทางนอกสถานที่ และปุ่มที่สว่างจะได้รับข้อมูลสำรอง แชร์ที่อยู่บน NAS อยู่แล้วไม่ต้องไป B2 อีก ตำแหน่งถูกตรึงตั้งแต่การสำรองครั้งแรก สำเนาเปลี่ยนได้ทุกเมื่อ และการ์ดบอกว่ามีกี่ที่เก็บรายการนี้และ 3-2-1 ครบหรือไม่ ดู [การจัดวางต่อรายการ](offsite-recovery.md#placement)
- **ลำดับการสำรองข้อมูลด้วยตนเอง** การ์ด **ลำดับ** ใต้ **การตั้งค่า, ตารางเวลา** กำหนดลำดับที่แน่นอนที่ container และ VM ถูกสำรอง การทำงานตามตารางเวลาและการสำรองข้อมูลทั้งหมดทำตามลำดับนั้น สิ่งที่ไม่ได้จัดลำดับยังเรียงตามที่เกินกำหนดมากที่สุดก่อน และการสำรองเดี่ยวไม่เปลี่ยน
- **การเก็บรักษาเป็นเส้นเวลา** แต่ละปลายทางเก็บข้อมูลสำรองตาม **เก็บไว้นานแค่ไหน**: **สั้น**, **สมดุล**, **ยาว** หรือ **ค่าที่กำหนดเอง** สำหรับข้อมูลสำรองล่าสุด วัน สัปดาห์ เดือน และปี ตัดทิ้งโดยอัตโนมัติ เส้นเวลาแสดงว่ากฎเก็บข้อมูลสำรองชุดใดไว้ **ถามก่อนเก็บน้อยลง** ถามก่อนที่กฎสั้นลงจะลบข้อมูลสำรองเก่าที่มีสำเนาเดียวอยู่ที่นั่น ส่วนหนึ่งเก็บค่าของตัวเองที่ปลายทางหนึ่งได้ใต้ **กฎแยกตามส่วน**
- **การบีบอัดต่อรีพอสิทอรี:** ปิด, อัตโนมัติ (ค่าเริ่มต้นของ restic) หรือสูงสุด ตั้งที่แต่ละปลายทาง และสำหรับหนึ่งส่วนใต้กฎของมันที่นั่น การสำรองข้อมูล สำเนานอกสถานที่ และการตัดทิ้งเขียนด้วยค่านั้น และชุดกู้คืนระบุไว้ ดังนั้น restic ธรรมดาเขียนต่อแบบเดียวกันได้
- **ตารางเวลาอ่านเป็นประโยค** เช่น *ทุกสัปดาห์วันอาทิตย์เวลา 04:00* และแก้ไขจากประโยคนั้น **การตั้งค่า, ตารางเวลา** มีทั้งหมด: แถบ **สัปดาห์** พร้อมทุกการรันที่วางแผนไว้ตั้งแต่วันจันทร์ถึงวันอาทิตย์ **สำรองข้อมูลทั้งหมด** พร้อมหนึ่งคำสั่งก่อนและหนึ่งคำสั่งหลัง **กำหนดการรายส่วน** **สำเนานอกสถานที่รายส่วน** และ **รายการที่อยู่ในกำหนดการ** **ทุก N วัน** ใช้ได้กับการซ้อมกู้คืน การทดสอบการแทรกแซง และสรุปรายสัปดาห์ด้วย
- **ส่วนที่มีแผนของตัวเองออกจากการสำรองข้อมูลทั้งหมด** ปุ่ม **ข้อยกเว้น** ใต้ **กำหนดการรายส่วน** ให้ส่วนหนึ่งมีแผนของตัวเอง ส่วนนั้นจึงรันตามเวลาของตัวเองและไม่รันซ้ำในการสำรองทั้งหมด ไม่มีอะไรถูกสำรองสองครั้ง **สำรองข้อมูลทั้งหมดเดี๋ยวนี้** ยังรวมทุกส่วนที่เปิดอยู่ เมื่อเปิด **กำหนดการของตัวเองรายรายการ** container, VM, ชุดโฟลเดอร์ หรือชุดข้อมูล ZFS เดี่ยวมีแผนของตัวเองบนหน้าของมันได้ และก็ออกจากการสำรองทั้งหมดด้วย
- **อัปเดต container หลังการสำรองข้อมูลสำเร็จ** สวิตช์เดียวใต้ **การตั้งค่า, ตารางเวลา, อัปเดตหลังการสำรองข้อมูล** ปิดเป็นค่าเริ่มต้น ดึงอิมเมจใหม่หลังจากการสำรองก่อนหน้าเสร็จเท่านั้น container เดี่ยวตั้งต่างออกไปได้บนหน้าของมัน
- **รอจนแอปว่าง** Container ให้การสำรองตามตารางเวลารอขณะแอปยุ่งได้ ไม่เกินจำนวนชั่วโมงที่ตั้ง และเริ่มทันทีที่แอปว่าง เซิร์ฟเวอร์สื่อนับว่าว่างเมื่อไม่ได้สตรีม container อื่นเมื่อ CPU และทราฟฟิกอยู่ต่ำกว่าขีดจำกัดในการ์ด **ความว่างก่อนสำรองข้อมูล** ใต้ **การตั้งค่า, ตารางเวลา** ไม่กี่นาที (บนเครือข่ายของโฮสต์นับเฉพาะ CPU) การสำรองที่รออยู่แสดงในบันทึกกิจกรรมและบน container พร้อมเหตุผลและเส้นตาย มันไม่ถือล็อก container อื่นจึงไปต่อได้ การสำรองด้วยตนเองไม่เคยรอ สมาชิกของ compose stack ที่ถึงกำหนดในรอบเดียวกันรอด้วยกัน และการรอทำต่อด้วยเส้นตายของมันหลังรีสตาร์ท การปิด container จะทิ้งการสำรองที่รออยู่ทั้งหมด และการปิดตารางเวลาของมันทิ้งรายการที่การรันของมันรั้งไว้ การลดจำนวนชั่วโมงทำให้การรอที่เริ่มแล้วสั้นลง
- **ขีดจำกัดแบนด์วิดท์นอกสถานที่** จำกัดอัตราการอัปโหลด/ดาวน์โหลดของ restic เพื่อไม่ให้การคัดลอกทำให้ WAN ของคุณเต็ม ในการ์ด **แบนด์วิดท์นอกสถานที่** ใต้ **การตั้งค่า, ปลายทาง** และต่อปลายทางในการ์ด **คัดลอก** ของมัน
- **สตรีมมิงมาก่อน** ขณะที่เซิร์ฟเวอร์สื่อเช่น Plex, Jellyfin หรือ Emby สตรีมอยู่ สำเนานอกสถานที่จะอัปโหลดด้วยขีดจำกัดที่ต่ำกว่า และกลับเป็นปกติไม่กี่นาทีหลังสตรีมจบ BombVault อ่านทราฟฟิกขาออกของเซิร์ฟเวอร์สื่อจาก Docker REST, S3, B2, Azure, Google Cloud, Swift และ rclone ผ่าน HTTP ช้าลงกลางการคัดลอก ส่วน SFTP และโฟลเดอร์ในเครื่องหรือที่เมานต์ใช้ขีดจำกัดที่ต่ำกว่าในขั้นตอนคัดลอกถัดไป เซิร์ฟเวอร์สื่อบนเครือข่ายของโฮสต์วัดไม่ได้ คือการ์ด **สตรีมมิง** บนหน้าปลายทาง
- **คลาสพื้นที่จัดเก็บแบบเย็นและแบบเก็บถาวร (S3)** สำหรับปลายทาง S3 เลือกคลาสพื้นที่จัดเก็บได้ โดยจำกัดเฉพาะระดับที่กู้คืนอ่านได้ (Standard, Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier Instant Retrieval) เพื่อให้ราคาแบบเก็บถาวรไม่ทำให้การกู้คืนพังโดยไม่รู้ตัว ระดับเก็บถาวรลึกที่ต้องละลายแบบอะซิงโครนัสก่อน (Glacier Flexible, Deep Archive) ถูกเว้นไว้ เพราะ restic อ่านจากมันไม่ได้ ใช้ได้กับแบ็กเอนด์ S3 ดั้งเดิมเท่านั้น รีโมต rclone ตั้งคลาสในการตั้งค่า rclone
- **โฟลเดอร์การสำรองข้อมูลยังคงคัดลอกออกนอกเครื่องได้** หลังการสำรองข้อมูลทุกครั้ง BombVault จะผ่อนสิทธิ์ของทรีรีพอสิทอรีในเครื่องเป็นไดเรกทอรี `0755` / ไฟล์ `0644` (รีพอสิทอรีถูกเข้ารหัส ดังนั้นจึงไม่มีอะไรเปิดเผย) เพื่อไม่ให้ผู้ใช้ซิงค์ที่ไม่ใช่ root ผ่าน SMB ถูกล็อกออก คำจำกัดความการกู้คืนอยู่ภายในรีพอสิทอรีแต่ละตัว ดังนั้นโฟลเดอร์รีพอสิทอรีที่คัดลอกมาจึงสมบูรณ์ในตัวเองอย่างเต็มที่

## ข้อมูลเชิงลึก, การตรวจสอบ และการเฝ้าติดตาม

- **ภาพรวม** เริ่มด้วยส่วนหัวสถานะและการ์ดสี่ใบ: **ต้องดูแล**, **สถานะการป้องกัน**, **ปลายทาง** พร้อมการคาดการณ์ว่าแต่ละแห่งจะเต็มเมื่อใด และ **ประวัติ** พร้อมการทำงานและบันทึก วงแหวนในส่วนหัวแสดงว่าปกป้องไว้เท่าไรและกลายเป็นวงแหวนความคืบหน้าพร้อมสถานีของมันขณะสำรองข้อมูล การ์ดเพิ่มเติมรออยู่ใต้ **ปรับแต่ง**: **ความผิดปกติ**, **ไม่ได้สำรองข้อมูล**, **ปฏิทิน**, **ที่จัดเก็บ**, **ภาพรวม**, **สถิติ** และ **การผสานรวมโฮสต์** ทุกการ์ดย้าย ปรับขนาด และซ่อนได้ และเลย์เอาต์ถูกบันทึกในเบราว์เซอร์
- **นับเหมือนกันทุกที่** ทุกการ์ดนับรายการของส่วนที่เปิดอยู่แบบเดียวกัน
- **หยุดชั่วคราวจากรายการ** **หยุดกำหนดการชั่วคราว** เอารายการออกจากตารางเวลาและการสำรองทั้งหมด และ **ทำกำหนดการต่อ** นำกลับ ตั้งสวิตช์เดียวกับ **อยู่ในตารางเวลา** บนแท็บการตั้งค่าของรายการ ทั้งสองจึงตรงกันเสมอ รายการที่หยุดชั่วคราวมีป้ายสีเทา **กำหนดการถูกหยุดชั่วคราว** และ **สำรองข้อมูลเดี๋ยวนี้** ยังใช้ได้
- **สถานะการป้องกัน** ทุกส่วนมีการตรวจสี่อย่าง: ข้อมูลสำรองปัจจุบันบนเซิร์ฟเวอร์นี้ สำเนานอกสถานที่ การป้องกันการลบที่นั่น และการกู้คืนทดลองจากที่นั่น ข้อมูลสำรองที่เลยกำหนดเปลี่ยนเป็นสีแดงแทนที่จะซ่อนในบันทึก และการคลิกที่ส่วนแสดงรายละเอียด
- **ปฏิทิน** 90 วันล่าสุด หนึ่งช่องต่อวันพร้อมผลการสำรองของวันนั้น การคลิกที่วันแสดงบรรทัดของวันนั้นในบันทึกใต้ประวัติ
- **เวลาการทำงานทุกที่** ทุกการทำงานอ่านเป็น `เริ่ม, จบ (ระยะเวลา)` และแต่ละรายการมีรายการ **การทำงานล่าสุด** ของตัวเองบนแท็บความสมบูรณ์
- **ขนาดรีพอสิทอรีและแนวโน้ม dedup** การ์ด **ที่จัดเก็บ** แสดงว่าแต่ละส่วนใช้พื้นที่เท่าไรและข้อมูลขจัดซ้ำได้ดีแค่ไหน
- **การซ้อมตรวจสอบการกู้คืน** BombVault พิสูจน์เป็นระยะว่าข้อมูลสำรองของคุณกู้คืนได้ (`restic check --read-data-subset` แบบมีขอบเขต) ตั้งค่าใต้ **การตั้งค่า, ยืนยัน, การตรวจสอบอัตโนมัติ** การ์ด **ตรวจสอบข้อมูลสำรอง** บนไทล์เดียวกันแสดงผลต่อส่วนและมี **ปลดล็อก** กับ **ตัดทิ้ง** ใต้ **เพิ่มเติม**
- **ตรวจการกู้คืนหลังการสำรองครั้งแรก** เมื่อการสำรองครั้งแรกของรายการเสร็จ BombVault กู้คืนตัวอย่างของมัน (สูงสุด 100 ไฟล์และ 256 MiB) ลงโฟลเดอร์ชั่วคราวใต้โฟลเดอร์การกู้คืน ให้ restic อ่านทุกไฟล์กลับเทียบกับแฮช และเปรียบเทียบขนาดกับข้อมูลสำรอง ไฟล์ที่ใหญ่เกินตัวอย่าง เช่นดิสก์ VM จะอ่านกลับเพียง 64 MiB แรก แท็บความสมบูรณ์ของรายการแสดงผล ความล้มเหลวส่งออกเป็นการแจ้งเตือน และ **ตรวจการกู้คืน** รันการตรวจเดียวกันกับข้อมูลสำรองล่าสุดเมื่อใดก็ได้ การสำรองครั้งต่อ ๆ ไปไม่ทำซ้ำ
- **ทดสอบการเริ่ม** การตรวจไบต์ไม่ได้แสดงว่าแอปกลับมาได้ **ทดสอบการเริ่ม** บนแท็บความสมบูรณ์ของ container กู้คืนข้อมูลสำรองล่าสุดของมันเป็นสำเนาที่แยกออกมาแล้วเริ่มมัน: ชื่อที่ขึ้นต้นด้วย `bombvault-test-` เครือข่าย Docker ภายในของตัวเองที่ไม่มีพอร์ตที่เผยแพร่และไม่มีทางออกไป LAN, 1 CPU และหน่วยความจำ 2 GiB และข้อมูลในโฟลเดอร์ชั่วคราวใต้โฟลเดอร์การกู้คืน การทดสอบผ่านเมื่อ healthcheck ของ container รายงานว่า healthy หรือถ้าไม่มี เมื่อพอร์ตแรกที่เปิดตอบจากในเครือข่ายนั้น หรือถ้าไม่มีทั้งสอง เมื่อ container ยังรันอยู่ Container ต้นฉบับไม่ถูกหยุดหรือเปลี่ยนเลย และสำเนา เครือข่าย และข้อมูลของมันถูกลบหลังจากนั้น แม้หลัง BombVault รีสตาร์ทกลางการทดสอบ Container บนเครือข่ายของโฮสต์ แบบ privileged ที่มีอุปกรณ์ และที่ต้องใช้ container อื่นจะแสดงว่าทดสอบไม่ได้ เปิด **ทดสอบการเริ่ม** ใต้ **การตั้งค่า, ยืนยัน, การตรวจสอบอัตโนมัติ** เพื่อทดสอบหนึ่ง container ต่อการรัน โดยตัวที่ทดสอบนานที่สุดก่อน สำเนาไม่มีป้ายกำกับของต้นฉบับ และรันโดยไม่มี capabilities, ตัวเลือกความปลอดภัย, sysctls และ cgroup parent ที่ต้นฉบับเพิ่ม Container ที่ต้องใช้สิ่งเหล่านี้จะไม่ผ่านการทดสอบ และผลระบุว่าสำเนารันโดยไม่มีอะไร
- **การดำเนินการที่ซ่อมตัวเอง** ล็อก restic ที่พิสูจน์ได้ว่าเป็นกำพร้า (เหลือจากการรีสตาร์ทกลางการดำเนินการ) จะถูกล้างด้วยการบังคับและลองใหม่หนึ่งครั้งโดยอัตโนมัติ การเก็บรักษามีเอกลักษณ์คงที่ (ตัดทิ้งต่อรายการ ไม่ถูกกระทบจากการเปลี่ยนพาธหรือโฮสต์) และความล้มเหลวของการเก็บรักษาส่งการแจ้งเตือน
- **คำเตือนที่การสแกนโฟลเดอร์มองไม่เห็น** ผู้ช่วยการยกเว้นตอบคำถามเรื่องขนาด แต่ความผิดพลาดในการสำรองข้อมูลที่แพงที่สุดบางอย่างไม่ใช่เรื่องขนาด มันจึงมีข้อควรระวังเฉพาะแอปเกี่ยวกับวิธีที่แอปพลิเคชันเก็บข้อมูลของตัวเองด้วย กรณีที่มันมีไว้เพื่อสิ่งนี้คือ Immich ซึ่งเก็บอัลบั้ม ใบหน้า และวันที่ของทุกภาพไว้ในฐานข้อมูล PostgreSQL ที่รันอยู่ใน container *แยกต่างหาก* ดังนั้นการสำรองข้อมูลระดับไฟล์ของ container Immich จะกู้คืนรูปภาพกลับมาโดยไม่มีสิ่งเหล่านั้นเลย และการกู้คืนก็ดูเหมือนสำเร็จ คำเตือนนี้แสดงไม่ว่าจะมีการเสนอการยกเว้นหรือไม่ รวมถึงบน container ที่ไม่ได้เลือกอะไรให้สแกนเลย เพราะข้อควรระวังนี้เป็นจริงในทั้งสองกรณี
- **ไม่ได้สำรองข้อมูล (ความครอบคลุม)** การ์ดภาพรวมที่ระบุทุกอย่างบนเซิร์ฟเวอร์ที่ไม่มีการสำรองตามตารางเวลาครอบคลุม พร้อมเหตุผลของแต่ละรายการ: ไม่เคยถูกเพิ่มใน BombVault เลย มีอยู่แต่ไม่อยู่ในตารางเวลา ตารางเวลาของมันเองตั้งเป็นปิด หรือไม่มีตารางเวลาที่เปิดอยู่เลย สถานะการป้องกันตอบคำถามอีกข้อ คือการสำรองที่ *ตั้งตาราง* ไว้รันตรงเวลาหรือไม่ และมองไม่เห็น container ที่ไม่มีใครตั้งค่า Container ถูกอ่านจากรายการ Docker สด ไม่ใช่จากแถวของ BombVault เอง เพราะรายการที่ไม่มีแถวคือตัวที่ต้องระบุชื่อพอดี ส่วนที่คุณปิดและรายการที่คุณทำเครื่องหมาย **ไม่สำรองข้อมูล** ไม่นับ เพราะเป็นการเลือกของคุณ
- **ตัวอย่างการเก็บรักษา** การ์ด **ดูตัวอย่าง** ใต้ **การตั้งค่า, ปลายทาง** แสดงสิ่งที่การรันครั้งถัดไปกำลังจะลบ ก่อนที่มันจะเกิด: ต่อรีพอสิทอรีและต่อรายการ พร้อมระบุชื่อจุดกู้คืน มันไม่ถือล็อกรีพอสิทอรีและไม่เปลี่ยนอะไร จึงตอบได้แม้ขณะสำรองข้อมูลอยู่ การเก็บรักษาที่ปิดอยู่จะบอกไว้แทนที่จะแสดงรายการว่าง รีพอสิทอรีแบบ append-only ถูกติดป้ายว่าเป็นเช่นนั้น (การเก็บรักษาไม่รันที่นั่นเลย) และรีพอสิทอรีที่เข้าถึงไม่ได้ถูกระบุชื่อแทนที่จะหายไปเงียบ ๆ
- **ความผิดปกติ** ทุกการสำรองของ container, VM, ชุดโฟลเดอร์, ดัมป์ฐานข้อมูล, แฟลชไดรฟ์ และสำรองข้อมูลตัวเองถูกเทียบกับประวัติของรายการนั้นเอง การตรวจดูข้อมูลใหม่ที่การรันเก็บ เทียบกับปริมาณปกติสูงสุดของข้อมูลสำรองล่าสุดและอัตราปกติต่อชั่วโมง ดูการสำรองที่เก็บข้อมูลส่วนใหญ่ซ้ำอีกครั้ง ซึ่งรวมไฟล์ที่เปลี่ยนชื่อและเขียนใหม่ ดูขนาดต้นทางและจำนวนไฟล์ที่ restic รายงานสำหรับแต่ละรายการและแต่ละดัมป์ฐานข้อมูล ดูเวลาสำรองของ restic เอง ดูชุดความล้มเหลวและความล้มเหลวเป็นช่วง ๆ ดูการตรวจการกู้คืนที่เลิกผ่าน และดูพื้นที่ว่างของรีพอสิทอรีในเครื่อง SFTP และ rclone ที่คาดการณ์จากการเติบโตของรีพอสิทอรี รายการเรียนรู้จาก 10 การสำรองแรก ขณะที่ต้นทางที่เกือบว่าง การเขียนข้อมูลส่วนใหญ่ใหม่ และความล้มเหลวถูกตรวจตั้งแต่เริ่ม ความไว (เข้มงวด สมดุล ผ่อนปรน) และระดับความรุนแรงต่ำสุดที่ส่งการแจ้งเตือนตั้งแบบทั่วไปในการ์ด **ความผิดปกติ** ใต้ **การตั้งค่า, ยืนยัน** และเปลี่ยนต่อรายการได้บนแท็บความสมบูรณ์ของมัน คำเตือนปิดเองเมื่อสาเหตุหายไป สิ่งที่พบระดับวิกฤตเรื่องข้อมูลที่สูญหายและดิสก์ที่กำลังเต็มคงอยู่จนกว่าคุณจะรับทราบ และสิ่งที่พบที่รับทราบแล้วจะไม่ถูกยกขึ้นอีกจนกว่าสาเหตุจะหายไปหนึ่งครั้ง **ทำเครื่องหมายว่าคาดไว้แล้ว** ทำให้ระดับใหม่เป็นปกติหลัง 10 การสำรอง แต่ไม่ปิดการตรวจต้นทางที่เกือบว่างเลย และการเลือกที่เปลี่ยนเริ่มประวัติของรายการใหม่เอง ขณะที่ต้นทางเกือบว่าง หดลงมาก หรือข้อมูลส่วนใหญ่ถูกเก็บซ้ำ การเก็บรักษาจะเก็บข้อมูลสำรองเก่าของรายการนั้นไว้จนกว่าคุณจะรับทราบหรือทำเครื่องหมายว่าคาดไว้แล้ว และสิ่งที่พบลิงก์ไปยังข้อมูลสำรองที่ดีล่าสุด การแจ้งเตือนออกครั้งเดียวต่อช่วง และความล้มเหลวกับการตรวจการกู้คืนที่แจ้งเตือนอยู่แล้วไม่รายงานซ้ำ สิ่งที่ไม่ทำ: รีพอสิทอรี S3, B2 และ REST ไม่มีตัวเลขพื้นที่ว่าง บนแชร์ผู้ใช้ของ Unraid พื้นที่ว่างคือของอาร์เรย์ทั้งหมด และการสำรองก่อน restic 0.17 ไม่มีประวัติขนาด รายการ ZFS ถูกตรวจด้วย ทีละชุดข้อมูล: ทุกชุดข้อมูลของทรีมีประวัติของตัวเอง ชุดที่ถูกทำให้ว่างหรืออ่านไม่ได้อีกนับเป็นข้อมูลสูญหาย และเก็บเฉพาะข้อมูลสำรองเก่าของชุดข้อมูลนั้น วิธีที่รายการ ZFS ถูกเฝ้าดูทีละชุดข้อมูลอธิบายไว้ใน[ชุดข้อมูล ZFS](zfs-datasets.md#anomalies) และผู้ช่วยอ่านสิ่งที่พบที่เปิดอยู่ได้ผ่าน[เซิร์ฟเวอร์ MCP](mcp.md#tools) สิ่งที่พบเกี่ยวกับขนาดหรือจำนวนไฟล์ของต้นทางลงวันที่ของการสำรองแรกที่มันปรากฏ และ **เปรียบเทียบกับข้อมูลสำรองก่อนหน้า** แสดงโฟลเดอร์ที่ไฟล์หายไป เข้ามา หรือเปลี่ยน พร้อมหมายเหตุเมื่อเกือบทั้งหมดอยู่ในดัชนีค้นหา แคช หรือภาพขนาดย่อที่แอปสร้างใหม่เอง
- **หน้าความผิดปกติ** ไทล์ **ร้ายแรง**, **คำเตือน** และ **หมายเหตุ** เลือกระดับความรุนแรง โดยมีสิ่งที่พบที่เปิดและปิดอยู่เหนือรายการ สิ่งที่พบเสนอวิธีแก้ก่อน และรายละเอียดแสดงค่าเป็นเส้นโค้งเหนือช่วงปกติ เมื่อไม่มีอะไรเปิดอยู่ วงแหวนต่อรายการแสดงว่าการตรวจจับเรียนรู้สิ่งที่ปกติไปได้แค่ไหน
- **การยกเว้นที่แนะนำต่อแอป** สำหรับอิมเมจที่รู้จักดี (Plex, Jellyfin, Emby, Sonarr, Radarr, Lidarr, Readarr, Prowlarr, Immich, Nextcloud, PhotoPrism และ Tautulli จาก linuxserver, hotio, binhex หรือผู้เผยแพร่ทางการ) ตัวช่วยยกเว้นในการ์ด **รูปแบบการยกเว้น** เสนอโฟลเดอร์ที่แอปเติมขึ้นใหม่เอง: แคช บันทึก ภาพตัวอย่าง และโปสเตอร์ แต่ละรายการบอกว่ามีอะไร ปิดรายการใดก็ได้ และไม่มีอะไรถูกยกเว้นจนกว่าคุณกด **ยกเว้นรายการที่เลือก**
- **รายงานบั๊ก** **รายงานบั๊ก** ในการ์ด **ความช่วยเหลือ** ใต้ **การตั้งค่า, ข้อมูล** ดาวน์โหลด ZIP ที่ปกปิดข้อมูลสำหรับ issue บน GitHub: การตรวจการผสานรวมโฮสต์ การตั้งค่าของคุณโดยลบความลับทุกอย่าง การทำงานล่าสุด สิ่งที่ตั้งเวลาไว้ถัดไป และบันทึกล่าสุด ยังมีผลการดัมป์ล่าสุดของแต่ละฐานข้อมูล รายการ ZFS พร้อมเมานต์ที่ container เห็น ความผิดปกติที่เปิดอยู่ และจำนวนคีย์ MCP ที่มี (ไม่เคยมีชื่อ) รหัสผ่าน โทเค็น rclone config ข้อมูลรับรองการแจ้งเตือน และรหัสผ่านที่ฝังในตำแหน่งรีพอสิทอรีถูกลบทั้งหมด และชุดข้อมูลบอกไว้ในแมนิเฟสต์ของตัวเอง เพราะไฟล์สนับสนุนต้องไม่ถูกเข้าใจผิดเป็นสำรองข้อมูลตัวเอง ต้องมีรหัสผ่านเข้าสู่ระบบด้วยเหตุผลเดียวกับชุดกู้คืน บันทึกที่มาด้วยคือเอาต์พุตของ container นี้ตั้งแต่เริ่มครั้งล่าสุด สำหรับการล่มที่รีสตาร์ท container ให้ดูที่ `docker logs`
- **ชุดกู้คืน** **ดาวน์โหลดชุดกู้คืน** ใต้ **การตั้งค่า, กู้คืน** ให้คีย์ รหัสผ่าน restic ที่ได้มา และตำแหน่งรีพอสิทอรีกับคำสั่งที่แน่นอน เพื่อให้กู้คืนได้โดยไม่ต้องมี BombVault ที่รันอยู่ ต้องมีรหัสผ่านเข้าสู่ระบบ ดู [Off-site & recovery](offsite-recovery.md#recovery-kit)
- **ส่งออกและนำเข้าการตั้งค่า** การ์ด **ส่งออก / นำเข้าการตั้งค่า** ใต้ **การตั้งค่า, ระบบ** เขียนการตั้งค่าทั้งหมดของคุณ (การตั้งค่าของแต่ละส่วน ปลายทาง ตารางเวลา การเก็บรักษา การแจ้งเตือน) ลงไฟล์ JSON แบบพกพา ดังนั้นการย้ายไปเครื่องใหม่หรือการโคลนการตั้งค่าไม่ต้องกรอกทุกอย่างใหม่ด้วยมือ คุณเลือกได้ว่าจะรวมข้อมูลรับรองนอกสถานที่และการแจ้งเตือนหรือไม่ ถ้ารวม ไฟล์ละเอียดอ่อนเท่าชุดกู้คืน การนำเข้าแสดงตัวอย่างและขอการยืนยัน และไม่แตะข้อมูลสำรองหรือประวัติของคุณเลย
- **การแจ้งเตือน** Webhook (Discord / Slack / Gotify / ntfy), Matrix, Healthchecks.io, อีเมล (SMTP), เซิร์ฟเวอร์ [Apprise API](https://github.com/caronc/apprise-api) ที่โฮสต์เอง และระบบแจ้งเตือนดั้งเดิมของ Unraid นโยบายต่อการสำรอง: ไม่เลย / เมื่อล้มเหลว / ทุกครั้ง การรันตามตารางเวลาของหลายรายการส่งสรุปเดียว *สำเร็จ N จาก M รายการ* ได้ Healthchecks ได้รับวงจรชีวิตครบ (`/start` แล้วสำเร็จหรือ `/fail`) เมื่อใดก็ตามที่ตั้ง URL
- **สรุปรายสัปดาห์** หนึ่งข้อความต่อสัปดาห์ผ่านช่องทางเดียวกัน: จำนวนการรัน ข้อมูลสำรองใหม่เข้ามาเท่าไร นอกสถานที่ทันสมัยหรือไม่ และความล้มเหลวหลัก ปิดเป็นค่าเริ่มต้น มีรอบของตัวเองใต้ **การตั้งค่า, การแจ้งเตือน** สัปดาห์ที่เงียบจึงถูกรายงานเช่นนั้นด้วย
- **Prometheus `/metrics`** เลือกเปิดได้ (ปิดเป็นค่าเริ่มต้น bearer token ไม่บังคับ) ในการ์ด **บริการ** ใต้ **การตั้งค่า, การเชื่อมต่อ** สำหรับ Grafana หรือ Uptime Kuma เปิดเผยสถานะ ขนาด และเวลาของการสำรอง โดยไม่มีความลับหรือพาธในป้ายกำกับ
- **HTTP API, Home Assistant และ mDNS** สคริปต์และแดชบอร์ดได้ API ใต้ `/api/v1` พร้อมโทเค็นที่ตั้งชื่อ อ่านอย่างเดียวหรืออนุญาตให้เริ่มการสำรอง Home Assistant พบ BombVault ผ่านการค้นพบ MQTT เป็นอุปกรณ์ที่มีเซ็นเซอร์ และถ้าคุณอนุญาต มีปุ่มสำรองต่อส่วน และ BombVault ประกาศตัวเองบนเครือข่ายเป็น `bombvault.local` ดู [API และการเชื่อมต่อ](api.md)
- **พื้นที่ว่างและกี่สัปดาห์กว่าจะเต็ม** รีพอสิทอรีในเครื่อง รีพอสิทอรี SFTP และปลายทาง SMB หรือ WebDAV ที่รายงานได้แสดงพื้นที่ว่างและจำนวนสัปดาห์ที่เหลือตามการเติบโตปัจจุบัน รีพอสิทอรี S3, B2 และ REST แสดง "ไม่ทราบขนาด" เพราะแบ็กเอนด์เหล่านั้นไม่รายงาน
- **ขนาดตามโฟลเดอร์** บนแท็บความสมบูรณ์ของ container, VM หรือชุดโฟลเดอร์ **ขนาดตามโฟลเดอร์** แสดงว่าโฟลเดอร์และไฟล์ใดใช้พื้นที่ในข้อมูลสำรองล่าสุด และข้อมูลสำรองล่าสุดนำเข้ามาใหม่หรือเปลี่ยนเท่าไรจากแต่ละอัน ทีละระดับ BombVault อ่านจากดัชนีของรีพอสิทอรีโดยไม่อ่านไฟล์ และอัปเดตให้ทันสมัยหลังการสำรองทุกครั้งเมื่อคุณเปิดดูแล้ว
- **ทำไมการสำรองข้อมูลจึงช้า** ระหว่างสำรองข้อมูล BombVault จะดูว่า CPU ดิสก์ และเครือข่ายทำงานหนักเพียงใด เมื่อการสำรองข้อมูลใช้เวลานานกว่าปกติมากและมีสิ่งหนึ่งที่ถึงขีดจำกัดอย่างชัดเจน รายการรันจะบอกไว้ เช่น "ดิสก์ปลายทาง disk1 ทำงานอยู่ 98%" หรือ "BombVault ใช้ 100% ของขีดจำกัด CPU ของคอนเทนเนอร์" มิฉะนั้นจะไม่แสดงอะไร
- **เปลี่ยนไปตั้งแต่การสำรองข้อมูลครั้งล่าสุด** คอนเทนเนอร์ที่ถูกสร้างใหม่ด้วยอิมเมจ พอร์ต ตัวแปร หรือวอลุ่มอื่นหลังการสำรองข้อมูลครั้งล่าสุดจะมีเครื่องหมายข้างชื่อ ปุ่ม (i) ของมันจะบอกว่าอะไรเปลี่ยนไป โดยแสดงตัวแปรเพียงชื่อ เป็นเพียงข้อความแจ้งและจะหายไปหลังการสำรองข้อมูลครั้งถัดไป

## การป้องกันแรนซัมแวร์

- **การป้องกันการลบ (append-only)** เปิดสำหรับปลายทางนอกสถานที่เพื่อไม่ให้แรนซัมแวร์หรือโฮสต์ที่ถูกบุกรุกลบหรือเขียนทับข้อมูลสำรองของคุณ ฝั่งไกล (`restic/rest-server` ในโหมด `--append-only`) บังคับใช้ BombVault เพียงตรวจสอบและไม่เคยแสดงสีเขียวจากคำกล่าวอ้างในการตั้งค่าอย่างเดียว โฟลเดอร์บนเซิร์ฟเวอร์นี้ปฏิเสธการลบไม่ได้ ปลายทางในเครื่องจึงไม่มีสวิตช์นี้
- **การทดสอบการแทรกแซง** BombVault พิสูจน์การรับประกัน append-only เป็นระยะโดยพยายามลบจริงกับรีพอสิทอรีนอกสถานที่ (เล็งที่วัตถุที่ไม่มีอยู่): ถูกปฏิเสธคือได้รับการป้องกัน ถูกยอมรับคือไม่ได้รับการป้องกัน ผลที่สรุปไม่ได้ไม่เคยพลิกคำตัดสินที่เก็บไว้ **ทดสอบการป้องกันการลบตอนนี้** บนหน้าของปลายทางรันตามต้องการ
- **การตั้งค่าแบบนำทาง** **เพิ่มปลายทาง** พาคุณจากผู้ให้บริการผ่านการเข้าสู่ระบบ การทดสอบการเชื่อมต่อ และโฟลเดอร์ ไปจนถึงคำพูดตรง ๆ เรื่องการป้องกันการลบและส่วนที่สำรองไปที่นั่น
- **การซ้อม DR (นอกสถานที่)** การกู้คืนทดลองนำเป้าหมายจริงจากรีพอสิทอรีนอกสถานที่ไปใส่ในแซนด์บ็อกซ์ที่แยกออก ตรวจสอบทีละไฟล์และทีละไบต์ แล้วทำความสะอาด ดู [Off-site & recovery](offsite-recovery.md)
- **สถานะการป้องกัน** การ์ดภาพรวมตรวจทุกส่วนว่ามีข้อมูลสำรองปัจจุบัน สำเนานอกสถานที่ การป้องกันการลบที่นั่น และการกู้คืนทดลองจากที่นั่น เป็นสีเขียวเฉพาะเมื่อมีข้อเท็จจริงที่ตรวจสอบแล้ว
- **สัญญาณเตือนงบประมาณการเติบโต** สำหรับปลายทาง append-only (ที่ข้อมูลสำรองเก่าไม่เคยถูกตัดทิ้งจากที่นี่) ตั้งงบประมาณขนาดและรับการเตือนก่อนที่จะบานปลาย
- **การลบต้องมีรหัสผ่าน** การลบข้อมูลสำรองที่ปลายทางต้องมีรหัสผ่านเข้าสู่ระบบและการเข้าสู่ระบบที่อินสแตนซ์นั้นเอง ดังนั้นทั้งโทรศัพท์ที่จับคู่หรืออินเทอร์เฟซที่เปิดอยู่ก็ทำไม่ได้
- **การจับคู่ด้วยวลี** อินสแตนซ์เข้าร่วมกลุ่มเดียวกันด้วยคำสิบสองคำ: สร้างวลีบนเครื่องหนึ่ง พิมพ์บนเครื่องถัดไป สมาชิกในเครือข่ายเดียวกันคุยกันโดยตรง ส่วนที่เหลือผ่านรีเลย์ (รีเลย์ของโปรเจกต์ ของคุณเอง หรือไม่มี) และทุกการเรียกระหว่างกันเข้ารหัสแบบ end-to-end กลุ่มส่งสถานะการป้องกันบนหน้าอินสแตนซ์ คำขอบทบาท ข้อเสนอปลายทาง และสิ่งที่ตัวรับหรือตัวดึงต้องใช้เมื่อบทบาทได้รับอนุญาต ไม่เคยส่งข้อมูลสำรองและไม่เคยส่ง APP_KEY ดู [Off-site & recovery](offsite-recovery.md#pairing)
- **อินสแตนซ์และบทบาท** เปิด **อินสแตนซ์** ใต้ **การตั้งค่า, อินสแตนซ์, หลายเซิร์ฟเวอร์** เพื่อให้มีหน้าที่มีการ์ดสำหรับทุกอินสแตนซ์ของกลุ่มคุณ รวมเครื่องนี้ด้วย: ที่อยู่ เชื่อมต่ออยู่หรือไม่ และการป้องกันของแต่ละส่วนพร้อมการสำรองล่าสุด บทบาทของมันอยู่บนการ์ดเป็นไทล์: **ตัวรับ**, **ตัวดึง**, **เซิร์ฟเวอร์ ZFS** และ **ผู้เก็บคีย์** บทบาทเริ่มก็ต่อเมื่อมีคนที่อินสแตนซ์อีกฝั่งกด **อนุญาต** และกลุ่มแสดงเป็นเครือข่ายว่าใครทำอะไรให้ใคร **ตรวจสอบเดี๋ยวนี้** ขอให้สมาชิกตรวจรีพอสิทอรีของหนึ่งส่วน ไม่มีอะไรบนหน้านี้เริ่มการสำรอง การกู้คืน หรือลบอะไรบนเครื่องอื่นได้ ดู [อินสแตนซ์และบทบาท](offsite-recovery.md#roles)
- **ข้อเสนอปลายทาง** สมาชิกเสนอปลายทางนอกสถานที่ของตัวเองให้สมาชิกอื่นผ่านกลุ่มได้ ผู้ดูแลอีกฝั่งเห็นข้อเสนอใน **รายละเอียด** ของสมาชิกบนหน้าอินสแตนซ์ และยอมรับหรือปฏิเสธ การยอมรับสร้างชุดข้อมูลรับรองและปลายทางธรรมดา มีเพียงรายละเอียดการเชื่อมต่อที่เดินทางทางนี้ ไม่เคยมีข้อมูลสำรอง
- **รีพอสิทอรีที่รับมา (ฝั่งรับ)** บนเครื่องที่รับสำเนานอกสถานที่แบบ append-only จาก BombVault อีกเครื่อง เปิด **ตัวรับ** ใต้ **การตั้งค่า, อินสแตนซ์** แล้วเพิ่มรีพอสิทอรีที่รับมาใน **รายละเอียด** ของสมาชิกที่ส่ง แบบอ่านอย่างเดียว (เปิดด้วยรหัสผ่าน restic ของอินสแตนซ์ที่ส่ง ซึ่งมาทางกลุ่มการจับคู่) คุณเห็นรายการข้อมูลสำรองจัดกลุ่มตามต้นทาง เวลาที่แต่ละต้นทางมาถึงล่าสุด และรัน `restic check` อิสระบนฮาร์ดแวร์ฝั่งรับได้ มันเตือนเมื่อต้นทางหยุดส่งภายในช่วงเวลาที่คุณตั้ง (สวิตช์คนตาย) หรือเมื่อการตรวจความสมบูรณ์ล้มเหลว อ่านอย่างเดียวโดยเคร่งครัด จึงไม่เขียนลงรีพอสิทอรีที่รับมาเลย และปิดเป็นค่าเริ่มต้น ดู [Off-site & recovery](offsite-recovery.md#receiver)
- **ดึงจากอินสแตนซ์อื่น (ฝั่งดึง)** ภาพสะท้อนของสำเนานอกสถานที่: แทนที่เครื่องนี้ส่งข้อมูลสำรองออกไป มันดึงของคนอื่นเข้ามา เปิด **ดึง** ใต้ **การตั้งค่า, อินสแตนซ์** แล้วเพิ่มต้นทางใน **รายละเอียด** ของสมาชิกอีกฝั่ง: ตำแหน่งรีพอสิทอรีของมัน ชนิดของข้อมูลสำรองที่มี และดึงบ่อยแค่ไหน รหัสผ่าน restic ของมันมาทางกลุ่ม ไม่เคยเป็น APP_KEY ฝั่งไกลไม่ต้องตั้งค่าอะไรเพิ่มและไม่ต้องรันอยู่ รีพอสิทอรีต้นทางถูกอ่านเท่านั้น: เปิดเพื่อตรวจรหัสผ่าน แสดงรายการ และระบุเป็นต้นทางของการคัดลอก และไม่เคยถูกเริ่มต้น ปลดล็อก ตัดทิ้ง หรือเขียน แต่ละฝั่งเก็บข้อมูลรับรองของตัวเอง และต้นทาง `rclone:` ถูกปฏิเสธเพราะ rclone จะเข้าถึงมันด้วยรีโมตของอินสแตนซ์นี้ ดู [Off-site & recovery](offsite-recovery.md#receiver)
- **ผู้เก็บคีย์** อินสแตนซ์อื่นในกลุ่มของคุณเก็บสำเนาชุดกู้คืนของเซิร์ฟเวอร์นี้ที่ปิดผนึกไว้ได้ ซึ่งมีเพียงรหัสปลดล็อก 20 ตัวอักษรของคุณเท่านั้นที่เปิดได้ และจะส่งมอบก็ต่อเมื่อมีคนที่นั่นกด **อนุญาต** ดู [ผู้เก็บคีย์](offsite-recovery.md#key-keeper)

## การส่งออกแบบธรรมดา

- **การส่งออก container และ VM** **ส่งออกคอนเทนเนอร์** และ **ส่งออก VM** ใต้ **เพิ่มเติม** บนหน้าของรายการเขียนสำเนาที่เรียกดูได้และไม่ต้องใช้เครื่องมือไว้ข้างรีพอสิทอรี: โฟลเดอร์ที่สำรองข้อมูลของ container ตามที่เป็นอยู่ตอนนี้พร้อมเทมเพลต Unraid หรืออิมเมจดิสก์ของ VM พร้อมคำจำกัดความ กู้คืนได้ด้วย `virsh define` กับดิสก์ โดยไม่ต้องใช้ BombVault หรือ restic **ส่งออก** บนข้อมูลสำรองเขียนข้อมูลสำรองที่เก็บไว้แบบเดียวกัน เป็น tar, zip หรือรีพอสิทอรี restic ของตัวเอง restic ยังเป็นเอนจิน นี่คือสำเนาเพื่อความสะดวกเพิ่มเติม
- **เข้ารหัสการส่งออกธรรมดา (age)** การส่งออกอยู่นอก restic จึงเป็นข้อความธรรมดาโดยค่าเริ่มต้น เปิด **เข้ารหัสการส่งออกด้วย age** ใต้ **การตั้งค่า, ระบบ** และเพิ่มผู้รับหนึ่งรายหรือมากกว่า (คีย์สาธารณะ age หรือคีย์สาธารณะ SSH) ทุกการส่งออก (รวม ZIP ของแฟลช) จะถูกปิดผนึกสำหรับผู้รับเหล่านั้น และคุณถอดรหัสภายหลังนอกเครื่องด้วยคีย์ส่วนตัวที่คู่กัน เป็นกฎความปลอดภัย เมื่อเปิดการเข้ารหัสและไม่มีผู้รับที่ถูกต้อง การส่งออกจะล้มเหลวพร้อมข้อผิดพลาดที่ชัดเจนแทนที่จะเขียนข้อความธรรมดา
- **ชุดกู้คืนก็ถูกผนึกด้วย** เมื่อเปิดการตั้งค่าเดียวกันนี้ ชุดกู้คืนจะดาวน์โหลดเป็น `bombvault-recovery-kit.md.age` มันอยู่ในรูปแบบ ASCII-armored แทนที่จะเป็นไบนารี จึงยังคงเป็นข้อความธรรมดาที่อ่านได้: คุณยังวางมันลงในตัวจัดการรหัสผ่านหรือพิมพ์ออกมาได้ ซึ่งเป็นสิ่งที่ชุดกู้คืนมีไว้ กฎความปลอดภัยเดียวกันมีผล ดังนั้นเมื่อเปิดการเข้ารหัสแต่ไม่มีผู้รับที่ใช้ได้ การดาวน์โหลดจะถูกปฏิเสธแทนที่จะถอยกลับไปส่ง master key แบบข้อความธรรมดา มีเรื่องหนึ่งที่ต้องทำให้ถูกเมื่อเปิดสิ่งนี้: คุณต้องใช้คีย์ส่วนตัว age ของคุณเพื่อเปิดชุดกู้คืน ดังนั้นเก็บคีย์นั้นไว้ในที่ที่ไม่ขึ้นกับตัวชุดกู้คืนเอง

## ผู้ช่วย AI (MCP) {#mcp}

BombVault มีเซิร์ฟเวอร์ MCP ในตัว ผู้ช่วยอย่าง Claude Code หรือ Claude Desktop จึงอ่านสถานะการสำรอง ความครอบคลุม ประวัติการรัน จุดกู้คืน และกิจกรรมปัจจุบันได้ ด้วยคีย์ที่อนุญาต ผู้ช่วยยังเริ่มการสำรองของหนึ่งรายการ หนึ่งส่วน หรือทั้งหมด และยกเลิกการสำรองที่มันเริ่มได้ การกู้คืน การลบ การตัดทิ้ง และการตั้งค่ายังอยู่ในเว็บอินเทอร์เฟซ แต่ละไคลเอนต์ได้คีย์ของตัวเองใต้ **การตั้งค่า, การเชื่อมต่อ, เซิร์ฟเวอร์ MCP** คีย์แสดงครั้งเดียว เก็บเป็นลายนิ้วมือเท่านั้น และเปลี่ยนชื่อ แทนที่ หรือเพิกถอนได้ทุกเมื่อ การเริ่มถูกจำกัดต่อชั่วโมงและต่อรายการ และตัวป้องกันการเก็บรักษาไม่ให้การสำรองของผู้ช่วยผลักจุดกู้คืนของคุณเองออกจากนโยบาย "เก็บ N ล่าสุด" ทุกการรันที่ผู้ช่วยเริ่มถูกทำเครื่องหมาย "via MCP" พร้อมชื่อคีย์ ดู [เซิร์ฟเวอร์ MCP](mcp.md) ดัมป์ฐานข้อมูลและ[ชุดข้อมูล ZFS](zfs-datasets.md) อยู่ในรายการและจุดกู้คืนที่มันอ่าน และมันแสดงรายการความผิดปกติที่ BombVault สังเกตเห็นได้

## แอปและเครื่องมือคู่หู {#apps}

- **แอป Android** เซิร์ฟเวอร์ทุกเครื่องในกลุ่มของคุณบนโทรศัพท์ พร้อมบันทึกกิจกรรมของทุกเครื่องในหน้าจอเดียว จับคู่กับกลุ่มของคุณด้วยคิวอาร์โค้ดและเปิดแต่ละเซิร์ฟเวอร์ในสถานะเข้าสู่ระบบแล้ว ด้วยเซสชันที่เข้าถึงได้เฉพาะสิ่งที่แอปแสดง ดู [แอป Android](android.md)
- **เซิร์ฟเวอร์รับข้อมูล** เครื่องที่รับสำเนานอกสถานที่รัน rest-server แบบ append-only ซึ่งตั้งค่าเมื่อมันอนุญาตคำขอ **ตัวรับ** ครั้งแรก และเสนอให้อินสแตนซ์อื่นในกลุ่มของคุณ แต่ละอินสแตนซ์มีล็อกอินของตัวเอง ดู [เซิร์ฟเวอร์รับข้อมูล](offsite-recovery.md#receiving-server)
- **การตั้งค่า, แอป** หน้าที่เริ่มด้วยแอป Android พร้อม APK ของรุ่นที่เซิร์ฟเวอร์รันอยู่และคิวอาร์โค้ดสำหรับมัน ตามด้วยการ์ดสำหรับเครื่องมือคู่หูแต่ละตัว การ์ดของ ParleyPort มีเทมเพลต Unraid ของมัน คัดลอกคำสั่ง Docker ที่ใช้เริ่มมันได้ และพาไปยังรีพอสิทอรีของมันและการตั้งค่ารีเลย์ใต้การจับคู่ การ์ดของ BombVault Widget มีเทมเพลตและรีพอสิทอรีของมัน และติดตั้งหรือลบปลั๊กอินผ่านการเชื่อมต่อ SSH ของโฮสต์
- **BombVault Widget** ไทล์บนแดชบอร์ดของ Unraid ที่แสดงบันทึกกิจกรรมของ BombVault และการทำงานตามกำหนดการครั้งถัดไป หากไม่มีการเชื่อมต่อ SSH ของโฮสต์ การ์ดจะให้ที่อยู่ `.plg` สำหรับติดตั้งใน **Plugins, Install Plugin** และลบปลั๊กอินได้จากที่นั่นเหมือนปลั๊กอินอื่น ๆ
- **บันทึกกิจกรรมแบบฝังได้** สร้างโทเค็นแบบอ่านอย่างเดียวในการ์ด **วิดเจ็ตแดชบอร์ด** ใต้ **การตั้งค่า, การเชื่อมต่อ** แล้วคุณจะได้ที่อยู่สำหรับแดชบอร์ดใดก็ได้ที่แสดง iframe เช่น Homepage, Organizr หรือ Heimdall: หน้าเล็ก ๆ ที่มีเฉพาะบันทึกกิจกรรมสด โทเค็นให้สิทธิ์เฉพาะบันทึกนั้น และ **ปิดใช้งาน** เพิกถอนทันที หน้าที่ฝังเป็นภาษาอังกฤษเท่านั้น

## อื่นๆ

- **หยุดการสำรองที่กำลังรัน** ขณะที่การรันทำงานอยู่ **ยกเลิกการสำรองข้อมูล** อยู่ข้างความคืบหน้าของมัน การรันถูกบันทึกเป็น *ยกเลิก* ไม่ใช่ล้มเหลว การหยุดปลอดภัย เพราะ restic เขียนสแนปช็อตเป็นอย่างสุดท้าย การรันที่ถูกขัดจึงเหลือข้อมูลที่ไม่มีใครอ้างถึงและไม่มีสแนปช็อต
- **สำรองหลายรายการพร้อมกัน** เลือกรายการในรายการการสำรองข้อมูลและสำรองส่วนที่เลือก ชุดงานรันบนเซิร์ฟเวอร์ จึงทำต่อแม้คุณปิดแท็บหรือขาดการเชื่อมต่อ BombVault ไม่เคยสำรอง (และจึงไม่เคยหยุด) container ของตัวเอง
- **ข้อมูลสำรองบนหน้าของรายการ** พร้อมรายการจุดกู้คืน การลบทีละชุด แท็กของคุณเอง และการเปรียบเทียบระหว่างข้อมูลสำรองสองชุด
- **การดูแลรีพอสิทอรีต่อส่วน** ในการ์ด **ตรวจสอบข้อมูลสำรอง** ใต้ **การตั้งค่า, ยืนยัน**: การตรวจสอบ (`restic check`) และใต้ **เพิ่มเติม** มี **ปลดล็อก** (ล้างล็อกที่ค้าง) และ **ตัดทิ้ง** (ใช้นโยบายการเก็บรักษาตามต้องการเมื่อมีตั้งไว้ มิฉะนั้นเป็นการเรียกคืนพื้นที่ธรรมดา)
- **ความคืบหน้าของการตรวจสอบ การตรวจการกู้คืน และการตัดทิ้ง** ขณะที่อย่างใดอย่างหนึ่งรันอยู่ บันทึกกิจกรรมและการ์ด **ตรวจสอบข้อมูลสำรอง** แสดงว่า restic นับไปถึงไหน เช่น *12 จาก 47 แพ็ก* พร้อมเวลาที่เหลือในขั้นตอนนั้นเมื่อมีข้อมูลพอจะประมาณ restic นับแพ็ก สแนปช็อต และไฟล์ดัชนีที่นี่ ไม่ใช่ไบต์ แถบจึงแสดงสิ่งนั้น ก่อนการนับครั้งแรกจะรันโดยไม่มีตัวเลข
- **ดัมป์ฐานข้อมูลอัตโนมัติ** Container PostgreSQL, MySQL และ MariaDB ที่รู้จัก (อิมเมจทางการ, PostGIS, TimescaleDB, pgvector, pgautoupgrade, อิมเมจฐานข้อมูลของ Immich, MariaDB ของ linuxserver, yobasystems และ jc21 และ mysql-server ของ Oracle) จะถูกดัมป์ก่อนการสำรองทุกครั้งจากเซิร์ฟเวอร์ที่รันอยู่ Container ที่เพียงดูเหมือนฐานข้อมูลได้ตัวเลือกเดียวกันในการ์ด **ฐานข้อมูล** บนแท็บการตั้งค่าของมัน ปิดไว้จนกว่าคุณเลือก ดัมป์ไหลตรงเข้ารีพอสิทอรีเป็นจุดกู้คืนของตัวเองข้างการสำรองไฟล์ และไม่เคยถูกเขียนลงดิสก์ ข้อมูลรับรองมาจากตัวแปรของ container เอง รวมถึงความลับ `*_FILE` และไม่เคยออกจากมัน การ์ดแสดงว่าโฟลเดอร์ข้อมูลของฐานข้อมูลถูกบันทึกขณะหยุด คัดลอกขณะรัน หรือไม่ถูกบันทึกเลย ดัมป์ที่ล้มเหลวไม่ทำให้การสำรองล้มเหลว: แสดงเป็นการรันที่ล้มเหลวพร้อมเหตุผลและคำแนะนำวิธีแก้ และส่งการแจ้งเตือน ดัมป์ไม่เคยถูกโหลดกลับโดยอัตโนมัติ ดาวน์โหลดหนึ่งชุด (ธรรมดาหรือบีบอัด) บันทึกลงโฟลเดอร์ นำเข้าสู่ฐานข้อมูลที่เพิ่งเริ่มด้วยคลิกเดียว หรือดึงด้วย restic CLI ปิดต่อ container ด้วยป้าย `bombvault.dbdump=false` หรือสำหรับทุก container ด้วย **ดัมป์ฐานข้อมูลอัตโนมัติ** ใต้ **การตั้งค่า, ทั่วไป** การตรวจจับความผิดปกติเฝ้าดูขนาดของทุกดัมป์ด้วย และผู้ช่วยแสดงรายการดัมป์ของ container ได้ผ่าน[เซิร์ฟเวอร์ MCP](mcp.md#tools)
- **คำสั่งก่อนและหลัง ต่อ container** คำสั่งเชลล์รันภายใน container (เช่น ล้างแคช) คำสั่งที่ล้มเหลวก่อนการสำรองทำให้การสำรองยกเลิก ฐานข้อมูลที่รู้จักถูกดัมป์โดยอัตโนมัติ จึงไม่ต้องใช้คำสั่ง
- **หยุด container อื่นระหว่างสำรอง พร้อมการรีสตาร์ทที่รอสุขภาพ** ระบุ container ที่พึ่งพา (เช่นฐานข้อมูล) ใน **หยุดคอนเทนเนอร์อื่น** เพื่อหยุดขณะตัวนี้ถูกสำรอง หลังจากนั้น BombVault นำกลับมาตามลำดับ `depends_on` ของ Compose และโดยค่าเริ่มต้นรอให้แต่ละตัวรายงานว่า healthy (หรือกำลังรัน ถ้าไม่มี healthcheck) ก่อนเริ่ม container ที่พึ่งพามัน ดังนั้นสิ่งที่พึ่งพาอย่าง Pi-hole ฐานข้อมูล หรือเกตเวย์ VPN จึงขึ้นจริงก่อนบริการที่ต้องใช้ แทนที่บริการเหล่านั้นจะกลับมาพร้อม *connection refused* การรอถูกจำกัดด้วย timeout ต่อ container (120 วินาทีโดยค่าเริ่มต้น) เพื่อไม่ให้ container ที่ช้าหรือไม่เคย healthy ทำให้การรันค้าง ทั้งการรอและ timeout อยู่ใต้ **รีสตาร์ทหลังการสำรองข้อมูล** ในการ์ด **ลำดับ** ใต้ **การตั้งค่า, ตารางเวลา** (ปิดการรอเพื่อรีสตาร์ททั้งหมดพร้อมกัน) การรีสตาร์ทตามลำดับที่รอสุขภาพเดียวกันยังครอบการอัปเดตอิมเมจหลังการสำรองด้วย ในวันที่มีการอัปเดต ตัวที่พึ่งพาจะถูกกดไว้ตลอดการสร้างใหม่ และนำกลับมาแบบรอสุขภาพเมื่อเสร็จเท่านั้น
- **รูปแบบการยกเว้นต่อ container** ระบุไดเรกทอรีย่อยที่จะข้ามภายในโวลุ่มที่สำรองข้อมูล บรรทัดละหนึ่งรายการ พิมพ์พาธตามที่คุณเห็นภายใน container ตัวอย่างแบบสดจะแสดงสิ่งที่แต่ละบรรทัดแปลงเป็น และเตือนเมื่อบรรทัดหนึ่งจะไม่ยกเว้นอะไรเลย
- **อัปเดตหลังการสำรองข้อมูลสำเร็จ (ปิดเป็นค่าเริ่มต้น)** เปิด **อัปเดตคอนเทนเนอร์หลังการสำรองข้อมูลสำเร็จ** ใต้ **การตั้งค่า, ตารางเวลา, อัปเดตหลังการสำรองข้อมูล** หรือตั้ง container เดี่ยวต่างออกไปบนหน้าของมัน แล้ว BombVault ดึงอิมเมจใหม่ล่าสุดและสร้าง container ใหม่ แต่เฉพาะเมื่อมีอิมเมจที่ใหม่กว่าจริง ๆ ดังนั้นจึงมีจุดกู้คืนใหม่เสมอก่อน ส่วนเสริมที่เลือกได้: การแจ้งเตือนต่อ container ที่อัปเดต และ **ลบ image เก่าหลังการอัปเดต** (อิมเมจพื้นฐานที่ container อื่นใช้ร่วมไม่เคยถูกลบ) หลังการอัปเดต BombVault ยังขอให้ Unraid ตรวจสถานะการอัปเดตของ container นั้นอีกครั้ง เพื่อให้แบนเนอร์ *update available* ที่ค้างบนแท็บ Docker หายเองแทนที่จะค้างอยู่ (การอัปเดตของ Unraid ผ่าน Docker API โดยตรง สถานะที่แคชไว้ และในบางเวอร์ชัน digest ที่แคชไว้ จะยังแสดงแบนเนอร์) เป็นแบบทำเท่าที่ทำได้ ไม่กระทบการสำรอง เปิดเป็นค่าเริ่มต้น และสลับด้วย **รีเฟรชสถานะการอัปเดตของ Unraid หลังอัปเดต container** ในการ์ดเดียวกัน
- **กู้คืนไปยังโฟลเดอร์อื่น** สำหรับการโคลนหรือการตรวจสอบ
- **มีอะไรใหม่หลังการอัปเดต** บันทึกประจำรุ่นปรากฏครั้งเดียวต่อเวอร์ชันใหม่ ส่งจากบันทึกที่ฝังในไบนารี หน้าต่างจึงใช้งานออฟไลน์ได้ จุดสีเขียวทำเครื่องหมายแต่ละการเปลี่ยนแปลงบนหน้าของมัน และการ์ด **ใหม่** ใต้ **การตั้งค่า, ข้อมูล** แสดงทั้งหมดพร้อม **ไปที่นั่น**
- **ข้อมูล** **การตั้งค่า, ข้อมูล** มี **รุ่น** (BombVault, GlimStone, restic และ rclone พร้อม **ตรวจหาอัปเดต**), **ความช่วยเหลือ** พร้อม **คู่มือ** และ **รายงานบั๊ก**, **ใหม่** และ **เกี่ยวกับ BombVault**
- **HTTPS พร้อมใช้งานทันที** (self-signed หรือใช้ใบรับรองของคุณเองหลัง reverse proxy)
- **Docker healthcheck** container รายงานสมบูรณ์/ไม่สมบูรณ์จาก `/api/health` ของตัวเอง ดังนั้นเครื่องมือ auto-heal จึงสามารถรีสตาร์ทมันได้หากเอนจินติดขัด
- **42 ภาษา** พร้อมตัวเลือกแบบธงใต้ **การตั้งค่า, รูปลักษณ์**
- **การตั้งค่าบันทึกเอง** สลับสวิตช์หรือออกจากช่อง การเปลี่ยนแปลงจะถูกเขียนทันที พร้อมแสงวาบสั้น ๆ บนตัวควบคุมและการสั่นถ้าเซิร์ฟเวอร์ปฏิเสธ บางที่ยังมีปุ่มบันทึกเพราะการบันทึกครึ่ง ๆ กลาง ๆ ไม่ปลอดภัย เช่นกล่อง rclone config ตัวแก้ไขชุดข้อมูลรับรอง และรหัสผ่านเข้าสู่ระบบ
- **การแจ้งเตือนแบบเงียบ** ใต้ **การตั้งค่า, รูปลักษณ์** คุณปิดเสียงการยืนยันตามปกติได้ เหลือเพียงความล้มเหลวที่ยังขัดจังหวะคุณ ซึ่งไม่กระทบช่องทางการแจ้งเตือน
- **ทำให้หน้าตาเป็นอย่างที่คุณต้องการ** **การตั้งค่า, รูปลักษณ์** กำหนด **ธีม** (มืด สว่าง หรือระบบ) สี (สีเน้นหนึ่งสี หรือ *โหมดสายรุ้ง* พร้อมจานสีแปดสี) มุม (กลม นุ่ม หรือเหลี่ยม) แอนิเมชัน (ปิด เบา ป่า หรือพายุ) และลำดับของไทล์การตั้งค่า BombVault เก็บรูปลักษณ์ไว้บนเซิร์ฟเวอร์ และเบราว์เซอร์ที่เข้ามาครั้งแรกรับไปใช้ เมื่อระบบของคุณขอให้ลดการเคลื่อนไหว สิ่งนั้นชนะเสมอ
