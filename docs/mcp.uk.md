# Сервер MCP

У BombVault вбудовано сервер Model Context Protocol (MCP), протоколу, за яким ШІ-помічники на кшталт Claude Code і Claude Desktop звертаються до зовнішніх інструментів. Через нього помічник може прочитати, як ідуть ваші копії, і, якщо ви дозволите, запустити копію або скасувати ту, яку сам запустив. Він вимкнений, поки ви не створите ключ або не ввімкнете [вхід через OAuth](#oauth): до того часу кінцева точка `/mcp` на все відповідає `404`.

## Що помічник може і чого не може {#tools}

| Інструмент | Що робить | Вид |
|---|---|---|
| `get_health` | Версія, ім'я екземпляра, чи триває копіювання і що дозволено цьому ключу | читання |
| `get_status` | Стан захисту за розділами: остання успішна копія, очікуваний інтервал, перевірки та зовнішні перевірки, найближчі планові запуски, копії, що чекають простою застосунку, а для контейнерів найсвіжіший тестовий запуск | читання |
| `get_coverage` | Що BombVault захищає і що ні, з причиною для кожного | читання |
| `list_items` | Кожен захищений контейнер, віртуальна машина, набір папок, флешка та конфігурація застосунку з розкладом, тим, що зупиняє копія, останньою копією та тим, скільки вона тривала. У контейнерів баз даних є й останній дамп. Набори даних ZFS теж перелічені, з результатом їхньої останньої перевірки. У кожного запису є остання перевірка відновлення, а в контейнера останній тестовий запуск або причина, чому його не можна перевірити. Контейнер, перестворений з іншими налаштуваннями після останньої копії, перелічує, що змінилося | читання |
| `list_runs` | Історія запусків, нові згори, з фільтрами за розділом, записом, станом, видом і часом. Повільна копія, яку щось одне затримало, називає це | читання |
| `list_restore_points` | Точки відновлення одного запису з його основного репозиторію, а для контейнера й його дампи баз даних. Набір даних ZFS отримує одну точку відновлення на копію, зі знімком кожного набору під ним | читання |
| `get_activity` | Що виконується зараз, з фазою і відсотком | читання |
| `get_storage_stats` | Історія розміру основного репозиторію одного розділу та його зростання за тиждень, а також використане, вільне й загальне місце на диску чи віддаленому ресурсі кожного з його репозиторіїв | читання |
| `get_size_breakdown` | Які папки та файли займають місце в найновішій копії одного контейнера, віртуальної машини чи набору папок і скільки з кожного додала остання копія | читання |
| `list_anomalies` | Аномалії, які BombVault помітив у копіях, з фільтрами за станом, серйозністю та розділом і з підсумком відкритих | читання |
| `get_anomaly` | Одна з цих знахідок, з приміткою, залишеною під час підтвердження | читання |
| `start_backup` | Копіює один запис зараз | запуск |
| `start_domain_backup` | Копіює кожен захищений запис одного розділу | запуск |
| `start_backup_everything` | Запускає прохід «Створити копію всього» | запуск |
| `cancel_backup` | Скасовує поточну копію, запущену цим ключем | скасування |

У вебінтерфейсі лишається таке: відновлення будь-якого виду (зокрема завантаження, збереження чи імпорт дампа бази даних), видалення копій, очищення, розблокування, перевірки та навчання, зовнішня реплікація, налаштування, облікові дані й ключі MCP, а також скасування копії, яку запустили розклад, вебінтерфейс чи інший ключ. Те саме стосується підтвердження аномалії та позначення її як очікуваної, що робиться на сторінці **Аномалії**. Причина в тому, що вивід інструментів містить імена й повідомлення про помилки з вашого сервера, і в будь-якому з них міг бути текст, написаний, щоб спрямовувати помічника. Помічник, який піддався такому тексту, у найгіршому разі запустить копію в межах обмежень нижче або скасує ту, яку запустив сам.

Якщо основний репозиторій запису віддалений (S3, REST, SFTP, rclone), `list_restore_points` звертається до нього, тож виклик може забрати час. Зовнішні копії через MCP перелічити не можна. Що дивляться перевірки аномалій, описано в розділі [Аномалії](anomalies.md), а як запис ZFS зберігає по одному знімку на набір даних, у розділі [Набори даних ZFS](zfs-datasets.md#contents).

## Що робить запущена копія {#starting-backups}

Копія помічника — та сама копія, яку запускає вебінтерфейс. Працюючий контейнер зупиняється, поки його копія не завершиться, разом із контейнерами, які мають зупинятися з ним. Віртуальна машина з методом коректного вимкнення вимикається й запускається знову. Набір даних ZFS зупиняє задані для нього контейнери, поки робиться його знімок. Набори папок, флешка й конфігурація продовжують працювати. Після цього BombVault застосовує політику зберігання й може скопіювати у зовнішній репозиторій. `list_items` повідомляє помічнику, що зупиняє запис і як довго тривала її остання копія, а описи інструментів просять його попередити вас, перш ніж щось запускати.

Оскільки копія щось зупиняє й витісняє старі точки відновлення, запуски через MCP обмежено:

- 12 запущених копій на годину на ключ.
- 15 хвилин між двома запусками MCP того самого запису, розділу чи «Створити копію всього».
- Не більше 4 запусків MCP одного запису за 24 години.
- **Захист зберігання.** Коли розділ зберігає фіксовану кількість точок відновлення (лише «зберігати останні N», без денного, тижневого чи місячного правила, локально або у зовнішньому місці), кожна нова копія витісняє найстарішу. BombVault тоді відмовляє в запуску MCP для запису, у якого всі найновіші N-1 успішних копій були запущені через MCP. Тож принаймні одна точка відновлення, зроблена розкладом чи вами, завжди лишається серед збережених. За «зберігати останню 1» помічник не може скопіювати цей запис взагалі. Наступна планова копія знову звільняє місце. Річне правило саме по собі рахується як «зберігати останню 1», бо зберігає одну точку відновлення за поточний рік.

Запуск розділу чи «Створити копію всього» пропускає записи, які затримує обмеження, і називає їх у відповіді. Вебінтерфейс і розклад нічим із цього не обмежені. Годинний бюджет живе в пам'яті, тому перезапуск BombVault його скидає.

Запуски через [API](api.md#errors) і з [Home Assistant](api.md#home-assistant) враховуються в тих самих обмеженнях на запис, що й запуски через MCP, і в захисті зберігання.

## Як увімкнути {#switch-on}

1. Відкрийте **Налаштування, Інтеграції, Сервер MCP**, натисніть **Вибрати клієнт** і виберіть свій у вікні. Пошук праворуч угорі знаходить його за іменем. Клієнт, якого немає в списку, підключається через **Інший клієнт**.
2. У розділі **Ключ** залиште **Новий ключ** і запропоноване ім'я, тобто ім'я клієнта, або введіть таке, яке каже, де ключ використовується, наприклад «Claude Code на ноутбуці». Один ключ на клієнта дозволяє відкликати один, не чіпаючи решту. **Наявний ключ** дає клієнту ключ, який ви створили раніше.
3. Увімкніть **Дозволити запуск копіювання** для ключа, який має вміти запускати копії. Без цього ключ може лише читати. Пізніше це можна змінити в **Подробиці** ключа, і зміна діє під час наступного запиту помічника без повторного підключення.
4. Натисніть **Створити ключ**. Ключ показується один раз. BombVault зберігає лише його відбиток і не може показати його знову, тому скопіюйте його зараз. Якщо ви закриєте вікно, перш ніж клієнт скористається ключем, картка продовжує його показувати, поки ви не підтвердите, що скопіювали.

Без пароля для входу сам вебінтерфейс відкритий усім у вашій мережі, і будь-хто, хто може його відкрити, може створити й ключ. Картка про це каже. Якщо ви відкриваєте BombVault під іменем, схожим на публічне (наприклад `bombvault.example.com` через зворотний проксі), і пароль для входу не задано, ключі з цієї адреси створювати й замінювати не можна, щоб жодна вебсторінка в інтернеті не могла змусити ваш браузер створити ключ. Задайте пароль для входу або відкрийте BombVault за його IP-адресою чи локальним іменем на кшталт `tower` або `tower.local`.

## Ваші ключі та їхній журнал {#keys}

У кожного ключа свій рядок у розділі **Ключі та підключені клієнти**. Він показує ім'я ключа, чи може він запускати копії, чи лише читати, останні чотири символи ключа, коли він створений або замінений востаннє і коли ним востаннє користувався клієнт. **Подробиці** відкривають вікно, де ключ можна перейменувати, змінити його дозвіл, замінити або відкликати і де видно, скільки викликів він зробив за сьогодні. Відкликаний ключ іде в список відкликаних, де його можна видалити остаточно, коли жоден запуск в історії його більше не називає.

Поруч з іменем у рядку стоїть значок клієнта, для якого створено ключ. Ключ, створений через **Інший клієнт** або до того, як картка перелічувала клієнтів, показує натомість ключ.

**Журнал** в подробицях ключа показує, що цей ключ робив, а у відкликаного ключа лишається власна кнопка **Журнал**. Спершу йдуть запущені ним копії, кожна зі станом і посиланням на цей запуск у журналі активності на панелі. Нижче йдуть його виклики, нові згори, з інструментом і тим, чим виклик закінчився. Відмова каже чому: ключ може лише читати, захист зберігання затримав копію, інша копія вже йшла, той самий запис, розділ чи прохід було запущено поза вебінтерфейсом кілька хвилин тому або ключ надіслав забагато запитів. Скасування посилається на запуск, про який ішлося.

BombVault зберігає записи кожного ключа до 30 днів: найновіші 500 успішних запусків і скасувань, а поруч із ними найновіші 200 інших викликів (читання, відмови та помилки). Помічник, який увесь час опитує поточну копію або повторює відхилений виклик, не може витіснити з журналу початок цієї копії. Для кожного виклику зберігаються інструмент, наслідок і запуск, який назвало скасування. Те, що надіслав помічник, ніколи не зберігається, як і ключ чи його відбиток. Пакет діагностики лише рахує записи, а експорт налаштувань їх не включає.

## Підключення клієнта {#clients}

**Вибрати клієнт** відкриває вікно, де кожен клієнт показаний плиткою в розділі **На цьому комп'ютері** або **У хмарі**, з пошуком праворуч угорі. Плитка відкриває налаштування клієнта в тому самому вікні в три кроки: ключ, конфігурація для цього клієнта з адресою, за якою ви відкрили картку, кнопкою копіювання, місцем, де конфігурація зберігається, і, з власним сертифікатом BombVault, тим, що клієнту потрібно для довіри до нього. І очікування першого виклику клієнта. Вікно стежить за останнім використанням ключа і стає зеленим, коли цей виклик надходить.

Налаштування не пускає ключ у жоден командний рядок. Там, де клієнт може прочитати його зі змінної середовища (`BOMBVAULT_MCP_KEY`), маскованого запиту чи власного файла, конфігурація лише називає його. Там, де в клієнта такого способу немає, ключ лежить у його файлі конфігурації чи налаштуваннях, і налаштування про це каже. ### Claude Code {#claude-code}

Claude Code звертається до BombVault через `mcp-remote`, якому на цьому комп'ютері потрібен Node.js. Спершу збережіть ключ в окремому текстовому файлі одним рядком:

```text
X-API-Key: <your key>
```

Потім один раз виконайте в терміналі команду з картки, підставивши шлях до цього файла. За сертифікатом, якому ваш комп'ютер довіряє, вона виглядає так:

```bash
claude mcp add bombvault --scope user -- npx -y mcp-remote@latest https://bombvault.example.com/mcp --header-file "<path of the file with your key>"
```

З власним сертифікатом BombVault (див. [TLS і сертифікати](#tls)) команда ще й вказує Node.js завантажений сертифікат:

```bash
claude mcp add bombvault --scope user -e "NODE_EXTRA_CA_CERTS=<path of the downloaded bombvault-cert.pem>" -- npx -y mcp-remote@latest https://192.168.1.10:3443/mcp --header-file "<path of the file with your key>"
```

Перевірте підключення командою `/mcp` у Claude Code. `--scope user` робить BombVault доступним у всіх ваших проєктах. Claude Code зберігає лише шлях до файла ключа, тож ключ не видно ні в команді та історії вашої оболонки, ні в списку процесів. Тримайте файл там, де його можете прочитати лише ви, і поза будь-якою текою, яку ви комітите. `@latest` змушує `npx` узяти актуальний `mcp-remote`. Старіший, встановлений глобально, використовувався б замість нього, а він не знає `--header-file`.

Не пишіть `${BOMBVAULT_MCP_KEY}` в аргументи `mcp-remote` для Claude Code. Claude Code підставляє таке посилання з власного середовища, перш ніж запустити `mcp-remote`, тож ключ опиняється в командному рядку цього процесу, де його можуть прочитати інші програми та користувачі комп'ютера.

Без Node.js і лише за сертифікатом, якому ваш комп'ютер довіряє, Claude Code може підключитися сам. Покладіть `.mcp.json` у теку проєкту:

```json
{
  "mcpServers": {
    "bombvault": {
      "type": "http",
      "url": "https://bombvault.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${BOMBVAULT_MCP_KEY}"
      }
    }
  }
}
```

Задайте `BOMBVAULT_MCP_KEY` там, де запускається Claude Code, наприклад у `"env"` в `~/.claude/settings.json` або в профілі оболонки, відредагованому в текстовому редакторі, а не набраному в командному рядку. Тут посилання безпечне, бо Claude Code не запускає другого процесу, який би його ніс. Власний сертифікат BombVault так не працює: власне підключення Claude Code відхиляє його навіть із заданим `NODE_EXTRA_CA_CERTS`. Ніколи не комітьте `.mcp.json` із записаним у нього ключем.

### Claude Desktop {#claude-desktop}

Claude Desktop звертається до BombVault через `mcp-remote`, якому на цьому комп'ютері потрібен Node.js. Спершу збережіть ключ в окремому текстовому файлі одним рядком, як описано для [Claude Code](#claude-code). Відкрийте файл конфігурації через **Settings, Developer, Edit Config** в Claude Desktop. У Windows він лежить у `%APPDATA%\Claude\claude_desktop_config.json`, у macOS у `~/Library/Application Support/Claude/claude_desktop_config.json`. Додайте запис із картки всередину `"mcpServers"`, поруч з уже наявними серверами, і перезапустіть Claude Desktop:

```json
{
  "mcpServers": {
    "bombvault": {
      "command": "npx",
      "args": ["-y", "mcp-remote@latest", "https://192.168.1.10:3443/mcp", "--header-file", "<path of the file with your key>"],
      "env": {
        "NODE_EXTRA_CA_CERTS": "<path of the downloaded bombvault-cert.pem>"
      }
    }
  }
}
```

- `NODE_EXTRA_CA_CERTS` потрібен лише для власного сертифіката BombVault. За сертифікатом, якому ваш комп'ютер уже довіряє, його не вказуйте.
- `--allow-http` додається лише для звичайної адреси `http://`.
- У Windows пишіть шляхи з прямими слешами, наприклад `C:/Users/sam/bombvault-key.txt`, бо одинарний зворотний слеш у JSON недопустимий. Шлях до файла ключа не повинен містити пробілів: Claude Desktop у Windows передає шлях з пробілом у `npx` двома частинами.
- Конфігурація називає лише файл ключа, тож ключ не видно ні в ній, ні в списку процесів. Тримайте файл там, де його можете прочитати лише ви.

### Хмарні клієнти {#cloud-clients}

ChatGPT, Claude на claude.ai, Grok і Le Chat звертаються до BombVault із серверів своїх постачальників, тому BombVault має бути доступний з інтернету з публічно довіреним сертифікатом, наприклад за зворотним проксі. Le Chat самопідписані відхиляє. Вхід на проксі може захищати вебінтерфейс, але `/mcp` має проходити до BombVault без нього: ці сервіси не вміють входити в проксі, а BombVault перевіряє їхній ключ чи токен сам. Grok і Le Chat надсилають фіксований ключ, і їхні кнопки налаштовують їх, як решту. ChatGPT і Claude на claude.ai у більшості організацій підключаються лише через вхід з OAuth, описаний далі.

### Вхід через OAuth {#oauth}

Для клієнта, який не приймає ключ, BombVault сам є сервером авторизації OAuth. Клієнт реєструється сам, надсилає вас на сторінку BombVault, і там ви входите з паролем для входу (і другим фактором, якщо ви його налаштували) та дозволяєте йому доступ. Потім клієнт отримує токен, який працює лише для кінцевої точки MCP цього BombVault, і сам його оновлює.

1. Задайте пароль для входу в **Налаштування, Безпека**. Без нього BombVault узагалі не пропонує вхід, бо питати згоду було б нікого.
2. Зробіть BombVault доступним з інтернету через https із сертифікатом, якому довіряють браузери, зазвичай через зворотний проксі. Клієнт звертається до `/mcp`, `/oauth/` та `/.well-known/` зі своїх серверів, тож проксі з власним входом має пропускати ці три шляхи до BombVault. Сторінка згоди `/oauth/authorize` відкривається у вашому браузері й може лишатися за входом на проксі. Назвіть проксі й у `TRUSTED_PROXY` (див. [Конфігурація](configuration.md)). BombVault обмежує реєстрації клієнтів з однієї адреси, і без цього кожен клієнт здається прийшлим з проксі.
3. У картці MCP увімкніть **Вхід через OAuth** і введіть **Публічна адреса**: адресу https без шляху, наприклад `https://backup.example.com`. Кожен токен прив'язаний до цієї адреси, тож після її зміни кожному клієнту потрібно увійти заново.
4. Виберіть ChatGPT або Claude в **Вибрати клієнт**. Вікно показує **URL конектора**, тобто публічну адресу плюс `/mcp`, і де його вводити в цьому клієнті. У ChatGPT увімкніть Developer mode в **Settings, Apps & Connectors, Advanced settings**, виберіть **Create**, вставте URL конектора як URL сервера MCP і виберіть OAuth як автентифікацію. На claude.ai відкрийте **Settings, Connectors, Add custom connector**, вставте URL конектора, залиште ID клієнта й секрет OAuth порожніми та виберіть **Connect**.
5. Клієнт відкриває сторінку згоди. Вона показує, хто просить, куди вас поверне ваша відповідь, і перемикач **Дозволити запуск копіювання**, який спершу вимкнений. Виберіть **Дозволити** або **Відмовити**.

Кожен клієнт, який увійшов, отримує в тому самому списку свій рядок зі своїм значком. Його **Подробиці** містять журнал, **Відкликати** та **Дозволити запуск копіювання**, і на нього діють ті самі обмеження, що й на ключ. Відкликання набирає чинності одразу. Коли той самий клієнт входить знову, його новий дозвіл замінює попередній, а дозвіл, яким ніхто не користувався 30 днів, спливає. Одночасно можуть бути увійшовшими до 10 клієнтів, понад 10 ключів.

Сторінка згоди приймає запит лише від зареєстрованого клієнта, який точно називає одну зі своїх зареєстрованих адрес повернення: https або адресу loopback на будь-якому порту для клієнта на вашому власному комп'ютері. Приймається лише потік коду авторизації з PKCE (S256), а ваша відповідь прив'язана до вашого сеансу, тож жоден інший сайт не може надіслати її за вас. Токени доступу живуть годину. Токен оновлення замінюється під час кожного використання, а той, що з'являється знову після цього, відкликає дозвіл, бо копія є в когось іншого. Клієнт, який повторює своє останнє оновлення протягом 30 секунд, бо відповідь до нього не дійшла, отримує нові токени. BombVault не завантажує документи метаданих клієнтів з інтернету, тому клієнти реєструються через динамічну реєстрацію клієнтів.

### Інші клієнти {#other-clients}

Підходить будь-який клієнт, який розуміє Streamable HTTP:

- URL: адреса вебінтерфейсу плюс `/mcp`, наприклад `https://192.168.1.10:3443/mcp`.
- Ключ у `Authorization: Bearer <key>` або в `X-API-Key: <key>`. Якщо надіслано обидва, вони мають нести той самий ключ.
- `POST` з `Content-Type: application/json` та `Accept: application/json, text/event-stream`.
- Одне повідомлення JSON-RPC на запит. Пакети відхиляються.
- Версії протоколу 2026-07-28, 2025-11-25, 2025-06-18 і 2025-03-26.

## TLS і сертифікати {#tls}

BombVault віддає HTTPS із сертифікатом, який зробив сам, і спочатку цей сертифікат називає лише `localhost`, `127.0.0.1` та `::1`. Claude Code і `mcp-remote` відхиляють його на адресі в локальній мережі. Способи це обійти в порядку, який підходить більшості установок Unraid:

1. **Додайте адресу в картці MCP.** Коли картку відкрито через HTTPS за адресою, якої в сертифікаті немає, вона про це каже й пропонує **Додати цю адресу до сертифіката**. BombVault випускає сертифікат заново з доданою адресою (браузер попередить ще раз, як першого разу). Потім натисніть **Завантажити сертифікат**. Фрагменти задають `NODE_EXTRA_CA_CERTS` завантаженим файлом, тож клієнт довіряє саме цьому сертифікату. Це також означає, що кожен клієнт, налаштований за раннішим завантаженням, перестає підключатися, щойно сертифікат випущено заново, на цьому комп'ютері й на будь-якому іншому, поки не отримає новий файл.
2. **Зворотний проксі з довіреним сертифікатом** (Nginx Proxy Manager, SWAG, Caddy, Traefik). Клієнт тоді бачить сертифікат проксі й йому нічого додаткового не потрібно, а картка не попереджає про власний сертифікат BombVault.
3. **Tailscale.** `tailscale serve` перед контейнером або інтеграція Tailscale в Unraid дає ім'я `ts.net` із довіреним сертифікатом.
4. **`HTTP_ONLY=true`**, лише за проксі, який завершує TLS, або в мережі, якій ви повністю довіряєте. Він перемикає весь вебінтерфейс на звичайний HTTP, потребує зміни налаштувань контейнера й надсилає ключ незашифрованим.

Ніколи не задавайте `NODE_TLS_REJECT_UNAUTHORIZED=0`. Це вимикає перевірку сертифікатів для всього, з чим розмовляє цей процес Node.js.

Зворотний проксі має пропускати заголовок `Authorization` (або `X-API-Key`), що проксі роблять, якщо їм не сказано іншого, і не повинен буферизувати чи переписувати `/mcp`. Блок location для Nginx або Nginx Proxy Manager, який заодно перевіряє сертифікат BombVault:

```nginx
location /mcp {
    proxy_pass https://192.168.1.10:3443;
    proxy_ssl_verify on;
    proxy_ssl_trusted_certificate /data/bombvault-cert.pem;
    proxy_ssl_name localhost;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_set_header Host $host;
}
```

За проксі кожен запит несе адресу проксі. П'ять хибних ключів від одного неправильно налаштованого клієнта тоді на хвилину блокують усіх клієнтів MCP за цим проксі. Назвіть проксі в `TRUSTED_PROXY` (див. [Конфігурація](configuration.md)), щоб рахувати за клієнтами.

## Модель безпеки {#security}

- Без активного ключа та за вимкненого входу через OAuth `/mcp` відповідає `404`.
- Вхід через OAuth пропонується, лише поки задано пароль для входу. Токени, коди й секрети клієнтів зберігаються лише як відбитки, а токен працює лише для адреси, для якої був виданий.
- Клієнт може зареєструватися щонайбільше 10 разів на годину з однієї адреси, а BombVault зберігає щонайбільше 100 зареєстрованих клієнтів, у які ніхто не входив, кожного по одному дню. Хибні коди й токени оновлення враховуються в тому самому блокуванні, що й хибні ключі.
- Дозволи поводяться як ключі, коли відновлюється копія конфігурації або змінюється `APP_KEY`: після відновлення кожному клієнту потрібно увійти заново.
- Жодних виключених адрес. Запитам з `localhost`, хоста Unraid, зворотного проксі чи `tailscale serve` потрібен ключ, як і всім іншим, зокрема й коли у вебінтерфейсу немає пароля для входу.
- Ключі зберігаються лише як відбитки, показуються один раз, і їх можна перейменовувати, замінювати та відкликати. До 10 активних ключів, у кожного свій перемикач **Дозволити запуск копіювання**.
- Кожне створення, заміна, зміна дозволу й відкликання надсилає сповіщення вашими каналами сповіщень з адресою, з якої воно прийшло, якщо тільки сповіщення не вимкнено.
- 5 хибних ключів на хвилину з однієї адреси, потім `429`. 120 запитів на хвилину та 12 запущених копій на годину на ключ, плюс перерва й захист зберігання вище.
- Запити зі сторінки браузера на іншому джерелі (origin) відхиляються.
- Ключі не можна створювати з імені хоста, схожого на публічне, поки не задано пароль для входу.
- Кожна копія, яку запускає помічник, і викликані нею очищення та зовнішні запуски позначаються «через MCP» з іменем ключа в журналі активності, в панелі помилок і в сповіщенні про копію.
- Кожен виклик інструмента записується в журнал контейнера з ідентифікатором ключа та його останніми чотирма символами (ніколи з іменем) і рахується в `/metrics` (`bombvault_mcp_requests_total`, `bombvault_mcp_tool_calls_total`, `bombvault_mcp_active_keys`).
- Відновлення копії конфігурації відкликає всі ключі, бо відновлена база даних могла б містити ключі, які ви відкликали після її збереження. Після цього створіть нові ключі.
- Ключ перестає працювати, коли змінюється `APP_KEY` (перевстановлення або відновлення в інший контейнер). Картка це виявляє й позначає ключ, а **Замінити ключ** знову дає йому робочий секрет.
- Ставтеся до ключа як до пароля. Клієнт, який не може прочитати ключ зі змінної середовища, запиту чи файла ключа, зберігає його відкритим текстом у своїй конфігурації чи налаштуваннях, і його налаштування про це каже. Віддавайте перевагу ключу лише для читання на комп'ютері, якому ви довіряєте менше.

## Що залишає сервер {#privacy}

Усе, що читає помічник, іде до постачальника ШІ за ним: назви записів, розклади, історія запусків із повідомленнями про помилки, ідентифікатори й час точок відновлення, назви рушіїв баз даних і розміри дампів, поточна активність, цифри сховища, охоплення й стан. BombVault видаляє шляхи хоста, розташування репозиторіїв, імена хостів, облікові дані, команди хуків і ключі, перш ніж щось піде.

## Усунення несправностей {#troubleshooting}

| Що ви бачите | Що це означає |
|---|---|
| `404` | Немає активного ключа, а вхід через OAuth вимкнено, або хибний шлях на кшталт `/api/mcp`. Кінцева точка — `/mcp`. |
| `401` | Ключ відсутній, набраний з помилкою, відкликаний або замінений. Проксі може відкидати заголовок `Authorization` (спробуйте `X-API-Key`). Якщо картка позначає ключ як більше не дійсний, `APP_KEY` змінився: замініть ключ. |
| `403` | Запит прийшов зі сторінки браузера на іншому джерелі (origin). Використовуйте клієнт для робочого столу чи командного рядка. |
| `405` на GET | Це нормально. Кінцева точка приймає лише `POST`. |
| `400` "Accept must contain both 'application/json' and 'text/event-stream'" | Клієнт надто старий для Streamable HTTP. Оновіть його. |
| `400` "batch requests are not accepted" | Клієнт надсилає пакети JSON-RPC. Надсилайте по одному повідомленню на запит. |
| `429` | Забагато хибних ключів із цієї адреси або понад 120 запитів на хвилину з одним ключем. Зачекайте хвилину й перевірте, чи не застряг помічник у циклі. |
| Помилки «certificate», «self-signed» або «unable to verify» | Клієнт не довіряє сертифікату BombVault. Див. [TLS і сертифікати](#tls). |
| `busy` | Інша копія або завдання обслуговування тримає цей розділ. Повторіть, коли воно закінчиться. |
| `cooldown` | Цей запис, розділ чи «Створити копію всього» було запущено поза вебінтерфейсом менш ніж 15 хвилин тому. |
| `retention_guard` | Ще одна копія через MCP залишила б у вікні «зберігати останні N» лише точки відновлення, зроблені через MCP, або запис уже отримав 4 копії через MCP за останні 24 години, зокрема невдалі та скасовані. У першому випадку наступна планова копія звільняє місце, у другому запис знову вільний через 24 години після найстарішої з цих копій. У будь-якому разі ви можете запустити її у вебінтерфейсі. |
| `rate_limited` | Ключ витратив свої 12 запусків на цю годину. |
| `not_permitted` під час запуску | Ключ лише для читання. Увімкніть **Дозволити запуск копіювання** в картці. Повторне підключення не потрібне. Під час скасування це означає, що запуск розпочав не цей ключ. |
| `domain_off` | Цей розділ вимкнено в **Налаштування, Загальні**. |
| `not_found` | Запис не захищено BombVault. Спершу додайте його у вебінтерфейсі. MCP ніколи не створює конфігурацію. |
| Клієнт не знаходить сервер авторизації | Вхід через OAuth вимкнено, пароль для входу не задано або проксі не пропускає `/.well-known/` до BombVault. |
| Сторінка згоди повідомляє, що адресу повернення не зареєстровано | Клієнт надіслав адресу повернення, яку не реєстрував. Видаліть конектор у клієнті й додайте його знову. |
| Клієнт, що увійшов, отримує `401` | Його дозвіл відкликано, він спливув після 30 днів без використання або змінилася публічна адреса. Клієнт входить заново. |

Не задавайте змінну середовища `MCPGODEBUG` на контейнері. Вона змінює поведінку бібліотеки MCP, а некоректне значення зупиняє BombVault під час запуску ще до запису єдиного рядка журналу.
