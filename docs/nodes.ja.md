# ノード

ノードは Web 画面のない BombVault で、たとえば VPS や、友人宅の小さなサーバーで動かします。自分のサーバー上のコンテナとフォルダーをバックアップし、いつバックアップするか、バックアップをどこへ送るかは、ノードを追加した側の BombVault が指示します。このページでは、その BombVault を**ホームインスタンス**と呼びます。ノードの管理は、自分の項目と並べてホームインスタンスの Web 画面で行います。

![インスタンスのページにあるノード vps-falkenstein のカード。接続済み、バージョン、受信サーバーへのバックアップ、セクションごとのバックアップの時刻、そして送り先を変更、置き換え、解放。](assets/screenshots/nodes/card-dark.png#only-dark)
![インスタンスのページにあるノード vps-falkenstein のカード。接続済み、バージョン、受信サーバーへのバックアップ、セクションごとのバックアップの時刻、そして送り先を変更、置き換え、解放。](assets/screenshots/nodes/card-light.png#only-light)

## しくみ {#how-it-works}

- **ノードの鍵はホームインスタンスが持ちます。** ノードを追加すると、ホームインスタンスがその `APP_KEY` を作り、封じたコピーを保管して、ノードの compose ファイルに入れて一度だけ渡します。ホームインスタンスはそのコピーでノードに接続し、そのバックアップを開きます。
- **ノードでポートを開ける必要はありません。** ホームインスタンスとノードは、ペアリンググループとは別の専用のプライベートな経路で、リレー越しに話します。呼び出しはすべてホームインスタンスが始めて署名し、ノードがホームインスタンスに送るのは最初のあいさつだけです。開いたポートが必要な送り先は、[ノードに保管](#keep-on-node)だけです。
- **バックアップがリレーを通ることはありません。** ノードは、選んだ場所へバックアップを直接送ります。送り先は、ホームインスタンスの受信サーバー、ホームインスタンスの保存先のどれか、またはノード自身の rest-server です。
- **ノードは自分では何も計画しません。** スケジュールを動かさず、通知を送らず、グループにも要塞にも加わりません。ホームインスタンスがバックアップを開始し、経過を見守り、アラートを送ります。
- **ノードがバックアップするのはコンテナとフォルダーセットです。** VM、フラッシュドライブ、ZFS データセット、セルフバックアップは、フルインストールだけが扱います。

経路には、ホームインスタンスのグループに専用のリレーがあればそれを使い、なければプロジェクトのリレーを使います。ホームインスタンスがリレーなしでペアリングしている場合も同じです。

## 始める前に {#before-you-start}

- **ホームインスタンスのログインパスワード。** ノードの追加、compose ファイルの再表示、ノードの項目を開くことには、パスワードでのサインインが必要です。[ログイン](configuration.md#login)を参照してください。
- **ノードのサーバーに Docker と Compose。**
- **バックアップの置き場所。** [バックアップの送り先](#placement)にある 3 つのどれかです。いちばん安全なのは受信サーバーです。ノードはそこで何も削除できないからです。

## ノードを追加する {#add}

1. ホームインスタンスで**インスタンス**を開き、右下の**ノードを追加**を選びます。
2. **名前。** ここでのノードの表示名を入力します。サーバーの名前などがおすすめです。**次へ**を選びます。

    ![ノードを追加ウィンドウの最初の手順。名前 vps-helsinki が入力されている。](assets/screenshots/nodes/add-name-dark.png#only-dark)
    ![ノードを追加ウィンドウの最初の手順。名前 vps-helsinki が入力されている。](assets/screenshots/nodes/add-name-light.png#only-light)

3. **バックアップ。** バックアップの送り先を選び、その場所が求める内容を入力します。**毎日のバックアップ時刻**は、両方のセクションが始まる時刻です。ホームインスタンスは自分のコンテナのバックアップの 30 分後を提案するので、両方が同時に同じディスクを使うことはありません。セクションごとの個別のプランは、あとでカードで設定できます。**次へ**を選びます。

    ![2 番目の手順。受信サーバーを選び、ノード用のアドレスに https のアドレスを入れ、毎日のバックアップ時刻は 03:00。](assets/screenshots/nodes/add-placement-dark.png#only-dark)
    ![2 番目の手順。受信サーバーを選び、ノード用のアドレスに https のアドレスを入れ、毎日のバックアップ時刻は 03:00。](assets/screenshots/nodes/add-placement-light.png#only-light)

4. **起動。** ウィンドウに、`MODE`、`APP_KEY`、`NODE_HOME`、`NODE_NAME` が入ったノードの compose ファイルが表示されます。これをコピーし、`APP_KEY` は安全な場所に保管してください。ノードのサーバーで次を実行します。

    ```sh
    mkdir -p /opt/bombvault-node && cd /opt/bombvault-node
    nano docker-compose.yml   # paste the file from the window
    docker compose up -d
    ```

    起動する前に、Host Data ボリュームをバックアップしたいデータに向け、`HOST_SOURCE_ROOT` に同じパスを設定してください。下の例のとおりです。

5. ウィンドウはノードを待ちます。ノードが応答すると、ホームインスタンスがバックアップの送り先を伝えてそこに届くかを確かめ、ウィンドウに **vps-helsinki はオンラインで、このインスタンスからの指示を受けています。** と表示されます。

    ![最後の手順。compose ファイルと、オンラインになったノード。バックアップの送り先は受信サーバー。](assets/screenshots/nodes/add-start-dark.png#only-dark)
    ![最後の手順。compose ファイルと、オンラインになったノード。バックアップの送り先は受信サーバー。](assets/screenshots/nodes/add-start-light.png#only-light)

ノードが応答する前にウィンドウを閉じてもかまいません。その場合、カードには**ノードを待っています**と表示され、ノードが現れた時点でホームインスタンスが送り先を伝えます。

### 例：受信サーバーにバックアップする VPS {#example-vps}

ホームインスタンスは `tower` という Unraid マシンで、[受信サーバー](offsite-recovery.md#receiving-server)を動かしています。リバースプロキシがそれを `https://backup.tower.example.org` として公開しています。VPS `vps-helsinki` では Nextcloud と Caddy が動いていて、データは `/srv/appdata` の下にあります。

1. `tower` で**インスタンス**、**ノードを追加**と進み、名前に `vps-helsinki` を入れて**次へ**。
2. **このインスタンスの受信サーバー**を選び、**ノード用のアドレス**に `https://backup.tower.example.org` を入力します。ホームインスタンスのコンテナは 02:30 にバックアップするので、ウィンドウは 03:00 を提案します。そのままにして**次へ**を選びます。
3. VPS で、ウィンドウのファイルを、ボリュームと `HOST_SOURCE_ROOT` を `/srv/appdata` に合わせて変えてから保存します。

    ```yaml
    services:
      bombvault-node:
        image: junkerderprovinz/bombvault:latest
        restart: unless-stopped
        hostname: bombvault-node
        container_name: bombvault-node
        volumes:
          - ./config:/config
          - /var/run/docker.sock:/var/run/docker.sock
          - /srv/appdata:/host/user
        environment:
          MODE: node
          APP_KEY: "<filled in by home>"
          NODE_HOME: "<filled in by home>"
          NODE_NAME: "vps-helsinki"
          PLATFORM: generic
          HOST_SOURCE_ROOT: /srv/appdata
    ```

4. `docker compose up -d` を実行します。数秒後、`tower` のウィンドウに、ノードがオンラインになったことと **バックアップは https://backup.tower.example.org に送られます。** が表示されます。
5. 03:00 にホームインスタンスがノードのバックアップを開始します。翌朝には、概要の**ノード**カードに `vps-helsinki` の最後のバックアップが表示され、**バックアップ**にはそのコンテナが専用のセクションに一覧されます。

普通の Docker ホストでコンテナのデータがどう見つかるかは、[バックアップ元の検出](configuration.md#backup-source-detection)で説明しています。

## バックアップの送り先 {#placement}

各ノードには、両方のセクションに共通の送り先が 1 つあります。ノードがオンラインなら、カードの**送り先を変更**で変えられます。新しい場所には新しいリポジトリができ、前の場所のバックアップはそのまま残ります。

### このインスタンスの受信サーバー {#to-receiver}

ノードは、ホームインスタンスの受信サーバーに append-only モードで書き込みます。バックアップを追加できますが、削除はできません。ノードには、ノードの名前がついた専用のログインと、そこにある専用フォルダー内にセクションごとのリポジトリが 1 つずつ用意されます。ノードには整理ができないので、ホームインスタンスが各リポジトリに自分の鍵を追加し、整理も自分で行います。

ホームインスタンスでまだ受信サーバーが動いていない場合、このステップがそれを伝え、**受信サーバーを設定**を表示します。そのためにグループは必要ありません。共有上のフォルダーとポートを選んで**設定して続行**を選び、ウィンドウにサーバーが表示されたら**完了**を選ぶと、ステップはそのサーバーで続きます。詳しくは[受信サーバー](offsite-recovery.md#receiving-server)を参照してください。

ノードは**ノード用のアドレス**で受信サーバーに接続します。これは 2 番目の手順か、**受信サーバー**のウィンドウで設定します。ノードはたいていインターネット越しに送るので、アドレスは次のどちらかにしてください。

- `https://`。たとえばリバースプロキシ、Pangolin、トンネルの後ろです。サーバーが公的な認証局のものではなく独自の証明書を示す場合は、それを PEM 形式で**証明書**に貼り付けてください。
- プライベート IP アドレスでの `http://`。たとえば WireGuard 接続の `10.0.0.5` や、Tailscale の `100.101.102.103` です。

公開アドレスへの普通の `http://` は拒否されます。ノードがバックアップを暗号化せずにインターネット越しに送ることになるからです。アドレスを変えると、ホームインスタンスは受信サーバーを使うすべてのノードに伝えます。つながっていないノードには、戻ったときに伝わります。

### 保存先 {#to-location}

ノードは、自分で届くホームインスタンスの保存先の 1 つに書き込みます。`https://` またはプライベートアドレスで届く S3 サービスか REST サーバーです。リポジトリは、そこの `bombvault-node-<node id>-containers` と `bombvault-node-<node id>-files` に置かれます。

ノードは、ノード用に作った[保存済みの認証情報](offsite-recovery.md#sign-ins)でサインインします。これは、ホームインスタンスがその保存先に書き込むときの認証情報とは別のものにしてください。ウィンドウに認証情報がないと表示されたら、先に追加します。受信サーバーとは違い、この認証情報があると、ノードはたいてい保存先にあるものを削除できます。ウィンドウにもそう表示されます。

### ノードに保管 {#keep-on-node}

ノードは、append-only モードの専用の rest-server の奥にバックアップを自分で保管し、ホームインスタンスが各セクションのコピーを自分のストレージに取得します。ホームインスタンスが置き場所を用意できないノードに向いています。開いたポートが必要な、ただ 1 つの送り先です。

![2 番目の手順でノードに保管を選んだところ。アドレス https://203.0.113.7:8443 と、開いたポートについての注意。](assets/screenshots/nodes/add-keep-dark.png#only-dark)
![2 番目の手順でノードに保管を選んだところ。アドレス https://203.0.113.7:8443 と、開いたポートについての注意。](assets/screenshots/nodes/add-keep-light.png#only-light)

1. **ノードのアドレス**に、ホームインスタンスがノードに接続する先を入力します。ノードの公開アドレスと空いているポートで、たとえば `https://203.0.113.7:8443` です。後ろにフォルダーは付けません。`http://` は、上と同じくプライベートアドレスのときだけ使ってください。
2. ノードは、そのポートでコンテナ `bombvault-node-rest-server` を起動し、リポジトリを Host Data の下のフォルダー `bombvault-node` に置きます。`https://` の場合は、そのアドレス用の証明書を作り、ホームインスタンスがそれを固定します。
3. ホームインスタンスが届くよう、ノードのファイアウォールでポートを許可してください。ノード上の別のコンテナが使っているポートは、そのコンテナの名前とともに拒否されます。

ホームインスタンスは、ノードがあるセクションのバックアップを終えるとすぐにそのセクションを取得し、予備として毎時 15 分にも取得します。**取得**がオフでも同じです。ホームインスタンスが取得したものは、ほかの[取得したコピー](offsite-recovery.md#receiver)と同じくホームインスタンスに残り、ノードがなくなっても消えません。ノードの rest-server は削除を受け付けないので、ノードはホームインスタンスに頼まれたときに自分のリポジトリを整理します。また、ノードのフォルダーセットは `bombvault-node` フォルダーを除外するので、自分のバックアップをバックアップすることはありません。

### ホームインスタンスと一緒のオフサイトコピー {#copy-onward}

**バックアップ**ステップか**送り先を変更**で**このインスタンスのバックアップと一緒にオフサイトへコピー**をオンにすると、ホームインスタンスは、自分のコンテナとフォルダーのコピー先と同じ保存先へ、同じプランでノードのコンテナとフォルダーセットをコピーします。そのためにノード専用のフォルダーやコピーのプランは要りません。

- コピーは、ホームインスタンスのコピーと同じリポジトリの中に、ノードのホスト名で置かれます。その保存先に対するホームインスタンスのルールはこれに手を付けず、ホームインスタンスはノードのルールでこれを残します。[ノードのバックアップを整理する](#schedule)ときと同じルールです。
- ホームインスタンスは、自分の鍵でノードのリポジトリを読み、その保存先用の自分の認証情報で書きます。ノードに新しい認証情報は渡らず、受信サーバーは append-only のままです。バックアップを自分で保管するノードでは、ホームインスタンスは取得したものをコピーします。
- ノードのリポジトリには独自の chunker 設定があるので、そのコピーが保存先でホームインスタンスのコピーと共有するデータはわずかです。
- append-only の保存先では、ホームインスタンス自身のコピーと同じく、何も整理されません。[共有リポジトリ](offsite-recovery.md#shared-repository)にはノードのコピーは入りません。持ち主がグループのサーバーのルールで整理するからです。
- カードには**コピーの送り先**と保存先が表示されます。コピーが失敗すると、カードのエラーとして数えられ、アラートが送られます。[ノードを見守る](#watch)を参照してください。
- オフにすると、ホームインスタンスはそれ以上コピーしません。すでにあるコピーは残り、ホームインスタンスのルールは引き続きそれに手を付けません。

#### 例：VPS をホームインスタンスのコンテナと一緒に B2 へコピー {#example-copy-onward}

`tower` は**保持期間**でコンテナごとに 7 つのバックアップを残し、毎晩 04:00 に自分のコンテナを B2 バケットへコピーします。バケットは最新の 14 を残します。`vps-helsinki` は tower の受信サーバーにバックアップし、そこではバックアップが同じ 7 で整理されます。スイッチをオンにすると、tower は 04:00 に VPS のコンテナもバケットへコピーします。するとバケットには、tower のバックアップがコンテナごとに 14、VPS のバックアップがコンテナごとに 7 あります。

## ノードがバックアップする時刻 {#schedule}

ノードのスケジュールはすべてホームインスタンスが持っています。カードには、**コンテナ** *毎日 2:00*、**フォルダー** *毎週（日）4:00* のように、セクションごとのプランが表示されます。クリックすると[スケジュール](schedules.md#plans)と同じエディターが開き、変更はすぐに保存されます。

![カードから開いたノードのコンテナのプラン。オフ、毎日、毎週、N日ごと、Cron がある。](assets/screenshots/nodes/schedule-dark.png#only-dark)
![カードから開いたノードのコンテナのプラン。オフ、毎日、毎週、N日ごと、Cron がある。](assets/screenshots/nodes/schedule-light.png#only-light)

- **つながっていなかったノード**は、戻りしだい、逃したバックアップを開始します。ホームインスタンスは 5 分ごとに確認します。
- **忙しいノード**には、5 分後にもう一度頼みます。
- **ホームインスタンスがノードの古いバックアップを整理している間**は、それが終わるまでノードは何も開始しません。受信サーバーとノード自身では、この時間帯は毎週日曜日の 03:00 に始まり、最長 6 時間続きます。保存先では、その保存先に対するホームインスタンスのオフサイトコピーのプランに従います。ホームインスタンスは、**保持期間**にあるそのセクションの自分のルールでバックアップを残します。保存先に独自のルールがあれば、そちらに従います。
- **ノードの実行一覧**では、ホームインスタンスが開始したバックアップと復元が、ホームインスタンスによる開始として表示されます。

## ノードを見守る {#watch}

概要の**ノード**カードには、すべてのノードが、状態、最後のバックアップ、エラー、未処理の異常とともに一覧されます。このカードはノードを追加すると表示されます。

![概要のノードカードに 3 つのノード。1 つは接続済み、1 つは非アクティブでエラーが 2 件、1 つはまだノードを待っている。](assets/screenshots/nodes/overview-card-dark.png#only-dark)
![概要のノードカードに 3 つのノード。1 つは接続済み、1 つは非アクティブでエラーが 2 件、1 つはまだノードを待っている。](assets/screenshots/nodes/overview-card-light.png#only-light)

ホームインスタンスは、ひとつの出来事につきアラートを 1 回だけ、[通知チャネル](notifications.md)で送ります。次のアラートは、その出来事が終わってからです。

- **バックアップの失敗。** たとえば *BombVault: vps-helsinki: backup failed* で、項目と理由が付きます。その項目のあとのバックアップが成功すると、出来事は終わります。
- **ノードに届かない。** たとえば *BombVault: vps-helsinki is out of reach*。ホームインスタンスは、ノードのリポジトリのデッドマンスイッチのうち最も短い時間だけ待ちます。変更していなければ 26 時間で、ノードにまだ送り先がない間は 6 時間です。
- **オフサイトコピーの失敗。** たとえば *BombVault: vps-helsinki: off-site copy failed*。ホームインスタンスがノードのバックアップを自分の保存先のどれかにコピーできなかったときです。次のコピーが成功すると、出来事は終わります。

ホームインスタンスのレシーバーの見張りは、ノードの各リポジトリも、デッドマンスイッチと毎日 04:00 の `restic check` で見守ります。[レシーバーと取得側](offsite-recovery.md#receiver)を参照してください。

## ノードの項目 {#entries}

**バックアップ**のコンテナとフォルダーの一覧には、自分の項目の下に、ノードごとのセクションがあります。ノード自身のコンテナは含まれません。項目のメニューの**今すぐバックアップ**はノードでそのバックアップを開始し、**開く**はその項目のページを開きます。

フォルダーの一覧にあるノードのセクションでは、**フォルダーセットを追加**でノードにフォルダーセットを追加し、セットのメニューの**編集**でそれを変更します。どちらも自分のセットと同じウィンドウを開きます。その中のフォルダー選択はノードのフォルダーを参照しますが、そこに新しいフォルダーは作りません。

![コンテナの一覧にあるノード vps-falkenstein のセクション。nextcloud、nextcloud-db、caddy、uptime-kuma。](assets/screenshots/nodes/backups-section-dark.png#only-dark)

ノードの項目のページには、**vps-falkenstein 上**のようにノードの名前が表示され、バックアップが一覧されます。そのどれかで**復元**を選ぶと、項目がノード上で復元され、今ある内容は置き換えられます。ホームインスタンスの場合と同じく、コンテナはそのあいだ停止されます。

ホームインスタンスを通じて届くのは、ノード自身のルートの決まった一覧です。コンテナ、フォルダーセット、実行、異常と、それらのバックアップと復元です。ノードの設定、鍵、ストレージには届かず、その一覧に削除を行うものはありません。[API のノード](api.md#nodes)を参照してください。

## 置き換えと解放 {#replace-release}

**置き換え**は、パスワードでサインインしたあとに、ノードの compose ファイルをもう一度表示します。ノードを別のサーバーへ移すときや作り直すときに使います。そのファイルを新しいサーバーで起動し、古いサーバーを停止してください。同じ `APP_KEY` と `NODE_HOME` があれば、バックアップも履歴もそのままに、また同じノードになります。ホームインスタンスは、各ノードのフォルダーセット、作り直すのに必要な情報を含むコンテナ、実行を保管しています。ノードが空の `config` フォルダーで起動すると、ホームインスタンスはノードを改めて引き受け、バックアップの送り先を伝え、次のバックアップの前にそれらをすべて返します。そのため、なくなったコンテナもノードで復元できます。新しいサーバーでは、バックアップを自分で保管するノードは空のリポジトリから始まります。それまでのバックアップは、ホームインスタンスが取得したコピーに残ります。同じ `APP_KEY` を持つ 2 台のサーバーは 1 つのノードとして扱われるので、両方を動かさないでください。

**解放**はノードを手放します。ノードはホームインスタンスからの指示を受けなくなり、何もバックアップしなくなります。バックアップはそのまま残り、ホームインスタンスが取得したコピーもすべて残ります。受信サーバーのログインはなくなり、ホームインスタンスはそのリポジトリを見守るのをやめます。解放したときにつながっていなかったノードは、それを受け取るまでカードが**解放中**のまま残ります。解放したノードは、同じ `APP_KEY` では二度とホームインスタンスを持てません。そのサーバーをまた使うには、新しいノードとして追加し、新しい compose ファイルと空の `config` フォルダーで起動してください。

## セキュリティ {#security}

ホームインスタンスを乗っ取られると、攻撃者はそのノードも操作できます。ノードは自分のサーバーの Docker を握っていて、それはそのサーバーの root と同じです。ホームインスタンスはパスワードで守り、インターネットに出さないでください。ノードを乗っ取られても、攻撃者はペアリンググループも要塞も、ほかのノードも、ほかのリポジトリも手に入れられず、受信サーバーの履歴も削除できません。詳しくは[セキュリティモデルのノード](configuration.md#nodes)にあります。

[リカバリーキット](offsite-recovery.md#recovery-kit)には**ノード**の章があり、各ノードの `APP_KEY`、restic のパスワード、リポジトリが載っています。これでノードを戻したり、普通の restic でそのバックアップを復元したりできます。
