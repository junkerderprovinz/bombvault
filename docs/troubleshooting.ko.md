# 문제 해결

간단한 FAQ입니다. SSH를 통한 VM 백업의 전체 호스트 측 문제 해결 표(권한 거부, 호스트 키 검증, 누락된 템플릿 변수 등)는 GitHub의 [SSH를 통한 VM 백업 가이드](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md)를 참고하세요.

## 무언가가 올바르게 연결되지 않았습니다

개요에 **호스트 통합** 카드를 **사용자 지정**에서 추가하세요. 호스트 통합 확인이 모든 마운트와 CLI(Docker 소켓, libvirt, restic, qemu-img, rclone)를 검사하고 누락된 부분을 보고하며, **지금 확인**으로 다시 실행할 수 있습니다. 버그라고 가정하기 전에 여기서 시작하세요: 누락된 마운트나 도달할 수 없는 호스트는 즉시 나타납니다.

## 웹 UI에 접근할 수 없습니다

BombVault는 기본으로 포트 `3443`에서 HTTPS를 제공하므로(자체 서명된 인증서), `https://<your-unraid-ip>:3443`을 여세요. 자체 서명 인증서 경고를 수락하거나, BombVault를 자체 인증서를 가진 리버스 프록시 뒤에 두세요. `HTTP_ONLY=true`로 실행하면 대신 포트 `3000`에서 일반 HTTP를 제공합니다(TLS 종료 프록시 뒤에서 사용하도록 의도됨).

## APP_KEY를 잃어버렸습니다

`APP_KEY`는 restic 저장소 비밀번호를 파생합니다. 이것도 없고 복구 키트도 없고 그룹에 키 보관본도 없다면 암호화된 백업을 복구할 수 없습니다. 그래서 복구 키트를 내려받을 때까지 개요에 **복구 키트를 저장하세요**가 표시됩니다. [오프사이트 및 복구](offsite-recovery.md#recovery-kit)를 참고하세요. `openssl rand -hex 32`로 키를 생성하고 어떤 백업에 의존하기 전에 서버 밖에 보관하세요.

## 로그인 비밀번호를 잊었습니다

로그인 페이지에서 **비밀번호를 잊으셨나요?**를 선택하세요. BombVault가 12자 코드를 컨테이너 로그에 기록합니다(Unraid에서는 Docker 탭에서 BombVault 아이콘을 누르고 **Logs**를 엽니다). 10분 안에 새 비밀번호와 함께 입력하세요. 재설정하면 2단계 인증이 꺼지고, 모든 패스키가 삭제되며, 모든 API 토큰, MCP 키, OAuth 로그인이 취소되고, 다른 세션은 모두 종료되며, 휴대폰 페어링이 꺼집니다. **설정, 보안**에서 패스키를 다시 추가하고, 거기서 휴대폰 페어링을 다시 켜고, 아직 필요한 토큰과 키를 새로 만드세요. [보안 모델](configuration.md#login)을 참고하세요.

## 백업이 멈추고 키를 더 이상 열 수 없다고 나옵니다

이 서버는 긴급 마법사에서 다른 서버의 백업 키를 인수했고, 그 뒤에 `APP_KEY`가 바뀌었습니다. 인수한 키는 이전 APP_KEY로 봉인되어 있어 BombVault가 열 수 없으며, 잘못된 키로 쓰는 대신 아무것도 백업하지 않습니다. 개요의 **조치 필요**가 이를 알려 줍니다. APP_KEY를 원래대로 되돌리거나, 복원 페이지의 **긴급**에서 복구 키트를 다시 올리세요.

## 휴대폰이 로그인 페이지로 갑니다

페어링된 휴대폰은 **설정, 보안**에서 **그룹의 12개 단어로 휴대폰 페어링 허용**이 켜져 있는 동안에만 그룹을 통해 세션을 받습니다. 비밀번호를 재설정하면 꺼집니다. 서버보다 오래된 앱도 업데이트하기 전에는 세션을 받지 못합니다. 주소로 추가한 서버는 항상 비밀번호를 요구합니다. 인스턴스 페이지에서 제거한 휴대폰은 앱을 다시 열면 꺼진 상태로 돌아옵니다. 들여보내려면 그 세부 정보의 **모니터링**에서 **이 인스턴스 조회**를 켜세요.

## VM 백업이 연결되지 않습니다

VM 백업은 마운트가 아니라 SSH를 통해 libvirt와 통신합니다.

- 호스트에서 SSH가 활성화되어 있고 BombVault의 공개 키가 `/root/.ssh/authorized_keys`에 승인되어 있는지 확인하세요(설정, 연동, 호스트 SSH에 키와 **연결 테스트** 버튼이 표시됨).
- 사용자 지정 `br0.x` 네트워크에서는 `LIBVIRT_HOST`를 Unraid LAN IP로 설정하세요(거기서는 컨테이너가 `host.docker.internal`을 통해 호스트에 도달할 수 없음). **Settings, Docker, Host access to custom networks**을 활성화하세요.
- Unraid의 SSH 포트를 변경했다면 `LIBVIRT_SSH_PORT`를 일치하도록 설정하세요.
- TrueNAS에서는 TrueNAS 자체 libvirt 소켓을 지정한 `LIBVIRT_URI`를 설정하고, 앱에 `SETPCAP` 기능을 주고, **Credentials, Users**에서 키를 root에 추가하세요([TrueNAS SCALE](getting-started.md#truenas) 참고).
- 전체 단계별 진단(도달 가능성 테스트, VLAN 라우팅, `Permission denied (publickey)`, `Host key verification failed`)은 [SSH를 통한 VM 백업 가이드](https://github.com/junkerderprovinz/bombvault/blob/main/docs/vm-backup-ssh-setup.md)에 있습니다.

## 라이브 VM 스냅샷이 실행되지 않았습니다

라이브 스냅샷은 VM에 설치된 qemu 게스트 에이전트와 `/mnt/user`가 아닌 `/mnt/cache`(또는 `/mnt/diskX`)에 있는 디스크가 필요합니다. 꺼진 VM에서는 라이브가 자동으로 정상 종료로 대체됩니다. 정상 종료 백업은 VM을 종료하고, 디스크를 백업한 다음, 재시작하므로 항상 일관됩니다. 게스트가 종료될 때까지 최대 10분을 기다리고 강제로 끄지는 않으므로, 업데이트를 설치하는 중인 Windows 게스트가 중간에 끊기지 않습니다. 그 뒤에도 계속 실행 중인 게스트는 그대로 두고, 그 백업은 이유와 함께 실패합니다.

## 백업이 "repository is already locked"로 실패했습니다

이는 보통 컨테이너가 작업 도중 업데이트되거나 재시작될 때 남겨진 고아 restic 잠금입니다. BombVault는 확실히 고아가 된 잠금을 감지하여 자동으로 강제 해제하고 한 번 재시도합니다. 지속되면 **설정, 검증**의 **백업 확인** 카드를 열고, 해당 섹션의 행에서 **더보기** 아래의 **잠금 해제**를 선택하여 멈춘 잠금을 손으로 제거하세요. 진짜 문제는 숨겨지지 않고 여전히 드러납니다. 재시작 후 BombVault는 그런 잠금이 10분 동안 갱신되지 않을 때까지 기다립니다. 아직 실행 중인 restic은, 예를 들어 같은 저장소를 쓰는 두 번째 BombVault 안에서, 5분마다 잠금을 갱신하기 때문입니다.

## 백업 후 오프사이트 복사가 일어나지 않았습니다

오프사이트 복제는 설계상 최선 노력 방식이므로, 오프사이트 장애가 로컬 백업을 실패시키는 일은 없습니다. 대상이 언제 복사하는지 확인하세요. 그 **복사** 카드에 **백업할 때마다**라고 적혀 있거나 자체 계획이 표시되며, **설정, 일정, 섹션별 오프사이트 복사**에서 섹션에 자체 계획을 줄 수 있습니다. 온디맨드 실행에는 **설정, 대상**의 섹션 **오프사이트 복사** 카드에 있는 **지금 복제**를 사용하고, 개요의 상태 머리글을 지켜보세요. 실행 중에는 **오프사이트 복사 진행 중**이라고 표시됩니다. 실패한 복사는 **조치 필요**에 나타납니다.

## rest-server의 인증서를 신뢰하지 않습니다

restic은 모르는 인증서를 거부하며, 오류 메시지가 인증서를 어디에 두어야 하는지 알려 줍니다. rest-server의 자체 서명 인증서나 그것에 서명한 인증 기관의 인증서를 PEM 파일로 BombVault 데이터 폴더의 `certs` 폴더(컨테이너 안에서는 `/config/certs`, Unraid에서는 `appdata/bombvault/certs`)에 복사하고 다시 테스트하세요. 재시작은 필요 없습니다.

## 백업이 Host Data 밖의 데이터가 백업되지 않았다고 알릴 때 {#data-outside-host-data}

컨테이너가 BombVault가 Host Data를 통해 읽을 수 없는 폴더에 데이터를 두고 있습니다. 백업은 정의와 닿을 수 있는 모든 폴더를 저장하고, 활동 로그의 줄을 주황색으로 표시하며, 빠진 폴더를 알려 줍니다. 흔한 경우는 두 가지입니다. TrueNAS의 `/mnt/.ix-apps` 아래 ixVolume, 그리고 `/var/lib/docker/volumes` 아래의 이름 있는 Docker 볼륨(compose 스택의 데이터베이스 볼륨 등)입니다. 컨테이너 **설정** 탭의 **백업 폴더** 카드는 이런 폴더를 컨테이너 안의 경로와 호스트 경로로 보여 주고 빨간색으로 표시합니다.

익명 Docker 볼륨은 알리지 않습니다. 이미지가 선언했지만 아무도 매핑하지 않은 폴더를 위해 Docker가 스스로 만들고, 16진수 64자리 이름을 붙여 `/var/lib/docker/volumes` 아래에 둡니다. 대개 캐시가 들어 있으므로 백업은 초록색으로 남고, 카드는 익명이라는 메모와 함께 보여 주기만 합니다.

- **그 데이터를 백업하고 싶다면.** 폴더를 Host Data 아래의 호스트 경로, 예를 들어 appdata 공유의 폴더에 매핑하세요. 다음 백업부터 포함됩니다.
- **필요 없다면.** 두 경로 중 하나를 같은 탭의 **제외 패턴** 카드에 한 줄로 추가하세요. 컨테이너 안의 경로(`/cache` 등)나 경고에 나온 호스트 경로(`/var/lib/docker/volumes/jellyfin_cache/_data` 등) 모두 됩니다. 다음 백업부터 경고에서 그 폴더가 빠지고, 입력란 아래 미리 보기가 이유를 알려 줍니다. 상위 폴더의 줄도 똑같이 통하지만, 단순 이름이나 `/`는 통하지 않습니다.

## 백업이 미뤄짐으로 표시됩니다 {#deferred-backups}

컨테이너의 앱이 사용 중이어서 백업이 기다렸다가 저절로 다시 시도됩니다. 활동 로그의 줄에 이유와 다음 시도 시각이 나오고, 컨테이너 **설정** 탭의 **앱이 사용 중일 때** 카드에도 같은 내용과 대기가 끝나는 시각이 나옵니다. 따로 할 일은 없습니다. 바로 백업하려면 앱이 비었을 때 **지금 백업**을 사용하세요.

- **직접 만든 검사.** 앱이 사용 중인 동안 **백업 전 명령**이 코드 75로 끝나게 하세요. 예: `[ "$(cat /tmp/players)" = 0 ] || exit 75`. 0이 아닌 다른 코드는 예전처럼 백업을 실패시키므로, 고장 난 스크립트는 여전히 **조치 필요**에 나타납니다.
- **Plex, Jellyfin, Emby에 한 번도 묻지 않음.** BombVault는 먼저 컨테이너 자신의 주소로 서버에 묻고, 응답이 없으면 컨테이너 안에서 curl이나 wget을 실행합니다. 둘 다 없는 이미지는 그 이미지를 통해 물을 수 없으며, 이때 로그가 그렇게 알려 줍니다. **서버가 응답하지 않으면 백업**이 켜져 있으면 그런 백업은 그대로 실행되고, 꺼져 있으면 기다립니다.
- **Jellyfin이나 Emby가 거부함.** **API 키**를 확인하세요. 키는 서버 대시보드의 API 키 항목에서 만듭니다.
- **Plex가 거부함.** BombVault는 `/config`에 마운트된 폴더의 `Preferences.xml`에서 토큰을 읽습니다. 한 번도 로그인하지 않은 서버에는 토큰이 없고, 토큰 없이 접근을 허용하는 곳에서만 응답합니다.
- **일시 정지된 영화 때문에 백업이 밤새 기다림.** **일시 정지 세션 무시 기준(분)**을 예를 들어 30으로 설정하세요.
- **트래픽 검사가 백업을 끝내 통과시키지 않음.** **사용 중 기준(KiB/s)**을 아무도 쓰지 않을 때 컨테이너가 보내는 양보다 높이세요. BombVault가 시작된 직후에는 컨테이너를 **조용한 시간(분)** 동안 지켜볼 때까지 검사가 기다립니다.
- **백업이 밤에 전혀 실행되지 않음.** 시간대를 설정하면 시도는 그 안에서만 이루어집니다. 시간대 밖에서 기한에 이른 대기도 기한에 끝납니다.

## 큰 백업이 메모리 부족으로 강제 종료되었습니다

**설정, 시스템**의 **성능** 카드에서 **백업당 메모리 제한 (MiB, 0 = 없음)**을 컨테이너가 쓸 수 있는 양보다 충분히 낮게 설정하세요. 제한에 가까워지면 restic이 메모리를 더 자주 비우며, 그만큼 속도가 조금 떨어지므로 백업은 강제 종료되는 대신 느려집니다.

## 복원이 시작되기 전에 중단되었습니다

어떤 것이 중지되거나 제거되기 전에, 복원은 사전 점검 충돌 검사를 실행합니다: 컨테이너의 고정 IP와 게시된 호스트 포트가 비어 있는지 확인합니다. 다른 컨테이너가 이미 하나를 점유하고 있으면, 중간에 끝난 복원을 남기는 대신 명확하고 실행 가능한 메시지와 함께 중단합니다. 충돌하는 포트나 IP를 비운 다음 다시 시도하세요.

예를 들어 TrueNAS 앱이 삭제되어 컨테이너의 네트워크가 없으면, 복원 전 확인이 그 네트워크를 알려 주고 복원은 아무것도 바꾸기 전에 거부됩니다. TrueNAS에서 같은 이름으로 앱을 다시 설치해 네트워크를 다시 만든 다음, 데이터를 복원하세요.

## 일반 내보내기가 파일을 쓰는 대신 실패했습니다

**age 로 내보내기 암호화**가 **설정, 시스템**에서 켜져 있지만 유효한 수신자가 설정되지 않으면, 내보내기는 평문을 쓰는 대신 명확한 오류와 함께 실패합니다. 유효한 수신자(age 공개 키 또는 SSH 공개 키)를 추가하거나, 내보내기를 평문으로 의도한다면 암호화를 끄세요. [기능](features.md)을 참고하세요.

## 데이터베이스 덤프가 실패했습니다

덤프가 실패해도 그 주위의 백업은 실패하지 않습니다. 덤프 자체가 실패한 실행으로 기록되고, 이유가 무엇을 고쳐야 하는지 알려 줍니다.

- **로그인 거부.** 덤프는 컨테이너 자신의 비밀번호 변수(`POSTGRES_PASSWORD`, `MARIADB_ROOT_PASSWORD`, `MYSQL_ROOT_PASSWORD` 또는 그 `_FILE` 판)로 로그인합니다. 데이터베이스 컨테이너에서 확인하세요. 컨테이너의 사용자가 읽을 수 없는 비밀을 가리키는 `_FILE` 변수도 같은 식으로 실패합니다.
- **권한 부족.** 무작위 root 비밀번호에서는 덤프가 앱 사용자로만 로그인할 수 있어 그 데이터베이스 하나만 담기고, MySQL 8.4 이상은 아예 거부할 수 있습니다. 컨테이너에 진짜 root 비밀번호를 주거나, 그 컨테이너의 덤프를 끄세요.
- **시스템 테이블 업그레이드 필요.** MariaDB는 시스템 테이블이 더 낮은 버전에서 온 경우 덤프를 거부합니다(오류 1558). 변수 `MARIADB_AUTO_UPGRADE=1`을 추가하고 컨테이너를 재시작하거나, 컨테이너 안에서 `mariadb-upgrade`를 한 번 실행하세요.
- **덤프 도구 없음.** `pg_dump`, `mysqldump`, `mariadb-dump`가 없는 경량 이미지나 직접 만든 이미지는 덤프할 수 없습니다. 공식 이미지를 쓰거나 덤프를 끄세요.
- **시간 제한.** 덤프에는 `DB_DUMP_MAX_HOURS`(기본 6), 주위 백업에는 `BACKUP_MAX_HOURS`가 걸리고, 진행이 멈춘 덤프는 `BACKUP_STALL_HOURS` 뒤에 잘립니다. 마지막 경우의 원인은 대개 애플리케이션이 쥐고 있는 잠금입니다. 걸린 제한을 올리거나, 애플리케이션이 한가할 때 덤프하세요.
- **컨테이너가 일시 중지되었거나 재시작 중.** 덤프는 실행 중인 서버와 이야기합니다. 컨테이너가 계속 재시작한다면 그 이유는 컨테이너 자신의 로그에 있습니다.
- **손상된 덤프를 제거하지 못함.** BombVault는 끝내지 못한 덤프를 다시 삭제합니다. 그 삭제가 실패하면 덤프는 손상 표시가 붙은 채 목록에 남고, 거기서 삭제할 수 있습니다.

## 가져오기가 실패했습니다

가져오기는 컨테이너를 멈추고, 데이터 폴더를 옆으로 옮긴 뒤, 이미지가 그 자리에 빈 폴더를 만들게 합니다. 가져오기 자체보다 앞선 단계가 실패하면 예전 폴더가 저절로 제자리로 돌아옵니다. 가져오기가 실패하면 컨테이너에는 새 폴더가 남고, 예전 폴더는 `<데이터 폴더>.bombvault-before-import-<타임스탬프>`로 그 옆에 남습니다. 실행의 오류 메시지가 정확한 경로를 알려 줍니다.

TrueNAS처럼 그 자체가 데이터세트인 데이터 폴더는 이름을 바꿀 수 없습니다. 이때 가져오기는 폴더를 그대로 두고 내용을 옆에 보관하는 폴더로 옮기므로, 상위 데이터세트에 그만큼의 공간이 필요합니다. 가져오기는 컨테이너를 멈추기 전에 이를 확인합니다.

손으로 되돌리려면 컨테이너를 멈추고, 현재 데이터 폴더의 이름을 바꿔 치운 다음, 보관된 폴더를 원래 이름으로 되돌리고 컨테이너를 시작하세요. 데이터세트라면 폴더 이름을 바꾸는 대신 내용을 옮기세요. Unraid에서는 Shares 탭의 파일 관리자로 할 수 있습니다.

## ZFS 데이터세트 백업이 실패했거나 데이터세트를 건너뛰었습니다 {#zfs-datasets}

문제마다 대괄호 안에 이유 코드가 붙으며, [ZFS 데이터세트](zfs-datasets.md#reason-codes) 페이지에 모든 코드와 해결 방법이 있습니다. 가장 흔한 세 가지:

- **`snapshot-loop`**: Host Data가 새 마운트를 전달하지 않아 스냅샷이 BombVault에 도달하지 못했습니다. 컨테이너를 편집해 Host Data의 Access Mode를 Read/Write - Slave로 바꾸고 BombVault를 다시 시작하세요.
- **`key-not-loaded`**: 키가 로드되지 않은 암호화 데이터세트는 건너뜁니다. `zfs load-key`로 키를 로드하고 데이터세트를 마운트하면 다음 백업에 포함됩니다.
- **`ssh-auth`**: 서버가 BombVault의 키를 거부했습니다. 백업 페이지의 **연결 보기**로 여는 **이 서버와의 ZFS 연결**에 키를 허용하는 명령이 나옵니다. 서버에서 한 번 실행하세요.

## 항목이 "학습 중 N/10"에 머물러 있음

대부분의 이상 징후 검사는 항목의 백업이 10번 성공한 뒤에 시작되며, **예상된 것으로 표시** 후와 항목의 선택이 바뀐 뒤에는 횟수를 다시 셉니다. 일정이 없는 항목은 학습하지 않고, appdata가 없는 컨테이너는 학습할 것이 없으며, 배지도 그렇게 알려 줍니다. 이상 징후 페이지의 **학습 진행 상황**은 항목마다 열 조각으로 된 링을 보여 줍니다.

## 보존 정책이 한 항목의 오래된 백업을 더 이상 삭제하지 않음

열린 심각한 이상 징후가 붙잡고 있습니다. 항목의 소스가 거의 비었거나, 크게 줄었거나, 한 백업이 데이터 대부분을 다시 저장했습니다. 항목의 배지에서 이상 징후를 여세요. 데이터가 없어졌거나 암호화되었다면 먼저 연결된 마지막 정상 백업에서 복원하세요. 그런 다음 이상 징후를 확인하거나, 변경이 본인에 의한 것이면 예상된 것으로 표시하면 다음 실행부터 평소대로 정리합니다. 보존 미리보기는 이런 항목을 보존됨으로 표시합니다. ZFS 항목에서는 이상 징후가 가리키는 데이터세트만 오래된 백업을 유지하고, 트리의 다른 데이터세트는 평소처럼 정리됩니다.

## 수동 정리에서 일부 항목이 보존되었다고 표시됨

원인은 같습니다. 정리는 이런 이상 징후가 있는 항목의 오래된 백업을 건드리지 않고 메시지에 그 항목을 적습니다. 나머지는 평소대로 정리됩니다.

## 기록 가져오기에서 저장소를 읽지 못했다고 표시됨

업데이트 뒤 BombVault는 각 저장소에서 이전 백업의 크기를 한 번 읽어 옵니다. 그때 연결할 수 없었던 저장소(멈춰 있던 오프사이트 대상이나 마운트되지 않은 공유 등)는 **설정, 검증**의 **이상 징후** 카드에 표시되고 하루에 한 번 다시 시도합니다. 그동안 그 저장소의 항목은 새 백업으로 학습합니다.

## 디스크 공간 경고가 Unraid 대시보드와 맞지 않음

Unraid 사용자 공유(`/mnt/user`)에서 여유 공간은 디스크 하나가 아니라 어레이 전체의 것입니다. 원격 저장소는 여유 공간을 보고하는 rclone 원격을 통해서만 측정됩니다. S3, B2, REST, SFTP 저장소는 값이 없으며 **이상 징후** 카드에 측정되지 않음으로 표시됩니다.

## AI 어시스턴트가 연결되지 않음

[MCP 서버](mcp.md#troubleshooting) 페이지에 MCP 엔드포인트의 각 상태 코드와 각 거부가 무엇을 뜻하는지, 어떻게 하면 되는지 정리되어 있습니다.

## 컨테이너가 계속 재시작하거나 비정상으로 보입니다

BombVault는 자체 `/api/health`에서 정상/비정상을 보고합니다. 자가 치유 도구(예: Autoheal)가 엔진이 멈추면 자동으로 재시작할 수 있습니다. 근본 원인은 컨테이너 로그와 **호스트 통합** 카드를 확인하세요.
