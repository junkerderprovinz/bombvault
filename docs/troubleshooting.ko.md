# 문제 해결

간단한 FAQ입니다. SSH를 통한 VM 백업의 호스트 쪽 문제 해결 표 전체(권한 거부, 호스트 키 검증, 누락된 템플릿 변수 등)는 [SSH를 통한 VM 백업 가이드](vm-backup-ssh-setup.md)를 참고하세요.

## 무언가가 올바르게 연결되지 않았습니다 {#something-is-not-wired-up-correctly}

개요에 **호스트 통합** 카드를 **사용자 지정**에서 추가하세요. 호스트 통합 확인은 모든 마운트와 CLI(Docker 소켓, libvirt, restic, qemu-img, rclone)를 검사해 빠진 부분을 알려 주고, **지금 확인**으로 다시 실행할 수 있습니다. 버그라고 단정하기 전에 여기서 시작하세요. 빠진 마운트나 닿지 않는 호스트는 바로 드러납니다.

## 웹 UI에 접속할 수 없습니다 {#i-cannot-reach-the-web-ui}

BombVault는 기본으로 포트 `3443`에서 HTTPS를 제공하므로(자체 서명 인증서), `https://<your-unraid-ip>:3443`을 여세요. 자체 서명 인증서 경고를 수락하거나, BombVault를 자체 인증서를 쓰는 리버스 프록시 뒤에 두세요. `HTTP_ONLY=true`로 실행하면 대신 포트 `3000`에서 일반 HTTP를 제공합니다(TLS를 종료하는 프록시 뒤에서 쓰도록 만든 설정입니다).

## APP_KEY를 잃어버렸습니다 {#i-lost-my-app_key}

`APP_KEY`는 restic 저장소 비밀번호를 만들어 냅니다. 이것도 없고 복구 키트도 없고 그룹에 키 보관본도 없다면 암호화된 백업을 복구할 수 없습니다. 그래서 복구 키트를 내려받을 때까지 개요에 **복구 키트를 저장하세요**가 표시됩니다. [오프사이트 및 복구](offsite-recovery.md#recovery-kit)를 참고하세요. `openssl rand -hex 32`로 키를 만들고, 어떤 백업이든 믿고 쓰기 전에 서버 밖에 보관하세요.

## 로그인 비밀번호를 잊었습니다 {#i-forgot-the-login-password}

로그인 페이지에서 **비밀번호를 잊으셨나요?**를 선택하세요. BombVault가 12자 코드를 컨테이너 로그에 기록합니다(Unraid에서는 Docker 탭에서 BombVault 아이콘을 누르고 **Logs**를 엽니다). 10분 안에 새 비밀번호와 함께 입력하세요. 재설정하면 2단계 인증이 꺼지고, 모든 패스키가 삭제되며, 모든 API 토큰, MCP 키, OAuth 로그인이 취소되고, 다른 세션이 모두 종료되며, 휴대폰 페어링이 꺼집니다. **설정, 보안**에서 패스키를 다시 추가하고, 거기서 휴대폰 페어링을 다시 켜고, 아직 필요한 토큰과 키를 새로 만드세요. [보안 모델](configuration.md#login)을 참고하세요.

## 백업이 멈추고 키를 더 이상 열 수 없다고 나옵니다 {#backups-stopped-and-say-the-key-can-no-longer-be-opened}

이 서버는 긴급 마법사에서 다른 서버의 백업 키를 넘겨받았고, 그 뒤에 `APP_KEY`가 바뀌었습니다. 넘겨받은 키는 이전 APP_KEY로 봉인되어 있어 BombVault가 열 수 없으며, 잘못된 키로 쓰는 대신 아무것도 백업하지 않습니다. 개요의 **조치 필요**에 이 내용이 나옵니다. APP_KEY를 원래대로 되돌리거나, 복원 페이지의 **긴급**에서 복구 키트를 다시 올리세요.

## 휴대폰이 로그인 페이지로 갑니다 {#a-phone-lands-on-the-login-page}

페어링된 휴대폰은 **설정, 보안**에서 **그룹의 12개 단어로 휴대폰 페어링 허용**이 켜져 있는 동안에만 그룹을 통해 세션을 받습니다. 비밀번호를 재설정하면 꺼집니다. 서버보다 오래된 앱도 업데이트하기 전에는 세션을 받지 못합니다. 주소로 추가한 서버는 항상 비밀번호를 요구합니다. 인스턴스 페이지에서 제거한 휴대폰은 앱을 다시 열면 꺼진 상태로 돌아옵니다. 들여보내려면 그 세부 정보의 **모니터링**에서 **이 인스턴스 조회**를 켜세요.

## VM 백업이 연결되지 않습니다 {#vm-backup-will-not-connect}

VM 백업은 마운트가 아니라 SSH를 통해 libvirt와 통신합니다.

- 호스트에서 SSH가 켜져 있고 BombVault의 공개 키가 `/root/.ssh/authorized_keys`에 승인되어 있는지 확인하세요(설정, 연동, 호스트 SSH에 키와 **연결 테스트** 버튼이 있습니다).
- 사용자 지정 `br0.x` 네트워크에서는 `LIBVIRT_HOST`를 Unraid LAN IP로 설정하세요(거기서는 컨테이너가 `host.docker.internal`로 호스트에 닿지 못합니다). **Settings, Docker, Host access to custom networks**를 켜세요.
- Unraid의 SSH 포트를 바꿨다면 `LIBVIRT_SSH_PORT`도 같게 설정하세요.
- TrueNAS에서는 TrueNAS 자체 libvirt 소켓을 가리키는 `LIBVIRT_URI`를 설정하고, 앱에 `SETPCAP` 기능을 주고, **Credentials, Users**에서 키를 root에 추가하세요([TrueNAS SCALE](getting-started.md#truenas) 참고).
- 단계별 전체 진단(도달 가능성 테스트, VLAN 라우팅, `Permission denied (publickey)`, `Host key verification failed`)은 [SSH를 통한 VM 백업 가이드](vm-backup-ssh-setup.md)에 있습니다.

## 라이브 VM 스냅샷이 실행되지 않았습니다 {#a-live-vm-snapshot-did-not-run}

라이브 스냅샷에는 `/mnt/user`가 아닌 `/mnt/cache`(또는 `/mnt/diskX`)에 있는 디스크가 필요합니다. VM에 qemu 게스트 에이전트가 있으면 스냅샷은 정지된(quiesced) 상태로 만들어지고, 없으면 크래시 일관성 스냅샷이 됩니다. 꺼진 VM에서는 라이브가 자동으로 정상 종료 방식으로 바뀝니다. 정상 종료 백업은 VM을 종료하고, 디스크를 백업한 다음, 다시 시작하므로 항상 일관됩니다. 게스트가 종료될 때까지 최대 10분을 기다리고 강제로 끄지는 않으므로, 업데이트를 설치하는 중인 Windows 게스트가 중간에 끊기지 않습니다. 그 뒤에도 계속 실행 중인 게스트는 그대로 두고, 그 백업은 이유와 함께 실패합니다.

## 백업이 "repository is already locked"로 실패했습니다 {#a-backup-failed-with-repository-is-already-locked}

보통은 컨테이너가 작업 도중 업데이트되거나 재시작되면서 남은, 주인 없는 restic 잠금입니다. BombVault는 확실히 주인이 없는 잠금을 알아보고 자동으로 해제한 뒤 한 번 다시 시도합니다. 재시작 뒤에는 그런 잠금이 10분 동안 갱신되지 않을 때까지 기다립니다. 아직 실행 중인 restic은 5분마다 잠금을 갱신하며, BombVault는 아직 갱신되고 있는 잠금을 절대 지우지 않습니다. 같은 저장소에 쓰고 있는 두 번째 BombVault의 잠금일 수 있기 때문입니다. 30분 동안 갱신되지 않은 잠금은 누가 걸었든 지워집니다. 오류가 계속되면 **설정, 검증**의 **백업 확인** 카드를 열고, 해당 섹션 행의 **더보기** 아래 **잠금 해제**를 선택해 멈춘 잠금을 직접 지우세요. **잠금 해제**도 아직 갱신되고 있는 잠금은 그대로 두고, 마지막으로 언제 갱신되었는지 알려 줍니다. 진짜 문제는 숨겨지지 않고 그대로 드러납니다.

## 백업 후 오프사이트 복사가 일어나지 않았습니다 {#my-off-site-copy-did-not-happen-after-a-backup}

오프사이트 복제는 설계상 최선을 다하는 방식이라, 오프사이트에서 문제가 생겨도 로컬 백업이 실패하는 일은 없습니다. 저장 위치가 언제 복사하는지 확인하세요. 그 **복사** 카드에 **백업할 때마다**라고 적혀 있거나 자체 계획이 표시되며, **설정, 일정, 섹션별 오프사이트 복사**에서 섹션에 자체 계획을 줄 수 있습니다. 바로 실행하려면 **설정, 대상**의 **오프사이트 복사본** 카드에서 해당 섹션 행의 **지금 복제**를 사용하고, 실행되는 동안 **오프사이트 복사 진행 중**이라고 표시되는 개요의 상태 머리글을 지켜보세요. 실패한 복사는 **조치 필요**에 나타납니다.

## rest-server의 인증서를 신뢰하지 않습니다 {#a-rest-servers-certificate-is-not-trusted}

restic은 모르는 인증서를 거부하며, 오류 메시지가 인증서를 어디에 두어야 하는지 알려 줍니다. rest-server의 자체 서명 인증서나 그것에 서명한 인증 기관의 인증서를 PEM 파일로 BombVault 데이터 폴더의 `certs` 폴더(컨테이너 안에서는 `/config/certs`, Unraid에서는 `appdata/bombvault/certs`)에 복사하고 다시 테스트하세요. 재시작은 필요 없습니다.

## 백업이 Host Data 밖의 데이터는 백업되지 않았다고 알립니다 {#data-outside-host-data}

컨테이너가 Host Data로는 BombVault가 읽을 수 없는 폴더에 데이터를 두고 있습니다. 백업은 정의와 닿을 수 있는 모든 폴더를 저장하고, 활동 로그의 해당 줄을 주황색으로 표시하며, 빠뜨린 폴더를 알려 줍니다. 흔한 경우는 두 가지입니다. TrueNAS의 `/mnt/.ix-apps` 아래 ixVolume, 그리고 compose 스택의 데이터베이스 볼륨 같은 `/var/lib/docker/volumes` 아래의 이름 있는 Docker 볼륨입니다. 컨테이너 **설정** 탭의 **백업 폴더** 카드는 이런 폴더를 컨테이너 안의 경로와 호스트 경로와 함께 빨간색으로 표시해 나열합니다.

익명 Docker 볼륨은 알리지 않습니다. 이미지가 선언했지만 아무도 매핑하지 않은 폴더를 위해 Docker가 스스로 만들고, 16진수 64자리 이름을 붙여 `/var/lib/docker/volumes` 아래에 둡니다. 대개 캐시가 들어 있으므로 백업은 초록색으로 남고, 카드는 익명이라는 메모와 함께 나열만 합니다.

- **그 데이터도 백업하고 싶을 때.** 폴더를 Host Data 아래의 호스트 경로, 예를 들어 appdata 공유 안의 폴더로 매핑하면 다음 백업부터 포함됩니다.
- **필요하지 않을 때.** 같은 탭의 **제외 패턴** 카드에 그 폴더의 경로 두 가지 중 하나를 한 줄로 추가하세요. `/cache`처럼 컨테이너 안의 경로나, `/var/lib/docker/volumes/jellyfin_cache/_data`처럼 경고에 나오는 호스트 경로입니다. 다음 백업부터 경고가 그 폴더를 빼며, 입력란 아래의 미리 보기가 이유를 알려 줍니다. 그 위쪽 폴더를 쓴 줄도 되지만, 이름만 있는 줄이나 `/`는 안 됩니다.

## 백업이 보류됨이라고 나옵니다 {#deferred-backups}

컨테이너의 앱이 바빠서 백업이 기다리고 있으며, 저절로 다시 시도합니다. 활동 로그의 줄에 이유와 다음 시도 시각이 나옵니다. 컨테이너 **설정** 탭의 **앱이 사용 중일 때** 카드에도 같은 내용과 대기가 끝나는 시각이 나옵니다. 따로 할 일은 없습니다. 바로 백업하려면 **지금 백업**을 쓰세요. 직접 시작한 백업은 기다리지 않으며, 종료 코드 75일 때도 마찬가지입니다.

- **직접 만든 검사.** 앱이 바쁜 동안 **백업 전 명령**이 종료 코드 75로 끝나게 하세요. 예를 들면 `[ "$(cat /tmp/players)" = 0 ] || exit 75`입니다. 0이 아닌 다른 코드는 예전처럼 백업을 실패시키므로, 고장 난 스크립트는 **조치 필요**에 그대로 나타납니다.
- **Plex, Jellyfin, Emby에 질의하지 않을 때.** BombVault는 먼저 컨테이너 자신의 주소로 서버에 묻고, 응답이 없으면 컨테이너 안에서 curl이나 wget을 실행합니다. 둘 다 없는 이미지는 스스로를 통해 물어볼 수 없으며, 그러면 로그에 그 사실이 나옵니다. **서버가 응답하지 않으면 백업**이 켜져 있으면 그런 백업은 그냥 실행되고, 꺼져 있으면 기다립니다.
- **Jellyfin이나 Emby가 거부할 때.** **API 키**를 확인하세요. 서버 대시보드의 API 키 메뉴에서 만듭니다.
- **Plex가 거부할 때.** BombVault는 `/config`에 마운트된 폴더의 `Preferences.xml`에서 토큰을 읽습니다. 한 번도 로그인한 적 없는 서버에는 토큰이 없고, 토큰 없이 접근을 허용하는 곳에서만 응답합니다.
- **일시 정지한 영화 때문에 백업이 밤새 기다릴 때.** **일시 정지 세션 무시 기준(분)**을 설정하세요. 예를 들어 30으로 둡니다.
- **트래픽 검사가 백업을 통과시키지 않을 때.** 아무도 쓰지 않을 때 컨테이너가 보내는 양보다 높게 **사용 중 기준(KiB/s)**을 올리세요. BombVault가 시작한 직후에는 검사가 컨테이너를 **조용한 시간(분)**만큼 지켜볼 때까지 기다립니다.
- **백업이 밤에 실행되지 않을 때.** 시간대를 정해 두면 그 안에서만 시도합니다. 마감이 시간대 밖에 걸리는 대기는 그래도 마감 시각에 끝납니다.

## 큰 백업이 메모리 부족으로 종료되었습니다 {#a-large-backup-was-killed-for-running-out-of-memory}

**설정, 시스템**의 **성능** 카드에서 **백업당 메모리 제한 (MiB, 0 = 없음)**을 컨테이너가 쓸 수 있는 양보다 한참 낮게 설정하세요. 제한에 가까워지면 restic이 메모리를 더 자주 비우므로 속도는 조금 떨어지지만, 백업이 종료되는 대신 느려집니다.

## 복원이 시작하기 전에 중단되었습니다 {#a-restore-aborted-before-it-started}

무엇이든 멈추거나 제거하기 전에, 복원은 사전 충돌 검사를 합니다. 컨테이너의 고정 IP와 공개 호스트 포트가 비어 있는지 확인합니다. 다른 컨테이너가 이미 하나를 쓰고 있으면, 복원을 반쯤 끝낸 채 두지 않고 분명하고 조치할 수 있는 메시지와 함께 중단합니다. 충돌하는 포트나 IP를 비운 다음 다시 시도하세요.

TrueNAS 앱을 삭제한 경우처럼 컨테이너의 네트워크가 없으면, 복원 확인이 그 네트워크의 이름을 알려 주고 아무것도 바꾸기 전에 복원을 거부합니다. TrueNAS에서 같은 이름으로 앱을 다시 설치하면 네트워크가 다시 만들어지므로, 그런 다음 데이터를 복원하세요.

## 일반 내보내기가 파일을 쓰지 않고 실패했습니다 {#a-plain-export-failed-instead-of-writing-a-file}

**설정, 시스템**에서 **age 로 내보내기 암호화**가 켜져 있는데 유효한 수신자가 없으면, 내보내기는 평문을 쓰지 않고 분명한 오류와 함께 실패합니다. 유효한 수신자(age 공개 키나 SSH 공개 키)를 추가하거나, 평문으로 내보낼 생각이라면 암호화를 끄세요. [일반 내보내기](backups.md#exports)를 참고하세요.

## 데이터베이스 덤프가 실패했습니다 {#a-database-dump-failed}

덤프가 실패해도 그것을 감싼 백업은 실패하지 않습니다. 덤프는 별도의 실패한 실행으로 기록되며, 이유에 고쳐야 할 것이 나옵니다.

- **로그인 거부.** 덤프는 컨테이너 자신의 비밀번호 변수(`POSTGRES_PASSWORD`, `MARIADB_ROOT_PASSWORD`, `MYSQL_ROOT_PASSWORD` 또는 `_FILE` 버전)로 로그인합니다. 데이터베이스 컨테이너에서 확인하세요. 컨테이너 자신의 사용자가 읽을 수 없는 시크릿을 가리키는 `_FILE` 변수도 같은 식으로 실패합니다.
- **권한 부족.** root 비밀번호가 무작위이면 덤프는 앱 사용자로만 로그인할 수 있어 그 데이터베이스 하나만 담으며, MySQL 8.4 이상에서는 아예 거부될 수 있습니다. 컨테이너에 실제 root 비밀번호를 주거나 그 컨테이너의 덤프를 끄세요.
- **시스템 테이블 업그레이드 필요.** MariaDB는 시스템 테이블이 이전 버전의 것이면 덤프를 거부합니다(오류 1558). `MARIADB_AUTO_UPGRADE=1` 변수를 추가하고 컨테이너를 재시작하거나, 컨테이너 안에서 `mariadb-upgrade`를 한 번 실행하세요.
- **덤프 도구 없음.** `pg_dump`, `mysqldump`, `mariadb-dump`가 없는 슬림 이미지나 직접 만든 이미지는 덤프할 수 없습니다. 공식 이미지를 쓰거나 덤프를 끄세요.
- **시간 제한.** 덤프에는 `DB_DUMP_MAX_HOURS`(기본 6), 그것을 감싼 백업에는 `BACKUP_MAX_HOURS`가 적용되고, 진행이 멈춘 덤프는 `BACKUP_STALL_HOURS` 뒤에 끊깁니다. 마지막의 흔한 원인은 애플리케이션이 쥐고 있는 잠금입니다. 걸린 제한을 올리거나, 애플리케이션이 조용할 때 덤프하세요.
- **컨테이너가 일시 정지되었거나 재시작 중.** 덤프는 실행 중인 서버와 통신합니다. 컨테이너가 계속 재시작한다면 이유는 그 컨테이너의 로그에 있습니다.
- **손상된 덤프를 지울 수 없었음.** BombVault가 끝내지 못한 덤프는 다시 삭제됩니다. 그 삭제가 실패하면 덤프는 손상됨으로 표시된 채 목록에 남고, 거기서 직접 삭제할 수 있습니다.

## 가져오기가 실패했습니다 {#an-import-failed}

가져오기는 컨테이너를 멈추고, 데이터 폴더를 옆으로 옮기고, 이미지가 그 자리에 빈 폴더를 만들게 합니다. 가져오기 자체 앞의 단계가 실패하면 옛 폴더가 자동으로 돌아옵니다. 가져오기가 실패하면 컨테이너는 새 폴더를 유지하고, 옛 폴더는 `<data folder>.bombvault-before-import-<timestamp>`라는 이름으로 그 옆에 남습니다. 실행의 오류 메시지에 정확한 경로가 나옵니다.

TrueNAS처럼 데이터 폴더가 자체 데이터셋이면 이름을 바꿀 수 없습니다. 그러면 가져오기는 폴더를 제자리에 두고 내용물을 그 옆의 보관 폴더로 옮기므로, 위의 데이터셋에 그만한 여유가 있어야 합니다. 가져오기는 컨테이너를 멈추기 전에 이를 확인합니다.

직접 되돌리려면 컨테이너를 멈추고, 현재 데이터 폴더의 이름을 바꿔 치우고, 보관된 폴더를 원래 이름으로 되돌린 다음 컨테이너를 시작하세요. 데이터셋이면 폴더 이름을 바꾸는 대신 내용물을 옮기세요. Unraid에서는 Shares 탭의 파일 관리자로 할 수 있습니다.

## ZFS 데이터셋 백업이 실패했거나 데이터셋을 건너뛰었습니다 {#zfs-datasets}

모든 문제에는 대괄호 안에 이유 코드가 붙으며, [ZFS 데이터셋](zfs-datasets.md#reason-codes) 페이지에 모든 코드와 해결 방법이 나와 있습니다. 가장 흔한 세 가지입니다.

- **`snapshot-loop`**: Host Data가 새 마운트를 전달하지 않아 스냅샷이 BombVault에 닿지 않았습니다. 컨테이너를 편집해 Host Data의 Access Mode를 Read/Write - Slave로 바꾸고 BombVault를 재시작하세요.
- **`key-not-loaded`**: 키가 로드되지 않은 암호화 데이터셋은 건너뜁니다. `zfs load-key`로 키를 로드하고 데이터셋을 마운트하세요. 다음 백업부터 포함됩니다.
- **`ssh-auth`**: 서버가 BombVault의 키를 거부했습니다. 백업 페이지에서 **연결 보기**로 여는 **이 서버와의 ZFS 연결**이 승인하는 명령을 보여 줍니다. 서버에서 한 번 실행하세요.

## 항목이 "학습 중 N/10"에서 멈춰 있습니다 {#an-entry-stays-at-learning-n10}

이상 징후 검사 대부분은 항목의 백업이 10번 성공한 뒤에 시작하며, **예상된 것으로 표시** 뒤와 항목의 선택이 바뀐 뒤에는 횟수를 처음부터 다시 셉니다. 일정이 없는 항목은 학습하지 않고, appdata가 없는 컨테이너는 학습할 것이 없으며, 배지에 그렇게 나옵니다. 이상 징후 페이지의 **학습 진행 상황**은 항목마다 열 칸짜리 고리를 보여 줍니다.

## 한 항목의 오래된 백업이 더 이상 삭제되지 않습니다 {#retention-stopped-deleting-old-backups-of-one-entry}

열려 있는 심각한 이상 징후가 붙잡고 있습니다. 항목의 원본이 거의 비었거나, 크게 줄었거나, 백업 하나가 데이터 대부분을 다시 저장했습니다. 항목의 배지에서 이상 징후를 여세요. 데이터가 없어졌거나 암호화되었다면 먼저 링크된 마지막 정상 백업에서 복원하세요. 그런 다음 이상 징후를 확인하거나, 변화가 직접 한 일이면 예상된 것으로 표시하세요. 다음 실행부터 평소처럼 정리합니다. 보존 미리 보기는 그런 항목을 보존됨으로 표시합니다. ZFS 항목에서는 이상 징후에 나온 데이터셋만 오래된 백업을 보존하고, 트리의 다른 데이터셋은 평소처럼 정리됩니다.

## 수동 정리에서 일부 항목이 보존되었다고 나옵니다 {#manual-prune-says-some-entries-were-kept}

같은 원인입니다. 정리는 그런 이상 징후가 있는 항목의 오래된 백업을 건드리지 않고, 메시지에 그 항목의 이름을 적습니다. 나머지는 모두 평소처럼 정리됩니다.

## 백업이 "on no mounted pool or share"로 실패합니다 {#no-mounted-pool}

Unraid에서 `/mnt`는 메모리에 있으므로, 풀이 마운트되지 않은 그곳의 폴더는 다음 재부팅 때 사라지고 풀이 돌아오면 가려집니다. BombVault는 그곳에 백업이나 플래시 ZIP을 쓰지 않으며, 이전에 쓴 저장소가 이미 그 폴더에 있어도 마찬가지입니다. 풀을 마운트하고 백업을 다시 실행하세요.

## 기록 가져오기가 저장소를 읽을 수 없었다고 나옵니다 {#history-import-says-a-repository-could-not-be-read}

업그레이드 뒤에 BombVault는 각 저장소에서 이전 백업의 크기를 한 번 읽습니다. 그때 닿지 못한 저장소, 예를 들어 꺼져 있던 오프사이트 대상이나 마운트되지 않은 공유는 **설정, 검증**의 **이상 징후** 카드에 개수로 표시되고 하루에 한 번 다시 시도합니다. 그 사이 그 항목들은 새 백업에서 학습합니다.

## 디스크 공간 경고가 Unraid 대시보드와 맞지 않습니다 {#the-disk-space-warning-does-not-match-the-unraid-dashboard}

Unraid 사용자 공유(`/mnt/user`)에서는 여유 공간이 디스크 하나가 아니라 배열 전체의 값입니다. SFTP, Hetzner Storage Box, SMB, WebDAV, 클라우드 드라이브처럼 BombVault가 rclone으로 닿는 원격 저장 위치는 상대편이 여유 공간을 알려 줄 때 측정되며, 직접 입력한 `sftp:` 주소도 마찬가지입니다. S3, B2, REST 저장소에는 수치가 없습니다. 저장 위치에 **크기 알 수 없음**이라고 나오고, **이상 징후** 카드에는 측정되지 않음으로 나열됩니다.

## AI 어시스턴트가 연결되지 않습니다 {#an-ai-assistant-cannot-connect}

[MCP 서버 페이지](mcp.md#troubleshooting)에 MCP 엔드포인트의 각 상태 코드와 거부가 무엇을 뜻하고 어떻게 해야 하는지 나와 있습니다.

## 컨테이너가 계속 재시작하거나 비정상으로 보입니다 {#the-container-keeps-restarting-or-looks-unhealthy}

BombVault는 자체 `/api/health`로 정상/비정상을 알립니다. 엔진이 멈추면 Autoheal 같은 자동 복구 도구가 자동으로 재시작할 수 있습니다. 근본 원인은 컨테이너 로그와 **호스트 통합** 카드에서 확인하세요.

## 저장 위치가 저장을 거부합니다 {#location-refused}

BombVault는 저장 위치를 저장하기 전에 검사하며, 거부할 때는 이유를 한 문장으로 알려 줍니다. 흔한 경우입니다.

- **"This location lies inside another repository or target, or contains one."** 저장소 안의 저장소는 둘 다 망가뜨립니다. 메시지가 다른 위치를 알려 줍니다. 다른 폴더를 고르거나 그쪽을 먼저 제거하세요.
- **직접 설정한 저장소일 때.** 그 위치가 **저장소** 아래의 행 중 하나이거나, 그 안이나 둘레에 있습니다. 다른 곳을 고르거나 그 저장소를 먼저 제거하세요.
- **섹션 자체 폴더와 같은 위치일 때.** 섹션 자체 폴더에 복사하면 실행할 때마다 백업을 자기 자신에게 복사하게 되므로 거부됩니다. 다른 곳을 고르거나 [섹션 자체 폴더](offsite-recovery.md#own-folder)를 참고하세요.
- **"That is not an off-site target of this domain"**은 제거된 저장 위치로 가는 링크에서 나왔습니다. 현재 버전은 시작할 때와 가져오기에서 이를 정리합니다. 그래도 보이면 BombVault를 업데이트하세요.
- **전체 호스트 경로**, 예를 들어 `/mnt/user/backups`일 때. BombVault는 컨테이너에서 실행되므로 Host Data 아래의 경로 `user/backups`를 원하며, 메시지가 입력할 값을 알려 줍니다.

## 원격 저장 위치에서 저장소가 사라졌다고 나옵니다 {#repository-gone}

백업이 있던 위치에 갑자기 저장소가 없다고 해서 새 빈 저장소를 저절로 만들지는 않습니다. 디스크가 돌아왔을 때 진짜 저장소를 가려 버리기 때문입니다. 흔한 원인은 디스크가 마운트되지 않은 rest-server이므로, 디스크를 다시 마운트하고 백업이나 복사를 한 번 더 실행하세요. 옛 저장소를 일부러 비우거나 삭제한 경우에만 그 위치 페이지에서 **여기에 새 저장소 만들기**를 누르세요. 그 위치의 모든 섹션이 한꺼번에 새로 시작합니다.

## 클라우드 로그인이 만료되었습니다 {#cloud-sign-in-expired}

그러면 테스트나 다음 복사가 로그인이 만료되었다고 알립니다. 그 위치 페이지의 **연결 변경**으로 다시 로그인하세요.

- **Box, Jottacloud 등 일회용 갱신 토큰을 쓰는 서비스:** BombVault는 rclone이 갱신한 토큰을 재시작해도, 복구 키트에서도 유지합니다. 오래된 설정 백업에서 복원한 뒤에는 그 안의 토큰이 만료되었을 수 있으므로 한 번 더 로그인하세요. 저장소는 그대로입니다.
- **iCloud Drive:** Apple이 30일 뒤에 로그인을 끝냅니다. `rclone config`에서 새 신뢰 토큰과 쿠키가 필요합니다.
- **OneDrive:** 드라이브가 여러 개인 로그인은 어느 것을 쓸지 묻기 때문에, 고르지 않은 위치는 고를 때까지 쓸 수 없습니다. OneDrive Business와 Google Drive는 [저장 위치](offsite-recovery.md#destinations)의 정리된 데이터에 관한 메모를 참고하세요.

## "마지막 백업의 오프사이트 복사가 아직 실행 중입니다" {#copy-still-running}

그 앞의 백업은 끝났지만 복사가 아직 진행 중이어서, 그 섹션의 새 백업이 막혀 있습니다. 상태 머리글에 더 이상 **오프사이트 복사 진행 중**이 표시되지 않을 때까지 기다리세요. 백업을 시작하는 버튼도 기다리는 동안 같은 내용을 알려 줍니다. 새 위치로의 첫 복사는 몇 시간 걸릴 수 있습니다. [S3 예시](offsite-recovery.md#example-s3)를 참고하세요.

## 대상에 더 새로운 스냅샷이 있어서 ZFS 복제가 멈춥니다 {#replica-target-newer}

대상에 이 서버와 공유하는 가장 새로운 스냅샷보다 더 새로운 스냅샷이 있습니다. 예를 들어 여기 데이터셋을 롤백했거나 대상의 사본이 바뀌었을 때입니다. 복제 카드와 실행 기록이 **대상을 되돌릴 스냅샷**에 그 스냅샷 이름을 적습니다. 실행이 알려 주는 각 데이터셋에 대해 대상에서 그 스냅샷으로 `zfs rollback -r`을 실행한 다음 **지금 복제**를 누르세요. [스냅샷이 남는 기간](zfs-datasets.md#replica-retention)을 참고하세요.

## Unraid 스냅샷이 있는 VM이 실패하고 파일 이름을 알려 줍니다 {#vm-chain}

BombVault는 각 디스크의 백업 체인을 따라가며 그 안의 모든 파일을 백업합니다. 끝까지 따라갈 수 없는 체인은 디스크의 일부를 빼놓는 대신 백업을 실패시키고, 메시지에 파일 이름을 적습니다. 그 파일이 `/mnt` 아래에 있는지, 스냅샷이 VM Manager에 아직 나열되는지 확인하세요. Host Data 밖의 파일은 아예 읽을 수 없습니다. [Unraid 스냅샷이 있는 VM](vm-backup-ssh-setup.md#unraid-snapshots)을 참고하세요.

## 재구축 뒤에 오프사이트 복사가 결정을 기다립니다 {#copies-paused}

**백업 검색**이나 설정을 복원하지 않은 긴급 마법사 뒤, 또는 섹션이 이 데이터베이스보다 이전의 자기 백업을 찾았을 때는 그 섹션의 오프사이트 복사가 기다립니다. BombVault가 어떤 항목을 제외했는지 더 이상 모르기 때문입니다. **조치 필요**와 대상 페이지가 이에 대해 묻습니다. 계속하려면 **이 서버의 백업으로 넘겨받기**를 누르고, 그 전에 섹션의 규칙을 보려면 **먼저 규칙 확인**을 누르세요. 설정 파일을 가져와도 결정을 대신 내려 주지는 않습니다. [재구축 뒤](offsite-recovery.md#after-a-rebuild)를 참고하세요.

## 알림이 오지 않습니다 {#notifications-do-not-arrive}

**설정, 알림**의 **테스트 보내기**로 시작하세요. 카드 아래의 줄이 무슨 일이 있었는지 알려 줍니다.

- **아무것도 전송되지 않을 때.** **알림**을 확인하세요. **안 함**이면 메시지는 나가지 않고 Healthchecks URL로 가는 ping만 나가며, **실패 시에만**이면 성공한 실행은 조용합니다. **예약 실행 요약**이 켜져 있으면 예약 실행은 끝에 요약 하나를 보냅니다.
- **새 주소일 때.** Matrix, Gotify, 이메일의 서버를 바꾸면 입력란이 토큰이나 비밀번호를 다시 묻고, 다시 입력해야 새 주소가 저장됩니다. BombVault는 옛 비밀을 새 곳으로 보내지 않습니다.
- **Gotify**가 서버가 앱 토큰을 거부했다고 하면 Gotify의 애플리케이션에서 토큰을 다시 복사하세요. **서버 URL**은 `/message` 없는 기본 주소입니다.
- **Webhook:** **Webhook 형식**이 서비스에 맞는지 확인하세요. Discord 주소에는 **Discord**가, ntfy에는 **ntfy**가 필요합니다.
- **Unraid 알림**은 호스트 SSH 연결을 통해 실행되므로, 먼저 **설정, 연동**에서 그것을 테스트하세요. 다른 플랫폼에서는 꺼져 있으며, 카드에 그렇게 나옵니다.
- **알림 메일이 오지 않을 때.** **암호화**를 포트와 맞춰 보세요. 보통 587은 **STARTTLS**, 465는 **TLS (implicit)**입니다.

Healthchecks 핑은 이것들과 무관합니다. [Healthchecks](notifications.md#healthchecks)를 참고하세요.

## Android 앱이 서버를 열 수 없습니다 {#android-cannot-open}

시작 화면의 서버 카드에 이유가 나옵니다.

- **연결 안 됨:** 서버 주소도 릴레이도 응답하지 않습니다. **릴레이 없음**이면 앱은 서버 자신의 주소로만 서버에 닿습니다.
- **인증서 확인:** 서버가 신뢰했던 것과 다른 인증서를 보여 줍니다. 앱은 새 인증서를 신뢰한 뒤에야 서버를 열므로, 그 변경이 본인이 한 것인지 확인하세요.
- **로그인이 필요합니다:** 주소로 추가한 서버는 비밀번호를 요구합니다. [휴대폰이 로그인 페이지로 갑니다](#a-phone-lands-on-the-login-page)도 참고하세요.
- **서버 키가 변경되었습니다:** 시작 화면에 새 키의 지문이 나오고, 신뢰한 뒤에야 페이지가 열립니다. [집 밖에서](android.md#away)를 참고하세요.

## 다른 사용자가 로컬 저장소를 읽을 수 없습니다 {#repository-permissions}

로컬 저장소는 SMB를 통한 동기화 사용자 같은 다른 사용자가 읽을 수 있게 유지됩니다. 10.4.1 이전에는 정리, 태그, 풀, 섹션 이동, 삭제, 스택 백업이 쓴 파일이 다음 날 밤까지 읽을 수 없는 채로 남을 수 있었습니다. BombVault를 업데이트하면 바로 읽을 수 있습니다. 자체 백업 저장소는 BombVault의 설정을 담고 있으므로 의도적으로 root만 읽을 수 있게 둡니다.

## 아직도 해결되지 않나요? {#still-stuck}

- [설정](configuration.md)과 [오프사이트 및 복구](offsite-recovery.md) 페이지 전체를 읽어 보세요.
- **설정, 정보**의 **도움말** 카드에 있는 **버그 신고**는 GitHub 이슈용 ZIP을 내려받습니다. 호스트 확인, 비밀을 모두 제거한 구성, 최근 실행, 다음 예약, 컨테이너가 마지막으로 시작한 이후의 최근 로그가 들어 있습니다. 각 데이터베이스의 마지막 덤프, 마운트가 있는 ZFS 항목, 열려 있는 이상 징후, MCP 키의 개수도 들어 있습니다. 비밀번호, 토큰, rclone 구성은 제거되며, 번들이 자체 매니페스트에 그렇게 적습니다. 로그인 비밀번호가 필요합니다. 컨테이너를 재시작시킨 충돌은 `docker logs`를 보세요.
- [Unraid 지원 스레드](https://forums.unraid.net/topic/199509-support-junkerderprovinz-bombvault/)에 질문하세요.
- [GitHub 이슈](https://github.com/junkerderprovinz/bombvault/issues)를 여세요.
