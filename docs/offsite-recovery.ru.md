# Внешняя копия и восстановление

Локальные резервные копии защищают вас от потерянного контейнера или неудачного обновления. Внешняя репликация и проверенный набор для восстановления защищают вас от потери всей машины, программ-вымогателей или пожара. Эта страница охватывает репликацию во внешнее хранилище, придание этой копии защиты от подделки, доказательство того, что вы можете восстановить, и восстановление, когда самого BombVault больше нет.

## Внешняя репликация

Сохраняйте быструю локальную резервную копию и копируйте её в одно или несколько других мест. Места, в которые копируется домен, выбираются на карточке **Домены** в **Настройки, Хранилище**, по одной метке на место (см. [Места хранения](storage-places.md#domains)). BombVault копирует туда новые снимки через `restic copy` по принципу максимальных усилий, поэтому неудачная копия никогда не проваливает локальную резервную копию. Место, в котором хранится домен, не обязано быть локальным; см. [Домен, хранящийся в удалённом месте](#remote-primary-repositories).

- **Несколько мест для копий на домен.** Домен можно копировать сразу в несколько мест, например в rest-server в доме друга и в бакет B2. Хранение, класс хранения, append-only, лимиты и бюджет роста принадлежат месту, поэтому каждая копия следует правилам того места, куда она попадает.
- **Расписание копирования для каждого домена** (редактируется рядом со всеми остальными расписаниями в Настройки, Расписания): оставьте его пустым, чтобы копировать после каждой локальной резервной копии, или задайте частоту (например `weekly Sun 03:00`), чтобы копировать реже, чем вы делаете резервные копии. **Копировать сейчас** в строке домена запускает копирование по требованию.
- **Хранение для каждого места.** У каждого места свои правила, поэтому внешнее место может хранить копии дольше как архив. Место, где все правила равны нулю, никогда не обрезает снимки.
- **Ограничения пропускной способности** для каждого места ограничивают скорость выгрузки и загрузки restic, чтобы копирование не насыщало ваш WAN.
- **Индикатор репликации** показывает, какой домен копируется, пока это происходит (на его странице и на Панели). Это активный индикатор, а не полоса процентов, потому что `restic copy` не выдаёт машиночитаемого прогресса.

!!! note "Восстановление из любого места"
    Каждый контейнер, VM, набор файлов, flash и конфигурация приложения перечисляют свои резервные копии как единую хронологию по всем местам, где лежит копия. Резервная копия, скопированная в B2, появляется один раз, помеченная каждым местом, которое её хранит. Восстановление берёт первое достижимое место, начиная с репозитория, в который записан элемент, и вы можете выбрать другое место для каждой строки. Внешние места читаются только когда вы их открываете. Удаление в одном месте сначала проверяет остальные и говорит, была ли это последняя копия.

## Размещение для каждого элемента {#placement}

У каждой карточки контейнера, VM и набора файлов есть строка **Размещение** с тремя сегментами:

- **Локально** записывает элемент в репозиторий, показанный под **Сохранено на**, и никуда его не копирует. Используйте это для данных, у которых уже есть вторая копия, например для общего ресурса, который живёт на NAS.
- **Локально + внешнее** записывает его туда же и копирует в цели, отмеченные под **Копировать в**, по одной метке на каждую внешнюю цель домена. Снимите отметку с метки, и эта цель перестанет получать от этого элемента что-либо новое.
- **Только внешнее** записывает элемент прямо в место под **Отправить в**, любое место, кроме домашнего места домена. Если домен уже копируется в это место, элемент получает прямой репозиторий рядом с копиями; иначе BombVault создаёт там репозиторий для домена.

Расположение фиксируется с первой резервной копии элемента, потому что BombVault никогда не переносит резервные копии между репозиториями. Копии можно менять в любое время. Цель, которая перестаёт получать элемент, сохраняет уже имеющиеся у неё копии и обрезает их по собственному хранению при следующем внешнем запуске домена; **Удалить в B2** на карточке удаляет их немедленно. Когда часть этих копий не существует больше нигде, подтверждение перечисляет их по дате и просит имя элемента. Из целей только для добавления удалить нельзя.

Под строкой карточка сообщает, куда идёт элемент и что там на самом деле есть: сколько объектов его хранит, когда каждую цель видели в последний раз, и соблюдается ли 3-2-1. Объектом считается сервер с исходными данными и каждое место на другой площадке (см. [Вне помещения](#off-the-premises-mark)). BombVault проверяет копии и объекты; часть «два носителя» правила 3-2-1 он не проверяет.

### Значения по умолчанию для каждого домена

Карточка **Домены** в Настройки, Хранилище содержит одну строку на домен. **Копируется в** сразу применяется к каждому элементу без собственного выбора, а также к папкам проектов стеков Compose. Когда у домена уже есть резервные копии, **Хранится в** применяется к новому элементу при его первой резервной копии, и изменение этого выбора не переносит ни одной резервной копии. Перед сохранением строка называет каждое место, которое приобретает или теряет элементы, и сколько это снимков, а в вопросе есть переключатель **Применить к элементам без резервных копий**, который также переводит на новое значение по умолчанию каждый элемент, у которого ещё нет резервной копии. **Исключения** перечисляют элементы с собственным выбором.

Новое место, отмеченное в **Копируется в**, получает каждый элемент, который не установлен на Локально. Подтверждение сообщает, сколько это элементов и, где известно, сколько это истории.

### Прямые репозитории

Если под Только внешнее выбрать место, куда домен уже копируется, BombVault один раз спрашивает подтверждение, затем создаёт прямой репозиторий рядом с копиями, например `s3:https://s3.eu-central-003.backblazeb2.com/bucket/container-direct`, и направляет элемент в него. Для цели копирования без места этот выбор открывает диалог с предлагаемым адресом и тестом соединения, который ничего не создаёт, а **Создать и использовать** создаёт репозиторий. Прямой репозиторий перенимает ключ места, класс хранения, лимиты, настройку append-only и хранение, и меняется вместе с ними. Когда новый ключ места не может его открыть, прямой репозиторий сохраняет тот ключ, что у него есть, и сохранение сообщает об этом. Его снимки несут тег `bv:direct`, и каждый другой проход хранения их сохраняет, поэтому прямой репозиторий, потерявший связь со своим местом, никогда не устаревает по локальным правилам. Ключ B2, ограниченный одной папкой, должен охватывать адрес места, а не только папку домена, иначе папка рядом с ней окажется недоступна.

### Вне помещения {#off-the-premises-mark}

Копия считается отдельным объектом, только если её место находится на другой площадке. Облачное место засчитывается всегда, а папка на этом Unraid никогда; для NAS, rest-server или сервера SFTP ответьте на вопрос **Где находится устройство?** в подробностях места: **Здесь, в доме** или **На другой площадке**. Ответ учитывается только для подсчёта объектов и 3-2-1 на карточках и на Панели. Он не меняет ни одной копии.

### После пересборки

Выборы копирования живут в собственных настройках BombVault. После пересборки через Найти без восстановленного `/config` они исчезают, и копирование всего заново отправило бы в B2 элементы, которые вы оставили в стороне. Поэтому внешняя репликация каждого пересобранного домена приостанавливается. Панель показывает это жёлтым, а строка домена на карточке Домены предлагает **Подтвердить значение по умолчанию** с предпросмотром того, что скопирует следующий запуск, и именами в резервных копиях, у которых нет записи, которые можно там же исключить. Только подтверждение завершает паузу; импорт файла настроек возвращает правила и значения по умолчанию, но не завершает её.

## Домен, хранящийся в удалённом месте {#remote-primary-repositories}

Домен не обязательно хранить локально. Пока в расположении его резервных копий нет ни одной резервной копии, выберите удалённое место в **Хранится в** на карточке Домены, и домен будет сохранять резервные копии прямо туда, без локальной копии и без шага копирования. Тогда удалённый репозиторий остаётся единственной копией, если домен не копируется ещё и в другое место. Каждое удалённое место получает одни и те же меры защиты:

- **Проверку соединения**, прежде чем что-либо будет записано.
- **Ограничения полосы** для самой резервной копии: те же ключи `--limit-upload` и `--limit-download`, что использует копирование.
- **Защиту append-only**, проверяемую тем же активным тестом на подделку. Когда она включена, BombVault никогда не очищает репозиторий, потому что учётные данные на этой машине не должны быть способны удалить единственную копию резервных данных.
- **Бюджет роста**, отслеживаемый по тому же тренду размера, что и на карточке Хранилище.

Домен, хранящийся в удалённом месте, служит источником своих копий так же, как локальный; см. [Копии между местами с разными учётными данными](storage-places.md#different-credentials).

!!! note "Учётные данные принадлежат месту"
    Удалённое место хранит собственные учётные данные. Место, настроенное с общими облачными учётными данными, продолжает их использовать, пока его доступ не изменят в подробностях места.

### SMB и WebDAV без монтирования на хосте {#smb-webdav}

Форма rclone в окне **Добавить место** содержит форму для общего ресурса Windows или Samba и для сервера WebDAV (Nextcloud, ownCloud, SharePoint или любого другого). Укажите короткое имя, хост и общий ресурс (SMB) или URL и тип сервера (WebDAV), пользователя и пароль, и BombVault запишет раздел rclone за вас. rclone сам маскирует пароль перед сохранением; если добавить назначение с уже существующим именем, этот раздел заменяется, а второй не добавляется.

Новое удалённое хранилище затем появляется в списке удалённых хранилищ формы, где вы выбираете его для места. Общий ресурс является первым сегментом пути, а не частью имени.

Это лучший путь, чем монтировать общий ресурс в Unraid: restic не советует держать репозиторий на смонтированном ресурсе CIFS, а здесь ничего не монтируется. NFS в форме нет, потому что ни у restic, ни у rclone нет бэкенда NFS; для NFS смонтируйте экспорт на хосте и добавьте его как место через **Другой общий ресурс**.

## Неизменяемая (append-only) внешняя копия

Пометьте внешний репозиторий как append-only, чтобы программа-вымогатель или скомпрометированный хост не могли удалить или переписать ваши резервные копии. Дальняя сторона (`restic/rest-server`, работающий в режиме `--append-only`) **обеспечивает** это. BombVault лишь **проверяет** это и никогда не показывает зелёный только на основании заявления о конфигурации.

Окно **Добавить место** содержит готовый к вставке рецепт rest-server в режиме append-only с одним пользователем для этого BombVault. В месте rest-server с включённым переключателем **Режим append-only** кнопка **Проверить append-only** в подробностях места запускает тест на подделку для каждого пути домена, включённой копии и репозитория в этом месте и даёт один ответ для всего места, поэтому append-only внешняя копия достижима без ручного редактирования конфигов.

!!! note "Успешное удаление в `/locks/` ожидаемо"
    Append-only не означает, что удалить больше ничего нельзя. restic должен создавать и снимать собственные блокировки, поэтому `/locks/` намеренно остаётся доступным для записи и удаления. Снимки и стоящие за ними данные, то есть именно то, на что нацелен шифровальщик, удалить невозможно. Если ты сам проверишь удалённую сторону, успешное удаление в `/locks/` является правильным поведением, а не дырой в защите.

!!! warning "Неизменяемые репозитории никогда не очищаются с этой машины"
    Неизменяемая внешняя копия намеренно никогда не очищает старые снимки. Задайте для неё **тревогу бюджета роста**, чтобы вас оповестили, прежде чем размер репозитория выйдет из-под контроля.

## Тест на подделку

BombVault периодически доказывает гарантию append-only, фактически пытаясь выполнить удаление в отношении внешнего репозитория, нацеленное на несуществующий объект:

- **Отказ** означает защищено.
- **Принятие** означает не защищено.
- **Неубедительный** результат (сервер недоступен, ошибка аутентификации) никогда не переворачивает сохранённый вердикт.

Настоящий переворот из защищённого в незащищённое запускает одно оповещение.

В месте кнопка **Проверить append-only** проверяет каждый путь домена, включённую копию и репозиторий там с их собственными учётными данными и сводит результаты в один ответ: достаточно одного репозитория, который принимает удаление, чтобы всё место получило *удаление разрешено*.

## Учебные DR

BombVault предлагает два уровня доказательства того, что ваши резервные копии действительно восстановимы, а не просто присутствуют.

- **Учебные восстановления для проверки (локальные).** BombVault периодически выполняет `restic check --read-data-subset` (ограниченно, никогда не полное восстановление, забивающее диск) и показывает бейдж *последний раз подтверждено восстановимым* по каждому домену. Частота живёт в Настройки, Расписания; бейдж в Настройки, Целостность.
- **Учебные DR (внешние).** BombVault восстанавливает реальную цель из внешнего репозитория в одноразовую песочницу, проверяет её файл за файлом и байт за байтом, затем очищает. Это доказывает, что вы можете восстановить из внешнего хранилища, а не только то, что репозиторий отвечает. Проверяются только места на другой площадке, потому что копия в том же доме ничего не доказывает на случай потери дома. Домен, копируемый в несколько таких мест, проверяется на одном из них за каждый запуск по расписанию, по очереди, а Панель называет место последней проверки.

**Оценочная карта защиты от программ-вымогателей** на Панели сводит это в зелёную / жёлтую / красную позицию по каждому домену, с чек-листом с отметками возраста (внешняя копия настроена, append-only проверено, репликация актуальна, учебное восстановление пройдено, шифрование включено, стратегия очистки задана). Каждая красная строка ведёт прямо к исправлению, и карточка становится зелёной только на проверенных фактах.

## Панель получателя (принимающая сторона)

![Принимающая сторона, наблюдаемая только на чтение, с проверкой целостности на этой машине.](assets/screenshots/receiver.png)

*Принимающая сторона, наблюдаемая только на чтение, с проверкой целостности на этой машине.*

Всё выше, это *отправляющая* сторона. На машине, которая **принимает** неизменяемые внешние копии от другого BombVault, панель получателя даёт вам независимый мониторинг этих репозиториев только для чтения на принимающем оборудовании, поэтому молчаливый сбой на дальнем конце не остаётся незамеченным.

Включите переключатель **Получатель** в Настройках, чтобы открыть вкладку **Получатель**. По умолчанию она отключена; включайте её только на машине, которая действительно принимает неизменяемые внешние резервные копии. Затем зарегистрируйте полученный репозиторий (только для чтения, открытый ключом отправляющего экземпляра), чтобы получить:

- **Инвентарь снимков, сгруппированный по источникам**, чтобы вы могли точно видеть, какие контейнеры, VM и наборы файлов прибыли.
- **Последнее получение** по каждому источнику, чтобы вы знали, насколько свеж каждый из них.
- **Независимый запуск `restic check`** на принимающем оборудовании, чтобы целостность проверялась там, где данные фактически лежат, а не только на отправителе.
- **Выключатель мертвеца:** оповещение, когда источник перестаёт отправлять в заданном вами окне.
- **Оповещения о целостности:** оповещение, когда проверка на принимающей стороне не проходит.

Получатель строго только для чтения. Он никогда не пишет в полученный репозиторий, поэтому никогда не может нарушить гарантию append-only, на которую полагается отправитель.

## Полный пример: две машины Unraid, от начала до конца

Выше описаны отдельные части. Здесь одна законченная установка с настоящими значениями, потому что части проще собрать, увидев их собранными хотя бы раз.

Две машины: **TOWER** держит контейнеры и отправляет копии, **VAULT** принимает их и обеспечивает неизменяемость. Подставьте свои имена, адреса и пути общих ресурсов.

**1. На VAULT поднимите сервер в режиме append-only.** В BombVault на TOWER откройте *Настройки → Хранилище*, нажмите **Добавить место**, выберите **rest-server** и нажмите **Показать рецепт**. Скопируйте блок **Шаблон Unraid**, сохраните его на VAULT как `/boot/config/plugins/dockerMan/templates-user/my-rest-server.xml`, затем *Docker → Add Container* и выберите **rest-server** из списка шаблонов. Перед запуском впишите показанную строку `htpasswd` на VAULT в `/mnt/user/appdata/rest-server/.htpasswd`. Пароль показывается один раз и нигде не хранится; рецепт уже вписал его и пользователя в форму на TOWER, поэтому оставьте это окно открытым. Строка `htpasswd` несёт тот же пароль, уже хешированный bcrypt, так что хешировать вам ничего не нужно.

    Оставьте `--append-only` в поле OPTIONS. Без него VAULT снова просто обычный общий ресурс.

**2. На TOWER добавьте место.** Введите адрес VAULT, `http://VAULT:8000`, рядом с пользователем и паролем, которые вписал рецепт, затем нажмите **Проверить соединение**. BombVault строит из них адрес:

    rest:http://VAULT:8000/tower

Первым сегментом пути служит пользователь htpasswd, здесь `tower`, а каждый домен получает под ним свою папку, например `rest:http://VAULT:8000/tower/container`. Ответьте на вопрос **Где находится устройство?** вариантом **На другой площадке**, нажмите **Добавить** и отметьте место в **Копируется в** для тех доменов, которые должны туда попадать.

**3. На TOWER включите режим append-only** в разделе **Защита** подробностей места, затем нажмите **Проверить append-only**. Проверка охватывает каждый путь домена, копию и репозиторий в этом месте и даёт один ответ для места, который должен быть *удаление отклонено*. Что означают ответы:

| Результат | Что произошло |
| --- | --- |
| **удаление отклонено** | VAULT отклонил удаление. Это единственное успешное состояние. |
| **удаление разрешено** | VAULT принял удаление. `--append-only` отсутствует или был убран. |
| сообщение вместо результата | Проверку не удалось выполнить. Обычно адрес не тот, который использует сам restic, или изменились учётные данные. Ничего не записывается и никакой сигнал не подаётся. |

**4. На VAULT смотрите, что приходит.** Включите *Настройки → Приёмник*, откройте вкладку **Приёмник** и зарегистрируйте репозиторий только для чтения.

!!! warning "Расположение — это путь **внутри** контейнера, записанный относительно точки монтирования хоста"
    Введите `user/appdata/rest-server/tower/container`, а **не** `/mnt/user/appdata/…`. BombVault работает в контейнере, где `/mnt` хоста примонтирован в другом месте; абсолютного пути хоста там не существует. Если вы его вставите, BombVault подскажет нужный относительный путь.

    **Отправляющий APP_KEY** — это ключ TOWER, а не VAULT. Он на TOWER в *Настройки → Система*.

**5. При желании сделайте это взаимно.** Повторите те же пять шагов в обратную сторону: rest-server на TOWER, принимающий копию с VAULT. Тогда каждая машина обеспечивает неизменяемость для другой, и ни одна не может удалить копии другой.

## Управляемое восстановление

Отдельная вкладка **Восстановление** проводит свежую или пересобранную установку через сценарий аварии, в одном месте:

1. **Проверяет, что BombVault может прочитать ваши резервные копии** (подводный камень с ключом шифрования сразу впереди).
2. **Восстанавливает собственные настройки BombVault**, поэтому пути резервных копий, внешние цели и учётные данные, которые нужны остальному потоку, приходят предзаполненными. Резервная копия настроек читается из места, которое строка «Автобэкап» указывает в **Хранится в**, или из копии автобэкапа в **Копируется в**, и это место показывается вместе с адресом; чтобы читать из другого места, сначала измените строку «Автобэкап» в шаге 3. Восстановление применяется через самоперезапуск по сокету Docker, поэтому работающая база данных настроек никогда не перезаписывается под открытым дескриптором.
3. **Подключает ваши существующие резервные копии** через строки карточки **Домены**: в строке каждого домена выберите в **Хранится в** место, где лежат его резервные копии, а в **Копируется в** места с его копиями. Место, которого ещё нет ни в одной строке, например общая папка, сервер или облачный бакет, подключается через **Добавить место**, то же окно, что и в Настройки, Хранилище. Затем **Подключить и предпросмотр** проверяет, что резервные копии читаются.
4. **Находит** контейнеры, VM, наборы файлов и наборы данных ZFS, хранящиеся в нём.
5. **Восстанавливает контейнеры и VM за один раз** (оставляя остановленными, чтобы вы запускали их обдуманно) и показывает наборы файлов и элементы ZFS, которые восстанавливаются по одному; элементы ZFS возвращаются выключенными. Набор для восстановления в одном клике.

!!! note "Внешние копии ждут после пересборки"
    Когда шаг 4 пересобирает записи без старых настроек, внешняя репликация этих доменов приостанавливается, пока не будет подтверждено значение по умолчанию для размещения. См. [Размещение для каждого элемента](#placement).

!!! tip "Плановая миграция против аварии"
    Управляемое восстановление восстанавливает собственные настройки BombVault из резервной копии. Для *планового* переезда на новую машину вы можете вместо этого перенести конфигурацию напрямую с помощью карточки **Экспорт и импорт настроек** (переносимый файл JSON). См. [Конфигурация](configuration.md#portable-settings-export-and-import).

### Восстановление из репозитория другого BombVault

Отдельная карточка на вкладке **Восстановление** открывает репозиторий *другого* экземпляра BombVault (общий ресурс, смонтированный под `/mnt`, или удалённый URL) с **`APP_KEY` этого экземпляра**, в одноразовой сессии только для чтения. Просматривайте хранящиеся там контейнеры, VM и наборы файлов, выберите снимок и восстановите его, и восстановленный объект становится обычным локальным контейнером, VM или набором файлов. Ничто никогда не записывается в другой репозиторий, а ваши собственные настройки резервного копирования остаются нетронутыми (сессия живёт в памяти и истекает сама собой). Перемещение контейнера с сервера A на сервер B больше не означает перенаправление настроек репозитория и их откат после. Живая федерация сервер-к-серверу явно вне области; это намеренный одноразовый вытяг.

## Набор для восстановления ключа шифрования

Это та часть, которая делает аварийное восстановление возможным даже когда нет работающего BombVault.

Один клик загружает **мастер-ключ**, **производный пароль restic** и **точные расположения репозиториев и команды**, поэтому вы можете восстановить прямо с помощью CLI restic на любой машине. Напоминание на Панели пилит вас, пока вы его не сохраните.

!!! danger "Храните набор для восстановления вне сервера"
    Набор содержит секрет, который расшифровывает ваши резервные копии. Держите его в надёжном месте отдельно от сервера (менеджер паролей, распечатанная копия в сейфе). Если вы потеряете и BombVault, и `APP_KEY` без набора для восстановления, ваши зашифрованные резервные копии не могут быть восстановлены.

!!! warning "Самый новый снимок не всегда тот, который нужно восстанавливать"
    Начиная с restic 0.17, `restic snapshots` показывает размер каждого снимка. После потери данных самым новым может оказаться опустошённый снимок, поэтому не восстанавливайте снимок, который намного меньше предыдущих. После шифровальщика это может быть зашифрованный снимок обычного размера. Если BombVault ещё работает, сначала загляните на его страницу **Аномалии**: там указана последняя хорошая копия. Для восстановления не нужны данные BombVault об аномалиях, а пауза хранения лишь оставляет больше снимков.

### Запечатывание набора

Если вы включили шифрование age для обычных экспортов (Настройки), набор для восстановления тоже запечатывается им и скачивается как `bombvault-recovery-kit.md.age`. Он в формате ASCII armor, а не двоичный, поэтому остаётся обычным текстом: вставить его в менеджер паролей или распечатать можно точно так же, как раньше, просто без вашего ключа содержимое не прочитать.

!!! warning "Не храните ключ age внутри набора"
    Чтобы открыть запечатанный набор, нужен ваш **закрытый** ключ age. Храните его там, где он не зависит от самого набора, иначе восстанавливать придётся две вещи вместо одной. Запечатывание имеет смысл, когда набор хранится в месте, которое вы контролируете не полностью (общий менеджер паролей, заметки в облаке, распечатка в офисе); набор в вашем собственном сейфе уже защищает сейф.

    Если шифрование включено, а пригодный получатель не настроен, скачивание сразу отклоняется. BombVault никогда не отдаёт вместо этого главный ключ в открытом виде.

### Если набора нет под рукой

Пароль нигде не хранится, он **вычисляется** из `APP_KEY`. Имея ключ и оболочку, вы можете воспроизвести его сами:

```sh
printf 'bombvault:restic-repo' \
  | openssl dgst -sha256 -mac HMAC -macopt hexkey:$APP_KEY -r \
  | cut -d' ' -f1
```

Это HMAC-SHA256 по фиксированной строке `bombvault:restic-repo`, ключом служат сырые байты шестнадцатеричного `APP_KEY`, результат печатается как 64 строчных шестнадцатеричных символа. То же значение есть в наборе как выведенный пароль restic; это на тот день, когда набор окажется не там, где вы.

!!! warning "Для полученного репозитория берите ключ ОТПРАВЛЯЮЩЕГО экземпляра"
    Репозиторий, попавший сюда через внешнюю репликацию, создала отправившая его машина своим **собственным** `APP_KEY`. Вывод из ключа принимающей машины даёт пароль, который restic отвергает, и это выглядит ровно как повреждённый репозиторий, не будучи им. Это обычная причина, по которой `restic check` на полученном репозитории снова и снова спрашивает пароль.

Поскольку определения восстановления живут **внутри** каждого репозитория (`<repo>/def`, `<repo>/vm-def`), скопированная папка репозитория полностью самодостаточна, поэтому набор плюс репозиторий, это всё, что нужно для восстановления на голом железе.

## Как достать дамп базы данных обратно {#database-dumps}

Дамп базы данных это отдельная точка восстановления в репозитории контейнеров, с меткой `dbdump:<container>` и единственным файлом `/dbdump/<container>.sql`. BombVault показывает, скачивает и импортирует их в разделе **Резервные копии**; ниже те же шаги с одним restic, на день, когда BombVault под рукой нет.

```sh
restic -r <repo> snapshots --tag dbdump:<container>
restic -r <repo> dump --tag dbdump:<container> latest /dbdump/<container>.sql > <container>.sql
```

Метки `dbversion:` и `dbname:` на каждом дампе говорят, из какой версии сервера он взят и какие базы в нём. Полный файл заканчивается строкой `-- PostgreSQL database cluster dump complete` или `-- Dump completed`.

Импортируйте его в контейнер той же или более новой версии (PostgreSQL) либо той же основной версии (MySQL и MariaDB), один раз запущенный с пустой папкой данных, чтобы он себя развернул. Клиент базы данных на хосте не нужен, он есть в контейнере:

```sh
docker exec -i <container> sh -c 'exec psql -X -U "${POSTGRES_USER:-postgres}" -d postgres' < <container>.sql
docker exec -i <container> sh -c 'exec mariadb -uroot -p"$MARIADB_ROOT_PASSWORD"' < <container>.sql
docker exec -i <container> sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < <container>.sql
```

Для одной базы из полного дампа MySQL и MariaDB принимают `--one-database <name>` в команде клиента. В дампе PostgreSQL на каждую базу приходится свой раздел, начинающийся строкой `\connect <name>`: скопируйте нужный раздел в отдельный файл и импортируйте его с `-d <name>` после создания базы.

!!! warning "Дамп, снятый под root, несёт с собой пользователей сервера"
    Полный дамп MySQL или MariaDB, снятый под root, содержит системную базу `mysql`, поэтому его импорт заменяет учётные записи нового сервера, включая пароль root, на записи из дампа. В PostgreSQL сообщение `role ... already exists` про пользователя, созданного самим контейнером, ожидаемо и безвредно.
