# โหนด

โหนดคือ BombVault ที่ไม่มีเว็บอินเทอร์เฟซ เช่น บน VPS หรือบนเซิร์ฟเวอร์เล็กๆ ที่บ้านเพื่อน โหนดสำรองคอนเทนเนอร์และโฟลเดอร์บนเซิร์ฟเวอร์ของตัวเอง ส่วน BombVault ที่คุณใช้เพิ่มโหนด ซึ่งหน้านี้เรียกว่า **อินสแตนซ์หลัก** จะบอกว่าโหนดต้องสำรองเมื่อไรและส่งข้อมูลสำรองไปที่ไหน คุณดูแลโหนดได้จากเว็บอินเทอร์เฟซของอินสแตนซ์หลัก ข้างๆ รายการของคุณเอง

![การ์ดของโหนด vps-falkenstein ในหน้าอินสแตนซ์: เชื่อมต่อแล้ว เวอร์ชัน ข้อมูลสำรองที่ไปยังเซิร์ฟเวอร์รับ เวลาสำรองของแต่ละส่วน และปุ่มเปลี่ยนปลายทาง แทนที่ และปล่อย](assets/screenshots/nodes/card-dark.png#only-dark)
![การ์ดของโหนด vps-falkenstein ในหน้าอินสแตนซ์: เชื่อมต่อแล้ว เวอร์ชัน ข้อมูลสำรองที่ไปยังเซิร์ฟเวอร์รับ เวลาสำรองของแต่ละส่วน และปุ่มเปลี่ยนปลายทาง แทนที่ และปล่อย](assets/screenshots/nodes/card-light.png#only-light)

## ทำงานอย่างไร {#how-it-works}

- **อินสแตนซ์หลักถือคีย์ของโหนด** เมื่อคุณเพิ่มโหนด อินสแตนซ์หลักจะสร้าง `APP_KEY` ให้ เก็บสำเนาที่ปิดผนึกไว้ และส่งให้คุณครั้งเดียวในไฟล์ compose ของโหนด อินสแตนซ์หลักใช้สำเนานี้ติดต่อโหนดและเปิดข้อมูลสำรองของโหนด
- **โหนดไม่ต้องเปิดพอร์ต** อินสแตนซ์หลักกับโหนดคุยกันผ่านรีเลย์ด้วยการเชื่อมต่อส่วนตัวของตัวเอง แยกจากกลุ่มการจับคู่ของคุณ อินสแตนซ์หลักเป็นฝ่ายเริ่มและเซ็นทุกการเรียก ส่วนโหนดส่งถึงอินสแตนซ์หลักแค่คำทักทายเท่านั้น ปลายทางเดียวที่ต้องเปิดพอร์ตคือ [เก็บไว้บนโหนด](#keep-on-node)
- **ข้อมูลสำรองไม่เคยผ่านรีเลย์** โหนดส่งข้อมูลสำรองตรงไปยังที่ที่คุณเลือก ได้แก่ เซิร์ฟเวอร์รับของอินสแตนซ์หลัก ปลายทางที่จัดเก็บแห่งใดแห่งหนึ่งของอินสแตนซ์หลัก หรือ rest-server บนตัวโหนดเอง
- **โหนดไม่วางแผนอะไรเอง** โหนดไม่รันตารางเวลา ไม่ส่งการแจ้งเตือน และไม่เข้าร่วมกลุ่มหรือป้อมปราการใด อินสแตนซ์หลักเป็นผู้เริ่มการสำรอง คอยดูว่าเป็นอย่างไร และส่งการแจ้งเตือน
- **โหนดสำรองคอนเทนเนอร์และชุดโฟลเดอร์** VM แฟลชไดรฟ์ ชุดข้อมูล ZFS และการสำรองข้อมูลตัวเอง ยังคงเป็นงานของการติดตั้งแบบเต็ม

การเชื่อมต่อใช้รีเลย์ของอินสแตนซ์หลักเองเมื่อกลุ่มของอินสแตนซ์หลักมีรีเลย์ของตัวเอง ไม่เช่นนั้นจะใช้รีเลย์ของโปรเจกต์ แม้อินสแตนซ์หลักจะจับคู่แบบไม่ใช้รีเลย์ก็ตาม

## ก่อนเริ่ม {#before-you-start}

- **รหัสผ่านเข้าสู่ระบบบนอินสแตนซ์หลัก** การเพิ่มโหนด การแสดงไฟล์ compose ของโหนดอีกครั้ง และการเปิดรายการของโหนด ต้องลงชื่อเข้าใช้ด้วยรหัสผ่าน ดู [การเข้าสู่ระบบ](configuration.md#login)
- **Docker พร้อม Compose บนเซิร์ฟเวอร์ของโหนด**
- **ที่สำหรับเก็บข้อมูลสำรอง** หนึ่งในสามแบบใต้ [ข้อมูลสำรองไปที่ไหน](#placement) เซิร์ฟเวอร์รับปลอดภัยที่สุด เพราะโหนดลบอะไรที่นั่นไม่ได้เลย

## การเพิ่มโหนด {#add}

1. บนอินสแตนซ์หลัก เปิด **อินสแตนซ์** แล้วเลือก **เพิ่มโหนด** ที่มุมขวาล่าง
2. **ชื่อ** พิมพ์ชื่อที่โหนดจะแสดงที่นี่ เช่น ชื่อเซิร์ฟเวอร์ แล้วเลือก **ถัดไป**

    ![หน้าต่างเพิ่มโหนดในขั้นแรก พิมพ์ชื่อ vps-helsinki ไว้แล้ว](assets/screenshots/nodes/add-name-dark.png#only-dark)
    ![หน้าต่างเพิ่มโหนดในขั้นแรก พิมพ์ชื่อ vps-helsinki ไว้แล้ว](assets/screenshots/nodes/add-name-light.png#only-light)

3. **ข้อมูลสำรอง** เลือกว่าข้อมูลสำรองจะไปที่ไหน แล้วกรอกสิ่งที่ที่นั่นต้องการ **สำรองข้อมูลทุกวันเวลา** คือเวลาที่ทั้งสองส่วนเริ่ม อินสแตนซ์หลักแนะนำครึ่งชั่วโมงหลังการสำรองคอนเทนเนอร์ของตัวเอง เพื่อไม่ให้ทั้งสองแย่งใช้ดิสก์ชุดเดียวกันพร้อมกัน ภายหลังคุณกำหนดตารางเวลาแยกให้แต่ละส่วนได้ที่การ์ด เลือก **ถัดไป**

    ![ขั้นที่สอง: เลือกเซิร์ฟเวอร์รับ กรอกที่อยู่สำหรับโหนดเป็นที่อยู่ https และสำรองข้อมูลทุกวันเวลา 03:00](assets/screenshots/nodes/add-placement-dark.png#only-dark)
    ![ขั้นที่สอง: เลือกเซิร์ฟเวอร์รับ กรอกที่อยู่สำหรับโหนดเป็นที่อยู่ https และสำรองข้อมูลทุกวันเวลา 03:00](assets/screenshots/nodes/add-placement-light.png#only-light)

4. **เริ่ม** หน้าต่างแสดงไฟล์ compose ของโหนดที่กรอก `MODE`, `APP_KEY`, `NODE_HOME` และ `NODE_NAME` ไว้แล้ว คัดลอกไฟล์นี้และเก็บ `APP_KEY` ไว้ในที่ปลอดภัย บนเซิร์ฟเวอร์ของโหนด:

    ```sh
    mkdir -p /opt/bombvault-node && cd /opt/bombvault-node
    nano docker-compose.yml   # paste the file from the window
    docker compose up -d
    ```

    ก่อนเริ่ม ให้ชี้วอลุ่ม Host Data ไปยังข้อมูลที่ต้องการสำรอง และตั้ง `HOST_SOURCE_ROOT` เป็นพาธเดียวกัน ตามตัวอย่างด้านล่าง

5. หน้าต่างจะรอโหนด เมื่อโหนดตอบ อินสแตนซ์หลักจะบอกโหนดว่าข้อมูลสำรองไปที่ไหนและตรวจว่าโหนดไปถึงที่นั่นได้ แล้วหน้าต่างจะแสดง **vps-helsinki ออนไลน์แล้วและรับคำสั่งจากอินสแตนซ์นี้**

    ![ขั้นสุดท้าย: ไฟล์ compose จากนั้นโหนดออนไลน์และข้อมูลสำรองของโหนดอยู่บนเซิร์ฟเวอร์รับ](assets/screenshots/nodes/add-start-dark.png#only-dark)
    ![ขั้นสุดท้าย: ไฟล์ compose จากนั้นโหนดออนไลน์และข้อมูลสำรองของโหนดอยู่บนเซิร์ฟเวอร์รับ](assets/screenshots/nodes/add-start-light.png#only-light)

คุณปิดหน้าต่างก่อนโหนดตอบได้ การ์ดของโหนดจะแสดง **กำลังรอโหนด** และอินสแตนซ์หลักจะบอกโหนดว่าข้อมูลสำรองไปที่ไหนเมื่อโหนดปรากฏตัว

### ตัวอย่าง: VPS ที่สำรองไปยังเซิร์ฟเวอร์รับ {#example-vps}

อินสแตนซ์หลักคือกล่อง Unraid ชื่อ `tower` ที่รัน[เซิร์ฟเวอร์รับ](offsite-recovery.md#receiving-server) reverse proxy เผยแพร่มันเป็น `https://backup.tower.example.org` VPS `vps-helsinki` รัน Nextcloud และ Caddy โดยมีข้อมูลอยู่ใต้ `/srv/appdata`

1. บน `tower` ไปที่ **อินสแตนซ์** แล้ว **เพิ่มโหนด** ตั้งชื่อ `vps-helsinki` แล้วเลือก **ถัดไป**
2. เลือก **เซิร์ฟเวอร์รับข้อมูลของอินสแตนซ์นี้** และพิมพ์ `https://backup.tower.example.org` ใต้ **ที่อยู่สำหรับโหนด** คอนเทนเนอร์ของอินสแตนซ์หลักสำรองตอน 02:30 หน้าต่างจึงเสนอ 03:00 ให้คงไว้แล้วเลือก **ถัดไป**
3. บน VPS บันทึกไฟล์จากหน้าต่าง โดยเปลี่ยนวอลุ่มและ `HOST_SOURCE_ROOT` ให้เป็น `/srv/appdata`:

    ```yaml
    services:
      bombvault-node:
        image: junkerderprovinz/bombvault:latest
        restart: unless-stopped
        hostname: bombvault-node
        container_name: bombvault-node
        volumes:
          - ./config:/config
          - /var/run/docker.sock:/var/run/docker.sock
          - /srv/appdata:/host/user
        environment:
          MODE: node
          APP_KEY: "<filled in by home>"
          NODE_HOME: "<filled in by home>"
          NODE_NAME: "vps-helsinki"
          PLATFORM: generic
          HOST_SOURCE_ROOT: /srv/appdata
    ```

4. รัน `docker compose up -d` ไม่กี่วินาทีต่อมา หน้าต่างบน `tower` จะบอกว่าโหนดออนไลน์แล้ว และ **ข้อมูลสำรองไปที่ https://backup.tower.example.org**
5. เวลา 03:00 อินสแตนซ์หลักเริ่มการสำรองของโหนด เช้าวันถัดมา การ์ด **โหนด** บนภาพรวมแสดงข้อมูลสำรองล่าสุดของ `vps-helsinki` และ **ข้อมูลสำรอง** แสดงคอนเทนเนอร์ของโหนดในส่วนแยกของตัวเอง

วิธีหาข้อมูลของคอนเทนเนอร์บนโฮสต์ Docker ธรรมดาอธิบายไว้ใน [การตรวจหาต้นทางการสำรอง](configuration.md#backup-source-detection)

## ข้อมูลสำรองไปที่ไหน {#placement}

แต่ละโหนดมีปลายทางเดียวสำหรับทั้งสองส่วน เมื่อโหนดออนไลน์แล้ว **เปลี่ยนปลายทาง** บนการ์ดจะใช้เปลี่ยนได้ ที่ใหม่จะได้ที่เก็บใหม่ และข้อมูลสำรองที่ที่เดิมยังอยู่ที่เดิม

### เซิร์ฟเวอร์รับข้อมูลของอินสแตนซ์นี้ {#to-receiver}

โหนดเขียนลงเซิร์ฟเวอร์รับของอินสแตนซ์หลักในโหมด append-only: เพิ่มข้อมูลสำรองได้แต่ลบไม่ได้เลย โหนดได้ข้อมูลเข้าสู่ระบบของตัวเองที่ตั้งชื่อตามโหนด และที่เก็บหนึ่งแห่งต่อส่วนในโฟลเดอร์ของตัวเองที่นั่น อินสแตนซ์หลักเพิ่มคีย์ของตัวเองเข้าไปในแต่ละที่เก็บและจัดระเบียบเอง เพราะโหนดทำไม่ได้

โหนดเข้าถึงเซิร์ฟเวอร์ที่ **ที่อยู่สำหรับโหนด** ซึ่งคุณตั้งไว้ในขั้นที่สองหรือในหน้าต่าง **เซิร์ฟเวอร์รับข้อมูล** โหนดมักส่งมาจากอินเทอร์เน็ต ที่อยู่จึงต้องเป็นแบบใดแบบหนึ่งต่อไปนี้:

- `https://` เช่น หลัง reverse proxy, Pangolin หรือ tunnel เมื่อเซิร์ฟเวอร์แสดงใบรับรองของตัวเองแทนใบรับรองจากผู้ออกใบรับรองสาธารณะ ให้วางใบรับรองนั้นในรูปแบบ PEM ใต้ **ใบรับรอง**
- `http://` กับที่อยู่ IP ส่วนตัว เช่น `10.0.0.5` บนลิงก์ WireGuard หรือ `100.101.102.103` บน Tailscale

`http://` ธรรมดาไปยังที่อยู่สาธารณะจะถูกปฏิเสธ เพราะโหนดจะส่งข้อมูลสำรองข้ามอินเทอร์เน็ตโดยไม่เข้ารหัส เมื่อคุณเปลี่ยนที่อยู่ อินสแตนซ์หลักจะบอกทุกโหนดที่ใช้เซิร์ฟเวอร์รับนี้ และโหนดที่ไม่อยู่จะรู้เมื่อกลับมา

### ปลายทาง {#to-location}

โหนดเขียนลงปลายทางที่จัดเก็บแห่งหนึ่งของอินสแตนซ์หลักที่โหนดเข้าถึงได้เอง: บริการ S3 หรือเซิร์ฟเวอร์ REST ผ่าน `https://` หรือที่ที่อยู่ส่วนตัว ที่เก็บของโหนดอยู่ที่ `bombvault-nodes/<node id>/containers` และ `bombvault-nodes/<node id>/files` ที่นั่น

โหนดลงชื่อเข้าใช้ด้วย[ข้อมูลรับรองที่บันทึกไว้](offsite-recovery.md#sign-ins)ที่สร้างไว้สำหรับโหนด ซึ่งต้องไม่ซ้ำกับชุดที่อินสแตนซ์หลักใช้เขียนลงปลายทางนั้น ถ้าหน้าต่างบอกว่ายังไม่มี ให้เพิ่มก่อน ต่างจากบนเซิร์ฟเวอร์รับ ด้วยข้อมูลรับรองนี้โหนดมักลบสิ่งที่อยู่ที่ปลายทางได้ และหน้าต่างก็บอกไว้แบบนั้น

### เก็บไว้บนโหนด {#keep-on-node}

โหนดเก็บข้อมูลสำรองเองไว้หลัง rest-server ของตัวเองในโหมด append-only และอินสแตนซ์หลักดึงสำเนาของแต่ละส่วนมาเก็บในที่จัดเก็บของตัวเอง แบบนี้เหมาะกับโหนดที่อินสแตนซ์หลักหาที่ให้ไม่ได้ และเป็นปลายทางเดียวที่ต้องเปิดพอร์ต

![ขั้นที่สองที่เลือกเก็บไว้บนโหนด พร้อมที่อยู่ https://203.0.113.7:8443 และหมายเหตุเรื่องพอร์ตที่เปิด](assets/screenshots/nodes/add-keep-dark.png#only-dark)
![ขั้นที่สองที่เลือกเก็บไว้บนโหนด พร้อมที่อยู่ https://203.0.113.7:8443 และหมายเหตุเรื่องพอร์ตที่เปิด](assets/screenshots/nodes/add-keep-light.png#only-light)

1. ใต้ **ที่อยู่ของโหนด** พิมพ์ที่ที่อินสแตนซ์หลักใช้เข้าถึงโหนด: ที่อยู่สาธารณะของโหนดกับพอร์ตที่ว่าง เช่น `https://203.0.113.7:8443` โดยไม่ต้องมีโฟลเดอร์ต่อท้าย ใช้ `http://` เฉพาะกับที่อยู่ส่วนตัวเท่านั้น เหมือนข้างบน
2. โหนดเริ่มคอนเทนเนอร์ `bombvault-node-rest-server` บนพอร์ตนั้น โดยเก็บที่เก็บไว้ในโฟลเดอร์ `bombvault-node` ใต้ Host Data ถ้าใช้ `https://` โหนดจะสร้างใบรับรองสำหรับที่อยู่นั้น และอินสแตนซ์หลักจะปักหมุดใบรับรองนั้นไว้
3. อนุญาตพอร์ตในไฟร์วอลล์ของโหนด เพื่อให้อินสแตนซ์หลักเข้าถึงได้ พอร์ตที่คอนเทนเนอร์อื่นบนโหนดใช้อยู่จะถูกปฏิเสธพร้อมชื่อคอนเทนเนอร์นั้น

อินสแตนซ์หลักดึงส่วนหนึ่งมาทันทีที่โหนดสำรองส่วนนั้นเสร็จ และดึงซ้ำทุกชั่วโมงตอนนาทีที่ 15 เผื่อไว้ แม้ปิด **ดึง** อยู่ก็ตาม สิ่งที่อินสแตนซ์หลักดึงมาจะอยู่กับอินสแตนซ์หลักเหมือน[สำเนาที่ดึงมา](offsite-recovery.md#receiver)อื่นๆ แม้โหนดจะหายไปแล้ว rest-server ของโหนดไม่รับการลบ โหนดจึงจัดระเบียบที่เก็บของตัวเองเมื่ออินสแตนซ์หลักขอ และชุดโฟลเดอร์ของโหนดจะไม่รวมโฟลเดอร์ `bombvault-node` โหนดจึงไม่สำรองข้อมูลสำรองของตัวเองซ้ำ

## โหนดสำรองเมื่อไร {#schedule}

ตารางเวลาของทุกโหนดเป็นของอินสแตนซ์หลัก การ์ดแสดงกำหนดการต่อส่วน เช่น **คอนเทนเนอร์** *ทุกวันเวลา 2:00* และ **โฟลเดอร์** *ทุกสัปดาห์ (อา.) เวลา 4:00* คลิกแล้วจะเปิดตัวแก้ไขแบบเดียวกับใน[ตารางเวลา](schedules.md#plans) และการเปลี่ยนจะบันทึกทันที

![กำหนดการของคอนเทนเนอร์ของโหนดที่เปิดจากการ์ด มีปิด รายวัน รายสัปดาห์ ทุก N วัน และ Cron](assets/screenshots/nodes/schedule-dark.png#only-dark)
![กำหนดการของคอนเทนเนอร์ของโหนดที่เปิดจากการ์ด มีปิด รายวัน รายสัปดาห์ ทุก N วัน และ Cron](assets/screenshots/nodes/schedule-light.png#only-light)

- **โหนดที่ไม่อยู่** จะเริ่มการสำรองที่พลาดไปทันทีที่กลับมา อินสแตนซ์หลักตรวจทุกห้านาที
- **โหนดที่ยุ่งอยู่** จะถูกขออีกครั้งในห้านาทีต่อมา
- **ระหว่างที่อินสแตนซ์หลักจัดระเบียบ** ข้อมูลสำรองเก่าของโหนด โหนดจะไม่เริ่มอะไรจนกว่าอินสแตนซ์หลักจะเสร็จ บนเซิร์ฟเวอร์รับและบนตัวโหนดเอง ช่วงเวลานี้เริ่มทุกวันอาทิตย์เวลา 03:00 และยาวได้ถึงหกชั่วโมง ที่ปลายทางที่จัดเก็บ จะเป็นไปตามกำหนดการสำเนานอกสถานที่ของอินสแตนซ์หลักสำหรับปลายทางนั้น อินสแตนซ์หลักเก็บข้อมูลสำรองตามกฎของตัวเองสำหรับส่วนนั้นใต้ **เก็บไว้นานแค่ไหน** หรือตามกฎของปลายทางถ้าปลายทางมีกฎของตัวเอง
- **ในรายการการทำงานของโหนด** การสำรองและการกู้คืนที่อินสแตนซ์หลักเริ่มจะแสดงว่าอินสแตนซ์หลักเป็นผู้เริ่ม

## คอยดูโหนดของคุณ {#watch}

การ์ด **โหนด** บนภาพรวมแสดงทุกโหนดพร้อมสถานะ ข้อมูลสำรองล่าสุด ข้อผิดพลาด และความผิดปกติที่ยังเปิดอยู่ การ์ดนี้จะปรากฏเมื่อคุณมีโหนดแล้ว

![การ์ดโหนดบนภาพรวมที่มีสามโหนด: หนึ่งเชื่อมต่อแล้ว หนึ่งไม่ได้ใช้งานและมีข้อผิดพลาดสองรายการ และหนึ่งยังรอโหนดอยู่](assets/screenshots/nodes/overview-card-dark.png#only-dark)
![การ์ดโหนดบนภาพรวมที่มีสามโหนด: หนึ่งเชื่อมต่อแล้ว หนึ่งไม่ได้ใช้งานและมีข้อผิดพลาดสองรายการ และหนึ่งยังรอโหนดอยู่](assets/screenshots/nodes/overview-card-light.png#only-light)

อินสแตนซ์หลักส่งการแจ้งเตือนหนึ่งครั้งต่อเหตุการณ์ผ่าน[ช่องทางการแจ้งเตือน](notifications.md)ของตัวเอง และจะส่งครั้งถัดไปหลังเหตุการณ์นั้นจบแล้วเท่านั้น:

- **การสำรองล้มเหลว** เช่น *BombVault: vps-helsinki: backup failed* พร้อมรายการและเหตุผล การสำรองครั้งหลังของรายการนั้นที่สำเร็จจะปิดเหตุการณ์
- **ติดต่อโหนดไม่ได้** เช่น *BombVault: vps-helsinki is out of reach* อินสแตนซ์หลักจะรอตามสวิตช์คนตายที่สั้นที่สุดบนที่เก็บของโหนด คือ 26 ชั่วโมงหากคุณไม่เปลี่ยน หรือ 6 ชั่วโมงระหว่างที่โหนดยังไม่มีปลายทาง

การเฝ้าดูของตัวรับบนอินสแตนซ์หลักยังดูแลที่เก็บแต่ละแห่งของโหนดด้วย พร้อมสวิตช์คนตายและ `restic check` ทุกวันเวลา 04:00 ดู [ตัวรับและตัวดึง](offsite-recovery.md#receiver)

## รายการของโหนด {#entries}

ใต้ **ข้อมูลสำรอง** รายการคอนเทนเนอร์และโฟลเดอร์มีส่วนสำหรับแต่ละโหนดอยู่ใต้รายการของคุณเอง โดยไม่รวมคอนเทนเนอร์ของตัวโหนดเอง **สำรองข้อมูลเดี๋ยวนี้** ในเมนูของรายการจะเริ่มการสำรองบนโหนด และ **เปิด** จะเปิดหน้าของรายการ

ในส่วนของโหนดในรายการโฟลเดอร์ **เพิ่มชุดโฟลเดอร์** จะเพิ่มชุดโฟลเดอร์บนโหนด และ **แก้ไข** ในเมนูของชุดจะเปลี่ยนชุดนั้น ทั้งสองเปิดหน้าต่างเดียวกับชุดของคุณเอง ตัวเลือกโฟลเดอร์ในหน้าต่างนั้นเรียกดูโฟลเดอร์ของโหนดได้ แต่ไม่สร้างโฟลเดอร์ใหม่ที่นั่น

![ส่วนของโหนด vps-falkenstein ในรายการคอนเทนเนอร์: nextcloud, nextcloud-db, caddy และ uptime-kuma](assets/screenshots/nodes/backups-section-dark.png#only-dark)
![ส่วนของโหนด vps-falkenstein ในรายการคอนเทนเนอร์: nextcloud, nextcloud-db, caddy และ uptime-kuma](assets/screenshots/nodes/backups-section-light.png#only-light)

หน้าของรายการบนโหนดจะแสดงชื่อโหนด เช่น **บน vps-falkenstein** และแสดงข้อมูลสำรองของรายการนั้น **กู้คืน** บนข้อมูลสำรองอันหนึ่งจะกู้คืนรายการนั้นบนโหนดและแทนที่สิ่งที่อยู่ตอนนี้ คอนเทนเนอร์จะถูกหยุดระหว่างนั้น เหมือนบนอินสแตนซ์หลัก

![หน้าของ nextcloud บน vps-falkenstein พร้อมข้อมูลสำรองและปุ่มกู้คืนข้างแต่ละอัน](assets/screenshots/nodes/entry-dark.png#only-dark)

## การแทนที่และการปล่อย {#replace-release}

**แทนที่** จะแสดงไฟล์ compose ของโหนดอีกครั้งหลังลงชื่อเข้าใช้ด้วยรหัสผ่าน ใช้เมื่อต้องการย้ายโหนดไปเซิร์ฟเวอร์อื่นหรือสร้างใหม่: เริ่มไฟล์นั้นที่เซิร์ฟเวอร์ใหม่และปิดเซิร์ฟเวอร์เก่า `APP_KEY` และ `NODE_HOME` ชุดเดิมจะทำให้เป็นโหนดเดิมอีกครั้ง พร้อมข้อมูลสำรองและประวัติของโหนด เซิร์ฟเวอร์สองเครื่องที่ใช้ `APP_KEY` เดียวกันนับเป็นโหนดเดียว จึงอย่ารันทั้งสองเครื่องพร้อมกัน

**ปล่อย** คือการปล่อยโหนดไป โหนดจะเลิกรับคำสั่งจากอินสแตนซ์หลักและไม่สำรองอะไรอีก ข้อมูลสำรองของโหนดยังอยู่ที่เดิม สำเนาทุกชุดที่อินสแตนซ์หลักดึงมาก็เช่นกัน ข้อมูลเข้าสู่ระบบของโหนดบนเซิร์ฟเวอร์รับจะถูกลบ และอินสแตนซ์หลักจะเลิกเฝ้าดูที่เก็บของโหนด โหนดที่ไม่อยู่ตอนที่คุณปล่อยจะคงการ์ดไว้เป็น **กำลังปล่อย** จนกว่าจะรู้เรื่อง โหนดที่ถูกปล่อยแล้วจะไม่รับอินสแตนซ์หลักใดอีกด้วย `APP_KEY` เดิม หากต้องการใช้เซิร์ฟเวอร์นี้อีก ให้เพิ่มเป็นโหนดใหม่และเริ่มด้วยไฟล์ compose ใหม่กับโฟลเดอร์ `config` ที่ว่างเปล่า

## ความปลอดภัย {#security}

ถ้าอินสแตนซ์หลักถูกยึด ผู้โจมตีจะควบคุมโหนดของมันได้ด้วย และโหนดถือ Docker บนเซิร์ฟเวอร์ของตัวเอง ซึ่งเท่ากับ root ที่นั่น ปกป้องอินสแตนซ์หลักด้วยรหัสผ่านและอย่าเปิดให้เข้าถึงจากอินเทอร์เน็ต ถ้าโหนดถูกยึด ผู้โจมตีจะไม่ได้กลุ่มการจับคู่ ป้อมปราการ โหนดอื่น หรือที่เก็บอื่น และลบประวัติบนเซิร์ฟเวอร์รับไม่ได้ รายละเอียดอยู่ใต้ [โหนดในโมเดลความปลอดภัย](configuration.md#nodes)

[ชุดกู้คืน](offsite-recovery.md#recovery-kit)มีบท **โหนด** ที่มี `APP_KEY` รหัสผ่าน restic และที่เก็บของแต่ละโหนด คุณจึงนำโหนดกลับมา หรือกู้คืนข้อมูลสำรองของโหนดด้วย restic ธรรมดาได้
