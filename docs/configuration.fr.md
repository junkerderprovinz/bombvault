# Configuration

Cette page couvre les variables d'environnement du conteneur, les montages que fournit le modèle, le modèle de sécurité, la sauvegarde de VM via SSH et la configuration hors site. L'endroit où vont les sauvegardes se règle dans l'application, comme **destinations**, pas par des variables d'environnement.

## Variables d'environnement {#environment-variables}

| Variable | Obligatoire | Description |
|---|---|---|
| `APP_KEY` | **Oui** | Secret hexadécimal de 32 octets (64 caractères hexadécimaux) qui sert à dériver le mot de passe du dépôt restic. Générez-le avec `openssl rand -hex 32`. Gardez-le précieusement : le perdre rend les sauvegardes chiffrées irrécupérables. |
| `LIBVIRT_HOST` | Pour les VMs et les jeux de données ZFS | Hôte Unraid joint via SSH pour les sauvegardes de VM et de jeux de données ZFS (champ du modèle **Host SSH: Address**, par défaut `host.docker.internal`). Le modèle préremplit l'espace réservé `192.168.x.x`, qui compte comme non défini. Utilisez l'IP de votre Unraid sur le réseau local, obligatoire sur un réseau personnalisé `br0.x`. Quand `host.docker.internal` ne se résout pas, comme dans une application TrueNAS, et que `LIBVIRT_URI` ne nomme pas d'hôte non plus, BombVault utilise la passerelle par défaut du conteneur et le journal de démarrage la nomme. |
| `LIBVIRT_SSH_PORT` | Non | Port SSH de l'hôte pour les sauvegardes de VM et de jeux de données ZFS (champ du modèle **Host SSH: Port**, par défaut `22`). |
| `LIBVIRT_SSH_USER` | Non | Utilisateur SSH sur l'hôte pour les sauvegardes de VM et de jeux de données ZFS (champ du modèle **Host SSH: User**, par défaut `root`). |
| `LIBVIRT_URI` | Non | URI de connexion libvirt complète, utilisée **telle quelle** au lieu d'en construire une à partir des trois variables `LIBVIRT_*` ci-dessus (qui sont alors ignorées pour la chaîne de connexion). Non définie par défaut. Nécessaire sur TrueNAS Scale, dont libvirtd écoute sur un socket non standard que la forme construite ne peut pas exprimer : `qemu+ssh://<user>@<truenas-host>/system?socket=/run/truenas_libvirt/libvirt-sock`. Voir le [guide des sauvegardes de VM](vm-backup-ssh-setup.md#truenas-scale). Quand c'est une URI `qemu+ssh://`, chacune des variables `LIBVIRT_HOST`, `LIBVIRT_SSH_USER` et `LIBVIRT_SSH_PORT` qui n'est pas définie en est tirée, aussi pour les propres commandes SSH de BombVault (transfert de la NVRAM, jeux de données ZFS). |
| `PORT` | Non | Port HTTP (par défaut `3000`, utilisé seulement avec `HTTP_ONLY=true`). |
| `HTTPS_PORT` | Non | Port HTTPS (par défaut `3443`, le modèle le publie à l'identique, l'interface web répond donc sur `https://<ip>:3443`). |
| `HTTP_ONLY` | Non | Mettez `true` pour désactiver l'écoute HTTPS autosignée et servir uniquement du HTTP simple (à utiliser derrière un reverse proxy qui termine le TLS). |
| `BIND_HOST` | Non | Adresse sur laquelle l'interface web écoute (par défaut `0.0.0.0`, toutes les interfaces). Laissez-la non définie dans le conteneur, dont les ports publiés ont besoin de toutes les interfaces. `127.0.0.1` convient pour un lancement hors de Docker. Le contrôle de santé interroge la même adresse. |
| `TRUSTED_PROXY` | Non | Adresses ou plages CIDR séparées par des virgules du reverse proxy placé devant BombVault (par exemple `192.168.20.11` ou `10.0.0.0/8`). `X-Forwarded-For` n'est cru que s'il vient de ces sauts, et le limiteur de connexions compte alors les échecs par client réel au lieu de mettre tous ceux qui sont derrière le proxy dans un seul panier. Non défini (le réglage par défaut), il ne fait confiance à personne : un en-tête cru sans condition laisserait n'importe quel appelant choisir son propre panier. |
| `HOST_SOURCE_ROOT` | Non | Le chemin de l'hôte monté comme **Host Data** (par défaut `/mnt`). BombVault traduit les sources de montages bind que Docker indique en chemins sous ce montage. Ne changez que si vous avez monté une autre racine de l'hôte. |
| `HOST_MOUNT_ROOT` | Non | L'endroit où Host Data est monté dans le conteneur (par défaut `/host/user`). Sur TrueNAS, Host Data est monté à son propre chemin d'hôte, donc celui-ci et `HOST_SOURCE_ROOT` nomment tous deux ce chemin, par exemple `/mnt/tank` (voir [TrueNAS SCALE](getting-started.md#truenas)). |
| `DATA_ROOT_SEGMENTS` | Non | Noms de segments de chemin séparés par des virgules qui désignent une source de montage bind comme données à sauvegarder (par défaut `appdata`, selon la convention `/mnt/user/appdata/<container>` d'Unraid). Un montage bind de conteneur est sélectionné automatiquement pour la sauvegarde quand N'IMPORTE QUEL segment listé apparaît comme segment de chemin complet de sa source sur l'hôte. Par exemple, `DATA_ROOT_SEGMENTS=appdata,config` prend aussi en compte un bind `.../config`. La comparaison ignore la casse, donc le réglage par défaut couvre aussi le `/DATA/AppData/<container>` de ZimaOS. Voir [Détection des sources de sauvegarde](#backup-source-detection) pour les autres façons, toujours actives, de trouver le dossier de données d'un conteneur. |
| `PLATFORM` | Non | Force la plateforme sur laquelle BombVault se croit exécuté, au lieu de la détecter : `unraid`, `generic` ou `truenas` (non défini par défaut : détecte Unraid en cherchant son marqueur `dockerMan` sous le montage flash, sinon `generic`. Une valeur non reconnue retombe aussi sur `generic`, avec une entrée dans le journal). Réglez-le explicitement sur un hôte Docker générique ou TrueNAS Scale plutôt que de compter sur la détection réservée à Unraid. Le fichier compose générique le fait. Change la convention de repli pour appdata, les valeurs par défaut des destinations de restauration entre instances, et si les étapes de notification et de plugin compagnon propres à Unraid sont tentées (voir `internal/platform`). |
| `BOMBVAULT_SELF_CONTAINER` | Non | Le nom du conteneur BombVault lui-même, pour qu'il ne se sauvegarde jamais (et donc ne s'arrête jamais) lui-même. |
| `BACKUP_MAX_HOURS` | Non | Nombre maximal d'heures d'horloge qu'une exécution de sauvegarde peut garder le verrou de sa section avant d'être annulée de force (une garde pour qu'une exécution bloquée ne bloque pas la section indéfiniment). Vide (le réglage par défaut), c'est `48`. Augmentez-le pour de très grosses sauvegardes ou des sauvegardes lentes vers le cloud (une exécution annulée à la limite échoue avec `context deadline exceeded`). Mettez `0` pour supprimer complètement la limite. Un élagage est soumis à la même limite, et une vérification ou un élagage dure tant que restic continue d'indiquer une progression. |
| `BACKUP_STALL_HOURS` | Non | Nombre d'heures pendant lesquelles une sauvegarde peut ne faire **aucun progrès** avant d'être annulée. Vide (le réglage par défaut), c'est `2`. Mettez `0` pour ne jamais annuler sur un blocage. C'est la plus fine des deux gardes et généralement celle qui se déclenche : elle regarde si quelque chose se passe encore plutôt que le temps déjà pris, si bien qu'une sauvegarde lente mais saine de plusieurs téraoctets est laissée tranquille alors qu'une sauvegarde bloquée sur un partage qui ne répond plus est arrêtée en quelques heures au lieu de quelques jours. Un avertissement est écrit dans le journal après 30 minutes de silence, avant toute annulation. L'analyse compte comme un progrès : restic n'écrit aucun octet pendant qu'il parcourt une grande arborescence, et cette phase est suivie par ses totaux de fichiers et d'octets plutôt que par les octets écrits. Les deux variables sont indépendantes, et `BACKUP_MAX_HOURS` borne toujours les phases après la sauvegarde elle-même (rétention, statistiques, copie hors site), où il n'y a pas de compteurs à surveiller. |
| `DB_DUMP_MAX_HOURS` | Non | Nombre d'heures pendant lesquelles un dump automatique de base de données peut tourner avant d'être arrêté. Vide (le réglage par défaut), c'est `6`. Les valeurs autorisées vont de `1` à `48`, et la limite reste une heure sous `BACKUP_MAX_HOURS` (à la moitié de celle-ci quand elle est inférieure à deux heures), si bien qu'un long dump est coupé par sa propre limite et signalé comme tel au lieu d'entraîner la sauvegarde avec lui. Un dump qui ne progresse pas est arrêté plus tôt, après `BACKUP_STALL_HOURS`. Un dump arrêté échoue seul et la sauvegarde du conteneur continue. Sur Unraid, ajoutez-la au conteneur BombVault avec **Add another Path, Port, Variable**. |
| `TZ` | Non | Fuseau horaire du planificateur (par exemple `Europe/Paris`). **Laissée non définie, chaque planning s'exécute en UTC** : un planning réglé sur 02:30 se déclenche alors à 02:30 UTC et non à l'heure de votre horloge. Sur Unraid, vous ne la réglez jamais vous-même : le système transmet son propre fuseau horaire à chaque conteneur. Le journal de démarrage dit quel fuseau a été retenu. Un fuseau avec heure d'été saute une exécution au printemps et en lance une deux fois en automne, alors qu'UTC ne fait ni l'un ni l'autre mais dérive d'une heure par rapport à votre horloge deux fois par an. |
| `DATA_DIR` | Non | L'endroit où BombVault garde sa base de données, ses clés et ses caches (par défaut `/config`). N'y touchez pas dans le conteneur. Cela compte quand vous lancez le binaire hors de Docker. |
| `FLASH_DIR`, `FLASH_TEMPLATES_DIR` | Non | L'endroit où la clé flash et ses modèles Docker sont montés dans le conteneur (par défaut `/host/boot` et `/host/boot/config/plugins/dockerMan/templates-user`). Ils suivent le montage `/boot` du modèle, laissez-les donc non définis. |

## Montages {#mounts}

Montez le socket Docker, la clé flash (`/boot`) et la racine **Host Data** (`/mnt`) comme dans le modèle CA. Les *sources* et les *destinations* de sauvegarde vivent toutes deux sous Host Data, et il est monté en **slave** pour qu'un partage distant monté après le démarrage du conteneur (par exemple sous `/mnt/remotes`) devienne visible sans redémarrage.

Sur TrueNAS, Host Data est un chemin de dataset comme `/mnt/tank`, jamais un ixVolume. Les données qu'une application garde dans un ixVolume sont en dehors et ne sont pas sauvegardées. Voir [TrueNAS SCALE](getting-started.md#truenas).

Les sauvegardes de jeux de données ZFS ont aussi besoin de ce mode : l'hôte ne monte l'instantané d'un jeu de données qu'après le démarrage du conteneur. Voir [Jeux de données ZFS](zfs-datasets.md).

Les dépôts locaux sont par défaut sous `/mnt/user/bombvault/{container,vms,flash,config,files,zfs}`, créés à la première sauvegarde. Ce sont les **dossiers propres** des sections et ils forment la destination **Local**. Sur sa page sous **Destinations**, la carte **Connexion** change le dossier de chaque section.

Le dossier propre d'une section peut aussi se trouver dans une destination que vous avez déjà, comme un NAS ou un bucket S3 : **Utiliser comme dossier propre** sur la page de cette destination l'y déplace et dit d'abord ce qu'il advient des sauvegardes déjà faites. Voir [Le dossier propre d'une section](offsite-recovery.md#own-folder).

Les dossiers des dépôts locaux restent aux modes `0755` et `0644`, pour qu'un utilisateur de synchronisation non root via SMB ne soit pas bloqué, et les dépôts sont chiffrés, ce qui n'expose donc rien. Les définitions de récupération vivent dans chaque dépôt, si bien qu'un dossier copié est complet à lui seul. Le dépôt de l'auto-sauvegarde reste lisible par root seulement.

!!! note "Contrôle de l'intégration à l'hôte"
    La carte **Intégration hôte** de l'aperçu (ajoutez-la sous **Personnaliser**) sonde chaque montage et chaque CLI (socket Docker, libvirt, restic, qemu-img, rclone) et signale les éléments manquants.

## Détection des sources de sauvegarde {#backup-source-detection}

Pour chaque conteneur, BombVault sélectionne automatiquement les montages bind et les volumes nommés à sauvegarder. Un chemin est retenu quand l'une des conditions suivantes s'applique (vous pouvez toujours corriger le résultat dans la carte **Dossiers à sauvegarder** de l'onglet Paramètres du conteneur) :

- **Correspondance avec un segment de racine de données :** la source du bind sur l'hôte contient l'un des segments de `DATA_ROOT_SEGMENTS` comme composant de chemin complet (par défaut `appdata` seulement).
- **Les volumes nommés Docker** sont toujours inclus, car ils n'ont pas d'équivalent jetable et il n'y a rien à filtrer, **mais seulement quand le vrai chemin de stockage du volume sur l'hôte est lui-même accessible via le montage Host Data**, exactement comme tout autre chemin d'hôte que BombVault sauvegarde. Le pilote de volumes local par défaut de Docker stocke un volume sous la propre racine de données du démon (`/var/lib/docker/volumes/<name>/_data` sauf personnalisation. Vérifiez avec `docker info -f '{{.DockerRootDir}}'`), qui n'est pas couverte par le montage Host Data étroit à répertoire unique que le `docker-compose.yml` générique utilise par défaut. Un volume inaccessible est ignoré en silence, ce n'est pas une erreur. Pour sauvegarder réellement des volumes nommés sur un hôte générique, pointez Host Data (et `HOST_SOURCE_ROOT`) vers un ancêtre commun qui couvre aussi la racine de données de Docker. Le commentaire sur Host Data dans le fichier compose explique le compromis (Unraid contourne cela en montant tout `/mnt`, sa propre convention universelle de niveau supérieur, pour la même raison).
- **Répertoire du projet Docker Compose :** si le conteneur porte l'étiquette standard `com.docker.compose.project.working_dir` (posée automatiquement par `docker compose up`), ce répertoire est ajouté aussi, que l'un des binds ait ou non correspondu à un segment de racine de données.
- **Remplacement par l'étiquette `bombvault.data` :** mettez l'étiquette `bombvault.data=true` sur un conteneur pour inclure tous ses montages bind, pour une disposition qu'aucune des deux conventions ci-dessus ne détecte (par exemple un seul bind `/srv/plex/config` sans projet Compose). Toute valeur non vide autre que `false` compte comme vraie. Une étiquette absente ou `bombvault.data=false` ne change rien.
- **Étiquette `bombvault.dbdump` :** mettez `bombvault.dbdump=false` sur un conteneur pour désactiver son dump automatique de base de données (`0`, `no` et `off` font de même), ou nommez le moteur (`postgres`, `mysql`, `mariadb`) pour exporter un conteneur que BombVault ne reconnaît pas tout seul. L'étiquette l'emporte sur l'interrupteur de la carte **Base de données** de l'onglet Paramètres du conteneur, qui est la façon de faire sur Unraid.

## Modèle de sécurité {#security-model}

!!! warning "Contrôle équivalent à root sur l'hôte"
    Via le socket Docker, BombVault peut arrêter, supprimer et recréer des conteneurs et lire et écrire appdata, et pour la sauvegarde de VM il se connecte à l'hôte via SSH (`qemu+ssh://`, root par défaut) pour exécuter `virsh`. Toute personne qui peut atteindre son interface web a en pratique root sur l'hôte.

### Connexion {#login}

- **Protection par mot de passe facultative** (carte **Mot de passe** sous **Paramètres, Sécurité**) : définissez un mot de passe pour exiger une connexion, effacez-le pour la désactiver. Désactivée par défaut pour un usage sur un réseau local de confiance. Le mot de passe est stocké avec Argon2id sur un poivre dérivé de `APP_KEY`, si bien qu'un `/config` copié est sans valeur sans la clé et lent à attaquer avec elle. Un nouveau mot de passe demande au moins 12 caractères. Un mot de passe existant plus court continue de fonctionner jusqu'à ce qu'il soit changé. Les sessions sont signées (HMAC dérivé de `APP_KEY`) et changer le mot de passe les invalide. Les connexions sont limitées à cinq échecs par minute et par client. Changer ou effacer le mot de passe demande le **Mot de passe actuel** et, avec l'authentification à deux facteurs, le code.
- **Certaines actions exigent un mot de passe.** Le téléchargement du kit de récupération, du rapport de bug et du ZIP d'une sauvegarde flash, l'export d'une sauvegarde flash ou d'une auto-sauvegarde, le dépôt de la clé chez un gardien, l'autorisation de remettre un dépôt, la création d'un nouveau code de récupération, l'export de réglages avec identifiants, l'authentification à deux facteurs et les clés d'accès sont refusés tant qu'aucun mot de passe de connexion n'est défini, et ils demandent une connexion sur l'instance elle-même. Supprimer des sauvegardes fonctionne sans mot de passe. Si un mot de passe est défini, cela demande aussi cette connexion.
- **Une destination ne montre aucun mot de passe.** Une destination peut contenir des identifiants, comme dans `rest:https://user:password@host/repo`, et chaque page et chaque réponse de l'API l'affichent sous la forme `rest:https://[redacted]@host/repo`, avec ou sans mot de passe de connexion. Si vous changez le chemin derrière, le mot de passe enregistré reste. Pour faire pointer la destination vers un autre serveur, saisissez la destination entière avec son mot de passe, car un mot de passe masqué reste lié à son serveur.
- **Authentification à deux facteurs** (**Paramètres, Sécurité**) : un code temporel d'une application d'authentification en plus du mot de passe, plus huit codes de récupération à usage unique remis une seule fois à l'activation. Le secret partagé est stocké chiffré avec `APP_KEY`, et désactiver le facteur demande un code valide.
- Les **Clés d'accès** (WebAuthn) ont leur propre carte dès qu'un mot de passe est défini, en plus du mot de passe et jamais à sa place, si bien que retirer toutes les clés d'accès ne verrouille personne. Elles demandent un vrai nom de domaine et un certificat que le navigateur approuve. Le `https://<ip>:3443` par défaut est exactement ce que WebAuthn refuse, et la carte le dit au lieu de proposer un bouton qui échoue. Avec l'authentification à deux facteurs activée, une clé d'accès doit vérifier votre code PIN, votre empreinte ou votre visage, sinon la connexion demande aussi le code.
- **Une restauration de configuration** (**Restaurer les réglages** dans l'assistant d'urgence) met fin à toutes les sessions, supprime toutes les clés d'accès et révoque tous les jetons d'API et toutes les clés MCP, car les réglages restaurés pourraient ramener des éléments supprimés après leur enregistrement. Connectez-vous avec le mot de passe et configurez de nouveau vos clés d'accès sous **Paramètres, Sécurité**.
- **Un mot de passe oublié** se réinitialise sur la page de connexion. **Mot de passe oublié ?** fait écrire par BombVault un code de 12 caractères, en trois groupes de quatre, dans le journal de son conteneur (sur Unraid : onglet Docker, icône BombVault, **Journaux**). Ce code et un nouveau mot de passe vous connectent. La réinitialisation désactive aussi l'authentification à deux facteurs, supprime toutes les clés d'accès, révoque tous les jetons d'API, toutes les clés MCP et toutes les connexions OAuth, met fin à toutes les autres sessions, déconnecte tous les téléphones appairés et désactive l'appairage des téléphones. La page liste ensuite ce qui a disparu. Un code est valable 10 minutes, et les mauvaises tentatives ne l'usent pas. Les jetons du widget et des métriques restent, puisqu'ils ne font que lire.
- **Toute personne qui peut lire le journal du conteneur peut réinitialiser le mot de passe.** C'est root sur l'hôte, mais aussi un afficheur de journaux comme Dozzle, tout conteneur auquel on a donné le socket Docker (en lecture seule suffit) et un expéditeur de journaux qui transmet la sortie des conteneurs. Ne donnez cela qu'à des personnes à qui vous confieriez le mot de passe. Quelqu'un qui n'atteint que l'interface web ne voit jamais le code.

### Téléphones et membres du groupe {#phones-and-members}

- **Les téléphones appairés atteignent une liste autorisée.** Un téléphone qui connaît les douze mots du groupe se connecte sans le mot de passe, tant que **Les téléphones peuvent s'appairer avec les douze mots du groupe** est activé dans la carte **Application Android** sous **Paramètres, Sécurité**. Sa session n'atteint que ce que montre l'application : l'aperçu, les exécutions, les sauvegardes à consulter, à lancer et à restaurer, les anomalies à lire et la page Instances à consulter. Les destinations et les commandes lui parviennent sans leurs adresses ni leurs secrets, et une restauration qui remplace l'original sauvegarde d'abord l'état actuel. Une restauration dans un dossier n'accepte qu'un dossier nouveau ou vide à l'intérieur du dossier de restauration, et un téléphone ne peut regarder dans aucun autre dossier. Tout le reste répond qu'il faut une connexion sur l'instance elle-même : clés, kit de récupération, dépôts de clés, réglages, suppression de sauvegardes. Une réinitialisation du mot de passe désactive l'appairage des téléphones jusqu'à ce que vous le réactiviez. Un téléphone retiré de la page Instances, ou dont **Interroger cette instance** est désactivé dans ses détails, perd sa session aussitôt, et un téléphone retiré qui rouvre son application revient désactivé.
- **Hors de chez soi, un téléphone ouvre les pages via le relais.** Chaque requête de la page est scellée avec la clé du groupe, que le relais ne peut ni lire ni modifier, et signée avec une clé propre au téléphone que le serveur a épinglée la première fois qu'il l'a demandée au téléphone. Le serveur exécute une requête une seule fois et seulement si elle est récente. Il ne répond qu'à un téléphone listé sur la page Instances tant que l'appairage des téléphones est activé, et seulement avec une session qu'il a donnée à ce téléphone, si bien que se déconnecter partout et réinitialiser le mot de passe mettent aussi fin à ces pages. Le serveur signe chaque réponse, et l'application vérifie la signature d'après la clé qu'elle a épinglée pour ce serveur et prévient quand la clé change. Une telle page atteint la même liste autorisée qu'un téléphone appairé, avec ou sans mot de passe de connexion, plus l'état de connexion que la page lit en premier. La connexion et la déconnexion, la réinitialisation du mot de passe et les téléchargements restent à l'adresse propre du serveur, et une réponse est plafonnée à 16 MB.
- **Les membres signent ce qu'ils demandent.** Les demandes de rôle et leurs réponses, les offres de stockage, la remise d'un mot de passe restic à un récepteur ou à un récupérateur, les connexions des récepteurs et les dépôts de clés sont signés avec une clé propre à chaque membre, qu'une instance épingle la première fois qu'elle voit ce membre. Un appel signé avec une autre clé est refusé. **Oublier la clé** dans les détails d'une instance abandonne la clé épinglée, au cas où celle qui est connue ici n'est pas la propre clé du membre. On redemande alors sa clé au membre à son prochain appel signé. Les membres sous BombVault 9.x ne signent pas et peuvent être usurpés par toute personne qui connaît les mots, comme dans la 9.9. Une demande de rôle ou une offre de stockage d'un membre sous 10.4 ou une version plus ancienne est refusée jusqu'à ce que ce membre soit mis à jour.
- **Les douze mots sont un mot de passe.** Toute personne qui les a rejoint le groupe, voit l'état de protection des membres et peut demander des rôles, qu'une personne sur l'autre instance doit encore autoriser. Sans mot de passe de connexion, toute personne qui peut ouvrir l'interface web peut les lire, et la carte d'appairage le dit tant qu'aucun mot de passe n'est défini.

### Clés {#keys}

- **APP_KEY fait deux choses.** Elle scelle ce que cette installation stocke (mots de passe, identifiants, jetons) et c'est la clé des sauvegardes : le mot de passe restic en est dérivé, et les définitions de conteneurs et de VM sont scellées avec elle.
- **Une clé reprise est gardée à part.** Quand l'assistant d'urgence reprend les sauvegardes d'un autre serveur, cette installation continue de sceller avec sa propre APP_KEY et stocke la clé de l'autre serveur comme sa **clé de sauvegarde**, scellée comme tout autre secret. Le kit de récupération imprime alors les deux. Si APP_KEY est changée ensuite, la clé de sauvegarde ne peut plus être ouverte : BombVault cesse de sauvegarder et le dit sous **À traiter**, au lieu d'écrire avec la mauvaise clé. Téléversez de nouveau le kit de récupération sous **Restauration, Urgence**, ou remettez APP_KEY en place. Voir [Assistant d'urgence](offsite-recovery.md#emergency).
- Le **Chiffrement** est activé par défaut (**Chiffrer les sauvegardes** dans la carte **Chiffrement** sous **Paramètres, Sécurité**). Les sauvegardes sont chiffrées par restic avec le mot de passe dérivé de la clé de sauvegarde.
- **Dépôts de clés.** Un gardien de votre groupe détient une copie scellée du kit de récupération de ce serveur qu'il ne peut pas ouvrir lui-même. Seul le code de récupération de 20 caractères l'ouvre, et le gardien ne le remet qu'après que quelqu'un là-bas a appuyé sur **Autoriser**. Voir [Gardien](offsite-recovery.md#key-keeper).

### Réseau {#network}

- **Les modifications demandent du JSON.** Une requête qui modifie quelque chose doit envoyer `Content-Type: application/json` et ne doit pas être marquée inter-sites par le navigateur, si bien qu'une page d'un autre site ne peut pas faire modifier des réglages par votre navigateur à une adresse du réseau local. Un script qui pilote l'API envoie cet en-tête. Tout le reste est refusé avec `415`.
- Comme la protection est facultative, quand elle n'est pas définie, toute l'interface et toute l'API (y compris les destinations, les routes de test d'altération et les routes de restauration) sont accessibles à toute personne qui atteint le port. Définissez un mot de passe de connexion dès que des sauvegardes hors site, en ajout seul, ou le chiffrement sont utilisés.
- N'exécutez BombVault que sur un réseau de confiance et non exposé. Pour l'accès à distance, placez-le derrière un reverse proxy qui ajoute l'authentification et le TLS. Les réponses portent des en-têtes de sécurité de base (CSP, `nosniff`, `X-Frame-Options`, `Referrer-Policy`).
- Derrière un reverse proxy, chaque requête porte l'adresse du proxy, si bien que sans `TRUSTED_PROXY` le limiteur de connexions compte tous les clients dans un seul panier et les échecs d'un attaquant vous bloquent aussi. Nommez le proxy dans `TRUSTED_PROXY` pour retrouver le comptage par client.
- Un reverse proxy placé devant BombVault doit transmettre l'en-tête `Authorization` ou `X-API-Key` vers `/mcp` et ne doit pas mettre ses réponses en mémoire tampon, sinon les assistants ne peuvent pas se connecter. Voir [Serveur MCP](mcp.md#tls).
- Le point d'accès MCP `/mcp` répond `404` tant qu'aucune clé n'existe ou que la connexion via OAuth n'est pas activée, et il demande à chaque client sa clé ou son jeton même avec le mot de passe de connexion désactivé. Aucune adresse n'est exemptée, pas même `localhost`. Il n'a ni outil de restauration ni outil de suppression, et restaurer une sauvegarde de configuration révoque toutes les clés. Voir [Serveur MCP](mcp.md#security).
- Avec `HTTP_ONLY=true`, le cookie de session perd son drapeau `Secure` (il le faut pour fonctionner en HTTP simple), n'activez donc le mot de passe que derrière un proxy qui termine le TLS si la confidentialité compte.
- La connexion SSH de sauvegarde de VM fait confiance à la clé de l'hôte à la première connexion (TOFU) et l'épingle ensuite. Vérifiez la clé de l'hôte par un autre canal si le chemin du conteneur à l'hôte n'est pas sûr.
- **Les liens ne mènent pas hors du montage.** Une sauvegarde ou une restauration sur place s'arrête avec un message quand un lien au-dessus de son chemin mène hors du montage de l'hôte, car un conteneur qui écrit dans son propre partage pourrait en placer un. Une destination dont l'hôte ou le remote rclone commence par un tiret est refusée de la même manière, à l'enregistrement et à l'exécution suivante, car `ssh` ou `rclone` le liraient comme une option.

## Serveur MCP {#mcp-server}

Le serveur MCP n'a besoin d'aucune variable d'environnement. Vous l'activez en créant une clé sous **Paramètres, Intégrations, Serveur MCP**, et il répond sur `/mcp` au même port que l'interface web (par exemple `https://192.168.1.10:3443/mcp`). Sans clé active, ce chemin répond `404`. Les clients, les certificats et les limites sont décrits sur [Serveur MCP](mcp.md).

## Sauvegarde de VM via SSH {#vm-backup-over-ssh}

BombVault sauvegarde les VMs KVM/libvirt **sans monter aucun chemin libvirt**. Il exécute `virsh` sur l'hôte via SSH (`qemu+ssh://`), si bien qu'il ne peut jamais affecter le gestionnaire de VM de votre hôte.

Monter le socket libvirt de l'hôte dans un conteneur est fragile sur Unraid : le gestionnaire de VM possède ces chemins, et basculer « Enable VMs » peut empêcher libvirt de démarrer. La clé SSH donne root sur l'hôte, le même niveau de confiance que le socket Docker que BombVault utilise déjà.

Mise en place rapide :

1. **Paramètres, Intégrations, SSH de l'hôte :** copiez la clé publique affichée.
2. Ajoutez-la au fichier `/root/.ssh/authorized_keys` d'Unraid (conservée aussi sur la clé flash pour survivre aux redémarrages).
3. Cliquez sur **Tester la connexion**.

Le modèle ajoute `--add-host=host.docker.internal:host-gateway` pour que le conteneur puisse joindre l'hôte. Réglez `LIBVIRT_HOST` sur l'IP de votre Unraid sur le réseau local si ce nom ne se résout pas (par exemple quand le conteneur tourne sur un réseau personnalisé `br0.x`). Si vous avez changé le port SSH d'Unraid, réglez `LIBVIRT_SSH_PORT` en conséquence. Les **instantanés à chaud** demandent aussi l'agent invité qemu dans la VM et le disque sur `/mnt/cache` (pas `/mnt/user`).

!!! important "Guide complet de la VM et du réseau"
    Le guide complet pas à pas (activation de SSH, autorisation persistante de la clé, routage réseau personnalisé et VLAN, méthode par VM et dépannage côté hôte) est le [guide des sauvegardes de VM](vm-backup-ssh-setup.md).

## Configuration hors site {#off-site-setup}

Les copies hors site vont vers des **destinations**. Ouvrez **Destinations** depuis sa tuile de paramètres (ou épinglez-la à la barre latérale) et choisissez **Ajouter une destination**. Voir [Hors site et récupération](offsite-recovery.md) pour le déroulement complet (protection contre la suppression, tests d'altération et exercices de reprise après sinistre). En bref :

- **Moteurs :** SMB/CIFS et WebDAV via rclone sans montage sur l'hôte, NFS (montez l'export sur l'hôte et utilisez-le comme dossier local), moteurs restic natifs sans rclone (`s3:...`, `rest:http://host:8000/repo`, `sftp:user@host:/repo`), ou tout remote rclone (`rclone:<remote>:<bucket>/path`). Backblaze B2 n'a pas de moteur natif ici : joignez-le par son point d'accès S3 (`s3:https://s3.<region>.backblazeb2.com/<bucket>/<path>`) avec l'ID de clé et la clé d'application comme identifiants S3.
- **Les identifiants** sont stockés chiffrés, comme une seule liste d'identifiants enregistrés dans la carte **Identifiants** sous **Paramètres, Destinations**. Une étoile marque celui par défaut, utilisé partout où aucun identifiant n'est choisi. La page propre à une destination choisit celui qu'elle utilise dans sa carte **Identifiants**. Voir [Identifiants](offsite-recovery.md#sign-ins).
- **Les cibles SSH n'ont besoin de rien d'installé de l'autre côté.** `sftp:` n'a besoin que d'un serveur SSH. Ajoutez la clé publique de **Paramètres, Intégrations, SSH de l'hôte** (aussi dans `/config/ssh/id_ed25519.pub`) au `~/.ssh/authorized_keys` de l'utilisateur cible, ou laissez **Ajouter la clé** dans **Ajouter une destination** l'y placer avec le mot de passe du compte.
- **rest-server avec un certificat autosigné :** placez son certificat, ou celui de l'autorité qui l'a signé, comme fichier PEM dans le dossier `certs` du dossier de données de BombVault (`/config/certs` dans le conteneur, `appdata/bombvault/certs` sur Unraid). Les sauvegardes, les copies et le test de protection contre la suppression lui font confiance sans redémarrage.
- **Copie hors site :** BombVault copie les nouveaux instantanés avec `restic copy` au mieux, en plus d'un dépôt principal (généralement local). La carte **Copier** d'une destination règle si elle copie **Après chaque sauvegarde** ou selon un plan à elle, et **Paramètres, Planning, Copies hors site par section** donne à une section son propre plan de copie. **Répliquer maintenant** se trouve dans la ligne de la section, dans la carte **Copies hors site** sous **Paramètres, Destinations**.
- **Plusieurs destinations par section :** la carte **Destinations par section** de la page Destinations active ou désactive d'un clic chaque ligne d'une section vers une destination, **Local** compris. Une section qui n'a que des destinations hors site sauvegarde directement vers elles, et une section dont toutes les lignes sont désactivées n'est pas sauvegardée. Les **Règles par section** d'une destination donnent à une section son propre dépôt, sa propre rétention ou sa propre compression là-bas.
- **Destinations par élément :** chaque conteneur, VM et ensemble de dossiers allume **Local** et les destinations qui reçoivent ses sauvegardes, dans la carte **Planning et destination** de son onglet Paramètres. Les éléments sans choix propre suivent leur section. Voir [Destinations par élément](offsite-recovery.md#placement).
- **Rétention :** chaque destination garde les sauvegardes selon sa carte **Durée de conservation**, et une section peut y garder ses propres valeurs sous **Règles par section**. Cela inclut la copie dans le champ hors site d'une section. Tout à zéro ne taille jamais les instantanés d'une destination.
- **Limites de bande passante :** plafonnez le débit d'envoi et de téléchargement de restic dans la carte **Bande passante hors site** sous **Paramètres, Destinations**, ou par destination dans sa carte **Copier**. Vous saisissez des KiB/s, et le champ montre le même débit en MB/s et en Mbit/s.
- **Le streaming d'abord :** dans la carte **Streaming** de la page Destinations, choisissez les serveurs multimédias (Plex, Jellyfin et Emby sont présélectionnés d'après le nom de l'image), le débit d'envoi à partir duquel on compte un streaming, la limite d'envoi pendant qu'il a lieu et le délai après un streaming au bout duquel la limite normale revient.
- **Classe de stockage froid et d'archivage (S3) :** pour une destination S3, choisissez sur sa page un niveau lisible à la restauration (Standard, Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier Instant Retrieval). Les remotes rclone règlent leur classe dans la configuration rclone.
- **Dossier propre dans une destination au lieu du local :** le dossier propre d'une section peut se trouver dans l'une des destinations ci-dessus, sans copie locale et sans étape de copie. Voir [Le dossier propre d'une section](offsite-recovery.md#own-folder).

## Anomalies {#anomalies}

La détection d'anomalies n'a besoin d'aucune variable d'environnement. Elle se règle dans la carte **Anomalies** sous **Paramètres, Vérification**, décrite sur [Anomalies](anomalies.md#settings).

## Réglages portables (export et import) {#portable-settings-export-and-import}

La carte **Exporter / importer les paramètres** sous **Paramètres, Système** écrit toute votre configuration BombVault (réglages des sections, destinations, plannings, rétention, notifications) dans un fichier JSON portable que vous pouvez importer sur une autre instance, si bien que passer à un nouveau serveur ou cloner une installation n'oblige pas à tout ressaisir à la main. L'import montre un aperçu et demande confirmation, et il ne touche jamais à vos données de sauvegarde ni à l'historique. Les liens du fichier vers des destinations ou des dépôts qui n'existent plus sont omis, et l'aperçu les nomme. Pendant qu'une réplique ZFS tourne, un import est refusé avant que quoi que ce soit soit écrit.

!!! warning "L'export peut contenir des identifiants"
    Vous choisissez d'inclure ou non dans le fichier les identifiants hors site, de notification et du broker MQTT. Avec les identifiants, l'export est aussi sensible que votre kit de récupération, conservez-le donc en lieu sûr. Sans eux, le fichier ne contient que des réglages non secrets.

!!! warning "L'APP_KEY ne voyage pas avec le fichier"
    Les dépôts sont verrouillés avec un mot de passe dérivé de l'`APP_KEY`, et le fichier ne la contient pas. Pour un déménagement prévu, donnez à la nouvelle machine l'ancienne `APP_KEY` dans son modèle, ou reprenez la clé avec le kit de récupération sous **Urgence**. Avec une autre clé, les dépôts répondent que le mot de passe est faux. Rien n'est perdu, et définir la bonne clé les ouvre de nouveau.
